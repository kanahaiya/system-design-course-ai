Tier 1 — Must Know 45 min

Design Uber / Ride Sharing

Design a ride-sharing platform that matches riders to nearby drivers in real-time using geospatial indexing, with live location tracking, fare estimation, and trip management at 10M trips/day scale.

🏢 Uber, Lyft, DoorDash, Google Maps
⏱️ 45 min

R — Requirements

Functional Requirements

  • Match riders to the nearest available driver within 3 seconds
  • Drivers continuously broadcast their location every 4 seconds
  • Fare estimation before confirming a ride
  • Real-time trip tracking for both rider and driver
  • Support vehicle types: economy, premium, XL

Non-Functional Requirements

  • Scale: 10M trips/day, 1M active drivers globally
  • Location write throughput: 1M drivers × 1 update/4s = 250,000 writes/second
  • Match latency: < 3 seconds from rider request to driver offer
  • Availability: 99.9% (≈ 8.7 hours downtime/year tolerable)
  • GPS accuracy: within 10 meters
Interviewer signal: The 250K location writes/second is the hardest constraint. Everything else (trips, fare) is normal CRUD. Focus your design on making the geospatial writes fast and the proximity query cheap.

E — Estimation

The location data for 1M drivers fits easily in a single Redis instance (100MB). The bottleneck is write throughput at 250K/s — we need Redis pipeline writes and a cluster with multiple shards.

S — Schema

-- MySQL: persistent data
CREATE TABLE drivers (
    driver_id    BIGINT PRIMARY KEY,
    name         VARCHAR(100),
    vehicle_type ENUM('ECONOMY','PREMIUM','XL'),
    status       ENUM('OFFLINE','AVAILABLE','ON_TRIP') DEFAULT 'OFFLINE',
    last_updated TIMESTAMP
);

CREATE TABLE trips (
    trip_id     BIGINT PRIMARY KEY AUTO_INCREMENT,
    rider_id    BIGINT NOT NULL,
    driver_id   BIGINT,
    status      ENUM('REQUESTED','MATCHING','ACTIVE','COMPLETED','CANCELLED'),
    origin_lat  DECIMAL(9,6),
    origin_lng  DECIMAL(9,6),
    dest_lat    DECIMAL(9,6),
    dest_lng    DECIMAL(9,6),
    fare_cents  INT,
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_rider (rider_id),
    INDEX idx_driver (driver_id)
);

-- Redis: live location index (NOT stored in MySQL)
-- GEOADD driver_locations <lng> <lat> <driver_id>
-- GEORADIUS driver_locations <lng> <lat> 5 km ASC COUNT 10
Why Redis for location? MySQL spatial indexes work for millions of static records but cannot handle 250K writes/second. Redis GEORADIUS runs O(N+log(M)) where M is the sorted set size — fast enough for real-time proximity queries.

Figure: Uber geo-grid — Rider (R) in center cell, search 9 surrounding cells for Drivers (D); Location Service writes GEOADD to Redis, Match Service queries GEORADIUS

  1. Driver App sends GPS coordinates every 4s to the Location Service via WebSocket or HTTP/2
  2. Location Service writes to Redis: GEOADD driver_locations {lng} {lat} {driver_id} and updates driver status in MySQL asynchronously
  3. Rider requests a trip → Matching Service calls GEORADIUS driver_locations {lng} {lat} 5 km ASC COUNT 10 filtered by vehicle type and AVAILABLE status
  4. Matching Service sends trip offer to first available driver via notification. If rejected or no response in 10s, tries next driver
  5. Trip Service creates trip record in MySQL, marks driver ON_TRIP in Redis
  6. Both apps receive real-time updates via WebSocket through a Notification/Push Service

D — Deep Dive: Geospatial Indexing

Geohash divides the Earth into a grid of rectangular cells. Each cell is identified by a base-32 string — longer string = smaller cell = higher precision. A 6-character geohash covers roughly 1.2km × 0.6km.

Nearby search algorithm: Take the driver's geohash prefix → find all 8 adjacent cells → query Redis for all drivers in those 9 cells. This is O(1) lookups rather than a full coordinate scan.

Redis implements this natively via a sorted set where the score is the geohash encoded as a 52-bit integer. GEORADIUS computes which geohash buckets to check and returns results sorted by distance.

Edge case — geohash boundary problem: A driver 100m away on the other side of a geohash boundary has a completely different prefix. Always query the 8 surrounding cells, not just the current cell. Redis GEORADIUS handles this automatically.

E — Evaluate

  • 250K writes/sec: Redis single instance handles ~100K ops/sec. Use Redis Cluster with 4-8 shards, each handling ~60K ops/sec with headroom. Shard key = geohash prefix (geographic partitioning).
  • Match latency <3s: GEORADIUS on Redis is sub-millisecond. The bottleneck is network round-trips and driver notification. Use WebSocket persistent connections to eliminate reconnect overhead.
  • Driver goes offline mid-trip: Trip Service has a watchdog that monitors heartbeats. If driver location stops updating for 30s, escalate to support and notify rider.
  • Hot spots (airport, stadium): Many drivers in one geohash cell. GEORADIUS COUNT 10 limits results — add random jitter to avoid always picking the same top driver.

D — Deliver

The final architecture centers on Redis Geo Cluster as the real-time location backbone, with MySQL handling durable trip records. The two write paths (location updates vs trip creation) are fully decoupled.

Scaling path: Start with a single Redis instance → add read replicas for GEORADIUS queries → cluster when write throughput exceeds 80K/s per shard. Matching Service is stateless and scales horizontally behind a load balancer.

Trade-off Table

Java Implementation

/**
 * GeospatialMatchingService
 * Finds nearby available drivers using geohash-based spatial indexing.
 * In production this delegates to Redis GEORADIUS; shown here with
 * an in-process TreeMap for interview demonstration purposes.
 */
public class GeospatialMatchingService {

    private static final double EARTH_RADIUS_KM = 6371.0;
    private static final int GEOHASH_PRECISION = 6; // ~1.2km x 0.6km cells

    // In production: Jedis/Lettuce Redis client
    // Here: driver_id -> [lat, lng] for demo
    private final Map<Long, double[]> driverLocations = new ConcurrentHashMap<>();
    private final Map<Long, DriverStatus> driverStatus = new ConcurrentHashMap<>();

    public enum DriverStatus { AVAILABLE, ON_TRIP, OFFLINE }

    /**
     * Updates driver location. Called 250K times/second in production.
     * Thin wrapper around Redis GEOADD in real system.
     *
     * @param driverId  the driver's unique identifier
     * @param latitude  GPS latitude
     * @param longitude GPS longitude
     */
    public void updateDriverLocation(long driverId, double latitude, double longitude) {
        driverLocations.put(driverId, new double[]{latitude, longitude});
        // Redis equivalent: GEOADD driver_locations <lng> <lat> <driverId>
    }

    /**
     * Finds up to maxResults available drivers within radiusKm of origin.
     * Returns list sorted by distance ascending.
     *
     * @param originLat  rider's latitude
     * @param originLng  rider's longitude
     * @param radiusKm   search radius in kilometers
     * @param maxResults cap on returned drivers (avoid sending 1000 offers)
     * @return sorted list of (driverId, distanceKm) pairs
     */
    public List<DriverMatch> findNearbyDrivers(
            double originLat, double originLng,
            double radiusKm, int maxResults) {

        List<DriverMatch> candidates = new ArrayList<>();

        for (Map.Entry<Long, double[]> entry : driverLocations.entrySet()) {
            long driverId = entry.getKey();
            double[] coords = entry.getValue();

            if (driverStatus.get(driverId) != DriverStatus.AVAILABLE) {
                continue;
            }

            double distanceKm = haversineDistanceKm(
                originLat, originLng, coords[0], coords[1]
            );

            if (distanceKm <= radiusKm) {
                candidates.add(new DriverMatch(driverId, distanceKm));
            }
        }

        candidates.sort(Comparator.comparingDouble(match -> match.distanceKm));
        return candidates.subList(0, Math.min(maxResults, candidates.size()));
    }

    /**
     * Haversine formula — great-circle distance between two GPS points.
     * More accurate than Euclidean for distances over ~1km.
     */
    private double haversineDistanceKm(
            double lat1, double lng1, double lat2, double lng2) {

        double deltaLat = Math.toRadians(lat2 - lat1);
        double deltaLng = Math.toRadians(lng2 - lng1);
        double sinDeltaLat = Math.sin(deltaLat / 2);
        double sinDeltaLng = Math.sin(deltaLng / 2);

        double haversineAngle = sinDeltaLat * sinDeltaLat
            + Math.cos(Math.toRadians(lat1))
            * Math.cos(Math.toRadians(lat2))
            * sinDeltaLng * sinDeltaLng;

        return 2 * EARTH_RADIUS_KM * Math.asin(Math.sqrt(haversineAngle));
    }

    public record DriverMatch(long driverId, double distanceKm) {}
}

/**
 * TripMatchingOrchestrator
 * Coordinates the full matching flow: find drivers → offer → accept/reject loop.
 */
public class TripMatchingOrchestrator {

    private static final int MAX_OFFER_ATTEMPTS = 5;
    private static final int OFFER_TIMEOUT_SECONDS = 10;
    private static final double INITIAL_SEARCH_RADIUS_KM = 5.0;

    private final GeospatialMatchingService geoService;
    private final NotificationService notificationService;
    private final TripRepository tripRepository;

    public TripMatchingOrchestrator(
            GeospatialMatchingService geoService,
            NotificationService notificationService,
            TripRepository tripRepository) {
        this.geoService = geoService;
        this.notificationService = notificationService;
        this.tripRepository = tripRepository;
    }

    /**
     * Attempts to match a trip request to an available driver.
     * Expands search radius if initial radius yields no candidates.
     *
     * @param tripRequest the rider's trip request details
     * @return matched driver ID, or empty if no driver accepted within timeout
     */
    public Optional<Long> matchTrip(TripRequest tripRequest) {
        double searchRadiusKm = INITIAL_SEARCH_RADIUS_KM;

        for (int attempt = 0; attempt < MAX_OFFER_ATTEMPTS; attempt++) {
            List<GeospatialMatchingService.DriverMatch> nearbyDrivers =
                geoService.findNearbyDrivers(
                    tripRequest.originLat(), tripRequest.originLng(),
                    searchRadiusKm, 10
                );

            if (nearbyDrivers.isEmpty()) {
                searchRadiusKm *= 1.5; // expand and retry
                continue;
            }

            for (GeospatialMatchingService.DriverMatch candidate : nearbyDrivers) {
                boolean accepted = notificationService.offerTripAndWait(
                    candidate.driverId(), tripRequest, OFFER_TIMEOUT_SECONDS
                );

                if (accepted) {
                    tripRepository.assignDriver(tripRequest.tripId(), candidate.driverId());
                    return Optional.of(candidate.driverId());
                }
            }

            searchRadiusKm *= 1.5;
        }

        return Optional.empty(); // no driver found — surface "no cars available" to rider
    }

    public record TripRequest(
        long tripId, long riderId,
        double originLat, double originLng,
        double destLat, double destLng,
        String vehicleType
    ) {}
}
