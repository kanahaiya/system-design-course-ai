Tier 1 — Must Know 45 min

Design Dropbox / Cloud File Storage

Design a cloud file storage service for 500M users with 10PB storage, resumable chunked uploads for files up to 5GB, delta sync across devices within 30 seconds, S3 backend, and content-addressed deduplication.

🏢 Dropbox, Google Drive, OneDrive, Box, iCloud
⏱️ 45 min

R — Requirements

Functional Requirements

  • Upload files up to 5GB from any device
  • Download files on any linked device
  • Sync changes across all a user's devices within 30 seconds
  • Share files and folders with other users (view/edit permissions)
  • File versioning (keep last 30 versions)

Non-Functional Requirements

  • Scale: 500M users, 1B files total, 10PB storage
  • Upload resilience: resume interrupted uploads from last successful chunk
  • Sync latency: < 30s from file change to visible on other devices
  • Availability: 99.99% for sync service, 99.9% for upload/download
  • Deduplication: identical files (even across users) stored only once
The chunking question is always asked: How do you upload a 5GB file reliably over a slow or interrupted connection? Answer: split into 4MB chunks, hash each chunk, upload chunks in parallel, track which chunks succeeded, resume by uploading only missing chunks.

With deduplication, actual S3 storage is lower — studies show ~30% of files are identical across users (common documents, OS files). 10PB × 0.7 = 7PB effective. At 3x replication (S3 default): 21PB raw storage. At $0.023/GB this is ~$483K/month — a real cost consideration.

S — Schema

-- MySQL: file metadata and directory structure
CREATE TABLE files (
    file_id      BIGINT PRIMARY KEY AUTO_INCREMENT,
    owner_id     BIGINT NOT NULL,
    name         VARCHAR(255) NOT NULL,
    parent_id    BIGINT,                     -- NULL = root
    size_bytes   BIGINT NOT NULL,
    content_hash CHAR(64) NOT NULL,          -- SHA-256 of full file content
    storage_key  VARCHAR(512),               -- S3 key if small file
    version      INT DEFAULT 1,
    created_at   TIMESTAMP,
    updated_at   TIMESTAMP,
    is_deleted   BOOLEAN DEFAULT FALSE,
    INDEX idx_owner_parent (owner_id, parent_id),
    INDEX idx_content_hash (content_hash)     -- dedup lookup
);

CREATE TABLE file_chunks (
    chunk_id    BIGINT PRIMARY KEY AUTO_INCREMENT,
    file_id     BIGINT NOT NULL,
    chunk_index INT NOT NULL,                 -- 0-based sequence
    chunk_hash  CHAR(64) NOT NULL,            -- SHA-256 of this chunk
    storage_url VARCHAR(512) NOT NULL,        -- S3 URL for this chunk
    UNIQUE KEY uq_file_chunk (file_id, chunk_index)
);

-- Sync events log (Cassandra, append-only, partition by user_id)
CREATE TABLE sync_events (
    user_id     BIGINT,
    event_id    BIGINT,          -- monotonically increasing
    file_id     BIGINT,
    event_type  TEXT,            -- 'CREATED', 'MODIFIED', 'DELETED', 'MOVED'
    device_id   TEXT,
    occurred_at TIMESTAMP,
    PRIMARY KEY (user_id, event_id)
);

-- Content-addressable store dedup index
-- Key: content_hash (SHA-256)
-- Value: s3_key, ref_count
-- If content_hash already exists on upload: reuse S3 key (dedup!)

Upload flow: Client splits file into 4MB chunks → hashes each chunk → asks API which chunks are already stored (dedup check) → uploads only missing chunks to S3 → calls /files to commit the file record pointing to chunk S3 keys.

Sync flow: Other devices of the same user long-poll GET /sync?last_event_id=N. The Sync Service returns all events since N from the Cassandra event log. The client downloads only the changed chunks (delta sync).

Download flow: Client calls GET /files/{fileId} → gets list of chunk S3 URLs → downloads chunks in parallel → reassembles file. For small files (< 1MB), the file is stored as a single S3 object (no chunking overhead).

D — Deep Dive: Chunking for Large File Uploads

Why 4MB chunks? Smaller chunks (e.g., 256KB) = more S3 API calls, more overhead. Larger chunks (e.g., 16MB) = long retries on slow connections, less granular resume. 4MB balances throughput and retry granularity.

Resume on interruption: Client calls GET /uploads/{uploadId}/status → gets list of received chunks → resumes uploading only missing chunks. No need to restart from byte 0.

Delta sync: When a file is modified, only changed chunks are re-uploaded. A 1GB file where 1 page changes: 1 chunk (4MB) is uploaded instead of 1GB. Client computes chunk hashes locally and compares with the server's known chunk hashes for the previous version.

Content-addressed storage (dedup): SHA-256 hash of chunk content → if another user's file has the same chunk hash, reuse the same S3 object. The S3 key is the chunk hash. Reference counting tracks how many files use each chunk; GC deletes chunks with ref_count = 0.

Security consideration: Hash-based dedup means an attacker who knows a file's hash could potentially confirm its existence without uploading it. For sensitive files, use HMACs instead of plain SHA-256: HMAC(user_secret, content) — unique per user, preventing cross-user hash collisions from being exploited.

E — Evaluate

  • Concurrent edits on the same file from two devices: Device A and B both edit the same file offline. On reconnect, both try to upload. Second upload creates a conflict copy (e.g., "report (conflicted copy 2025-01-01).docx"). User manually resolves.
  • Large folder sync (100K files): Instead of long-polling one event at a time, paginate: return up to 1000 events per sync request. Client processes in batches.
  • Sync notification latency: Long-polling with 30s timeout means worst-case 30s delay. For near-real-time, use WebSockets or SSE (Server-Sent Events) for instant push on file change.
  • Chunk GC: When a file is deleted or versioned, its chunks may still be referenced by other files (dedup). GC only deletes S3 objects when ref_count drops to 0. Run GC as a nightly batch job scanning the chunks table.

D — Deliver

Dropbox's architecture cleanly separates the data plane (chunks in S3 — high throughput, globally distributed) from the metadata plane (MySQL for file structure, Cassandra for sync events — low latency, strongly consistent). This separation is the correct pattern for any large-scale file storage system.

The chunking strategy solves three problems at once: (1) resumable uploads for unreliable connections; (2) parallel uploads for better throughput on fast connections; (3) delta sync that uploads only changed chunks, reducing bandwidth for large files by 99%+ in the common case of small edits.

Trade-off Table

DecisionOption AOption BChosenWhy
Chunk size 4MB chunks 16MB chunks 4MB 16MB chunks are better for fast, stable connections but painful on slow/mobile: a single failure retries 16MB. 4MB balances retry cost with S3 API overhead (~1280 API calls for 5GB).
Sync mechanism Polling (GET /sync every N seconds) Long-polling (hold connection 30s) Long-polling (upgrade to WebSocket later) Regular polling at 5s intervals = 12 requests/minute/device with mostly empty responses. Long-polling reduces API calls by 10x. WebSocket is best for real-time but harder to scale.
Encryption Server-side encryption (S3 manages keys) Client-side encryption (user manages keys) Server-side by default; client-side optional Server-side: simpler UX, enables thumbnail generation, search. Client-side: better privacy but Dropbox can't generate previews. Offer client-side as opt-in for power users.
Deduplication scope Per-user (same file = one copy per user) Global (same file = one copy for all users) Global with HMAC keys Global dedup saves the most storage (30% of files are common). Use HMAC(user_key, chunk_hash) as the lookup key — prevents cross-user hash oracle attacks while still enabling dedup.

Java Implementation

/**
 * FileChunker
 * Splits a large file into fixed-size chunks, computes SHA-256 per chunk,
 * tracks upload state in a local SQLite DB for resume capability.
 */
public class FileChunker {

    private static final int CHUNK_SIZE_BYTES = 4 * 1024 * 1024; // 4MB
    private static final String HASH_ALGORITHM = "SHA-256";
    private static final int MAX_PARALLEL_UPLOADS = 4;

    private final UploadApiClient uploadApiClient;
    private final ChunkUploadStateRepository stateRepository; // local SQLite

    public FileChunker(UploadApiClient uploadApiClient,
                       ChunkUploadStateRepository stateRepository) {
        this.uploadApiClient = uploadApiClient;
        this.stateRepository = stateRepository;
    }

    /**
     * Uploads a file using chunked upload with resume capability.
     * Computes SHA-256 per chunk for deduplication and integrity.
     * Uploads pending chunks in parallel (up to MAX_PARALLEL_UPLOADS).
     *
     * @param localFile  the file to upload
     * @param parentFolderId  the destination folder on the server
     * @return the resulting file_id on the server after commit
     */
    public long uploadFile(File localFile, long parentFolderId) throws IOException {
        List<ChunkDescriptor> allChunks = computeChunkDescriptors(localFile);
        String fileContentHash = computeFileHash(localFile);

        // Initiate or resume upload
        UploadSession uploadSession = initializeOrResumeUpload(
            localFile.getName(), localFile.length(), fileContentHash, allChunks
        );

        // Upload only chunks that the server doesn't have yet
        List<ChunkDescriptor> missingChunks = allChunks.stream()
            .filter(chunk -> uploadSession.missingChunkIndexes().contains(chunk.chunkIndex()))
            .toList();

        uploadChunksInParallel(localFile, missingChunks, uploadSession.uploadId());

        // Commit: tell server the upload is complete
        return uploadApiClient.commitUpload(uploadSession.uploadId(), parentFolderId);
    }

    /**
     * Splits the file into 4MB chunk descriptors (no actual reading yet — just metadata).
     * Actual chunk bytes are read during upload.
     */
    private List<ChunkDescriptor> computeChunkDescriptors(File localFile) throws IOException {
        List<ChunkDescriptor> chunks = new ArrayList<>();
        long fileLength = localFile.length();
        int totalChunks = (int) Math.ceil((double) fileLength / CHUNK_SIZE_BYTES);

        try (RandomAccessFile randomAccessFile = new RandomAccessFile(localFile, "r")) {
            for (int chunkIndex = 0; chunkIndex < totalChunks; chunkIndex++) {
                long chunkStartByte = (long) chunkIndex * CHUNK_SIZE_BYTES;
                int chunkLength = (int) Math.min(CHUNK_SIZE_BYTES, fileLength - chunkStartByte);
                byte[] chunkBytes = new byte[chunkLength];
                randomAccessFile.seek(chunkStartByte);
                randomAccessFile.readFully(chunkBytes);
                String chunkHash = computeSha256Hex(chunkBytes);
                chunks.add(new ChunkDescriptor(chunkIndex, chunkStartByte, chunkLength, chunkHash));
            }
        }

        return chunks;
    }

    private void uploadChunksInParallel(File localFile, List<ChunkDescriptor> missingChunks,
                                         String uploadId) throws IOException {
        ExecutorService uploadExecutor = Executors.newFixedThreadPool(MAX_PARALLEL_UPLOADS);
        List<CompletableFuture<Void>> uploadFutures = new ArrayList<>();

        for (ChunkDescriptor chunk : missingChunks) {
            CompletableFuture<Void> uploadFuture = CompletableFuture.runAsync(() -> {
                try {
                    byte[] chunkBytes = readChunkBytes(localFile, chunk);
                    uploadApiClient.uploadChunk(uploadId, chunk.chunkIndex(), chunkBytes);
                    stateRepository.markChunkUploaded(uploadId, chunk.chunkIndex());
                } catch (IOException chunkUploadException) {
                    throw new RuntimeException(
                        "Failed to upload chunk " + chunk.chunkIndex(), chunkUploadException
                    );
                }
            }, uploadExecutor);
            uploadFutures.add(uploadFuture);
        }

        // Wait for all chunks to complete (or fail fast on first exception)
        CompletableFuture.allOf(uploadFutures.toArray(new CompletableFuture[0])).join();
        uploadExecutor.shutdown();
    }

    private UploadSession initializeOrResumeUpload(String fileName, long fileSizeBytes,
            String fileHash, List<ChunkDescriptor> allChunks) {
        List<String> chunkHashes = allChunks.stream()
            .map(ChunkDescriptor::chunkHash)
            .toList();

        // Server responds with which chunk indexes are missing (not yet uploaded or deduped)
        return uploadApiClient.initiateUpload(fileName, fileSizeBytes, fileHash, chunkHashes);
    }

    private byte[] readChunkBytes(File file, ChunkDescriptor chunk) throws IOException {
        byte[] chunkBytes = new byte[chunk.chunkLengthBytes()];
        try (RandomAccessFile randomAccessFile = new RandomAccessFile(file, "r")) {
            randomAccessFile.seek(chunk.chunkStartByte());
            randomAccessFile.readFully(chunkBytes);
        }
        return chunkBytes;
    }

    private String computeSha256Hex(byte[] data) {
        try {
            MessageDigest digest = MessageDigest.getInstance(HASH_ALGORITHM);
            byte[] hashBytes = digest.digest(data);
            StringBuilder hexString = new StringBuilder();
            for (byte hashByte : hashBytes) {
                String hex = Integer.toHexString(0xff & hashByte);
                if (hex.length() == 1) hexString.append('0');
                hexString.append(hex);
            }
            return hexString.toString();
        } catch (NoSuchAlgorithmException algorithmException) {
            throw new RuntimeException("SHA-256 not available", algorithmException);
        }
    }

    private String computeFileHash(File file) throws IOException {
        try {
            MessageDigest digest = MessageDigest.getInstance(HASH_ALGORITHM);
            try (FileInputStream fileInputStream = new FileInputStream(file)) {
                byte[] buffer = new byte[CHUNK_SIZE_BYTES];
                int bytesRead;
                while ((bytesRead = fileInputStream.read(buffer)) != -1) {
                    digest.update(buffer, 0, bytesRead);
                }
            }
            byte[] hashBytes = digest.digest();
            StringBuilder hexString = new StringBuilder();
            for (byte hashByte : hashBytes) {
                String hex = Integer.toHexString(0xff & hashByte);
                if (hex.length() == 1) hexString.append('0');
                hexString.append(hex);
            }
            return hexString.toString();
        } catch (NoSuchAlgorithmException algorithmException) {
            throw new RuntimeException("SHA-256 not available", algorithmException);
        }
    }

    public record ChunkDescriptor(int chunkIndex, long chunkStartByte,
                                   int chunkLengthBytes, String chunkHash) {}
    public record UploadSession(String uploadId, Set<Integer> missingChunkIndexes) {}
}
