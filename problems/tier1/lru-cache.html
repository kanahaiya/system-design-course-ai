Tier 1 — Must Know 45 min Data Structure + System Design

Design an LRU Cache

A hybrid problem: first implement the LRU Cache data structure in O(1) time, then scale it to a distributed cache handling 1M QPS across 10TB of data. Asked at every MAANG company.

🏢 Amazon, Google, Meta, Microsoft
⏱️ 45 min interview
📈 Read-heavy (90%+ reads)

❓ R — Requirements 3–5 min

This problem has two layers. Start with the data structure, then escalate to distributed design when the interviewer asks how you'd scale it.

Functional Requirements

  • get(key) → returns value, or -1 if not found; moves accessed key to most-recently-used position
  • put(key, value) → inserts or updates; if capacity is reached, evicts the least-recently-used key first
  • TTL (time-to-live) per key — expired keys return -1 as if not found

Non-Functional Requirements

  • O(1) time complexity for both get and put — this is the core constraint
  • Thread-safe for concurrent access from multiple threads
  • For distributed scale: 1M QPS, 10TB total cache size, sub-millisecond latency
Interview tip: When the interviewer says "design an LRU Cache", ask: "Are you looking for the data structure implementation first, or should I design it as a distributed cache service?" This shows you understand both dimensions of the problem.

🔢 E — Estimation 3–5 min

For the single-node problem, estimation is trivial (it's bounded by capacity). For the distributed version:

  • Scale: 1M QPS total, 10TB cache, average value size 1KB
  • Entries: 10TB / 1KB = 10 billion entries total
  • Nodes: With 10GB RAM per node → 10,000 entries per GB × 10,000 nodes... too many. Use 10GB/node usable → 10M entries/node → need 1,000 nodes
  • QPS/node: 1M QPS / 1,000 nodes = 1,000 QPS/node — very manageable
  • Network: 1M QPS × 1KB avg = 1GB/s total network bandwidth across the cluster
Key insight: 10TB fits in memory across 1,000 nodes. This is exactly how Redis Cluster and Memcached work — distribute the keyspace using consistent hashing.

🗄️ S — Schema / Data Structures 5 min

LRU Cache has no database schema — it's an in-memory data structure. The "schema" is the internal structure design.

Core Data Structure: HashMap + Doubly Linked List

  • HashMap<Key, Node> — gives O(1) lookup of any node by key
  • DoublyLinkedList — maintains access order; most-recently-used at head, least-recently-used at tail
  • Node — stores key, value, prev pointer, next pointer, and optional expiryMs

Why both structures together?

  • HashMap alone: O(1) lookup, but no way to know the access order → can't find LRU entry
  • Linked list alone: access order maintained, but O(N) to find a key → can't do O(1) get
  • Together: HashMap gives O(1) direct pointer to the node in the list → O(1) move-to-front (relink prev/next)

Dummy Head and Tail Sentinels

Use sentinel nodes (dummy head and tail) to eliminate null checks on boundary cases during insert/remove operations.

// Internal structure layout:
// [dummy_head] ↔ [most_recent] ↔ ... ↔ [least_recent] ↔ [dummy_tail]
//
// HashMap: key → Node (direct pointer into the list)
// On get(key): HashMap lookup → move node to front → return value
// On put(key, val): HashMap lookup → update or insert at front; if over capacity → remove tail

🏗️ H — High-level Design 10 min

Level 1: Single-Node LRU Cache

One process, one HashMap + DoublyLinkedList. All operations O(1). Thread safety via ReentrantReadWriteLock (allow concurrent reads).

Level 2: Distributed LRU Cache

  • Consistent Hashing Ring — maps each key to a specific cache node; adding/removing nodes only remaps 1/N of keys
  • Cache Nodes — each node runs an independent LRU cache (e.g., Memcached or a custom service)
  • Cache Client Library — client-side library handles key routing via consistent hash ring; no central coordinator needed
  • Replication — each key stored on N nodes (e.g., N=3) for fault tolerance; reads from any replica, writes to all

Architecture Diagram (text form)

// Client → CacheClient (consistent hash ring)
//              ↓
//     ┌────────┬────────┬────────┐
//   Node 0   Node 1   Node 2  ... Node 999
//  (10GB)   (10GB)   (10GB)      (10GB)
//   LRU      LRU      LRU         LRU
//
// Each node: HashMap + DLL, evicts LRU on capacity reached
// Total: 1000 × 10GB = 10TB
Mention Redis: In real systems this is Redis Cluster. Each shard is a Redis instance with its own LRU eviction policy (maxmemory-policy: allkeys-lru). You're essentially re-deriving how Redis Cluster works.

🔌 A — APIs 5 min

Single-Node Interface

int get(int key)
// Returns value for key, or -1 if not found or expired
// Side effect: moves key to most-recently-used position

void put(int key, int value)
// Inserts or updates key. If at capacity, evicts LRU key first.

void put(int key, int value, long ttlMillis)
// Same as put() but sets expiry timestamp = now + ttlMillis

Typed Distributed Cache Interface

Optional<T> get(String key, Class<T> type)
// Deserializes value to type T; returns Optional.empty() on miss or expiry

void put(String key, T value, long ttlSeconds)
// Serializes value, routes to correct node via consistent hash ring

void invalidate(String key)
// Deletes key from all replicas

🔬 D — Deep Dive 10 min

Why Doubly Linked List (not Singly)?

When get(key) is called, you must move the node to the front. Moving requires removing the node from its current position. With a doubly linked list and a direct pointer to the node:

node.prev.next = node.next;  // O(1) — we have both pointers
node.next.prev = node.prev;

With a singly linked list, you'd need to traverse from the head to find the predecessor node — O(N). The doubly linked list is not optional; it's what makes O(1) deletion possible.

Thread Safety: ReadWriteLock vs synchronized

Caches are read-heavy (90%+ reads in typical use). A synchronized method serializes all access — even concurrent reads block each other. ReentrantReadWriteLock allows multiple simultaneous readers as long as no writer holds the lock. Under read-heavy load, this dramatically improves throughput.

TTL: Lazy vs Eager Expiry

Lazy expiry (what we implement): check expiry on access. Simple, no background threads. Downside: expired keys consume memory until accessed or LRU-evicted.

Eager expiry (what Redis does): lazy expiry + a background thread that periodically samples random keys and deletes expired ones. This caps memory waste from never-accessed expired keys.

LinkedHashMap Shortcut

Java's LinkedHashMap maintains insertion or access order internally (it's the same HashMap + doubly linked list pattern). You can build a one-liner LRU by overriding removeEldestEntry. But: it's not thread-safe, doesn't support TTL, and interviewers expect you to know the underlying implementation.

⚖️ E — Evaluate 3 min

  • Correctness: get() and put() are O(1). Eviction always removes the true LRU entry (tail of list).
  • Thread safety: ReadWriteLock ensures no data races. get() holds read lock (shared), put() holds write lock (exclusive).
  • TTL correctness: Expired keys return -1 and are removed from both the list and HashMap, reclaiming memory on access.
  • Distributed correctness: Consistent hashing ensures the same key always routes to the same node(s). A client-side ring avoids a coordinator bottleneck.

🚀 D — Deliver 2 min

Summarize your design to the interviewer:

  • Data structure: HashMap + Doubly Linked List with sentinel head/tail. Both structures updated atomically on every get/put. O(1) guaranteed.
  • Thread safety: ReentrantReadWriteLock — multiple concurrent reads, exclusive writes. For single-key hot-spot scenarios, striped locking (lock per hash bucket) further reduces contention.
  • Distributed: Consistent hashing ring, each node an independent LRU cache. Client library routes keys — no central coordinator. Add replication factor N=3 for fault tolerance.
  • TTL: Lazy expiry on access + optional background cleanup thread (Redis-style periodic sampling).

⚡ Trade-offs

Decision Option A Option B Choose When
Internal structure HashMap + DLL (custom) LinkedHashMap (built-in) Custom: need TTL, thread safety, or interviewer wants to see the internals. LinkedHashMap: prototype or non-concurrent usage.
Thread safety strategy ReentrantReadWriteLock synchronized on all methods ReadWriteLock: read-heavy workloads (typical cache). synchronized: write-heavy or when simplicity > performance.
TTL expiry Lazy (check on access) Background cleanup thread Lazy: simpler, no extra threads, acceptable if expired-but-unaccessed keys are rare. Background: bounded memory waste matters.
Eviction policy LRU (evict least recently used) LFU (evict least frequently used) LRU: recency matters (e.g., news feed cache). LFU: frequency matters (e.g., popular product pages). ARC: adapts between both automatically.

☕ Java Implementation 

import java.util.HashMap;
import java.util.concurrent.locks.ReentrantReadWriteLock;

/**
 * Thread-safe LRU Cache with TTL support.
 * get() and put() are both O(1).
 *
 * Internally: HashMap (O(1) lookup) + DoublyLinkedList (O(1) reorder).
 * Sentinel head/tail nodes eliminate null-pointer edge cases.
 */
public class LRUCache {

    // ── Inner classes ──────────────────────────────────────────────

    private static class Node {
        int key;
        int value;
        long expiryMs;   // 0 = no expiry
        Node prev;
        Node next;

        Node(int key, int value, long ttlMillis) {
            this.key = key;
            this.value = value;
            this.expiryMs = (ttlMillis > 0)
                ? System.currentTimeMillis() + ttlMillis
                : 0;
        }
    }

    private static class DoublyLinkedList {
        // Sentinel nodes: head.next = most recent, tail.prev = least recent
        final Node head = new Node(0, 0, 0);
        final Node tail = new Node(0, 0, 0);

        DoublyLinkedList() {
            head.next = tail;
            tail.prev = head;
        }

        void addToFront(Node node) {
            node.next = head.next;
            node.prev = head;
            head.next.prev = node;
            head.next = node;
        }

        void remove(Node node) {
            node.prev.next = node.next;
            node.next.prev = node.prev;
        }

        /** Removes and returns the LRU node (tail.prev). Returns null if list is empty. */
        Node removeLast() {
            Node lruNode = tail.prev;
            if (lruNode == head) {
                return null;
            }
            remove(lruNode);
            return lruNode;
        }
    }

    // ── Fields ─────────────────────────────────────────────────────

    private final int capacity;
    private final HashMap<Integer, Node> nodeMap;
    private final DoublyLinkedList accessList;
    private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();

    // ── Constructor ────────────────────────────────────────────────

    public LRUCache(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("Capacity must be positive");
        }
        this.capacity = capacity;
        this.nodeMap = new HashMap<>(capacity);
        this.accessList = new DoublyLinkedList();
    }

    // ── Public API ─────────────────────────────────────────────────

    /**
     * Returns value for key, or -1 if not found or expired.
     * Moves accessed key to most-recently-used position.
     * Uses read lock initially, upgrades to write lock on hit (must move node).
     */
    public int get(int key) {
        // Note: we acquire write lock because even a read moves the node.
        // A pure read lock would be invalid here since we mutate the list.
        lock.writeLock().lock();
        try {
            Node node = nodeMap.get(key);
            if (node == null) {
                return -1;
            }
            if (isExpired(node)) {
                evictNode(node);
                return -1;
            }
            // Move to front (most recently used)
            accessList.remove(node);
            accessList.addToFront(node);
            return node.value;
        } finally {
            lock.writeLock().unlock();
        }
    }

    /**
     * Inserts or updates the key. If at capacity, evicts the LRU key first.
     * Optional TTL: 0 means no expiry.
     */
    public void put(int key, int value) {
        put(key, value, 0);
    }

    public void put(int key, int value, long ttlMillis) {
        lock.writeLock().lock();
        try {
            Node existingNode = nodeMap.get(key);
            if (existingNode != null) {
                existingNode.value = value;
                existingNode.expiryMs = (ttlMillis > 0)
                    ? System.currentTimeMillis() + ttlMillis
                    : 0;
                accessList.remove(existingNode);
                accessList.addToFront(existingNode);
                return;
            }
            // Evict if at capacity
            if (nodeMap.size() >= capacity) {
                Node evicted = accessList.removeLast();
                if (evicted != null) {
                    nodeMap.remove(evicted.key);
                }
            }
            Node newNode = new Node(key, value, ttlMillis);
            nodeMap.put(key, newNode);
            accessList.addToFront(newNode);
        } finally {
            lock.writeLock().unlock();
        }
    }

    // ── Private helpers ────────────────────────────────────────────

    private boolean isExpired(Node node) {
        return node.expiryMs > 0 && System.currentTimeMillis() > node.expiryMs;
    }

    private void evictNode(Node node) {
        accessList.remove(node);
        nodeMap.remove(node.key);
    }
}

// ── LinkedHashMap one-liner alternative ───────────────────────────
// Useful to mention: Java's LinkedHashMap IS the same pattern internally.
// Override removeEldestEntry to auto-evict on put().
// Limitation: not thread-safe, no TTL support.

import java.util.LinkedHashMap;
import java.util.Map;

class LRUCacheSimple<K, V> extends LinkedHashMap<K, V> {
    private final int maxCapacity;

    LRUCacheSimple(int maxCapacity) {
        // accessOrder=true: get() moves entry to back (most recent = last)
        super(maxCapacity, 0.75f, true);
        this.maxCapacity = maxCapacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxCapacity;
    }
}
