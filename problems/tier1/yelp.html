Tier 1 — Must Know 45 min Geospatial

Design Yelp / Proximity Service

The core challenge: search 500M businesses by proximity in under 200ms. The answer lies in geospatial indexing — understanding geohash, S2 cells, and quadtrees separates passing candidates from failing ones.

🏢 Google, Amazon, Yelp, Uber
⏱️ 45 min interview
📈 Read-heavy (search vs write)

❓ R — Requirements 3–5 min

Functional Requirements

  • Search businesses within a given radius (e.g., "restaurants within 5km of my location")
  • View business details (name, address, category, hours, photos) and reviews
  • Add or update business information (owner/admin operation)
  • Add a review with a star rating (1–5) and text

Non-Functional Requirements

  • Scale: 100M DAU, 500M businesses globally
  • Search latency: <200ms at the 99th percentile
  • Consistency: Strong consistency for business data (name, address must be accurate); eventual consistency for review counts and average ratings is acceptable
  • Availability: 99.9% uptime; search should degrade gracefully (return cached results) rather than fail
Clarify radius: Ask "what is the max radius a user can search?" In Yelp/Google Maps, it's typically 50km. This affects which geohash precision level you choose (see Deep Dive).

🔢 E — Estimation 3–5 min

  • Search QPS: 100M DAU × 5 searches/day ÷ 86,400s = ~5,800 QPS (peak ~3× = 17K QPS)
  • Business data: 500M businesses × 1KB metadata = 500GB — this fits in a Redis Cluster (in memory!)
  • Review data: 500M businesses × avg 100 reviews × 500B per review = 25TB — this lives on disk (PostgreSQL or Cassandra)
  • Write QPS for reviews: 100M DAU × 0.1 reviews/day ÷ 86,400 = ~115 QPS (write-light system)
Key insight: 500GB for the entire business index (name + location + category) fits in memory. This is the most important estimation in this problem — it enables in-memory geospatial search.

🗄️ S — Schema 5 min 

-- businesses table (PostgreSQL with PostGIS, or any RDBMS + geohash column)
CREATE TABLE businesses (
    business_id  UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    name         VARCHAR(255) NOT NULL,
    description  TEXT,
    address      VARCHAR(500),
    lat          FLOAT       NOT NULL,
    lng          FLOAT       NOT NULL,
    category     VARCHAR(100),
    avg_rating   FLOAT       DEFAULT 0,
    review_count INT         DEFAULT 0,
    geohash      VARCHAR(12),   -- indexed column for proximity search
    created_at   TIMESTAMP   DEFAULT NOW()
);
CREATE INDEX idx_businesses_geohash ON businesses(geohash);
-- PostGIS alternative: CREATE INDEX idx_businesses_geo ON businesses USING GIST(ST_Point(lng, lat));

-- reviews table (write-heavy, append-only → good candidate for Cassandra)
CREATE TABLE reviews (
    review_id    UUID        PRIMARY KEY,
    business_id  UUID        REFERENCES businesses(business_id),
    user_id      UUID        NOT NULL,
    rating       SMALLINT    CHECK (rating BETWEEN 1 AND 5),
    text_content TEXT,
    created_at   TIMESTAMP   DEFAULT NOW()
);
CREATE INDEX idx_reviews_business ON reviews(business_id, created_at DESC);
Geohash column: Geohash is just a string — any database with a B-tree index can do geohash prefix queries efficiently (WHERE geohash LIKE 'dr5ru%'). No spatial extension required.

🏗️ H — High-level Design 10 min

Services

  • Location/Search Service — handles proximity queries; uses in-memory geospatial index (Redis GEO or Elasticsearch geo_distance)
  • Business Service — CRUD for business data; PostgreSQL as source of truth; Redis as read cache
  • Review Service — append-only review writes; Cassandra for write-heavy storage; async update of avg_rating in Business DB
  • API Gateway — routes requests, handles auth, rate limiting

Architecture Flow

// Search request flow:
// Client → API GW → Location Service
//                       ↓
//              Redis GEO (GEORADIUSBYMEMBER) or Elasticsearch geo_distance
//                       ↓
//              Returns business_ids within radius
//                       ↓
//              Batch fetch business details from Redis cache / PostgreSQL
//                       ↓
//              Apply filters (category, rating, price) on candidate set
//                       ↓
//              Return ranked results (by distance, then rating)

// Business data write flow:
// Admin → Business Service → Write to PostgreSQL → Async sync to Redis + Search Index

// Review write flow:
// User → Review Service → Write to Cassandra
//                              ↓
//                         Kafka event → Business Service
//                              ↓
//                         UPDATE businesses SET running_total += rating, review_count += 1

🔬 D — Deep Dive: Geospatial Search with Geohash 10 min

How Geohash Works

Geohash divides the world into a recursive grid of rectangular cells. Each cell is identified by a base-32 string. Longer string = smaller cell. Cells sharing a prefix are geographically adjacent (usually — boundary cases exist).

Geohash Precision vs Cell Size

  • Precision 4 (4 chars): ~40km × 20km cell — too large for 5km search
  • Precision 5 (5 chars): ~4.9km × 4.9km cell — good for 5km search
  • Precision 6 (6 chars): ~1.2km × 0.6km cell — good for 1km search
  • Precision 8 (8 chars): ~38m × 19m cell — for precise point queries

The Boundary Problem: Always Search 9 Cells

A business 4km from the user might be in an adjacent geohash cell. Always query the center cell + all 8 neighbors (N, NE, E, SE, S, SW, W, NW). Then apply exact Haversine distance filter on the candidate set.

Two-Step Search Algorithm

// Step 1: Geohash approximation (fast, uses index)
// → Get candidate businesses from center + 8 neighbor cells

// Step 2: Exact distance filter (Haversine formula)
// → Remove candidates that are outside the actual radius circle
// (Geohash cells are rectangles; the search radius is a circle)

// This two-step approach is standard in Elasticsearch geo_distance,
// Redis GEORADIUS, PostGIS ST_DWithin queries — all do it internally.

Why Geohash is a String (and Why That Matters)

Because geohash is just a string, you can store it in any database column with a standard B-tree index and query it with WHERE geohash LIKE 'dr5ru%'. No spatial extension required. This is a major practical advantage over S2 cells or quadtrees.

⚖️ E — Evaluate 3 min

  • Latency: 500GB business index fits in Redis Cluster → geohash lookup in ~0.1ms. Adding 9-cell neighbor query + Haversine filter on ~5000 candidates → well under 200ms.
  • Scale: Location Service is stateless — scale horizontally. Redis Cluster handles 500GB across 50 nodes.
  • Accuracy: 9-cell search + Haversine ensures no false negatives at cell boundaries. Haversine is exact for Earth's surface distances.
  • Review avg_rating: Running total pattern (store sum + count) keeps updates O(1) without recalculating AVG across all reviews.

🚀 D — Deliver 2 min

  • Geospatial index: Geohash column in PostgreSQL (indexed) OR Redis GEO commands. Search = center cell + 8 neighbors → Haversine exact filter.
  • Business index in memory: 500GB across Redis Cluster → sub-millisecond lookups. PostgreSQL is the durable source of truth; Redis is the hot path.
  • Reviews: Cassandra for append-only storage. Running total pattern for avg_rating updates (O(1), no AVG recalculation).
  • Filters (category, rating, open_now): Applied in-memory on the geospatial candidate set (~5000 candidates max), not as a pre-filter that would prevent index use.

⚡ Trade-offs

Decision Option A Option B Choose When
Geospatial indexing Geohash (string prefix index) PostGIS / S2 cells / Quadtree Geohash: works in any DB, simple prefix queries, good for most cases. PostGIS: complex polygon queries, more accurate near poles. S2: Google's choice, better cell uniformity.
Search storage Redis GEO commands Elasticsearch geo_distance Redis GEO: simpler setup, lower latency for pure proximity. Elasticsearch: needed when combining geo with full-text search (business name search + proximity).
Review storage PostgreSQL (relational) Cassandra (wide-column) PostgreSQL: simpler, strong consistency, good for moderate write volumes. Cassandra: needed when review write QPS exceeds PostgreSQL's single-node capacity or multi-region write replication is required.
avg_rating updates Running total (sum + count in businesses table) Recalculate SELECT AVG() on every review insert Always use running total. AVG recalculation is O(N) per review insert — creates a join bottleneck at scale.

☕ Java Implementation 

import java.util.ArrayList;
import java.util.List;

/**
 * GeohashProximitySearch: finds nearby businesses using geohash indexing.
 *
 * Two-step algorithm:
 *   1. Geohash approximation: search center cell + 8 neighbors (fast, uses DB index)
 *   2. Haversine exact filter: remove candidates outside the actual radius circle
 */
public class GeohashProximitySearch {

    // ── Constants ──────────────────────────────────────────────────

    private static final double EARTH_RADIUS_KM = 6371.0;

    // Mapping from search radius (meters) to geohash precision level.
    // Precision chosen so the geohash cell is slightly smaller than the radius,
    // ensuring the 9-cell search captures all results within the radius.
    private static final int[][] RADIUS_TO_PRECISION = {
        {  5_000, 5},   // 5km radius → precision 5 (~5km cell)
        { 20_000, 4},   // 20km radius → precision 4 (~40km cell)
        {100_000, 3},   // 100km radius → precision 3 (~150km cell)
    };
    private static final int DEFAULT_PRECISION = 2;

    private final BusinessRepository businessRepository;

    public GeohashProximitySearch(BusinessRepository businessRepository) {
        this.businessRepository = businessRepository;
    }

    // ── Public API ─────────────────────────────────────────────────

    /**
     * Returns businesses within radiusMeters of the given coordinates.
     * Applies category filter if provided. Results sorted by distance ascending.
     *
     * @param lat           center latitude in decimal degrees
     * @param lng           center longitude in decimal degrees
     * @param radiusMeters  search radius in meters
     * @param category      optional category filter (null = no filter)
     * @param limit         max results to return
     * @return list of matching businesses with computed distance
     */
    public List<BusinessResult> searchNearby(
            double lat, double lng, int radiusMeters,
            String category, int limit) {

        int precision = getPrecisionForRadius(radiusMeters);
        String centerHash = encodeGeohash(lat, lng, precision);
        List<String> searchHashes = getNeighborCells(centerHash);
        searchHashes.add(centerHash);   // include center cell

        // Step 1: DB query with geohash prefix filter (fast index scan)
        List<Business> candidates = businessRepository.findByGeohashPrefixes(
            searchHashes, category
        );

        // Step 2: Exact Haversine distance filter and sort
        double radiusKm = radiusMeters / 1000.0;
        List<BusinessResult> nearbyResults = new ArrayList<>();

        for (Business business : candidates) {
            double distanceKm = haversineDistanceKm(lat, lng, business.getLat(), business.getLng());
            if (distanceKm <= radiusKm) {
                nearbyResults.add(new BusinessResult(business, distanceKm));
            }
        }

        nearbyResults.sort((firstResult, secondResult) ->
            Double.compare(firstResult.getDistanceKm(), secondResult.getDistanceKm())
        );

        return nearbyResults.subList(0, Math.min(limit, nearbyResults.size()));
    }

    // ── Geohash encoding (simplified base-32 implementation) ───────

    /**
     * Encodes (lat, lng) to a geohash string of the given precision.
     * Full implementation uses base-32 encoding with alternating lat/lng bits.
     * This shows the precision → cell size relationship.
     */
    public String encodeGeohash(double lat, double lng, int precision) {
        // Production: use a geohash library (e.g., com.github.davidmoten:geo)
        // Conceptually: interleave lat/lng bits, encode in base-32
        // precision 5 = 25 bits per coordinate = ~5km cell
        return com.github.davidmoten.geo.GeoHash.encodeHash(lat, lng, precision);
    }

    /**
     * Returns the 8 neighboring geohash cells for a given cell.
     * Neighbors share a face or corner with the center cell.
     */
    public List<String> getNeighborCells(String geohash) {
        // Production: use geohash library's neighbor() function
        return com.github.davidmoten.geo.GeoHash.neighbours(geohash);
    }

    // ── Haversine distance calculation ─────────────────────────────

    /**
     * Calculates the great-circle distance between two points on Earth.
     * Accurate to within 0.5% for distances up to a few hundred km.
     *
     * @return distance in kilometers
     */
    public double haversineDistanceKm(
            double lat1, double lng1,
            double lat2, double lng2) {

        double deltaLat = Math.toRadians(lat2 - lat1);
        double deltaLng = Math.toRadians(lng2 - lng1);

        double sinHalfDeltaLat = Math.sin(deltaLat / 2);
        double sinHalfDeltaLng = Math.sin(deltaLng / 2);

        double haversineValue =
            sinHalfDeltaLat * sinHalfDeltaLat
            + Math.cos(Math.toRadians(lat1))
              * Math.cos(Math.toRadians(lat2))
              * sinHalfDeltaLng * sinHalfDeltaLng;

        double centralAngle = 2 * Math.asin(Math.sqrt(haversineValue));
        return EARTH_RADIUS_KM * centralAngle;
    }

    // ── Private helpers ────────────────────────────────────────────

    private int getPrecisionForRadius(int radiusMeters) {
        for (int[] radiusToPrecisionEntry : RADIUS_TO_PRECISION) {
            if (radiusMeters <= radiusToPrecisionEntry[0]) {
                return radiusToPrecisionEntry[1];
            }
        }
        return DEFAULT_PRECISION;
    }

    // ── Inner types ────────────────────────────────────────────────

    public static class BusinessResult {
        private final Business business;
        private final double distanceKm;

        BusinessResult(Business business, double distanceKm) {
            this.business = business;
            this.distanceKm = distanceKm;
        }

        public Business getBusiness() { return business; }
        public double getDistanceKm() { return distanceKm; }
    }
}

// ── Running total pattern for avg_rating ──────────────────────────

// On every new review insert, atomically update the business:
// UPDATE businesses
//   SET running_total = running_total + ?,
//       review_count  = review_count + 1,
//       avg_rating    = (running_total + ?) / (review_count + 1)
// WHERE business_id = ?;
//
// This is O(1) per review — no AVG(rating) recalculation needed.
// The UPDATE is a single atomic SQL statement.
