Tier 1 — Must Know 45 min

Design a Distributed Message Queue (like Kafka)

Design a high-throughput distributed message queue handling 1M messages/second with partitioned topics, consumer groups with offset tracking, 7-day message retention, and ISR-based fault-tolerant replication.

🏢 LinkedIn (Kafka), Amazon (SQS/Kinesis), Meta, Uber
⏱️ 45 min

R — Requirements

Functional Requirements

  • Producers publish messages to named topics
  • Consumers subscribe to topics via consumer groups; each message delivered to one consumer per group
  • Messages persist for 7 days (consumers can replay from any offset)
  • Message ordering guaranteed within a partition
  • Topics have configurable partition count and replication factor

Non-Functional Requirements

  • Throughput: 1M messages/second write; 5M messages/second read (fan-out)
  • Message size: up to 1MB per message
  • Retention: 7 days → 7 × 24 × 3600 × 1GB/s = 604TB total, 3x replication = 1.8PB
  • Delivery guarantee: at-least-once (default); exactly-once with idempotent producers
  • Latency: end-to-end < 100ms p99
The key insight: Message queues are logs. A partition is an append-only log file. Consumer "consuming" just means advancing an offset pointer. The broker never deletes messages — time-based expiry does. This is why replay is free.

1GB/s write throughput × 100 brokers = 10MB/s per broker — very manageable with sequential disk writes. The 1.8PB storage is the main cost driver; use commodity HDDs (not SSDs) since message queues are write-once, read-once workloads that favor sequential I/O.

S — Schema

    topic_name: "user-events",

    topic: "user-events",

    leader_broker_id: 42,

-- Consumer offset tracking (stored in __consumer_offsets internal topic)
offsets {
    consumer_group: "analytics-service",
    topic: "user-events",
    partition: 0,
    committed_offset: 1_048_576   // next message to read = offset 1,048,576
}

-- On-disk partition log segment (binary, append-only)
// Each segment: {base_offset}.log + {base_offset}.index + {base_offset}.timeindex
// .log: [offset(8B)][timestamp(8B)][key_len(4B)][key][value_len(4B)][value][crc(4B)]
// .index: sparse offset-to-file-position map for O(log n) seeks
// Segment rolls when size > 1GB or age > 1 hour

Figure: Kafka — Producer hashes key to partition; Broker stores 3 partitions each with 1 Leader + 2 Replicas; Consumer Group assigns 1 consumer per partition with offset tracking

  1. Producer: Hashes message key → selects partition → connects to that partition's leader broker → sends batch of messages
  2. Broker (leader): Appends to Write-Ahead Log (WAL) on disk → replicates to ISR followers → when all ISR acknowledge, marks offset as committed → ACKs producer
  3. Consumer: Polls the broker with its current offset → broker responds with a batch of messages → consumer processes, commits new offset → repeat
  4. ZooKeeper / KRaft: Stores cluster metadata (topic configs, partition leaders, ISR lists, broker membership)
  5. Partition assignment: Consumer group coordinator assigns partitions to consumers in the group (1 partition → 1 consumer at most). If consumer count > partition count, some consumers are idle.

A — APIs

// Producer API
interface MessageProducer {
    /**
     * Publishes a message to a topic.
     * Partition assignment: hash(key) % partitionCount if key provided;
     * round-robin if key is null.
     *
     * @param topic   the topic name
     * @param key     optional partition key (same key → same partition → ordering)
     * @param value   the message payload
     * @param acks    0=fire-and-forget, 1=leader-ack, -1=all-ISR-ack
     * @return RecordMetadata with partition and offset of written message
     */
    CompletableFuture<RecordMetadata> send(String topic, byte[] key, byte[] value, int acks);
}

// Consumer API
interface MessageConsumer {
    /**
     * Subscribes to a list of topics as part of a consumer group.
     * Partition assignments are rebalanced automatically.
     */
    void subscribe(List<String> topics, String consumerGroup);

    /**
     * Polls for new messages up to maxMessages.
     * Blocks up to timeoutMs waiting for messages.
     * Advances the consumer's position but does NOT commit the offset.
     */
    List<ConsumerRecord> poll(int maxMessages, long timeoutMs);

    /**
     * Commits the current offset for all assigned partitions.
     * Messages before this offset will not be re-delivered on restart.
     */
    void commitOffset();
}

// Admin API
interface AdminClient {
    void createTopic(String name, int partitions, int replicationFactor);
    void deleteTopic(String name);
    TopicMetadata describeTopic(String name);
    void resetConsumerGroupOffset(String group, String topic, long newOffset);
}

D — Deep Dive: Partitioning and Replication

Why Partitions?

A single broker can sustain ~500MB/s of sequential writes. At 1GB/s required throughput, we need at least 2 brokers writing in parallel. Partitions are the unit of parallelism: 1000 partitions across 100 brokers = 10 partitions/broker.

Partition key: Messages with the same key always go to the same partition → ordering guarantee within a key. E.g., all events for user_id=42 go to partition hash(42) % 1000, preserving event order for that user.

ISR (In-Sync Replicas)

ISR is the set of replicas that are fully caught up with the leader's log (within replica.lag.time.max.ms, default 10s). With acks=-1, the leader waits for ALL ISR replicas to acknowledge before committing. If a follower falls behind (network blip, GC pause), it's removed from ISR and the leader doesn't wait for it.

Leader election: When the leader fails, ZooKeeper notifies the broker cluster. The first broker in ISR is elected as new leader. If ISR is empty (all replicas behind), either wait (safer) or elect an out-of-sync replica (unclean leader election — may lose messages).

unclean.leader.election.enable: Setting this to false (safer) means your partition becomes unavailable if the leader fails and ISR is empty. Setting to true (available) risks message loss. Most production systems: false.

E — Evaluate

  • Consumer lag: If a consumer can't keep up with producer rate, offset falls behind. Monitor consumer group lag (latest offset − committed offset). Alert if lag exceeds threshold. Fix by adding consumers (up to partition count).
  • Exactly-once delivery: Kafka achieves this with idempotent producers (each message has a producer_id + sequence_number, broker deduplicates retries) + transactional API (atomic write across multiple partitions).
  • Message ordering: Guaranteed within a partition. NOT guaranteed across partitions. If global ordering is needed, use 1 partition (sacrifices parallelism) or embed sequence numbers in messages and sort on the consumer side.
  • Hot partition: If one partition key (e.g., one very active user) gets 80% of traffic, one broker gets 80% of load. Solution: add a random suffix to the key to spread across sub-partitions; aggregate on the consumer side.

D — Deliver

The message queue is fundamentally a distributed append-only log. Sequential disk writes are ~1000x faster than random writes — this is why Kafka on commodity hardware outperforms databases for this use case. The consumer model (pull-based with explicit offset management) gives consumers full control over replay and backpressure.

Zero-copy optimization: Kafka uses Linux sendfile() to transfer data directly from the page cache to the network socket without copying to user space. This eliminates two memory copies and enables the high throughput (100K msg/s per broker on commodity hardware).

Trade-off Table

DecisionOption AOption BChosenWhy
Consumer model Push (broker pushes to consumers) Pull (consumer polls broker) Pull Push can overwhelm slow consumers. Pull lets consumers set their own pace (backpressure). Pull also enables batching — consumer requests as many messages as it can handle per poll.
Replication acks acks=1 (leader only) acks=-1 (all ISR) acks=-1 for durability acks=1: leader dies before replicating → message lost. acks=-1: no data loss if any ISR member survives. Latency cost: ISR replication adds ~5ms. Acceptable for most use cases.
Delivery guarantee At-least-once Exactly-once At-least-once (default) Exactly-once requires idempotent producers + transactions — complex and adds overhead. At-least-once is simpler; make consumers idempotent (dedup by message key) instead.
Offset storage ZooKeeper Internal Kafka topic (__consumer_offsets) Internal topic ZooKeeper is a bottleneck for high-frequency offset commits. Internal topic handles millions of commits/second and keeps all metadata in Kafka itself (single system to operate).

Java Implementation

/**
 * MessagePartitioner
 * Determines which partition a message should be written to.
 * Consistent hashing ensures same key always maps to same partition.
 */
public class MessagePartitioner {

    /**
     * Assigns a partition for a message.
     * If key is null: round-robin for load balancing.
     * If key present: consistent hash for ordering guarantees.
     *
     * @param key            the message key (may be null)
     * @param partitionCount total number of partitions in the topic
     * @param roundRobinCounter shared counter for null-key round-robin
     * @return partition index in range [0, partitionCount)
     */
    public int selectPartition(byte[] key, int partitionCount, AtomicLong roundRobinCounter) {
        if (key == null) {
            // Round-robin: distribute evenly across partitions
            return (int) (roundRobinCounter.getAndIncrement() % partitionCount);
        }
        // Murmur2 hash, same algorithm as Kafka's default partitioner
        int murmurHash = murmur2Hash(key);
        return Math.abs(murmurHash) % partitionCount;
    }

    private int murmur2Hash(byte[] data) {
        final int seed = 0x9747b28c;
        final int multiplier = 0x5bd1e995;
        final int rotationAmount = 24;
        int hashValue = seed ^ data.length;

        for (int index = 0; index + 4 <= data.length; index += 4) {
            int chunk = (data[index] & 0xFF)
                | ((data[index + 1] & 0xFF) << 8)
                | ((data[index + 2] & 0xFF) << 16)
                | ((data[index + 3] & 0xFF) << 24);
            chunk *= multiplier;
            chunk ^= chunk >>> rotationAmount;
            chunk *= multiplier;
            hashValue *= multiplier;
            hashValue ^= chunk;
        }

        // Handle remaining bytes
        int remaining = data.length & 3;
        if (remaining == 3) hashValue ^= (data[data.length - 3] & 0xFF) << 16;
        if (remaining >= 2) hashValue ^= (data[data.length - 2] & 0xFF) << 8;
        if (remaining >= 1) {
            hashValue ^= (data[data.length - 1] & 0xFF);
            hashValue *= multiplier;
        }

        hashValue ^= hashValue >>> 13;
        hashValue *= multiplier;
        hashValue ^= hashValue >>> 15;
        return hashValue;
    }
}

/**
 * WalMessageStore
 * Write-Ahead Log based message store for a single partition.
 * Append-only: all writes are sequential, enabling high throughput.
 */
public class WalMessageStore {

    private static final int SEGMENT_SIZE_BYTES = 1_073_741_824; // 1GB per segment
    private static final String LOG_FILE_EXTENSION = ".log";
    private static final String INDEX_FILE_EXTENSION = ".index";

    private final Path partitionDirectory;
    private RandomAccessFile currentLogFile;
    private RandomAccessFile currentIndexFile;
    private long currentBaseOffset;
    private long currentOffset;
    private long currentSegmentBytes;

    public WalMessageStore(Path partitionDirectory) throws IOException {
        this.partitionDirectory = partitionDirectory;
        Files.createDirectories(partitionDirectory);
        initializeLatestSegment();
    }

    /**
     * Appends a message to the partition log.
     * Returns the offset assigned to this message.
     * Thread-safety: caller must synchronize; only partition leader writes.
     *
     * @param messageKey   the message key (may be null)
     * @param messageValue the message payload bytes
     * @return the offset at which this message was written
     */
    public long append(byte[] messageKey, byte[] messageValue) throws IOException {
        long assignedOffset = currentOffset;
        long filePosition = currentLogFile.length();

        writeMessageToLog(assignedOffset, messageKey, messageValue);
        updateSparseIndex(assignedOffset, filePosition);

        currentOffset++;
        currentSegmentBytes += computeMessageSize(messageKey, messageValue);

        if (currentSegmentBytes >= SEGMENT_SIZE_BYTES) {
            rollNewSegment();
        }

        return assignedOffset;
    }

    /**
     * Reads up to maxMessages starting at startOffset.
     * Uses sparse index to seek to the correct file position efficiently.
     *
     * @param startOffset the offset to start reading from (inclusive)
     * @param maxMessages maximum number of messages to return
     * @return list of messages in order
     */
    public List<MessageRecord> read(long startOffset, int maxMessages) throws IOException {
        long filePosition = findFilePositionForOffset(startOffset);
        List<MessageRecord> messages = new ArrayList<>();

        RandomAccessFile logFile = openSegmentForOffset(startOffset);
        logFile.seek(filePosition);

        while (messages.size() < maxMessages && logFile.getFilePointer() < logFile.length()) {
            MessageRecord record = readNextMessage(logFile);
            if (record.offset() >= startOffset) {
                messages.add(record);
            }
        }

        return messages;
    }

    private void writeMessageToLog(long offset, byte[] key, byte[] value) throws IOException {
        long timestamp = System.currentTimeMillis();
        int keyLength = key != null ? key.length : -1;

        currentLogFile.writeLong(offset);
        currentLogFile.writeLong(timestamp);
        currentLogFile.writeInt(keyLength);
        if (key != null) currentLogFile.write(key);
        currentLogFile.writeInt(value.length);
        currentLogFile.write(value);
        // CRC32 checksum for corruption detection
        CRC32 checksum = new CRC32();
        if (key != null) checksum.update(key);
        checksum.update(value);
        currentLogFile.writeLong(checksum.getValue());
    }

    private void updateSparseIndex(long offset, long filePosition) throws IOException {
        // Write every 4096th offset to the sparse index for O(log n) seeks
        if (offset % 4096 == 0) {
            currentIndexFile.writeLong(offset);
            currentIndexFile.writeLong(filePosition);
        }
    }

    private long findFilePositionForOffset(long targetOffset) throws IOException {
        // Binary search the sparse index to find nearest lower-bound position
        // Then scan forward in the log file from that position
        return 0L; // Simplified — real implementation does binary search on index file
    }

    private void rollNewSegment() throws IOException {
        currentLogFile.close();
        currentIndexFile.close();
        currentBaseOffset = currentOffset;
        currentSegmentBytes = 0;
        initializeLatestSegment();
    }

    private void initializeLatestSegment() throws IOException {
        String segmentName = String.format("%020d", currentBaseOffset);
        currentLogFile = new RandomAccessFile(
            partitionDirectory.resolve(segmentName + LOG_FILE_EXTENSION).toFile(), "rw");
        currentIndexFile = new RandomAccessFile(
            partitionDirectory.resolve(segmentName + INDEX_FILE_EXTENSION).toFile(), "rw");
    }

    private int computeMessageSize(byte[] key, byte[] value) {
        // offset(8) + timestamp(8) + keyLen(4) + key + valueLen(4) + value + crc(8)
        int keySize = key != null ? key.length : 0;
        return 8 + 8 + 4 + keySize + 4 + value.length + 8;
    }

    private MessageRecord readNextMessage(RandomAccessFile logFile) throws IOException {
        long offset = logFile.readLong();
        long timestamp = logFile.readLong();
        int keyLength = logFile.readInt();
        byte[] key = keyLength > 0 ? new byte[keyLength] : null;
        if (key != null) logFile.readFully(key);
        int valueLength = logFile.readInt();
        byte[] value = new byte[valueLength];
        logFile.readFully(value);
        logFile.readLong(); // skip CRC
        return new MessageRecord(offset, timestamp, key, value);
    }

    private RandomAccessFile openSegmentForOffset(long targetOffset) throws IOException {
        return currentLogFile; // Simplified — real impl finds correct segment file
    }

    public record MessageRecord(long offset, long timestamp, byte[] key, byte[] value) {}
}
