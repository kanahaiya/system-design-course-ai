Tier 3 — Expert 60 minObservability Infrastructure

Design a Distributed Tracing System

Distributed tracing answers the question: what happened during this one request across all 15 services it touched? The core challenge is that at 1M req/sec with 50 spans each, storing everything costs 500 MB/sec. Sampling strategies determine what you keep — and the wrong strategy means you never have the trace you need when an incident hits.

🏢 Jaeger (Uber), Zipkin (Twitter), AWS X-Ray, Datadog APM
⏱️ 60 min interview

❓R — Requirements3–5 min

Functional Requirements

  • Capture the full tree of service calls for each request: which services were called, in what order, how long each took
  • Propagate trace context across HTTP, gRPC, and Kafka message boundaries
  • Search traces by: service name, operation name, duration, error status, custom tags
  • Visualize a trace as a waterfall/flamegraph: show span durations, parent-child relationships
  • Service dependency map: auto-discover which services call which other services
  • Error traces: immediately accessible; never sampled away
  • Sampling: configurable rates per service and operation to manage storage costs

Non-Functional Requirements

  • Overhead: instrumentation must add <1% latency to services being traced
  • Throughput: 1M requests/second, each with ~50 spans
  • Storage budget: ~10K traces/second after sampling (1% of 1M req/sec)
  • Search latency: p99 < 2 seconds for queries over the last 24 hours
  • Trace completeness: all spans for a given trace must be retrievable together
  • Retention: recent traces 7 days (fast search), older traces 30 days (slower)

Clarifying Questions

  • Do we need tail-based sampling (requires collecting all spans before making keep/drop decision)?
  • Is this internal infrastructure or a multi-tenant product (each customer traces their own services)?
  • What is the latency budget for the tracing instrumentation? (1% overhead? 0.1%?)

🔢E — Estimation3–5 min

Span Volume Calculation

  • 1M req/sec × 50 spans/trace = 50M spans/sec total
  • Each span: ~1 KB (operation name, timestamps, tags, log messages) = 50 GB/sec raw
  • Storing everything: 50 GB/sec × 86,400 sec = 4.3 PB/day — economically impossible
  • At 1% head sampling: 500K spans/sec = 500 MB/sec = 43 TB/day — still expensive
  • At 0.1% head sampling: 50 MB/sec = 4.3 TB/day — manageable

After Sampling: Storage Sizing

  • Target: 10K traces/sec sampled (mix of head and tail-based)
  • 10K traces/sec × 50 spans × 1 KB = 500 MB/sec to storage
  • 500 MB/sec × 86,400 sec × 7 days = ~300 TB for 7-day hot tier
  • Cassandra: 3 TB per node (with replication factor 3 = 1 TB effective) → 300 nodes? Too expensive.
  • Revised: 10K traces/sec × 50 spans × 500 bytes (compressed) = 250 MB/sec = ~150 TB for 7 days. With replication factor 2: 300 TB total. ~100 nodes at 3 TB each.

Cassandra Write Throughput

  • 10K traces/sec × 50 spans = 500K writes/sec to Cassandra
  • Cassandra can handle ~50K–100K writes/sec per node → need 10 nodes minimum for writes
  • Storage needs 100 nodes → bottleneck is storage, not write throughput. Node count = 100.
💡 Senior Signal: Walk through the math publicly. At 1M req/sec the naive "store everything" answer costs PBs/day. The interviewer wants to see you derive the sampling rate from the storage budget, then reason about which traces MUST be kept (errors, slow outliers) vs which can be dropped (successful fast traces).

🗄️S — Schema3–5 min

Span Data Model

// The fundamental unit of tracing is a Span.
// A Trace is a tree of Spans sharing the same traceId.

public record Span(
    String traceId,       // 128-bit hex: "4bf92f3577b34da6a3ce929d0e0e4736"
    String spanId,        // 64-bit hex:  "00f067aa0ba902b7"
    String parentSpanId,  // null for root span (the entry point of the request)
    String operationName, // "HTTP GET /api/v1/users" or "PostgreSQL SELECT users"
    String serviceName,   // "payment-service"
    long startTimeEpochMicros,  // microsecond precision
    long durationMicros,
    SpanStatus status,    // OK | ERROR | UNSET
    Map<String, String> tags,   // key-value metadata: http.method, db.type, error.message
    List<SpanLog> logs,         // timestamped log messages within this span
    boolean isSampled            // whether this span should be exported
) {}

// W3C traceparent header format (propagated across service calls):
// "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
//  ^  ^                                ^                 ^
//  version  traceId (128-bit hex)      parentSpanId       flags (01 = sampled)

Cassandra Schema: Wide Row per Trace

// Cassandra is the right store for traces: one partition per traceId,
// all spans for that trace in the same partition = one read to get the full trace.

CREATE TABLE traces (
    trace_id         TEXT,
    span_id          TEXT,
    parent_span_id   TEXT,
    service_name     TEXT,
    operation_name   TEXT,
    start_time       TIMESTAMP,
    duration_us      BIGINT,
    status           TEXT,
    tags             MAP<TEXT, TEXT>,
    logs             LIST<FROZEN<span_log>>,
    PRIMARY KEY (trace_id, span_id)     -- partition key: trace_id; clustering key: span_id
) WITH default_time_to_live = 604800   -- 7-day TTL, automatic expiry
  AND compaction = { 'class': 'LeveledCompactionStrategy' };

-- Lookup by trace_id: one partition read, returns all spans. O(1).
SELECT * FROM traces WHERE trace_id = '4bf92f3577b34da6a3ce929d0e0e4736';

// Elasticsearch: separate index for tag-based search (by service, operation, duration, error)
// Cannot use Cassandra for this — Cassandra can only query by partition key efficiently.
PUT traces-search/_doc/{trace_id}
{
  "trace_id":       "4bf92f3577b34da6a3ce929d0e0e4736",
  "root_service":   "api-gateway",
  "root_operation": "HTTP GET /api/v1/users",
  "duration_ms":    342,
  "has_error":      true,

}

System Architecture

// ─── Instrumented Services ────────────────────────────────────────────────────
// Each service has the OpenTelemetry Java agent attached (-javaagent:otel-agent.jar)
// The agent auto-instruments: Spring MVC, JDBC, gRPC, Kafka, HTTP clients
// Spans are created and exported asynchronously (non-blocking to the request path)

// ─── Span Export Pipeline ────────────────────────────────────────────────────
// Service → OTel SDK (batches spans in-process) → Kafka topic: "spans.raw"
//   (Key = traceId — ensures all spans of a trace go to same Kafka partition)
//   (Value = Protobuf-serialized span batch)

// ─── Sampling Decision ───────────────────────────────────────────────────────
// Two sampling strategies (choose based on requirements):
//
// Head-based: Decision made at the ROOT SPAN (first service).
//   Propagated via traceparent flags bit (01 = sampled).
//   Downstream services ONLY export spans if the flag is set.
//   Pros: minimal overhead (unsampled spans never touch Kafka or storage).
//   Cons: cannot sample based on outcome (error status, latency) — unknown at start.
//
// Tail-based: ALL spans exported to a collector buffer.
//   After 30 seconds (max trace duration), the buffer applies rules:
//   - Keep if any span has status=ERROR
//   - Keep if root span duration > 2000ms (slow trace)
//   - Keep 1% of remaining (representative sample)
//   Pros: keeps ALL interesting traces (errors + slow).
//   Cons: requires buffering ALL spans for 30s — 50 GB/sec × 30s = 1.5 TB buffer. Expensive.

// ─── Span Processing (Flink) ─────────────────────────────────────────────────
// Consumes from Kafka → enriches spans (service → team owner lookup)
// For tail sampling: windows spans by traceId, applies sampling rules, emits kept traces
// Writes to Cassandra (all spans) and Elasticsearch (trace summary for search)

// ─── Storage ─────────────────────────────────────────────────────────────────
// Cassandra: full span data, partitioned by traceId, 7-day TTL
// Elasticsearch: trace summaries (1 doc per trace), searchable by all fields

// ─── Query Layer ─────────────────────────────────────────────────────────────
// Trace Search: Elasticsearch query → get list of trace_ids matching criteria
// Trace Detail: Cassandra read by trace_id → all spans → reconstruct the tree
// Service Map: Kafka Streams job builds service dependency graph from span parent/child

Context Propagation Across Service Boundaries

Every service-to-service call must propagate the trace context. The W3C traceparent header is the standard:

// HTTP/gRPC propagation:
// Outgoing request from Service A → Service B:
// Header: traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
//                       ^ version ^ traceId (128-bit)               ^ parentSpanId  ^ flags

// Service B reads the header, creates a child span:
// new span: traceId=4bf92f3577b34da6a3ce929d0e0e4736, parentSpanId=00f067aa0ba902b7, spanId=new_id

// Kafka message propagation:
// Producer adds to Kafka message headers:
//   "traceparent": "00-traceId-spanId-01"
// Consumer extracts from headers before processing, creates child span.
// This links the async processing trace to the original request trace.

// gRPC metadata propagation:
// OTel gRPC interceptor automatically reads/writes traceparent as gRPC metadata.
// No manual code required with auto-instrumentation.

Head-based vs Tail-based Sampling: The Key Tradeoff

💡 The Core Problem with Head-based Sampling: You make the keep/drop decision at the first service before the request has touched any downstream services. A 1% sample rate means 99% of traces are dropped. If an error occurs in a service at the end of the call chain, there is a 99% chance it was dropped by the head sampler — and you will never see the trace for it.

Tail-based sampling solves this by collecting all spans and making the decision after the trace completes:

  • All spans flow to a collector fleet (Kafka as the buffer)
  • The collector waits 30 seconds for trace completion (the maximum expected request duration)
  • Then applies rules: keep if error=true, keep if duration>2s, keep 0.1% of the rest
  • Cost: you must buffer all spans for 30 seconds. 50M spans/sec × 30s × 1 KB = 1.5 TB in-flight buffer. This is the storage cost of tail-based sampling. Manageable with a Kafka cluster, very expensive in RAM.

🔬D — Deep Dive10 min

1. Auto-instrumentation vs Manual Instrumentation

The OpenTelemetry Java agent uses bytecode weaving (via Java agent API) to automatically instrument known libraries without source code changes:

  • Agent instrumentation: Attach the OTEL Java agent jar at JVM startup: -javaagent:/opt/otel-javaagent.jar -Dotel.service.name=payment-service. The agent intercepts class loading and injects tracing code into Spring MVC controllers, RestTemplate/OkHttp clients, JDBC drivers, Kafka producers/consumers, gRPC stubs. Zero application code changes required.
  • What agent cannot do: Custom business spans ("time spent in pricing calculation"), custom tags ("customer_id", "order_amount"), custom events within a span. For these, developers add manual spans via the OTEL SDK API.
  • Manual instrumentation: Span span = tracer.spanBuilder("processPayment").startSpan(); try (Scope s = span.makeCurrent()) { ... span.setAttribute("amount_cents", 4999); } finally { span.end(); }
  • Why both: Agent gives you 80% coverage with zero effort. Manual instrumentation adds the 20% that matters most for business-specific debugging.

2. Tail-based Sampling: The Implementation Challenge

Tail-based sampling requires correlating all spans for a trace (which arrive from 50 different services over up to 30 seconds) before deciding whether to keep or drop the trace. The Kafka-based implementation:

// Key insight: use traceId as the Kafka partition key.
// All spans for the same trace go to the same partition → handled by the same consumer.
// This enables stateful windowing: one consumer accumulates all spans for a trace.

// Flink tail sampling job:
// 1. Consume from Kafka topic "spans.raw" (keyed by traceId)
// 2. KeyedProcessFunction: per-traceId state
// 3. For each incoming span: add to trace buffer in state
// 4. Set a timer for 30 seconds after the first span (max trace duration)
// 5. When timer fires:
//    - Does any span have status=ERROR? → KEEP
//    - Is root span duration > 2000ms? → KEEP
//    - Random(0,1) < 0.001 → KEEP (0.1% sample of remaining)
//    - Otherwise: DROP (discard all spans in buffer, release state)
// 6. For KEEP: emit all spans to the storage sink (Cassandra + ES)

3. Sampling Math and Storage Verification

Always verify your sampling math against storage constraints:

// Scenario: 1M req/sec, 50 spans each, tail-based sampling
//
// Without sampling:
// 1M × 50 spans = 50M spans/sec × 1 KB = 50 GB/sec → 4.3 PB/day
//
// With tail-based sampling rules:
// Error rate: ~0.5% of requests → 5,000 req/sec → 250K spans/sec (always kept)
// Slow traces: ~1% of requests > 2s → 10,000 req/sec → 500K spans/sec (kept)
// Remaining: ~990K req/sec → 0.1% random → 990 req/sec → 49.5K spans/sec (sampled)
// Total kept: 250K + 500K + 49.5K ≈ 800K spans/sec
// 800K × 1 KB × 86,400 sec = ~69 TB/day
// After LZ4 compression (5×): ~14 TB/day
// With replication factor 2: ~28 TB/day in Cassandra
// 28 TB/day × 7 days = 196 TB → ~65 nodes at 3 TB each
//
// This is within budget. Without tail sampling, it's 100× larger.

4. Service Dependency Map Construction

Jaeger and Zipkin both auto-generate service maps from trace data. The mechanism:

  • A Kafka Streams job (or Flink) reads all spans. For each span with a parent, it emits an edge: (parent.serviceName → span.serviceName)
  • These edges are aggregated into a call graph with counts and error rates. Stored in Redis (ZINCRBY for counts) with a 1-hour rolling window.
  • The service map API reads from Redis and returns the graph. Automatically shows new dependencies when a service starts calling a new service — no manual configuration.
  • This is one of the most valuable outputs of distributed tracing beyond individual trace debugging. It reveals hidden dependencies (service A calls service B's database directly) and helps capacity planning.

5. Adaptive Sampling

Fixed sampling rates create a problem: a service that normally handles 100 req/sec (low traffic) but suddenly spikes to 10K req/sec will overwhelm the collector. Adaptive sampling adjusts the rate to maintain a target throughput:

  • Target: 100 traces/sec per service regardless of traffic volume
  • If service handles 100 req/sec → 100% sample rate
  • If service handles 1,000 req/sec → 10% sample rate
  • If service handles 100,000 req/sec → 0.1% sample rate
  • Implementation: the sampling decision service monitors ingest rate per service (from a Kafka Streams count) and pushes rate adjustments to all SDK instances via the config service. SDKs receive the rate update via SSE (same pattern as feature flags).

✅E — Evaluate3 min

Performance Overhead Verification

The 1% overhead requirement for instrumentation must be verified in production. The overhead sources:

  • Span creation: Allocating a span object, recording start time (System.nanoTime() — ~20 ns). Across 50 spans per request: ~1 microsecond of CPU time. Negligible.
  • Context propagation: Reading/writing the traceparent header adds ~50 bytes to each HTTP request and ~200 ns of string manipulation. At 1,000 outgoing calls per second per service: ~200 microseconds total. Still negligible.
  • Span export (the real cost): The in-process SDK batches spans. Every 5,000 spans or 5 seconds (whichever comes first), a background thread serializes and sends to Kafka. This is off the critical path — the application thread never blocks waiting for export. The serialization cost is ~50 microseconds per batch, amortized across 5,000 spans = 10 nanoseconds per span.
  • Total overhead at 1% sampling: For unsampled spans (99% of traffic), the cost is one boolean check: if (flags != 01) return;. <1 ns. This is why head-based sampling is so efficient — unsampled spans are essentially free.
💡 Benchmark: Uber's Jaeger team measured OpenTelemetry Java agent overhead at ~0.03% additional CPU and <0.1% additional latency on a realistic microservices benchmark. The theoretical 1% limit is very conservative — real-world overhead is far lower.

Failure Modes

  • Cassandra hot partition: A single trace with 10,000 spans (e.g., a loop that spawned thousands of DB calls) creates a 10 MB Cassandra partition — the maximum recommended is 100 MB. Not an immediate problem but monitor for outlier traces. Mitigation: set a max spans-per-trace limit in the collector (discard spans after 1,000 per trace, log a warning).
  • Kafka consumer lag in tail sampler: If the Flink tail sampler falls behind, trace windows extend beyond 30 seconds and timer accuracy degrades. The trace is still eventually assembled but may include spans from the next minute. Mitigation: over-provision Flink workers; use Kafka partition count = Flink parallelism for linear scaling.
  • Clock skew between services: Span timestamps are generated by each service's local clock. If service A's clock is 500ms ahead of service B's, a child span appears to start before its parent. Mitigation: ensure NTP synchronization across all nodes; display spans using relative offsets from trace start, not absolute timestamps.
  • Elasticsearch index mapping explosion: Tags are stored as a map. If high-cardinality tag values (like user IDs) are mapped as Elasticsearch fields, mapping explosion occurs. Solution: map tags as a nested Elasticsearch type, not top-level fields.

🚀D — Deliver2 min

  • Trace model: Span = (traceId, spanId, parentSpanId, operationName, timestamps, tags). Trace = tree of spans sharing traceId.
  • Propagation: W3C traceparent header in HTTP/gRPC. Kafka message headers for async. OTel Java agent handles propagation automatically.
  • Pipeline: Service → OTel SDK (async batching) → Kafka (partitioned by traceId) → Flink tail sampler → Cassandra (full spans) + Elasticsearch (trace summary for search).
  • Sampling: Tail-based — keep all errors (status=ERROR), all slow traces (>2s), 0.1% random of the rest. Results in ~14 TB/day (compressed) from 50 GB/sec raw.
  • Storage: Cassandra wide row per traceId (7-day TTL, one partition read = complete trace). Elasticsearch for tag-based search queries.

⚖️Trade-offs

DimensionHead-based SamplingTail-based Sampling
Error trace coveragePoor — error traces dropped at same rate as normal tracesExcellent — all error traces kept, regardless of sample rate
Infrastructure costLow — unsampled spans never reach the collectorHigh — all spans must flow to collector for 30s before drop decision
Implementation complexityLow — flag in traceparent header propagates decision downstreamHigh — stateful windowing, timer management, trace assembly
Latency addedMinimal (<1 ms) — decision is localMinimal in app — decision is in collector pipeline, not app path
Use whenVery high volume where even collector pipeline is too expensiveDefault choice for most systems — guarantees you have error traces
DimensionCassandraElasticsearch
Primary access patternRead all spans for one trace (by traceId) — single partition readSearch traces by tag, service, duration — inverted index required
Write performanceExcellent — append-only writes, LSM tree, no index overheadGood — inverted index built asynchronously but adds write amplification
Storage efficiencyGood with compaction; TTL handled automaticallyHigh overhead (3–5× raw) for inverted index
Why both:Use both: Cassandra stores all span data; Elasticsearch stores only trace summaries (one doc per trace, not 50 spans). Search uses Elasticsearch to find trace IDs, then Cassandra to fetch the full trace. This hybrid gives O(1) trace retrieval with full-text search capability.

☕Java Implementation

/**
 * TracingFilter — servlet filter that extracts or creates trace context for each HTTP request.
 * Creates the root span for server-received requests.
 * Propagates context to downstream calls via TraceContext thread-local (set by OTel SDK).
 */
@Component
public class TracingFilter implements Filter {

    private static final String TRACEPARENT_HEADER = "traceparent";

    private final Tracer tracer;

    public TracingFilter(OpenTelemetry openTelemetry) {
        this.tracer = openTelemetry.getTracer("http-server", "1.0.0");
    }

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        HttpServletResponse httpResponse = (HttpServletResponse) response;

        // Extract parent context from incoming traceparent header (if present)
        // If no header: this is the root service — generate a new traceId
        Context parentContext = extractParentContext(httpRequest);

        String operationName = httpRequest.getMethod() + " " + httpRequest.getRequestURI();
        Span serverSpan = tracer.spanBuilder(operationName)
            .setParent(parentContext)
            .setSpanKind(SpanKind.SERVER)
            .startSpan();

        try (Scope scope = serverSpan.makeCurrent()) {
            serverSpan.setAttribute("http.method", httpRequest.getMethod());
            serverSpan.setAttribute("http.url", httpRequest.getRequestURI());
            serverSpan.setAttribute("service.name", "payment-service");

            chain.doFilter(request, response);

            int statusCode = httpResponse.getStatus();
            serverSpan.setAttribute("http.status_code", statusCode);
            if (statusCode >= 500) {
                serverSpan.setStatus(StatusCode.ERROR, "HTTP " + statusCode);
            }
        } catch (Exception exception) {
            serverSpan.setStatus(StatusCode.ERROR, exception.getMessage());
            serverSpan.recordException(exception);
            throw exception;
        } finally {
            serverSpan.end(); // CRITICAL: always end the span; open spans = memory leak
        }
    }

    private Context extractParentContext(HttpServletRequest request) {
        String traceparent = request.getHeader(TRACEPARENT_HEADER);
        if (traceparent == null) {
            return Context.root(); // generate new traceId
        }
        // W3C traceparent format: "00-traceId-parentSpanId-flags"
        TextMapGetter<HttpServletRequest> getter = new HttpServletRequestTextMapGetter();
        return W3CTraceContextPropagator.getInstance()
            .extract(Context.root(), request, getter);
    }
}

/**
 * KafkaSpanExporter — exports spans to Kafka asynchronously.
 * Replaces the default OTLP exporter for high-throughput environments.
 * Kafka provides better durability and backpressure handling than HTTP OTLP.
 */
public class KafkaSpanExporter implements SpanExporter {

    private static final String SPANS_TOPIC   = "spans.raw";
    private static final int    MAX_BATCH_SIZE = 512;

    private final KafkaProducer<String, byte[]> kafkaProducer;

    public KafkaSpanExporter(Properties kafkaProperties) {
        this.kafkaProducer = new KafkaProducer<>(kafkaProperties);
    }

    @Override
    public CompletableResultCode export(Collection<SpanData> spans) {
        CompletableResultCode result = new CompletableResultCode();
        List<SpanData> spanList = new ArrayList<>(spans);

        // Batch by traceId: all spans for the same trace to the same Kafka partition.
        // This is the critical property for tail-based sampling — same partition = same consumer.
        Map<String, List<SpanData>> byTraceId = spanList.stream()
            .collect(Collectors.groupingBy(span -> span.getTraceId()));

        byTraceId.forEach((traceId, traceSpans) -> {
            byte[] serializedSpans = serializeToProtobuf(traceSpans);
            ProducerRecord<String, byte[]> record =
                new ProducerRecord<>(SPANS_TOPIC, traceId, serializedSpans);
            kafkaProducer.send(record, (metadata, exception) -> {
                if (exception != null) {
                    // Log but don't block — tracing failures must never affect application
                    System.err.println("[SPAN_EXPORT_FAIL] " + exception.getMessage());
                }
            });
        });

        result.succeed();
        return result;
    }

    @Override
    public CompletableResultCode flush() {
        kafkaProducer.flush();
        return CompletableResultCode.ofSuccess();
    }

    @Override
    public CompletableResultCode shutdown() {
        kafkaProducer.close();
        return CompletableResultCode.ofSuccess();
    }

    private byte[] serializeToProtobuf(List<SpanData> spans) {
        // Serialize to OpenTelemetry Protobuf format (ExportTraceServiceRequest)
        // Using the OTEL SDK's built-in protobuf serialization
        ExportTraceServiceRequest protoRequest = SpanAdapter.toProtoResourceSpans(spans);
        return protoRequest.toByteArray();
    }
}

/**
 * SpanBuilder — utility for creating manual custom spans within application code.
 * Wraps the OTel SDK with a simpler API and consistent attribute naming.
 */
public class SpanBuilder {

    private final Tracer tracer;

    public SpanBuilder(OpenTelemetry openTelemetry, String instrumentationName) {
        this.tracer = openTelemetry.getTracer(instrumentationName);
    }

    /**
     * Wraps a supplier in a custom span. The span is automatically ended when the
     * supplier returns or throws. Tags are set as span attributes.
     */
    public <T> T withSpan(String operationName, Map<String, String> tags, Supplier<T> operation) {
        Span span = tracer.spanBuilder(operationName).startSpan();
        try (Scope ignored = span.makeCurrent()) {
            tags.forEach(span::setAttribute);
            T result = operation.get();
            span.setStatus(StatusCode.OK);
            return result;
        } catch (Exception exception) {
            span.setStatus(StatusCode.ERROR, exception.getMessage());
            span.recordException(exception);
            throw exception;
        } finally {
            span.end();
        }
    }
}
