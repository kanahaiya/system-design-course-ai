Tier 3 — Expert 60 minPlatform Architecture

Design Multi-tenant SaaS Platform

Multi-tenancy is about one platform serving many customers with guaranteed isolation. The three isolation models trade off cost, complexity, and isolation strength. The wrong choice is hard to reverse -- designing the tenant isolation model is the most important architectural decision in a SaaS system.

🏢 Salesforce, Slack, GitHub
⏱️ 60 min interview

❓R — Requirements3–5 min

Functional Requirements

  • Multiple tenants share the same infrastructure with logical isolation
  • Tenant data must never be visible to other tenants
  • Per-tenant customization: settings, feature flags, branding
  • Self-service tenant onboarding
  • Usage metering and billing per tenant

Non-Functional Requirements

  • Isolation: Tenant A can never read, write, or infer Tenant B data
  • Scale: 10K tenants, each with 0–100K users
  • Latency: tenant_id filtering must not add measurable latency

🔢E — Estimation3–5 min

  • 10K tenants × avg 10K users = 100M user records total
  • Shared schema: one DB table, tenant_id column on every row
  • Most SaaS: shared DB + row-level security for small/medium tenants; separate DB for enterprise

🗄️S — Schema3–5 min

// Shared schema model (most common for mid-market SaaS)
// Every table has tenant_id as first column in composite primary key
users:     (tenant_id, user_id) PRIMARY KEY, email, name, role
documents: (tenant_id, doc_id) PRIMARY KEY, title, content, owner_id
settings:  (tenant_id) PRIMARY KEY, plan, feature_flags, custom_config

// Row-level security (PostgreSQL RLS)
ALTER TABLE users ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON users
  USING (tenant_id = current_setting('app.current_tenant_id'));

// Thread-local tenant context (application layer)
// Set before every DB query: SET LOCAL app.current_tenant_id = 'tenant123'

🏗️H — High-level Design10 min

  • Model 1 — Shared DB + shared schema (tenant_id column): All tenants in same tables. RLS enforces isolation. Cheapest. Risk: misconfigured query leaks cross-tenant data.
  • Model 2 — Shared DB + separate schema (one schema per tenant): Schema isolation at DB level. Medium cost. Easy to migrate one tenant to their own DB later.
  • Model 3 — Separate DB per tenant: Strongest isolation. Most expensive. Required for regulated industries (healthcare, finance).
  • Hybrid (most common): SMB tenants share DB (Model 1). Enterprise tenants get dedicated DB (Model 3). Migration path: tenant grows → move to own DB.
  • Tenant context propagation: Middleware extracts tenant_id from JWT. Sets thread-local. Query interceptor automatically adds WHERE tenant_id = ? to all queries.

🔌A — APIs5 min

// Tenant Management API (admin only)
POST /api/v1/tenants           { name, plan, admin_email } -> { tenant_id, api_keys }
GET  /api/v1/tenants/{id}      -> { tenant settings, usage stats }
POST /api/v1/tenants/{id}/plan { plan: "enterprise" }  -- upgrade to dedicated DB

// All other APIs are tenant-scoped via JWT claim
// JWT payload: { sub: "user123", tenant_id: "tenant456", plan: "pro" }
// Gateway extracts tenant_id, passes to service as X-Tenant-Id header
// Service layer sets TenantContextHolder.setCurrentTenantId("tenant456")

🔬D — Deep Dive10 min

Preventing tenant data leakage (the critical requirement):

  1. Query interceptor: JPA/Hibernate entity listener or Spring AOP. Intercepts all queries. Injects AND tenant_id = ? automatically. Developers cannot forget to add tenant_id filter -- it is enforced by the framework.
  2. PostgreSQL Row-Level Security (RLS): DB-level enforcement. Even if the application bug forgets the filter, RLS blocks cross-tenant reads at the database. Defense in depth.
  3. Tenant-scoped access tokens: JWTs embed tenant_id as a claim. A user cannot create a valid token for a different tenant.
  4. Integration test: Always include a cross-tenant leakage test: tenant A token cannot access tenant B resources at any endpoint.

Noisy neighbor problem: Tenant A runs a heavy report query, degrading performance for all other tenants sharing the same DB. Mitigation: per-tenant query quotas, read replicas for analytics, automatic migration of high-volume tenants to dedicated DB instances.

✅E — Evaluate3 min

  • Schema migration at scale: ALTER TABLE with millions of rows and 10K tenants all sharing one table = potentially long lock time. Mitigation: online DDL, or feature flags to roll out new columns gradually.
  • Tenant onboarding: For shared schema: one row in tenants table + settings = minutes. For dedicated DB: provision DB instance, run migrations, configure connection pool = hours. Automate with Terraform + migration runner.

🚀D — Deliver2 min

Multi-tenant SaaS = shared schema (tenant_id column) + PostgreSQL RLS (DB-level backstop) + thread-local tenant context + query interceptor (auto-inject WHERE tenant_id). Hybrid model for scale: shared DB for SMB, dedicated DB for enterprise.

☕Java Implementation

/**
 * TenantContextHolder -- stores the current tenant_id in thread-local storage.
 * Set by HTTP middleware from JWT claim; read by the query interceptor.
 */
public class TenantContextHolder {
    private static final ThreadLocal<String> currentTenantId = new ThreadLocal<>();

    public static void setCurrentTenantId(String tenantId) { currentTenantId.set(tenantId); }

    public static String getCurrentTenantId() {
        String tenantId = currentTenantId.get();
        if (tenantId == null) {
            throw new IllegalStateException("No tenant context set -- missing tenant_id in JWT");
        }
        return tenantId;
    }

    public static void clear() { currentTenantId.remove(); } // MUST call in finally block
}

/**
 * TenantFilterInterceptor -- Spring MVC interceptor that sets tenant context.
 * Called before every controller method. Extracts tenant_id from JWT.
 */
@Component
public class TenantFilterInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        String jwtToken = extractBearerToken(request);
        if (jwtToken == null) { response.setStatus(401); return false; }
        String tenantId = extractTenantIdFromJwt(jwtToken);
        TenantContextHolder.setCurrentTenantId(tenantId);
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res, Object handler, Exception ex) {
        TenantContextHolder.clear(); // CRITICAL: prevent tenant context leaking to next request
    }

    private String extractBearerToken(HttpServletRequest request) {
        String authHeader = request.getHeader("Authorization");
        return (authHeader != null && authHeader.startsWith("Bearer "))
               ? authHeader.substring(7) : null;
    }

    private String extractTenantIdFromJwt(String token) {
        // Production: decode and verify JWT, extract "tenant_id" claim
        // Simplified: return claim from verified JWT payload
        return JwtUtils.getClaim(token, "tenant_id");
    }
}
