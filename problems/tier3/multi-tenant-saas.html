Tier 3 — Expert 60 minPlatform Architecture

Design Multi-tenant SaaS Platform

Multi-tenancy is about one platform serving many customers with guaranteed isolation. The three isolation models trade off cost, complexity, and isolation strength. The wrong choice is hard to reverse — designing the tenant isolation model is the most important architectural decision in a SaaS system. This is a Staff-level question: the interviewer wants to hear you reason about the operational consequences over years, not just the day-one implementation.

🏢 Salesforce, Snowflake, Slack, GitHub, Zendesk
⏱️ 60 min interview

❓R — Requirements3–5 min

Functional Requirements

  • Multiple tenants share the same application infrastructure with strict logical or physical isolation
  • Tenant A data must never be visible, writable, or inferable by Tenant B
  • Per-tenant customization: feature flags, branding, settings, role definitions
  • Self-service tenant onboarding with automated provisioning
  • Usage metering per tenant for billing (API calls, storage, compute)
  • Admin portal: view all tenants, override settings, trigger migrations, deactivate accounts
  • GDPR right-to-erasure: delete all data for a tenant or specific user on request

Non-Functional Requirements

  • Isolation: Tenant A can never read, write, or infer Tenant B data — at application layer and database layer
  • Scale: 10,000 tenants, each with 0–100K active users; top-tier enterprise tenants have 1M+ records
  • Latency: tenant_id filtering must not add measurable latency; p99 < 100ms for typical queries
  • Availability: 99.99% uptime; one tenant's DB failure must not cascade to others
  • Compliance: SOC 2, GDPR, HIPAA-readiness (for healthcare tenants)
  • Onboarding time: SMB tenant online within 60 seconds; enterprise tenant within 4 hours

Clarifying Questions to Ask the Interviewer

  • Do we need physical data residency (EU tenants' data must stay in EU datacenters)?
  • Are there regulated-industry tenants requiring HIPAA BAA or financial data segregation?
  • What is the expected tenant size distribution: thousands of small tenants vs. hundreds of enterprise?
  • Is schema-per-tenant customization a product requirement, or do all tenants share the same schema?

🔢E — Estimation3–5 min

Data Volume

  • 10,000 tenants × avg 10,000 users = 100M user records total
  • Each user record ~2 KB → 200 GB for user table alone
  • Enterprise tenants (top 1%) likely hold 80% of data (power-law distribution)
  • Shared schema: 100M rows in users table, indexed on (tenant_id, user_id)

Traffic

  • Assume 100M users, 10% DAU = 10M DAU
  • 10M DAU × 50 API calls/day = 500M API calls/day = ~5,800 RPS average
  • Peak: 10× average = 58,000 RPS at peak (morning login surge)
  • Write ratio: ~20% writes, 80% reads; DB writes = ~1,160 TPS average

Infrastructure Sizing (Shared Pool Model)

  • PostgreSQL: 3-node cluster (primary + 2 replicas). 200GB data fits on 1TB SSD per node with room for indexes and WAL.
  • Connection pooling (PgBouncer): 10K tenants × up to 5 concurrent connections = 50K connections. PgBouncer pools these into 200 real DB connections.
  • Redis for rate limiting: 10K tenants × 100 bytes per sliding window counter = 1 MB — trivial.
💡 Senior Signal: The interviewer wants you to reason about the long tail. Most tenants are tiny; a handful are enormous. The isolation model that works for 9,900 small tenants breaks for 100 enterprise giants. State the power-law assumption early and let it drive your hybrid model recommendation.

🗄️S — Schema3–5 min

Pool Model: Shared Tables with tenant_id

-- Every application table carries tenant_id as the first PK component.
-- Composite PK ensures uniqueness within a tenant's scope.
-- B-tree index on (tenant_id, created_at DESC) serves "list recent records" queries.

CREATE TABLE tenants (
    tenant_id    UUID PRIMARY KEY,
    name         VARCHAR(255) NOT NULL,
    plan         VARCHAR(50)  NOT NULL,  -- 'starter' | 'pro' | 'enterprise'
    data_region  VARCHAR(20)  NOT NULL,  -- 'us-east-1' | 'eu-west-1' for data residency
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    deleted_at   TIMESTAMPTZ,            -- soft-delete for GDPR erasure workflow
    settings     JSONB        NOT NULL DEFAULT '{}'
);

CREATE TABLE users (
    tenant_id    UUID         NOT NULL REFERENCES tenants(tenant_id),
    user_id      UUID         NOT NULL DEFAULT gen_random_uuid(),
    email        VARCHAR(320) NOT NULL,
    name         VARCHAR(255) NOT NULL,
    role         VARCHAR(50)  NOT NULL DEFAULT 'member',
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    anonymized_at TIMESTAMPTZ,           -- set on GDPR erasure; email/name replaced
    PRIMARY KEY (tenant_id, user_id)
);
CREATE UNIQUE INDEX idx_users_email ON users(tenant_id, email);

CREATE TABLE documents (
    tenant_id    UUID         NOT NULL,
    doc_id       UUID         NOT NULL DEFAULT gen_random_uuid(),
    owner_id     UUID         NOT NULL,  -- references users(user_id) within same tenant
    title        VARCHAR(512) NOT NULL,
    content      TEXT,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, doc_id)
);
CREATE INDEX idx_documents_tenant_updated ON documents(tenant_id, updated_at DESC);

-- Row-Level Security: DB-level backstop even if application layer has a bug
ALTER TABLE users     ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_users ON users
    USING (tenant_id = current_setting('app.current_tenant_id')::UUID);

CREATE POLICY tenant_isolation_documents ON documents
    USING (tenant_id = current_setting('app.current_tenant_id')::UUID);

-- Application sets this at the start of every transaction:
-- SET LOCAL app.current_tenant_id = 'xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx';

Bridge Model: Schema-per-Tenant (PostgreSQL Search Path)

-- Each tenant gets their own schema: tenant_abc123.users, tenant_abc123.documents
-- The application sets search_path before queries; no tenant_id column needed.
-- Allows per-tenant schema customization (adding custom columns).

SET search_path TO tenant_abc123, public;
-- All unqualified table references now resolve to tenant_abc123.users, etc.

-- Tenant schema provisioning at onboarding time:
CREATE SCHEMA tenant_abc123;
CREATE TABLE tenant_abc123.users (
    user_id   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email     VARCHAR(320) UNIQUE NOT NULL,
    name      VARCHAR(255) NOT NULL,
    role      VARCHAR(50)  NOT NULL DEFAULT 'member',
    created_at TIMESTAMPTZ  NOT NULL DEFAULT now()
    -- No tenant_id column needed — schema IS the isolation boundary
);

Metadata Tables (All Models)

-- Tenant routing metadata: maps tenant slug/subdomain to their data location
CREATE TABLE tenant_routing (
    tenant_slug  VARCHAR(63)  PRIMARY KEY,  -- 'acme' from acme.app.com
    tenant_id    UUID         NOT NULL,
    model        VARCHAR(20)  NOT NULL,     -- 'pool' | 'bridge' | 'silo'
    db_host      VARCHAR(255),              -- NULL for pool tenants (use shared pool)
    schema_name  VARCHAR(63),               -- NULL for pool tenants
    region       VARCHAR(20)  NOT NULL
);
-- This table is cached in Redis (TTL 5 min) — loaded on every request

🏗️H — High-level Design10 min

Figure: Three multi-tenancy isolation models — Silo (best isolation, highest cost) vs Bridge (schemas) vs Pool (shared tables, lowest cost)

The Three Isolation Models in Detail

Model 1 — Silo (Separate DB per Tenant)

Each tenant gets a dedicated database instance. The application maintains a connection string registry and routes each request to the correct DB. Used by Salesforce for their largest enterprise customers.

  • Security isolation: Maximum. DB-level access controls, no cross-tenant query possible even with a full application compromise.
  • Cost: Extremely high. 10,000 tenants = 10,000 DB instances minimum. AWS RDS minimum ~$25/month × 10,000 = $250K/month.
  • Operational complexity: Very high. Schema migrations must be applied to 10,000 DBs. A migration script that takes 1 second per DB takes 2.7 hours across the fleet.
  • Data residency: Easy. Provision the DB in the tenant's required region.
  • Noisy neighbor: Zero. Resources are not shared.

Model 2 — Bridge (Schema per Tenant)

All tenants share the same PostgreSQL instance but each has their own schema. The application sets search_path before queries. Used by Heroku's original multi-tenant Postgres offering.

  • Security isolation: Strong. PostgreSQL schema permissions prevent cross-schema access. search_path injection is the main attack vector (must validate tenant slugs).
  • Cost: Medium. One DB instance per cluster (maybe 100-200 tenants per cluster), each with separate schemas.
  • Schema customization: Excellent. Per-tenant migrations. Enterprise tenant can have extra columns without affecting others.
  • Operational complexity: Medium. Each new tenant requires CREATE SCHEMA + run migrations in the provisioning pipeline.
  • Limit: PostgreSQL practical limit is ~10,000 schemas per instance before catalog overhead degrades performance.

Model 3 — Pool (Shared Tables with tenant_id)

All tenants share the same tables. Every row has a tenant_id column. PostgreSQL Row-Level Security (RLS) enforces isolation. Used by the majority of mid-market SaaS (Zendesk, HubSpot core services).

  • Security isolation: Weakest by architecture. Defense-in-depth critical: application layer (query interceptor) + DB layer (RLS) + test layer (cross-tenant leakage tests).
  • Cost: Lowest. One DB cluster for thousands of tenants. All infrastructure is shared.
  • Noisy neighbor: Worst. One tenant's heavy query consumes shared DB resources.
  • Schema migrations: Easiest. One ALTER TABLE affects all tenants simultaneously.

Hybrid Model (Production Reality)

💡 How Salesforce actually does it: Free/starter tenants → pool. Pro tenants → bridge (schema per tenant within shared Postgres clusters). Enterprise tenants (>$100K ARR) → silo. Tenant onboarding into the right tier is fully automated. When a tenant upgrades from Pro to Enterprise, an automated job: (1) exports all data from shared schema, (2) provisions new dedicated DB in tenant's required region, (3) imports data, (4) runs smoke tests, (5) flips routing table entry, (6) deprecates shared schema slot.

Tenant Routing: From Request to Correct Database

Every API request must resolve to the correct data store before any business logic runs. There are three common resolution strategies:

  1. Subdomain parsing: acme.app.com → extract "acme" → Redis lookup → tenant metadata. Fast (Redis TTL=5min), but requires a wildcard TLS cert (*.app.com) and DNS configuration.
  2. JWT claim: JWT contains tenant_id claim. Validated and extracted by API gateway. Most common for API-first products. Eliminates one Redis lookup but requires JWT validation on every request anyway.
  3. API key lookup: X-API-Key: sk_live_abc123 → Redis lookup by key hash → tenant_id + plan + rate limit config. Necessary for server-to-server integrations where JWTs are not used.

Request Flow (Annotated)

// Request: GET acme.app.com/api/v1/users
// Header: Authorization: Bearer eyJ...

// Step 1: API Gateway (Kong/Nginx)
//   → Extract subdomain "acme"
//   → Redis GET tenant:acme → { tenant_id: "uuid-1", model: "bridge", schema: "tenant_acme" }
//   → Validate JWT signature, extract tenant_id claim — must match Redis result
//   → Rate check: Redis ZADD/ZCOUNT sliding window for tenant UUID
//   → Forward to app service with headers: X-Tenant-Id, X-Tenant-Schema, X-Tenant-Plan

// Step 2: Application Service
//   → TenantFilterInterceptor reads X-Tenant-Id, sets TenantContextHolder
//   → TenantDataSourceRouter.determineCurrentLookupKey() returns tenant_id or "shared"
//   → DataSource resolves to the correct connection pool
//   → Before every query: SET LOCAL app.current_tenant_id = 'uuid-1'
//   → RLS policy enforces tenant_id filter at DB level (defense in depth)

// Step 3: Response
//   → Data returned, TenantContextHolder.clear() called in finally block
//   → Metering: Redis INCR usage:tenant-uuid-1:api_calls:2024-01 (for billing)

🔬D — Deep Dive10 min

1. Preventing Tenant Data Leakage (Defense in Depth)

  1. Query interceptor (application layer): JPA/Hibernate @Filter or Spring AOP intercepts all repository calls and injects AND tenant_id = :currentTenantId. Developers cannot forget — the framework enforces it. Implementation: a TenantAwareHibernateInterceptor that adds the filter before every Session flush.
  2. PostgreSQL Row-Level Security (DB layer): Even if the application bug forgets the filter, the DB policy fires. Two independent layers means one bug does not equal a data breach. RLS uses current_setting('app.current_tenant_id') which the application sets via SET LOCAL at transaction start.
  3. Tenant-scoped access tokens: JWTs embed tenant_id as a signed claim. A user cannot forge a token for a different tenant without the signing key.
  4. Integration tests: Mandatory cross-tenant leakage test in CI: create resources as Tenant A, attempt to access with Tenant B's token at every endpoint, assert 403 or empty result. This test suite is the regression net against accidental RLS disablement during schema changes.

2. Noisy Neighbor Problem and Tenant Throttling

In the pool model, Tenant A running a heavy monthly export query can consume 80% of the shared DB's I/O, causing p99 latency spikes for all tenants. Mitigation layers:

  • Per-tenant rate limiting: Redis sliding window counter per tenant. Plan determines the limit: starter → 100 RPS, pro → 1,000 RPS, enterprise → 10,000 RPS. Enforced at the API gateway before hitting the DB.
  • Query quotas: pg_query_settings or connection-level statement timeout per tenant plan. Heavy analytics queries are routed to read replicas with statement_timeout = 30s.
  • Automatic shard migration: If a tenant's per-minute query count exceeds a threshold for 3 consecutive days, an automated job moves them to their own schema or dedicated DB. The flag that enables this is set in the tenant routing table; the application adapts without redeploy.
  • Resource isolation: For Kubernetes-hosted application services, assign each enterprise tenant to a dedicated pod group with its own resource quota. Shared tenants share a pool of pods.

3. Schema Migrations in Multi-tenant Systems

Adding a column to users in the pool model is one ALTER TABLE. In the bridge or silo model, it must run against 10,000 schemas/DBs. The strategies differ:

  • Pool model migrations: Use PostgreSQL's online DDL via pg_repack or Flyway with lock_timeout = 2s. Adding a nullable column with no default is instantaneous (no table rewrite). Never add a NOT NULL column with a default in one step on a large table — use three steps: (1) add nullable column, (2) backfill in batches, (3) add NOT NULL constraint.
  • Bridge model migrations: Flyway/Liquibase with a schema-iteration script. The migration runner iterates over all schema names in information_schema.schemata where schema_name LIKE 'tenant_%' and runs the migration in each. Rate-limited to 50 schemas/minute to avoid DB load spike.
  • Silo model migrations: Terraform + Ansible or a custom migration orchestrator. Each DB is an independent target. Rolling deployment: migrate 10% of DBs, monitor for errors, continue if clean. Rollback: Flyway undo or restore from snapshot.
  • Expand/Contract pattern: For breaking schema changes (renaming a column), use: (1) Expand — add the new column, write to both old and new; (2) Migrate — backfill new column from old; (3) Contract — stop writing to old column; (4) Delete — drop old column after next deploy. This enables zero-downtime migrations regardless of isolation model.

4. Tenant Onboarding Automation

Onboarding must be fully automated. Manual steps at scale (10K tenants) are operationally impossible. The provisioning pipeline for a bridge-model tenant:

// Provisioning pipeline (async, event-driven)

-- Invalidate Redis cache for this slug

// Step 5: Configure billing
billingService.createSubscription(tenant_id, plan, payment_method_id);

// Step 6: Warm caches
-- Prefetch settings and feature flags into Redis

// Step 7: Send onboarding email + emit TenantProvisionedEvent

// Total time: ~15 seconds for bridge model, ~4 hours for silo (DB provisioning)

5. GDPR Right-to-Erasure in Multi-tenant Systems

GDPR Article 17 requires that a user's personal data be deleted within 30 days of a verified erasure request. In a shared DB with millions of rows, this is non-trivial:

  • Soft delete + anonymization (preferred): Do not hard-delete rows (foreign key constraints, audit log integrity). Instead: set anonymized_at = now(), replace email with a hash, replace name with "Deleted User", nullify all other PII fields. The row remains for referential integrity but contains no personal data.
  • Hard delete for tenant-level erasure: When an entire tenant is deleted (tenant churns, GDPR deletion request), the pool model requires DELETE FROM every_table WHERE tenant_id = ?. Use a background job with batched deletes (1,000 rows/batch) to avoid lock contention. For silo model: drop the entire DB.
  • Backup handling: Backups are immutable. Document in DPA that backups are purged after the stated retention period (typically 35 days for daily backups). Erased data will naturally fall out when backups older than 35 days are purged.
  • Audit log: Keep an anonymized audit record "User (deleted) performed action X at timestamp Y." The user identity is gone; the action record is kept for compliance (SOC 2).

6. Data Partitioning for Non-relational Stores

When the SaaS uses Cassandra or DynamoDB alongside PostgreSQL:

  • Cassandra: tenant_id as partition key. All data for a tenant on the same vnodes. Risk: if one tenant has 100M rows, their partition is a hot partition. Mitigation: composite partition key (tenant_id, date_bucket) to spread large tenants across vnodes.
  • DynamoDB: tenant_id as PK prefix in sort key (USER#user_id) with tenant_id as hash key. Use DynamoDB's per-partition throughput limits (3,000 RCU / 1,000 WCU per partition) as a natural noisy-neighbor throttle.
  • Elasticsearch: Index-per-tenant for large enterprise customers; alias-based multi-tenant index for small tenants. Routing key = tenant_id ensures all tenant documents land on the same shard (fast reads), but creates hot shards for large tenants.

✅E — Evaluate3 min

Cross-tenant Leakage Test Suite (Required in CI)

The most important test category in any multi-tenant system is cross-tenant leakage tests. These must run in CI on every deploy and after every schema migration:

// Required test scenarios (run as integration tests against a real DB, not mocks):
// 1. GET /api/v1/users/{userId} with Tenant A JWT → 403 if userId belongs to Tenant B
// 2. GET /api/v1/documents (list) with Tenant A JWT → zero Tenant B documents in response
// 3. Simulate RLS disabled: rerun all tests → they must FAIL (proves the suite catches the bug)
// 4. Multi-threaded: two threads with different tenant tokens run concurrently
//    → confirm no cross-tenant data appears (catches ThreadLocal not-cleared bug)

@Test
void tenantBTokenCannotReadTenantAData() {
    String tenantAUserId = createUser(TENANT_A_TOKEN, "alice@acme.com");
    // Tenant B's token should see 403 or 404, never the actual user data
    given().header("Authorization", "Bearer " + TENANT_B_TOKEN)
        .get("/api/v1/users/" + tenantAUserId)
        .then()
        .statusCode(anyOf(is(403), is(404)));
}

What Can Go Wrong

  • RLS accidentally disabled during migration: A DBA runs ALTER TABLE users DISABLE ROW LEVEL SECURITY temporarily for a migration and forgets to re-enable it. Impact: all tenants' data exposed to any authenticated user. Mitigation: CI check that verifies RLS is ENABLED on all application tables before and after every migration.
  • Connection pool exhaustion: In the bridge model with PgBouncer, 10K tenants × 5 max connections each exceeds PgBouncer's pool. Mitigation: PgBouncer with session-mode pooling, max_client_conn = 10,000, pool_size = 200 per schema group. For silo model: Hikari CP with max pool size capped per DB.
  • Thread-local not cleared: If TenantContextHolder.clear() is not called in the finally block, thread pool reuse means the next request handled by that thread inherits the previous tenant's context. This is a data leakage bug that is intermittent and hard to reproduce in testing.
  • Schema migration timeout: Running ALTER TABLE on a 500M-row shared table during peak traffic takes a long time and holds a lock. Use lock_timeout = '2s'; the migration retries until it acquires the lock during a low-traffic window.

Scale Bottlenecks

  • Pool model at 100K tenants: The routing table lookup (Redis) becomes critical path. At 100K tenants, the metadata is still small (<100MB in Redis). The bottleneck is PostgreSQL connection count — move to a connection pooler like PgBouncer or pgpool-II.
  • Silo model at 10K tenants: Schema migration across 10K DBs requires parallelism. A naive sequential loop takes hours. Build a migration orchestrator that runs 100 DBs in parallel with error isolation (one failing migration does not block the rest).

🚀D — Deliver2 min

Multi-tenant SaaS architecture summary:

  • Isolation model: Hybrid — pool (tenant_id column + RLS) for SMB tenants, bridge (schema per tenant) for mid-market, silo (dedicated DB) for enterprise and regulated industries
  • Tenant routing: API gateway resolves subdomain/JWT claim to tenant metadata (Redis cache, 5-min TTL). Sets X-Tenant-Id header forwarded to all services.
  • Application layer: TenantContextHolder (ThreadLocal) + TenantDataSourceRouter (AbstractRoutingDataSource) + query interceptor (Hibernate @Filter). Three independent layers prevent data leakage.
  • Noisy neighbor: Redis sliding window rate limiter per tenant at gateway. Per-tenant statement_timeout at DB. Auto-migrate high-volume tenants to dedicated infrastructure.
  • Schema migrations: Expand/contract pattern for zero-downtime. Flyway with lock_timeout for pool model. Parallel migration orchestrator for silo model.
  • GDPR erasure: Anonymize (don't hard-delete) individual users. Batch hard-delete for tenant-level erasure. Backups fall out naturally within 35-day backup retention window.

☕Java Implementation

/**
 * TenantContextHolder — stores the current tenant_id in ThreadLocal storage.
 * Set by HTTP middleware from JWT claim; read by the query interceptor and data source router.
 * CRITICAL: clear() MUST be called in a finally block to prevent context leakage across requests.
 */
public final class TenantContextHolder {

    private static final ThreadLocal<String> currentTenantId = new ThreadLocal<>();

    private TenantContextHolder() {}

    public static void setCurrentTenantId(String tenantId) {
        if (tenantId == null || tenantId.isBlank()) {
            throw new IllegalArgumentException("tenantId must not be blank");
        }
        currentTenantId.set(tenantId);
    }

    public static String getCurrentTenantId() {
        String tenantId = currentTenantId.get();
        if (tenantId == null) {
            throw new TenantContextMissingException(
                "No tenant context set — JWT claim 'tenant_id' missing or middleware not applied"
            );
        }
        return tenantId;
    }

    public static void clear() {
        currentTenantId.remove(); // Prevents context leaking to the next request on this thread
    }
}

/**
 * TenantDataSourceRouter — Spring AbstractRoutingDataSource that routes DB connections
 * to the correct pool based on the current tenant's isolation model.
 * Pool tenants → shared DataSource. Bridge/silo tenants → tenant-specific DataSource.
 */
@Component
public class TenantDataSourceRouter extends AbstractRoutingDataSource {

    private final TenantRoutingRepository tenantRoutingRepository;
    private final DataSourceFactory dataSourceFactory;

    public TenantDataSourceRouter(
            TenantRoutingRepository tenantRoutingRepository,
            DataSourceFactory dataSourceFactory,
            DataSource sharedDataSource) {
        this.tenantRoutingRepository = tenantRoutingRepository;
        this.dataSourceFactory = dataSourceFactory;
        setDefaultTargetDataSource(sharedDataSource);
    }

    @Override
    protected Object determineCurrentLookupKey() {
        String tenantId = TenantContextHolder.getCurrentTenantId();
        TenantRouting routing = tenantRoutingRepository.findByTenantId(tenantId);
        // Pool tenants return null → falls through to defaultTargetDataSource (shared)
        if (routing.getModel() == IsolationModel.POOL) {
            return null;
        }
        // Bridge/silo tenants get their own DataSource, lazy-initialized on first access
        return ensureDataSourceRegistered(routing);
    }

    private String ensureDataSourceRegistered(TenantRouting routing) {
        String key = routing.getTenantId();
        if (!getResolvedDataSources().containsKey(key)) {
            DataSource dedicatedDataSource = dataSourceFactory.create(routing.getDbHost());
            addTargetDataSource(key, dedicatedDataSource); // Thread-safe via ConcurrentHashMap
        }
        return key;
    }
}

/**
 * TenantFilterInterceptor — Spring MVC interceptor.
 * Sets tenant context before controller execution; clears it after (in all paths).
 */
@Component
public class TenantFilterInterceptor implements HandlerInterceptor {

    private static final String HEADER_TENANT_ID = "X-Tenant-Id";

    @Override
    public boolean preHandle(HttpServletRequest request,
                              HttpServletResponse response,
                              Object handler) throws IOException {
        // API Gateway has already validated the JWT and extracted tenant_id into a header.
        // Never trust client-supplied tenant_id directly — the gateway is the trust boundary.
        String tenantId = request.getHeader(HEADER_TENANT_ID);
        if (tenantId == null || tenantId.isBlank()) {
            response.sendError(HttpServletResponse.SC_UNAUTHORIZED, "Missing tenant context");
            return false;
        }
        TenantContextHolder.setCurrentTenantId(tenantId);
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                 Object handler, Exception exception) {
        TenantContextHolder.clear(); // CRITICAL: always clear, even on exceptions
    }
}

/**
 * TenantRateLimiter — Redis sliding window rate limiter, per-tenant.
 * Uses Lua script for atomic check-and-increment.
 * Returns true if the request is allowed; false if the tenant is over quota.
 */
@Component
public class TenantRateLimiter {

    private static final int WINDOW_SECONDS = 60;

    // Lua script: atomic sliding window — safe even with Redis Cluster
    private static final String RATE_LIMIT_LUA = """
        local key = KEYS[1]
        local now = tonumber(ARGV[1])
        local window = tonumber(ARGV[2])
        local limit = tonumber(ARGV[3])
        local clearBefore = now - window * 1000
        redis.call('ZREMRANGEBYSCORE', key, '-inf', clearBefore)
        local count = redis.call('ZCARD', key)
        if count < limit then
            redis.call('ZADD', key, now, now)
            redis.call('EXPIRE', key, window)
            return 1
        end
        return 0
        """;

    private final StringRedisTemplate redisTemplate;
    private final TenantPlanService tenantPlanService;

    public TenantRateLimiter(StringRedisTemplate redisTemplate, TenantPlanService tenantPlanService) {
        this.redisTemplate = redisTemplate;
        this.tenantPlanService = tenantPlanService;
    }

    public boolean isAllowed(String tenantId) {
        int limitPerMinute = tenantPlanService.getRateLimitPerMinute(tenantId);
        String key = "ratelimit:" + tenantId + ":requests";
        long nowMillis = System.currentTimeMillis();

        Long result = redisTemplate.execute(
            RedisScript.of(RATE_LIMIT_LUA, Long.class),
            List.of(key),
            String.valueOf(nowMillis),
            String.valueOf(WINDOW_SECONDS),
            String.valueOf(limitPerMinute)
        );
        return Long.valueOf(1L).equals(result);
    }
}
