Design a Recommendation Engine

Recommendation is a two-stage funnel: candidate generation (retrieve top-K candidates from millions of items quickly using embeddings + ANN) followed by re-ranking (score each candidate with a rich feature set). Each stage optimizes for different trade-offs.

🏢 Netflix, Spotify, Amazon
⏱️ 60 min interview
🎯 100M items

❓R — Requirements3–5 min

Functional Requirements

  • Recommend items (products, songs, movies) based on user history and preferences
  • Handle cold-start: new users with no history, new items with no interactions
  • Real-time updates: recent interactions should influence recommendations quickly
  • Diversity: avoid recommending only the most popular items

Non-Functional Requirements

  • Scale: 100M users, 50M items, 10B interactions/day
  • Latency: Recommendation response <200ms
  • Offline training: Full model retrain daily; incremental update hourly

🔢E — Estimation3–5 min

  • 50M items × 128-dim float32 embedding = 25.6GB for all item embeddings → fits in GPU RAM for ANN index
  • 100M users × 128-dim user embeddings = 51.2GB → shard across multiple ANN servers
  • Candidate retrieval: ANN top-1000 in <10ms (HNSW index). Re-ranking: score 1000 candidates in <50ms.

🗄️S — Schema3–5 min

// User-item interactions (Cassandra — write-heavy, time-series)
interactions: (user_id, item_id, interaction_type, timestamp)
  // interaction_type: view, click, purchase, like, skip

// Embeddings (stored in Redis + ANN index like Faiss/Weaviate)
user_embeddings: user_id → 128-dim float vector
item_embeddings: item_id → 128-dim float vector
  // Updated by offline training job daily
  // Retrieved by ANN service for similarity search

// Pre-computed recommendations (Redis, 1hr TTL)
// Key: recs:{user_id}  Value: JSON list of item_ids
// Generated by offline batch job for all active users
// Fallback: popular items for new users (cold start)

🏗️H — High-level Design10 min

  • Offline Training (Spark + GPU cluster, daily): Reads interaction log from Cassandra/S3. Trains matrix factorization model (or neural collaborative filtering). Produces user/item embeddings. Writes to Redis + ANN index.
  • Candidate Generation (online, <10ms): Given user_id → fetch user embedding → ANN query (HNSW) → top-1000 similar item embeddings → candidate item IDs.
  • Re-ranking (online, <50ms): Score each of 1000 candidates using richer features (recency, context, diversity penalty, business rules). Return top-20.
  • Serving: Pre-computed recommendations in Redis for active users (batch update hourly). Online fallback via ANN for cache miss.
  • Cold start — new user: Serve popular items by category. After 5+ interactions, run online recommendation.
  • Cold start — new item: Use content-based features (item embeddings from item metadata) until interaction data accumulates.

🔌A — APIs5 min

GET /v1/recommendations?userId={}&context=homepage&limit=20
  Returns: [{ itemId, score, reason: "because_you_liked_X" }]

POST /v1/interactions
  Body: { userId, itemId, interactionType: view|click|purchase|skip, timestamp }
  // Async: publishes to Kafka for model updates

GET /v1/items/{itemId}/similar?limit=10
  // Item-to-item: find similar items (used for "You might also like")

🔬D — Deep Dive: Two-Tower Model + ANN10 min

Two-Tower Neural Network:

  • User tower: takes user features (history, demographics) → produces 128-dim user embedding
  • Item tower: takes item features (metadata, category, text description) → produces 128-dim item embedding
  • Similarity: cosine(user_embedding, item_embedding) = probability of interaction
  • Training: positive pairs (user, interacted_item) vs negative sampling (user, random_item)

ANN (Approximate Nearest Neighbor) search:

  • Exact search of 50M item embeddings for each query: O(50M × 128) = too slow
  • HNSW (Hierarchical Navigable Small World): graph-based index. Query: O(log N) comparisons. ~95% recall at 10ms latency vs 100% recall at 5s.
  • Faiss (Facebook): GPU-accelerated ANN. 50M items → index fits in 25GB GPU RAM → <5ms query.

Why approximate (ANN) not exact: Missing 5% of the optimal candidates is acceptable. If items 501-1000 would have appeared in exact search but not ANN, the re-ranker would likely not promote them above the top 20 anyway. The quality loss is negligible at scale.

✅E — Evaluate3 min

  • Filter bubble: Pure collaborative filtering amplifies popularity bias — popular items get more clicks → ranked higher → even more clicks. Mitigation: diversity penalty in re-ranker (penalize items too similar to already-shown items), exploration bucket (10% of recs are exploratory).
  • Real-time updates: Daily retraining means a user's purchases today don't affect recommendations until tomorrow. Mitigation: session-based recommendations layer on top using recent interaction sequence (e.g., last 10 items) to bias candidates in real-time.

🚀D — Deliver2 min

We designed a recommendation engine serving 100M users with <200ms latency. Key decisions: two-tower model for scalable embedding generation, HNSW/Faiss ANN for fast candidate retrieval, two-stage funnel (candidate generation + re-ranking), Redis pre-computed cache for active users, and content-based cold start fallback.

⚖️Trade-offs

DecisionChosenAlternativeWhy Chosen
Candidate retrievalANN (approximate)Exact nearest neighbor50M items: exact search takes seconds. ANN achieves 95% recall in 5ms. Quality loss negligible since re-ranker handles final ordering.
Model typeTwo-tower neural networkMatrix factorization (SVD)Two-tower: handles new items via content features (cold start). SVD: pure ID-based, can't handle cold start. Two-tower more complex but better coverage.
Serving strategyPre-computed + online fallbackAll-online inferencePre-computed: <1ms Redis read for 99% of requests. Online: 150ms for ANN+rerank. Pre-computed scales cheaply; online reserved for cache misses and new users.

☕Java Implementation

/**
 * CandidateRetriever — retrieves top-K candidate items for a user using
 * pre-computed embeddings and approximate nearest neighbor (ANN) search.
 */
public class CandidateRetriever {

    private static final int CANDIDATE_COUNT = 1000;
    private static final String USER_EMBEDDING_PREFIX = "embedding:user:";

    private final JedisPool jedisPool;
    private final AnnIndex itemAnnIndex; // Faiss/HNSW index loaded in memory

    public CandidateRetriever(JedisPool jedisPool, AnnIndex itemAnnIndex) {
        this.jedisPool = jedisPool;
        this.itemAnnIndex = itemAnnIndex;
    }

    /**
     * Returns top candidate items for a user by embedding similarity.
     * First fetches the user's embedding, then does ANN search over item space.
     *
     * @param userId  the user to generate recommendations for
     * @return list of candidate item IDs (unranked, to be passed to re-ranker)
     */
    public List<String> retrieveCandidates(String userId) {
        float[] userEmbedding = fetchUserEmbedding(userId);
        if (userEmbedding == null) {
            return retrieveColdStartCandidates();
        }
        return itemAnnIndex.findNearest(userEmbedding, CANDIDATE_COUNT);
    }

    /**
     * Fetches the user's embedding vector from Redis.
     * Embeddings are stored as binary-encoded float arrays for space efficiency.
     * Returns null if user has no embedding (new user → cold start).
     */
    private float[] fetchUserEmbedding(String userId) {
        try (Jedis jedis = jedisPool.getResource()) {
            byte[] embeddingBytes = jedis.get((USER_EMBEDDING_PREFIX + userId).getBytes());
            if (embeddingBytes == null) {
                return null;
            }
            return decodeBinaryToFloats(embeddingBytes);
        }
    }

    /**
     * Cold start: return popular items across categories as seed candidates.
     * These will be further filtered/ranked by the re-ranker.
     */
    private List<String> retrieveColdStartCandidates() {
        try (Jedis jedis = jedisPool.getResource()) {
            // Popular items pre-computed by a daily job
            return jedis.lrange("cold_start:popular_items", 0, CANDIDATE_COUNT - 1);
        }
    }

    /**
     * Decodes a packed binary float array stored in Redis.
     * Using binary encoding: 128 floats × 4 bytes = 512 bytes vs ~1KB for JSON.
     */
    private float[] decodeBinaryToFloats(byte[] bytes) {
        float[] floats = new float[bytes.length / Float.BYTES];
        ByteBuffer.wrap(bytes).order(ByteOrder.LITTLE_ENDIAN).asFloatBuffer().get(floats);
        return floats;
    }
}
