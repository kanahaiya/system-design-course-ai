Tier 3 — Expert 60 minML Systems

Design a Recommendation Engine (like Netflix / Amazon)

A recommendation engine at scale is a two-stage pipeline: candidate retrieval (fast, recall-oriented, top 500 from billions of items using ANN search over embeddings) followed by ranking (slower, precision-oriented, ML model with rich features on those 500). The retrieval-ranking split is the fundamental architectural insight. Understanding two-tower neural networks, ALS matrix factorization, and the cold start problem separates senior from staff.

🏢 Netflix, Amazon, YouTube, Spotify
⏱️ 60 min interview
📊 250M users, 500M items, <50ms serving

❓R — Requirements3–5 min

Functional Requirements

  • Personalized homepage recommendations: given a user, return N (typically 20-50) recommended items ordered by predicted relevance.
  • Similar items: given an item, return similar items. Used on product pages ("Customers also bought"), video detail pages ("More like this").
  • Real-time signal incorporation: user just watched/purchased/clicked item X → immediately boost items similar to X in the next recommendation call.
  • Context awareness: different recommendations for morning vs evening, mobile vs desktop, US vs India.
  • Diversity enforcement: avoid showing only the most popular items or only one genre. Mix in exploration to avoid filter bubbles.
  • Content-based fallback for cold start: new users with no history get recommendations based on demographic, location, or explicitly stated preferences.
  • A/B testing support: run multiple recommendation model variants simultaneously. Route traffic to models. Track CTR and engagement metrics per variant.

Non-Functional Requirements

  • Serving latency: recommendation API returns in <50ms p99 (user is waiting for the page to load).
  • Scale: 250M active users, 500M items (Amazon catalog), 15K movies (Netflix). Handle 10M recommendation requests/sec.
  • Freshness: model trained on interactions up to yesterday (batch pipeline), real-time signals incorporated within seconds.
  • Throughput: 10M QPS on recommendation serving. Model training: batch weekly or daily. Feature computation: near-real-time stream processing.
  • Accuracy: primary metric: CTR (click-through rate), watch time, or conversion rate. Evaluated via A/B test holdback groups.

Out of Scope

  • Model training infrastructure (Spark, TensorFlow — assumed to exist)
  • Content ingestion and metadata management
  • User authentication and session management

🔢E — Estimation3–5 min

Scale Numbers

  • User embeddings: 250M users × 64 dimensions × 4 bytes (float32) = 64GB. Fits in memory across a few serving nodes.
  • Item embeddings: 15K items (Netflix) × 64 dim × 4 bytes = trivial (~4MB). For Amazon's 500M items: 500M × 64 × 4 = 128GB — sharded across nodes.
  • ANN index (FAISS): 128GB item embeddings + HNSW index overhead (~3x) = ~400GB. Shard across 10 nodes with 40GB each (replication for HA).
  • Interaction log: 250M users × 50 interactions/day avg = 12.5B events/day = 145K events/sec. At 100 bytes/event: ~1.25TB/day. Stored in data lake (S3/GCS), hot 30-day window in columnar store.
  • Recommendation serving: 10M req/sec. Each request = user embedding lookup (1ms) + ANN search top-500 (5ms) + ranking model inference on 500 items (30ms) = ~36ms. Tight but achievable with GPU serving and batching.
💡 Why two stages instead of scoring all items directly? Scoring all 500M items with a complex ML model at <50ms is physically impossible. Even at 1 microsecond per item: 500M × 1μs = 500 seconds. The retrieval stage (ANN search) narrows 500M items to 500 candidates in ~5ms. The ranking stage scores only 500 items with a rich model in ~30ms. This 1M:1 funnel is the fundamental design insight for any large-scale recommendation system.

🔬D — Deep Dive10 min

Two-Tower Neural Network Architecture

Used by YouTube (2016 paper), Airbnb, Pinterest, and Google for production retrieval. The key insight: separate the user and item representations into two independent towers trained jointly to maximize the dot product for positive (user, item) pairs.

// Architecture:
//
//  User Tower                    Item Tower
//  ──────────────────────────    ──────────────────────────
//  Input: userId                 Input: itemId
//         recent_item_ids               category_embedding
//         demographic features          description_embedding
//         device_type                   popularity_score
//         time_of_day                   release_year
//         │                             │
//  [Embedding lookup]            [Embedding lookup]
//         │                             │
//  [Dense layers: 512→256→64]    [Dense layers: 512→256→64]
//         │                             │
//  User embedding: float[64]     Item embedding: float[64]
//
//                   ↓                 ↓
//         dot_product(user_emb, item_emb) = relevance_score
//
// Training objective: maximize dot product for observed (user, item) interactions
//   vs. randomly sampled negative pairs. Loss = cross-entropy or softmax over negatives.
//
// Why separate towers?
// 1. Pre-compute item embeddings offline once. Store in ANN index.
// 2. At serving time: only run user tower (fast, no item tower needed).
// 3. ANN search finds top-K items by maximum inner product (MIPS).
// 4. Total serving time: ~5ms for user tower + ~10ms for FAISS MIPS search over 500M items.
//
// Key training trick: in-batch negatives
// During training, the other items in the batch serve as negatives for each (user, item) pair.
// With batch size=512: each sample has 511 in-batch negatives. Very efficient, no need
// to separately mine hard negatives (though hard negatives from re-weighting improve quality).

Approximate Nearest Neighbor (ANN) Search

After training produces item embeddings, finding the top-500 items closest to a user embedding is a Maximum Inner Product Search (MIPS) problem over potentially 500M vectors. Exact nearest neighbor requires O(N) distance computations. ANN algorithms reduce this to O(log N) at the cost of small recall loss.

  • FAISS (Facebook): HNSW (Hierarchical Navigable Small World graphs) for approximate search. Recall@100 of 99% with <10ms search time over 100M vectors. Open source. Used by Elasticsearch, Pinecone, Weaviate internally.
  • ScaNN (Google): trained quantization for MIPS. Often faster than FAISS for large-scale MIPS. Used in Google Search.
  • HNSW algorithm: builds a multi-layer graph where each node connects to its nearest neighbors. Search starts at the top layer (coarse), follows edges to the correct region, then searches the bottom layer (fine). Like a skip list for nearest neighbors.
  • Trade-off: recall vs latency: FAISS HNSW is configurable. efConstruction (index build quality) and efSearch (query-time search width) control the recall-latency trade-off. Higher efSearch = higher recall, higher latency.

Cold Start Problem

Cold start is arguably the most important practical problem in recommendation systems:

  • New user (no interaction history): collaborative filtering has no signal. Solution: (1) use demographic/context features as user representation in two-tower model, (2) ask explicit preferences at onboarding ("What genres do you like?"), (3) show popularity-based recommendations ("trending in your country"), (4) use contextual bandit: explore different recommendation strategies, learn what works quickly.
  • New item (no interactions yet): collaborative filtering has no co-occurrence signal for this item. Solution: (1) content-based embedding from item metadata (genre, description, cast), (2) inject new items into retrieval results even without embedding similarity — ensure every new item gets at least N exposures before the collaborative model has data, (3) "warm-up" period: 30 days of interactions before fully relying on collaborative signal.
  • Power law reality: 20% of items get 80% of interactions. The long tail of 80% of items rarely appear in training data. Content-based fallback is essential for the tail. Collaborative filtering excels for the head (popular items) where data is rich.

Exploration vs Exploitation (Bandit Problem)

If you always recommend what the model thinks is best (exploit), users get stuck in a filter bubble. The model never learns whether new content would have been better. Exploration deliberately shows some "uncertain" recommendations to gather data.

  • ε-greedy: with probability ε (e.g., 10%), show a random item from a diverse set instead of the top recommendation. Simple. Does not adapt to which explorations are working.
  • Thompson sampling: maintain a distribution over each item's true click probability. Sample from the distribution; show the item with the highest sampled score. Items with high uncertainty have wide distributions, so they are sampled more until confidence narrows. More principled than ε-greedy.
  • Contextual bandits (LinUCB): model the expected reward as a function of context features (user features + item features). Upper confidence bound = expected reward + exploration bonus. Items that haven't been shown to this user type have high uncertainty, high UCB, so they get explored. Used by Yahoo! News for article recommendation (classic 2010 paper).
🟢 Real-time signal incorporation: When a user watches a movie, this should immediately affect their next recommendation — not wait for the daily model retrain. The pattern: (1) User watches item X → publish event to Kafka. (2) Streaming processor (Flink/Spark Streaming) updates user's recentItemIds in Redis within 1-2 seconds. (3) Recommendation serving reads recentItemIds from Redis on every request. (4) The "recent interactions retriever" finds items similar to recently watched items using a fast ANN lookup. This gives real-time personalization without model retraining.

A/B Testing Recommendation Models

You cannot evaluate a recommendation model offline (on held-out data) and trust the result. Offline metrics (AUC-ROC, precision@K) often don't correlate with online metrics (CTR, watch time, revenue). You need live A/B tests.

  • User-level splitting: assign each user to a model variant at random. Ensure the same user always sees the same model (deterministic hash). User-level splitting prevents cross-contamination — users don't see inconsistent recommendations.
  • Holdback group: keep 5-10% of users on the old model as a control group even after you're confident in the new model. This detects long-term effects (novelty effect: new model looks good initially, degrades as users get bored).
  • Guardrail metrics: besides primary metric (CTR), monitor guardrails: session length, return rate next day, content diversity. A model that maximizes CTR by showing clickbait damages long-term engagement — guardrails catch this.

🚀D — Deliver2 min

Summary for the interview:

A recommendation system is a two-stage funnel: (1) retrieval — fast ANN search over pre-computed embeddings finds top-500 candidates from billions of items in <10ms; (2) ranking — precision ML model (logistic regression or GBDT) scores 500 candidates with rich features in ~30ms. Total: <50ms. The retrieval stage runs multiple retrievers in parallel (collaborative + content-based + trending). Real-time signals feed through Kafka → Flink → Redis feature store. Cold start uses content-based embeddings from item metadata. Model improvements are evaluated via live A/B tests, not offline metrics alone.

Phased delivery:

  • Phase 1: Item-based collaborative filtering (item-item similarity from co-occurrence matrix). Simple, effective, no neural networks. Offline training.
  • Phase 2: ALS matrix factorization (Spark MLlib). Two-tier architecture. Feature store. <50ms serving.
  • Phase 3: Two-tower neural network. Real-time event streaming. Multi-armed bandit exploration. Full A/B testing infrastructure.

⚖️Trade-offs

DecisionOption AOption BRecommended
Collaborative vs content-based Collaborative: learns from user behavior, captures community taste, cold start problem for new items/users Content-based: works immediately for new items, no behavior data needed, can't discover user preferences for items in categories they haven't tried Hybrid: collaborative for warm users/items (80% of traffic), content-based fallback for cold start (20%). Use separate retrievers, blend in ranking.
Matrix factorization vs neural ALS/SVD: fast to train, interpretable latent factors, handles sparse data, no GPU needed Two-tower NN: higher accuracy, incorporates rich features, online learning possible, requires GPU training and serving ALS for initial system (simpler, proven). Two-tower as next iteration after baseline metrics are established. Don't optimize prematurely.
Online vs offline learning Offline batch training (daily/weekly): stable, reproducible, easy to debug, stale model Online learning (update model continuously): fresher model, captures trends, training instability, harder to debug Offline training + real-time feature updates (recentItemIds in Redis). Full online model training is complex; start with offline and add real-time features.
Single ranker vs cascade Single ranker: simpler, one model to maintain Cascade: light pre-ranker on 500 → top 50, then heavy ranker on 50. Lower latency for heavy models. Single ranker if <50ms budget allows (usually does). Cascade only if ranking model is so complex it can't score 500 items in budget.

☕Java Implementation

/**
 * AlsMatrixFactorization — simplified 2-factor ALS implementation.
 * Production uses Spark MLlib ALS with 50-200 factors, but the core algorithm is identical.
 *
 * ALS alternates between:
 *   1. Fix item factors → solve for each user's factors (least squares)
 *   2. Fix user factors → solve for each item's factors (least squares)
 * Repeating until convergence, typically 10-20 iterations.
 */
public class AlsMatrixFactorization {

    private static final int NUM_FACTORS = 2;
    private static final double LAMBDA = 0.01;  // L2 regularization to prevent overfitting
    private static final int MAX_ITERATIONS = 20;

    private double[][] userFactors;   // userFactors[userId][factor]
    private double[][] itemFactors;   // itemFactors[itemId][factor]

    /**
     * Trains the model on an interaction matrix where entries are implicit feedback weights.
     * rating[userId][itemId] = 1.0 if interaction exists, else 0.0 (implicit feedback).
     *
     * @param interactions sparse interaction matrix: Map<userId, Map<itemId, weight>>
     * @param numUsers     total number of users
     * @param numItems     total number of items
     */
    public void train(Map<Integer, Map<Integer, Double>> interactions,
                      int numUsers, int numItems) {
        userFactors = initializeFactors(numUsers);
        itemFactors = initializeFactors(numItems);

        for (int iteration = 0; iteration < MAX_ITERATIONS; iteration++) {
            // Step 1: Fix item factors, update all user factors
            for (int userId = 0; userId < numUsers; userId++) {
                Map<Integer, Double> userInteractions = interactions.getOrDefault(userId, Map.of());
                userFactors[userId] = solveForFactors(itemFactors, userInteractions);
            }

            // Step 2: Fix user factors, update all item factors
            Map<Integer, Map<Integer, Double>> transposedInteractions = transpose(interactions, numItems);
            for (int itemId = 0; itemId < numItems; itemId++) {
                Map<Integer, Double> itemInteractions = transposedInteractions.getOrDefault(itemId, Map.of());
                itemFactors[itemId] = solveForFactors(userFactors, itemInteractions);
            }
        }
    }

    /**
     * Predicts relevance score for a (user, item) pair.
     * Score = dot product of user factors and item factors.
     */
    public double predict(int userId, int itemId) {
        double[] userFactor = userFactors[userId];
        double[] itemFactor = itemFactors[itemId];
        double dotProduct = 0;
        for (int factorIndex = 0; factorIndex < NUM_FACTORS; factorIndex++) {
            dotProduct += userFactor[factorIndex] * itemFactor[factorIndex];
        }
        return dotProduct;
    }

    private double[] solveForFactors(double[][] fixedFactors,
                                     Map<Integer, Double> interactions) {
        // Closed-form solution: (A^T W A + λI)^-1 A^T W r
        // Where A = item factor matrix, W = diagonal confidence matrix, r = rating vector
        // Simplified for 2 factors using direct formula
        double[][] ata = new double[NUM_FACTORS][NUM_FACTORS];
        double[] atr = new double[NUM_FACTORS];

        for (Map.Entry<Integer, Double> entry : interactions.entrySet()) {
            int otherIndex = entry.getKey();
            double rating = entry.getValue();
            double confidence = 1.0 + 40 * rating;  // ALS confidence: 1 + α × rating

            double[] factor = fixedFactors[otherIndex];
            for (int row = 0; row < NUM_FACTORS; row++) {
                for (int col = 0; col < NUM_FACTORS; col++) {
                    ata[row][col] += confidence * factor[row] * factor[col];
                }
                atr[row] += confidence * rating * factor[row];
            }
        }

        // Add L2 regularization to diagonal
        for (int diag = 0; diag < NUM_FACTORS; diag++) {
            ata[diag][diag] += LAMBDA;
        }

        return solve2x2(ata, atr);
    }

    private double[] solve2x2(double[][] matrix, double[] vector) {
        // Direct solution for 2x2 system: [a b; c d] [x; y] = [e; f]
        double determinant = matrix[0][0] * matrix[1][1] - matrix[0][1] * matrix[1][0];
        if (Math.abs(determinant) < 1e-10) return new double[NUM_FACTORS];
        return new double[]{
            (matrix[1][1] * vector[0] - matrix[0][1] * vector[1]) / determinant,
            (matrix[0][0] * vector[1] - matrix[1][0] * vector[0]) / determinant
        };
    }

    private double[][] initializeFactors(int count) {
        double[][] factors = new double[count][NUM_FACTORS];
        Random random = new Random(42);
        for (double[] factor : factors) {
            for (int i = 0; i < NUM_FACTORS; i++) {
                factor[i] = random.nextGaussian() * 0.1;
            }
        }
        return factors;
    }

    private Map<Integer, Map<Integer, Double>> transpose(
            Map<Integer, Map<Integer, Double>> interactions, int numItems) {
        Map<Integer, Map<Integer, Double>> transposed = new HashMap<>();
        for (Map.Entry<Integer, Map<Integer, Double>> userEntry : interactions.entrySet()) {
            for (Map.Entry<Integer, Double> itemEntry : userEntry.getValue().entrySet()) {
                transposed.computeIfAbsent(itemEntry.getKey(), k -> new HashMap<>())
                          .put(userEntry.getKey(), itemEntry.getValue());
            }
        }
        return transposed;
    }
}

// ─────────────────────────────────────────────────────────────────────────────
// TwoTowerScorer — dot product scoring using pre-computed user/item embeddings.
// At serving time: only compute user tower, then ANN search. This class shows
// the full scoring path including retrieval (linear scan for small catalogs).
// ─────────────────────────────────────────────────────────────────────────────
public class TwoTowerScorer {

    private final Map<String, float[]> userEmbeddings;  // userId → embedding vector
    private final Map<String, float[]> itemEmbeddings;  // itemId → embedding vector

    public TwoTowerScorer(Map<String, float[]> userEmbeddings,
                          Map<String, float[]> itemEmbeddings) {
        this.userEmbeddings = Map.copyOf(userEmbeddings);
        this.itemEmbeddings = Map.copyOf(itemEmbeddings);
    }

    /**
     * Retrieves top-K items for a user by maximum inner product search.
     * In production: replace this with FAISS/ScaNN ANN index lookup.
     *
     * @param userId  user to recommend for
     * @param topK    number of candidates to retrieve
     * @return list of itemId sorted by descending relevance score
     */
    public List<String> retrieveTopK(String userId, int topK) {
        float[] userEmbedding = userEmbeddings.get(userId);
        if (userEmbedding == null) {
            return List.of();  // Cold start: no embedding
        }

        // Score all items (linear scan — in production: FAISS MIPS search)
        return itemEmbeddings.entrySet().stream()
            .map(entry -> Map.entry(entry.getKey(), dotProduct(userEmbedding, entry.getValue())))
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .limit(topK)
            .map(Map.Entry::getKey)
            .collect(Collectors.toList());
    }

    /** Computes dot product of two float vectors. */
    private double dotProduct(float[] vectorA, float[] vectorB) {
        double result = 0;
        for (int dimensionIndex = 0; dimensionIndex < vectorA.length; dimensionIndex++) {
            result += vectorA[dimensionIndex] * vectorB[dimensionIndex];
        }
        return result;
    }
}

// ─────────────────────────────────────────────────────────────────────────────
// CandidateRanker — logistic regression ranker for the ranking stage.
// Takes top-500 candidates from retrieval, scores with rich features, returns top-N.
// ─────────────────────────────────────────────────────────────────────────────
public class CandidateRanker {

    // Feature weights learned during offline training
    // Features: [relevance_score, popularity, freshness, quality, category_match, ...]
    private final double[] featureWeights;
    private final double bias;

    public CandidateRanker(double[] featureWeights, double bias) {
        this.featureWeights = featureWeights;
        this.bias = bias;
    }

    /**
     * Re-ranks candidates from retrieval stage using rich features.
     *
     * @param candidates    items from retrieval stage with their feature vectors
     * @param topN          number of final recommendations to return
     * @return top-N item IDs sorted by ranking score descending
     */
    public List<String> rank(List<CandidateItem> candidates, int topN) {
        return candidates.stream()
            .map(candidate -> Map.entry(candidate.itemId(), scoreCandidate(candidate)))
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .limit(topN)
            .map(Map.Entry::getKey)
            .collect(Collectors.toList());
    }

    private double scoreCandidate(CandidateItem candidate) {
        double[] features = candidate.features();
        double logit = bias;
        for (int featureIndex = 0; featureIndex < featureWeights.length; featureIndex++) {
            logit += featureWeights[featureIndex] * features[featureIndex];
        }
        // Sigmoid function → probability of click/watch
        return 1.0 / (1.0 + Math.exp(-logit));
    }

    public record CandidateItem(String itemId, double retrievalScore, double[] features) {}
}

/**
 * RealtimeFeaturePipeline — processes user interaction events and updates
 * the user's recent interaction list in Redis for real-time recommendation signals.
 *
 * Flink/Kafka consumer pattern: one event → update Redis → available to serving in <2s.
 */
public class RealtimeFeaturePipeline {

    private static final int MAX_RECENT_ITEMS = 50;  // Keep last 50 interactions
    private static final int RECENT_ITEMS_TTL_SECONDS = 7 * 24 * 3600;  // 7 days

    private final JedisPool jedisPool;

    public RealtimeFeaturePipeline(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }

    /**
     * Processes a user interaction event and updates real-time features in Redis.
     * Called by Kafka consumer for each interaction event.
     *
     * @param event the interaction event (watch, click, purchase, thumbs up)
     */
    public void processEvent(InteractionEvent event) {
        // Only update recent items for meaningful positive signals
        if (!isPositiveSignal(event.eventType())) return;

        String redisKey = "user:recent:" + event.userId();

        try (Jedis jedis = jedisPool.getResource()) {
            // Redis List with LPUSH (prepend) + LTRIM (keep only last N)
            // Atomic: both commands execute before any other client can read
            Pipeline pipeline = jedis.pipelined();
            pipeline.lpush(redisKey, event.itemId().toString());
            pipeline.ltrim(redisKey, 0, MAX_RECENT_ITEMS - 1);  // Keep last 50
            pipeline.expire(redisKey, RECENT_ITEMS_TTL_SECONDS);  // Refresh TTL
            pipeline.sync();
        } catch (JedisException redisError) {
            System.err.println("[RealtimeFeaturePipeline] Redis update failed for user " +
                event.userId() + ": " + redisError.getMessage());
            // Fail gracefully: recommendation quality degrades slightly but system stays up
        }
    }

    private boolean isPositiveSignal(InteractionEvent.EventType eventType) {
        return switch (eventType) {
            case WATCH, PURCHASE, THUMBS_UP, CLICK -> true;
            case SKIP, THUMBS_DOWN -> false;  // Don't add negative signals to recent list
        };
    }
}

/**
 * RecommendationService — orchestrates the full two-stage retrieval + ranking pipeline.
 * Runs all retrievers in parallel for minimum latency.
 */
public class RecommendationService {

    private final TwoTowerScorer collaborativeScorer;
    private final TwoTowerScorer contentBasedScorer;
    private final CandidateRanker ranker;
    private final JedisPool jedisPool;
    private final ExecutorService retrieverExecutorService;

    private static final int RETRIEVAL_CANDIDATE_COUNT = 500;
    private static final int FINAL_RECOMMENDATION_COUNT = 20;
    private static final int RETRIEVAL_TIMEOUT_MS = 15;

    public RecommendationService(TwoTowerScorer collaborativeScorer,
                                  TwoTowerScorer contentBasedScorer,
                                  CandidateRanker ranker,
                                  JedisPool jedisPool) {
        this.collaborativeScorer = collaborativeScorer;
        this.contentBasedScorer = contentBasedScorer;
        this.ranker = ranker;
        this.jedisPool = jedisPool;
        this.retrieverExecutorService = Executors.newFixedThreadPool(4);
    }

    /**
     * Returns top-N personalized recommendations for a user.
     * Parallel retrieval from multiple sources → deduplicate → rank → return top N.
     *
     * @param userId    user requesting recommendations
     * @param context   request context (homepage, similar_items, etc.)
     * @return ordered list of recommended item IDs
     */
    public List<String> recommend(String userId, String context) {
        // Phase 1: Parallel retrieval from all sources
        List<String> recentItemIds = getRecentItemIds(userId);

        CompletableFuture<List<String>> collaborativeFuture = CompletableFuture.supplyAsync(
            () -> collaborativeScorer.retrieveTopK(userId, RETRIEVAL_CANDIDATE_COUNT / 2),
            retrieverExecutorService
        ).orTimeout(RETRIEVAL_TIMEOUT_MS, TimeUnit.MILLISECONDS)
         .exceptionally(retrievalError -> List.of());

        CompletableFuture<List<String>> recentSimilarFuture = CompletableFuture.supplyAsync(
            () -> retrieveSimilarToRecent(recentItemIds, RETRIEVAL_CANDIDATE_COUNT / 4),
            retrieverExecutorService
        ).orTimeout(RETRIEVAL_TIMEOUT_MS, TimeUnit.MILLISECONDS)
         .exceptionally(retrievalError -> List.of());

        CompletableFuture<List<String>> trendingFuture = CompletableFuture.supplyAsync(
            () -> retrieveTrending(RETRIEVAL_CANDIDATE_COUNT / 4),
            retrieverExecutorService
        ).orTimeout(RETRIEVAL_TIMEOUT_MS, TimeUnit.MILLISECONDS)
         .exceptionally(retrievalError -> List.of());

        // Wait for all retrievers
        CompletableFuture.allOf(collaborativeFuture, recentSimilarFuture, trendingFuture).join();

        // Phase 2: Merge and deduplicate candidates
        Set<String> seenItemIds = new LinkedHashSet<>();
        seenItemIds.addAll(collaborativeFuture.join());
        seenItemIds.addAll(recentSimilarFuture.join());
        seenItemIds.addAll(trendingFuture.join());

        // Remove already-watched items
        Set<String> watchedItemIds = new HashSet<>(recentItemIds);
        List<String> deduplicatedCandidates = seenItemIds.stream()
            .filter(itemId -> !watchedItemIds.contains(itemId))
            .collect(Collectors.toList());

        if (deduplicatedCandidates.isEmpty()) {
            return retrieveTrending(FINAL_RECOMMENDATION_COUNT);  // Fallback
        }

        // Phase 3: Rank candidates
        List<CandidateRanker.CandidateItem> candidatesWithFeatures =
            hydrateCandidateFeatures(deduplicatedCandidates, userId);

        return ranker.rank(candidatesWithFeatures, FINAL_RECOMMENDATION_COUNT);
    }

    private List<String> getRecentItemIds(String userId) {
        try (Jedis jedis = jedisPool.getResource()) {
            List<String> recentIds = jedis.lrange("user:recent:" + userId, 0, 49);
            return recentIds != null ? recentIds : List.of();
        } catch (JedisException redisError) {
            System.err.println("[RecommendationService] Failed to get recent items for " +
                userId + ": " + redisError.getMessage());
            return List.of();
        }
    }

    private List<String> retrieveSimilarToRecent(List<String> recentItemIds, int topK) {
        if (recentItemIds.isEmpty()) return List.of();
        // Find items similar to the most recently watched item (strongest signal)
        String mostRecentItemId = recentItemIds.get(0);
        return contentBasedScorer.retrieveTopK(mostRecentItemId, topK);
    }

📚Advanced Recommendation Patterns

Feature Store: Bridging Offline Training and Online Serving

The feature store is a critical infrastructure component that ensures features used during model training are identically computed at serving time (the "training-serving skew" problem).

// Feature store architecture:
//
// Offline (batch):
// Spark job computes features for all users/items → writes to feature store
// Feature store has two storage layers:
//   Hot layer (Redis): most recent user features (last interaction, current session)
//   Cold layer (Cassandra/BigTable): full historical features, item catalog features
//
// Online (serving):
// Recommendation server reads features from feature store at serving time
// Must be identical computation to what was used during training
//
// The skew problem without a feature store:
//   Training: "days_since_last_purchase" computed in Spark as (train_date - last_purchase_date)
//   Serving:  "days_since_last_purchase" computed in Java as (now - last_purchase_timestamp)
//   Dates/timezones/rounding may differ → model receives different feature values → poor predictions
//
// Feature store solves this: features are computed ONCE by the batch pipeline,
// stored with a timestamp, and served identically to both training and inference.
//
// Example: user feature vector at serving time
// {
//   "user_id": "user_123",
//   "embedding": [0.12, -0.45, 0.78, ...],     // from latest model training run
//   "recent_item_ids": ["movie_456", "movie_789"],  // updated by streaming pipeline (Redis)
//   "days_active_last_30": 18,                      // batch feature (Cassandra)
//   "preferred_genres": ["action", "sci-fi"],        // batch feature
//   "avg_watch_completion_pct": 0.72                 // batch feature
// }

Diversity and Serendipity in Recommendations

Pure relevance maximization creates a "filter bubble" — users see only variations of what they've already consumed. Diversity enforcement is important for long-term engagement and discovery:

  • Category diversity: after ranking, apply a maximum of K recommendations per category. "At most 3 action movies, at most 3 comedies" in a set of 20 recommendations. Simple and effective.
  • DPP (Determinantal Point Process): a principled probabilistic model for diverse subset selection. DPP selects a set of items that are individually relevant AND collectively diverse. Commonly used at Pinterest, Yelp, and Google. More principled than greedy post-ranking filters but computationally heavier.
  • Serendipity vs relevance: serendipity = surprise + relevance. Items the user probably hasn't seen but would enjoy based on latent signal. Measured by: fraction of recommendations outside the user's typical consumption pattern. Tunable as a hyperparameter in the ranking stage (boost items with high content-based score but low collaborative-filtering history).
  • Freshness injection: reserve 5-10% of recommendation slots for recently added content regardless of model score. Ensures new content gets exposure. Surface the fact that it's "new" in the UI ("Just added" badge) to set user expectations.

Multi-Armed Bandit vs Full A/B Test: When to Use Each

A/B testing allocates fixed traffic to each variant for the duration of the experiment. Multi-armed bandits adaptively allocate more traffic to the better-performing variant as the experiment runs. The trade-off:

  • A/B test: simple, statistically clean (power calculation, hypothesis test at end). Best for major model launches where you need a definitive answer with controlled statistical properties. A/B tests should not be ended early even if one variant looks better — "peeking" inflates false positive rate.
  • Multi-armed bandit: faster learning, less regret (fewer users exposed to the worse variant). Best for hyperparameter tuning (which content type for cold start recommendation?), UI variants (button color, ranking display order). Thompson sampling is the most principled bandit algorithm for recommendation contexts.
  • Contextual bandit: combines bandit exploration with per-user context features. The same arm may be best for user type A and worst for user type B. Netflix uses contextual bandits to optimize artwork selection (which movie thumbnail to show) per user, achieving significant CTR improvements over fixed artwork.

Handling Popularity Bias and Algorithmic Fairness

Recommendation systems trained on engagement data amplify popularity: items that were popular in training data get recommended more → get more engagement data → become even more popular. This is a positive feedback loop that harms the long tail and new content.

  • Inverse propensity scoring (IPS): during training, weight samples from popular items lower (they're over-represented). Weight samples from rare items higher. Debiases the model toward predicting preferences, not just reflecting historical popularity distribution.
  • Provider fairness: content creators (individual youtubers, small publishers) vs large studios. Pure engagement metrics favor large studios (better production, larger existing audiences). Fairness-aware ranking can enforce minimum exposure per content creator category.
  • User fairness: ensure recommendations are equally good quality for all demographic groups. If the model performs significantly worse for women vs men, or for non-English speakers vs English speakers, this is a measurable fairness violation. Track precision@K, recall@K, and NDCG separately per demographic slice.
