Tier 3 — Expert 60 minInfrastructure

Design an API Gateway (like AWS API Gateway / Kong)

An API gateway is a reverse proxy that implements a composable plugin pipeline: TLS termination, authentication, rate limiting, request transformation, routing, load balancing, circuit breaking, and response transformation. The gateway is in the hot path of every external request, so correctness, latency, and fault tolerance are all critical. Understanding plugin ordering, JWT vs opaque token trade-offs, and how the gateway relates to a service mesh separates senior from staff-level answers.

🏢 Kong, AWS API Gateway, Nginx, Envoy
⏱️ 60 min interview
📊 1M req/sec, <5ms overhead, 99.999% SLA

❓R — Requirements3–5 min

Functional Requirements

  • Request routing: route to backend services based on URL path, HTTP method, and host header. Support path-based, header-based, and weighted routing.
  • Authentication & authorization: validate JWT tokens (offline signature check), verify API keys (Redis lookup), introspect OAuth2 opaque tokens (cached external call).
  • Rate limiting: enforce per-API-key, per-user, per-IP, and per-route limits. Sliding window with Redis. Return 429 with Retry-After header.
  • Request/response transformation: add/remove headers, rewrite paths, inject correlation IDs, strip sensitive response fields.
  • SSL/TLS termination: accept HTTPS from clients, forward plain HTTP to internal services. Manage certificates via Let's Encrypt or ACM.
  • Load balancing: distribute traffic across backend instances using round-robin, least connections, or consistent hash.
  • Circuit breaking: track per-backend error rate; open circuit when threshold exceeded; protect backends from being overwhelmed during recovery.
  • Response caching: cache idempotent responses (GET/HEAD) by cache key. Respect Cache-Control, ETag, and Vary headers.
  • Canary routing: send a configurable percentage of traffic to a new backend version. Support header-based and random-hash-based splitting.
  • API composition (BFF): fan-out to multiple upstream services in parallel, merge responses into a single client response.
  • Plugin extensibility: define a plugin interface so teams can add new cross-cutting concerns without modifying the core gateway.

Non-Functional Requirements

  • Throughput: 1M requests/sec sustained across a horizontally scaled fleet.
  • Latency overhead: gateway adds <5ms p99 to every request (the entire pipeline, not per plugin).
  • Availability: 99.999% (5 nines) — the gateway is in the hot path of every API call. Any downtime is customer-visible.
  • Observability: per-route request rate, latency histograms (p50/p99/p999), error rate, and circuit breaker state exported to metrics system.
  • Config propagation: route and plugin configuration changes propagate to all gateway instances within 30 seconds.
  • Security: no credentials logged, sensitive headers stripped from logs, rate limit keys use HMAC of IP/user to avoid PII in Redis keys.

Out of Scope

  • Service-to-service (east-west) traffic — that is the service mesh's responsibility
  • Business logic, data storage, or application-level orchestration
  • Developer portal (API documentation, key provisioning UX)

🔢E — Estimation3–5 min

Traffic & Scale Numbers

  • Target throughput: 1M req/sec across the fleet. A single Nginx/Envoy instance handles ~50K-100K req/sec. Implies 10-20 gateway instances minimum, with headroom for 2x burst → provision 40 instances.
  • Latency budget: 5ms total gateway overhead. TLS termination: ~0.5ms. Auth (JWT offline): ~0.5ms. Rate limit (Redis): ~1ms. Routing + backend call setup: ~1ms. Leaves 2ms for other plugins. This rules out synchronous external calls in the hot path.
  • Rate limit state in Redis: 10M active API keys × 2 counters (current + previous minute window) × 8 bytes each = 160MB. Comfortably fits in a Redis Cluster with 3 shards.
  • Circuit breaker state: stored in-memory per gateway instance. O(backend_services) = typically <1000 entries. Memory cost is negligible (<1MB).
  • Canary routing state: stored in control plane DB, pushed to gateway instances on change. No per-request state needed — stateless hash or RNG decision.
  • Response cache: edge cache (Varnish/nginx) with 1GB RAM per instance holds ~200K cached responses at 5KB average. Cache hit rate target: 30% for GET endpoints.
💡 Key insight for the interview: The 5ms latency budget forces all hot-path operations to be either local (JWT validation, circuit breaker state) or single Redis round-trip (<1ms on same AZ). Any design that requires an external HTTP call per request will blow the latency budget. This is why JWT is preferred over opaque token introspection in the hot path.

🏗️H — High-level Design10 min

Figure: API Gateway request pipeline — 8-stage plugin chain with canary traffic splitting

System Components

  • Load Balancer (L4/L7): AWS ALB or GCP Load Balancer in front of the gateway fleet. DNS-based failover across AZs. Health checks every 5 seconds.
  • Gateway Fleet: 40+ stateless instances (Nginx+Lua, Envoy, or custom JVM service). Stateless means any instance can serve any request — rate limit state is in Redis, not local.
  • Control Plane: manages route config, plugin configuration, API key issuance. PostgreSQL for persistence. Pushes config changes to gateways via WebSocket or polling.
  • Redis Cluster: rate limit counters, OAuth2 token cache, circuit breaker state. 3 shards × 2 replicas. Same AZ as gateway to keep latency <1ms.
  • Backend Services: downstream microservices. Gateway forwards requests via HTTP/1.1 or HTTP/2.
  • Observability Pipeline: gateway emits access logs (JSON) and metrics (Prometheus). Grafana for dashboards. PagerDuty alerts on error rate > 1% or p99 latency > 500ms.

Plugin Pipeline (Chain of Responsibility)

Every request flows through a fixed-order plugin chain. Plugin order is critical — you must authenticate before rate limiting (otherwise you can't identify who to rate limit), and rate limit before routing (no point routing a request you'll reject). The chain:

API Gateway vs. Service Mesh

🟢 Architecture clarification interviewers love:
  • API Gateway = north-south traffic: external clients (browsers, mobile apps, third-party services) to internal backend services. The gateway authenticates, rate-limits, and routes.
  • Service Mesh (Istio/Linkerd) = east-west traffic: service-to-service calls inside the cluster. The mesh handles mTLS, retries, load balancing, and observability for internal calls.
  • They complement, not replace each other. The gateway handles the external boundary; the mesh handles the internal network. Running both is the standard production architecture at companies like Airbnb, Lyft, and Netflix.
  • Duplication to avoid: don't implement JWT validation in both the gateway and the service mesh. The gateway validates and forwards user context (X-User-Id header). The mesh handles mTLS between services. Services trust the gateway's validated context.

Canary Routing

Two strategies for splitting traffic:

  • Header-based: if X-Canary: true in request, route to canary backend. Used for internal testing and opted-in beta users. Deterministic (same user always hits canary).
  • Hash-based: hash(userId) % 100 < canary_percent. Deterministic: same user always hits same backend. Avoids session inconsistency (user doesn't bounce between v1 and v2 on different requests).
  • Random-based: random() < canary_percent/100. Simple but non-sticky: same user may hit v1 for one request and v2 for the next. Acceptable for stateless APIs.

Authentication Flows

// Flow 1: JWT (most common, offline validation)
// Client: Authorization: Bearer eyJhbGciOiJSUzI1NiJ9...
// Gateway:
//   1. Split header/payload/signature
//   2. Decode header → algorithm = RS256
//   3. Load public key from local key ring (refreshed hourly from JWKS endpoint)
//   4. Verify RSA signature over (header + "." + payload)
//   5. Check exp claim > now, iss claim matches expected issuer
//   6. Extract sub (user ID), scope (permissions) from payload
//   7. Set X-User-Id header, continue chain
// No network call. ~0.5ms CPU.

// Flow 2: API Key
// Client: X-Api-Key: ak_live_xK9mP2...
// Gateway:
//   1. HMAC-SHA256 of raw key → lookup key in Redis hash "apikeys:{hmac}"
//   2. If found and active: extract owner_id and rate_limit_tier
//   3. Set X-Api-Key-Owner header, continue chain
// One Redis GET. ~1ms.

// Flow 3: OAuth2 opaque token (avoid in hot path if possible)
// Client: Authorization: Bearer opaque_token_xyz...
// Gateway:
//   1. Hash token → check introspection cache in Redis
//   2. Cache hit: return cached result (active/inactive + claims)
//   3. Cache miss: POST to auth-service /introspect with token
//   4. Cache result in Redis for min(token_remaining_ttl, 60s)
// Cache hit: ~1ms. Cache miss: ~5-20ms external call (blows latency budget for high-traffic routes)

🔬D — Deep Dive10 min

Plugin Architecture: Why Ordering Matters

The plugin chain is not a bag of middleware you can order arbitrarily. Each plugin has dependencies on what the previous plugin produced:

  • Auth must run before Rate Limit: rate limiting is per-identity. Without auth, you can only rate limit by IP (trivially bypassed with proxies). Auth populates the identity that rate limit uses.
  • Rate Limit must run before Backend Call: there is no point forwarding a request to the backend if you're going to reject it. Fail fast, save upstream capacity.
  • Circuit Breaker must run before Backend Call: same reason — if the circuit is OPEN, return 503 immediately without attempting the network call.
  • Request Transform must run before Backend Call: the transform injects X-User-Id into the request. The backend depends on this header being present.
  • Cache Check runs after auth but before backend: we check cache after auth because some caches are user-specific (private cache). For shared public caches, you could check before auth, but this risks serving one user's private data to another.

Rate Limiting: Redis Sliding Window Algorithm

Fixed window counters (reset every minute) have a burst problem: a client can make 1000 requests at 11:59:59 and another 1000 at 12:00:01. In a 2-second window they sent 2000 requests. The sliding window algorithm prevents this:

// Sliding window implementation using two Redis keys:
// Current window key: "rl:{identity}:{current_minute}"
// Previous window key: "rl:{identity}:{previous_minute}"
//
// Algorithm:
//   elapsed_in_current_window = now_ms % 60_000  (milliseconds into current minute)
//   weight_of_previous = 1.0 - (elapsed_in_current_window / 60_000.0)
//
//   estimated_count = (previous_window_count * weight_of_previous) + current_window_count
//
//   if estimated_count >= limit: reject with 429
//   else: INCR current_window_count
//
// Example: limit = 1000
//   Previous minute count: 800, current minute elapsed: 30s (50% through)
//   Weight of previous: 0.5
//   Estimated: 800 * 0.5 + 200 (current) = 600 → allow request
//
// The two Redis calls (GET prev, INCR curr) can be done in a single Lua script
// for atomicity. Or use Redis pipeline (not atomic but close enough for rate limiting).

Distributed Rate Limiting Trade-offs

Rate limiting state can live in three places, each with different consistency/latency trade-offs:

  • Local in-memory (per gateway instance): Zero latency. But 10 gateway instances each allow N requests → effective limit is 10N. Incorrect for strict global limits. OK for very loose limits where a 10x burst is acceptable.
  • Redis (centralized): 1ms round-trip. Accurate global counting. Redis becomes a hot dependency — Redis failure means rate limiting fails open (all requests allowed) or fails closed (all requests rejected). Choose fail-open for availability.
  • Token bucket with Redis: more forgiving for burst traffic. Tokens refill continuously. INCR + Lua script for atomic check-and-decrement.

At 1M req/sec with 10M API keys, Redis rate limit calls = 1M ops/sec. A Redis Cluster with 3 shards handles ~300K-500K ops/sec per shard. Need careful sharding by API key hash to avoid hot shards.

Circuit Breaker State Machine

The circuit breaker is a state machine that protects backends from being called when they are failing. Without it, a single slow backend can exhaust all gateway threads waiting for responses, cascading the failure to all routes.

// State machine:
//
//   CLOSED (normal operation)
//     → track success/failure count in sliding window (e.g., last 10 seconds)
//     → if failure_rate > threshold (e.g., 50%) AND min_calls (e.g., 20) exceeded:
//         transition to OPEN
//
//   OPEN (circuit tripped)
//     → all requests immediately fail with 503 (no upstream call)
//     → start timer (e.g., 30 seconds)
//     → when timer expires: transition to HALF_OPEN
//
//   HALF_OPEN (probe state)
//     → allow exactly ONE request through to upstream
//     → if request succeeds: transition to CLOSED (backend recovered)
//     → if request fails: transition back to OPEN (reset timer)
//
// Why HALF_OPEN matters: without it, after 30s OPEN you go straight to CLOSED
// and might immediately re-trip because the backend isn't actually recovered.
// HALF_OPEN provides a safe probe with a single request.
//
// Key configuration parameters:
//   failure_threshold: 50%    (below this, stay CLOSED)
//   min_request_volume: 20    (don't open circuit on 1-of-1 failures)
//   measurement_window: 10s   (sliding window for failure rate calculation)
//   open_duration: 30s        (how long to stay OPEN before HALF_OPEN probe)
//   half_open_max_calls: 1    (probe with exactly 1 request)

Observability: What to Measure at the Gateway

The gateway is the ideal observability point: every request passes through it, and it can record data before the backend even receives the request.

  • Per-route metrics: request rate (req/sec), error rate (4xx/5xx separately), latency histogram (p50, p99, p999). Label by route ID, auth policy, and backend service.
  • Rate limit metrics: rate_limit_allowed_total, rate_limit_rejected_total. Alert if rejection rate spikes (could indicate API abuse or misconfigured limits).
  • Circuit breaker metrics: cb_state{service="payments"} = 0 (CLOSED), 1 (OPEN), 2 (HALF_OPEN). Alert immediately when any circuit opens.
  • Cache metrics: cache_hit_rate per route. If hit rate drops below expected baseline, could indicate cache invalidation bug or TTL misconfiguration.
  • Upstream latency: measure time from request forwarded to response received. Separate from total latency to distinguish gateway overhead from backend slowness.
⚠️ Common interview mistake: Candidates often describe rate limiting as "check if user has exceeded limit, if not increment and proceed." This is a race condition under concurrent requests from the same key. Two goroutines both read count=999, both see it's under 1000, both increment to 1000 and 1001. Use Redis INCR (atomic) followed by a check, or a Lua script for atomic check-and-increment. The pattern: if INCR(key) > limit: DECR(key); reject;

Single Points of Failure

  • Gateway fleet: solved by horizontal scaling behind ALB. Loss of one instance is handled by ALB health checks within 5 seconds.
  • Redis: most critical dependency. Failure means rate limiting fails open (configurable: fail open = allow traffic, fail closed = reject traffic). Fail open is correct for availability. Redis Cluster with 3 master + 3 replica nodes provides HA.
  • Control plane: gateway instances cache route config locally. Control plane failure means no config updates for 30 seconds, but existing routes continue working. This is the correct trade-off: availability > config freshness.
  • Auth service (for OAuth2 introspection): cache the introspection result in Redis. Auth service failure means cached tokens continue working for up to 60 seconds. New tokens cannot be validated — return 503 for new opaque tokens, not 401 (fail open vs closed is a security policy decision).

🚀D — Deliver2 min

Summary statement for the interview:

The API gateway is a stateless plugin chain (Chain of Responsibility pattern) that processes every external request through ordered middleware: auth → rate limit → transform → route → circuit break → backend call → response transform. Stateless design enables horizontal scaling to 1M req/sec. Shared state (rate limit counters, circuit breaker state) lives in Redis Cluster for consistency. JWT offline validation keeps auth latency <1ms with no network call. Circuit breakers prevent cascading failures with the CLOSED→OPEN→HALF_OPEN state machine. Canary routing enables safe incremental rollouts. The gateway owns north-south traffic; the service mesh owns east-west — they are complementary.

Phased delivery:

  • Phase 1 (MVP): Auth + Rate Limit + Routing. Single region, in-memory circuit breakers. Covers 80% of the value.
  • Phase 2: Redis-backed rate limiting, circuit breaker state in Redis, response caching, request/response transformation.
  • Phase 3: Canary routing, plugin extensibility API, multi-region with latency-based routing, advanced observability.

⚖️Trade-offs

DecisionOption AOption BRecommended

Individual plugins (JWT validation, Redis check) are fast enough that parallelism doesn't help much.

☕Java Implementation

/**
 * ApiGatewayPipeline — executes a composable middleware chain for each inbound request.
 *
 * Design: Chain of Responsibility. Each GatewayPlugin handles one concern and decides
 * whether to continue (call next.run()) or short-circuit (set error response, return).
 * Plugin order is fixed and critical: auth → rate limit → transform → route → circuit break → backend.
 */
public class ApiGatewayPipeline {

    private final List<GatewayPlugin> plugins;

    public ApiGatewayPipeline(List<GatewayPlugin> plugins) {
        this.plugins = List.copyOf(plugins);
    }

    /** Entry point: process a single inbound request through the full plugin chain. */
    public GatewayResponse process(GatewayRequest request) {
        GatewayResponse response = new GatewayResponse();
        executeChain(request, response, 0);
        return response;
    }

    private void executeChain(GatewayRequest request, GatewayResponse response, int index) {
        if (index >= plugins.size()) return;
        GatewayPlugin current = plugins.get(index);
        current.handle(request, response, () -> executeChain(request, response, index + 1));
    }

    public interface GatewayPlugin {
        void handle(GatewayRequest request, GatewayResponse response, Runnable next);
    }
}

// ─────────────────────────────────────────────────────────────────────────────
// Plugin 1: JWT Authentication
// Offline validation — no network call. Validates signature, expiry, issuer.
// ─────────────────────────────────────────────────────────────────────────────
public class JwtAuthPlugin implements GatewayPlugin {

    private final PublicKey publicKey;     // Loaded from JWKS endpoint at startup, refreshed hourly
    private final String expectedIssuer;

    public JwtAuthPlugin(PublicKey publicKey, String expectedIssuer) {
        this.publicKey = publicKey;
        this.expectedIssuer = expectedIssuer;
    }

    @Override
    public void handle(GatewayRequest request, GatewayResponse response, Runnable next) {
        String authHeader = request.getHeader("Authorization");
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            sendUnauthorized(response, "Missing or invalid Authorization header");
            return;  // Short-circuit: do NOT call next
        }

        String token = authHeader.substring(7);
        JwtClaims claims = validateJwt(token);
        if (claims == null) {
            sendUnauthorized(response, "Invalid or expired JWT");
            return;
        }

        // Inject validated identity for downstream plugins and the backend
        request.setAttribute("authenticatedUserId", claims.getSubject());
        request.setAttribute("tokenScopes", claims.getScopes());
        request.setHeader("X-User-Id", claims.getSubject());

        next.run();  // Continue to rate limit plugin
    }

    private JwtClaims validateJwt(String token) {
        try {
            // Split header.payload.signature
            String[] parts = token.split("\\.");
            if (parts.length != 3) return null;

            // Verify RSA/ECDSA signature over header + "." + payload
            Signature sig = Signature.getInstance("SHA256withRSA");
            sig.initVerify(publicKey);
            sig.update((parts[0] + "." + parts[1]).getBytes(StandardCharsets.UTF_8));
            byte[] signatureBytes = Base64.getUrlDecoder().decode(parts[2]);
            if (!sig.verify(signatureBytes)) return null;

            // Decode payload and check standard claims
            String payloadJson = new String(Base64.getUrlDecoder().decode(parts[1]));
            JwtClaims claims = JwtClaims.parse(payloadJson);

            if (claims.getExpiry() < System.currentTimeMillis() / 1000L) return null;
            if (!expectedIssuer.equals(claims.getIssuer())) return null;

            return claims;
        } catch (Exception verificationError) {
            // Log with context but don't expose internals to client
            System.err.println("[JwtAuthPlugin.validateJwt] Validation failed: " + verificationError.getMessage());
            return null;
        }
    }

    private void sendUnauthorized(GatewayResponse response, String message) {
        response.setStatus(401);
        response.setHeader("WWW-Authenticate", "Bearer realm=\"api.example.com\"");
        response.setBody("{\"error\":\"" + message + "\"}");
    }
}

// ─────────────────────────────────────────────────────────────────────────────
// Plugin 2: Redis Sliding Window Rate Limiter
// Two-bucket sliding window: accurate global rate limiting with sub-millisecond overhead.
// ─────────────────────────────────────────────────────────────────────────────
public class RateLimitPlugin implements GatewayPlugin {

    private static final long WINDOW_SIZE_MS = 60_000L;

    private final JedisPool jedisPool;
    private final int requestsPerMinute;

    public RateLimitPlugin(JedisPool jedisPool, int requestsPerMinute) {
        this.jedisPool = jedisPool;
        this.requestsPerMinute = requestsPerMinute;
    }

    @Override
    public void handle(GatewayRequest request, GatewayResponse response, Runnable next) {
        String identity = extractRateLimitIdentity(request);
        if (identity == null) {
            next.run();  // No identity to rate limit on — allow
            return;
        }

        long nowMs = System.currentTimeMillis();
        long currentWindow = nowMs / WINDOW_SIZE_MS;
        long previousWindow = currentWindow - 1;
        long elapsedInCurrentWindowMs = nowMs % WINDOW_SIZE_MS;
        double previousWindowWeight = 1.0 - ((double) elapsedInCurrentWindowMs / WINDOW_SIZE_MS);

        String currentKey = "rl:" + identity + ":" + currentWindow;
        String previousKey = "rl:" + identity + ":" + previousWindow;

        try (Jedis jedis = jedisPool.getResource()) {
            // Lua script ensures atomic check-and-increment
            String luaScript =
                "local prev = tonumber(redis.call('GET', KEYS[1]) or '0') " +
                "local curr = redis.call('INCR', KEYS[2]) " +
                "redis.call('EXPIRE', KEYS[2], 120) " +
                "local estimate = prev * tonumber(ARGV[1]) + curr " +
                "return estimate";

            Object result = jedis.eval(
                luaScript,
                Arrays.asList(previousKey, currentKey),
                Arrays.asList(String.valueOf(previousWindowWeight))
            );

            double estimatedCount = ((Long) result).doubleValue();

            if (estimatedCount > requestsPerMinute) {
                long resetEpoch = (currentWindow + 1) * (WINDOW_SIZE_MS / 1000L);
                response.setStatus(429);
                response.setHeader("X-RateLimit-Limit", String.valueOf(requestsPerMinute));
                response.setHeader("X-RateLimit-Remaining", "0");
                response.setHeader("X-RateLimit-Reset", String.valueOf(resetEpoch));
                response.setHeader("Retry-After", String.valueOf(resetEpoch - (nowMs / 1000L)));
                response.setBody("{\"error\":\"Rate limit exceeded\",\"retry_after_seconds\":" +
                                 (resetEpoch - nowMs / 1000L) + "}");
                return;
            }

            long remaining = Math.max(0, requestsPerMinute - (long) estimatedCount);
            response.setHeader("X-RateLimit-Limit", String.valueOf(requestsPerMinute));
            response.setHeader("X-RateLimit-Remaining", String.valueOf(remaining));
        } catch (JedisException redisError) {
            // Fail open: Redis failure should not block all traffic
            System.err.println("[RateLimitPlugin] Redis error, failing open: " + redisError.getMessage());
        }

        next.run();
    }

    private String extractRateLimitIdentity(GatewayRequest request) {
        // Prefer API key identity; fall back to user ID from JWT; then IP
        String apiKey = request.getHeader("X-Api-Key");
        if (apiKey != null) return hmacSha256(apiKey);  // Don't store raw key in Redis

        String userId = (String) request.getAttribute("authenticatedUserId");
        if (userId != null) return "user:" + userId;

        return "ip:" + request.getClientIp();
    }

    private String hmacSha256(String input) {
        // Implementation omitted for brevity — use javax.crypto.Mac with HMAC-SHA256
        return "hmac:" + input.hashCode();  // Placeholder
    }
}

// ─────────────────────────────────────────────────────────────────────────────
// Plugin 3: Circuit Breaker
// State machine per backend. Prevents cascading failures.
// ─────────────────────────────────────────────────────────────────────────────
public class CircuitBreakerPlugin implements GatewayPlugin {

    private static final double FAILURE_THRESHOLD = 0.5;  // 50% failure rate triggers OPEN
    private static final int MIN_REQUEST_VOLUME = 20;       // Don't open on 1-of-1 failures
    private static final long OPEN_DURATION_MS = 30_000L;  // 30 seconds in OPEN state
    private static final long MEASUREMENT_WINDOW_MS = 10_000L;  // 10-second sliding window

    private final Map<String, CircuitState> circuitMap = new ConcurrentHashMap<>();

    @Override
    public void handle(GatewayRequest request, GatewayResponse response, Runnable next) {
        Route matchedRoute = (Route) request.getAttribute("matchedRoute");
        if (matchedRoute == null) {
            next.run();
            return;
        }

        String serviceId = matchedRoute.getServiceId();
        CircuitState circuit = circuitMap.computeIfAbsent(serviceId, id -> new CircuitState());

        CircuitAction action = circuit.checkAndAct();

        if (action == CircuitAction.REJECT) {
            response.setStatus(503);
            response.setHeader("Retry-After", "30");
            response.setBody("{\"error\":\"Service temporarily unavailable\",\"service\":\"" + serviceId + "\"}");
            return;
        }

        // Call upstream and record result
        next.run();

        boolean isSuccess = response.getStatus() < 500;
        circuit.recordResult(isSuccess, action == CircuitAction.PROBE);
    }

    private enum CircuitAction { ALLOW, PROBE, REJECT }

    private static class CircuitState {
        private enum State { CLOSED, OPEN, HALF_OPEN }

        private volatile State state = State.CLOSED;
        private final AtomicInteger successCount = new AtomicInteger(0);
        private final AtomicInteger failureCount = new AtomicInteger(0);
        private volatile long openedAtMs = 0;

        synchronized CircuitAction checkAndAct() {
            return switch (state) {
                case CLOSED -> CircuitAction.ALLOW;
                case OPEN -> {
                    if (System.currentTimeMillis() - openedAtMs > OPEN_DURATION_MS) {
                        state = State.HALF_OPEN;
                        yield CircuitAction.PROBE;
                    }
                    yield CircuitAction.REJECT;
                }
                case HALF_OPEN -> CircuitAction.REJECT;  // Only one probe at a time
            };
        }

        synchronized void recordResult(boolean success, boolean isProbe) {
            if (isProbe) {
                state = success ? State.CLOSED : State.OPEN;
                if (!success) openedAtMs = System.currentTimeMillis();
                return;
            }
            if (success) successCount.incrementAndGet();
            else failureCount.incrementAndGet();

            int total = successCount.get() + failureCount.get();
            if (total >= MIN_REQUEST_VOLUME) {
                double failureRate = (double) failureCount.get() / total;
                if (failureRate > FAILURE_THRESHOLD) {
                    state = State.OPEN;
                    openedAtMs = System.currentTimeMillis();
                    successCount.set(0);
                    failureCount.set(0);
                }
            }
        }
    }
}

        ));
    }
