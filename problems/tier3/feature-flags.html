Tier 3 — Expert 60 minPlatform Engineering

Design a Feature Flag System

Feature flags decouple deploy from release. The hard parts: evaluating flags in under 1ms per request, consistent rollout (same user always gets same experience), and kill switches that work globally in 30 seconds. The evaluation algorithm uses hashing for deterministic gradual rollout.

🏢 LaunchDarkly, Split.io, Statsig
⏱️ 60 min interview

❓R — Requirements3–5 min

Functional Requirements

  • Create feature flags with targeting rules (% rollout, user segment, A/B test)
  • Evaluate flags for a given user in <1ms
  • Kill switch: disable flag globally in <30 seconds
  • Audit log: who changed what flag when
  • Gradual rollout: 1% → 10% → 50% → 100% over time

Non-Functional Requirements

  • Scale: 10M flag evaluations/sec (every request evaluates 10–50 flags)
  • Latency: <1ms per evaluation (must not add noticeable latency)
  • Propagation: Flag changes reach all servers in <30 seconds

🔢E — Estimation3–5 min

  • 10M evaluations/sec × 1000 flags → must be in-memory, never hit network per evaluation
  • Flag config: 1000 flags × 1KB config = 1MB → trivially cached locally in each service
  • Change events: <100 flag changes/day → very low write volume

🗄️S — Schema3–5 min

// Flag definitions (PostgreSQL -- source of truth)
feature_flags:
    flag_id         UUID PRIMARY KEY,
    flag_key        VARCHAR(100) UNIQUE,  -- "checkout-v2-enabled"
    enabled         BOOLEAN,
    rollout_pct     INT,           -- 0-100 (what % of users get this)
    targeting_rules JSONB,         -- [{ attribute: "plan", op: "eq", value: "premium" }]
    description     VARCHAR(500),
    updated_at      TIMESTAMP,
    updated_by      VARCHAR(100)

// Flag evaluation cache (Redis -- synced from DB, TTL-based invalidation)
// Key: flags:{environment}  Value: serialized JSON of all flag configs
// Updated on every flag change via Kafka event

🏗️H — High-level Design10 min

  • SDK (client-side): Loads all flag configs from Redis on startup. Caches locally with 30s TTL. Evaluates entirely in-memory — no network call per evaluation.
  • Consistent rollout: hash(userId + flagKey) % 100. If result < rollout_pct: enabled. Same user always gets same result for the same rollout percentage.
  • Targeting rules: Before rollout hash, check targeting rules: premium users get flag regardless of rollout %. Segment targeting applies first.
  • Change propagation: Flag change → write to DB → publish to Kafka → all servers receive event → reload flag config from Redis.
  • Kill switch: Set enabled=false → Kafka event propagates to all SDKs → re-evaluation returns false. 30s for full propagation.

🔌A — APIs5 min

// Flag Management API
POST /api/v1/flags
Body: { key: "checkout-v2", enabled: true, rollout_pct: 10, targeting_rules: [...] }

PUT /api/v1/flags/{flagKey}
Body: { rollout_pct: 50 }  -- gradual rollout increase

DELETE /api/v1/flags/{flagKey}/enable   -- kill switch: immediately disable

// SDK Evaluation (in-process -- no API call at evaluation time)
// SDK loads all flags from Redis at startup, polls every 30s for updates
// Evaluation: FeatureFlagEvaluator.isEnabled("checkout-v2", userId, userAttrs)

🔬D — Deep Dive10 min

Consistent hash rollout algorithm:

// Deterministic: same user always gets same result
long hashValue = Math.abs(MurmurHash3.hash(userId + ':' + flagKey));
int bucketNumber = (int) (hashValue % 100); // 0-99
boolean flagEnabled = bucketNumber < rolloutPercent;

Why hash(userId + flagKey) not just hash(userId)? Without the flagKey, all flags would have correlated rollout -- if you are in the 1% for flag A, you would also be in the 1% for flag B. This creates experimental contamination. Including flagKey decorrelates rollout groups.

Sticky bucketing: Once a user is assigned to a variant, they stay in that variant even as rollout % changes. Hash-based assignment achieves this automatically: rolling from 10% to 20% adds new users (buckets 10-19) but does not remove existing users (buckets 0-9).

Feature flag vs A/B test: Feature flag: is this feature on/off for this user? A/B test: what variant does this user see, and what are the metric outcomes? Feature flags can implement A/B tests (multiple variants) but a pure feature flag system does not need experiment analysis infrastructure.

✅E — Evaluate3 min

  • Flag explosion: Too many flags slow down code and create tech debt. Flags should have a TTL (clean up after rollout completes). Stale flags in code = maintenance burden and evaluation overhead.
  • Override rules: Enable flag for specific users (QA team, beta testers) by user ID override list. This overrides rollout percentage. Must be fast to evaluate: store as Set of userIds in memory.

🚀D — Deliver2 min

Feature flags = in-memory SDK evaluation (no network per call) + hash(userId+flagKey) % 100 for consistent rollout + Kafka event propagation for kill switch in 30s. Key insight: including flagKey in hash prevents experimental contamination across A/B tests.

⚖️Trade-offs

DecisionOption AOption B
SDK pollingPoll Redis every 30s: simple, 30s max stalenessPush via Kafka/WebSocket: instant propagation, more infrastructure
Rollout algorithmHash-based: deterministic, sticky, no stored stateRandom per evaluation: not sticky, user experience changes on each request
Isolation modelShared flag service: simpler ops, all teams share one servicePer-team flag service: stronger isolation, more overhead

☕Java Implementation

/**
 * FeatureFlagEvaluator -- evaluates feature flags for a user in O(1) time.
 * All flag configs loaded in-memory; no network call per evaluation.
 */
public class FeatureFlagEvaluator {

    private volatile Map<String, FlagConfig> flagConfigs = new HashMap<>();

    /**
     * Evaluates whether a flag is enabled for a specific user.
     * Order: overrides > targeting rules > rollout hash.
     */
    public boolean isEnabled(String flagKey, String userId, Map<String, String> userAttrs) {
        FlagConfig config = flagConfigs.get(flagKey);
        if (config == null || !config.isEnabled()) {
            return false; // Flag missing or globally disabled (kill switch)
        }

        // User-specific overrides (QA, beta testers)
        if (config.getUserOverrides().contains(userId)) {
            return true;
        }

        // Targeting rules (plan=premium -> always on)
        for (TargetingRule rule : config.getTargetingRules()) {
            if (rule.matches(userAttrs.get(rule.getAttribute()))) {
                return true;
            }
        }

        // Consistent hash-based percentage rollout
        return isInRolloutBucket(flagKey, userId, config.getRolloutPercent());
    }

    /**
     * Deterministic bucket assignment.
     * hash(userId:flagKey) % 100 ensures:
     * - Same user always gets same bucket (sticky)
     * - Different flags have uncorrelated rollout groups (no contamination)
     */
    private boolean isInRolloutBucket(String flagKey, String userId, int rolloutPercent) {
        if (rolloutPercent <= 0) return false;
        if (rolloutPercent >= 100) return true;
        String hashInput = userId + ":" + flagKey;
        int hashValue = Math.abs(hashInput.hashCode()); // Production: MurmurHash3
        return (hashValue % 100) < rolloutPercent;
    }

    /**
     * Called when Kafka delivers a flag config update.
     * Atomically replaces the entire config map (copy-on-write).
     */
    public void updateFlagConfigs(Map<String, FlagConfig> newConfigs) {
        this.flagConfigs = Map.copyOf(newConfigs); // volatile write -- safe for readers
    }
}
