Design a Feature Flag System

A feature flag system is deceptively simple to describe but hard to get right at scale. The critical constraint is that flag evaluation must never add latency to critical paths — 100K evaluations/second must happen entirely in-memory with no network calls. The challenge is how to keep that in-memory cache consistent across thousands of SDK instances while propagating changes in seconds.

🏢 LaunchDarkly, Unleash, Optimizely, Split.io
⏱️ 60 min interview

❓R — Requirements3–5 min

Functional Requirements

  • Create and manage feature flags: boolean, multivariate (A/B/C/D), percentage rollout, user segment targeting
  • Targeting rules: evaluate flags based on user attributes (ID, email, country, plan, custom attributes)
  • Gradual rollout: expose a feature to X% of users; increase over time without code changes
  • Kill switch: instantly disable a feature across all users in seconds (production incident response)
  • Experimentation: A/B tests with statistical significance tracking
  • Audit log: record every flag change with who changed it, what changed, and when
  • SDK: server-side and client-side SDKs for multiple languages (Java, JS, Python, Go)

Non-Functional Requirements

  • Evaluation latency: <1 ms per flag evaluation (must be in-memory, no network call)
  • Throughput: 100K flag evaluations/second per SDK instance
  • Propagation time: flag changes reach all SDK instances within 30 seconds
  • Availability: SDK must evaluate flags even when the flag service is unreachable (use cached config)
  • Consistency: once a user is assigned a variant, they stay in that variant (sticky sessions)
  • Scale: 10K flags, 1B user evaluations/day, 100K SDK instances worldwide

Clarifying Questions

  • Is this a multi-tenant system (each customer manages their own flags) or internal only?
  • What is the acceptable flag propagation latency for kill-switch scenarios?
  • Do we need real-time experimentation analytics, or is batch analysis (hourly) acceptable?

🔢E — Estimation3–5 min

Flag Configuration Size

  • 10,000 flags × 5 KB average config (targeting rules, variants, percentages) = 50 MB total config
  • 50 MB fits entirely in RAM on a single Redis node with room for indexes (Redis uses ~10× raw data for overhead at this size)
  • Each SDK instance caches the full config locally: 50 MB heap is trivial for a JVM service

Evaluation Throughput

  • 100K flag evaluations/second per SDK instance, all in-memory: trivial for modern JVM (can do 10M+/sec in-memory)
  • 1B evaluations/day total system-wide = ~11,600/sec average, ~100K/sec peak
  • Evaluation events (for experimentation analytics): 1B events/day → write to Kafka for async processing

Flag Service Load

  • 100K SDK instances × 1 SSE connection each = 100K persistent connections to the flag service
  • SSE is HTTP/2 multiplexed; one server can handle ~10K concurrent SSE connections
  • 10 flag service instances needed to handle 100K SDK connections
  • Flag updates are rare (maybe 100 changes/day), so SSE traffic is sparse — mostly idle keep-alives
💡 Senior Signal: The flag service is not on the critical path of serving user requests. The SDK is. State this clearly: the SDK evaluates flags entirely locally. The flag service only pushes config updates. A flag service outage degrades propagation of new flag changes — it does NOT degrade the application's ability to evaluate existing flags.

Flag Types in Detail

  • Boolean: true/false. The simplest. Used for kill switches and simple feature gates. isEnabled("new-checkout").
  • Multivariate (A/B/C/D): Returns one of N string variants. Used for testing different UI components, algorithm variants, or pricing options. getVariant("checkout-button-color") → "blue", "green", or "red".
  • Percentage rollout: A multivariate flag where the assignment is determined by hashing the user ID. 20% → "treatment", 80% → "control". The hash is deterministic: same user always gets same variant.
  • User segment targeting: Evaluate targeting rules first (e.g., "all enterprise users get treatment"). Users not matching any rule fall through to the percentage rollout. This is the composition that powers sophisticated experiments.

Targeting Rule Evaluation (First-match Priority)

// Rule evaluation pipeline for a given user context:
// UserContext { userId: "u123", email: "alice@acme.com", plan: "enterprise", country: "US" }

// Flag: "new-pricing-page" with these rules (in priority order):
// Rule 1: plan == "enterprise"         → variant: "control"    (enterprise excluded from test)
// Rule 2: country in ["US", "CA"]      → rollout: {treatment: 50, control: 50}
// Rule 3: no conditions (catch-all)    → rollout: {treatment: 10, control: 90}

// Evaluation:
// 1. Check Rule 1: plan == "enterprise" → alice.plan == "enterprise" → MATCH → return "control"
// 2. (Rules 2 and 3 are never evaluated — first match wins)

// If alice.plan == "pro" (not enterprise):
// 1. Check Rule 1: MISS (plan != enterprise)
// 2. Check Rule 2: country in ["US","CA"] → alice.country == "US" → MATCH
//    → Rollout rule: hash(userId + flagKey) % 100 = 37 → falls in treatment bucket (0-49) → "treatment"

Consistent Hashing for Percentage Rollout

The key property of percentage rollout is stickiness: a user assigned "treatment" today must remain in "treatment" tomorrow, even if the flag percentage changes (from 20% to 30% — only new users should be added). This requires deterministic assignment, not random:

// Bucket assignment: 0-99
// hash(userId + flagKey) % 100 = bucketNumber
// If bucketNumber < rolloutPercent → treatment; else → control

// Example: userId = "user-123", flagKey = "new-checkout"
// MurmurHash3("user-123:new-checkout") = 3829473847
// 3829473847 % 100 = 47
// rolloutPercent = 20 → bucket 47 >= 20 → control
// rolloutPercent increased to 50 → bucket 47 < 50 → treatment (now included!)

// The flagKey is included in the hash input so the same user gets independent
// assignments across different flags (not always in treatment or always in control).

SDK Config Propagation via SSE

Server-Sent Events (SSE) is the right transport for flag config updates:

  • Why SSE over WebSocket: Flag updates are server-to-client only. SSE is unidirectional HTTP, simpler to implement, proxy-friendly, and auto-reconnects. WebSocket is bidirectional — unnecessary overhead for push-only config updates.
  • Why SSE over polling: Polling at 1-second intervals from 100K SDK instances = 100K requests/second to the flag service for what is usually empty responses. SSE maintains one persistent connection per SDK instance and only pushes when something changes.
  • Startup: SDK connects to the SSE stream and immediately receives a "snapshot" event containing all flag configs. Subsequent events contain only the changed flag's config (delta update).
  • Reconnection: If the SSE connection drops, the SDK continues evaluating with its last known config (stale but safe). On reconnect, it receives a fresh snapshot to resync.

🔬D — Deep Dive10 min

1. Client-side vs Server-side SDK: Why They Differ

This is one of the most important architectural distinctions in feature flag systems:

  • Server-side SDK: Runs in your application server (JVM, Python process). Has access to all flag configs for all users. Evaluates flags locally using the full config. Safe to do this because the flag config is internal infrastructure — it never leaves your server.
  • Client-side SDK: Runs in the user's browser or mobile app. Cannot download the full flag config — it contains your business rules (e.g., "enterprise users always get feature X") which would reveal competitive information. Also: 50 MB config download per browser pageload is unacceptable.
  • Client-side evaluation model: The browser SDK sends the user's context (ID, attributes) to the flag service server. The server evaluates all flags for that user and returns only the assignment results: { "new-checkout": true, "dark-mode": false }. The evaluation logic never runs client-side.
  • Implication: Client-side evaluation requires a network call per session (or per user context change). It cannot be truly zero-latency. The tradeoff is security over performance.

2. Flag Lifecycle Management

Technical debt in feature flag systems is real and dangerous. Flags never cleaned up become permanent code paths that confuse developers. The lifecycle state machine:

  • Draft: Created but not enabled. Exists in config but SDK returns default variant for all users. Safe for development and testing.
  • Active: Fully evaluating rules. Production traffic is being split. This is the normal operational state.
  • Deprecated: The winning variant has been chosen. The flag is being removed from code. SDK still evaluates it (in case some code paths haven't been cleaned up yet). Dashboard shows a warning: "remove from code before archiving."
  • Archived: Removed from SDK cache. Any code still calling client.booleanVariation("archived-flag", ...) receives the hardcoded default — it will never be "true". Acts as a safety net for code that missed the cleanup.
  • Kill switch: A boolean flag with no targeting rules and 100% rollout, used purely for emergency disable. Best practice: every major feature has a corresponding kill switch flag. When a production incident hits, flip the kill switch in the dashboard — within 30 seconds all SDK instances receive the update and the feature is off without a deployment.

3. Experimentation and Statistical Significance

A feature flag percentage rollout becomes an A/B experiment when you attach a metric to it:

  • Randomization unit: Always randomize by user_id, not session. Same user must always see same variant for valid statistical inference. (Two sessions by the same user seeing different variants pollutes both variant's metrics.)
  • Metric collection: Every flag evaluation event includes variant assignment. The analytics pipeline joins evaluations with conversion events: "user u123 saw variant 'treatment' at 10:00, then converted at 10:45." This join happens in a Flink or Spark job.
  • Statistical significance: Two-proportion z-test for conversion rates. Requires minimum sample size before results are valid (calculated by power analysis). LaunchDarkly's approach: show "results not yet significant" until p-value < 0.05 AND minimum sample size reached. Prevents peeking problem (stopping test early when random variation looks like a winner).
  • Multi-armed bandit: Alternative to fixed A/B split. Automatically increases traffic to the winning variant as evidence accumulates. Reduces regret (lost conversions from showing users the inferior variant). Implementation: Thompson sampling updates variant probabilities using a Beta distribution over conversion observations.

4. Audit Log and Rollback

Every flag change must be auditable and reversible. Flag changes can cause production incidents (enabling a half-built feature for enterprise users by mistake):

  • The audit log stores old_config and new_config as JSONB snapshots. Rollback = PUT /api/v1/flags/{key}/rules with the previous config from the audit log.
  • The dashboard shows a diff view of what changed (e.g., "rollout_percent changed from 10 to 50"). This is computed at display time from the old/new JSONB blobs.
  • Optimistic concurrency control prevents concurrent edits from silently overwriting each other. The version field acts as a optimistic lock: if two engineers edit the same flag simultaneously, the second save returns 409 Conflict with "flag was modified by another user."

5. SDK Resilience and Offline Mode

The SDK's most important feature is that it works when the flag service is down:

  • Bootstrap cache: On first startup, the SDK fetches a full config snapshot and writes it to a local file (or Redis cache for stateless services). On subsequent startups, the SDK loads from this bootstrap cache immediately (sub-millisecond) and connects to the SSE stream in the background. No blocking startup waiting for the flag service.
  • Stale config operation: If the SSE connection drops and cannot reconnect, the SDK continues using its last known config indefinitely. This is the correct behavior: the system degrades to the last known good state rather than failing closed (returning defaults for everything) or failing open (treating all flags as enabled).
  • Default values: Every flag evaluation call requires a default value parameter: client.booleanVariation("flag", user, false). This default is only used if the flag key is not found in the config (e.g., flag was archived). It provides a safe fallback defined by the calling code, not the SDK.

✅E — Evaluate3 min

Edge Cases in Flag Evaluation

The rule evaluation engine has several non-obvious edge cases that must be explicitly handled:

  • Missing attribute: A rule checks plan == "enterprise" but the user context does not include plan. Decision: treat as non-match (rule does not apply). Never throw an exception — flag evaluation must be infallible.
  • Archived flag accessed: Application code calls client.booleanVariation("archived-flag", user, false). The flag is not in the cache. Return the provided default (false). Emit a "flag not found" metric so developers are alerted that code references a removed flag.
  • Rules not summing to 100%: A rollout rule has { "treatment": 20, "control": 75 } (sums to 95%). Bucket 96 falls outside all ranges. Decision: return the flag's defaultVariant. The dashboard should validate that all rollout percentages sum to exactly 100% before allowing a flag to go active.
  • Concurrent flag update during evaluation: A ConcurrentHashMap update (SSE delta) replaces the FlagConfig object while another thread is mid-evaluation. Java's ConcurrentHashMap guarantees atomic put — the evaluator sees either the old or new complete FlagConfig, never a partial state. Records (immutable) ensure the config object itself cannot be partially modified.

Failure Modes

  • SSE connection drops silently: Load balancer with a 60-second idle timeout kills the SSE connection. SDK does not know. It continues with stale config. Mitigation: server sends heartbeat events every 30 seconds. SDK reconnects on missed heartbeat. Standard SSE client libraries handle this automatically.
  • Flag config inconsistency during SSE reconnect: Between disconnect and reconnect, 3 flag changes happened. The SDK receives a snapshot on reconnect and sees all 3 changes atomically. No partial state.
  • Hash collision giving wrong percentage assignment: MurmurHash3 collisions are extremely rare (128-bit output). But the key mistake is using a non-deterministic hash (e.g., Java's default Object.hashCode() which differs across JVM restarts). Always use a stable, specification-defined hash function (MurmurHash3 or FNV1a).
  • Flag key typo: client.booleanVariation("new-chekout", user, false) (typo). The key is not in the cache. SDK returns the default value (false) and emits a "flag not found" warning metric. This is a silent failure — the feature appears to be disabled rather than throwing an error. Best practice: define flag keys as constants, not raw strings.

Scaling the Flag Streaming Service

  • 100K concurrent SSE connections require 10 flag service instances (10K connections each). Each service subscribes to Redis Pub/Sub for flag change events. When a flag changes: flag management API writes to PostgreSQL → publishes to Redis channel → all 10 flag service instances receive the event → each sends SSE event to its 10K connected SDKs. Propagation to all 100K SDKs happens within seconds.
  • Redis Pub/Sub is not persistent — if a flag service instance is down when a change is published, it misses it. On reconnect, it fetches the full config from PostgreSQL and does a full resync push to all its clients.

🚀D — Deliver2 min

  • Evaluation: 100% in-memory, sub-millisecond. Server-side SDK caches full config (50 MB). Flag evaluation never touches the network.
  • Config propagation: Flag service → Redis Pub/Sub → 10 SSE servers → 100K SDK instances. Kill switch propagation: <30 seconds.
  • Consistency: MurmurHash3(userId + flagKey) % 100 for deterministic, sticky variant assignment.
  • Experimentation: Evaluation events batched to Kafka → analytics pipeline computes significance.
  • Resilience: SDK operates on stale config if flag service is unreachable. Bootstrap file enables cold starts without blocking on the flag service.

☕Java Implementation

/**
 * FeatureFlagEvaluator — core rule engine. Pure logic, no I/O.
 * Evaluates targeting rules in priority order, returns the first matching variant.
 * Falls back to rollout percentage if no explicit rule matches.
 */
public class FeatureFlagEvaluator {

    /**
     * Evaluates a flag for the given user context.
     * Returns the variant name, or the flag's defaultVariant if no rule matches.
     * Never throws — returns defaultVariant on any evaluation error.
     */
    public String evaluate(FlagConfig flag, UserContext user) {
        if (flag.status() != FlagStatus.ACTIVE) {
            return flag.defaultVariant(); // archived/deprecated flags always return default
        }
        for (TargetingRule rule : flag.rules()) { // rules are already sorted by priority
            if (ruleMatches(rule, user)) {
                return resolveVariantFromRule(rule, user, flag.flagKey());
            }
        }
        return flag.defaultVariant(); // no rule matched
    }

    private boolean ruleMatches(TargetingRule rule, UserContext user) {
        if (rule.conditions().isEmpty()) {
            return true; // catch-all rule (no conditions = always matches)
        }
        // AND logic: all conditions must match
        return rule.conditions().stream().allMatch(condition -> evaluateCondition(condition, user));
    }

    private boolean evaluateCondition(RuleCondition condition, UserContext user) {
        String attributeValue = user.getAttribute(condition.attribute());
        if (attributeValue == null) {
            return false; // missing attribute never matches
        }
        return switch (condition.operator()) {
            case "eq"         -> attributeValue.equals(condition.value());
            case "neq"        -> !attributeValue.equals(condition.value());
            case "in"         -> condition.valueList().contains(attributeValue);
            case "not_in"     -> !condition.valueList().contains(attributeValue);
            case "starts_with"-> attributeValue.startsWith(condition.value());
            case "contains"   -> attributeValue.contains(condition.value());
            default           -> false;
        };
    }

    private String resolveVariantFromRule(TargetingRule rule, UserContext user, String flagKey) {
        if (rule.variant() != null) {
            return rule.variant(); // explicit variant assignment for this rule
        }
        // Rollout rule: assign by hash
        return assignByHash(user.getUserId(), flagKey, rule.rollout());
    }

    /**
     * Assigns a variant based on a deterministic hash of userId + flagKey.
     * Same user always gets the same variant for a given flag.
     * Uses MurmurHash3 for uniform distribution with no seed-dependency issues.
     */
    private String assignByHash(String userId, String flagKey, Map<String, Integer> rollout) {
        int bucket = ConsistentHashRollout.getBucket(userId, flagKey);
        int cumulativePercent = 0;
        for (Map.Entry<String, Integer> entry : rollout.entrySet()) {
            cumulativePercent += entry.getValue();
            if (bucket < cumulativePercent) {
                return entry.getKey(); // variant name
            }
        }
        return rollout.keySet().iterator().next(); // fallback — shouldn't happen if percentages sum to 100
    }
}

/**
 * ConsistentHashRollout — deterministic bucket assignment for percentage rollouts.
 * Critical property: given the same userId and flagKey, always returns the same bucket (0-99).
 * Using different flagKey salt ensures users are independently randomized across flags.
 */
public final class ConsistentHashRollout {

    private ConsistentHashRollout() {}

    public static int getBucket(String userId, String flagKey) {
        // Concatenate with a separator to prevent prefix collision
        // "user:123" + "flag:abc" is different from "user:12" + "3flag:abc"
        String hashInput = userId + "::" + flagKey;
        int hashValue = murmurHash3(hashInput.getBytes(StandardCharsets.UTF_8));
        // Math.abs handles Integer.MIN_VALUE edge case: use bitwise AND with max int
        return (hashValue & Integer.MAX_VALUE) % 100;
    }

    private static int murmurHash3(byte[] data) {
        // MurmurHash3 x86 32-bit — optimized for speed, excellent distribution
        int seed = 0;
        int h = seed ^ data.length;
        int i = 0;
        while (i + 4 <= data.length) {
            int k = (data[i] & 0xFF)
                  | ((data[i + 1] & 0xFF) << 8)
                  | ((data[i + 2] & 0xFF) << 16)
                  | ((data[i + 3] & 0xFF) << 24);
            k *= 0xcc9e2d51;
            k = (k << 15) | (k >>> 17);
            k *= 0x1b873593;
            h ^= k;
            h = (h << 13) | (h >>> 19);
            h = h * 5 + 0xe6546b64;
            i += 4;
        }
        // Handle remaining bytes (tail)
        int remaining = data.length - i;
        if (remaining > 0) {
            int tail = 0;
            for (int j = remaining - 1; j >= 0; j--) {
                tail = (tail << 8) | (data[i + j] & 0xFF);
            }
            tail *= 0xcc9e2d51;
            tail = (tail << 15) | (tail >>> 17);
            tail *= 0x1b873593;
            h ^= tail;
        }
        // Finalization mix
        h ^= data.length;
        h ^= (h >>> 16);
        h *= 0x85ebca6b;
        h ^= (h >>> 13);
        h *= 0xc2b2ae35;
        h ^= (h >>> 16);
        return h;
    }
}

/**
 * FlagConfigCache — maintains the in-memory copy of all flag configs.
 * Updated via SSE events from the flag streaming service.
 * Thread-safe: ConcurrentHashMap for reads; synchronized update block for writes.
 */
@Component
public class FlagConfigCache {

    private final ConcurrentHashMap<String, FlagConfig> flagConfigs = new ConcurrentHashMap<>();
    private volatile long lastUpdatedEpochMs = 0;

    public Optional<FlagConfig> getFlag(String flagKey) {
        return Optional.ofNullable(flagConfigs.get(flagKey));
    }

    /**
     * Replaces the entire config with a fresh snapshot from the streaming service.
     * Called on SSE connect/reconnect.
     */
    public void loadSnapshot(Map<String, FlagConfig> snapshot) {
        flagConfigs.clear();
        flagConfigs.putAll(snapshot);
        lastUpdatedEpochMs = System.currentTimeMillis();
    }

    /**
     * Applies a delta update for a single flag. Called on each SSE flag-update event.
     * Atomic: the map entry is replaced atomically, so concurrent reads see either old or new, never partial.
     */
    public void updateFlag(FlagConfig updatedFlag) {
        flagConfigs.put(updatedFlag.flagKey(), updatedFlag);
        lastUpdatedEpochMs = System.currentTimeMillis();
    }

    public void removeFlag(String flagKey) {
        flagConfigs.remove(flagKey);
    }

    public long getLastUpdatedEpochMs() {
        return lastUpdatedEpochMs;
    }
}
