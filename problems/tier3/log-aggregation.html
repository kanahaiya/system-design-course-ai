Tier 3 — Expert 60 minObservability Infrastructure

Design Distributed Log Aggregation System

Log aggregation at scale is an ingest-heavy, search-heavy system where the write volume (1M lines/sec) is orders of magnitude larger than any OLTP workload. The core tension is between cost of storage (keep everything) and cost of search (inverted indexes are expensive). Every architectural decision traces back to: what do on-call engineers need to find, in what time window, and at what cost?

🏢 Elastic (ELK Stack), Splunk, Datadog, Grafana Loki
⏱️ 60 min interview

❓R — Requirements3–5 min

Functional Requirements

  • Collect logs from all microservices (50+ services, 1,000+ instances)
  • Support both structured (JSON) and unstructured (freeform text) log formats
  • Full-text search on log content: keyword search, field filters, time range
  • Correlation: given a request ID, show all logs across all services for that request
  • Alerting: trigger PagerDuty/Slack on log patterns (error rate spike, specific error message)
  • Retention tiers with different storage costs at different ages
  • Dynamic log level adjustment without service restart

Non-Functional Requirements

  • Ingestion throughput: 1M log lines/sec peak; 1 TB/day total volume
  • Search latency: p99 < 1 second for queries over the last 24 hours
  • Availability: 99.9% for ingestion (logs must not be lost); best-effort for search
  • Retention: hot 7 days (fast search), warm 30 days, cold 1 year (S3 + Athena), archive 7 years (Glacier)
  • Security: PII scrubbing before indexing; no credit card numbers, SSNs, emails in search index
  • Durability: at-least-once delivery; acceptable to have duplicate logs, not acceptable to lose logs

Clarifying Questions

  • Do we need real-time streaming (sub-second search) or near-real-time (up to 30 seconds)?
  • Is the system internal (engineers only) or external (customers query their own logs)?
  • What compliance requirements apply to log data? (SOC 2, HIPAA, PCI-DSS)

🔢E — Estimation3–5 min

Ingest Volume

  • 1M log lines/sec × 1 KB average log size = 1 GB/sec raw
  • 1 GB/sec × 86,400 sec/day = 86 TB/day raw (before sampling and compression)
  • After log-level sampling (debug 1%, info 10%, warn 50%, error 100%): ~10 TB/day effective
  • After LZ4 compression (logs compress 5–10×): ~1–2 TB/day on disk

Elasticsearch Index Size

  • Inverted index overhead: Elasticsearch typically uses 3–5× the raw data size for the full index
  • Hot tier (7 days): 7 × 1.5 TB/day = 10.5 TB data + 3× index overhead = ~40 TB per hot cluster
  • Elasticsearch nodes: 40 TB ÷ 2 TB SSD per node (leaving headroom for merges) = 20 data nodes
  • With replication factor 2 = 40 data nodes total for hot tier

Kafka Sizing

  • 1 GB/sec ingest, 24-hour retention on Kafka (for reprocessing): 86 TB of Kafka storage
  • Kafka brokers: 86 TB ÷ 10 TB per broker (commodity, ~50% utilization) = ~9 brokers minimum
  • Partitions: 1M lines/sec ÷ 100K lines/sec per partition = 10 partitions minimum; use 100 for headroom
💡 Senior Signal: Always separate ingestion scale from search scale. At 1M lines/sec, you cannot afford to index everything — sampling is required. The interviewer wants to hear you reason about: what must be indexed (errors always), what can be sampled (debug logs), and what should be stored but not indexed (S3 raw logs for audit).

//   → Kibana Discover for ad-hoc log search
//   → Kibana Alerts for saved alert rules
//   → Correlation view: search by trace_id → show all logs across all services

Elasticsearch Internals: Inverted Index

Understanding why Elasticsearch is fast for log search requires understanding the inverted index:

  • For message: "payment failed", Elasticsearch tokenizes to ["payment", "failed"], builds an inverted index: payment → [doc1, doc45, doc892, ...], failed → [doc1, doc33, ...]. Intersection gives results. This is O(log N) lookup in the posting list, not a table scan.
  • For level: "ERROR" (keyword field), Elasticsearch uses a BKD tree for efficient range queries and exact matches. No tokenization — the entire value "ERROR" is one index term.
  • stack_trace is stored but "index": false — it is returned in results but never tokenized. This saves ~30% of index size for typical log data where stack traces are long but you search on message or error_type, not stack trace content.

Sharding Strategy: Index per Day

Elasticsearch index per day (logs-2024.03.15) is the standard pattern for time-series log data:

  • Time-bounded queries hit only relevant indices (Kibana adds _index: logs-2024.03.* automatically). No need to scan the entire index for last-7-days queries.
  • ILM rollover moves entire indices between hot/warm/cold, not individual documents. Simple and atomic.
  • 5 primary shards per daily index. Each shard ~10–15 GB on hot tier. Shard size is the key performance tuning knob: shards under 10 GB are underutilized; shards over 50 GB have slow merge operations.

🔬D — Deep Dive10 min

1. Sampling Strategy at 1M Lines/Second

Indexing everything at 1M lines/sec is financially prohibitive (40 data nodes for 7-day hot tier). The correct strategy is level-based sampling with reservoir sampling for debug logs:

  • ERROR / FATAL: 100% indexed. You cannot miss production errors. These are low volume (typically <0.1% of total log volume).
  • WARN: 50% sampled. Warnings are high-signal but often noisy; half is sufficient for trending.
  • INFO: 10% sampled. Info logs provide context but are high volume. Sample deterministically by trace_id so all logs for a given request are included or excluded together.
  • DEBUG: 1% sampled using reservoir sampling. Debug logs are for local development; in production they should be turned off by default and only enabled per-service for 15-minute windows during incidents.

Deterministic sampling by trace_id: Instead of random sampling (which means you might miss the ERROR log for a sampled-out trace), sample based on hash(trace_id) % 100 < SAMPLE_RATE. This ensures all-or-nothing per trace — you either see the complete trace logs or none of them. Much more useful for debugging than randomly scattered logs.

2. PII Scrubbing Before Indexing

Logs frequently contain PII accidentally (user email in stack traces, credit card numbers in request logs). Scrubbing must happen in the log processor before data reaches Elasticsearch or S3:

// PII scrubbing patterns applied in Logstash grok/Ruby filter or Flink operator
// Order matters: apply most specific patterns first

CREDIT_CARD: \b(?:4[0-9]{12}(?:[0-9]{3})?|5[1-5][0-9]{14}|3[47][0-9]{13})\b → "***CARD***"
SSN:         \b\d{3}-\d{2}-\d{4}\b                                              → "***SSN***"
EMAIL:       \b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b              → "***EMAIL***"
PHONE:       \b(\+?1[-.\s]?)?\(?\d{3}\)?[-.\s]?\d{3}[-.\s]?\d{4}\b            → "***PHONE***"

// For structured logs: scrub specific JSON fields by name
// user.email, payment.card_number, auth.password → replace with "***REDACTED***"

// Note: Scrubbing is best-effort. Logs containing PII from services that do not use
// the standard logging library should be flagged for compliance review.
// Raw S3 archives are stored in an access-controlled bucket (separate from the
// Elasticsearch-backed hot tier) accessible only to security/compliance team.

3. Retention Tiers and ILM Policy

Elasticsearch Index Lifecycle Management (ILM) automates tier transitions based on age and index size:

// ILM Policy: logs-ilm-policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": { "max_age": "1d", "max_size": "50gb" },  // daily index rotation
          "set_priority": { "priority": 100 }
        }
      },
      "warm": {
        "min_age": "7d",      // move to warm tier after 7 days
        "actions": {
          "shrink": { "number_of_shards": 1 },    // reduce from 5 to 1 shard (less overhead)
          "forcemerge": { "max_num_segments": 1 }, // merge segments → smaller, faster reads
          "set_priority": { "priority": 50 },
          "allocate": { "require": { "data": "warm" } }  // move to warm data nodes (HDD)
        }
      },
      "cold": {
        "min_age": "30d",
        "actions": {
          "searchable_snapshot": { "snapshot_repository": "s3-cold-repo" },
          "set_priority": { "priority": 0 }
        }
      },
      "delete": {
        "min_age": "365d",     // delete from Elasticsearch; raw files still in S3/Glacier
        "actions": { "delete": {} }
      }
    }
  }
}

// S3 lifecycle for raw Parquet files:
// 0-30 days:    S3 Standard (hot, immediate query with Athena)
// 30-365 days:  S3 Standard-IA (infrequent access, ~40% cost reduction)
// 1-7 years:    S3 Glacier Instant Retrieval (archive, 75% cost reduction)
// After 7 years: delete (compliance retention period expired)

4. Correlation IDs Across 50 Microservices

Without correlation IDs, debugging a failed request that touched 12 services is manually correlating timestamps across 12 Kibana tabs. With correlation IDs, one query shows the complete story:

  • Generation: API gateway generates a UUID correlation_id for every incoming request. Also creates a W3C traceparent header for distributed tracing. Both are distinct: correlation_id is business-level, trace_id is observability-level.
  • Propagation: Every service-to-service call (HTTP, gRPC, Kafka message) includes X-Correlation-Id header. Receiving service reads it and stores in SLF4J MDC: MDC.put("correlation_id", incomingId). StructuredLogger reads from MDC and includes in every log line.
  • Search: GET /api/v1/logs/trace/{correlation_id} queries Elasticsearch with term: { correlation_id: "req-uuid-1234" }. Returns all 47 log lines from all 12 services, sorted chronologically. The full story of one request in one view.

5. Dynamic Log Level Control

Changing log verbosity in production traditionally requires a deployment (changing a config file and restarting). With a centralized config service, it is instant:

  • Config service stores current log levels per service in Redis with a short TTL
  • Each service instance subscribes to log config updates via SSE or polling every 10 seconds
  • Incoming config change: set payment-service to DEBUG for 15 minutes, then auto-revert
  • Application code: StructuredLogger checks the dynamic level on every log call; if above threshold, skip. The overhead is a Redis read every 10 seconds and a volatile field check per log call — nanoseconds.
  • This is essential for production incident investigation: debug-level logs reveal internal state without the full debug flood being permanently on.

✅E — Evaluate3 min

Failure Modes

  • Kafka backpressure: If log processors fall behind (Flink/Logstash slow), Kafka consumer lag grows. Log data is still safe (Kafka has 24-hour retention), but Elasticsearch search is delayed. Resolution: scale Logstash workers horizontally; each consumer reads a subset of partitions.
  • Elasticsearch disk full: ILM not configured correctly leads to hot tier filling up. Mitigation: set cluster.routing.allocation.disk.watermark.high: 85% — ES stops allocating new shards. Alert on 75% disk usage.
  • Log agent crash (Filebeat OOM): Filebeat tracks its file read offset in a state file. If the agent crashes and restarts, it resumes from the last committed offset. No log loss, but possible duplication (Kafka deduplication not guaranteed — use at-least-once semantics).
  • PII scrubbing miss: A new service formats a log message with an email in an unexpected field. Not caught by the regex scrubber. Mitigation: field-name-based scrubbing for known PII fields, plus a compliance audit that scans sampled log lines with an ML classifier for PII patterns.

Scaling Beyond 1TB/Day

  • At 10 TB/day, switch from Elasticsearch to ClickHouse or Apache Druid for the hot tier — column-store architecture handles time-series log queries 10–100× faster per node.
  • Kafka at 10 GB/sec: use Kafka with tiered storage (Confluent Platform) — offloads old partitions to S3, reducing broker disk requirements significantly.

🚀D — Deliver2 min

Log aggregation system summary:

  • Pipeline: App (StructuredLogger/MDC) → Filebeat sidecar → Kafka (100 partitions, 24h retention) → Flink processor (PII scrub + sampling) → Elasticsearch hot tier + S3 raw archive
  • Sampling: Level-based (ERROR 100%, INFO 10%, DEBUG 1%) with deterministic sampling by trace_id to preserve complete traces
  • Retention: ES hot (7d SSD) → ES warm (30d HDD, force-merged) → ES searchable snapshot on S3 (1yr) → Glacier (7yr). S3 raw Parquet queryable via Athena throughout.
  • Correlation: X-Correlation-Id header propagated across all services, stored in SLF4J MDC, included in every log line. One query shows the complete request flow.
  • Security: PII scrubbed in Flink before ES indexing. Raw logs in access-controlled S3 bucket.

☕Java Implementation

/**
 * StructuredLogger — wraps SLF4J, enforces JSON log format, reads correlation ID from MDC.
 * All application services use this instead of directly using Logger.
 * The MDC (Mapped Diagnostic Context) is SLF4J's thread-local key-value store.
 */
public final class StructuredLogger {

    private static final String MDC_CORRELATION_ID = "correlation_id";
    private static final String MDC_TRACE_ID       = "trace_id";
    private static final String MDC_SPAN_ID        = "span_id";

    private final Logger delegate;
    private final String serviceName;

    public StructuredLogger(Class<?> clazz, String serviceName) {
        this.delegate    = LoggerFactory.getLogger(clazz);
        this.serviceName = serviceName;
    }

    /**
     * Sets correlation context in SLF4J MDC for the duration of a request.
     * Call at the start of each request handler; call clearContext() in finally.
     * The logback JSON encoder reads MDC fields and includes them in the log JSON output.
     */
    public static void setRequestContext(String correlationId, String traceId, String spanId) {
        MDC.put(MDC_CORRELATION_ID, correlationId);
        MDC.put(MDC_TRACE_ID, traceId);
        MDC.put(MDC_SPAN_ID, spanId);
    }

    public static void clearContext() {
        MDC.clear();
    }

    public void info(String message, Object... keyValuePairs) {
        if (delegate.isInfoEnabled()) {
            delegate.info(buildMessage(message, keyValuePairs));
        }
    }

    public void error(String message, Throwable cause, Object... keyValuePairs) {
        if (delegate.isErrorEnabled()) {
            delegate.error(buildMessage(message, keyValuePairs), cause);
        }
    }

    private String buildMessage(String message, Object[] keyValuePairs) {
        // In production, logback-encoder handles JSON serialization.
        // The delegate.info() call emits: { "message": ..., "service": ..., + all MDC fields }
        // keyValuePairs are structured fields added to the JSON output.
        return message; // logback-encoder picks up MDC and structured arguments
    }
}

/**
 * KafkaLogAppender — Logback appender that writes log events directly to Kafka.
 * Async: uses an in-memory queue to avoid blocking the application thread.
 * Falls back to console if Kafka is unavailable (prevents logging from affecting app availability).
 */
public class KafkaLogAppender extends AppenderBase<ILoggingEvent> {

    private static final String LOG_TOPIC      = "logs.raw";
    private static final int    QUEUE_CAPACITY  = 100_000;
    private static final int    BATCH_SIZE      = 500;
    private static final long   BATCH_LINGER_MS = 100;

    private KafkaProducer<String, String> kafkaProducer;
    private final BlockingQueue<ILoggingEvent> eventQueue = new LinkedBlockingQueue<>(QUEUE_CAPACITY);
    private volatile boolean running = true;

    @Override
    public void start() {
        Properties kafkaProperties = buildKafkaProperties();
        this.kafkaProducer = new KafkaProducer<>(kafkaProperties);
        Thread senderThread = new Thread(this::sendLoop, "kafka-log-sender");
        senderThread.setDaemon(true);
        senderThread.start();
        super.start();
    }

    @Override
    protected void append(ILoggingEvent event) {
        // Non-blocking: if queue is full, drop the log event rather than block the app thread.
        // We prefer dropping low-priority logs over impacting application latency.
        boolean offered = eventQueue.offer(event);
        if (!offered && event.getLevel().isGreaterOrEqual(Level.ERROR)) {
            // For ERROR and above: write synchronously to stderr as fallback
            System.err.println("[LOG_OVERFLOW] " + event.getFormattedMessage());
        }
    }

    private void sendLoop() {
        List<ILoggingEvent> batch = new ArrayList<>(BATCH_SIZE);
        while (running) {
            try {
                ILoggingEvent firstEvent = eventQueue.poll(BATCH_LINGER_MS, TimeUnit.MILLISECONDS);
                if (firstEvent == null) {
                    continue;
                }
                batch.add(firstEvent);
                eventQueue.drainTo(batch, BATCH_SIZE - 1);
                sendBatch(batch);
                batch.clear();
            } catch (InterruptedException interruptedException) {
                Thread.currentThread().interrupt();
                break;
            }
        }
    }

    private void sendBatch(List<ILoggingEvent> events) {
        for (ILoggingEvent event : events) {
            String serviceName = event.getMDCPropertyMap().getOrDefault("service", "unknown");
            String logJson = serializeToJson(event);
            ProducerRecord<String, String> record = new ProducerRecord<>(LOG_TOPIC, serviceName, logJson);
            // Key = service name: ensures all logs from same service go to same partition (ordering)
            kafkaProducer.send(record, (metadata, exception) -> {
                if (exception != null) {
                    System.err.println("[KAFKA_LOG_FAIL] " + exception.getMessage());
                }
            });
        }
    }

    private Properties buildKafkaProperties() {
        Properties properties = new Properties();
        properties.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka-1:9092,kafka-2:9092,kafka-3:9092");
        properties.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,   StringSerializer.class.getName());
        properties.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
        properties.put(ProducerConfig.ACKS_CONFIG,         "1");        // leader ack only — fast
        properties.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "snappy"); // 3× compression, low CPU
        properties.put(ProducerConfig.LINGER_MS_CONFIG,    "50");       // batch for 50ms before sending
        properties.put(ProducerConfig.BATCH_SIZE_CONFIG,   "65536");    // 64KB batch
        return properties;
    }

    private String serializeToJson(ILoggingEvent event) {
        // Simplified — in production use Jackson ObjectMapper with all MDC fields
        return String.format(
            "{\"timestamp\":\"%s\",\"level\":\"%s\",\"message\":\"%s\",\"trace_id\":\"%s\"}",
            Instant.ofEpochMilli(event.getTimeStamp()),
            event.getLevel(),
            event.getFormattedMessage().replace("\"", "\\\""),
            event.getMDCPropertyMap().getOrDefault(StructuredLogger.MDC_TRACE_ID, "")
        );
    }
}

/**
 * LogSampler — reservoir sampling for debug-level logs.
 * Reservoir sampling: first K items are always kept; each subsequent item
 * replaces a random existing item with probability K/n.
 * Result: a statistically representative sample of K logs from the stream.
 */
public class LogSampler {

    private static final int RESERVOIR_SIZE = 1000;  // keep 1000 debug logs per minute window
    private final AtomicInteger totalSeen     = new AtomicInteger(0);
    private final AtomicReferenceArray<String> reservoir =
        new AtomicReferenceArray<>(RESERVOIR_SIZE);
    private final ThreadLocalRandom random = ThreadLocalRandom.current();

    /**
     * Attempts to add a log entry to the reservoir sample.
     * Returns true if the log should be forwarded to Kafka; false if it was dropped.
     */
    public boolean shouldSample(String logJson, Level level) {
        if (level.isGreaterOrEqual(Level.WARN)) {
            return true; // WARN and above: always keep
        }
        if (level == Level.INFO) {
            return Math.abs(logJson.hashCode()) % 10 == 0; // 10% deterministic sample
        }
        // DEBUG: reservoir sampling
        int position = totalSeen.incrementAndGet();
        if (position <= RESERVOIR_SIZE) {
            reservoir.set(position - 1, logJson);
            return true;
        }
        int randomIndex = random.nextInt(position);
        if (randomIndex < RESERVOIR_SIZE) {
            reservoir.set(randomIndex, logJson);
            return true; // replaced an existing entry — still sample this one
        }
        return false; // dropped
    }
}
