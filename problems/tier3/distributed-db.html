Tier 3 — Expert 75 minDatabases

Design a Distributed Database (like Google Spanner / CockroachDB)

Spanner is perhaps the most technically complex production database ever built. Its key insight: TrueTime (GPS + atomic clock hardware) gives a bounded uncertainty interval for real-world time. Waiting until that uncertainty passes (commit wait) makes external consistency provably correct without a centralized coordinator. Understanding MVCC, Raft vs Paxos, cross-shard 2PC, and the difference between strong and stale reads is what distinguishes L6+ candidates on this topic.

🏢 Google Spanner, CockroachDB, YugabyteDB, TiDB
⏱️ 75 min interview
📊 Global, petabytes, external consistency, millions QPS

❓R — Requirements3–5 min

Functional Requirements

  • SQL interface: full SQL (DDL, DML, queries, indexes). Clients use standard SQL drivers (JDBC/ODBC). No learning curve for application developers.
  • ACID transactions: serializability isolation. Cross-row, cross-table, cross-shard transactions must be atomic. Either all succeed or all are rolled back.
  • Global distribution: data replicated across multiple geographic regions. Reads can be served from any region. Writes are globally ordered.
  • Horizontal scaling: add nodes to increase throughput and storage. Data automatically re-sharded (split/merge) as load changes.
  • Schema changes: online DDL (add/remove columns) without taking the database offline. Spanner does this without locking all rows during migration.
  • Strong reads: reads that are guaranteed to reflect all committed writes up to the current time. No stale data.
  • Stale reads: reads at a past timestamp. Served from any replica (no coordination required). Lower latency than strong reads, slightly stale.
  • Snapshot transactions: read-only transaction at a consistent snapshot across all shards. No locks. Reads are globally consistent.

Non-Functional Requirements

  • Consistency: external consistency (a.k.a. strict serializability) — if transaction T2 starts after T1 commits in real time, T2 must see T1's writes. Stronger than serializability.
  • Availability: survives single-node failure transparently. Survives single-datacenter failure with degraded write performance. Configurable quorum for read/write.
  • Throughput: millions of QPS. Google F1 (Google Ads) uses Spanner — billions of ad auction queries per day.
  • Latency: same-region reads: <1ms. Cross-region strong reads: ~10ms. Cross-region writes: ~100ms (limited by speed of light). Stale reads: <1ms anywhere.
  • Durability: data replicated to multiple regions. Loss of any single region does not lose data.

Out of Scope

  • Query optimizer implementation (complex, separate system)
  • Full SQL parser (use an existing parser library)
  • Storage engine internals (we'll reference RocksDB/Bigtable as given)

🔢E — Estimation3–5 min

Scale Numbers

  • Data size: petabytes. Each row stored as key-value: key = (table_id, row_key, column_id, timestamp), value = bytes. With versioning (MVCC), multiple versions per cell.
  • Shard size: each Paxos group manages a shard of ~100MB-1GB. At 1PB total data: 1M-10M shards. Each shard has 5 replicas across 5 zones (typical Spanner config).
  • Node count: Spanner nodes serve ~2000 QPS reads / 1000 QPS writes each. For 10M QPS: ~5000-10000 nodes in a large deployment.
  • Transaction throughput: single-shard transactions: ~10ms commit. Cross-region 2PC: ~100-500ms. This means high-throughput workloads should minimize cross-shard transactions via data locality (co-locate related rows in the same shard using interleaved tables).
  • Latency of commit wait (TrueTime): TrueTime uncertainty epsilon is typically 1-7ms. Commit wait adds epsilon to each write commit. In practice: 1-10ms added per transaction. This is the cost of TrueTime-based external consistency.
💡 Speed of light bottleneck: Cross-region write latency is fundamentally bounded by the speed of light. US East Coast to Western Europe: ~75ms one-way. For a 2-phase commit requiring 2 round trips: ~300ms. This is not an engineering problem — it is a physics problem. Spanner can reduce coordination overhead (TrueTime eliminates some coordinator round trips), but cannot defeat the speed of light. Application architects must co-locate data and traffic geographically for write-intensive workloads.

Internal Key-Value Storage Model

// All data stored as sorted key-value pairs in the underlying storage engine (RocksDB/Bigtable).
// The key encodes: table + row key + column + version timestamp.
// Multiple MVCC versions exist per key, sorted by timestamp descending.

// Key encoding (encoded for sorted order):
// {table_id (8 bytes)} + {row_key (variable)} + {column_family (4 bytes)} +
//   {column_qualifier (variable)} + {~timestamp (8 bytes, inverted for descending sort)}
//
// Example: row "user_123" in table "users", column "name", at timestamp 1720000100
// Key: 0x00000001 + "user_123" + 0x00000001 + "name" + (~1720000100)
// Value: "Alice"
//
// Another version: same row at timestamp 1720000050
// Key: 0x00000001 + "user_123" + 0x00000001 + "name" + (~1720000050)
// Value: "Alicia"
//
// Sorted iteration by key gives: user_123.name@100 → user_123.name@50 → user_123.name@20
// A read at timestamp T returns the first version with timestamp ≤ T.

// Transaction log (Raft/Paxos log entry)
LogEntry {
  logIndex:     long          // monotonically increasing, unique per Raft group
  term:         long          // Raft term (epoch for leader election)
  timestamp:    long          // TrueTime commit timestamp
  operations:  List<Operation>  // list of key-value writes in this transaction
  transactionId: UUID
}

Operation {
  type:       enum   // PUT | DELETE
  key:        byte[]
  value:      byte[] // null for DELETE
}

// Shard (a.k.a. tablet in Spanner terminology)
// A contiguous range of sorted keys
Shard {
  shardId:    UUID
  startKey:   byte[]   // inclusive start of key range
  endKey:     byte[]   // exclusive end of key range
  leaderId:   UUID     // which node is the current Raft/Paxos leader
  replicas:   List<ReplicaLocation>  // where each replica is hosted
  size:       long     // current data size in bytes; used to trigger split
}

MVCC Version Chain Example

// Scenario: bank account balance with three writes at different times
// Key: "account:alice:balance"
//
// Version chain (newest first):
// Version @T=100: value=500  (latest write — Alice received $200)
// Version @T=70:  value=300  (previous write — Alice received $100)
// Version @T=40:  value=200  (original write)
//
// Read at T=100: returns 500 (see latest)
// Read at T=75:  returns 300 (T=100 didn't exist yet from this read's perspective)
// Read at T=50:  returns 200 (T=70 didn't exist yet)
// Read at T=30:  returns null (no version existed at T=30)
//
// Transaction T1 reads at snapshot T=75 → sees 300
// Transaction T2 writes at T=100 → creates version @T=100
// T1 never sees T2's write — it's reading a consistent historical snapshot
// This is how MVCC achieves snapshot isolation without locking readers

Paxos vs Raft: What's the Difference?

Both algorithms achieve the same goal: replicated state machine consensus. Given a set of replicas, they agree on a sequence of log entries even in the face of failures (up to (N-1)/2 node failures with N replicas).

  • Paxos (Spanner): the original algorithm. More flexible (multi-decree Paxos allows pipelining), more complex to implement correctly. Paxos is technically a family of algorithms; Spanner uses a variant called "Multi-Paxos" with persistent leadership for efficiency.
  • Raft (CockroachDB, etcd, TiKV): designed to be understandable. Explicit leader election phase, clear log replication protocol, explicit membership change protocol. Simpler to implement correctly. Equivalent guarantees to Paxos but with different performance characteristics in edge cases.
  • Performance parity: for most workloads, Paxos and Raft have identical throughput and latency. Paxos has a slight edge in specific multi-leader scenarios. For an interview: saying "I'll use Raft because it's simpler to implement correctly" is a perfectly valid L6 answer.

🔬D — Deep Dive10 min

MVCC: How Reads Never Block Writers

Multi-Version Concurrency Control (MVCC) is the foundation of Spanner's performance. Without MVCC, every read would need to acquire a shared lock, blocking writers during reads (or vice versa). MVCC eliminates read-write contention entirely by maintaining multiple versions of each row, one per timestamp.

// MVCC read algorithm:
// 1. Determine read timestamp T (from transaction's snapshot or TrueTime.now())
// 2. For each key K we want to read:
//    a. Iterate the version chain for K in reverse-chronological order
//    b. Return the first version with timestamp ≤ T
//    c. If no version exists with timestamp ≤ T: key did not exist at time T → return null
// 3. No locks acquired. Writer can concurrently write version @T+1 without blocking this read.

// MVCC write algorithm:
// 1. Generate commit timestamp T (from TrueTime)
// 2. For each key K being written:
//    a. Create new version entry: (K, T) → new_value
//    b. Do NOT modify or delete existing versions
// 3. Commit: log entry to Paxos, replicate, apply
// Concurrent readers at timestamps < T see old values; readers at timestamps ≥ T see new values.

// Version garbage collection:
// Old versions consume storage. Spanner GCs versions older than:
//   max(transaction_retention_period, oldest_active_read_timestamp)
// Versions needed by active snapshot reads are preserved.
// GC runs as background compaction in the storage layer (like RocksDB compaction).

TrueTime: The Secret Weapon of Spanner

TrueTime is a hardware-backed API unique to Google's infrastructure. Every Google datacenter has GPS receivers and atomic clocks. The TrueTime API exposes not a single timestamp, but an interval:

// TrueTime API:
// TT.now() → TrueTimeInterval { earliest: long, latest: long }
// TT.before(t) → boolean: is t definitely in the past?
// TT.after(t) → boolean: is t definitely in the future?
//
// The interval [earliest, latest] is a guarantee: the true current time is
// somewhere within this interval. The uncertainty epsilon = latest - earliest.
// In production: epsilon is typically 1-7ms.
//
// External consistency protocol (commit wait):
//
// Step 1: Acquire commit timestamp T
//   T = TT.now().latest  (take the LATEST bound — pessimistic)
//
// Step 2: WAIT until TT.now().earliest > T
//   This means: wait until we're CERTAIN that T is in the past.
//   Wait time ≈ epsilon (typically 1-7ms)
//
// Step 3: Commit and release locks
//
// Why does this achieve external consistency?
// Any transaction T2 that STARTS after T1 COMMITS in real time will see:
//   T2.read_timestamp ≥ T2_start_time > T1_commit_time = T1.timestamp
//   Because we waited until T1.timestamp is definitely in the past before releasing.
// Therefore: T2 will always read T1's writes. QED.
//
// Without TrueTime (using logical clocks):
// You'd need a centralized timestamp server (Percolator's approach).
// Every transaction must contact the timestamp server — a bottleneck and single point of failure.
// TrueTime eliminates the need for a centralized coordinator for timestamp ordering.

// CockroachDB's HLC (Hybrid Logical Clock) alternative:
// HLC = max(physical_clock_ms * 10^6 + logical_counter)
// Satisfies: if event A → event B (causally), then HLC(A) < HLC(B)
// Does NOT satisfy external consistency: if A and B are concurrent with no causal relationship,
// HLC order may not match real-time order. CockroachDB must use uncertainty retries to handle this.
// Less precise than TrueTime but works with standard commodity hardware (no GPS required).

Cross-Shard Transactions: 2PC with Paxos Groups

A transaction that touches multiple shards (e.g., transfer money between accounts on different shards) requires coordination. Spanner uses two-phase commit (2PC) where each shard's Paxos group is a participant:

// Cross-shard 2PC protocol:
//
// Transaction: transfer $100 from Alice (shard A) to Bob (shard B)
//
// Phase 1: Prepare
//   Transaction coordinator (one of the shards' Paxos leaders, often the largest shard)
//   sends PREPARE to each participant shard.
//
//   Shard A receives PREPARE:
//     - Acquire write lock on Alice's row
//     - Verify account has sufficient balance (read under lock)
//     - Log PREPARED record to Paxos (makes prepare durable even if coordinator fails)
//     - Reply PREPARED to coordinator with proposed commit timestamp
//
//   Shard B receives PREPARE:
//     - Acquire write lock on Bob's row
//     - Log PREPARED record to Paxos
//     - Reply PREPARED to coordinator
//
// Phase 2: Commit
//   Coordinator receives PREPARED from all participants.
//   Coordinator determines final commit timestamp:
//     T_commit = max(all proposed timestamps) + commit_wait
//   Coordinator logs COMMIT record (this is the point of no return).
//   Sends COMMIT with T_commit to all participants.
//
//   Shard A receives COMMIT:
//     - Apply the write: Alice's balance -= 100, versioned at T_commit
//     - Release lock on Alice's row
//
//   Shard B receives COMMIT:
//     - Apply the write: Bob's balance += 100, versioned at T_commit
//     - Release lock on Bob's row
//
// If coordinator fails after logging COMMIT:
//   Participants can read the coordinator's COMMIT log from its Paxos group.
//   Protocol completes without the original coordinator.
//
// If coordinator fails after PREPARE but before COMMIT:
//   Participants hold locks (blocking). Eventually a new coordinator detects the
//   timeout and decides to ABORT. All participants release locks and roll back.
//
// This is the classic 2PC problem: blocking in the failure window between
// prepare and commit. Spanner mitigates via Paxos durability of the PREPARE record
// (a new leader can recover the decision) and short timeout (~10-20s).

Strong Reads vs Stale Reads

One of Spanner's most useful features is the ability to explicitly trade freshness for latency:

  • Strong reads (read at TrueTime.now()): must be served from the Paxos leader of each shard. The leader is guaranteed to have all committed writes. If data is distributed across 3 regions, strong reads must contact the leader in its region (may be a different region than the client). Latency: 1ms local, 10-50ms cross-region.
  • Stale reads (read at T = now - staleness): can be served from any replica that has applied all writes up to T. Since all replicas apply writes in order (Paxos guarantees this), any replica that is within the staleness window can serve the read. Latency: <1ms (local replica, no coordination). Perfect for read-heavy workloads where 15-second staleness is acceptable (reporting, analytics, caches).
  • Why stale reads are so powerful: a global Spanner deployment in 5 regions has 5x the read capacity for stale reads vs strong reads. Mobile apps that need consistent data but can tolerate 30-second staleness can route to the nearest region, dramatically reducing latency and cost.

Data Placement and GDPR Compliance

Spanner's zone configuration allows fine-grained control of where data is stored:

  • Default placement: replicate across 3-5 regions globally for availability and performance.
  • GDPR EU data residency: configure European user data with zone constraint: all replicas must be in EU regions. Spanner enforces this: the shard for EU user data will only have replicas in Frankfurt, Netherlands, Belgium. No data leaves the EU.
  • Leader pinning: for write-heavy workloads in a specific region, pin the Paxos leader to that region. All writes go to that region's leader directly. Reduces cross-region write latency.
  • Read-write tradeoff: concentrating replicas in EU (for GDPR) means non-EU reads must go cross-region to EU. This is the correct trade-off for regulated data.
🟢 The CAP theorem and Spanner: Spanner chooses CP in CAP terms: under network partition, Spanner becomes unavailable (cannot achieve quorum without contacting a majority of replicas). This is the correct choice for a transactional database — serving stale data during a partition would violate external consistency. However, Spanner's actual availability is extremely high (Google claims 99.999%+ for multi-region) because TrueTime reduces the window during which coordination is needed, and Paxos with 5 replicas can sustain 2-node failures without impacting availability.

Hot Key Problem

A single high-traffic key (e.g., a global counter or a viral social media post) creates a hotspot on one shard. That shard's Paxos leader becomes the bottleneck, regardless of how many total nodes exist. Solutions:

  • Key design: distribute writes by sharding the hot key. A global counter can be 100 partial counters, each on a different shard, summed at read time.
  • Application-level caching: cache hot read values in Redis in front of Spanner. Reduce reads hitting the hot shard.
  • Batching: batch multiple increments and write them together, reducing write rate to the hot shard.

🚀D — Deliver2 min

Summary for the interview:

Spanner achieves global ACID transactions through three key mechanisms: (1) MVCC — multiple versions per key enable readers to access historical snapshots without locking writers; (2) Paxos/Raft consensus per shard — provides durability and consistent replication across zones; (3) TrueTime — GPS+atomic clock hardware provides a bounded time uncertainty interval. Commit wait (waiting until TT.now().earliest > commit_timestamp) makes external consistency provable: any transaction that starts after T1 commits will have a read timestamp > T1's commit timestamp, guaranteeing it sees T1's writes. Cross-shard transactions use 2PC where each shard's Paxos group is a participant, making 2PC prepare durable and allowing crash recovery without coordinator. Stale reads can serve any replica for <1ms latency at the cost of bounded staleness.

Phased delivery:

  • Phase 1: Single-region. Raft consensus per shard. MVCC. 2PC for cross-shard. HLC for ordering. (CockroachDB-style)
  • Phase 2: Multi-region replication. Stale reads on any replica. Leader pinning for read-heavy regions.
  • Phase 3: TrueTime integration (or HLC with uncertainty retries). Commit wait for external consistency. Zone configuration for GDPR.

CockroachDB and TiKV both use RocksDB.

☕Java Implementation

/**
 * MvccStorage — simplified multi-version key-value store demonstrating MVCC read/write.
 *
 * Stores multiple versions of each key, indexed by timestamp.
 * Reads return the latest version at or before the read timestamp.
 * Writers create new versions without modifying old ones.
 * Background GC cleans versions older than the GC horizon.
 */
public class MvccStorage {

    // version_map: key → TreeMap<timestamp, value> (sorted ascending by timestamp)
    private final ConcurrentHashMap<String, TreeMap<Long, byte[]>> versionMap
        = new ConcurrentHashMap<>();

    private final ReadWriteLock gcLock = new ReentrantReadWriteLock();

    /**
     * Reads the value of a key as it existed at the given timestamp.
     * Returns the latest version with timestamp ≤ readTimestamp.
     * Returns null if the key did not exist at readTimestamp.
     *
     * No locks acquired — MVCC readers never block writers.
     *
     * @param key           the key to read
     * @param readTimestamp the snapshot timestamp for this read
     * @return the byte[] value at readTimestamp, or null
     */
    public byte[] read(String key, long readTimestamp) {
        gcLock.readLock().lock();  // only blocks during GC (rare)
        try {
            TreeMap<Long, byte[]> versions = versionMap.get(key);
            if (versions == null) return null;

            // floorKey returns the greatest timestamp ≤ readTimestamp
            synchronized (versions) {
                Map.Entry<Long, byte[]> matchingVersion = versions.floorEntry(readTimestamp);
                if (matchingVersion == null) return null;

                byte[] value = matchingVersion.getValue();
                return value == TOMBSTONE_MARKER ? null : value;  // Handle deletes
            }
        } finally {
            gcLock.readLock().unlock();
        }
    }

    /**
     * Writes a new version of a key at the given commit timestamp.
     * Does not modify existing versions — creates a new version entry.
     *
     * @param key             the key to write
     * @param value           the new value (null to create a delete tombstone)
     * @param commitTimestamp the commit timestamp (from TrueTime or HLC)
     */
    public void write(String key, byte[] value, long commitTimestamp) {
        gcLock.readLock().lock();
        try {
            TreeMap<Long, byte[]> versions = versionMap.computeIfAbsent(
                key, k -> new TreeMap<>()
            );
            synchronized (versions) {
                versions.put(commitTimestamp, value != null ? value : TOMBSTONE_MARKER);
            }
        } finally {
            gcLock.readLock().unlock();
        }
    }

    private static final byte[] TOMBSTONE_MARKER = new byte[0];  // Sentinel for deletes

    /**
     * Garbage collects versions older than gcHorizon.
     * Safe to call when all active transactions have readTimestamp > gcHorizon.
     *
     * @param gcHorizon all versions with timestamp < gcHorizon can be removed
     */
    public void garbageCollect(long gcHorizon) {
        gcLock.writeLock().lock();  // Exclusive lock: blocks reads during GC (brief)
        try {
            for (TreeMap<Long, byte[]> versions : versionMap.values()) {
                synchronized (versions) {
                    // Keep the latest version at or before gcHorizon (for reads at gcHorizon)
                    Long latestVersionBeforeHorizon = versions.floorKey(gcHorizon - 1);

                    // Remove all versions strictly older than latestVersionBeforeHorizon
                    if (latestVersionBeforeHorizon != null) {
                        versions.headMap(latestVersionBeforeHorizon, false).clear();
                    }
                }
            }
        } finally {
            gcLock.writeLock().unlock();
        }
    }
}

// ─────────────────────────────────────────────────────────────────────────────
// RaftLog — simplified Raft log implementation demonstrating append + commit.
// In production (etcd, CockroachDB): each log entry is replicated to majority before commit.
// ─────────────────────────────────────────────────────────────────────────────
public class RaftLog {

    private final List<LogEntry> entries = new ArrayList<>();
    private volatile long commitIndex = -1;  // highest index known to be committed
    private volatile long applyIndex = -1;   // highest index applied to state machine

    private final MvccStorage stateMachine;  // the state machine to apply entries to
    private final Lock appendLock = new ReentrantLock();

    public RaftLog(MvccStorage stateMachine) {
        this.stateMachine = stateMachine;
    }

    /**
     * Appends a log entry (called on leader for each client write).
     * In a real Raft implementation: entry is replicated to followers before committing.
     * Here we simulate the leader-only path.
     *
     * @return the log index of the appended entry
     */
    public long appendEntry(List<Operation> operations, long commitTimestamp) {
        appendLock.lock();
        try {
            long logIndex = entries.size();
            LogEntry entry = new LogEntry(logIndex, commitTimestamp, List.copyOf(operations));
            entries.add(entry);
            return logIndex;
        } finally {
            appendLock.unlock();
        }
    }

    /**
     * Commits entries up to and including commitUpTo.
     * Called once leader has received acknowledgment from a quorum of replicas.
     * In a 5-replica group: need 3 acks (majority) before committing.
     *
     * @param commitUpTo the log index to commit up to (inclusive)
     */
    public synchronized void commitEntries(long commitUpTo) {
        if (commitUpTo <= commitIndex) return;  // Already committed
        commitIndex = commitUpTo;
        applyCommittedEntries();
    }

    /**
     * Applies committed but not-yet-applied entries to the state machine.
     * This is the point where writes become visible to readers.
     */
    private void applyCommittedEntries() {
        while (applyIndex < commitIndex) {
            applyIndex++;
            LogEntry entryToApply = entries.get((int) applyIndex);
            applyToStateMachine(entryToApply);
        }
    }

    private void applyToStateMachine(LogEntry entry) {
        for (Operation operation : entry.operations()) {
            if (operation.type() == Operation.Type.PUT) {
                stateMachine.write(operation.key(), operation.value(), entry.commitTimestamp());
            } else if (operation.type() == Operation.Type.DELETE) {
                stateMachine.write(operation.key(), null, entry.commitTimestamp());
            }
        }
    }

    public long commitIndex() { return commitIndex; }
    public long applyIndex() { return applyIndex; }
    public int logSize() { return entries.size(); }

    public record LogEntry(long logIndex, long commitTimestamp, List<Operation> operations) {}
    public record Operation(Type type, String key, byte[] value) {
        public enum Type { PUT, DELETE }
    }
}

// ─────────────────────────────────────────────────────────────────────────────
// TwoPhaseCommit — coordinator implementing 2PC for cross-shard transactions.
// Participants: each shard's Paxos leader acts as a participant.
// ─────────────────────────────────────────────────────────────────────────────
public class TwoPhaseCommit {

    private final TrueTimeClock trueTimeClock;

    public TwoPhaseCommit(TrueTimeClock trueTimeClock) {
        this.trueTimeClock = trueTimeClock;
    }

    /**
     * Executes a distributed transaction across multiple shards.
     *
     * @param participants  list of shard participants in the transaction
     * @param operationsPerShard  map of shard ID → list of operations for that shard
     * @return CommitResult with the commit timestamp, or a failed result
     */
    public CommitResult execute(List<TransactionParticipant> participants,
                                 Map<String, List<RaftLog.Operation>> operationsPerShard) {
        String transactionId = UUID.randomUUID().toString();

        // ── Phase 1: Prepare ──
        List<PrepareResult> prepareResults = new ArrayList<>();
        for (TransactionParticipant participant : participants) {
            List<RaftLog.Operation> participantOperations =
                operationsPerShard.getOrDefault(participant.shardId(), List.of());

            PrepareResult result = participant.prepare(transactionId, participantOperations);
            if (!result.success()) {
                // Any failure → abort all participants
                abortAll(participants, transactionId);
                return CommitResult.failure("Prepare failed on shard: " + participant.shardId());
            }
            prepareResults.add(result);
        }

        // ── Determine commit timestamp ──
        // Must be > all proposed timestamps from participants
        long maxProposedTimestamp = prepareResults.stream()
            .mapToLong(PrepareResult::proposedTimestamp)
            .max()
            .orElse(0L);

        // TrueTime commit: take latest bound and apply commit wait
        long trueTimeLatest = trueTimeClock.now().latest();
        long commitTimestamp = Math.max(maxProposedTimestamp + 1, trueTimeLatest);

        // Commit wait: block until TrueTime.now().earliest > commitTimestamp
        // This ensures external consistency: any future transaction starts after this time
        waitForCommitTimestampToPassInRealTime(commitTimestamp);

        // ── Phase 2: Commit ──
        for (TransactionParticipant participant : participants) {
            participant.commit(transactionId, commitTimestamp);
        }

        return CommitResult.success(commitTimestamp);
    }

    private void waitForCommitTimestampToPassInRealTime(long commitTimestamp) {
        // Block until TrueTime earliest bound exceeds commitTimestamp
        // Typically ~1-7ms delay (TrueTime epsilon)
        while (trueTimeClock.now().earliest() <= commitTimestamp) {
            try {
                Thread.sleep(1);  // 1ms spin — in production use a more efficient wait
            } catch (InterruptedException interrupted) {
                Thread.currentThread().interrupt();
                return;
            }
        }
    }

    private void abortAll(List<TransactionParticipant> participants, String transactionId) {
        for (TransactionParticipant participant : participants) {
            try {
                participant.abort(transactionId);
            } catch (Exception abortError) {
                System.err.println("[TwoPhaseCommit] Failed to abort on shard " +
                    participant.shardId() + ": " + abortError.getMessage());
                // Best-effort abort; participant will self-abort after lock timeout
            }
        }
    }

    // Interface for shard participants in 2PC
    public interface TransactionParticipant {
        String shardId();
        PrepareResult prepare(String transactionId, List<RaftLog.Operation> operations);
        void commit(String transactionId, long commitTimestamp);
        void abort(String transactionId);
    }

    public record PrepareResult(boolean success, long proposedTimestamp, String errorReason) {
        public static PrepareResult ok(long proposedTimestamp) {
            return new PrepareResult(true, proposedTimestamp, null);
        }
        public static PrepareResult failure(String reason) {
            return new PrepareResult(false, 0, reason);
        }
    }

    public record CommitResult(boolean success, long commitTimestamp, String errorReason) {
        public static CommitResult success(long commitTimestamp) {
            return new CommitResult(true, commitTimestamp, null);
        }
        public static CommitResult failure(String reason) {
            return new CommitResult(false, 0, reason);
        }
    }

    // TrueTime clock abstraction
    public interface TrueTimeClock {
        TrueTimeInterval now();
        record TrueTimeInterval(long earliest, long latest) {}
    }
}

/**
 * SnapshotTransaction — implements a read-only snapshot transaction using MVCC.
 * No locks acquired. All reads reflect a consistent view at snapshotTimestamp.
 * Can be served from any replica (does not need Paxos leader).
 */
public class SnapshotTransaction {

    private final long snapshotTimestamp;  // All reads use this timestamp
    private final MvccStorage storage;
    private final List<String> keysRead = new ArrayList<>();
    private volatile boolean closed = false;

    public SnapshotTransaction(long snapshotTimestamp, MvccStorage storage) {
        this.snapshotTimestamp = snapshotTimestamp;
        this.storage = storage;
    }

    /**
     * Reads a key at the snapshot timestamp.
     * Consistent: every read in this transaction sees the same versions.
     * No locks required — MVCC ensures this read is non-blocking.
     *
     * @param key the key to read
     * @return value as it existed at snapshotTimestamp, or null if absent
     */
    public byte[] read(String key) {
        ensureOpen();
        keysRead.add(key);
        return storage.read(key, snapshotTimestamp);
    }

    /**
     * Reads a range of keys at the snapshot timestamp.
     * Equivalent to a table scan between startKey and endKey.
     * Returns a consistent snapshot of the range — no locks.
     */
    public Map<String, byte[]> readRange(String startKey, String endKey) {
        ensureOpen();
        Map<String, byte[]> results = new TreeMap<>();
        // In production: use storage.scan(startKey, endKey, snapshotTimestamp)
        // For simplicity: single key lookup (real implementation iterates storage)
        byte[] value = storage.read(startKey, snapshotTimestamp);
        if (value != null) results.put(startKey, value);
        return results;
    }

    public long snapshotTimestamp() { return snapshotTimestamp; }

    public void close() { closed = true; }

    private void ensureOpen() {
        if (closed) throw new IllegalStateException("Transaction has been closed");
    }
}

/**
 * LockManager — manages row-level read/write locks for read-write transactions.
 * Implements strict 2PL: all locks acquired before any are released.
 * Lock release happens only at commit or rollback.
 */
public class LockManager {

    private enum LockMode { SHARED, EXCLUSIVE }

    private static class RowLock {
        LockMode mode;
        UUID holdingTransactionId;
        Instant acquiredAt;

        RowLock(LockMode mode, UUID transactionId) {
            this.mode = mode;
            this.holdingTransactionId = transactionId;
            this.acquiredAt = Instant.now();
        }
    }

    // Per-key lock table
    private final ConcurrentHashMap<String, RowLock> lockTable = new ConcurrentHashMap<>();
    // Per-transaction lock tracking (for release-all-at-commit)
    private final ConcurrentHashMap<UUID, Set<String>> transactionLocks = new ConcurrentHashMap<>();

    private static final long LOCK_WAIT_TIMEOUT_MS = 5_000;  // 5 seconds
    private static final long LOCK_EXPIRY_MS = 30_000;       // 30 seconds (for deadlock/crash recovery)

    /**
     * Acquires a shared (read) lock on a key for a transaction.
     * Multiple transactions can hold shared locks simultaneously.
     * Fails if another transaction holds an exclusive (write) lock.
     *
     * @param key           the key to lock
     * @param transactionId the requesting transaction
     * @throws LockTimeoutException if lock not acquired within timeout
     */
    public void acquireSharedLock(String key, UUID transactionId) throws LockTimeoutException {
        long deadline = System.currentTimeMillis() + LOCK_WAIT_TIMEOUT_MS;

        while (System.currentTimeMillis() < deadline) {
            RowLock existingLock = lockTable.get(key);

            if (existingLock == null || existingLock.mode == LockMode.SHARED
                    || existingLock.holdingTransactionId.equals(transactionId)) {
                // No lock or compatible shared lock: acquire
                RowLock newLock = new RowLock(LockMode.SHARED, transactionId);
                if (lockTable.putIfAbsent(key, newLock) == null || lockTable.get(key).mode == LockMode.SHARED) {
                    trackLock(transactionId, key);
                    return;
                }
            }

            // Lock conflict: wait and retry
            try {
                Thread.sleep(10);  // 10ms retry interval
            } catch (InterruptedException interrupted) {
                Thread.currentThread().interrupt();
                throw new LockTimeoutException("Interrupted while waiting for lock on: " + key);
            }
        }
        throw new LockTimeoutException("Timed out acquiring shared lock on: " + key);
    }

    /**
     * Acquires an exclusive (write) lock on a key.
     * Only one transaction can hold an exclusive lock.
     * Fails if any other transaction holds any lock (shared or exclusive).
     */
    public void acquireExclusiveLock(String key, UUID transactionId) throws LockTimeoutException {
        long deadline = System.currentTimeMillis() + LOCK_WAIT_TIMEOUT_MS;

        while (System.currentTimeMillis() < deadline) {
            RowLock existingLock = lockTable.get(key);

            if (existingLock == null || existingLock.holdingTransactionId.equals(transactionId)) {
                RowLock exclusiveLock = new RowLock(LockMode.EXCLUSIVE, transactionId);
                if (lockTable.replace(key, existingLock, exclusiveLock)
                        || (existingLock == null && lockTable.putIfAbsent(key, exclusiveLock) == null)) {
                    trackLock(transactionId, key);
                    return;
                }
            }

            try { Thread.sleep(10); }
            catch (InterruptedException interrupted) {
                Thread.currentThread().interrupt();
                throw new LockTimeoutException("Interrupted while waiting for exclusive lock on: " + key);
            }
        }
        throw new LockTimeoutException("Timed out acquiring exclusive lock on: " + key);
    }

    /**
     * Releases all locks held by a transaction.
     * Called on commit or rollback. Strict 2PL: locks held until transaction ends.
     *
     * @param transactionId the committing/aborting transaction
     */
    public void releaseAllLocks(UUID transactionId) {
        Set<String> heldKeys = transactionLocks.remove(transactionId);
        if (heldKeys == null) return;

        for (String key : heldKeys) {
            lockTable.remove(key, new RowLock(LockMode.EXCLUSIVE, transactionId));
            lockTable.remove(key, new RowLock(LockMode.SHARED, transactionId));
            // In production: use compare-and-remove to handle concurrent lock release
        }
    }

    /** Periodically called to evict locks held by crashed transactions. */
    public void evictExpiredLocks() {
        Instant expiryThreshold = Instant.now().minusMillis(LOCK_EXPIRY_MS);
        lockTable.entrySet().removeIf(entry ->
            entry.getValue().acquiredAt.isBefore(expiryThreshold)
        );
    }

    private void trackLock(UUID transactionId, String key) {
        transactionLocks.computeIfAbsent(transactionId, id -> ConcurrentHashMap.newKeySet())
                        .add(key);
    }

    public static class LockTimeoutException extends Exception {
        public LockTimeoutException(String message) { super(message); }
    }
}
