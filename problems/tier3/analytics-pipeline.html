Tier 3 — Expert 60 minData Engineering

Design Real-time Analytics Pipeline

Analytics pipelines face a fundamental tension: stream processing is fast but approximate; batch processing is accurate but slow. Lambda architecture runs both in parallel. Kappa architecture bets that stream processing is good enough. Know both trade-offs cold.

🏢 Meta, Airbnb, Uber
⏱️ 60 min interview

❓R — Requirements3–5 min

Functional Requirements

  • Ingest events in real-time (clicks, purchases, page views)
  • Compute aggregations with low latency: count, sum, avg, percentile
  • Support time-windowed queries: hourly, daily totals
  • Ad-hoc SQL queries over historical data
  • Dashboard with live metrics (seconds latency)

Non-Functional Requirements

  • Scale: 10M events/sec, 100TB historical data
  • Latency: Stream aggregations <30s; batch queries <60s
  • Accuracy: Stream <1% error for real-time; batch exact for reporting

🔢E — Estimation3–5 min

  • 10M events/sec × 100 bytes = 1GB/sec raw data → 86TB/day
  • Aggregated to 1-min buckets: much smaller — ~1TB/day aggregated
  • Kafka: 1GB/sec across 1000 partitions = 1MB/sec/partition — manageable

🗄️S — Schema3–5 min

// Raw events (Kafka -- 7-day retention, archived to S3)
event: { event_id, event_type, user_id, properties: JSONB, timestamp }

// Stream aggregations (ClickHouse -- columnar OLAP)
agg_metrics: (metric_name, dimensions, window_start, window_end, value)
  // Written by Flink every 30s per metric+dimension combination

// Historical raw events (S3 -- Parquet format, partitioned by date/hour)
// Queried by Spark for batch jobs and ad-hoc analysis via Athena/Presto

🏗️H — High-level Design10 min

  • Lambda Architecture: Two paths: (1) Speed layer (Kafka → Flink): seconds latency, approximate. (2) Batch layer (S3 → Spark): hours latency, exact. (3) Serving layer (ClickHouse): merges results from both.
  • Flink streaming: Tumbling and sliding windows. State management (RocksDB backend for large state). Watermarks for late data handling.
  • ClickHouse: Columnar OLAP. MergeTree engine. Blazing fast for aggregation queries (SUM/COUNT/GROUP BY). Handles petabytes.
  • Kappa Alternative: Single stream processing pipeline (Kafka + Flink). Simpler ops but cannot reprocess historical data easily — must retain raw Kafka for long periods.

🔌A — APIs5 min

// Ingestion API
POST /api/v1/events
Body: { event_type: "purchase", user_id: "u123", properties: {...}, timestamp: ISO8601 }

// Query API (Serving Layer)
GET /api/v1/metrics?metric=revenue&from=2024-01-01&to=2024-01-02&granularity=1h
Response: { windows: [{start, end, value}, ...] }

// Real-time streaming API
GET /api/v1/metrics/live?metric=active_users   (Server-Sent Events)

🔬D — Deep Dive10 min

Windowing types:

  • Tumbling window: Fixed, non-overlapping. "Orders per hour." Each event belongs to exactly one window. Simple, efficient.
  • Sliding window: Overlapping. "Orders in the last 5 minutes, updated every minute." Each event may belong to multiple windows. More state.
  • Session window: Dynamic, user-activity based. Window closes after N seconds of inactivity. Variable size.

Late data handling (watermarks):

  • Events may arrive out of order (mobile app offline 5 minutes, then bulk send).
  • Watermark = a marker that says all events before time T have arrived. Events before the watermark are considered complete.
  • Flink uses event-time watermarks: advance watermark to max(event_time) - allowed_lateness.
  • Events arriving after watermark: counted in a late-event side output, can trigger window recomputation.

✅E — Evaluate3 min

  • Lambda complexity: Maintaining two separate pipelines (stream + batch) with the same business logic is error-prone. Kappa (stream-only with long Kafka retention for replay) is gaining adoption as stream frameworks mature.
  • ClickHouse at scale: For 100TB+, use distributed ClickHouse cluster. ZooKeeper-based replication. Shard by high-cardinality dimension (user_id) to distribute write load.

🚀D — Deliver2 min

Lambda architecture: speed layer (Kafka + Flink) for real-time dashboards, batch layer (Spark + S3) for accurate reporting, serving layer (ClickHouse) merges both. Key insight: windowing + watermarks handle out-of-order events gracefully.

⚖️Trade-offs

DecisionLambdaKappa
ArchitectureTwo pipelines: stream + batch. High accuracy. High complexity.One pipeline: stream only. Lower accuracy. Simpler ops.
ReprocessingEasy: re-run Spark job over S3Requires long Kafka retention or S3 compaction
Window typeTumbling: simple, no overlapSliding: more insight, higher state/memory cost

☕Java Implementation

/**
 * StreamingAggregator -- implements tumbling window aggregation with
 * circular buffer and bounded late data acceptance.
 */
public class StreamingAggregator {

    private static final int WINDOW_SIZE_SECONDS = 60;
    private static final int LATE_ARRIVAL_GRACE_SECONDS = 30;

    private final long[] windowCounts;
    private final long[] windowStartTimes;
    private int currentWindowIndex = 0;
    private long currentWindowStart;

    public StreamingAggregator(int windowCount) {
        this.windowCounts = new long[windowCount];
        this.windowStartTimes = new long[windowCount];
        this.currentWindowStart = System.currentTimeMillis() / 1000 / WINDOW_SIZE_SECONDS * WINDOW_SIZE_SECONDS;
    }

    /**
     * Processes an event with its event-time timestamp.
     * Handles on-time and late events; ignores too-late events.
     */
    public void processEvent(long eventTimestampSeconds, long incrementValue) {
        long eventWindowStart = eventTimestampSeconds / WINDOW_SIZE_SECONDS * WINDOW_SIZE_SECONDS;
        long ageSeconds = currentWindowStart - eventWindowStart;

        if (ageSeconds < 0) {
            incrementCurrentWindow(incrementValue); // future event (clock skew)
        } else if (ageSeconds <= LATE_ARRIVAL_GRACE_SECONDS) {
            int targetIndex = findWindowIndex(eventWindowStart);
            if (targetIndex >= 0) {
                windowCounts[targetIndex] += incrementValue;
            }
        }
        // Too late -- drop or route to late-data side output
    }

    /**
     * Advances to the current time window, flushing completed windows.
     */
    public List<WindowResult> advanceToCurrentTime() {
        long nowWindowStart = System.currentTimeMillis() / 1000 / WINDOW_SIZE_SECONDS * WINDOW_SIZE_SECONDS;
        List<WindowResult> completedWindows = new ArrayList<>();

        while (currentWindowStart < nowWindowStart) {
            completedWindows.add(new WindowResult(windowStartTimes[currentWindowIndex], windowCounts[currentWindowIndex]));
            currentWindowIndex = (currentWindowIndex + 1) % windowCounts.length;
            currentWindowStart += WINDOW_SIZE_SECONDS;
            windowCounts[currentWindowIndex] = 0;
            windowStartTimes[currentWindowIndex] = currentWindowStart;
        }
        return completedWindows;
    }

    private void incrementCurrentWindow(long value) { windowCounts[currentWindowIndex] += value; }

    private int findWindowIndex(long targetWindowStart) {
        for (int i = 0; i < windowCounts.length; i++) {
            if (windowStartTimes[i] == targetWindowStart) return i;
        }
        return -1;
    }

    public record WindowResult(long windowStart, long count) {}
}
