Tier 3 — Expert 60 minData Engineering

Design Real-time Analytics Pipeline

Analytics pipelines live at the intersection of two competing requirements: the product manager wants to see metrics updating every minute; the data engineer knows that accurate metrics over historical data require batch reprocessing. Lambda architecture tries to have both; Kappa architecture argues you can reprocess streaming data. Understanding why each exists — and when to choose which — is the Staff-level insight.

🏢 Google Analytics, Amplitude, Mixpanel, Segment
⏱️ 60 min interview

❓R — Requirements3–5 min

Functional Requirements

  • Ingest user behavior events from web/mobile clients (page views, clicks, purchases, custom events)
  • Real-time dashboards: active users, events per minute, revenue per hour — updates within 60 seconds
  • Funnel analysis: conversion from step A → B → C, with drop-off rates at each step
  • Cohort analysis: group users by signup week, track retention over 8 weeks
  • Session analysis: group events into sessions (30-minute inactivity timeout)
  • Historical queries: arbitrary SQL-like queries over 1 year of event history
  • Segmentation: filter any analysis by user attributes (country, plan, device type)

Non-Functional Requirements

  • Ingest throughput: 1B events/day = ~11,600 events/sec average, ~100K events/sec peak
  • Real-time latency: dashboard metrics updated within 60 seconds of event receipt
  • Historical query latency: p99 < 10 seconds for queries over 1 year of data
  • Data freshness: real-time metrics within 60 seconds; accurate historical metrics within 2 hours
  • Storage: 1 PB of historical event data (1 year)
  • Availability: event ingestion 99.99% (no events dropped); analytics query 99.9%

Clarifying Questions

  • Is approximate real-time data acceptable (99%+ accurate) or do we need exact accuracy for all queries?
  • What query patterns dominate: ad-hoc SQL or pre-defined dashboards?
  • Do we need user-level event history (for debugging one user's journey) or only aggregate metrics?

🔢E — Estimation3–5 min

Event Volume and Storage

  • 1B events/day × 500 bytes average event size = 500 GB/day raw
  • After LZ4 compression (Parquet columnar format, ~10× for event data): ~50 GB/day on disk
  • 1 year: 50 GB/day × 365 = ~18 TB. Well within S3 for $0.023/GB = ~$414/month.
  • Kafka: 500 GB/day ÷ 86,400 = ~6 MB/sec continuous ingest. 3-day retention on Kafka = 1.5 TB Kafka storage.

Kafka Sizing

  • 6 MB/sec × 3 replicas = 18 MB/sec disk writes across cluster
  • 100K events/sec peak × 500 bytes = 50 MB/sec peak. Kafka handles this with 3 brokers + 100 partitions.
  • Partition count: 100K events/sec ÷ 10K events/sec per partition = 10 minimum; use 100 for headroom.

ClickHouse/Druid Cluster for Real-time Queries

  • Hot data: last 30 days = 30 × 50 GB = 1.5 TB compressed. 3 ClickHouse nodes with 1 TB SSD each = 3 TB, enough for hot data + indexes.
  • Historical queries on S3 Parquet via Athena: pay per query, ~$5/TB scanned. 100K queries/day × 1 TB scan average = $500/day — expensive. Use ClickHouse for last 30 days to avoid Athena for common queries.
💡 Senior Signal: State the Kappa vs Lambda choice upfront with your reasoning. For this problem: Kappa is preferred because Kafka retains 3 days (enough to handle most late-arriving data), reprocessing is possible by resetting consumer offsets, and the architecture is simpler. The only case for Lambda is if accurate reprocessing over years of data is needed frequently — in that case you need a separate batch layer.

ClickHouse Table Design

-- ClickHouse: wide table, all events in one table.
-- MergeTree family with ORDER BY (date, user_id) for efficient time-range + user queries.
-- Partition by month enables dropping old data and parallel query execution.

CREATE TABLE events
(
    event_id       UUID,
    event_type     LowCardinality(String),   -- LowCardinality: dictionary-encoded, efficient for enums
    user_id        String,
    anonymous_id   String,
    session_id     String,
    timestamp      DateTime64(3, 'UTC'),
    received_at    DateTime64(3, 'UTC'),
    date           Date MATERIALIZED toDate(timestamp),    -- for partition pruning
    country        LowCardinality(String),
    device_type    LowCardinality(String),
    page_url       String,
    revenue_usd    Nullable(Float64),
    properties     String                    -- JSON blob for event-specific fields
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(date)                  -- monthly partition: drop month = instant
ORDER BY (date, user_id, timestamp)          -- primary sort: enables fast user-timeline queries
SETTINGS index_granularity = 8192;          -- 8192 rows per index entry

-- Materialized views for common aggregations (pre-computed at ingest time):
CREATE MATERIALIZED VIEW hourly_page_views
ENGINE = SummingMergeTree()
PARTITION BY toYYYYMM(hour)
ORDER BY (hour, page_url)
AS SELECT
    toStartOfHour(timestamp) AS hour,
    page_url,
    countIf(event_type = 'page_view') AS views,
    uniqState(user_id) AS unique_users_state    -- HyperLogLog state for approximate distinct count
FROM events
GROUP BY hour, page_url;

🏗️H — High-level Design10 min

Figure: Lambda vs Kappa architecture — Lambda adds accuracy via batch layer at the cost of operational complexity

Lambda Architecture vs Kappa Architecture

Lambda Architecture (Traditional)

// Three layers:
// 1. Batch layer (Spark on S3): accurate, complete, slow (2-hour delay for last hour's data)
//    → Processes all historical events from S3 Parquet
//    → Outputs: accurate aggregates, complex metrics, ML training data
//
// 2. Speed layer (Flink on Kafka): approximate, fast (sub-minute freshness)
//    → Processes only the last few hours of events from Kafka
//    → Outputs: real-time counters (pageviews/minute), active user counts
//
// 3. Serving layer (ClickHouse + Redis): merges batch and speed layer outputs
//    → For recent data: serve from speed layer (fast, approximate)
//    → For historical data: serve from batch layer (accurate)
//    → Dashboard API: "is this query asking about recent data? → speed layer. historical? → batch"
//
// Problem: two codebases doing similar logic, both must be kept in sync.
// A bug in the batch Spark job that fixes a calculation must also be fixed in the Flink job.
// Nathan Marz (creator of Lambda) later acknowledged this is the biggest maintenance burden.

Kappa Architecture (Modern Preferred Approach)

// Single streaming pipeline (Flink on Kafka):
// Kafka is the immutable event log. Flink processes it.
// For reprocessing: reset consumer group offset to start of Kafka retention (3 days)
//   OR replay from S3 Parquet (the archive) using a Flink S3 source connector.
//
// Key insight: a streaming job can replay historical data by reading from S3 Parquet
// the same way it reads from Kafka — both are just ordered streams of events.
// The Flink job is written once; it processes both real-time and historical replay.
//
// Advantages:
// - One codebase for all analytics logic
// - Reprocessing = restart job with earlier start time
// - Simpler operational model
//
// Limitations:
// - Kafka retention is bounded (3-7 days). Replay beyond that requires reading from S3.
// - S3 replay is slower than Kafka replay (no real-time serving during reprocess).
// - Complex stateful operations (e.g., 1-year cohort analysis) require large Flink state.

Full Kappa Architecture Pipeline

// ─── Event Ingestion ──────────────────────────────────────────────────────────
// Client SDK (JS/iOS/Android) → HTTP POST to ingestion API
//   → API validates, enriches (geo-resolve IP → country, user-agent → device type)
//   → Deduplication: Redis SETNX event_id (expire 24h) — drop duplicate events
//   → Write to Kafka topic: "events.raw" (partitioned by userId for session ordering)
//   → Write to S3 Parquet (every 5 minutes, micro-batching): archive layer

// ─── Stream Processing (Flink) ────────────────────────────────────────────────
// Flink job 1: Sessionization
//   → Reads "events.raw"
//   → KeyedProcessFunction keyed by userId
//   → State: last event timestamp per user
//   → If gap > 30 minutes: emit SessionEnd event, reset session
//   → Enriches all events with session_id, session_number, session_duration
//   → Outputs to "events.enriched" topic

// Flink job 2: Real-time Aggregations
//   → Reads "events.enriched"
//   → Tumbling windows: 1-minute counts per event_type
//   → Outputs to Redis: INCR realtime:pageviews:2024-03-15T10:23 (key per minute)
//   → Dashboard reads from Redis: last 60 keys = last hour, chart rendered in browser

// Flink job 3: Funnel Analysis
//   → Reads "events.enriched"
//   → Stateful windowed join: user must complete step A within 24h of step B
//   → Outputs funnel completion events to ClickHouse

// ─── Storage (Serving) ────────────────────────────────────────────────────────
// Redis: real-time counters (last 24 hours, pre-aggregated per minute/hour)
// ClickHouse: last 30 days of events (fast SQL queries, sub-second on aggregations)
// S3 Parquet + Athena: full history (slow but complete, for long-range queries)

Real-time Dashboard Architecture

The real-time part is the most commonly misdesigned. The naive approach (query the database every minute) creates constant read pressure. The correct approach is pre-computed counters:

  • Flink writes to Redis: INCR metric:pageviews:2024-03-15T10:23 (key = metric name + minute bucket). Each event increments the relevant counters atomically.
  • Dashboard API reads the last 60 keys (last 60 minutes) from Redis in a single MGET command → builds the time series. Total latency: ~1ms, no ClickHouse query needed.
  • Active users (HyperLogLog): use Redis HLL PFADD active:2024-03-15T10 user123. PFCOUNT active:2024-03-15T10 returns approximate distinct count with <1% error. Exact distinct count requires much more memory.

🔬D — Deep Dive10 min

1. Sessionization: Stateful Flink with Timers

Sessionization groups events into sessions based on the 30-minute inactivity timeout. This is a fundamentally stateful operation — you need to remember each user's last event time across the entire event stream:

// Flink KeyedProcessFunction: processes events keyed by userId.
// For each event:
//   1. Record the timestamp in state.
//   2. Cancel any existing inactivity timer.
//   3. Set a new inactivity timer for 30 minutes from now.
//
// When the timer fires (30 minutes after last event):
//   → Session ended. Emit SessionEnd event with session_id, duration, event_count.
//   → Clear state for this userId.
//
// For each event within a session:
//   → Tag with current session_id (UUID generated at first event of session).
//   → Emit enriched event downstream.
//
// Late arriving events (mobile offline, 2-hour delay):
// Flink watermarking handles late events. Set watermark = event time - 2 hours.
// Events arriving within 2 hours of the watermark are assigned to the correct session.
// Events older than 2 hours are emitted to a late-data side output for separate handling.

2. Funnel Analysis: Ordered Event Join

Funnel analysis requires finding users who performed event A, then event B, then event C — in order — within a time window. This is not a simple GROUP BY. It requires an ordered join:

// Approach 1: Batch SQL (ClickHouse, for historical funnels)
// Self-join approach: each step joins to the previous step's result.

WITH step1 AS (
    SELECT user_id, min(timestamp) AS step1_time
    FROM events
    WHERE event_type = 'page_view'
      AND page_url LIKE '/product/%'
      AND date BETWEEN '2024-03-01' AND '2024-03-15'
    GROUP BY user_id
),
step2 AS (
    SELECT e.user_id, min(e.timestamp) AS step2_time
    FROM events e
    JOIN step1 ON e.user_id = step1.user_id
    WHERE e.event_type = 'add_to_cart'
      AND e.timestamp BETWEEN step1.step1_time AND step1.step1_time + INTERVAL 24 HOUR
    GROUP BY e.user_id
),
step3 AS (
    SELECT e.user_id, min(e.timestamp) AS step3_time
    FROM events e
    JOIN step2 ON e.user_id = step2.user_id
    WHERE e.event_type = 'purchase'
      AND e.timestamp BETWEEN step2.step2_time AND step2.step2_time + INTERVAL 24 HOUR
    GROUP BY e.user_id
)
SELECT
    (SELECT count(DISTINCT user_id) FROM step1) AS entered,
    (SELECT count(DISTINCT user_id) FROM step2) AS reached_step2,
    (SELECT count(DISTINCT user_id) FROM step3) AS converted;

-- ClickHouse executes this in 2-3 seconds on 1B events (column-store, parallel reads).

3. Cohort Analysis: The Retention Matrix

Cohort analysis requires two passes over event data: (1) find when each user first performed the cohort event, (2) find each subsequent period they performed the return event. In ClickHouse:

-- Step 1: Assign cohort week to each user
WITH user_cohorts AS (
    SELECT
        user_id,
        toMonday(min(timestamp)) AS cohort_week    -- ISO week of first event
    FROM events
    WHERE event_type = 'user_signed_up'
    GROUP BY user_id
),

-- Step 2: For each session, compute which period (relative to cohort week) it falls in
user_periods AS (
    SELECT
        e.user_id,
        uc.cohort_week,
        dateDiff('week', uc.cohort_week, toMonday(e.timestamp)) AS period_number
    FROM events e
    JOIN user_cohorts uc ON e.user_id = uc.user_id
    WHERE e.event_type = 'session_start'
      AND dateDiff('week', uc.cohort_week, toMonday(e.timestamp)) BETWEEN 0 AND 7
    GROUP BY e.user_id, uc.cohort_week, period_number
)

-- Step 3: Aggregate into retention matrix
SELECT
    cohort_week,
    countDistinctIf(user_id, period_number = 0)  AS week_0,   -- cohort size
    countDistinctIf(user_id, period_number = 1)  AS week_1,
    countDistinctIf(user_id, period_number = 2)  AS week_2,
    -- ...
    countDistinctIf(user_id, period_number = 7)  AS week_7
FROM user_periods
GROUP BY cohort_week
ORDER BY cohort_week;

4. Late-arriving Events and Watermarking

Mobile apps frequently send events after the user comes back online. An event that happened at 10:00 AM might arrive at the server at 2:00 PM (4-hour delay if the user was on a flight). How to handle this:

  • Event timestamp vs received_at: Always store both. timestamp = when the event happened (client's clock). received_at = when the server received it (server's clock). Use received_at for real-time streaming (to avoid out-of-order processing). Use timestamp for historical batch analytics (for accurate user timeline).
  • Flink watermark: Set watermark = max(received_at) - 4 hours. Events older than the watermark trigger window closure. Events within 4 hours of the watermark are included in the current window. This handles mobile late arrivals without indefinitely delaying windows.
  • S3 correction: For events arriving more than 4 hours late, they land in S3 with their original timestamp. The daily batch Spark job reprocesses the previous day's S3 data and produces accurate aggregate corrections, replacing the approximate real-time counts in ClickHouse.

5. Pre-aggregation for Real-time Dashboards

A naive implementation queries ClickHouse for "pageviews in the last hour" every time a dashboard loads. With 100K dashboard queries/day and each requiring a full-table scan, this is expensive. Pre-aggregation solves this:

  • Flink writes pre-aggregated results to Redis. Key: metric:pageviews:2024-03-15T10:23. Value: count. One Redis key per metric per minute.
  • Dashboard API reads 60 keys (MGET) → 1ms response, no ClickHouse query. Redis TTL = 25 hours (one day of minute-granularity data).
  • For HyperLogLog (approximate distinct users): Flink calls PFADD active_users:hour:2024-03-15T10 {user_id}. Dashboard reads PFCOUNT active_users:hour:2024-03-15T10 → ~10,000 distinct users with <1% error in 12 bytes of memory. Exact count would require storing all user IDs.

✅E — Evaluate3 min

Failure Modes

  • Duplicate events: Client SDK retries on network error. Same event sent twice. Without deduplication: pageview counted twice. Mitigation: Redis SETNX by event_id (24-hour TTL at ingestion). If SETNX returns 0 (key existed): drop the duplicate before it reaches Kafka. The 24-hour window covers retry scenarios.
  • Kafka consumer lag during traffic spike: Black Friday: 10× normal traffic. Flink consumers fall behind Kafka producers. Real-time metrics become delayed (60 minutes instead of 60 seconds). Kafka retains 3 days so no data is lost. Resolution: auto-scale Flink taskmanager instances. Pre-scale before known traffic spikes.
  • ClickHouse MergeTree write amplification: At 100K events/sec, small INSERTs cause many small parts. ClickHouse background merges these. If inserts are too frequent, parts exceed the limit and inserts are throttled. Solution: batch inserts (write every 1 second, not per-event) via Flink ClickHouse sink with configurable batch size.
  • Clock skew on client devices: A mobile device with incorrect clock sends events with timestamps 1 year in the past. These events would be placed in the wrong ClickHouse partition. Mitigation: validate event timestamp at ingestion — if more than 24 hours from server time, replace with received_at. Log the original client timestamp in properties for debugging.

Scale to 10B Events/Day

  • Kafka: increase partition count to 1,000. Add 10 more brokers (linear scaling).
  • ClickHouse: add more shards. ClickHouse supports distributed tables that shard data across nodes; queries are scatter-gathered automatically.
  • S3 cost at 10B events/day: 5 TB/day compressed × 365 = 1.8 PB/year = $41K/year in S3 storage. Acceptable.

🚀D — Deliver2 min

  • Architecture: Kappa — single Flink pipeline on Kafka. Reprocessing via S3 Parquet replay. No duplicate batch + speed codebase.
  • Ingest: Client SDK → batch POST (50 events/10 sec) → ingestion API (validate + geo-enrich + deduplicate) → Kafka (partitioned by userId) + S3 Parquet (5-min micro-batches)
  • Processing: Flink job 1: sessionization (stateful, 30-min timer). Job 2: real-time aggregations to Redis. Job 3: funnel/cohort computation to ClickHouse.
  • Real-time dashboards: Redis pre-aggregated counters per minute (1ms query). HyperLogLog for distinct user counts.
  • Historical queries: ClickHouse for last 30 days (sub-second SQL). Athena on S3 Parquet for full history (10-second queries, pay-per-scan).
  • Data freshness: Real-time metrics <60 seconds. Accurate historical metrics: next batch run (2-hour delay for late-arriving mobile events).

☕Java Implementation

/**
 * SessionizationProcessFunction — Flink stateful function that groups events into sessions.
 * A session ends when there is 30 minutes of user inactivity.
 * Keyed by userId so each user's state is independent.
 */
public class SessionizationProcessFunction
        extends KeyedProcessFunction<String, AnalyticsEvent, SessionizedEvent> {

    private static final long SESSION_TIMEOUT_MS = 30 * 60 * 1000L; // 30 minutes

    // Flink managed state: survives task failures (checkpointed to RocksDB)
    private ValueState<String>  currentSessionId;
    private ValueState<Long>    lastEventTimeMs;
    private ValueState<Integer> eventCountInSession;

    @Override
    public void open(Configuration parameters) {
        currentSessionId     = getRuntimeContext().getState(
            new ValueStateDescriptor<>("session-id", String.class));
        lastEventTimeMs      = getRuntimeContext().getState(
            new ValueStateDescriptor<>("last-event-time", Long.class));
        eventCountInSession  = getRuntimeContext().getState(
            new ValueStateDescriptor<>("event-count", Integer.class));
    }

    @Override
    public void processElement(AnalyticsEvent event,
                                Context context,
                                Collector<SessionizedEvent> output) throws Exception {
        String sessionId = currentSessionId.value();
        long   eventTime = event.getTimestampMs();

        if (sessionId == null) {
            // First event for this user (or first after a session expiry): start new session
            sessionId = UUID.randomUUID().toString();
            currentSessionId.update(sessionId);
            eventCountInSession.update(0);
        }

        // Update last event time and event count
        lastEventTimeMs.update(eventTime);
        eventCountInSession.update(eventCountInSession.value() + 1);

        // Cancel existing inactivity timer and set a new one
        // (Flink allows registering multiple timers; we track via the processing-time timer API)
        context.timerService().registerProcessingTimeTimer(
            System.currentTimeMillis() + SESSION_TIMEOUT_MS
        );

        // Emit the event enriched with session context
        output.collect(SessionizedEvent.from(event, sessionId, eventCountInSession.value()));
    }

    @Override
    public void onTimer(long timerTimestamp, OnTimerContext context,
                        Collector<SessionizedEvent> output) throws Exception {
        Long lastEvent = lastEventTimeMs.value();
        if (lastEvent == null) {
            return;
        }
        long timeSinceLastEvent = System.currentTimeMillis() - lastEvent;
        if (timeSinceLastEvent >= SESSION_TIMEOUT_MS) {
            // Session ended — emit session summary event
            String sessionId = currentSessionId.value();
            int eventCount   = eventCountInSession.value();
            output.collect(SessionizedEvent.sessionEnd(
                context.getCurrentKey(), sessionId, eventCount, lastEvent
            ));
            // Clear state so the next event starts a new session
            currentSessionId.clear();
            lastEventTimeMs.clear();
            eventCountInSession.clear();
        }
        // If not yet expired: another event arrived recently, timer was superseded
    }
}

/**
 * EventIngestionService — HTTP endpoint that receives event batches, validates,
 * deduplicates, and forwards to Kafka.
 */
@RestController
@RequestMapping("/api/v1/events")
public class EventIngestionService {

    private static final int MAX_BATCH_SIZE     = 500;
    private static final int MAX_EVENT_SIZE_BYTES = 10_240; // 10 KB per event

    private final KafkaProducer<String, String> kafkaProducer;
    private final StringRedisTemplate redisTemplate;
    private final GeoIpResolver geoIpResolver;

    public EventIngestionService(KafkaProducer<String, String> kafkaProducer,
                                  StringRedisTemplate redisTemplate,
                                  GeoIpResolver geoIpResolver) {
        this.kafkaProducer  = kafkaProducer;
        this.redisTemplate  = redisTemplate;
        this.geoIpResolver  = geoIpResolver;
    }

    @PostMapping("/batch")
    public ResponseEntity<BatchResponse> ingestBatch(
            @RequestBody EventBatch batch,
            @RequestHeader("X-Forwarded-For") String clientIp) {

        if (batch.getEvents().size() > MAX_BATCH_SIZE) {
            return ResponseEntity.badRequest()
                .body(BatchResponse.error("Batch exceeds " + MAX_BATCH_SIZE + " events"));
        }

        List<String> acceptedIds    = new ArrayList<>();
        List<String> duplicateIds   = new ArrayList<>();

        for (AnalyticsEvent event : batch.getEvents()) {
            if (isDuplicate(event.getEventId())) {
                duplicateIds.add(event.getEventId());
                continue;
            }
            AnalyticsEvent enrichedEvent = enrichEvent(event, clientIp);
            sendToKafka(enrichedEvent);
            acceptedIds.add(event.getEventId());
        }

        return ResponseEntity.accepted()
            .body(BatchResponse.success(acceptedIds.size(), duplicateIds.size()));
    }

    private boolean isDuplicate(String eventId) {
        // Redis SETNX: set key only if not exists. Returns true if key was SET (not duplicate).
        // If false: key already existed → duplicate event.
        Boolean wasSet = redisTemplate.opsForValue()
            .setIfAbsent("dedup:" + eventId, "1", Duration.ofHours(24));
        return !Boolean.TRUE.equals(wasSet);
    }

    private AnalyticsEvent enrichEvent(AnalyticsEvent event, String clientIp) {
        String country = geoIpResolver.resolveCountry(clientIp); // MaxMind GeoIP2 DB
        long receivedAtMs = System.currentTimeMillis();

        // Validate and bound the client timestamp — reject events more than 24h old
        long eventTimeMs = event.getTimestampMs();
        if (Math.abs(receivedAtMs - eventTimeMs) > 86_400_000L) {
            eventTimeMs = receivedAtMs; // replace with server time for extreme clock skew
        }
        return event.toBuilder()
            .country(country)
            .receivedAtMs(receivedAtMs)
            .timestampMs(eventTimeMs)
            .build();
    }

    private void sendToKafka(AnalyticsEvent event) {
        String userId = event.getUserId() != null ? event.getUserId() : event.getAnonymousId();
        String eventJson = JsonSerializer.serialize(event);
        ProducerRecord<String, String> record = new ProducerRecord<>("events.raw", userId, eventJson);
        // Async send — fire and forget with error logging
        kafkaProducer.send(record, (metadata, exception) -> {
            if (exception != null) {
                // Log but do not surface to client — ingestion is accepted once we decide to keep it
                System.err.println("[KAFKA_INGEST_FAIL] eventId=" + event.getEventId()
                    + " error=" + exception.getMessage());
            }
        });
    }
}
