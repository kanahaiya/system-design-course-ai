Tier 2 — Should Know 45 min Media Heavy Social Graph

Design Instagram

Instagram forces you to solve two distinct hard problems simultaneously: media storage and delivery at petabyte scale, and social graph fanout where a single celebrity post must reach 380M followers. The celebrity problem alone disqualifies any pure fanout-on-write strategy. At L6 you must know the hybrid approach, the algorithmic ranking pipeline, Stories vs Posts storage differences, and the Explore tab recommendation system.

🏢 Meta, Pinterest, Snap
⏱️ 45 min interview
📸 100M photos/day
👥 2B MAU

❓ R — Requirements 3–5 min

Interview tip: Spend 3–4 minutes here. Ask: "Should I prioritize feed generation, the upload pipeline, or Explore?" Most interviewers say the feed. Scope explicitly before designing.

Functional Requirements (in-scope)

  • Photo & video upload: Users upload photos (up to 20MB) and short videos (up to 60 seconds). The system stores originals and asynchronously produces 5 resized variants.
  • Home Feed: Chronological-then-algorithmic ranked feed of posts from followed accounts. Pre-load next 20 posts on scroll.
  • Stories: 24-hour ephemeral content; viewers can see who watched; auto-advance slideshow.
  • Like, comment, save: Like counts visible; comments threaded; saved posts private collection.
  • Follow / unfollow: Public accounts followable immediately; private accounts require approval.
  • Explore tab: Personalized grid of posts from non-followed accounts; powered by ML ranking.
  • Search: User and hashtag search (out of deep-dive scope — treat as full-text search on Elasticsearch).
  • Notifications: Push notifications (APNs / FCM) for likes, comments, follows, mentions.

Non-Functional Requirements

  • Scale: 2B MAU, 500M DAU, 100M photos/day uploaded, 1B Stories/day, 10B feed views/day
  • Feed load latency: p99 < 500ms; p50 < 150ms
  • Image render from CDN: < 50ms at edge; < 200ms globally
  • Upload acknowledgment: Client receives 201 within 2 seconds; processing continues async
  • Availability: 99.99% for feed reads (revenue-critical); 99.9% for uploads
  • Consistency: Eventual consistency acceptable for feed (a follower seeing a post 2s late is fine); strong consistency for follow/unfollow (bidirectional must complete atomically)
  • Storage durability: Photos must never be lost (11 nines via S3)
  • Compliance: GDPR — deleted photos must be purged from all storage tiers within 30 days

Explicitly Out of Scope

  • Direct messaging (separate DM service)
  • Live streaming (RTMP ingestion pipeline)
  • Reels / long-form video (requires HLS/DASH transcoding — see YouTube design)
  • Ads ranking system

🔢 E — Estimation 3–5 min

Storage

  • Photo uploads: 100M photos/day × 5 variants × avg 200KB/variant = 100TB/day new photo storage
  • Stories: 1B stories/day × 1 variant (Stories are lower resolution) × 300KB avg = 300TB/day, but expire after 24h → rolling ~300TB hot storage
  • Original photos: 100M × 5MB avg original = 500TB/day (archived to S3 Glacier after 30 days)
  • Annual total (processed variants + metadata): ~40PB/year cumulative

Traffic

  • Feed views: 10B/day ÷ 86,400s = ~115K read QPS
  • Photo uploads: 100M/day ÷ 86,400s = ~1,160 write QPS → read:write ≈ 100:1
  • Feed fanout: 1,160 posts/sec × 500 avg followers = 580K Redis feed writes/sec
  • CDN bandwidth: 115K feed-item views/sec × 200KB avg image = ~23 GB/s CDN egress
  • Like events: 4.2B likes/day ÷ 86,400 = ~49K write QPS (Cassandra counter writes)

Celebrity Fanout Problem — The Numbers

  • Kylie Jenner: 380M followers. One post triggers 380M Redis writes in fanout-on-write.
  • At 100K Redis writes/sec sustained, that would take 63 minutes to complete — unacceptable.
  • Conclusion: accounts above a follower threshold (~1M) must be excluded from fanout-on-write.
L6 insight: The 100:1 read-write ratio means every optimization for feed reads (caching, CDN, pre-computation) has 100× the impact of write optimizations. Always optimize the hot path first.

-- Comments (threaded)
CREATE TABLE comments (
    post_id        BIGINT,
    comment_id     BIGINT,                     -- Snowflake ID
    parent_id      BIGINT,                     -- null for top-level
    user_id        BIGINT,

    created_at     TIMESTAMP,

Why Cassandra for follows and posts, not PostgreSQL? Follow-graph reads are fan-out reads: "give me all followers of user X" — this can be millions of rows. PostgreSQL handles this poorly beyond millions of rows without sharding. Cassandra's wide-partition model (all followers of X in one partition) makes this a single-node range scan. The trade-off: no JOINs, eventual consistency for counts.

🏗️ H — High-level Design 10 min

System Components

  • API Gateway: Auth (JWT), rate limiting, routing. Terminates TLS.
  • Upload Service: Generates S3 pre-signed URLs, records metadata, publishes to Kafka photo-uploads topic.
  • Photo Processor Workers: Kafka consumers. Resize to 5 variants, write to S3, update post status to READY, publish to post-ready topic.
  • Fanout Service: Consumes post-ready. For normal users (<1M followers): writes post_id to each follower's Redis feed sorted set (fanout-on-write). For celebrities: skips fanout — feed assembly handles it on read.
  • Feed Service: Reads from Redis feed cache. For accounts followed by the user that are celebrities, merges their latest posts on the fly. Returns list of post_ids for the client to hydrate.
  • Post Metadata Service: Takes a list of post_ids, fetches metadata + CDN URLs in parallel from Cassandra. Batches reads with a 10ms timeout.
  • CDN (CloudFront / Fastly): Serves all photo variants. Origin is S3. TTL = 1 year (immutable content). URL format: cdn.example.com/{post_id}/{variant}.jpg
  • Stories Service: Separate service managing TTL in Redis, fanout to followers' story tray, viewer tracking.
  • Explore Service: ML-based candidate generation + ranking. Reads from ANN index of content embeddings.
  • Notification Service: Consumes like/comment/follow events from Kafka, routes to APNs (iOS) or FCM (Android).

Photo Upload Flow (Step by Step)

  1. Client calls POST /v1/posts/upload-url → Upload Service generates S3 pre-signed PUT URL (15-minute TTL), returns {uploadUrl, postId}
  2. Client uploads binary directly to S3 via pre-signed URL — Upload Service never sees the bytes
  3. S3 emits ObjectCreated event → Upload Service Kafka producer publishes {postId, userId, s3Key} to photo-uploads topic
  4. Photo Processor Worker consumes event, downloads original, generates 5 variants, uploads each variant, updates post status = READY in Cassandra
  5. Processor publishes {postId, userId} to post-ready topic
  6. Fanout Service consumes post-ready, queries follower list, writes to Redis feed sorted sets

Feed Read Flow (Step by Step)

  1. Client calls GET /v1/feed?cursor={lastPostId}&limit=20
  2. Feed Service reads from feed:{userId} Redis sorted set: ZREVRANGEBYSCORE ... LIMIT 0 20
  3. Feed Service identifies if the user follows any celebrities. If yes, fetches those celebrities' latest 20 posts from Cassandra (fanout-on-read for celebrities only)
  4. Merge + rank the two lists (chronological or ML score)
  5. Pass list of post_ids to Post Metadata Service → bulk fetch metadata from Cassandra
  6. Return enriched feed JSON to client (metadata + CDN URLs per variant)

Fanout Architecture SVG Diagram

L6 insight — Hybrid Fanout: Instagram uses a hybrid fanout. For users with fewer than ~10K followers, fanout-on-write pre-populates all followers' feed caches immediately on post creation. For celebrities with more than ~1M followers, the feed is assembled on-read by merging the user's pre-built feed cache with the celebrity's latest posts fetched directly from Cassandra. The threshold is configurable — a background job monitors follower counts and updates the is_celebrity flag.

🔬 D — Deep Dive 15 min

1. Photo Upload Pipeline — Client → S3 → Kafka → Processor → CDN

Raw uploads from phones are 5–20MB HEIC/JPEG files. Processing them synchronously would block upload ACKs for 2–10 seconds. The pipeline is fully asynchronous after the S3 write.

Five Resized Variants

VariantDimensionsUse CaseApprox Size
thumbnail150×150 px (square crop)Profile grid, explore grid, comments~8KB
low320px wide, proportionalLow-bandwidth 3G preview~30KB
medium640px wide, proportionalDefault mobile feed~80KB
high1080px wide, proportionalFull-res feed view, web~200KB
originalAs uploaded (up to 4K)Download, archival, future re-processing~5MB avg

The original variant is stored in a separate S3 bucket with cold-tier storage (Glacier after 30 days). CDN only distributes the four processed variants. The original is never served directly from CDN — it's for archival and potential future re-processing if Instagram adds new sizes.

CDN URL Generation

CDN URLs are deterministic and immutable: https://cdn.ig.com/{postId}/{variant}.jpg. Because photos are immutable once processed, CDN TTL is set to 1 year (Cache-Control: max-age=31536000, immutable). Cache invalidation is never needed — if a post is deleted, the app server stops returning the URL; the CDN key becomes unreachable without explicit invalidation.

For private account content, URLs include a short-lived HMAC signature parameter: ?sig={hmac}&exp={timestamp}. The CDN validates the signature at edge before serving, without hitting origin.

Photo Deduplication via Perceptual Hash (pHash)

Users (and spam bots) frequently re-upload the same photo. Instagram uses perceptual hashing to detect near-duplicate images at upload time.

// Perceptual hash algorithm (simplified):
// 1. Resize image to 32×32 pixels (removes noise)
// 2. Convert to grayscale
// 3. Compute DCT (Discrete Cosine Transform) — keeps low-frequency features
// 4. Take top-left 8×8 of DCT result (64 values)
// 5. Compute mean of 64 values
// 6. Build 64-bit hash: bit[i] = (dct[i] > mean) ? 1 : 0
//
// Two images are near-duplicates if Hamming distance between their pHashes < 10
//
// Storage: pHash stored in post metadata (8 bytes)
// Lookup: Redis HSET dedup:{phash} postId  (for fast collision check at upload time)
// On upload: compute pHash, check Redis, if match found → surface warning to user
Why pHash and not MD5/SHA? Cryptographic hashes (MD5, SHA-256) change completely if even one pixel is different. pHash produces similar hash values for visually similar images — a cropped version, a compressed version, and a screenshot of the same photo will all have pHash Hamming distances under 10. This catches spam reposts that are slightly cropped or have minimal edits.

2. Feed Generation — Fanout-on-Write vs Fanout-on-Read vs Hybrid

Fanout-on-Write (Push)

When a post is created, the Fanout Service iterates through all of the poster's followers and writes the post_id into each follower's Redis feed sorted set immediately. Feed reads are O(1) — just a Redis ZRANGE.

  • Pro: Feed reads are instant — no computation at read time
  • Pro: Simple read path
  • Con: Write amplification — 500 followers = 500 Redis writes per post
  • Con: Celebrity problem — Kylie Jenner with 380M followers would trigger 380M Redis writes per post, taking ~63 minutes at 100K writes/sec
  • Con: Wasted writes — feeds for inactive users (who haven't opened the app in months) still get populated

Fanout-on-Read (Pull)

When a user opens their feed, the Feed Service queries: "give me the IDs of everyone I follow", then for each followed user, fetches their latest posts. Merge and sort all results.

  • Pro: No write amplification — posting is cheap regardless of follower count
  • Pro: Feed is always up-to-date (no stale cache)
  • Con: Feed read is expensive — a user following 500 accounts requires 500 Cassandra queries per feed load, each with its own latency
  • Con: At 115K feed reads/sec, 500 queries each = 57.5M DB queries/sec — impossible

Hybrid Approach (What Instagram Actually Uses)

// Hybrid strategy thresholds (configurable in feature flags):
// FANOUT_WRITE_THRESHOLD = 1_000_000  // users above this → fanout-on-read
// ACTIVE_USER_DAYS = 30               // inactive users → skip fanout-on-write

// Fanout Service decision logic (pseudocode):
void handlePostReady(PostReadyEvent event) {
    List<Long> followerIds = followerService.getFollowers(event.getUserId());

    for (Long followerId : followerIds) {
        UserProfile follower = userCache.get(followerId);

        // Skip inactive users — don't waste Redis writes for users who won't open the app
        if (follower.getLastActiveAt().isBefore(now().minusDays(ACTIVE_USER_DAYS))) {
            continue;
        }

        feedCacheService.addToFeed(followerId, event.getPostId(), event.getCreatedAt());
    }
}

// Feed Service read path:
FeedResponse getFeed(Long userId, Long cursor, int limit) {
    List<Long> feedPostIds = redisClient.zrevrangebyscore("feed:" + userId, cursor, limit);

    // Identify celebrities the user follows
    List<Long> followedCelebIds = followingCache.getCelebrities(userId);

    if (!followedCelebIds.isEmpty()) {
        // Pull celebrity posts on-read and merge
        List<Post> celebPosts = cassandra.getLatestPostsFromUsers(followedCelebIds, limit);
        feedPostIds = mergeAndDeduplicate(feedPostIds, celebPosts, cursor, limit);
    }

    return postMetadataService.hydrate(feedPostIds);
}

3. Feed Ranking — Chronological vs Algorithmic

Early Instagram showed posts in reverse-chronological order. By 2016, they switched to algorithmic ranking because the average user missed 70% of their feed due to volume. Algorithmic ranking surfaces the posts the user is most likely to engage with.

Ranking Signal Categories

Signal CategoryExamplesWeight
Interest / Engagement HistoryPast likes, saves, comments on similar content; time spent on similar postsHigh
Relationship StrengthDM frequency, mutual follows, profile visits, tagsHigh
Post RecencyMinutes since post was created (decay function)Medium
Content TypePhoto vs video; carousel; aspect ratio preferenceMedium
Post PopularityLike velocity in first 30 minutes; comment rateMedium
Device / ContextMobile vs tablet; time of day; network speedLow

Ranking Pipeline Architecture

// Two-stage ranking pipeline:
//
// STAGE 1 — Candidate Generation (retrieve ~500 candidates from feed cache)
//   Input:  Redis feed sorted set (chronological post_ids)
//   Output: Top 500 candidates by recency
//
// STAGE 2 — ML Ranking (score all 500 candidates, return top 20)
//   Model: Gradient Boosted Trees (offline training) or two-tower neural net
//   Features computed per (user, post) pair:
//     - user_embedding vector (128-dim) from historical engagement
//     - post_embedding vector (128-dim) from content features
//     - dot_product(user_embedding, post_embedding) → affinity score
//     - recency_score: 1 / (1 + hours_since_post)
//     - relationship_score: from graph features (shared follows, DMs)
//     - post_velocity: likes_per_hour in past 30 min
//
// STAGE 3 — Re-ranking (diversity + freshness rules)
//   - No more than 3 consecutive posts from same user
//   - At least 1 post from last 6 hours in top 5
//   - Inject sponsored content at positions 3, 8, 13

// Online serving: <20ms inference budget for scoring 500 posts
// Achieved via: pre-computed user embeddings (updated every 1h),
//               post embeddings pre-computed at upload time,
//               fast dot product via BLAS

5. Explore Tab — Graph-Based Recommendation + ANN Search

Explore surfaces posts from accounts the user does not follow. It's a three-stage recommendation pipeline: candidate generation → scoring → diversity re-ranking.

Candidate Generation Strategies

  • Co-follow graph: "Users who follow the same accounts as you also engaged with these posts" — classic collaborative filtering on the social graph
  • Content similarity (embedding ANN): Each post has a 128-dimensional embedding vector computed at upload time (from image features via CNN + caption features via BERT). At query time, find the top-K nearest posts to the user's interest vector using FAISS (Facebook AI Similarity Search). FAISS enables sub-millisecond ANN search over billions of vectors.
  • Trending in your network: Posts with high like velocity from accounts in your 2-hop social graph
  • Hashtag affinity: Hashtags you've engaged with in the past → posts tagged with those hashtags
// Content embedding pipeline:
// At upload time (Photo Processor Worker also does):
//   1. Run image through MobileNet CNN → 128-dim visual embedding
//   2. Run caption through DistilBERT → 128-dim text embedding
//   3. Concatenate + project to single 128-dim post embedding
//   4. Insert into FAISS index (approximate nearest neighbor)
//   5. Store embedding in Cassandra post_embeddings table

// User interest vector (updated every 1 hour by batch job):
//   Weighted average of embeddings of posts user engaged with in past 30 days
//   Recency-weighted: engagement from yesterday has 2× weight vs 30 days ago

// ANN query at Explore request time:
//   1. Fetch user embedding vector
//   2. FAISS.search(user_vector, k=200) → 200 candidate post_ids
//   3. Filter out: already seen, from followed accounts, deleted, reported
//   4. Score remaining with ML ranker (same ranker as feed but different feature weights)
//   5. Apply diversity: max 3 posts from same author, distribute across categories
//   6. Return top 50 for explore grid

7. Follow Graph — Adjacency List in Cassandra

The follow relationship is uni-directional (A follows B ≠ B follows A, unlike Facebook's bidirectional friendship). At scale, the graph has billions of edges.

// Why Cassandra over a dedicated graph DB (Neo4j/JanusGraph)?
// Instagram's graph queries are simple:
//   - "Who follows user X?" → single partition scan in followers_of table
//   - "Who does user X follow?" → single partition scan in following_of table
//
// These are O(1) partition reads in Cassandra. Graph DBs are optimized for
// multi-hop traversals (find friends-of-friends-of-friends) — unnecessary here.
// Graph DBs at Instagram's scale (100B+ edges) are operationally complex.
//
// Cassandra approach:
// - followers_of partitioned by followee_id → "give me all followers of user X"
//   for fanout is a single partition scan
// - following_of partitioned by follower_id → "who does user X follow"
//   for feed assembly is a single partition scan
//
// Write path (follow action):
// BEGIN BATCH
//   INSERT INTO followers_of (followee_id, follower_id, created_at) VALUES (...)
//   INSERT INTO following_of (follower_id, followee_id, created_at) VALUES (...)
// APPLY BATCH;
// Note: Cassandra batches are NOT transactions — they're hints for locality.
// For true atomicity, use application-level retry with idempotency check.

// Follower count:
// Counter column in users table (denormalized)
// Increment via: UPDATE users SET follower_count = follower_count + 1 WHERE user_id = ?
// Periodic reconciliation job checks for drift between counter and actual row count

✅ E — Evaluate 3–5 min

Does the Design Meet Each Requirement?

Feed load p99 < 500ms

Feed Service reads Redis (sub-millisecond). For celebrity merges: Cassandra read for latest 20 posts per celebrity, typically 3–5 celebrities followed = 3–5 parallel Cassandra reads (~5ms each). Total feed assembly: ~20ms. ML ranking over 500 candidates: ~15ms (pre-computed embeddings, fast dot product). Total p99 well under 500ms. ✓

The Celebrity Problem

Resolved by the hybrid strategy: Kylie Jenner (380M followers) is flagged as is_celebrity=true. When she posts, Fanout Service skips write fanout. At feed read time, Feed Service fetches her latest posts from Cassandra and merges them. Cost per user's feed read: one extra Cassandra partition read per celebrity followed, merged in memory. ✓

Inactive Users — Wasted Fanout

Fanout Service skips users who haven't been active in 30+ days. When these users return, Feed Service detects the stale/empty Redis cache and triggers a backfill (pull latest posts from all followed accounts, populate Redis). This lazy re-hydration is acceptable since it happens once on re-engagement, not on every post by everyone they follow. ✓

Photo Availability 99.99%

S3 provides 99.999999999% durability. CDN provides geographic redundancy. CDN failures fall back to S3 origin (with higher latency). Multi-region CDN PoPs ensure availability even if one region goes down. ✓

Stories Expiry

Redis TTL provides automatic expiry of story metadata. S3 bucket lifecycle policy deletes media objects after 48 hours. Two mechanisms ensure no story survives past its TTL. ✓

GDPR — Photo Deletion

Delete flow: mark post as DELETED in Cassandra (soft delete, instant). Schedule hard delete job: remove S3 keys for all 5 variants, purge from CDN (explicit invalidation via CloudFront API), remove from all Redis feed caches (ZREM), remove from FAISS index. Entire pipeline must complete within 30 days. ✓

Potential Bottlenecks

  • Fanout Service throughput: At 1,160 posts/sec × 500 avg followers = 580K Redis writes/sec. Redis cluster handles ~500K writes/sec per shard. Solution: horizontal sharding of Redis feed caches by user_id range, or use Redis Cluster with consistent hashing.
  • Photo Processor throughput: 1,160 uploads/sec × 4 resize operations each = 4,640 CPU-intensive operations/sec. Solution: dedicated auto-scaling group of processor workers; Kafka provides backpressure and replay on failure.
  • Cassandra follower list scans for celebrities: A user with 380M followers has a partition of 380M rows. LIMIT 1000 for the fanout is still a large scan. Solution: since celebrity posts skip write fanout, we never need to scan the full follower list — the celebrity bypass path only needs the user's is_celebrity flag, not their follower list.

🚀 D — Deliver 2 min

We designed a photo-sharing platform for 2B MAU handling 100M photo uploads/day, 1B Stories/day, and 10B feed reads/day. The five critical architectural decisions:

  1. Pre-signed S3 uploads: Client uploads directly to S3, bypassing app servers entirely. Upload Service only handles metadata. Eliminates app server as upload bandwidth bottleneck.
  2. Async image processing pipeline: Kafka-driven Photo Processor Workers produce 5 variants per photo. Upload API returns 201 in <2s. Processing completes within 5–30s. Kafka provides durability, backpressure, and replay.
  3. Hybrid fanout strategy: Fanout-on-write for normal users (<1M followers), fanout-on-read for celebrities. Feed reads merge Redis pre-built feed + celebrity latest posts at query time. Eliminates 380M-write celebrity problem while keeping feed reads fast.
  4. Stories-as-ephemeral in Redis: Stories are fundamentally different from posts (24h TTL, lighter access pattern). Redis sorted sets with TTL scores, S3 lifecycle rules, and separate fanout path. No Cassandra overhead for ephemeral content.
  5. ML ranking pipeline: Two-stage (candidate retrieval from Redis + ML scoring). Pre-computed user and post embeddings keep online inference under 20ms. FAISS-based ANN search powers Explore with sub-millisecond candidate retrieval over billions of posts.

PhotoUploadService — Pre-signed URL generation + Kafka publish

/**
 * @file PhotoUploadService.java
 * @description Handles phase-1 of photo upload: generates pre-signed S3 PUT URL,
 *              persists post metadata, and publishes upload event to Kafka.
 *
 * @requires S3Presigner (AWS SDK v2), KafkaProducer, CassandraSession
 *
 * Public API:
 *   initiateUpload(userId, caption, location) — returns UploadInitiateResponse
 *   confirmUpload(postId, s3Key)              — marks upload complete, triggers processing
 */
public class PhotoUploadService {

    private static final String ORIGINALS_BUCKET  = "ig-photo-originals";
    private static final String PHOTO_UPLOADS_TOPIC = "photo-uploads";
    private static final Duration PRESIGNED_URL_TTL = Duration.ofMinutes(15);

    private final S3Presigner    s3Presigner;
    private final KafkaProducer<String, PhotoUploadEvent> kafkaProducer;
    private final PostRepository postRepository;
    private final SnowflakeIdGenerator idGenerator;

    public PhotoUploadService(S3Presigner s3Presigner,
                              KafkaProducer<String, PhotoUploadEvent> kafkaProducer,
                              PostRepository postRepository,
                              SnowflakeIdGenerator idGenerator) {
        this.s3Presigner    = s3Presigner;
        this.kafkaProducer  = kafkaProducer;
        this.postRepository = postRepository;
        this.idGenerator    = idGenerator;
    }

    /**
     * Phase 1: Generate a pre-signed S3 URL so the client can upload directly.
     * The app server never handles the binary — only this signed token.
     *
     * @param userId   authenticated user's ID
     * @param caption  post caption (stored now; post visible after Phase 2)
     * @param location optional location string
     * @return UploadInitiateResponse containing postId and the S3 upload URL
     */
    public UploadInitiateResponse initiateUpload(long userId, String caption, String location) {
        long postId   = idGenerator.nextId();
        String s3Key  = buildOriginalS3Key(userId, postId);
        String uploadUrl = generatePresignedPutUrl(s3Key);

        postRepository.createPost(new PostDraft(postId, userId, caption, location, s3Key));

        return new UploadInitiateResponse(postId, uploadUrl, Instant.now().plus(PRESIGNED_URL_TTL));
    }

    /**
     * Phase 2: Client has finished uploading to S3 and calls to confirm.
     * Publishes to Kafka to trigger async image processing pipeline.
     *
     * @param postId confirmed post ID from Phase 1
     * @param s3Key  the key the client uploaded to (for verification)
     */
    public void confirmUpload(long postId, String s3Key) {
        postRepository.updateStatus(postId, PostStatus.PROCESSING);

        PhotoUploadEvent uploadEvent = new PhotoUploadEvent(postId, s3Key, Instant.now());
        ProducerRecord<String, PhotoUploadEvent> record =
            new ProducerRecord<>(PHOTO_UPLOADS_TOPIC, String.valueOf(postId), uploadEvent);

        kafkaProducer.send(record, (metadata, exception) -> {
            if (exception != null) {
                // Kafka publish failure: post stays in PROCESSING state.
                // A reconciliation job retries posts stuck in PROCESSING for >5 min.
                System.err.println("[PhotoUploadService.confirmUpload] Kafka publish failed "
                    + "for postId=" + postId + ": " + exception.getMessage());
            }
        });
    }

    private String generatePresignedPutUrl(String s3Key) {
        PutObjectPresignRequest presignRequest = PutObjectPresignRequest.builder()
            .signatureDuration(PRESIGNED_URL_TTL)
            .putObjectRequest(builder -> builder
                .bucket(ORIGINALS_BUCKET)
                .key(s3Key)
                .contentType("image/jpeg")
                .build())
            .build();
        return s3Presigner.presignPutObject(presignRequest).url().toString();
    }

    private String buildOriginalS3Key(long userId, long postId) {
        // originals/{userId}/{postId}.jpg
        return "originals/" + userId + "/" + postId + ".jpg";
    }

    public record UploadInitiateResponse(long postId, String uploadUrl, Instant expiresAt) {}
}

PhotoProcessorWorker — Kafka consumer, 5-variant resize, CDN URL generation

/**
 * @file PhotoProcessorWorker.java
 * @description Kafka consumer that processes uploaded photos.
 *              Downloads original from S3, resizes to 5 variants using BufferedImage,
 *              uploads variants back to S3, and emits post-ready event.
 *
 * @requires KafkaConsumer, S3Client, BufferedImage (javax.imageio)
 *
 * Public API:
 *   run() — blocking Kafka poll loop; call from worker thread
 */
public class PhotoProcessorWorker {

    // ── Constants ────────────────────────────────────────────────────────
    private static final String ORIGINALS_BUCKET  = "ig-photo-originals";
    private static final String PROCESSED_BUCKET  = "ig-photo-processed";
    private static final String POST_READY_TOPIC  = "post-ready";
    private static final String PHOTO_UPLOADS_TOPIC = "photo-uploads";
    private static final long   POLL_TIMEOUT_MS   = 1_000;
    private static final float  JPEG_QUALITY      = 0.85f;  // 85% quality — good balance vs size

    // Five variants: name, targetWidth, squareCrop
    private static final List<PhotoVariant> VARIANTS = List.of(
        new PhotoVariant("thumbnail", 150,  true),   // square crop for grids
        new PhotoVariant("low",       320,  false),  // 3G / data-saver preview
        new PhotoVariant("medium",    640,  false),  // default mobile feed
        new PhotoVariant("high",      1080, false),  // full-res mobile / web
        new PhotoVariant("original",  -1,   false)   // archived as-is (no resize)
    );

    // ── Dependencies ─────────────────────────────────────────────────────
    private final KafkaConsumer<String, PhotoUploadEvent>   kafkaConsumer;
    private final KafkaProducer<String, PostReadyEvent>     kafkaProducer;
    private final S3Client                                   s3Client;
    private final PostRepository                             postRepository;
    private final PostMediaRepository                        mediaRepository;
    private volatile boolean                                 running = true;

    public PhotoProcessorWorker(KafkaConsumer<String, PhotoUploadEvent> kafkaConsumer,
                                KafkaProducer<String, PostReadyEvent> kafkaProducer,
                                S3Client s3Client,
                                PostRepository postRepository,
                                PostMediaRepository mediaRepository) {
        this.kafkaConsumer  = kafkaConsumer;
        this.kafkaProducer  = kafkaProducer;
        this.s3Client       = s3Client;
        this.postRepository = postRepository;
        this.mediaRepository = mediaRepository;
    }

    /** Blocking poll loop. Run on a dedicated thread. */
    public void run() {
        kafkaConsumer.subscribe(List.of(PHOTO_UPLOADS_TOPIC));
        while (running) {
            ConsumerRecords<String, PhotoUploadEvent> records =
                kafkaConsumer.poll(Duration.ofMillis(POLL_TIMEOUT_MS));

            for (ConsumerRecord<String, PhotoUploadEvent> record : records) {
                processUploadEvent(record.value());
            }
            kafkaConsumer.commitSync();
        }
    }

    /**
     * Processes a single photo upload event.
     * Downloads original, generates all variants, updates DB, publishes post-ready.
     *
     * @param event the upload event from Kafka
     */
    private void processUploadEvent(PhotoUploadEvent event) {
        try {
            byte[] originalBytes   = downloadFromS3(ORIGINALS_BUCKET, event.getS3Key());
            BufferedImage original = decodeImage(originalBytes);

            List<MediaVariantRecord> variantRecords = new ArrayList<>();

            for (PhotoVariant variant : VARIANTS) {
                byte[] variantBytes = generateVariant(original, variant, originalBytes);
                String variantKey   = buildVariantKey(event.getPostId(), variant.name());
                uploadToS3(PROCESSED_BUCKET, variantKey, variantBytes);

                String cdnUrl = buildCdnUrl(event.getPostId(), variant.name());
                variantRecords.add(new MediaVariantRecord(
                    event.getPostId(), variant.name(), variantKey, cdnUrl,
                    getVariantWidth(original, variant), getVariantHeight(original, variant),
                    variantBytes.length
                ));
            }

            mediaRepository.saveAll(variantRecords);
            postRepository.updateStatus(event.getPostId(), PostStatus.READY);
            publishPostReadyEvent(event.getPostId(), event.getUserId());

        } catch (IOException processingError) {
            System.err.println("[PhotoProcessorWorker.processUploadEvent] Failed for postId="
                + event.getPostId() + ": " + processingError.getMessage());
            postRepository.updateStatus(event.getPostId(), PostStatus.FAILED);
        }
    }

    /**
     * Generates a single variant. For "original", returns the raw bytes unchanged.
     * For all others, resizes using BilinearInterpolation (quality/speed balance).
     *
     * @param original    decoded source image
     * @param variant     variant specification (name, width, squareCrop flag)
     * @param rawBytes    original raw bytes (returned unchanged for "original" variant)
     * @return JPEG-encoded bytes for the variant
     */
    private byte[] generateVariant(BufferedImage original, PhotoVariant variant,
                                   byte[] rawBytes) throws IOException {
        if (variant.name().equals("original")) {
            return rawBytes;  // store original as-is, no re-encoding
        }

        int targetWidth  = variant.targetWidth();
        int targetHeight = variant.squareCrop()
            ? targetWidth
            : (int) ((double) original.getHeight() / original.getWidth() * targetWidth);

        BufferedImage resizedImage = new BufferedImage(
            targetWidth, targetHeight, BufferedImage.TYPE_INT_RGB
        );
        Graphics2D graphics = resizedImage.createGraphics();
        graphics.setRenderingHint(RenderingHints.KEY_INTERPOLATION,
                                  RenderingHints.VALUE_INTERPOLATION_BILINEAR);
        graphics.setRenderingHint(RenderingHints.KEY_RENDERING,
                                  RenderingHints.VALUE_RENDER_QUALITY);

        if (variant.squareCrop()) {
            // Center-crop: take the middle square of the source before scaling
            int cropSize = Math.min(original.getWidth(), original.getHeight());
            int cropX    = (original.getWidth()  - cropSize) / 2;
            int cropY    = (original.getHeight() - cropSize) / 2;
            graphics.drawImage(original, 0, 0, targetWidth, targetHeight,
                               cropX, cropY, cropX + cropSize, cropY + cropSize, null);
        } else {
            graphics.drawImage(original, 0, 0, targetWidth, targetHeight, null);
        }
        graphics.dispose();

        return encodeAsJpeg(resizedImage, JPEG_QUALITY);
    }

    private byte[] encodeAsJpeg(BufferedImage image, float quality) throws IOException {
        ByteArrayOutputStream outputStream = new ByteArrayOutputStream();
        ImageWriter jpegWriter = ImageIO.getImageWritersByFormatName("jpeg").next();
        ImageWriteParam writeParam = jpegWriter.getDefaultWriteParam();
        writeParam.setCompressionMode(ImageWriteParam.MODE_EXPLICIT);
        writeParam.setCompressionQuality(quality);
        jpegWriter.setOutput(ImageIO.createImageOutputStream(outputStream));
        jpegWriter.write(null, new IIOImage(image, null, null), writeParam);
        jpegWriter.dispose();
        return outputStream.toByteArray();
    }

    /**
     * Generates CDN URL for a variant. Deterministic and immutable.
     * Format: https://cdn.ig.com/{postId}/{variant}.jpg
     *
     * For private account content, a signed URL would append ?sig=&exp= params.
     * Signature is HMAC-SHA256(secret, postId + variant + expiryEpoch).
     *
     * @param postId    Snowflake post ID
     * @param variantName thumbnail|low|medium|high|original
     * @return public CDN URL string
     */
    private String buildCdnUrl(long postId, String variantName) {
        return "https://cdn.ig.com/" + postId + "/" + variantName + ".jpg";
    }

    private String buildVariantKey(long postId, String variantName) {
        return "processed/" + postId + "/" + variantName + ".jpg";
    }

    private byte[] downloadFromS3(String bucket, String key) {
        return s3Client.getObjectAsBytes(
            builder -> builder.bucket(bucket).key(key)
        ).asByteArray();
    }

    private void uploadToS3(String bucket, String key, byte[] data) {
        s3Client.putObject(
            builder -> builder.bucket(bucket).key(key).contentType("image/jpeg"),
            RequestBody.fromBytes(data)
        );
    }

    private BufferedImage decodeImage(byte[] bytes) throws IOException {
        BufferedImage decoded = ImageIO.read(new ByteArrayInputStream(bytes));
        if (decoded == null) {
            throw new IOException("Could not decode image — unsupported format or corrupt data");
        }
        return decoded;
    }

    private void publishPostReadyEvent(long postId, long userId) {
        PostReadyEvent readyEvent = new PostReadyEvent(postId, userId, Instant.now());
        kafkaProducer.send(new ProducerRecord<>(POST_READY_TOPIC,
            String.valueOf(postId), readyEvent));
    }

    private int getVariantWidth(BufferedImage original, PhotoVariant variant) {
        return variant.name().equals("original") ? original.getWidth() : variant.targetWidth();
    }

    private int getVariantHeight(BufferedImage original, PhotoVariant variant) {
        if (variant.name().equals("original")) return original.getHeight();
        if (variant.squareCrop()) return variant.targetWidth();
        return (int) ((double) original.getHeight() / original.getWidth() * variant.targetWidth());
    }

    public void stop() { running = false; }

    /** Value record for a photo variant specification */
    private record PhotoVariant(String name, int targetWidth, boolean squareCrop) {}
}

FanoutService — Hybrid push/pull routing

/**
 * @file FanoutService.java
 * @description Consumes post-ready events and distributes posts to follower feed caches.
 *              Implements the hybrid fanout strategy: write-fanout for normal users,
 *              skip for celebrities (handled at read time by FeedService).
 *
 * @requires KafkaConsumer, FollowerRepository, FeedCacheRepository, UserRepository
 *
 * Public API:
 *   run() — blocking Kafka consumer loop
 */
public class FanoutService {

    // ── Constants ─────────────────────────────────────────────────────────
    private static final int  CELEBRITY_FOLLOWER_THRESHOLD = 1_000_000;
    private static final int  INACTIVE_USER_DAYS           = 30;
    private static final int  MAX_FEED_SIZE                = 300;   // trim Redis sorted set to this
    private static final int  FANOUT_BATCH_SIZE            = 1_000; // process followers in batches

    // ── Dependencies ─────────────────────────────────────────────────────
    private final KafkaConsumer<String, PostReadyEvent> kafkaConsumer;
    private final FollowerRepository                     followerRepository;
    private final FeedCacheRepository                    feedCacheRepository;
    private final UserRepository                         userRepository;

    public FanoutService(KafkaConsumer<String, PostReadyEvent> kafkaConsumer,
                         FollowerRepository followerRepository,
                         FeedCacheRepository feedCacheRepository,
                         UserRepository userRepository) {
        this.kafkaConsumer       = kafkaConsumer;
        this.followerRepository  = followerRepository;
        this.feedCacheRepository = feedCacheRepository;
        this.userRepository      = userRepository;
    }

    public void run() {
        kafkaConsumer.subscribe(List.of("post-ready"));
        while (true) {
            ConsumerRecords<String, PostReadyEvent> records =
                kafkaConsumer.poll(Duration.ofSeconds(1));
            for (ConsumerRecord<String, PostReadyEvent> record : records) {
                handlePostReadyEvent(record.value());
            }
            kafkaConsumer.commitSync();
        }
    }

    /**
     * Routes a new post through the appropriate fanout strategy.
     * Celebrity accounts bypass write-fanout entirely to avoid write amplification.
     *
     * @param event post-ready event from Kafka
     */
    private void handlePostReadyEvent(PostReadyEvent event) {
        UserProfile poster = userRepository.getById(event.getUserId());

        if (poster.isCelebrity()) {
            // Celebrity bypass: no write-fanout.
            // FeedService will fetch their latest posts at read time via Cassandra.
            return;
        }

        distributeToActiveFollowers(event.getPostId(), event.getUserId(),
                                    event.getCreatedAt().toEpochMilli());
    }

    /**
     * Iterates follower list in batches, skipping inactive users, and writes post_id
     * into each active follower's Redis feed sorted set.
     *
     * @param postId        the post to distribute
     * @param posterId      user who created the post
     * @param scoreEpochMs  Unix timestamp ms — used as sorted set score for ordering
     */
    private void distributeToActiveFollowers(long postId, long posterId, long scoreEpochMs) {
        String paginationCursor = null;
        Instant inactiveCutoff  = Instant.now().minus(INACTIVE_USER_DAYS, ChronoUnit.DAYS);

        do {
            FollowerPage followerPage =
                followerRepository.getFollowers(posterId, FANOUT_BATCH_SIZE, paginationCursor);

            for (long followerId : followerPage.followerIds()) {
                UserProfile follower = userRepository.getById(followerId);
                if (follower.getLastActiveAt().isBefore(inactiveCutoff)) {
                    continue;  // skip inactive users — save Redis writes
                }
                feedCacheRepository.addToFeed(followerId, postId, scoreEpochMs);
                feedCacheRepository.trimFeed(followerId, MAX_FEED_SIZE);
            }

            paginationCursor = followerPage.nextCursor();
        } while (paginationCursor != null);
    }
}

FeedCacheRepository — Redis sorted set operations

/**
 * @file FeedCacheRepository.java
 * @description Redis-backed feed cache using sorted sets.
 *              Score = post creation timestamp (epoch ms) for ordering.
 *
 * @requires Jedis or Lettuce Redis client
 *
 * Public API:
 *   addToFeed(userId, postId, scoreEpochMs) — add post to user's feed sorted set
 *   trimFeed(userId, maxSize)               — keep only the most recent N posts
 *   getFeedPage(userId, beforeScore, limit) — paginated feed read
 */
public class FeedCacheRepository {

    private static final String FEED_KEY_PREFIX = "feed:";
    private static final int    FEED_TTL_DAYS   = 7;

    private final JedisPool jedisPool;

    public FeedCacheRepository(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }

    /**
     * Adds a post to the user's feed sorted set.
     * Score is the post's creation timestamp in epoch milliseconds — ensures ordering.
     *
     * @param userId       recipient user
     * @param postId       Snowflake post ID to add
     * @param scoreEpochMs post creation time (used as sort score)
     */
    public void addToFeed(long userId, long postId, long scoreEpochMs) {
        String feedKey = FEED_KEY_PREFIX + userId;
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.zadd(feedKey, (double) scoreEpochMs, String.valueOf(postId));
            // Refresh TTL on every write so active users never have their cache expire
            jedis.expire(feedKey, (long) FEED_TTL_DAYS * 24 * 3600);
        }
    }

    /**
     * Trims the feed sorted set to maxSize entries, removing the oldest posts.
     * Prevents unbounded memory growth — a user following 1000 active accounts
     * would accumulate thousands of posts without this trim.
     *
     * @param userId  user whose feed to trim
     * @param maxSize maximum number of entries to retain
     */
    public void trimFeed(long userId, int maxSize) {
        String feedKey = FEED_KEY_PREFIX + userId;
        try (Jedis jedis = jedisPool.getResource()) {
            // ZREMRANGEBYRANK removes by rank (0 = lowest score = oldest)
            // Keeps elements from rank (-(maxSize)) to -1 (newest maxSize entries)
            long currentSize = jedis.zcard(feedKey);
            if (currentSize > maxSize) {
                jedis.zremrangeByRank(feedKey, 0, currentSize - maxSize - 1);
            }
        }
    }

    /**
     * Returns paginated post IDs for the user's feed, ordered newest-first.
     * Uses cursor-based pagination via score: "posts with score < beforeScore".
     *
     * @param userId       user requesting their feed
     * @param beforeScore  epoch ms cursor (posts older than this); Long.MAX_VALUE for first page
     * @param limit        number of posts to return (typically 20)
     * @return list of post IDs ordered newest-first
     */
    public List<Long> getFeedPage(long userId, long beforeScore, int limit) {
        String feedKey = FEED_KEY_PREFIX + userId;
        try (Jedis jedis = jedisPool.getResource()) {
            // ZREVRANGEBYSCORE: newest first, exclude the cursor score itself (< not <=)
            Set<String> postIdStrings = jedis.zrevrangeByScore(
                feedKey,
                "(" + beforeScore,  // exclusive upper bound
                "-inf",
                0, limit
            );
            return postIdStrings.stream()
                .map(Long::parseLong)
                .collect(Collectors.toList());
        }
    }
