Tier 2 — Should Know 45 min Correctness-critical

Design a Payment System (Stripe)

Payment systems have zero tolerance for money duplication or loss. Two cardinal rules: idempotency (charging a user twice is catastrophic) and double-entry bookkeeping (every debit has a corresponding credit). Stripe processes $800B/year = $25,000/second. Black Friday creates 10× spikes.

🏢 Stripe, PayPal, Amazon
⏱️ 45 min interview
💰 Zero money loss tolerance

❓R — Requirements3–5 min

Functional Requirements

  • Charge a payment method (credit/debit card, bank account)
  • Authorize and capture separately (authorize = reserve funds; capture = charge)
  • View transaction history and balance
  • Support refunds and chargebacks
  • Multi-currency support (USD, EUR, GBP, etc.)
  • Webhook delivery to merchants on payment status changes

Non-Functional Requirements

  • Correctness: No double charges, no money creation or loss — ACID transactions required
  • Idempotency: Retrying a failed payment request must not charge twice
  • Scale: $25K/second ($800B/year); 10× spikes on Black Friday = ~250K TPS peaks
  • Latency: Payment response <3s (includes PSP authorization round-trip)
  • Auditability: Every state change must be logged and traceable (PCI DSS, SOX compliance)
L6 signal — mention PCI DSS proactively: "We never store raw card numbers. Only the PSP token (last 4 digits + network token). PCI DSS compliance is why companies use Stripe/Braintree — they handle the cardholder data environment, not us. This reduces our PCI scope from SAQ D (hardest) to SAQ A (simplest)."

🔢E — Estimation3–5 min

  • Normal: 1M transactions/day = 12 TPS; Black Friday: 120 TPS peak (10× spike)
  • Each transaction = 2 ledger entries (debit + credit) → 2M ledger rows/day → 400MB/day → 150GB/year → PostgreSQL easily handles this
  • Idempotency keys: 1M/day with 24h TTL → at most 1M keys in Redis → ~100MB RAM
  • Reconciliation: 1M transactions × avg 200 bytes = 200MB/day to compare against PSP settlement files
  • Webhook delivery: 1M events/day × 3 delivery attempts avg = 3M HTTP calls/day = ~35 RPS

🗄️S — Schema3–5 min

// Double-entry ledger (PostgreSQL — ACID required)
// Every payment creates TWO rows: debit (negative) on payer, credit (positive) on payee
// SUM(amount) across all rows for an account = current balance
// SUM(amount) across ALL rows = 0 always (invariant — detects bugs immediately)
ledger_entries:
    entry_id     BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    account_id   UUID NOT NULL,
    amount       BIGINT NOT NULL,     -- integer cents! (100 = $1.00) — NEVER FLOAT
    currency     CHAR(3) NOT NULL,    -- ISO 4217 (USD, EUR, GBP)
    entry_type   ENUM(debit, credit),
    payment_id   UUID NOT NULL,       -- links both sides of a transaction
    created_at   TIMESTAMP NOT NULL DEFAULT NOW(),
    INDEX(account_id, created_at)     -- for efficient balance computation

// Payment state machine
payments:
    payment_id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    idempotency_key    VARCHAR(255) UNIQUE NOT NULL,
    payer_account_id   UUID NOT NULL,
    payee_account_id   UUID NOT NULL,
    amount             BIGINT NOT NULL,   -- integer cents
    currency           CHAR(3) NOT NULL,
    status             VARCHAR(20) NOT NULL DEFAULT 'INITIATED',
    -- INITIATED → PROCESSING → AUTHORIZED → CAPTURED → SETTLED
    -- Also: FAILED, REFUNDED, DISPUTED, REVERSED
    psp_charge_id      VARCHAR(255),      -- Stripe charge ID / PSP reference
    fraud_score        SMALLINT,          -- 0-100 from fraud ML model
    created_at         TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at         TIMESTAMP NOT NULL DEFAULT NOW()

// Outbox table (transactional outbox pattern)
payment_outbox:
    outbox_id    BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
    payment_id   UUID NOT NULL,
    event_type   VARCHAR(50) NOT NULL,  -- PSP_CHARGE, WEBHOOK_DELIVERY, etc.
    payload      JSONB NOT NULL,
    processed    BOOLEAN DEFAULT FALSE,
    created_at   TIMESTAMP NOT NULL DEFAULT NOW()

// Webhook subscriptions
webhook_endpoints:
    endpoint_id  UUID PRIMARY KEY,
    merchant_id  UUID NOT NULL,
    url          VARCHAR(500) NOT NULL,
    events       VARCHAR[],             -- ['payment.succeeded', 'payment.failed']
    secret_key   VARCHAR(255) NOT NULL  -- for HMAC signature validation

Money Representation — Why BIGINT, Not DECIMAL

// Store amounts as integer smallest-currency-units:
// USD: cents (100 = $1.00), EUR: cents (100 = €1.00)
// JPY: yen (100 = ¥100 — no cents in JPY)
// BHD: fils (1000 = 1 BHD — 3 decimal places)

// In Java: use a MoneyAmount value object
public record MoneyAmount(long amount, String currency) {

    public static MoneyAmount ofDollars(BigDecimal dollars) {
        // 1.99 dollars = 199 cents
        return new MoneyAmount(
            dollars.multiply(BigDecimal.valueOf(100))
                   .setScale(0, RoundingMode.HALF_EVEN)
                   .longValueExact(),
            "USD"
        );
    }

    public BigDecimal toDollars() {
        return BigDecimal.valueOf(amount).movePointLeft(2);
    }

    public MoneyAmount add(MoneyAmount other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException("Cannot add different currencies");
        }
        return new MoneyAmount(this.amount + other.amount, this.currency);
    }
}
// Integer arithmetic: no floating-point rounding errors.
// $0.10 + $0.20 = 30 cents (not 29.999... as with double)

🏗️H — High-level Design10 min

  • Payment API: Client sends payment request with Idempotency-Key header. API checks Redis idempotency cache before any processing.
  • Idempotency Layer (Redis): Key = idempotency-key. If exists: return cached response (no re-processing). If not: process + cache result with 24h TTL.
  • Fraud Detection (real-time ML): Before calling PSP, score the transaction (0–100). Block if >80. Flag for review if 60–80. Accept if <60. Sub-100ms latency requirement.
  • PSP Integration (Stripe/Braintree): Handles the actual card network interaction. We never see raw card numbers — only PSP tokens. PSP charges 2.9% + 30¢ per transaction. Authorization + Capture: two separate API calls.
  • Outbox Pattern (transactional outbox): DB write (payment record + outbox entry) in one ACID transaction. Separate outbox processor polls the table and makes PSP API calls. Guarantees at-least-once PSP call without two-phase commit.
  • Ledger Service (double-entry): Append-only. Balances = SUM(amount) for account. Cached in Redis; invalidated on new entry.
  • Webhook Service: Delivers payment status events to merchant-registered URLs. Retry with exponential backoff (1s, 5s, 30s, 5m, 30m, 2h, 8h, 24h — Stripe's actual schedule). Idempotent delivery via webhook_id.
  • Reconciliation Job: Nightly batch: compare internal ledger with PSP settlement files. Flag discrepancies for manual review.

Payment Lifecycle: Authorize vs Capture

// Two-step payment: Authorize + Capture
// Authorize: "reserve" funds on the card (hold, no actual charge yet)
//   → Card network responds: authorized or declined
//   → Funds "reserved" but customer still has them until capture
//
// Capture: actually move the money (can be done days later)
//   → Only charge what you actually need (can capture less than authorized)
//   → Hotel: authorize on check-in, capture on check-out (actual charges may differ)
//   → E-commerce: authorize at order, capture at shipment
//
// One-step (authorize + capture simultaneously):
//   → Used when amount is known and final (food delivery, immediate charges)

// Stripe API flow:
// Step 1: PaymentIntent.create(amount, currency, capture_method='manual')
//          → returns paymentIntentId, status='requires_capture'
// Step 2: PaymentIntent.confirm(paymentIntentId, payment_method=pm_xxx)
//          → PSP communicates with card network
//          → returns status='requires_capture' (authorized, not charged)
// Step 3: PaymentIntent.capture(paymentIntentId, amount_to_capture=actual_amount)
//          → Money moves to merchant account
//          → status='succeeded'

Idempotency — The Full Protocol

// Problem: network failure after PSP charges but before response arrives
// Client retries. Without idempotency: user charged twice.

// Full idempotency protocol:
// 1. Client generates UUID idempotency-key before first attempt
//    (generated ONCE per user intent, same on every retry)
// 2. Server: GET Redis idempotency:{key}
//    - HIT: return cached response (skip all processing)
//    - MISS: continue to processing
// 3. Acquire distributed lock on idempotency:{key}:lock (prevents concurrent duplicates)
// 4. Re-check Redis (another thread may have processed while waiting for lock)
// 5. Process payment (call PSP, write ledger, etc.)
// 6. SETEX idempotency:{key} 86400 {serialized_response} (24h TTL)
// 7. Release lock
// 8. Return response

// Edge case: server crashes between step 5 (PSP charge) and step 6 (Redis write)
// On restart: client retries with same key, no Redis hit
// → Server calls PSP AGAIN with same PSP idempotency key
// → PSP returns original response (PSP also implements idempotency)
// → Server caches in Redis and returns

// PSP idempotency: Stripe accepts an idempotency-key header
// If you send the same key within 24h, Stripe returns the original charge result
// This creates end-to-end idempotency: our key → Stripe's key → card network

3D Secure (3DS) — Strong Customer Authentication

// 3DS: extra authentication step for high-risk transactions
// EU PSD2 regulation requires 3DS for most online transactions
// Cardholder must authenticate with their bank (SMS OTP, banking app)

// Frictionless flow (low-risk transactions):
// Card issuer silently authenticates using transaction data (device fingerprint, amount)
// No user interaction required
// 95% of transactions in well-configured systems

// Challenge flow (high-risk transactions):
// PSP returns: status = "requires_action", redirect_url = "..."
// Client must redirect user to bank's authentication page
// After authentication: user redirected back to merchant site
// Merchant confirms: PaymentIntent.confirm() → PSP verifies 3DS with card network

// In our system:
// POST /v1/payments → fraud score check → PSP authorize call
// If PSP returns requires_action → return to client: { status: "ACTION_REQUIRED", redirectUrl }
// Client completes 3DS → POST /v1/payments/{paymentId}/confirm-3ds
// → PSP verifies 3DS token → capture payment

// Liability shift: if 3DS authentication happens, fraud liability shifts from merchant to issuing bank
// This is the primary business reason merchants implement 3DS

Fraud Detection — Real-time ML Scoring

// Fraud ML model: runs before every PSP call
// Must complete in <100ms to stay within 3s total payment latency budget
// Score: 0 (definitely legit) to 100 (definitely fraud)

// Features used:
// - IP geolocation: matches billing address country? (country mismatch = +20 score)
// - Device fingerprint: new device never seen before? (+ 15 score)
// - Transaction velocity: 5+ transactions in last 10 minutes? (+25 score)
// - Amount anomaly: 10× user's average transaction? (+20 score)
// - Time of day: 3am local time? (+10 score)
// - Email domain: newly created email? (+5 score)
// - Merchant category: crypto exchanges, gambling (+20 score baseline)

// Decision thresholds (configurable per merchant):
if (fraudScore > 80) {
    return PaymentResult.blocked("High fraud risk");  // automatic rejection
} else if (fraudScore > 60) {
    // 3DS challenge — force strong authentication
    return PaymentResult.requiresAction("3ds-challenge");
} else {
    // Proceed to PSP
    return proceedToPaymentProvider();
}

// False positive rate: ~0.5% of legitimate transactions incorrectly blocked
// At $25K/sec: 0.5% = $125/sec of legitimate revenue blocked → review queue for 60-80 zone

Webhook Reliability

// PSP sends webhook on every payment status change
// Must acknowledge (HTTP 200) within 30 seconds or PSP retries
// Webhooks CAN be delivered multiple times (network issues, PSP retries)
// → Our webhook handler MUST be idempotent

// Webhook idempotency:
// PSP includes unique webhook_id in every delivery
// Handler: INSERT INTO processed_webhooks (webhook_id) ON CONFLICT DO NOTHING
// If insert succeeds: process. If conflict (duplicate): skip.

// Webhook verification (HMAC signature):
// PSP sends: X-Stripe-Signature: t=timestamp,v1=hmac_sha256
// Verify: HMAC-SHA256(webhookSecret, timestamp + "." + body) == v1
// This prevents spoofed webhooks

// Merchant webhook delivery (our outgoing webhooks):
// We deliver payment events to merchant-registered URLs
// Retry schedule (Stripe's actual schedule):
// Attempt 1: immediately
// Attempt 2: 1 minute
// Attempt 3: 5 minutes
// Attempt 4: 30 minutes ... up to 8 attempts over 24 hours
// After 8 failures: mark endpoint disabled, notify merchant

Reconciliation

// Nightly reconciliation: compare internal records with PSP settlement file
// PSP provides daily settlement file (CSV/JSON): all charges, refunds, fees

@Scheduled(cron = "0 2 * * *")  // 2am daily, after PSP settlement cut-off
public void runDailyReconciliation() {
    LocalDate yesterday = LocalDate.now().minusDays(1);

    // Load internal transactions from DB
    List<PaymentRecord> internalRecords = paymentRepository.findByDate(yesterday);

    // Download PSP settlement file from S3 (PSP uploads automatically)
    List<PspSettlementRecord> pspRecords = pspSettlementLoader.load(yesterday);

    // Compare: for each internal record, find matching PSP record
    List<ReconciliationDiscrepancy> discrepancies = reconcile(internalRecords, pspRecords);

    // Categories of discrepancies:
    // MISSING_IN_PSP: internal record has no PSP match → possible double-spend in our system
    // MISSING_IN_INTERNAL: PSP has charge with no internal record → data loss or bug
    // AMOUNT_MISMATCH: amounts differ → currency conversion error or partial capture bug
    // STATUS_MISMATCH: internal=CAPTURED, PSP=FAILED → state machine bug

    if (!discrepancies.isEmpty()) {
        alertOncallEngineer(discrepancies);
        saveDiscrepanciesToDB(discrepancies);
    }
}

✅E — Evaluate3 min

  • Distributed transaction problem: Charging PSP + writing ledger are different systems. Outbox pattern: write payment record + outbox entry in one ACID transaction. Separate outbox processor polls table and calls PSP. On success: marks outbox row processed. At-least-once delivery guaranteed without 2PC.
  • Balance calculation cost: SUM of all ledger rows is O(N) — expensive for accounts with years of history. Mitigation: periodic balance snapshots. Store "balance as of midnight Jan 1 = X". Then SUM only since last snapshot. O(1) lookup + small incremental SUM.
  • Black Friday 10× spike (250K TPS): PSP is the bottleneck — Stripe's rate limits. Solution: auto-scale idempotency layer (Redis cluster), queued PSP calls with back-pressure, pre-warm DB connection pools. Fraud model: use cached scores for repeat customers during peak.
  • Currency conversion risk: FX rates change between authorization and settlement. Pre-authorize at current rate + 2% buffer. Settle at actual rate. Difference absorbed as FX risk or passed to customer (disclosed in T&C).

🚀D — Deliver2 min

We designed a payment system handling Stripe-scale: $800B/year with zero money duplication tolerance. Key decisions: Redis idempotency layer prevents double-charges on network retry; integer cents (never float) prevents rounding errors; Outbox pattern for atomic PSP + ledger writes; double-entry ledger with invariant SUM=0 catches bugs immediately; real-time fraud scoring (<100ms) blocks high-risk transactions; 3DS for strong customer authentication; and nightly reconciliation catches any PSP discrepancies.

⚖️Trade-offs

DecisionChosenAlternativeWhy Chosen
Idempotency storage Redis (TTL-based) DB UNIQUE constraint on idempotency_key Redis: fast O(1) lookup, automatic expiry via TTL, no cleanup job needed. DB unique constraint: also valid, slower (DB roundtrip on every payment), requires explicit cleanup of old keys. Use DB as fallback if Redis is down.
PSP call integration Outbox pattern (async) Synchronous 2PC 2PC with external systems (PSP) is unreliable — PSP doesn't support 2PC. Outbox stores intent atomically in our DB, separate processor executes it. At-least-once PSP call with idempotency handles duplicates. Simpler, more resilient.
Money representation BIGINT (integer cents) DECIMAL(19,4) or FLOAT Integer: exact arithmetic, no rounding errors, language-agnostic. DECIMAL: exact but slower arithmetic, more complex. FLOAT: binary representation causes errors ($0.10 + $0.20 ≠ $0.30 exactly). Never use FLOAT for money.
Balance computation SUM from append-only ledger (with snapshots) Mutable balance column Mutable balance: update contention under concurrent transactions, requires locking, harder to audit. Ledger: append-only (no contention on writes), full audit trail, correctness invariant (SUM=0 across all entries). Snapshots keep query cost O(1) for recent balance.
PSP integration Stripe/Braintree (PSP handles PCI scope) Direct card network integration Direct network: cheapest per-transaction cost (no PSP fee), but requires full PCI DSS Level 1 compliance (~$500K/year audit cost), dedicated security team. PSP: 2.9% + 30¢ fee, but PCI scope reduced to SAQ A — worth it until $1B+ volume.

☕Java Implementation

/**
 * @file IdempotentPaymentService.java
 * @description Processes payments with Redis-based idempotency.
 *              Guarantees a payment with a given idempotency-key executes at most once.
 *
 * Public API:
 *   processPayment(idempotencyKey, request) — idempotent payment execution
 */
public class IdempotentPaymentService {

    private static final String IDEMPOTENCY_KEY_PREFIX = "idempotency:payment:";
    private static final String LOCK_KEY_PREFIX = "lock:payment:";
    private static final int IDEMPOTENCY_TTL_SECONDS = 86_400; // 24 hours
    private static final int LOCK_TIMEOUT_SECONDS = 30;

    private final JedisPool jedisPool;
    private final PaymentProcessor paymentProcessor;
    private final FraudDetectionService fraudDetectionService;
    private final ObjectMapper objectMapper = new ObjectMapper();

    public IdempotentPaymentService(JedisPool jedisPool, PaymentProcessor paymentProcessor,
                                     FraudDetectionService fraudDetectionService) {
        this.jedisPool = jedisPool;
        this.paymentProcessor = paymentProcessor;
        this.fraudDetectionService = fraudDetectionService;
    }

    /**
     * Processes a payment idempotently.
     * Same idempotency-key on retry returns original result without re-processing.
     *
     * @param idempotencyKey  client-generated UUID, same on all retries for same intent
     * @param paymentRequest  amount (in cents), currency, paymentMethodId, etc.
     * @return PaymentResult — same object on retries as on original call
     */
    public PaymentResult processPayment(String idempotencyKey, PaymentRequest paymentRequest) {
        String cacheKey = IDEMPOTENCY_KEY_PREFIX + idempotencyKey;

        // Fast path: check cache without acquiring lock
        PaymentResult cachedResult = getFromCache(cacheKey);
        if (cachedResult != null) {
            return cachedResult;
        }

        // Slow path: acquire lock to prevent concurrent duplicate processing
        String lockKey = LOCK_KEY_PREFIX + idempotencyKey;
        if (!acquireDistributedLock(lockKey, LOCK_TIMEOUT_SECONDS)) {
            throw new PaymentConflictException("Concurrent payment with same idempotency key: " + idempotencyKey);
        }

        try {
            // Re-check after acquiring lock (another thread may have processed during our wait)
            cachedResult = getFromCache(cacheKey);
            if (cachedResult != null) {
                return cachedResult;
            }

            // Fraud check before calling PSP
            int fraudScore = fraudDetectionService.score(paymentRequest);
            if (fraudScore > 80) {
                PaymentResult blockedResult = PaymentResult.blocked(fraudScore);
                storeInCache(cacheKey, blockedResult);
                return blockedResult;
            }

            // Process payment through PSP
            PaymentResult paymentResult = paymentProcessor.execute(paymentRequest);

            // Cache result for idempotency (includes PSP reference, final status)
            storeInCache(cacheKey, paymentResult);
            return paymentResult;

        } finally {
            releaseDistributedLock(lockKey);
        }
    }

    // ── Cache Operations ──────────────────────────────────────────

    private PaymentResult getFromCache(String cacheKey) {
        try (Jedis jedis = jedisPool.getResource()) {
            String cachedJson = jedis.get(cacheKey);
            return cachedJson != null ? deserialize(cachedJson) : null;
        }
    }

    private void storeInCache(String cacheKey, PaymentResult result) {
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.setex(cacheKey, IDEMPOTENCY_TTL_SECONDS, serialize(result));
        }
    }

    // ── Distributed Lock (Redis SET NX EX) ───────────────────────

    private boolean acquireDistributedLock(String lockKey, int timeoutSeconds) {
        try (Jedis jedis = jedisPool.getResource()) {
            // SET NX EX is atomic: set only if not exists, with TTL
            String result = jedis.set(lockKey, "1",
                SetParams.setParams().nx().ex(timeoutSeconds));
            return "OK".equals(result);
        }
    }

    private void releaseDistributedLock(String lockKey) {
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.del(lockKey);
        }
    }

    // ── Serialization ─────────────────────────────────────────────

    private String serialize(PaymentResult result) {
        try {
            return objectMapper.writeValueAsString(result);
        } catch (JsonProcessingException jsonException) {
            throw new RuntimeException("[IdempotentPaymentService.serialize] failed", jsonException);
        }
    }

    private PaymentResult deserialize(String json) {
        try {
            return objectMapper.readValue(json, PaymentResult.class);
        } catch (JsonProcessingException jsonException) {
            throw new RuntimeException("[IdempotentPaymentService.deserialize] failed", jsonException);
        }
    }
}

// ── ReconciliationService ─────────────────────────────────────────

/**
 * @file ReconciliationService.java
 * @description Nightly batch job comparing internal ledger against PSP settlement file.
 *
 * Public API:
 *   runDailyReconciliation(date) — compares and flags discrepancies
 */
public class ReconciliationService {

    private final PaymentRepository paymentRepository;
    private final PspSettlementLoader pspSettlementLoader;
    private final AlertService alertService;

    @Scheduled(cron = "0 0 2 * * *") // 2am daily
    public void runDailyReconciliation() {
        LocalDate yesterday = LocalDate.now().minusDays(1);

        List<PaymentRecord> internalRecords = paymentRepository.findByDate(yesterday);
        List<PspSettlementRecord> pspRecords = pspSettlementLoader.loadFor(yesterday);

        Map<String, PspSettlementRecord> pspByChargeId = pspRecords.stream()
            .collect(Collectors.toMap(PspSettlementRecord::getChargeId, r -> r));

        List<ReconciliationDiscrepancy> discrepancies = new ArrayList<>();

        for (PaymentRecord internal : internalRecords) {
            PspSettlementRecord pspRecord = pspByChargeId.get(internal.getPspChargeId());

            if (pspRecord == null) {
                discrepancies.add(ReconciliationDiscrepancy.missingInPsp(internal));
            } else if (!internal.getAmountCents().equals(pspRecord.getAmountCents())) {
                discrepancies.add(ReconciliationDiscrepancy.amountMismatch(internal, pspRecord));
            } else if (!internal.getStatus().equals(pspRecord.getStatus())) {
                discrepancies.add(ReconciliationDiscrepancy.statusMismatch(internal, pspRecord));
            }
        }

        if (!discrepancies.isEmpty()) {
            alertService.sendReconciliationAlert(yesterday, discrepancies);
        }
    }
}
