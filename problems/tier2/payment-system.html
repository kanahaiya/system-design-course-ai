Tier 2 — Should Know 45 min Correctness-critical

Design a Payment System

Payment systems have zero tolerance for money duplication or loss. The two cardinal rules: idempotency (charging a user twice is catastrophic) and double-entry bookkeeping (every debit has a corresponding credit — balances must always sum to zero).

🏢 Stripe, PayPal, Amazon
⏱️ 45 min interview
💰 Zero money loss tolerance

❓R — Requirements3–5 min

Functional Requirements

  • Transfer money between user accounts
  • Pay merchants (debit user account, credit merchant account)
  • View transaction history and balance
  • Support refunds and chargebacks
  • Multi-currency support

Non-Functional Requirements

  • Correctness: No double charges, no money creation or loss — ACID transactions required
  • Idempotency: Retrying a failed payment request must not charge twice
  • Scale: 1M transactions/day = ~12 TPS average, 100 TPS peak
  • Latency: Payment response <3s (includes bank authorization)
  • Auditability: Every state change must be logged and traceable

🔢E — Estimation3–5 min

  • 1M transactions/day; each transaction = ~2 ledger entries (double-entry) → 2M ledger rows/day
  • Each ledger row ~200 bytes → 400MB/day, 150GB/year → fits in PostgreSQL easily
  • Idempotency keys: 1M/day with 24h TTL → 1M keys in Redis at any time → ~100MB RAM
  • Read:write ratio ~10:1 (users checking balances) → balance cache in Redis, recomputed from ledger on miss

🗄️S — Schema3–5 min

// Double-entry ledger (PostgreSQL — ACID required)
// Every payment creates TWO rows: debit on payer, credit on payee
// SUM(amount) across all rows for an account = current balance
ledger_entries:
    entry_id     BIGINT PRIMARY KEY,
    account_id   UUID NOT NULL,
    amount       DECIMAL(19,4) NOT NULL,  -- negative = debit, positive = credit
    currency     CHAR(3) NOT NULL,
    entry_type   ENUM(debit, credit),
    payment_id   UUID NOT NULL,           -- links the two sides of a transaction
    created_at   TIMESTAMP NOT NULL,
    INDEX on (account_id, created_at)

// Payments (state machine)
payments:
    payment_id         UUID PRIMARY KEY,
    idempotency_key    VARCHAR(255) UNIQUE NOT NULL,
    payer_account_id   UUID,
    payee_account_id   UUID,
    amount             DECIMAL(19,4),
    currency           CHAR(3),
    status             ENUM(pending, processing, completed, failed, refunded),
    external_txn_id    VARCHAR(255),   -- bank/card network reference
    created_at         TIMESTAMP,
    updated_at         TIMESTAMP

🏗️H — High-level Design10 min

  • Payment API: Client sends payment request with idempotency-key header. API checks Redis for existing result before processing.
  • Idempotency Layer: Redis key = idempotency-key. If exists: return cached response. If not: process + store result in Redis (24h TTL) atomically.
  • Payment Processor: Validates funds, calls external payment gateway (Stripe/bank), on success writes double-entry ledger rows in a single DB transaction.
  • Ledger Service: Append-only. Balances computed as SUM(amount) for account. Cached in Redis, invalidated on new ledger entry.
  • Reconciliation Job: Nightly batch job compares internal ledger with bank statements. Flags discrepancies for manual review.
  • Audit Log (Kafka): Every payment state change emitted to Kafka topic. Consumers write to immutable audit log (S3/BigQuery).

🔬D — Deep Dive: Idempotency Guarantees10 min

The problem: Network failures happen. The client sends a payment request; the server processes it (charges the card) but the response is lost. The client retries. Without idempotency: the user is charged twice.

Solution:

  1. Client generates a UUID idempotency-key before the first attempt. Same key on every retry.
  2. Server checks Redis: GET idempotency:{key}. If found: return cached response immediately (no processing).
  3. If not found: acquire distributed lock on the key. Process payment. Store result: SET idempotency:{key} {response} EX 86400 (24h TTL). Release lock. Return response.
  4. Concurrent requests with the same key: lock ensures only one processes, the other waits and gets the cached result.

Why 24h TTL? After 24h, a retry of a 24-hour-old payment is almost certainly a bug, not a network retry. Expire the key to reclaim Redis memory.

✅E — Evaluate3 min

  • Distributed transaction problem: Charging external bank + writing ledger are two different systems. Use the Outbox Pattern: write to ledger + outbox table in one DB transaction. Separate service polls outbox and calls bank API. On success, marks outbox row processed.
  • Balance calculation cost: SUM of all ledger rows is O(N). For accounts with years of history: use periodic balance snapshots (checkpoint balance at end of each day) and SUM only since last snapshot.

🚀D — Deliver2 min

We designed a payment system with zero-tolerance for money duplication. Key decisions: Redis idempotency layer prevents double-charges on retry, double-entry ledger ensures every debit has a credit (sum = 0), ACID PostgreSQL transactions for ledger writes, Outbox Pattern for safe bank API calls, and nightly reconciliation to catch any discrepancies.

⚖️Trade-offs

DecisionChosenAlternativeWhy Chosen
Idempotency storageRedis (TTL-based)DB unique constraint on idempotency_keyRedis: fast lookup, automatic expiry. DB unique constraint also valid but slower and requires cleanup job

☕Java Implementation

/**
 * IdempotentPaymentService — processes payments with Redis-based idempotency.
 * Guarantees: a payment with a given idempotency-key is executed at most once,
 * even under concurrent retries.
 */
public class IdempotentPaymentService {

    private static final String IDEMPOTENCY_KEY_PREFIX = "idempotency:";
    private static final int IDEMPOTENCY_TTL_SECONDS = 86400; // 24 hours

    private final JedisPool jedisPool;
    private final PaymentProcessor paymentProcessor;
    private final ObjectMapper objectMapper = new ObjectMapper();

    public IdempotentPaymentService(JedisPool jedisPool, PaymentProcessor paymentProcessor) {
        this.jedisPool = jedisPool;
        this.paymentProcessor = paymentProcessor;
    }

    /**
     * Processes a payment idempotently.
     * If this idempotency key was used before, returns the original result.
     * Otherwise processes the payment and caches the result.
     *
     * @param idempotencyKey  client-generated UUID; must be the same on retries
     * @param paymentRequest  payment details
     * @return PaymentResult — same object on retries
     */
    public PaymentResult processPayment(String idempotencyKey, PaymentRequest paymentRequest) {
        String redisKey = IDEMPOTENCY_KEY_PREFIX + idempotencyKey;

        // Check for cached result (fast path — no lock needed for read)
        String cachedResult = getFromRedis(redisKey);
        if (cachedResult != null) {
            return deserializePaymentResult(cachedResult);
        }

        // Acquire distributed lock to prevent concurrent duplicate processing
        String lockKey = "lock:" + redisKey;
        boolean lockAcquired = tryAcquireLock(lockKey, 30); // 30s timeout
        if (!lockAcquired) {
            throw new PaymentConflictException("Concurrent payment with same idempotency key");
        }

        try {
            // Re-check after acquiring lock (another thread may have processed while we waited)
            cachedResult = getFromRedis(redisKey);
            if (cachedResult != null) {
                return deserializePaymentResult(cachedResult);
            }

            // Process the payment — this calls external bank API and writes the ledger
            PaymentResult paymentResult = paymentProcessor.execute(paymentRequest);

            // Cache the result so retries return immediately
            storeInRedis(redisKey, serializePaymentResult(paymentResult), IDEMPOTENCY_TTL_SECONDS);

            return paymentResult;
        } finally {
            releaseLock(lockKey);
        }
    }

    private String getFromRedis(String key) {
        try (Jedis jedis = jedisPool.getResource()) {
            return jedis.get(key);
        }
    }

    private void storeInRedis(String key, String value, int ttlSeconds) {
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.setex(key, ttlSeconds, value);
        }
    }

    private boolean tryAcquireLock(String lockKey, int timeoutSeconds) {
        try (Jedis jedis = jedisPool.getResource()) {
            // SET NX EX is atomic — prevents race condition between check and set
            String result = jedis.set(lockKey, "1", SetParams.setParams().nx().ex(timeoutSeconds));
            return "OK".equals(result);
        }
    }

    private void releaseLock(String lockKey) {
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.del(lockKey);
        }
    }

    private String serializePaymentResult(PaymentResult result) {
        try {
            return objectMapper.writeValueAsString(result);
        } catch (JsonProcessingException jsonException) {
            throw new RuntimeException("[IdempotentPaymentService.serialize] failed", jsonException);
        }
    }

    private PaymentResult deserializePaymentResult(String json) {
        try {
            return objectMapper.readValue(json, PaymentResult.class);
        } catch (JsonProcessingException jsonException) {
            throw new RuntimeException("[IdempotentPaymentService.deserialize] failed", jsonException);
        }
    }
}
