Tier 2 — Should Know 45 min Security-critical

Design Online Code Judge (LeetCode)

The central challenge is security: you're executing arbitrary user code on your servers. A malicious submission could delete your database, exfiltrate secrets, or fork-bomb the host. Sandboxing is non-negotiable. LeetCode serves 10M users with 100K submissions during a contest — requiring 100K containers in <60 seconds.

🏢 LeetCode, HackerRank, Google
⏱️ 45 min interview
🔒 Untrusted code execution

❓R — Requirements3–5 min

Functional Requirements

  • Submit code in multiple languages (Java, Python, C++, Go, JavaScript)
  • Run code against hidden test cases; return pass/fail per test
  • Show: runtime (ms), memory usage (MB), output diff on failure, compile errors
  • Support custom test runs (user provides their own input)
  • Problem management: create/edit problems with test cases, public and hidden
  • Contests: time-limited, ranked submissions, live leaderboard

Non-Functional Requirements

  • Security: Submitted code must be fully isolated — no network, no filesystem, CPU/memory/PID limited
  • Scale: 100K submissions/day normal; 100K submissions in 60 seconds during contests
  • Fairness: Same code must produce consistent runtime measurements ±5%
  • Latency: Result delivered within 5–10 seconds of submission (p95)
L6 depth signal: Proactively mention gVisor as a stronger sandboxing alternative: "Docker containers share the host kernel — a kernel exploit could break out. gVisor (Google's user-space kernel) intercepts all system calls and runs them in a separate user-space process, adding an extra isolation layer at ~20% performance overhead."

🔢E — Estimation3–5 min

  • 100K submissions/day normal; each runs avg 50 test cases → 5M container executions/day
  • Avg execution: 500ms → 5M × 0.5s = 2.5M execution-seconds/day → need ~30 executor cores continuously busy
  • Contest peak: 100K submissions in 60 seconds = 1,667 submissions/sec → need ~8,335 concurrent containers (at 500ms execution time) → ~100 executor machines at 100 containers each
  • Container startup overhead (cold): 200ms; pre-warmed pool reduces to <10ms
  • Code storage: 100K submissions × avg 2KB code = 200MB/day → S3, negligible
  • Test case storage: 1M problems × 100 test cases × avg 10KB = ~1TB → S3 with aggressive caching on executor nodes

🏗️H — High-level Design10 min

Figure: Submission pipeline — code stored in S3, job queued in Kafka, worker pulls and executes in Docker, result pushed via WebSocket

  • Submission API: Validates language, problem exists. Stores code in S3 (not DB — security + size). Creates submission row (status=QUEUED). Publishes to Kafka. Returns submission_id immediately. Never blocks on execution.
  • Kafka Job Queue: Buffers submission jobs. Multiple partitions = multiple concurrent consumer groups. If contest spike: queue absorbs burst; workers drain at their own rate.
  • Executor Pool (Worker Farm): Kubernetes Pods with Docker daemon. Each worker pulls a job, gets code from S3, downloads test cases from S3 (cached on disk), executes in container, compares output, writes result to DB.
  • Container Pool (Pre-warmed): Maintain a pool of pre-started containers per language. Container reuse eliminates 200ms cold start. Pool size tuned to expected concurrency per language.
  • Result Delivery: WebSocket (real-time push when result is ready) + REST polling (GET /submissions/{id}) as fallback for clients that can't maintain WebSocket.

🔬D — Deep Dive: Sandboxing and Security10 min

Why You Can't Run User Code on Bare Metal

Malicious code can:

  • Read /etc/passwd, environment variables, AWS metadata endpoint (steal credentials)
  • Fork-bomb: import os; os.fork() in a loop → exhaust host process table → crash host
  • Consume all CPU/RAM → starve other executions → fairness violation
  • Open network connections → exfiltrate test case answers from your DB
  • Write to disk → fill host filesystem → crash other services

Docker Sandboxing Configuration

// The complete Docker run command for a Java submission:
docker run
  --rm                                 // auto-remove container on exit
  --network=none                       // no network access (critical)
  --cpus=1                             // one CPU core max
  --memory=256m                        // hard memory limit (RAM)
  --memory-swap=256m                   // = --memory → disables swap (prevents bypass)
  --pids-limit=100                     // prevents fork bombs (max 100 processes)
  --read-only                          // read-only root filesystem
  --tmpfs=/tmp:size=64m,noexec         // writable /tmp, no executable files
  --security-opt=no-new-privileges     // prevent privilege escalation
  --security-opt=seccomp=judge.json    // custom seccomp profile (whitelist syscalls)
  --user=1000:1000                     // run as non-root user
  --cap-drop=ALL                       // drop all Linux capabilities
  -v /judge/submissions/{id}:/code:ro  // mount code read-only
  --stop-timeout=6                     // SIGTERM at 5s, SIGKILL at 6s
  openjdk:17-slim
  java -cp /code Main                  // execute compiled bytecode

// seccomp profile (judge.json): whitelist only necessary syscalls
// Blocks: ptrace (debugging), mount, clone (with dangerous flags), etc.
// Allows: read, write, open, close, exit, brk (memory), futex (threading), etc.

Docker vs gVisor — Security Depth

// Docker: containers share the HOST LINUX KERNEL
// A kernel vulnerability in the host can be exploited from within a container
// Example: CVE-2019-5736 (runc vulnerability) allowed container breakout

// gVisor (by Google): user-space kernel for containers
// Every syscall from container code is intercepted by gVisor's Sentry process
// Sentry runs in user space, makes LIMITED syscalls to the actual host kernel
// Attack surface: host kernel sees only ~20 syscalls from Sentry (vs 300+ directly)
// Cost: ~20% performance overhead (syscall interception in user space)

// In production judge systems:
// - Normal submissions: Docker + seccomp (fast, secure enough for most code)
// - Contest with prize money: gVisor (higher security, worth the overhead)
// - Unrecognized attack patterns: automatic escalation to gVisor-isolated nodes

// Runtime example for Python "hello world":
// Docker:  ~80ms total (container startup 30ms + Python startup 40ms + execution 10ms)
// gVisor:  ~200ms total (extra user-space kernel overhead)
// Pre-warmed Docker: ~15ms (container already running, just execute)

Execution Pipeline — Compiled vs Interpreted Languages

// Compiled languages (Java, C++): two-phase execution
// Phase 1: COMPILE
//   docker run --network=none --read-only ... gcc:12 g++ -O2 /code/solution.cpp -o /tmp/solution
//   If exit_code != 0: status = COMPILE_ERROR, return compiler stderr to user
//   If success: compiled binary cached in /judge/binaries/{submissionId}/solution
//
// Phase 2: RUN (once per test case)
//   docker run --network=none ... -v /judge/binaries/{id}:/bin:ro \
//     alpine /bin/solution < test_case_N.in
//   Capture stdout, compare with expected_output_N.txt

// Interpreted languages (Python, JavaScript): single phase
// No compilation step: docker run ... python3 /code/solution.py < input

// Caching compiled output:
// Key: hash(code + language + compiler_version)
// If same code submitted again: skip compilation, reuse binary
// Reduces compile time from ~2s to 0 for identical resubmissions

Test Case Management — Public vs Hidden

// Test cases have two tiers:
// 1. Public (is_hidden=false): shown in UI with actual input/output
//    User can see "Input: [1,2,3]\nOutput: [3,2,1]"
//    Used for "Run Code" feature to let users debug
//
// 2. Hidden (is_hidden=true): never revealed to user
//    Judge runs these and only says ACCEPTED or WRONG_ANSWER
//    Hidden test cases prevent hardcoding answers
//    Typically 5-50 hidden tests per problem

// Test case security:
// - Hidden test cases stored in S3 with IAM policy: only judge workers can read
// - Test case content never sent to the API server or client
// - Output comparison happens inside worker process: user never sees expected output
// - Workers are network-isolated from each other

// Problem creator workflow:
// 1. Creator uploads test cases via admin API
// 2. System runs the reference solution (Creator's correct code) to generate expected outputs
// 3. Test cases and expected outputs stored in S3
// 4. Problem published: public test cases visible in UI, hidden ones silently available

Anti-Cheat — Code Similarity Detection

// Two anti-cheat mechanisms:

// 1. Code hashing: SHA-256 of normalized code
//    Normalize: remove whitespace, comments, rename variables uniformly
//    If hash matches a known correct submission from contest: flag for review
//    If hash matches another user's submission in same contest: plagiarism alert

// 2. AST comparison (deeper similarity):
//    Parse code into Abstract Syntax Tree
//    Two codes are "similar" if their ASTs are structurally identical after:
//    - Variable renaming
//    - Loop variable substitution
//    - Comment removal
//    Similarity score > 0.85: flag as likely plagiarism

// Rate limiting (prevents gaming the system):
// - 5 submissions per problem per user per minute
// - 100 submissions per user per day during contests
// - Custom input runs: 10 per minute per user

// Contest fairness:
// - Random test case ordering per user (prevents timing attacks)
// - Submissions locked for review 30 minutes before contest end (prevents last-minute flooding)
// - All contest results are provisional until 1 hour post-contest (for manual review)

Pre-warmed Container Pool

/**
 * Manages a pool of pre-started Docker containers per language.
 * Containers are reset between uses (not restarted — reset is faster).
 * On contest start: scale pool to match expected concurrency.
 */
public class ContainerPool {

    private static final int DEFAULT_POOL_SIZE_PER_LANGUAGE = 20;
    private static final Map<String, String> LANGUAGE_IMAGES = Map.of(
        "java",   "openjdk:17-slim",
        "python", "python:3.11-slim",
        "cpp",    "gcc:12-slim",
        "go",     "golang:1.21-alpine"
    );

    // Language → queue of warm container IDs
    private final Map<String, BlockingQueue<String>> warmContainers = new ConcurrentHashMap<>();

    /**
     * Returns a warm container ID for the given language.
     * If pool is empty, starts a new container (cold start fallback).
     */
    public String acquireContainer(String language) throws InterruptedException {
        BlockingQueue<String> pool = warmContainers.getOrDefault(
            language, new LinkedBlockingQueue<>());
        String containerId = pool.poll(100, TimeUnit.MILLISECONDS);
        if (containerId == null) {
            containerId = startFreshContainer(language); // cold start fallback
        }
        return containerId;
    }

    /**
     * Returns a container to the pool after resetting its state.
     * Reset: remove output files, kill any lingering processes.
     */
    public void releaseContainer(String containerId, String language) {
        resetContainerState(containerId); // docker exec {id} rm -rf /tmp/*
        warmContainers.computeIfAbsent(language, l -> new LinkedBlockingQueue<>())
                      .offer(containerId);
    }

    private String startFreshContainer(String language) {
        String image = LANGUAGE_IMAGES.get(language);
        ProcessBuilder processBuilder = new ProcessBuilder(
            "docker", "run", "-d",          // -d: detached mode (keep running)
            "--network=none", "--pids-limit=100",
            "--memory=256m", "--memory-swap=256m",
            "--read-only", "--tmpfs=/tmp:size=64m,noexec",
            "--security-opt=no-new-privileges",
            "--user=1000:1000",
            image, "sleep", "infinity"      // keep alive, waiting for exec
        );
        // Returns container ID (stdout of docker run -d)
        return runAndCaptureOutput(processBuilder).trim();
    }

    private void resetContainerState(String containerId) {
        new ProcessBuilder("docker", "exec", containerId, "sh", "-c",
            "rm -rf /tmp/* && kill -9 $(ps aux | grep -v 'sleep infinity' | awk '{print $1}') 2>/dev/null || true")
            .start(); // fire and forget
    }
}

✅E — Evaluate3 min

  • Runtime fairness: Container overhead varies by 10-15ms. Measure wall-clock time inside the container using language-native timing (not external). Dedicated executor nodes with no other workloads ("noisy neighbors") ensure consistent measurements. Same hardware per language.
  • Test case isolation: Each test case runs sequentially in the same container but with state reset between cases (write to /tmp only, cleaned between cases). For complete isolation: one container per test case (slower, but eliminates any stateful side effects).
  • Container escape (kernel exploit): Docker shares host kernel — a kernel CVE could allow escape. Mitigations: (1) Seccomp whitelist reduces exploit surface. (2) gVisor for high-value contests. (3) Separate physical hosts for judge workers (not shared with production services). (4) Regular kernel patching.
  • Contest spike (100K submissions/60s): Kafka absorbs the burst. Auto-scale executor pods based on Kafka consumer lag (Kubernetes HPA on custom metrics). Pre-warm containers for all languages before contest start. Scale-out to 100+ nodes during contest.

🚀D — Deliver2 min

We designed a code judge handling LeetCode's scale: 10M users, 100K contest submissions in 60 seconds. Key decisions: Docker containers with CPU/memory/PID/network/seccomp limits for security; gVisor for high-stakes contests; Kafka job queue for burst absorption and async decoupling; pre-warmed container pools eliminating 200ms cold start; per-language executor clusters for fairness; compiled language caching by code hash; and two-tier test cases (public for debugging, hidden for judging).

⚖️Trade-offs

DecisionChosenAlternativeWhy Chosen
Sandboxing technology Docker + seccomp (normal) / gVisor (contests) VM per submission Docker: 200ms cold start vs 5s for VM, much lower overhead. gVisor: user-space kernel provides stronger isolation than Docker at ~20% performance overhead. VMs: strongest isolation but too slow and resource-heavy for 100K/min.
Execution model Async queue (Kafka) Synchronous HTTP execution Execution takes 1–10s. Synchronous would hold connections — at 1,667/sec during contests, 10K+ concurrent connections on API server. Kafka decouples acceptance from execution; rate limiting built in via partition count.
Result delivery WebSocket push Client polling every 2s WebSocket delivers result immediately on completion (~2-5s); polling adds 0-2s additional latency and generates 5× more requests. WebSocket requires connection management overhead — REST polling is the simpler fallback.
Container lifecycle Pre-warmed pool, reset between runs New container per submission Container startup adds 200ms. Pre-warm pool reduces to <10ms. Reset (rm -rf /tmp/*, kill processes) is <100ms. Net saving: 100ms per submission. At 100K/day: saves ~2.8 hours of execution time.

☕Java Implementation

/**
 * @file JudgeWorker.java
 * @description Kafka consumer that pulls submission jobs and executes them
 *              in Docker containers. Handles compilation, execution, output comparison.
 *
 * Public API:
 *   run() — main consumer loop (blocking)
 */
public class JudgeWorker implements Runnable {

    private static final int COMPILE_TIMEOUT_SECONDS = 15;
    private static final int EXECUTION_TIMEOUT_BUFFER_MS = 1000;

    private final KafkaConsumer<String, String> kafkaConsumer;
    private final ContainerPool containerPool;
    private final SubmissionRepository submissionRepository;
    private final S3Client s3Client;
    private final TestCaseRepository testCaseRepository;

    // ── Main Loop ─────────────────────────────────────────────────

    @Override
    public void run() {
        kafkaConsumer.subscribe(List.of("submission-jobs"));

        while (true) {
            var records = kafkaConsumer.poll(Duration.ofMillis(100));
            for (var record : records) {
                processSubmission(deserializeJob(record.value()));
            }
            kafkaConsumer.commitSync();
        }
    }

    // ── Submission Processing ─────────────────────────────────────

    private void processSubmission(SubmissionJob job) {
        submissionRepository.updateStatus(job.getSubmissionId(), SubmissionStatus.RUNNING);

        try {
            String codeFilePath = downloadCode(job);
            String compiledPath = compileIfNeeded(job.getLanguage(), codeFilePath, job.getSubmissionId());
            if (compiledPath == null) {
                return; // COMPILE_ERROR already written to DB
            }

            List<TestCase> testCases = testCaseRepository.findByProblemId(job.getProblemId());
            List<TestResult> testResults = runAllTestCases(
                job, compiledPath, testCases);

            SubmissionStatus finalStatus = determineFinalStatus(testResults);
            submissionRepository.writeResults(job.getSubmissionId(), finalStatus, testResults);

        } catch (Exception unexpectedException) {
            System.err.println("[JudgeWorker.processSubmission] Unexpected error for submission "
                + job.getSubmissionId() + ": " + unexpectedException.getMessage());
            submissionRepository.updateStatus(job.getSubmissionId(), SubmissionStatus.INTERNAL_ERROR);
        }
    }

    // ── Compilation ───────────────────────────────────────────────

    /**
     * Compiles code for compiled languages. Returns path to binary.
     * Returns null and writes COMPILE_ERROR to DB if compilation fails.
     * Returns original path (no compile needed) for interpreted languages.
     */
    private String compileIfNeeded(String language, String codeFilePath, String submissionId) {
        if (isInterpretedLanguage(language)) {
            return codeFilePath; // Python, JS: no compilation
        }

        String containerBuildId = containerPool.acquireContainer(language + "-compile");
        try {
            List<String> compileCommand = buildCompileCommand(language, codeFilePath);
            ProcessBuilder processBuilder = new ProcessBuilder(compileCommand);
            Process compileProcess = processBuilder.start();
            boolean finished = compileProcess.waitFor(COMPILE_TIMEOUT_SECONDS, TimeUnit.SECONDS);

            if (!finished) {
                compileProcess.destroyForcibly();
                submissionRepository.writeCompileError(submissionId, "Compilation timed out");
                return null;
            }
            if (compileProcess.exitValue() != 0) {
                String compileError = readStream(compileProcess.getErrorStream());
                submissionRepository.writeCompileError(submissionId, compileError);
                return null;
            }
            return codeFilePath.replace(".java", "").replace(".cpp", ""); // compiled binary path
        } catch (Exception exception) {
            throw new RuntimeException("[JudgeWorker.compileIfNeeded] Compile invocation failed", exception);
        } finally {
            containerPool.releaseContainer(containerBuildId, language + "-compile");
        }
    }

    // ── Test Execution ────────────────────────────────────────────

    private List<TestResult> runAllTestCases(SubmissionJob job, String compiledPath,
                                               List<TestCase> testCases) {
        List<TestResult> results = new ArrayList<>();
        String containerId = containerPool.acquireContainer(job.getLanguage());

        try {
            for (TestCase testCase : testCases) {
                TestResult result = executeOneTestCase(job, compiledPath, testCase, containerId);
                results.add(result);
                // Early termination: stop on first failure for efficiency
                if (!result.isPassed() && result.getStatus() != SubmissionStatus.WRONG_ANSWER) {
                    break; // TLE, MLE, RE — no point running remaining cases
                }
            }
        } finally {
            containerPool.releaseContainer(containerId, job.getLanguage());
        }
        return results;
    }

    /**
     * Executes one test case in a Docker container.
     * Returns TestResult with status, runtime, and actual output.
     */
    private TestResult executeOneTestCase(SubmissionJob job, String compiledPath,
                                           TestCase testCase, String containerId) {
        String testInput = s3Client.getObjectAsString(testCase.getInputS3Key());
        String expectedOutput = s3Client.getObjectAsString(testCase.getExpectedOutputS3Key());
        int timeLimitMs = job.getTimeLimitMs();

        List<String> execCommand = buildExecCommand(job.getLanguage(), compiledPath, containerId);

        try {
            ProcessBuilder processBuilder = new ProcessBuilder(execCommand);
            Process execProcess = processBuilder.start();

            // Feed test input to container's stdin
            try (OutputStream stdinStream = execProcess.getOutputStream()) {
                stdinStream.write(testInput.getBytes());
            }

            long startMs = System.currentTimeMillis();
            boolean completedInTime = execProcess.waitFor(
                timeLimitMs + EXECUTION_TIMEOUT_BUFFER_MS, TimeUnit.MILLISECONDS);
            long runtimeMs = System.currentTimeMillis() - startMs;

            if (!completedInTime) {
                execProcess.destroyForcibly();
                return TestResult.timeLimitExceeded(testCase.getTestCaseId(), runtimeMs);
            }

            String actualOutput = readStream(execProcess.getInputStream());
            int exitCode = execProcess.exitValue();

            if (exitCode != 0) {
                String stderr = readStream(execProcess.getErrorStream());
                return TestResult.runtimeError(testCase.getTestCaseId(), stderr, runtimeMs);
            }

            boolean passed = normalizeOutput(actualOutput).equals(normalizeOutput(expectedOutput));
            return passed
                ? TestResult.accepted(testCase.getTestCaseId(), runtimeMs)
                : TestResult.wrongAnswer(testCase.getTestCaseId(), actualOutput, expectedOutput, runtimeMs);

        } catch (IOException ioException) {
            throw new RuntimeException("[JudgeWorker.executeOneTestCase] exec failed", ioException);
        } catch (InterruptedException interruptedException) {
            Thread.currentThread().interrupt();
            throw new RuntimeException("[JudgeWorker.executeOneTestCase] interrupted", interruptedException);
        }
    }

    // ── Helpers ───────────────────────────────────────────────────

    private String normalizeOutput(String output) {
        // Trim trailing whitespace and normalize line endings — common source of false WA
        return output.strip().replace("\r\n", "\n").stripTrailing();
    }

    private SubmissionStatus determineFinalStatus(List<TestResult> results) {
        for (TestResult result : results) {
            if (result.getStatus() != SubmissionStatus.ACCEPTED) {
                return result.getStatus(); // first non-accepted status = final verdict
            }
        }
        return SubmissionStatus.ACCEPTED;
    }

    private boolean isInterpretedLanguage(String language) {
        return language.equals("python") || language.equals("javascript");
    }

    private String readStream(InputStream stream) throws IOException {
        return new String(stream.readAllBytes());
    }
}
