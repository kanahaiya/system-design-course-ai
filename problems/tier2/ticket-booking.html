Tier 2 — Should Know 45 min Inventory Contention

Design Ticket Booking System

The real problem isn't booking tickets — it's selling the last seat to exactly ONE person when 10,000 people click Buy simultaneously. Inventory contention at flash-sale scale.

🏢 BookMyShow, Ticketmaster, Amazon, Airbnb
⏱️ 45 min interview
🎟️ Concurrency / flash-sale
🧠 The One Mental Model That Wins This Interview

Ticket booking = the INVENTORY CONTENTION problem. Every other piece of the system (event catalog, user accounts, payment, email) is standard CRUD you've built a dozen times. The interview is really asking: how do you sell the last seat to exactly ONE person when 10,000 people click Buy simultaneously?

Think of it like a parking garage with one space left. 10,000 cars pull up at once. Your system is the attendant. You need to let exactly one car in and turn away the other 9,999 — instantly, without confusion, and without accidentally letting two cars into the same space.

The answer: Two-phase reservation — Redis SETNX as fast rejection layer (turns away 9,950 cars in microseconds before they even reach the DB), then a DB write for the ~50 that pass. Seats hold 3 states: AVAILABLE → RESERVED (10-min TTL) → BOOKED.

❓R — Requirements3–5 min

Functional Requirements

  • Browse events (movies, concerts, sports) with available seats and pricing tiers
  • Select seats from a visual seat map showing real-time availability
  • Reserve seats for a 10-minute checkout window (soft lock — no payment yet)
  • Complete payment within the window → confirm booking → send QR code ticket via email
  • Cancel booking (up to 24 hours before event) → immediately release seats back to AVAILABLE

Non-Functional Requirements

  • Zero double-booking: Each physical seat sold to exactly one person — the primary correctness constraint
  • Scale: 5M DAU; 500K concurrent users during flash events (Taylor Swift on-sale)
  • Reservation TTL: Seats auto-release after exactly 10 minutes if checkout not completed
  • Latency: Seat map <1s; seat selection confirmation <500ms
  • Availability: 99.99% — booking service never goes down mid-sale
  • Real-time seat map: When User A grabs seat 15A, User B sees it gray out within ~500ms
🎯 What to Clarify in the Interview
  • Seat map granularity: Individual seats (concerts) or sections (standing areas)? — affects locking strategy
  • Group booking atomicity: If user selects 4 seats, must all 4 succeed together? Yes — partial booking is worse UX than rejection.
  • Flash sale fairness: First-come-first-served or virtual waiting room? Matters for extremely high-demand events.
  • Payment retry: If payment fails, release reservation immediately or wait for TTL?

🔢E — Estimation3–5 min

  • Event scale: 100K active events; 50K seats per large venue = 5 billion seat records total
  • Peak load (Taylor Swift on-sale): 1M users simultaneously trying to book → ~1M reservation requests/minute at peak
  • Seat write throughput: During booking rush, every selection triggers a status write — 1M writes/min = ~17K writes/sec. Postgres handles ~5K TPS comfortably; Redis handles 1M+ ops/sec. This is why Redis is the front-line filter.
  • Seat map reads: 1M users viewing seat map simultaneously → millions of reads/sec. Must be served from Redis cache, never from DB.
  • Reservation records: At any moment, at most 500K active reservations (one per seat being held). Tiny dataset.
  • Booking storage: 50M bookings/year × 2KB = 100GB/year. Trivially managed in Postgres.
  • Kafka throughput: Every seat status change → 1 event. Peak: 17K events/sec, well within Kafka's 1M+/sec capacity.

Key insight from estimation: The DB cannot handle 1M concurrent writes. Redis can. The architecture follows from this math — Redis as a fast filter, DB as a durable store.

💡 Why This Schema

The status field on seats is the critical state machine: AVAILABLE → RESERVED → BOOKED. The seat_reservations table is ephemeral — records only exist during the 10-minute window. The composite index on (event_id, status) makes the seat map query (get all seats for event X, show which are available) a fast index range scan instead of a full table scan.

🏗️H — High-level Design10 min

Three Critical Subsystems

Subsystem 1 — Seat Map Service

  • Returns all seats for an event with current status (AVAILABLE / RESERVED / BOOKED)
  • Redis Hash per event: seats:{event_id} → field per seat_id → value is status. Cache is served to all seat map requests; DB is never hit directly.
  • WebSocket push: When any seat changes status, push {seat_id, status} to all users viewing that event's seat map. Users see seats gray out in real-time without polling.
  • Cache invalidated on every seat status change (reservation, payment, cancellation, TTL expiry)

Subsystem 2 — Reservation Service (the hard part)

  • User selects seats → Reservation Request arrives
  • Phase 1 (Redis): For each selected seat_id, attempt SET seat:{seat_id} {userId} NX PX 600000. If ANY seat fails (returns nil), undo all successfully set keys and return 409.
  • Phase 2 (DB): All Redis locks acquired → INSERT reservation record with expires_at = NOW() + 10min, UPDATE seat status to RESERVED.
  • Atomicity for multi-seat: Acquire all Redis locks before writing to DB. Process seat_ids in sorted order (ascending) to prevent deadlocks.
  • TTL Sweeper: Quartz job every 30 seconds: DELETE FROM seat_reservations WHERE expires_at < NOW() → UPDATE released seats back to AVAILABLE → publish Kafka events.
  • Seat status → Kafka topic seat-status-changes → fan-out to WebSocket servers → push to connected users.

Subsystem 3 — Payment & Confirmation Service

  • User completes payment within 10-minute window via Stripe/Razorpay
  • On success: UPDATE seat status → BOOKED, DELETE reservation record, INSERT booking, generate QR code, set email_sent=false
  • On failure: Release reservation immediately (don't wait for TTL — better UX for others)
  • Idempotency: payment_session_id on reservation prevents double-charging if user submits payment form twice
  • Outbox pattern: Email notification is a side effect. If email service crashes, email_sent=false records are retried by background job. Booking is durable; notification is eventually consistent.

🔬D — Deep Dive15 min

1. Three Approaches to Preventing Double-Booking

Know all three — interviewers ask you to compare them:

Approach A — Pessimistic Locking (SELECT FOR UPDATE)

/**
 * Pessimistic locking: holds a DB row lock for the entire reservation transaction.
 * Simple and ACID-correct, but creates DB lock contention under high load.
 * Suitable for low-concurrency bookings; collapses under Taylor Swift load.
 */
@Transactional
public Reservation reserveSeats(List<UUID> seatIds, UUID userId) {
    // Sort by seat_id BEFORE locking — prevents deadlocks from opposite-order acquisition
    // Without this: Thread A locks seatId=100 then tries 200; Thread B locks 200 then tries 100 → deadlock
    List<UUID> sortedSeatIds = seatIds.stream()
        .sorted()
        .collect(Collectors.toList());

    // SELECT FOR UPDATE: acquires row-level exclusive lock on each seat record
    List<Seat> lockedSeats = seatRepository.findByIdsForUpdate(sortedSeatIds);

    for (Seat seat : lockedSeats) {
        if (seat.getStatus() != SeatStatus.AVAILABLE) {
            // Lock released when transaction rolls back
            throw new SeatNotAvailableException(seat.getSeatId());
        }
    }

    lockedSeats.forEach(seat -> seat.setStatus(SeatStatus.RESERVED));
    seatRepository.saveAll(lockedSeats);

    Instant expiresAt = Instant.now().plus(10, ChronoUnit.MINUTES);
    return reservationRepository.save(
        Reservation.of(sortedSeatIds, userId, expiresAt)
    );
    // Lock released on transaction commit
}

Approach B — Optimistic Locking (version CAS)

/**
 * Optimistic locking: no lock held. Race is detected at write time via version field.
 * Better than pessimistic for low contention (most bookings). Retry loop under high contention.
 */
public Reservation reserveSeatOptimistic(UUID seatId, UUID userId) {
    for (int attempt = 0; attempt < MAX_RETRY_ATTEMPTS; attempt++) {
        // Read current version — no lock acquired
        SeatWithVersion seat = seatRepository.findWithVersion(seatId);
        if (seat.getStatus() != SeatStatus.AVAILABLE) {
            throw new SeatNotAvailableException(seatId);
        }

        // UPDATE ... WHERE seat_id = ? AND status = 'AVAILABLE' AND version = ?
        // This is the CAS (compare-and-swap): only succeeds if version unchanged
        int updatedRows = seatRepository.updateStatusIfVersionMatches(
            seatId,
            SeatStatus.RESERVED,
            SeatStatus.AVAILABLE,
            seat.getVersion()          // if another thread changed this seat, version won't match → 0 rows
        );

        if (updatedRows == 1) {
            // Won the race — create reservation record
            Instant expiresAt = Instant.now().plus(10, ChronoUnit.MINUTES);
            return reservationRepository.save(Reservation.of(seatId, userId, expiresAt));
        }
        // Lost the race → retry. Another thread changed the seat between our read and write.
    }
    throw new SeatNotAvailableException("Seat unavailable after " + MAX_RETRY_ATTEMPTS + " attempts");
}

Approach C — Redis Atomic SETNX (Recommended for Flash Sales)

/**
 * Redis SETNX (SET if Not eXists): atomic, O(1), handles 1M+ ops/sec.
 * Used as the fast-rejection layer before any DB interaction.
 * The 10-minute TTL (PX 600000) is the safety net: if server crashes after
 * Redis lock but before DB write, the key auto-expires and seat becomes available.
 */
public class ReservationService {

    private static final Duration SEAT_HOLD_DURATION = Duration.ofMinutes(10);

    private final StringRedisTemplate redisTemplate;
    private final SeatRepository seatRepository;
    private final ReservationRepository reservationRepository;
    private final KafkaTemplate<String, SeatStatusEvent> kafkaTemplate;

    /**
     * Two-phase reservation: Redis SETNX (fast filter) + DB write (durable record).
     *
     * @param seatIds    seats to reserve — sorted ascending to prevent deadlock
     * @param userId     user claiming these seats
     * @param sessionId  idempotency key — prevents double-reservation on retry
     * @returns          Reservation with expires_at
     * @throws SeatNotAvailableException if any seat already locked
     */
    public Reservation reserveSeats(List<UUID> seatIds, UUID userId, String sessionId) {
        // Sort seat IDs for consistent acquisition order (deadlock prevention)
        List<UUID> sortedSeatIds = seatIds.stream().sorted().collect(Collectors.toList());
        List<String> acquiredKeys = new ArrayList<>();

        try {
            // Phase 1: Acquire Redis locks for all seats atomically
            for (UUID seatId : sortedSeatIds) {
                String redisKey = "seat:" + seatId;
                Boolean locked = redisTemplate.opsForValue()
                    .setIfAbsent(redisKey, userId.toString(), SEAT_HOLD_DURATION);

                if (!Boolean.TRUE.equals(locked)) {
                    // Seat already locked by someone else — release all acquired keys and reject
                    releaseRedisLocks(acquiredKeys);
                    throw new SeatNotAvailableException(seatId);
                }
                acquiredKeys.add(redisKey);
            }

            // Phase 2: All seats locked in Redis — persist to DB as source of truth
            return persistReservation(sortedSeatIds, userId, sessionId);

        } catch (SeatNotAvailableException exception) {
            // acquiredKeys already released inside the loop above
            throw exception;
        } catch (Exception databaseException) {
            // DB write failed after Redis locks acquired — release Redis locks
            releaseRedisLocks(acquiredKeys);
            throw new RuntimeException("[ReservationService.reserveSeats] DB write failed", databaseException);
        }
    }

    @Transactional
    private Reservation persistReservation(List<UUID> seatIds, UUID userId, String sessionId) {
        // Update seat status in DB (source of truth)
        seatRepository.updateStatusBatch(seatIds, SeatStatus.RESERVED);

        Instant expiresAt = Instant.now().plus(10, ChronoUnit.MINUTES);
        Reservation reservation = reservationRepository.save(
            Reservation.of(seatIds, userId, expiresAt, sessionId)
        );

        // Publish status change events for WebSocket fan-out
        seatIds.forEach(seatId ->
            kafkaTemplate.send("seat-status-changes",
                new SeatStatusEvent(seatId, SeatStatus.RESERVED, userId))
        );

        return reservation;
    }

    private void releaseRedisLocks(List<String> redisKeys) {
        if (!redisKeys.isEmpty()) {
            redisTemplate.delete(redisKeys);
        }
    }
}

2. The TTL Sweeper — Releasing Expired Reservations

/**
 * Quartz job runs every 30 seconds to release expired reservations.
 * Belt-and-suspenders: Redis TTL auto-expires the lock, but the DB record
 * must also be cleaned up, and seats must be set back to AVAILABLE in DB.
 */
@Component
public class ReservationExpiryJob {

    private static final int SWEEP_INTERVAL_SECONDS = 30;

    private final ReservationRepository reservationRepository;
    private final SeatRepository seatRepository;
    private final KafkaTemplate<String, SeatStatusEvent> kafkaTemplate;

    @Scheduled(fixedDelay = SWEEP_INTERVAL_SECONDS * 1000)
    public void releaseExpiredReservations() {
        List<Reservation> expiredReservations =
            reservationRepository.findAllExpiredBefore(Instant.now());

        if (expiredReservations.isEmpty()) {
            return;
        }

        List<UUID> expiredSeatIds = expiredReservations.stream()
            .flatMap(reservation -> reservation.getSeatIds().stream())
            .collect(Collectors.toList());

        // Bulk update: AVAILABLE seats back (idempotent — safe if run twice)
        seatRepository.updateStatusBatch(expiredSeatIds, SeatStatus.AVAILABLE);
        reservationRepository.deleteAll(expiredReservations);

        // Notify WebSocket clients that these seats are available again
        expiredSeatIds.forEach(seatId ->
            kafkaTemplate.send("seat-status-changes",
                new SeatStatusEvent(seatId, SeatStatus.AVAILABLE, null))
        );

        // Lazy check: when reading seat status, also check if reservation is expired
        // (belt-and-suspenders with the sweeper — seat is treated as AVAILABLE if
        // reservation.expires_at < NOW(), even before sweeper runs)
    }
}

3. Real-Time Seat Map — WebSocket Fan-Out

The real-time seat map update pipeline:

  1. Reservation Service publishes SeatStatusEvent to Kafka topic seat-status-changes
  2. Fan-out worker consumes Kafka events → publishes to Redis Pub/Sub channel event:{event_id}:seats
  3. WebSocket servers subscribe to Redis channel → receive published message
  4. WebSocket server pushes {seat_id, status} to all connected users viewing that event
  5. Client JavaScript receives WebSocket message → updates that seat's visual state (gray out if RESERVED)

Why Kafka between Reservation Service and WebSocket farm? Decoupling. The Reservation Service doesn't know how many WebSocket servers exist. Kafka fan-out handles distribution. Also: Kafka buffers events during WebSocket server restart — no missed updates.

✅E — Evaluate3 min

  • Thundering herd (Taylor Swift): 1M users → Redis absorbs instantly (SET NX is O(1), Redis handles 1M+ ops/sec single-threaded). ~950K get immediate 409. Only ~50K (actual seat count) proceed to DB. DB sees 50K writes/sec instead of 1M — a 95% load reduction.
  • Redis single point of failure: Run Redis Sentinel (3-node: 1 primary + 2 replicas + sentinel monitors) or Redis Cluster (shards across nodes). If Redis is down, fall back to DB pessimistic locking (slower but correct).
  • Redis/DB divergence: Server crashes after Redis SETNX but before DB write → Redis TTL expires in 10 min, seat becomes available. No orphaned DB record. Self-healing.
  • Fairness at extreme demand: For Beyoncé-tier demand, add a virtual waiting room. Users enter a queue instead of hitting the booking system directly. Queue position shown. Server admits N users per minute. Perceived fairness reduces rage; prevents thundering herd entirely at the source.
  • Group booking partial failure: If user selects 4 seats and only 3 are available → reject entire request (all-or-nothing). Partial booking (3 of 4 seats) is a terrible UX — user is in the venue without their friend.

🚀D — Deliver2 min

🎤 Your 60-Second Closing Summary

"Ticket booking is the inventory contention problem. The entire design flows from one insight: the database cannot handle 1M concurrent writes, but Redis can. So we use a two-phase reservation: Redis SETNX as a fast rejection layer that turns away 95% of requests in microseconds, then a DB write for the confirmed reservations.

Seats have three states: AVAILABLE → RESERVED (10-minute TTL) → BOOKED. The TTL is not just convenience — it's a correctness guarantee. If anything goes wrong after the Redis lock, the key expires and the seat self-heals back to AVAILABLE.

For multi-seat atomicity: acquire all Redis locks before any DB write, sorted by seat_id to prevent deadlocks. Real-time seat map via WebSocket + Kafka fan-out. For extreme demand (Taylor Swift): virtual waiting room queues users before they ever hit the booking system."

⚖️Trade-offs

☕Java Implementation

/**
 * @file BookingConfirmationService.java
 * @description Handles payment processing and booking confirmation.
 * Separates the idempotent booking record creation from the side-effect email dispatch.
 *
 * Key pattern: booking is ACID (seats + booking record updated atomically).
 * Email is eventually consistent (retried until email_sent = true).
 */
@Service
public class BookingConfirmationService {

    private static final String LOG_PREFIX = "[BookingConfirmationService]";

    private final ReservationRepository reservationRepository;
    private final SeatRepository seatRepository;
    private final BookingRepository bookingRepository;
    private final PaymentGateway paymentGateway;
    private final QrCodeGenerator qrCodeGenerator;
    private final KafkaTemplate<String, SeatStatusEvent> kafkaTemplate;
    private final StringRedisTemplate redisTemplate;

    /**
     * Confirms a booking: processes payment, atomically transitions seats to BOOKED,
     * and creates the booking record. Email sending is a separate retryable step.
     *
     * @param reservationId  active reservation (must not be expired)
     * @param paymentToken   Stripe payment method token
     * @returns              confirmed Booking with QR code URL
     * @throws ReservationExpiredException  if reservation TTL has elapsed
     * @throws PaymentFailedException       if payment is declined
     */
    @Transactional
    public Booking confirmBooking(UUID reservationId, String paymentToken) {
        // Step 1: Validate reservation is not expired (lazy check — belt-and-suspenders with sweeper)
        Reservation reservation = reservationRepository.findById(reservationId)
            .orElseThrow(() -> new ReservationNotFoundException(reservationId));

        if (reservation.getExpiresAt().isBefore(Instant.now())) {
            throw new ReservationExpiredException(reservationId);
        }

        // Step 2: Process payment via gateway
        PaymentResult paymentResult = processPaymentSafely(
            paymentToken,
            reservation.getTotalPrice(),
            reservation.getPaymentSessionId()  // idempotency key — safe to retry
        );

        if (!paymentResult.isSuccessful()) {
            // Release reservation immediately — don't make other buyers wait for TTL
            releaseReservationOnFailure(reservation);
            throw new PaymentFailedException(paymentResult.getDeclineReason());
        }

        // Step 3: Transition seats from RESERVED → BOOKED (atomic with booking creation)
        seatRepository.updateStatusBatch(reservation.getSeatIds(), SeatStatus.BOOKED);

        // Step 4: Create durable booking record (email_sent=false — retried separately)
        String qrCodeUrl = qrCodeGenerator.generate(reservationId);
        Booking booking = bookingRepository.save(Booking.builder()
            .bookingId(UUID.randomUUID())
            .userId(reservation.getUserId())
            .eventId(reservation.getEventId())
            .seatIds(reservation.getSeatIds())
            .totalPrice(reservation.getTotalPrice())
            .status(BookingStatus.CONFIRMED)
            .qrCodeUrl(qrCodeUrl)
            .emailSent(false)    // outbox pattern: background job retries until true
            .createdAt(Instant.now())
            .build());

        // Step 5: Remove reservation record (seat is now permanently BOOKED)
        reservationRepository.delete(reservation);

        // Step 6: Release Redis locks (seats are BOOKED, no longer need TTL guard)
        releaseRedisSeatlocks(reservation.getSeatIds());

        // Step 7: Publish BOOKED status events for WebSocket fan-out
        reservation.getSeatIds().forEach(seatId ->
            kafkaTemplate.send("seat-status-changes",
                new SeatStatusEvent(seatId, SeatStatus.BOOKED, reservation.getUserId()))
        );

        return booking;
    }

    /**
     * Releases a reservation when payment fails.
     * Sets seats back to AVAILABLE, deletes reservation record, clears Redis locks.
     */
    private void releaseReservationOnFailure(Reservation reservation) {
        seatRepository.updateStatusBatch(reservation.getSeatIds(), SeatStatus.AVAILABLE);
        reservationRepository.delete(reservation);
        releaseRedisSeatlocks(reservation.getSeatIds());

        reservation.getSeatIds().forEach(seatId ->
            kafkaTemplate.send("seat-status-changes",
                new SeatStatusEvent(seatId, SeatStatus.AVAILABLE, null))
        );
    }

    private PaymentResult processPaymentSafely(String paymentToken, BigDecimal amount, String idempotencyKey) {
        try {
            return paymentGateway.charge(paymentToken, amount, idempotencyKey);
        } catch (PaymentGatewayException gatewayException) {
            // Log full error internally — never expose internal details to user
            log.error("{} Payment gateway error for idempotency key {}: {}",
                LOG_PREFIX, idempotencyKey, gatewayException.getMessage());
            return PaymentResult.failed("Payment service unavailable. Please try again.");
        }
    }

    private void releaseRedisSeatlocks(List<UUID> seatIds) {
        List<String> redisKeys = seatIds.stream()
            .map(seatId -> "seat:" + seatId)
            .collect(Collectors.toList());
        redisTemplate.delete(redisKeys);
    }
}

/**
 * EmailRetryJob — retries email delivery for bookings where email_sent=false.
 * Runs every 60 seconds. Safe to run concurrently (UPDATE ... WHERE email_sent=false).
 */
@Component
public class BookingEmailRetryJob {

    private static final int RETRY_BATCH_SIZE = 100;
    private static final int RETRY_INTERVAL_SECONDS = 60;

    private final BookingRepository bookingRepository;
    private final EmailService emailService;

    @Scheduled(fixedDelay = RETRY_INTERVAL_SECONDS * 1000)
    public void retryPendingEmailNotifications() {
        List<Booking> pendingEmailBookings =
            bookingRepository.findByEmailSentFalseOrderByCreatedAtAsc(
                PageRequest.of(0, RETRY_BATCH_SIZE)
            );

        for (Booking booking : pendingEmailBookings) {
            try {
                emailService.sendBookingConfirmation(booking);
                // Only mark sent after successful delivery
                bookingRepository.markEmailSent(booking.getBookingId());
            } catch (EmailDeliveryException emailException) {
                // Log and continue — will retry next iteration
                log.warn("{} Email retry failed for booking {}: {}",
                    "[BookingEmailRetryJob]", booking.getBookingId(), emailException.getMessage());
            }
        }
    }
}
