Tier 2 — Should Know 45 min Real-time messaging

Design Facebook Messenger

Messenger = three distinct sub-problems: message delivery (WebSocket + durable store), group chat fan-out (N recipients in <500ms), and presence (who's online right now). Each sub-problem has a different scale challenge and a different right answer.

🏢 Meta, WhatsApp, Telegram, Signal
⏱️ 45 min interview
💬 1B+ DAU, 40B messages/day
🧠 The Mental Model: Three Sub-Problems

Messenger is actually three separate systems that share data. Most candidates try to solve it as one monolith and get lost. Decompose it explicitly:
(1) Message Delivery: WebSocket + message store → how does a message get from A to B?
(2) Group Fan-out: how do you push one message to 250 members in <500ms?
(3) Presence: how do you know who's online right now across 150M concurrent users?
Each has a different scale challenge. Name the three sub-problems first, then solve each one. Interviewers love this structure.

This page focuses on Messenger. The key differences: group read receipts, prominent presence, and optional E2E change the architecture significantly.

❓R — Requirements3–5 min

Functional Requirements

  • 1:1 messaging: send/receive text, images, video, GIFs, reactions
  • Group messaging: up to 250 members, group admin controls
  • Read receipts: "Seen by 43 people" on group messages
  • Online presence: green dot showing who's online, last active time
  • Message search: search within a conversation by keyword
  • Message threading: reply to specific messages, create threads

Non-Functional Requirements

  • Scale: 1B+ daily active users, 150M concurrent users at peak, 40B messages/day
  • Delivery latency: <100ms for online recipients, best-effort push notification for offline
  • Ordering: messages in a conversation must always appear in correct send order
  • Group fan-out: message to 250-person group delivered to all online members in <500ms
  • Presence accuracy: online/offline status should update within 30 seconds of change
  • Durability: 99.99% message delivery — no lost messages even during server failures
⚡ Clarifying Questions to Ask
  • "Should messages be end-to-end encrypted?" → No (or optional) → simplifies architecture, allows server-side search
  • "What's the maximum group size?" → 250 → sizes your fan-out strategy (different from 10K-member broadcast groups)
  • "Do we need message search?" → Yes → requires Elasticsearch or similar; E2E encryption makes this impossible

📌 The scary number: 116M fan-out operations per second. This is the number interviewers want to see you address. The answer: Kafka parallelism + targeted WebSocket routing. You don't need one central broker — you need many parallel fan-out workers, each responsible for a subset of conversations.

🗄️S — Schema5 min

// ── messages ─────────────────────────────────────────────────────────────
// Cassandra: partitioned by (conversation_id, bucket_month)
// High write throughput (40TB/day), time-range queries for conversation history.
// Snowflake ID as PK: time-sortable, globally unique, no DB auto-increment needed.
CREATE TABLE messages (
    conversation_id  UUID,
    bucket_month     TEXT,           -- partition key: "2024-01"
    message_id       BIGINT,         -- Snowflake ID: sortable by time
    sender_id        BIGINT,
    content_type     TEXT,           -- TEXT | IMAGE | VIDEO | REACTION | THREAD
    content          TEXT,
    replied_to_id    BIGINT,         -- nullable — for threading
    created_at       TIMESTAMP,
    is_deleted       BOOLEAN,
    PRIMARY KEY ((conversation_id, bucket_month), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);

// ── conversations ─────────────────────────────────────────────────────────
// MySQL/Postgres: low volume, needs transactions (e.g., add/remove member)
CREATE TABLE conversations (
    conversation_id   UUID PRIMARY KEY,
    type              ENUM('DIRECT', 'GROUP'),
    name              VARCHAR(255),  -- nullable (1:1 has no name)
    created_at        TIMESTAMP,
    last_message_id   BIGINT,        -- for conversation list preview
    last_activity_at  TIMESTAMP
);

// ── conversation_members ─────────────────────────────────────────────────
// MySQL: low write volume, needs joins with conversations
CREATE TABLE conversation_members (
    conversation_id     UUID,
    user_id             BIGINT,
    joined_at           TIMESTAMP,
    role                ENUM('ADMIN', 'MEMBER'),
    last_read_message_id BIGINT,     -- critical: source of read receipts
    PRIMARY KEY (conversation_id, user_id)
);

// ── message_receipts ──────────────────────────────────────────────────────
// Cassandra: very high write throughput (1B users can read = 1B receipt writes)
CREATE TABLE message_receipts (
    message_id    BIGINT,
    user_id       BIGINT,
    delivered_at  TIMESTAMP,
    read_at       TIMESTAMP,
    PRIMARY KEY (message_id, user_id)
);
-- "Seen by N" = COUNT(*) WHERE message_id = ? AND read_at IS NOT NULL
-- Optimization: also maintain seen_count COUNTER in messages table (see deep dive)

// ── presence ─────────────────────────────────────────────────────────────
// Redis: in-memory TTL-based. Key expires = user is offline.
// SETEX presence:{user_id} 60 "ONLINE"
// Client sends heartbeat every 20s → refreshes TTL → key survives
// No heartbeat for 60s → key expires → user appears offline
// GET presence:{user_id} → "ONLINE" (if key exists) | nil (offline)

🔬D — Deep Dive10–15 min

1. Snowflake IDs — Why Database Auto-Increment Doesn't Work Here

With 40B messages/day across many Cassandra nodes, a central auto-increment ID has a single point of failure and a write bottleneck. Snowflake IDs are distributed ID generation that gives you:

  • Global uniqueness: datacenter + machine bits prevent collision across all servers
  • Time-sortable: 41-bit millisecond timestamp prefix → IDs sort naturally by time → ORDER BY message_id = correct message ordering
  • No coordination needed: each server generates its own IDs without talking to a central service (epoch + machine_id makes them unique)

2. The Read Receipt Scale Problem

Naive approach: when each of 250 members reads a message → INSERT into message_receipts → query COUNT(*) on every render. Problems:

  • 250 receipt writes per group message × 465K group msg/sec = 116M writes/sec to Cassandra
  • COUNT(*) query on every message render = thousands of Cassandra reads per second per active conversation

Solution — two-layer design:

  1. Maintain seen_count COUNTER on the messages table. Atomically incremented per read. SELECT seen_count is a single column read — O(1).
  2. Full receipt list (who exactly saw it) in separate message_receipts table. Only queried when user taps "Seen by 43".
  3. Batch receipt writes: client sends { message_ids_read: [1,2,3,...] } every 5 seconds, not on each individual read. Reduces write throughput 5×.

3. Presence — Why Not Push to All Friends?

When a user comes online, why not push their "online" status to all 500 friends immediately? The math kills this:

// Naive push-to-all approach:
// 150M users × avg 500 friends × 1 status change every 30 min
// = 150M × 500 / 1800 = 41.7M push events per second
// For a "nice-to-have" feature (green dot), this is unacceptable.

// Solution: Lazy pull
// Friends only check presence when they open a conversation.
// GET presence:{user_id} from Redis → O(1), sub-ms.
// If 5M users are actively chatting, they each make maybe 10 presence
// checks per minute = 50M Redis reads/minute = trivially small.
// Redis can handle 1M+ reads/sec on a single node.

4. Message Search with Elasticsearch

Full-text search in Cassandra is not possible — it's a columnar store, not an inverted index. Architecture:

  • Messages written to Cassandra → change data capture → Debezium streams inserts to Kafka → Elasticsearch consumer indexes each message with conversation_id as a filter field
  • Search query: GET /search?q=birthday party&conversation_id=xxx → Elasticsearch full-text search filtered by conversation_id
  • Privacy: Elasticsearch access is authenticated and checked against conversation_members — you can only search conversations you're in
  • E2E encrypted messages: cannot be indexed or searched server-side. Search is disabled for encrypted conversations (WhatsApp limitation)

⚠️E — Evaluate5 min

Failure Modes & Mitigations

  • Hot Cassandra partition: One very active group (250 members, high-frequency) generates many messages in one month → hot (conversation_id, bucket_month) partition. Mitigation: smaller time buckets (weekly instead of monthly) for active conversations; monitor partition size and alert.
  • WebSocket server goes down: 50K connections drop. Users reconnect within seconds (client retry logic). The message_id of their last received message is stored client-side. On reconnect, they fetch missed messages via REST pagination: GET /messages?after_message_id={last_id}. Durability guaranteed — messages are in Cassandra.
  • Fan-out worker bottleneck: One conversation (250 members all online) sends 100 messages/second = 25K fan-out ops/sec for one conversation. Kafka partitioning by conversation_id means one partition handles this. Mitigation: partition key = hash(conversation_id) % num_partitions with num_partitions > max_workers to allow scaling.
  • Presence false-positive: A user's phone loses network silently (no disconnect event). The Redis TTL of 60s means they appear online for up to 60s after going offline. Mitigation: on WebSocket disconnect event, proactively delete the Redis key (but rely on TTL as safety net for silent disconnects).
  • Race condition in seen_count: 250 users read simultaneously → 250 concurrent increments. Mitigation: Cassandra counters are CRDTs — designed for concurrent increment, eventually consistent. Slight undercount during high concurrency is acceptable (counter will converge).

✅D — Deliver2 min

📣 Your Closing Statement (memorize this structure):

Facebook Messenger = 3 subsystems: (1) Message Delivery: Kafka-backed WebSocket fan-out, Cassandra for message storage (partitioned by conversation+month), Snowflake IDs for ordering. Write to Cassandra first (durability), then push — message is never lost. (2) Group Fan-out: push to online members immediately via parallel fan-out workers; batch read receipts (seen_count COUNTER for display + receipt table for detail, batched writes every 5s). (3) Presence: Redis TTL heartbeat (SETEX 60s), lazy pull by friends on conversation open — avoids 150M × 500 friends push storm. The hardest part is group fan-out at 250 members × 465K group msgs/sec = 116M fan-out ops/sec — Kafka parallelism + targeted WebSocket routing by (user_id → ws_server_id) in Redis makes this tractable.

⚖️Trade-offsKey decisions

DecisionOption AOption BWinner & Why
Message storage MySQL (relational, joins) Cassandra (wide column, time-series) ✅ Cassandra — 40TB/day write throughput; time-range queries (load last 50 messages) are natural
Message ordering DB auto-increment ID (single bottleneck) Snowflake ID (distributed, time-sortable) ✅ Snowflake — no single point of failure, globally unique, natural sort order by time

Message search Cassandra ALLOW FILTERING (no index) Elasticsearch with conversation_id filter ✅ Elasticsearch — inverted index purpose-built for text search; Cassandra cannot do full-text

☕Java Implementation

/**
 * SnowflakeIdGenerator — distributed time-sortable unique ID generator.
 *
 * Bit layout of the 64-bit long:
 *   [63]     sign bit — always 0 (positive)
 *   [62–22]  41 bits — milliseconds since custom epoch (2021-01-01)
 *   [21–17]   5 bits — datacenter ID (0–31)
 *   [16–12]   5 bits — machine ID (0–31)
 *   [11–0]   12 bits — sequence number per millisecond (0–4095)
 *
 * Why this layout?
 * - 41-bit timestamp = ~69 years of IDs before overflow
 * - 5+5 bits for datacenter+machine = 1024 unique generators
 * - 12-bit sequence = 4096 IDs per millisecond per machine = 4M/sec max
 * - Total: 32 × 32 × 4096 = ~4.3B IDs/millisecond system-wide
 *
 * The ID naturally sorts by time because the timestamp occupies the
 * most significant bits. ORDER BY message_id = ORDER BY created_at.
 */
public class SnowflakeIdGenerator {
    private static final long EPOCH_MS = 1609459200000L; // 2021-01-01 00:00:00 UTC

    private static final long DATACENTER_ID_BITS = 5L;
    private static final long MACHINE_ID_BITS    = 5L;
    private static final long SEQUENCE_BITS      = 12L;

    private static final long MAX_DATACENTER_ID = (1L << DATACENTER_ID_BITS) - 1; // 31
    private static final long MAX_MACHINE_ID    = (1L << MACHINE_ID_BITS) - 1;    // 31
    private static final long SEQUENCE_MASK     = (1L << SEQUENCE_BITS) - 1;      // 4095

    private static final long MACHINE_SHIFT    = SEQUENCE_BITS;
    private static final long DATACENTER_SHIFT = SEQUENCE_BITS + MACHINE_ID_BITS;
    private static final long TIMESTAMP_SHIFT  = SEQUENCE_BITS + MACHINE_ID_BITS + DATACENTER_ID_BITS;

    private final long datacenterId;
    private final long machineId;
    private long lastTimestampMs = -1L;
    private long sequence        = 0L;

    public SnowflakeIdGenerator(long datacenterId, long machineId) {
        if (datacenterId > MAX_DATACENTER_ID || datacenterId < 0) {
            throw new IllegalArgumentException("datacenterId must be 0–31, got: " + datacenterId);
        }
        if (machineId > MAX_MACHINE_ID || machineId < 0) {
            throw new IllegalArgumentException("machineId must be 0–31, got: " + machineId);
        }
        this.datacenterId = datacenterId;
        this.machineId    = machineId;
    }

    /**
     * Generates the next Snowflake ID.
     * Synchronized to prevent race conditions within one JVM instance.
     * At peak (4096 IDs/ms), spins until next millisecond — brief and bounded.
     */
    public synchronized long nextId() {
        long currentMs = System.currentTimeMillis();

        if (currentMs == lastTimestampMs) {
            sequence = (sequence + 1) & SEQUENCE_MASK;
            if (sequence == 0L) {
                // All 4096 sequence slots used this millisecond — wait for next
                currentMs = waitForNextMillisecond(lastTimestampMs);
            }
        } else {
            sequence = 0L; // new millisecond — reset sequence
        }

        if (currentMs < lastTimestampMs) {
            // Clock moved backwards (NTP adjustment) — throw rather than generate duplicate
            throw new IllegalStateException(
                "Clock moved backwards. Refusing to generate ID for " +
                (lastTimestampMs - currentMs) + " ms."
            );
        }

        lastTimestampMs = currentMs;

        return ((currentMs - EPOCH_MS) << TIMESTAMP_SHIFT)
             | (datacenterId << DATACENTER_SHIFT)
             | (machineId    << MACHINE_SHIFT)
             | sequence;
    }

    private long waitForNextMillisecond(long lastMs) {
        long currentMs = System.currentTimeMillis();
        while (currentMs <= lastMs) {
            currentMs = System.currentTimeMillis();
        }
        return currentMs;
    }
}

/**
 * PresenceService — Redis TTL-based online/offline tracking.
 *
 * Protocol:
 *   - Client sends WebSocket HEARTBEAT every 20 seconds
 *   - Server calls refreshPresence(userId) → SETEX key 60 seconds
 *   - If no heartbeat for 60s, key expires → user is OFFLINE
 *   - On explicit disconnect: delete key immediately for faster offline detection
 *
 * Why TTL=60, heartbeat=20?
 *   - 20s heartbeat interval gives 3 missed heartbeats before TTL expires
 *   - Tolerates brief network interruptions (elevator, tunnel) without false offline
 *   - 60s is the max time a friend appears "online" after actual disconnect
 *   - Most messaging apps: Slack 30s, WhatsApp 30s, Messenger ~60s
 */
public class PresenceService {
    private static final int PRESENCE_TTL_SECONDS   = 60;
    private static final String PRESENCE_KEY_PREFIX = "presence:";

    private final JedisPool jedisPool;

    public PresenceService(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }

    /**
     * Called on each HEARTBEAT WebSocket message from the client.
     * Refreshes (or creates) the presence key with a fresh 60-second TTL.
     */
    public void refreshPresence(long userId) {
        String key = buildPresenceKey(userId);
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.setex(key, PRESENCE_TTL_SECONDS, "ONLINE");
        }
    }

    /**
     * Called on explicit WebSocket disconnect event.
     * Deletes key immediately — friend sees OFFLINE without waiting for TTL.
     * TTL expiry remains as a safety net for silent disconnects.
     */
    public void markOffline(long userId) {
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.del(buildPresenceKey(userId));
        }
    }

    /**
     * Returns the presence status for a user.
     * Called lazily when a friend opens a conversation (NOT proactively pushed).
     * O(1) Redis GET — sub-millisecond.
     *
     * @return ONLINE if key exists, OFFLINE if key is absent or expired
     */
    public PresenceStatus getPresence(long userId) {
        try (Jedis jedis = jedisPool.getResource()) {
            String status = jedis.get(buildPresenceKey(userId));
            return status != null ? PresenceStatus.ONLINE : PresenceStatus.OFFLINE;
        }
    }

    /**
     * Bulk presence check for all members of a group conversation.
     * Used by the fan-out worker to decide: WebSocket push vs APNS/FCM.
     * Uses Redis MGET for O(1) network round-trip regardless of group size.
     */
    public Map<Long, PresenceStatus> getBulkPresence(List<Long> userIds) {
        String[] keys = userIds.stream()
            .map(this::buildPresenceKey)
            .toArray(String[]::new);

        Map<Long, PresenceStatus> result = new HashMap<>();
        try (Jedis jedis = jedisPool.getResource()) {
            List<String> values = jedis.mget(keys);
            for (int i = 0; i < userIds.size(); i++) {
                result.put(userIds.get(i),
                    values.get(i) != null ? PresenceStatus.ONLINE : PresenceStatus.OFFLINE);
            }
        }
        return result;
    }

    private String buildPresenceKey(long userId) {
        return PRESENCE_KEY_PREFIX + userId;
    }

    public enum PresenceStatus { ONLINE, OFFLINE }
}

/**
 * MessageFanoutService — delivers a message to all members of a conversation.
 *
 * Flow:
 *   1. Load conversation members from MySQL (cached in local memory, TTL 5min)
 *   2. Bulk-check presence for all members via Redis MGET (one round-trip)
 *   3. For ONLINE members: look up their WS server from Redis, push message
 *   4. For OFFLINE members: send APNS/FCM push notification
 *
 * The scary number: 250 members × 465K group msg/sec = 116M operations/sec.
 * Solution: many parallel MessageFanoutService instances, each processing
 * a subset of Kafka partitions. Kafka partition key = conversation_id → all
 * messages for one conversation go to the same partition/consumer instance,
 * guaranteeing ordering per conversation.
 */
public class MessageFanoutService {
    private final PresenceService presenceService;
    private final WebSocketRouter webSocketRouter;
    private final PushNotificationService pushNotificationService;
    private final ConversationMemberCache memberCache; // local cache, TTL 5min

    public MessageFanoutService(
        PresenceService presenceService,
        WebSocketRouter webSocketRouter,
        PushNotificationService pushNotificationService,
        ConversationMemberCache memberCache
    ) {
        this.presenceService       = presenceService;
        this.webSocketRouter       = webSocketRouter;
        this.pushNotificationService = pushNotificationService;
        this.memberCache           = memberCache;
    }

    /**
     * Fans out a message to all conversation members.
     * Called by Kafka consumer on each message event.
     *
     * @param message the persisted message to deliver
     */
    public void fanOut(Message message) {
        List<Long> memberUserIds = memberCache.getMembers(message.getConversationId());

        // Exclude the sender — they already see their own message optimistically
        List<Long> recipientIds = memberUserIds.stream()
            .filter(userId -> userId != message.getSenderId())
            .collect(java.util.stream.Collectors.toList());

        // One Redis MGET round-trip for all presence checks (not N individual GETs)
        Map<Long, PresenceService.PresenceStatus> presenceMap =
            presenceService.getBulkPresence(recipientIds);

        for (long recipientId : recipientIds) {
            if (presenceMap.get(recipientId) == PresenceService.PresenceStatus.ONLINE) {
                // Real-time delivery via WebSocket
                webSocketRouter.pushMessageToUser(recipientId, message);
            } else {
                // Offline — send push notification to wake the app
                pushNotificationService.sendPushNotification(recipientId, message);
            }
        }
    }
}
