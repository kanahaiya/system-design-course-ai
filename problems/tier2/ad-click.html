Tier 2 — Should Know 45 min Stream processing Exactly-once

Design Ad Click Aggregator

Ad systems generate 10 billion click events daily. The hard part is not counting clicks — it is counting them exactly once. Billing accuracy requires exactly-once semantics. Fraud prevention requires real-time deduplication. Reporting latency must be under 1 minute. This is why Kafka transactions, Flink checkpoints, and Lambda architecture exist.

🏢 Google, Meta, Twitter, Amazon
⏱️ 45 min interview
📊 10B clicks/day, 115K/sec

❓ R — Requirements 3–5 min

💡
L6 Opening Move — Clarify the Billing Constraint Immediately
Before designing anything, ask: "Are these click counts used for billing advertisers?" If yes, the entire architecture shifts. An approximate count (Bloom filter, HyperLogLog) is not acceptable for financial reporting. You need exactly-once semantics — and that forces specific choices in Kafka, Flink, and your reconciliation layer. Most candidates never ask this. Asking it signals senior engineering judgment.

Functional Requirements

  • Ingest click events from ad servers: {click_id, ad_id, campaign_id, user_id, timestamp, ip_address, user_agent, page_url, device_type}
  • Deduplicate clicks: same click_id arriving multiple times (Kafka at-least-once) must be counted exactly once
  • Deduplicate fraudulent double-clicks: same (user_id, ad_id) within a 5-minute window counts as one click
  • Aggregate click counts per ad per time window: 1-minute, 1-hour, 1-day granularity
  • Query API: "how many clicks did ad X get between 14:00 and 15:00?"
  • Top-N ads by click count in a given time window
  • Real-time fraud detection: flag ads with abnormal click rates (bot traffic)
  • Billing report: exact click counts per campaign per day (used to charge advertisers)

Non-Functional Requirements

  • Scale: 10B clicks/day = ~115K clicks/sec average; 500K/sec peak (during Black Friday, viral campaigns)
  • Impressions: 100B impressions/day (click-through rate ~10%); 1M active ad campaigns
  • Reporting latency: Aggregations visible within <1 minute of click event (near-real-time dashboard)
  • Billing accuracy: Exact counts — zero tolerance for over-billing or under-billing advertisers
  • Availability: Click ingestion at 99.99% (missing clicks = lost revenue); reporting at 99.9%
  • Durability: No click event may be permanently lost — Kafka retention 7 days, archive to S3 forever
  • Fraud tolerance: Bot detection must run in <5 seconds of click arrival to block invalid clicks in near-real-time

Out of Scope

  • Ad serving and targeting (which ad to show)
  • Impression tracking (separate pipeline, similar design)
  • User identity resolution (cross-device tracking)

🔢 E — Estimation 3–5 min

Throughput

  • Click events: 10B/day ÷ 86,400 sec = ~115K clicks/sec average
  • Peak: 4× average = ~500K clicks/sec (holiday sales, viral events)
  • Kafka partitions needed: 500K clicks/sec ÷ 5K events/sec/partition = 100 partitions

Storage

  • Raw click events (Kafka, 7-day retention): 10B/day × 200 bytes/click = 2TB/day raw → 14TB in Kafka ring. Compressed ~5×: 2.8TB in Kafka.
  • Raw archive (S3, forever): 2TB/day × 365 = 730TB/year. Use Parquet + Snappy: 200GB/day. Cost: ~$5/TB/month on S3 → ~$1K/month at steady state.
  • Aggregated counts (ClickHouse): 1M ads × 1,440 min/day × 16 bytes/row = ~23GB/day. 365 days = 8TB/year. With compression (5×): 1.6TB/year — trivial to store.
  • Dedup index (Redis): Per-click dedup: 10B click_ids/day at 36 bytes UUID = 360GB if stored naively. We use a Bloom filter: 10B elements at 0.01% false positive = ~20GB Bloom filter per day window. Far too large — we use 5-minute windows instead (see Deep Dive).

Deduplication Window Math

  • 5-minute dedup window: 115K clicks/sec × 300 sec = 34.5M unique click events in-flight
  • Bloom filter (0.1% FP): 34.5M elements → m = -n×ln(p)/ln(2)² = ~470M bits = ~59MB per 5-min window
  • Redis SET (exact): 34.5M keys × 64 bytes = 2.2GB RAM. Bloom filter is 37× more memory-efficient at the cost of 0.1% false positive rate.
  • Flink checkpoint state per operator: ~100MB per task manager node (state = in-progress window counts + dedup filters).

Bandwidth

  • Ingest API: 500K clicks/sec × 200 bytes = 100MB/sec inbound → needs 1Gbps NIC on load balancers
  • Kafka replication (3× factor): 100MB/sec × 3 = 300MB/sec internal cluster traffic
  • ClickHouse query layer: p99 query scans 1M rows → 16MB → <50ms response with columnar storage

-- ReplicatedSummingMergeTree: automatically sums click_count on merge.
-- Enables idempotent upserts: Flink can write the same window row twice
-- (after crash recovery) and ClickHouse will sum correctly.
CREATE TABLE ad_click_aggregations (
    ad_id          String,
    campaign_id    String,
    window_start   DateTime,          -- truncated to minute
    window_end     DateTime,
    click_count    UInt64,
    unique_users   UInt64,            -- HyperLogLog approximation (±2%)

) ENGINE = ReplicatedSummingMergeTree('/clickhouse/tables/{shard}/ad_click_agg', '{replica}')
PARTITION BY toYYYYMM(window_start)   -- monthly partitions for TTL management
ORDER BY (ad_id, window_start)        -- cluster key: all windows for one ad are contiguous
TTL window_start + INTERVAL 2 YEAR;  -- auto-delete data older than 2 years

🏗️ H — High-level Design 10 min

Full Pipeline Architecture

Component Responsibilities

1. Click Ingestion API (stateless, horizontal scaling)

Lightweight HTTP service running on every ad server. Responsibilities: (a) validate the click schema, (b) attach server-side timestamp as ingest_time for watermark debugging, (c) publish to Kafka using the idempotent producer API (prevents duplicate Kafka messages on producer retry). Returns HTTP 200 immediately — fire-and-forget. The API never waits for aggregation.

💡
Why idempotent producer matters here
Without enable.idempotence=true, a producer retry (after a network blip) can write the same click event twice to Kafka. This is Kafka's at-least-once guarantee. With idempotent producers, Kafka assigns each record a producer ID + sequence number. If the broker receives the same sequence number twice, it deduplicates at the broker level. This is the first dedup layer — before even reaching Flink.

2. Kafka (durable event bus)

Partitioned by ad_id. This is a deliberate choice: all clicks for the same ad land on the same partition, which means a single Flink operator instance handles all clicks for that ad — no cross-partition joins or coordination needed for per-ad aggregation. Retention: 7 days. Every Kafka message is simultaneously mirrored to S3 via the Kafka S3 sink connector for the batch layer.

3. Flink Stream Processor (the heart of the system)

  • Deduplication: Check click_id against Redis Bloom filter. If present, discard. If absent, add and count.
  • Windowed aggregation: TumblingEventTimeWindows of 1 minute, keyed by (ad_id, campaign_id). Counts clicks per window.
  • Watermarks: Allow up to 5 minutes of late event arrival (mobile clicks on spotty connections). Events arriving after the watermark deadline go to a side output for batch reprocessing.
  • Checkpointing: Every 30 seconds. State (in-progress window counts + Bloom filter) is snapshotted to S3. On crash, Flink restores to the last checkpoint — guaranteeing exactly-once processing of every click.
  • Output: Writes to ClickHouse (SummingMergeTree handles idempotent duplicate writes) and updates Redis sorted sets for Top-N.

4. ClickHouse (real-time analytical store)

Columnar OLAP database optimized for aggregation queries over time ranges. A query like "total clicks for campaign X in the last 24 hours" scans only two columns (campaign_id, click_count) across 1,440 rows — sub-millisecond. ReplicatedSummingMergeTree engine automatically sums click_count on merge operations, making Flink's idempotent writes safe.

5. Batch Reconciliation Layer (Spark, nightly)

Reads raw Parquet files from S3. Performs exact deduplication using SQL COUNT(DISTINCT click_id). Writes exact counts back to ClickHouse with is_reconciled=1. This is the source of truth for billing. Advertisers are charged based on batch counts, not stream counts.

⚠️
The billing requirement changes everything
An approximate count is not acceptable for charging advertisers. If your Bloom filter has a 0.1% false-positive rate and you process 10B clicks/day, you're under-counting by 10M clicks — potentially millions of dollars in lost revenue or inaccurate invoices. This is why we maintain two separate pipelines: the stream pipeline for speed (dashboards, real-time bidding decisions) and the batch pipeline for accuracy (billing). This dual architecture is not over-engineering — it is the industry-standard Lambda architecture for exactly this reason.

6. Reporting API

Read-only service. Routes time-range queries to ClickHouse. Routes Top-N queries to Redis sorted sets (sub-millisecond). Applies cache-control headers — dashboard widgets poll every 30 seconds, so query results are cached in Varnish for 30 seconds to prevent thundering-herd against ClickHouse.

7. Fraud Detection (parallel stream)

Flink sends a copy of every raw click to a parallel fraud detection job. This job maintains a 5-minute sliding window per (ip_address, user_agent). If click rate exceeds 10 clicks/5-min from the same IP to the same ad, the clicks are flagged as suspicious and sent to a human review queue. Invalid clicks are excluded from billing.

🔬 D — Deep Dive 10 min

1. Exactly-Once Semantics: The Full Picture

Achieving exactly-once processing requires coordination at three layers. Miss any layer and you either over-count or under-count.

LayerFailure mode without protectionSolutionMechanism
Kafka Producer Network timeout causes producer to retry → duplicate message in Kafka Idempotent producer enable.idempotence=true: broker assigns producer ID + sequence number. Duplicate sequence → discard.
Flink Processing Flink crashes mid-window → partial counts lost or duplicated Checkpointing + at-least-once consumer, exactly-once via state Flink snapshots window state + Kafka consumer offsets atomically every 30s. On restart, replays from last checkpoint offset. Window state ensures no double-counting.
Flink → ClickHouse Write Flink writes window result, then crashes before committing Kafka offset → same window written twice on restart Idempotent sink (SummingMergeTree) ClickHouse SummingMergeTree sums on merge. If Flink writes the same (ad_id, window_start) row twice, ClickHouse sums both values. Flink must write incremental deltas (not cumulative totals) for this to work correctly.
Kafka Transactions (alternative) Cross-topic writes need atomic commit Kafka transactional API initTransactions(), beginTransaction(), write to output topic + commit consumer offset atomically. If broker fails, transaction is aborted — consumer sees no partial state. Flink's Kafka sink uses this internally when semantic=EXACTLY_ONCE.
⚠️
What happens when Flink crashes mid-window?
Scenario: Flink is 45 seconds into aggregating a 1-minute window for ad_X when it crashes. It has counted 8,400 clicks. On restart, it reads its last checkpoint (taken 30 seconds ago), which has 6,200 clicks for that window. It resets Kafka offset to the checkpoint offset and replays the last 15 seconds of events. The final window total is correct — no events are missed, no events are double-counted. This is Flink's core value proposition: stateful exactly-once stream processing with millisecond-granularity checkpointing.

2. Window Types and When to Use Each

Window TypeDescriptionUse Case in Ad SystemMemory Cost
Tumbling (fixed) Non-overlapping, fixed-size buckets. 00:00–01:00, 01:00–02:00. Each event belongs to exactly one window. Billing aggregation (clicks per minute), dashboard charts, storage in ClickHouse Low — one window state per key at a time
Sliding (hopping) Overlapping windows. "Last 5 minutes" = new window every 1 minute, each 5 minutes wide. One event belongs to up to 5 windows. Fraud detection (clicks per 5 minutes, updated every minute), real-time anomaly dashboards Higher — slide/hop_size windows active per key. 5 windows × state = 5× memory vs tumbling.
Session Gap-based. Window closes when no events arrive for X minutes. Variable size. User engagement sessions (not click counting per se), A/B test session analysis Variable — state grows until gap is detected
Global Unbounded — never closes. Triggered manually. Running total campaign click count (for budget cap checks) Grows indefinitely — use only with manual triggers

3. Flink Watermarks and Late Event Handling

Flink uses event time (the timestamp embedded in the click event) not processing time (when Flink receives it). This is critical: a click on a mobile app may be generated at 14:00:30 but only reach Kafka at 14:05:45 due to spotty connectivity. If we used processing time, this click would be counted in the wrong minute.

Watermarks tell Flink "I'm confident all events up to time T have arrived." Flink closes and emits a window when the watermark passes the window's end time. A 5-minute watermark delay means Flink waits 5 extra minutes before closing each 1-minute tumbling window, accommodating network delays. Events arriving after the watermark (more than 5 minutes late) go to a side output for separate batch reprocessing.

// Flink watermark strategy: allow up to 5 minutes of late events
WatermarkStrategy<ClickEvent> watermarkStrategy = WatermarkStrategy
    .<ClickEvent>forBoundedOutOfOrderness(Duration.ofMinutes(5))
    .withTimestampAssigner((clickEvent, recordTimestamp) -> clickEvent.getEventTime());

// Side output for events arriving more than 5 minutes late
OutputTag<ClickEvent> lateEventsTag = new OutputTag<>("late-clicks") {};

// Late events → separate Kafka topic → batch reprocessing picks them up nightly
SingleOutputStreamOperator<ClickAggregation> mainStream = clickStream
    .assignTimestampsAndWatermarks(watermarkStrategy)
    .keyBy(click -> new Tuple2<>(click.getAdId(), click.getCampaignId()))
    .window(TumblingEventTimeWindows.of(Time.minutes(1)))
    .allowedLateness(Duration.ofMinutes(5))  // reopen closed window for late events
    .sideOutputLateData(lateEventsTag)
    .aggregate(new ClickCountAggregator());

DataStream<ClickEvent> lateEvents = mainStream.getSideOutput(lateEventsTag);

4. Click Deduplication: Three Layers

Deduplication happens at multiple layers because no single mechanism is sufficient at this scale.

Layer 1 — Kafka Idempotent Producer (infrastructure-level)

Prevents the same click event from being written to Kafka twice due to producer retries. Zero application-level cost. Enabled with enable.idempotence=true. This handles the "network retry duplicate" case.

Layer 2 — Redis Bloom Filter (near-real-time, probabilistic)

For deduplicating the same click_id that arrives from multiple sources (e.g., click was recorded by two different ad servers simultaneously). Key insight: a Bloom filter never has false negatives. If a click_id is a genuine duplicate, the Bloom filter will always catch it. The 0.1% false positive rate means 1 in 1,000 genuine new clicks might be incorrectly flagged as duplicates — acceptable for real-time dashboards, not for billing.

// Redis RedisBloom module — BF.ADD returns 1 if new, 0 if already seen
// Window: 5 minutes (one Bloom filter per 5-minute bucket, TTL=6 min)
private boolean isNewClick(String clickId, long eventTimeMs) {
    long bucketKey = eventTimeMs / (5 * 60 * 1000L);  // 5-min bucket
    String redisKey = "dedup:" + bucketKey;
    // BF.ADD returns 1 if added (new click), 0 if already present (duplicate)
    Long addResult = redisBloomCommands.bfAdd(redisKey, clickId);
    return addResult != null && addResult == 1L;
}

Layer 3 — Batch Exact Dedup (billing-grade)

Nightly Spark job on S3 Parquet files. Uses SQL SELECT ad_id, campaign_id, date, COUNT(DISTINCT click_id) AS exact_click_count. Exact deduplication using shuffle-based GROUP BY. Slow (hours), but 100% accurate. This is the number that appears on the advertiser's invoice.

5. Lambda Architecture vs Kappa Architecture

💡
Why Kappa is now preferred at most companies — but we still use Lambda here
Kappa architecture eliminates the batch layer entirely. Historical reprocessing is done by replaying Kafka (or archived events) through the same stream processor. This is operationally simpler — one codebase, one pipeline to monitor. Companies like LinkedIn and Confluent advocate Kappa. However, for ad billing specifically, the regulatory and financial audit requirements make a separate, human-auditable batch pipeline easier to certify. The exact Spark SQL that produces billing numbers is simpler to audit than "what did our Flink checkpoints contain at 2AM?"

6. Hot Ad Problem: Skewed Partitions

A viral ad or a major brand campaign can receive 1M clicks per minute — 100× the average. Because we partition by ad_id, one Kafka partition receives all these clicks. That partition's Flink operator becomes a bottleneck. One operator processing 100K events/sec while all others process 1K events/sec.

Solution: Two-phase aggregation (map-reduce for streams)

// Phase 1: Add random suffix to ad_id for sharding (map phase)

// Kafka partition key becomes the sharded ad_id

// Phase 2: Aggregate per shard (partial aggregation in stream)

7. Click Fraud Detection

Click fraud costs the digital ad industry ~$100B annually. The system must detect and exclude fraudulent clicks before billing. Real-time detection (within 5 seconds) prevents billing advertisers for bot traffic.

Signal types:

  • IP-based rate: More than 20 clicks/5-min from the same IP to the same ad → bot. Use Flink sliding window keyed by (ip_address, ad_id).
  • User agent: Headless browser signatures (HeadlessChrome, PhantomJS) → immediate rejection before Kafka publish.
  • Abnormal CTR: An ad with 0.1% normal CTR suddenly seeing 15% CTR → campaign-level anomaly. Compared against historical baseline using a 7-day rolling average.
  • Click timing patterns: Regular interval clicks (every 3.7 seconds exactly) → bot. Humans click irregularly. Detect using coefficient of variation of inter-click intervals.
  • Geographic impossibility: Same user_id clicking from New York and Tokyo within 10 minutes → account compromise or bot.
// Flink fraud detection: 5-minute sliding window, 1-minute slide
// Keyed by (ip_address, ad_id) to detect IP-level click stuffing
DataStream<FraudAlert> fraudAlerts = clickStream
    .keyBy(click -> click.getIpAddress() + "|" + click.getAdId())
    .window(SlidingEventTimeWindows.of(Time.minutes(5), Time.minutes(1)))
    .process(new FraudDetectionProcessWindowFunction());

// In FraudDetectionProcessWindowFunction:
// - Count clicks in window
// - If count > IP_CLICK_THRESHOLD (20): emit FraudAlert
// - Compute inter-click interval variance — low variance = bot
// - Emit to fraud-alerts Kafka topic for human review + billing exclusion

8. Why ClickHouse Over PostgreSQL / Cassandra

A query like "sum of clicks for campaign X across all ads, grouped by hour, over the last 30 days" touches 43,200 rows and needs to aggregate across many ad IDs. This is an analytical query pattern, not a transactional one.

  • PostgreSQL: Row-oriented. To compute SUM(click_count), it reads entire rows including all columns. At 43,200 rows × 200 bytes/row = 8.6MB of I/O for a query that only needs 2 columns. Also lacks pre-aggregation materialized views at ClickHouse's scale.
  • Cassandra: Excellent for high-write, key-value reads. Not designed for ad-hoc range scans across millions of rows. Would require materialized views per query shape — operationally expensive.
  • ClickHouse: Columnar. Same query reads only click_count and window_start columns — 43,200 × 16 bytes = 691KB of I/O. 12× less I/O. Additionally, SummingMergeTree pre-aggregates in the background — many queries complete in single-digit milliseconds.
  • Apache Druid: Also columnar, OLAP-optimized. Better at sub-second queries on streaming data (native Kafka ingestion). Better UI ecosystem. Higher operational complexity. Good alternative to ClickHouse for real-time analytics.
  • Apache Pinot: LinkedIn's choice. Designed for user-facing analytics (direct query from end-users). Very low p99 latency. Supports upserts natively. Good when advertisers query their own dashboards directly.

✅ E — Evaluate 3 min

Failure Modes and Mitigations

  • Flink job failure: Checkpoint restores in ~2 minutes. Kafka consumer lag accumulates but is bounded. No data loss. Duplicate prevention via checkpoint + idempotent ClickHouse sink.
  • ClickHouse node failure: Replication factor=2. Read from replica. Background replication catches up. <1s write latency impact.
  • Redis failure: Bloom filter is best-effort. On Redis failure, Flink can bypass dedup (slightly over-count) or fail-closed (drop all clicks until Redis recovers). Policy decision for product team: fail-open is safer for revenue.
  • Kafka partition leader failure: Controller re-election takes ~30 seconds. During this window, producers buffer (at-most 30 seconds of data in producer buffer). After re-election, all buffered events publish. Zero data loss.
  • S3 unavailability: Kafka S3 sink connector buffers in memory / local disk. S3 writes are eventually consistent — no data loss as long as Kafka retains the messages (7-day window).

🚀 D — Deliver 2 min

We designed an ad click aggregator handling 10B clicks/day with two distinct accuracy tiers:

  • Real-time tier (stream): Kafka (100 partitions, keyed by ad_id) → Flink (1-min tumbling windows, 5-min watermark tolerance, Redis Bloom filter dedup) → ClickHouse (columnar, SummingMergeTree). Latency: <6 minutes. Accuracy: ~99.9% (0.1% Bloom filter false positive). Used for: advertiser dashboards, real-time bidding decisions, fraud alerting.
  • Batch tier (billing): Kafka → S3 Parquet archive → nightly Spark batch (exact COUNT DISTINCT) → ClickHouse (is_reconciled=true). Latency: 24 hours. Accuracy: 100% (exact). Used for: advertiser billing, regulatory compliance, revenue recognition.

Key architectural decisions: (1) Partition by ad_id for stateful aggregation locality; (2) Lambda architecture because billing correctness overrides operational simplicity; (3) Three-layer deduplication (Kafka idempotent → Bloom filter → batch exact); (4) Two-phase aggregation for hot ads; (5) ClickHouse SummingMergeTree for safe idempotent stream writes.

What this code demonstrates

Main Flink Job

/**
 * AdClickAggregationJob — main Flink streaming job.
 *
 * Pipeline:
 *   Kafka source (ClickEvent, Avro)
 *   → deduplicate via Redis Bloom filter
 *   → keyBy (adId, campaignId)
 *   → TumblingEventTimeWindows(1 minute)
 *   → aggregate click counts + HyperLogLog unique users
 *   → sink to ClickHouse + Redis sorted set for Top-N
 *
 * Exactly-once guarantee:
 *   Kafka source: reads committed offsets (checkpoint-aligned)
 *   Bloom filter: stored in Flink operator state — checkpointed with job
 *   ClickHouse sink: SummingMergeTree handles idempotent duplicate writes
 *   Checkpoint interval: 30 seconds to S3
 */
public class AdClickAggregationJob {

    private static final String KAFKA_BOOTSTRAP_SERVERS = "kafka:9092";
    private static final String KAFKA_TOPIC = "ad-clicks-raw";
    private static final String KAFKA_CONSUMER_GROUP = "flink-click-aggregator";
    private static final Duration WATERMARK_DELAY = Duration.ofMinutes(5);
    private static final Duration WINDOW_SIZE = Duration.ofMinutes(1);
    private static final Duration CHECKPOINT_INTERVAL = Duration.ofSeconds(30);

    public static void main(String[] args) throws Exception {
        StreamExecutionEnvironment environment = buildStreamExecutionEnvironment();

        DataStream<ClickEvent> rawClickStream = buildKafkaSource(environment);

        OutputTag<ClickEvent> lateEventsOutputTag =
            new OutputTag<ClickEvent>("late-clicks") {};

        SingleOutputStreamOperator<ClickAggregation> aggregatedStream =
            rawClickStream
                .assignTimestampsAndWatermarks(buildWatermarkStrategy())
                .process(new RedisBloomDeduplicationFunction())
                .keyBy(click -> click.getAdId() + "|" + click.getCampaignId())
                .window(TumblingEventTimeWindows.of(Time.minutes(1)))
                .allowedLateness(Duration.ofMinutes(5))
                .sideOutputLateData(lateEventsOutputTag)
                .aggregate(
                    new ClickCountAggregateFunction(),
                    new ClickAggregationWindowFunction()
                );

        // Main output: write aggregations to ClickHouse
        aggregatedStream.addSink(new ClickHouseSink());

        // Side effect: update Redis Top-N sorted set on each window close
        aggregatedStream.addSink(new RedisTopNSink());

        // Late events: write to separate Kafka topic for batch reprocessing
        aggregatedStream
            .getSideOutput(lateEventsOutputTag)
            .addSink(new KafkaLateEventSink("ad-clicks-late"));

        environment.execute("Ad Click Aggregation Job");
    }

    private static StreamExecutionEnvironment buildStreamExecutionEnvironment() {
        StreamExecutionEnvironment environment =
            StreamExecutionEnvironment.getExecutionEnvironment();

        // Checkpoint every 30 seconds to S3. Exactly-once mode:
        // Flink aligns barriers across all parallel operators before snapshotting.
        environment.enableCheckpointing(
            CHECKPOINT_INTERVAL.toMillis(),
            CheckpointingMode.EXACTLY_ONCE
        );

        CheckpointConfig checkpointConfig = environment.getCheckpointConfig();
        // Keep last 3 checkpoints for recovery (rolling)
        checkpointConfig.setMaxConcurrentCheckpoints(1);
        checkpointConfig.setCheckpointStorage("s3://my-bucket/flink-checkpoints/");
        // Do not discard checkpoints on job cancellation — needed for restart
        checkpointConfig.setExternalizedCheckpointCleanup(
            CheckpointConfig.ExternalizedCheckpointCleanup.RETAIN_ON_CANCELLATION
        );

        return environment;
    }

    private static DataStream<ClickEvent> buildKafkaSource(
        StreamExecutionEnvironment environment
    ) {
        KafkaSource<ClickEvent> kafkaSource = KafkaSource.<ClickEvent>builder()
            .setBootstrapServers(KAFKA_BOOTSTRAP_SERVERS)
            .setTopics(KAFKA_TOPIC)
            .setGroupId(KAFKA_CONSUMER_GROUP)
            // Start from committed offset (checkpoint-aligned);
            // on first run, start from earliest.
            .setStartingOffsets(OffsetsInitializer.committedOffsets(
                OffsetResetStrategy.EARLIEST
            ))
            .setValueOnlyDeserializer(new ClickEventAvroDeserializer())
            .build();

        return environment.fromSource(
            kafkaSource,
            WatermarkStrategy.noWatermarks(),  // watermarks added downstream
            "Kafka Click Source"
        );
    }

    private static WatermarkStrategy<ClickEvent> buildWatermarkStrategy() {
        // Allow events up to 5 minutes late before closing windows.
        // Mobile clicks on spotty connections can arrive significantly delayed.
        return WatermarkStrategy
            .<ClickEvent>forBoundedOutOfOrderness(WATERMARK_DELAY)
            .withTimestampAssigner(
                (clickEvent, recordTimestamp) -> clickEvent.getEventTime()
            )
            // Idle timeout: if a partition receives no events for 30s,
            // advance watermark anyway (prevents other partitions stalling).
            .withIdleness(Duration.ofSeconds(30));
    }
}

Deduplication with Keyed Process Function

/**
 * RedisBloomDeduplicationFunction — Flink ProcessFunction that deduplicates
 * clicks using Redis RedisBloom before they enter the aggregation window.
 *
 * Design choice: Redis (not Flink state) for the Bloom filter because:
 * 1. The dedup window (5 min) is different from the aggregation window (1 min).
 * 2. Flink restarts should not lose the Bloom filter — Redis persists independently.
 * 3. Multiple Flink operator instances share one Bloom filter (same click_id
 *    could arrive on different Kafka partitions if producer used round-robin
 *    for a brief moment during rebalance).
 */
public class RedisBloomDeduplicationFunction
    extends ProcessFunction<ClickEvent, ClickEvent> {

    private static final String REDIS_HOST = "redis-cluster:6379";
    private static final long DEDUP_WINDOW_MINUTES = 5L;
    private static final long DEDUP_TTL_MINUTES = DEDUP_WINDOW_MINUTES + 1L;

    private transient JedisBloomCommands bloomCommands;

    @Override
    public void open(Configuration configuration) {
        JedisPool jedisPool = new JedisPool(REDIS_HOST);
        bloomCommands = new JedisBloom(jedisPool);
    }

    /**
     * Checks click_id against Redis Bloom filter.
     * Emits the event only if it is genuinely new (not a duplicate).
     * Duplicate events are silently dropped — they were already counted.
     */
    @Override
    public void processElement(
        ClickEvent clickEvent,
        Context context,
        Collector<ClickEvent> collector
    ) {
        String bucketKey = buildDedupBucketKey(clickEvent.getEventTime());
        String redisKey = "dedup:" + bucketKey;

        // BF.ADD returns 1 if item is new (added), 0 if already present (duplicate).
        // This is an atomic Redis operation — safe under concurrent access.
        boolean isNewClick = bloomCommands.bfAdd(redisKey, clickEvent.getClickId());

        if (isNewClick) {
            // Set TTL on first use; subsequent BF.ADDs don't reset TTL
            bloomCommands.expire(redisKey, DEDUP_TTL_MINUTES * 60L);
            collector.collect(clickEvent);
        }
        // Duplicates are dropped silently — no output, no error
    }

    /**
     * Computes the 5-minute bucket key for a given event timestamp.
     * All events within the same 5-minute bucket share a Bloom filter.
     * Example: event at 14:03:45 → bucket key "2024-01-15T14:00" (floor to 5-min)
     */
    private String buildDedupBucketKey(long eventTimeMs) {
        long bucketBoundaryMs = (eventTimeMs / (DEDUP_WINDOW_MINUTES * 60_000L))
                                * (DEDUP_WINDOW_MINUTES * 60_000L);
        return new SimpleDateFormat("yyyy-MM-dd'T'HH:mm")
            .format(new Date(bucketBoundaryMs));
    }
}

Aggregation Functions

/**
 * ClickCountAggregateFunction — incremental aggregation function.
 * Flink calls add() for each event in the window. The accumulator
 * holds running totals. getResult() is called once per window close.
 *
 * Using AggregateFunction (incremental) rather than ProcessWindowFunction
 * (buffering all events) because we only need a count — no need to buffer
 * 115K raw click events per window per key in memory.
 */
public class ClickCountAggregateFunction
    implements AggregateFunction<ClickEvent, ClickCountAccumulator, ClickCountAccumulator> {

    @Override
    public ClickCountAccumulator createAccumulator() {
        return new ClickCountAccumulator();
    }

    @Override
    public ClickCountAccumulator add(
        ClickEvent clickEvent,
        ClickCountAccumulator accumulator
    ) {
        accumulator.incrementClickCount();
        // HyperLogLog: approximate unique user count (±2% error, 12KB per counter)
        accumulator.addUserToHyperLogLog(clickEvent.getUserId());
        return accumulator;
    }

    @Override
    public ClickCountAccumulator getResult(ClickCountAccumulator accumulator) {
        return accumulator;
    }

    @Override
    public ClickCountAccumulator merge(
        ClickCountAccumulator first,
        ClickCountAccumulator second
    ) {
        // Merge is called when combining partial results (e.g., session windows,
        // or when re-joining after task failure). Counts are additive;
        // HyperLogLog registers are merged using max-register algorithm.
        first.mergeWith(second);
        return first;
    }
}

/**
 * ClickAggregationWindowFunction — wraps the aggregation result with
 * window timing metadata (window_start, window_end) for ClickHouse.
 * This is called once per window, after ClickCountAggregateFunction.getResult().
 */
public class ClickAggregationWindowFunction
    implements WindowFunction<ClickCountAccumulator, ClickAggregation, String, TimeWindow> {

    @Override
    public void apply(
        String adAndCampaignKey,               // "ad_8f3b2a1c|camp_9d4e1f7a"
        TimeWindow timeWindow,
        Iterable<ClickCountAccumulator> accumulatorIterable,
        Collector<ClickAggregation> collector
    ) {
        ClickCountAccumulator accumulator = accumulatorIterable.iterator().next();
        String[] keyParts = adAndCampaignKey.split("\\|");

        collector.collect(new ClickAggregation(
            keyParts[0],                         // adId
            keyParts[1],                         // campaignId
            timeWindow.getStart(),               // window_start millis
            timeWindow.getEnd(),                 // window_end millis
            accumulator.getClickCount(),
            accumulator.getUniqueUserCount()     // from HyperLogLog
        ));
    }
}

/**
 * Accumulator state for one window.
 * HyperLogLog provides ~2% error on unique user count in 12KB vs exact
 * counting which would require a full HashSet (unbounded memory growth).
 */
public class ClickCountAccumulator {
    private long clickCount = 0L;
    private final HyperLogLog hyperLogLog = new HyperLogLog(0.02);  // 2% error

    public void incrementClickCount() { clickCount++; }

    public void addUserToHyperLogLog(String userId) {
        hyperLogLog.offer(userId);
    }

    public long getClickCount() { return clickCount; }

    public long getUniqueUserCount() { return hyperLogLog.cardinality(); }

    public void mergeWith(ClickCountAccumulator other) {
        this.clickCount += other.clickCount;
        this.hyperLogLog.addAll(other.hyperLogLog);
    }
}

ClickHouse Sink

/**
 * ClickHouseSink — writes ClickAggregation records to ClickHouse.
 *
 * Uses batch inserts (buffer 1,000 rows or 5 seconds, whichever comes first)
 * to minimize round-trips. SummingMergeTree on the ClickHouse side handles
 * idempotent writes: if Flink writes the same (ad_id, window_start) twice
 * (after crash recovery), ClickHouse sums both click_count values.
 * Flink must write incremental deltas (not cumulative totals) for this to work.
 */
public class ClickHouseSink extends RichSinkFunction<ClickAggregation> {

    private static final String CLICKHOUSE_URL = "jdbc:clickhouse://clickhouse:8123/ads";
    private static final int BATCH_SIZE = 1_000;
    private static final long FLUSH_INTERVAL_MS = 5_000L;

    private static final String INSERT_SQL =
        "INSERT INTO ad_click_aggregations " +
        "(ad_id, campaign_id, window_start, window_end, click_count, unique_users) " +
        "VALUES (?, ?, ?, ?, ?, ?)";

    private transient Connection connection;
    private transient PreparedStatement preparedStatement;
    private transient List<ClickAggregation> pendingBatch;
    private transient ScheduledFuture<?> flushSchedule;

    @Override
    public void open(Configuration configuration) throws Exception {
        connection = DriverManager.getConnection(CLICKHOUSE_URL);
        preparedStatement = connection.prepareStatement(INSERT_SQL);
        pendingBatch = new ArrayList<>(BATCH_SIZE);

        ScheduledExecutorService flushExecutor = Executors.newSingleThreadScheduledExecutor();
        flushSchedule = flushExecutor.scheduleAtFixedRate(
            this::flushBatch,
            FLUSH_INTERVAL_MS, FLUSH_INTERVAL_MS, TimeUnit.MILLISECONDS
        );
    }

    @Override
    public void invoke(ClickAggregation aggregation, Context context) throws Exception {
        pendingBatch.add(aggregation);
        if (pendingBatch.size() >= BATCH_SIZE) {
            flushBatch();
        }
    }

    private synchronized void flushBatch() {
        if (pendingBatch.isEmpty()) {
            return;
        }
        try {
            for (ClickAggregation aggregation : pendingBatch) {
                preparedStatement.setString(1, aggregation.getAdId());
                preparedStatement.setString(2, aggregation.getCampaignId());
                preparedStatement.setTimestamp(3, new Timestamp(aggregation.getWindowStartMs()));
                preparedStatement.setTimestamp(4, new Timestamp(aggregation.getWindowEndMs()));
                preparedStatement.setLong(5, aggregation.getClickCount());
                preparedStatement.setLong(6, aggregation.getUniqueUserCount());
                preparedStatement.addBatch();
            }
            preparedStatement.executeBatch();
            pendingBatch.clear();
        } catch (SQLException sqlException) {
            // Log with full context — never swallow silently
            throw new RuntimeException(
                "[ClickHouseSink.flushBatch] Batch insert failed. " +
                "Batch size: " + pendingBatch.size() +
                ". Flink will retry from last checkpoint.",
                sqlException
            );
        }
    }

    @Override
    public void close() throws Exception {
        flushBatch();
        if (flushSchedule != null) {
            flushSchedule.cancel(true);
        }
        if (connection != null) {
            connection.close();
        }
    }
}
