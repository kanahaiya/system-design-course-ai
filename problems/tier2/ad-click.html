Tier 2 — Should Know 45 min Stream processing

Design Ad Click Aggregator

Ad systems generate billions of click events daily. You can't store raw clicks forever — you aggregate them. The key tradeoff: stream processing (fast but approximate) vs batch (accurate but slow). Click fraud requires deduplication at scale.

🏢 Google, Meta, Twitter
⏱️ 45 min interview
📊 10B clicks/day

❓R — Requirements3–5 min

Functional Requirements

  • Ingest click events: {ad_id, user_id, timestamp, ip_address, device}
  • Aggregate click counts per ad per time window (1-min, 1-hour, 1-day)
  • Query API: "how many clicks did ad X get in the last 5 minutes?"
  • Click deduplication: same user clicking same ad within 5 minutes = 1 click
  • Top-N ads by click count in time window

Non-Functional Requirements

  • Scale: 10B clicks/day = ~115K clicks/sec average; peak 500K/sec
  • Latency: Aggregations available within 1 minute of click (near-real-time)
  • Accuracy: <1% error in click counts acceptable; billing reports need exact counts (batch)

🔢E — Estimation3–5 min

  • 10B clicks/day × 100 bytes/click = 1TB/day raw click data → too expensive to store long-term
  • Aggregate to 1-min buckets: 10M ads × 1440 min/day × 8 bytes = 115GB/day (100× smaller)
  • Kafka: 115K events/sec across 100 partitions = 1,150 events/sec/partition → manageable
  • Dedup window: 5 min × 115K clicks/sec = 34M in-flight dedup checks → Bloom filter in Redis: 34M bits = 4MB

🗄️S — Schema3–5 min

// Raw click events (Kafka — ephemeral, 7-day retention)
// Also archived to S3 for batch reprocessing
click_event: { click_id: UUID, ad_id, user_id, ip, device, timestamp, page_url }

// Aggregated counts (ClickHouse / TimeSeries DB)
// Partition by ad_id; cluster by window_start for time-range queries
ad_click_agg:
    ad_id          UUID,
    window_start   TIMESTAMP,  -- truncated to minute
    window_end     TIMESTAMP,
    click_count    BIGINT,
    unique_users   BIGINT,     -- HyperLogLog approximation
    PRIMARY KEY (ad_id, window_start)

// Top-N cache (Redis Sorted Set)
// Key: top_ads:{window_minute}  Score: click_count  Member: ad_id
// TTL: 2 hours (only recent top-N matters)

🏗️H — High-level Design10 min

  • Click Ingestion API: Lightweight HTTP endpoint. Validates click, publishes to Kafka. Returns 200 immediately (fire-and-forget semantics).
  • Kafka: Click events partitioned by ad_id (so all clicks for an ad go to the same partition → no cross-partition aggregation needed).
  • Stream Processor (Flink): Consumes Kafka. Deduplicates clicks (Bloom filter). Aggregates per ad_id per 1-min tumbling window. Writes to ClickHouse.
  • Batch Reconciliation (Spark): Nightly. Reads raw clicks from S3. Produces exact counts. Reconciles with stream counts. Used for billing.
  • Query API: Reads from ClickHouse for time-range queries. Reads from Redis for top-N queries.

🔌A — APIs5 min

POST /v1/clicks                    // record a click event
  Body: { adId, userId, pageUrl, device }
  Returns: 200 OK (fire-and-forget)

GET  /v1/ads/{adId}/clicks?start={}&end={}&granularity=1min
  // Returns: [{ windowStart, clickCount, uniqueUsers }]

GET  /v1/ads/top?window=1h&limit=10
  // Returns: [{ adId, clickCount }] — top 10 by clicks in last hour

🔬D — Deep Dive: Windowed Aggregation + Deduplication10 min

Tumbling windows: Non-overlapping fixed-time buckets. 00:00–01:00, 01:00–02:00, etc. Every click in the 1-minute window is counted together. Simple aggregation; query by truncating timestamp to minute.

Sliding windows: Overlapping. "Last 5 minutes" = window slides with every new event. More complex; requires maintaining counts for multiple overlapping windows.

Click deduplication with Bloom filter:

  • Key: hash(user_id + ad_id + 5-min-bucket)
  • Bloom filter: probabilistic set membership. False positives (deduplicate a genuine click) ≤0.1%. No false negatives (a duplicate is never missed).
  • 4MB per 5-min window; expire old windows.
  • For exact deduplication: Redis SET with TTL — but 34M keys at 64 bytes each = 2GB RAM. Bloom filter is 500× more memory-efficient.

Late data handling: Network delays mean clicks arrive up to 5 min late. Flink's watermark mechanism: process events up to W minutes late before closing a window. Reprocess late events via batch job.

✅E — Evaluate3 min

  • Billing accuracy: Stream counts have <1% error (Bloom filter false positives). For billing, use nightly Spark batch on raw S3 data for exact counts. Advertisers see stream counts in real-time, billed on batch counts.
  • Hot ad problem: A viral ad gets 1M clicks/min. Single Kafka partition for that ad_id becomes a bottleneck. Solution: sub-partition by (ad_id, random_shard), aggregate per shard, then sum shards at query time.

🚀D — Deliver2 min

We designed an ad click aggregator handling 10B clicks/day. Key decisions: Kafka partitioned by ad_id for ordered aggregation, Flink for stream processing with tumbling windows, Bloom filter for memory-efficient click deduplication, ClickHouse for time-series storage, and nightly Spark batch for billing-accurate exact counts.

⚖️Trade-offs

DecisionChosenAlternativeWhy Chosen
DeduplicationBloom filter (probabilistic)Redis SET (exact)34M unique (user,ad,window) combos. Bloom = 4MB; Redis SET = 2GB. <0.1% false positive rate is acceptable for ad analytics (not billing).
Stream vs batchBoth (Lambda architecture)Stream-only (Kappa)Stream for real-time dashboard; batch for billing accuracy. Trade-off: operational complexity of two pipelines vs guaranteed accuracy for financial reporting.
Aggregation storageClickHousePostgreSQLClickHouse is columnar, optimized for time-series aggregation queries (SUM over millions of rows in ms). PostgreSQL would be too slow for ad-hoc time range queries at this scale.
Kafka partition keyad_idRandom / round-robinPartitioning by ad_id co-locates all clicks for an ad to one partition — enables stateful per-ad aggregation without cross-partition joins.

☕Java Implementation

/**
 * ClickAggregator — sliding window click counter with Bloom filter deduplication.
 * Uses a circular buffer of fixed-size buckets (one per minute).
 * Memory: O(WINDOW_MINUTES × BUCKET_SIZE) regardless of click volume.
 */
public class ClickAggregator {

    private static final int WINDOW_MINUTES = 5;
    private static final int BLOOM_FILTER_BITS = 4_000_000; // 4MB per window
    private static final double BLOOM_FALSE_POSITIVE_RATE = 0.001;

    // Circular buffer: one bucket per minute, WINDOW_MINUTES buckets total
    private final long[] clickBuckets = new long[WINDOW_MINUTES];
    private final BloomFilter[] deduplicationFilters = new BloomFilter[WINDOW_MINUTES];
    private int currentBucketIndex = 0;
    private long currentWindowMinute = 0;

    public ClickAggregator() {
        for (int bucketIndex = 0; bucketIndex < WINDOW_MINUTES; bucketIndex++) {
            deduplicationFilters[bucketIndex] = BloomFilter.create(
                Funnels.stringFunnel(), BLOOM_FILTER_BITS, BLOOM_FALSE_POSITIVE_RATE
            );
        }
    }

    /**
     * Records a click event if it passes deduplication check.
     * Thread-safe: synchronized to protect circular buffer rotation.
     *
     * @param adId    the ad that was clicked
     * @param userId  the user who clicked
     */
    public synchronized void recordClick(String adId, String userId) {
        long nowMinute = System.currentTimeMillis() / 60_000;
        advanceWindowIfNeeded(nowMinute);

        // Deduplication key: same user clicking same ad within 5-min window = one click
        String deduplicationKey = userId + ":" + adId;
        if (!deduplicationFilters[currentBucketIndex].mightContain(deduplicationKey)) {
            deduplicationFilters[currentBucketIndex].put(deduplicationKey);
            clickBuckets[currentBucketIndex]++;
        }
        // Bloom filter may report false positive (mightContain=true for new click)
        // This means we occasionally miss a genuine click — acceptable at <0.1% rate
    }

    /**
     * Returns total click count for the sliding window (last WINDOW_MINUTES minutes).
     */
    public synchronized long getWindowClickCount() {
        long total = 0;
        for (long bucketCount : clickBuckets) {
            total += bucketCount;
        }
        return total;
    }

    /**
     * Advances the circular buffer when the current minute has changed.
     * Clears the bucket that's being overwritten (it's now older than the window).
     */
    private void advanceWindowIfNeeded(long nowMinute) {
        long minutesElapsed = nowMinute - currentWindowMinute;
        if (minutesElapsed <= 0) {
            return; // Still in the same minute
        }

        long bucketsToAdvance = Math.min(minutesElapsed, WINDOW_MINUTES);
        for (long advancement = 0; advancement < bucketsToAdvance; advancement++) {
            currentBucketIndex = (currentBucketIndex + 1) % WINDOW_MINUTES;
            clickBuckets[currentBucketIndex] = 0; // clear expired bucket
            deduplicationFilters[currentBucketIndex] = BloomFilter.create(
                Funnels.stringFunnel(), BLOOM_FILTER_BITS, BLOOM_FALSE_POSITIVE_RATE
            );
        }
        currentWindowMinute = nowMinute;
    }
}
