Tier 2 — Senior 45 min Inverted Index · PageRank · Crawling

Design a Search Engine

A search engine is a 3-phase pipeline: COLLECT → INDEX → SERVE. Every component — crawlers, inverted index, ranking — maps to one of these three phases. Master that mental model and the entire system clicks into place.

🏢 Google, Microsoft (Bing), Amazon
⏱️ 45 min interview
🎯 Inverted index · TF-IDF · PageRank
🧠 The Core Mental Model

COLLECT → INDEX → SERVE. The crawler collects raw web pages. The indexing pipeline transforms them into an inverted index. The query server serves results by merging posting lists and ranking. Every single design decision in this problem maps to one of these three phases. Use it as your skeleton throughout the interview.

❓R — Requirements3–5 min

Functional Requirements

  • Crawl the web: Discover, download, and parse web pages continuously
  • Index content: Store processed content for fast full-text retrieval
  • Rank results: Relevance scoring using TF-IDF × PageRank combined signal
  • Serve queries: Return top-10 results for any keyword query in <200ms
  • Support advanced query syntax: phrase search ("exact phrase"), boolean operators (AND/OR/NOT), field filters (site:example.com)

Non-Functional Requirements

  • Scale: Index 50 billion pages, serve 10 billion queries/day
  • Query latency: p99 <500ms, p50 <100ms (users abandon at 500ms)
  • Freshness: Popular pages re-crawled every hour; cold pages every 30 days
  • Availability: 99.99% — search downtime makes international headlines
⛔ Explicitly Out of Scope

Image search, personalization, ads, auto-suggest, spell correction. State these up front — it shows you know how to scope a 45-minute conversation.

🗄️S — Schema & Data Structures5 min

Three completely separate stores — each optimized for its access pattern:

1. Crawl Store (S3 / Object Storage)

// raw_pages table (metadata in DynamoDB, content in S3)
url_hash     VARCHAR  PRIMARY KEY   -- SHA-256 of normalized URL
url          TEXT
raw_html     BLOB                   -- stored in S3, key = url_hash
crawled_at   TIMESTAMP
http_status  INT
content_hash VARCHAR               -- SHA-256 of body, for deduplication

2. Forward Index (Document Store — Cassandra)

// documents table — one row per indexed page
doc_id          BIGINT   PRIMARY KEY
url             TEXT
title           TEXT
snippet         TEXT     -- ~160 char excerpt for result display
word_count      INT
page_rank       FLOAT    -- pre-computed, updated weekly
last_indexed    TIMESTAMP
outbound_links  LIST<TEXT>

3. Inverted Index — The Heart of Search

// For each term → sorted posting list on disk (Lucene segment files)
// In memory during build: HashMap<String, List<Posting>>
//
// Posting: { doc_id, term_frequency, positions[] }
// Example: "design" → [(doc:42, tf:3, pos:[5,19,88]), (doc:107, tf:1, pos:[3]), ...]
//
// Stored sorted by doc_id — enables fast AND-merge (like merge sort)
// Immutable segment files on disk, merged periodically (LSM-tree style)

4. Link Graph (PageRank computation)

// Adjacency list partitioned across servers
// doc_id → [outbound_doc_id_1, outbound_doc_id_2, ...]
// Stored as Parquet files in object storage, loaded into Spark for weekly PageRank job

🏗️H — High-level Design10 min

Phase 1 — COLLECT: The Web Crawler

  • URL Frontier: A prioritized queue (BFS + priority boost by estimated PageRank). Seeds: known high-authority domains, sitemaps, direct submissions.
  • Crawler workers: Download pages in parallel, extract all <a href> links, store raw HTML to S3, push new URLs into the frontier.
  • Politeness: Respect robots.txt, enforce 1 request/domain/second (rate limit per domain in Redis), honor Crawl-delay header.
  • DNS cache: Each crawler maintains a local DNS cache with 1-hour TTL — crawling 10K domains without a DNS cache would be catastrophic latency.
  • Dedup: SHA-256 of normalized URL before fetching. Content-hash after fetching — skip indexing if content_hash matches existing record.

Phase 2 — INDEX: Building the Inverted Index

  • Parsing: Strip HTML tags, remove boilerplate (nav, footer, cookie banners), extract title, body text, headings, anchor text.
  • NLP pipeline: Tokenize → Lowercase → Remove stop words (the, a, is) → Stem (running → run, searches → search)
  • MapReduce job: Map phase: emit(term, {doc_id, tf, positions[]}). Reduce phase: merge all emissions for each term into a sorted posting list.
  • PageRank: Weekly Spark job on the full link graph. 50+ iterations until convergence. Result: page_rank float stored in the document record.
  • Segment files: Inverted index stored as immutable Lucene-style segment files. New documents create new segments. Background process merges small segments into large ones (like LSM-tree compaction).

Phase 3 — SERVE: Answering Queries in <200ms

  • Query processing: Tokenize query → look up posting lists for each term → AND-merge (intersection) for multi-word queries → score → sort → top-10
  • Scatter-gather: Query server fans out to ALL 500 index shards simultaneously, each shard returns its local top-10, query server merges into global top-10
  • Result cache: Redis caches complete results for the top 10,000 most frequent queries (LRU eviction, 5-minute TTL). Top 1% of queries → 50% of traffic eliminated from shard load.
  • Snippet generation: For each result, extract 160 chars around the first occurrence of query terms in the document body.

🔬D — Deep Dive15 min

1. The Inverted Index: AND-Merge Algorithm

The inverted index maps every word to a sorted list of documents containing it. Finding documents that contain ALL query terms is the AND-intersection — identical to merging sorted arrays (merge sort's merge step).

Example: Query = "system design interview"

Posting lists (sorted by doc_id):
"system"    → [4, 7, 12, 19, 31, 45, ...]
"design"    → [4, 9, 12, 28, 31, ...]
"interview" → [4, 31, 67, ...]

AND-merge result: [4, 31, ...] — only docs in ALL three lists

Algorithm: 3 pointers, advance the smallest.
When all 3 point to same doc_id → match! Time: O(N₁ + N₂ + N₃)

2. TF-IDF Ranking — Why Rare Terms Win

TF-IDF answers: "Which documents are most relevant to this term?" It rewards terms that appear frequently in a document but rarely across the entire corpus.

TF(term, doc)  = count of term in doc / total terms in doc
IDF(term)      = log(total_docs / docs_containing_term)
TF-IDF score   = TF × IDF

"the" → IDF ≈ log(50B / 49B) ≈ 0.02  ← nearly useless signal
"eigenvector" → IDF ≈ log(50B / 50K) ≈ 6.0  ← very strong signal

Final ranking: finalScore = 0.7 × TF-IDF + 0.3 × PageRank
(weights tuned by Google's quality raters — these are illustrative)
💡 Why PageRank Beat AltaVista

AltaVista used TF-IDF only — trivially gamed by "keyword stuffing" (repeating terms 100 times in white text). PageRank treats each hyperlink as a vote, weighted by the voting page's own PageRank. It's an eigenvector calculation: the PageRank vector is the principal eigenvector of the web's link matrix. This makes it exponentially harder to fake — you'd need other high-PageRank sites to link to you.

3. Deduplication: SimHash for Near-Duplicate Detection

The web is ~30% duplicate or near-duplicate content (articles syndicated across news sites, forums quoting the same text). Exact hashing misses paraphrased copies. SimHash is locality-sensitive — similar texts produce similar fingerprints.

SimHash algorithm:
1. Generate overlapping 3-word shingles: "system design is" "design is hard" ...
2. Hash each shingle to 64 bits (MurmurHash)
3. XOR all hashes → 64-bit fingerprint
4. Hamming distance ≤ 3 bits → near-duplicate

URL normalization (always do this BEFORE hashing):
• Remove tracking params: ?utm_source=twitter → removed
• Lowercase domain, normalize trailing slash
• Remove session IDs, timestamps in query params

4. Crawl Frontier: Politeness + Priority

A naive BFS crawler will DDoS every website it touches. The frontier must enforce politeness while also prioritizing pages most worth crawling.

  • Priority score: crawl_score = estimated_pagerank × freshness_factor. High-PageRank + not recently crawled = top priority.
  • Politeness in Redis: Key = crawl_delay:{domain}, value = last_crawl_ts. Enforce minimum 1s gap per domain. Respect Crawl-delay in robots.txt.
  • Distributed Kafka topics: One topic per domain hash range. Crawler workers consume from assigned topics — prevents multiple workers from hitting the same domain simultaneously.
  • Tiered crawl budget: Top 10M domains → unlimited crawl. Mid-tier → 100 pages/day. Unknown → just the homepage.

⚖️E — Evaluate Bottlenecks5 min

🚨 Bottleneck 1: Scatter-Gather Fan-Out

500K QPS × 500 shards = 250 million shard requests/second. Each query touches every shard. Solution: (1) Read replicas per shard distribute load. (2) Redis result cache for top queries eliminates most shard traffic entirely. In practice, the top 1% of queries generate ~50% of traffic — cache hit rate for those is near 100%.

🚨 Bottleneck 2: Crawl Freshness vs Cost

Crawling all 50B pages hourly would require ~14M pages/second — impossible. Solution: Tiered freshness. Top 100M pages (news, social, major domains): hourly. Next 5B: daily. Remaining 45B: monthly. Pages that link to frequently-updated pages get boosted crawl priority automatically.

🚨 Bottleneck 3: Spam and SEO Gaming

TF-IDF can be gamed (keyword stuffing). PageRank can be gamed (link farms). Defense layers: (1) TrustRank: seed from known-good domains, propagate trust. (2) Link spam detection: flag domains with suspicious inbound link growth patterns. (3) Manually curated spam domain blocklist.

🎯D — Deliver: Closing Statement2 min

"A search engine is a 3-phase pipeline. COLLECT: the crawler discovers and downloads pages via a prioritized URL frontier, stores raw HTML to S3, and enforces politeness per domain. INDEX: the MapReduce pipeline tokenizes, stems, and builds a sorted inverted index — each term maps to a posting list of (doc_id, TF, positions). TF-IDF × PageRank produces the final relevance score. SERVE: the query server scatter-gathers across all 500 index shards simultaneously — each returns local top-10, merged into global top-10. Redis caches the most frequent queries. The core algorithm powering query answering is the AND-merge of sorted posting lists — identical to merge-sort's merge step — running in O(N₁ + N₂ + N₃)."

⚠️ The Most Common Interview Mistake

Do NOT say "I'd use Elasticsearch" as your primary answer. Elasticsearch is the right deployment answer, but interviewers want to know you understand the internals: posting lists, AND-merge algorithm, TF-IDF scoring, how scatter-gather works. Show the internals first, then mention Elasticsearch as the operational choice.

💡 If They Say "Focus on the Interesting Part"

Go deep on the inverted index immediately. Explain posting lists, draw the AND-merge algorithm on the whiteboard, discuss TF-IDF with concrete numbers, explain phrase search (position arrays), then transition to scatter-gather serving. That's the 15 minutes that separates candidates who pass from those who don't.

⚡Key Trade-offs

Decision Option A Option B Winner & Why
Index structure Hash map (O(1) lookup) Sorted segment files (range queries) ✅ Sorted files — enables prefix search, phrase search, better compression
Ranking signal TF-IDF only TF-IDF + PageRank ✅ Combined — TF-IDF gives relevance, PageRank gives authority. Either alone is gameable.
Index freshness Push (crawler triggers re-index) Pull (periodic batch re-index) ✅ Pull + priority queue — batch is manageable, priority ensures news/critical pages are fast
Query routing Scatter-gather all shards Partition by first letter of query term ✅ Scatter-gather — AND queries span multiple terms which span all shards; partitioning would require cross-shard joins anyway
Dedup strategy Exact SHA-256 hash SimHash (near-duplicate detection) ✅ SimHash — catches paraphrased and lightly reformatted copies that share identical content
Crawl ordering Pure BFS Priority BFS (by estimated PageRank) ✅ Priority BFS — discovers high-value pages first, BFS alone wastes crawl budget on low-value deep pages

☕Java Implementation

The inverted index with AND-merge search — the core algorithm powering every search engine:

/**
 * InvertedIndex — core data structure for a search engine.
 *
 * Supports:
 *   addDocument(docId, terms[]) — indexes a document
 *   search(queryTerms[])        — AND-merge across posting lists, returns ranked doc IDs
 *   computeTfIdf(term, docId)   — TF-IDF relevance score
 */
import java.util.*;

public class InvertedIndex {

    // ── Inner Types ────────────────────────────────────────────────────────────

    /**
     * One entry in a posting list: the document containing the term,
     * how often the term appears, and the byte positions (for phrase search).
     */
    public static class Posting implements Comparable<Posting> {
        public final int docId;
        public final int termFrequency;
        public final List<Integer> positions;   // byte offsets — enables phrase search

        public Posting(int docId, int termFrequency, List<Integer> positions) {
            this.docId = docId;
            this.termFrequency = termFrequency;
            this.positions = Collections.unmodifiableList(positions);
        }

        @Override
        public int compareTo(Posting other) {
            return Integer.compare(this.docId, other.docId);
        }
    }

    // ── State ─────────────────────────────────────────────────────────────────

    // term → sorted posting list (sorted by docId for efficient AND-merge)
    private final Map<String, List<Posting>> invertedIndex = new HashMap<>();

    // docId → total term count in that document (for TF normalization)
    private final Map<Integer, Integer> documentLengths = new HashMap<>();

    // docId → pre-computed PageRank score
    private final Map<Integer, Double> pageRanks = new HashMap<>();

    private int totalDocuments = 0;

    // Weight constants — in production, these are tuned by quality raters
    private static final double TF_IDF_WEIGHT = 0.7;
    private static final double PAGE_RANK_WEIGHT = 0.3;

    // ── Core Logic ─────────────────────────────────────────────────────────────

    /**
     * Indexes a document. Builds posting lists for each unique term.
     * In production: called by the MapReduce reducer after Combine phase.
     *
     * @param docId unique document identifier
     * @param terms array of pre-processed tokens (lowercased, stemmed, no stopwords)
     */
    public void addDocument(int docId, String[] terms) {
        // Track how many terms this document has (for TF normalization)
        documentLengths.put(docId, terms.length);
        totalDocuments++;

        // Build per-term frequency + position maps
        Map<String, List<Integer>> termPositions = new LinkedHashMap<>();
        for (int position = 0; position < terms.length; position++) {
            String term = terms[position];
            termPositions.computeIfAbsent(term, ignored -> new ArrayList<>()).add(position);
        }

        // Insert into inverted index — maintain sort order by docId
        for (Map.Entry<String, List<Integer>> entry : termPositions.entrySet()) {
            String term = entry.getKey();
            List<Integer> positions = entry.getValue();
            int termFrequency = positions.size();

            Posting posting = new Posting(docId, termFrequency, positions);

            List<Posting> postingList = invertedIndex.computeIfAbsent(term, ignored -> new ArrayList<>());
            postingList.add(posting);  // Documents added in ascending docId order during MapReduce
        }
    }

    /**
     * Sets the pre-computed PageRank for a document.
     * PageRank is computed weekly by a separate Spark job on the link graph.
     *
     * @param docId  the document
     * @param pageRank  value in range [0, 1]
     */
    public void setPageRank(int docId, double pageRank) {
        pageRanks.put(docId, pageRank);
    }

    /**
     * AND-search: returns docs containing ALL query terms, ranked by TF-IDF × PageRank.
     *
     * Algorithm: pointer-based merge identical to merging sorted arrays.
     * Time complexity: O(N₁ + N₂ + ... + Nₖ) where Nᵢ = posting list length for term i.
     * This is the same operation as merge-sort's merge step.
     *
     * @param queryTerms pre-processed query tokens (same stemming as indexing)
     * @return list of matching docIds sorted by relevance score descending
     */
    public List<Integer> search(String[] queryTerms) {
        if (queryTerms == null || queryTerms.length == 0) {
            return Collections.emptyList();
        }

        // Gather posting lists for all query terms
        List<List<Posting>> postingLists = new ArrayList<>();
        for (String term : queryTerms) {
            List<Posting> postingList = invertedIndex.get(term);
            if (postingList == null || postingList.isEmpty()) {
                return Collections.emptyList();  // AND: if any term is missing → no results
            }
            postingLists.add(postingList);
        }

        // Sort posting lists ascending by size: start with rarest term first
        // This minimizes iterations — we advance the smallest list most often
        postingLists.sort(Comparator.comparingInt(List::size));

        // AND-merge using one pointer per posting list
        List<Integer> matchingDocIds = andMerge(postingLists);

        // Score and rank matching documents
        return rankDocuments(matchingDocIds, queryTerms);
    }

    /**
     * Core AND-merge: finds doc IDs present in ALL posting lists.
     * One pointer per list, always advance the list with the smallest current docId.
     * When all pointers agree on the same docId → it's a match.
     *
     * @param postingLists  sorted posting lists for each query term
     * @return doc IDs appearing in all lists
     */
    private List<Integer> andMerge(List<List<Posting>> postingLists) {
        List<Integer> result = new ArrayList<>();
        int[] pointers = new int[postingLists.size()];  // one pointer per list

        while (true) {
            // Find current docId at each pointer position
            int maxDocId = Integer.MIN_VALUE;
            boolean anyListExhausted = false;

            for (int listIndex = 0; listIndex < postingLists.size(); listIndex++) {
                if (pointers[listIndex] >= postingLists.get(listIndex).size()) {
                    anyListExhausted = true;
                    break;
                }
                int currentDocId = postingLists.get(listIndex).get(pointers[listIndex]).docId;
                maxDocId = Math.max(maxDocId, currentDocId);
            }

            if (anyListExhausted) {
                break;  // One list is exhausted — AND is done
            }

            // Check if all pointers are on the same docId
            boolean allMatch = true;
            for (int listIndex = 0; listIndex < postingLists.size(); listIndex++) {
                int currentDocId = postingLists.get(listIndex).get(pointers[listIndex]).docId;
                if (currentDocId != maxDocId) {
                    allMatch = false;
                    // Advance this pointer to skip ahead toward maxDocId
                    pointers[listIndex]++;
                }
            }

            if (allMatch) {
                result.add(maxDocId);
                // Advance ALL pointers past this matched docId
                for (int listIndex = 0; listIndex < postingLists.size(); listIndex++) {
                    pointers[listIndex]++;
                }
            }
        }

        return result;
    }

    /**
     * Scores each matching document and returns docIds sorted by score descending.
     * Score = 0.7 × TF-IDF + 0.3 × PageRank
     *
     * @param docIds       candidate document IDs from AND-merge
     * @param queryTerms   original query terms
     * @return docIds ranked by combined relevance score
     */
    private List<Integer> rankDocuments(List<Integer> docIds, String[] queryTerms) {
        // Score each document
        Map<Integer, Double> scores = new HashMap<>();
        for (int docId : docIds) {
            double tfIdfSum = 0.0;
            for (String term : queryTerms) {
                tfIdfSum += computeTfIdf(term, docId);
            }
            double pageRank = pageRanks.getOrDefault(docId, 0.001);
            double combinedScore = TF_IDF_WEIGHT * tfIdfSum + PAGE_RANK_WEIGHT * pageRank;
            scores.put(docId, combinedScore);
        }

        // Sort descending by score
        List<Integer> ranked = new ArrayList<>(docIds);
        ranked.sort((docIdA, docIdB) -> Double.compare(scores.get(docIdB), scores.get(docIdA)));
        return ranked;
    }

    /**
     * TF-IDF score for one term in one document.
     *
     * TF  = termFrequency / documentLength  (normalized frequency)
     * IDF = log(totalDocs / docsContainingTerm)  (inverse document frequency)
     *
     * @param term   the search term
     * @param docId  the document to score
     * @return TF-IDF relevance score, or 0.0 if term not in document
     */
    public double computeTfIdf(String term, int docId) {
        List<Posting> postingList = invertedIndex.get(term);
        if (postingList == null) {
            return 0.0;
        }

        // Find the posting for this specific document (binary search — list is sorted)
        int postingIndex = Collections.binarySearch(
            postingList,
            new Posting(docId, 0, Collections.emptyList())
        );

        if (postingIndex < 0) {
            return 0.0;  // Term not in this document
        }

        Posting posting = postingList.get(postingIndex);
        int documentLength = documentLengths.getOrDefault(docId, 1);
        int docsContainingTerm = postingList.size();

        double termFrequency = (double) posting.termFrequency / documentLength;
        double inverseDocFrequency = Math.log((double) totalDocuments / docsContainingTerm);

        return termFrequency * inverseDocFrequency;
    }
}
