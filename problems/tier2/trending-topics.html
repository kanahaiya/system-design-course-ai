Tier 2 — Should Know 45 min Stream processing

Design Trending Topics

Trending = count events in a sliding time window, rank by frequency, serve fast. The entire problem is about doing this at massive scale without exact counting. The answer is always approximation algorithms.

🏢 Twitter/X, Google, TikTok, Meta, LinkedIn
⏱️ 45 min interview
📊 40K hashtag events/sec
🧠 The Mental Model

Trending = count events in a sliding time window, rank by frequency, serve fast. The entire problem is about doing this at massive scale without exact counting. A HashMap of all 1B hashtags needs 50GB per node — impossible. The answer is always approximation algorithms: Count-Min Sketch gives you near-exact counts in 32KB. The interviewer expects you to know this trade-off exists and name it.

☕ Real-World Analogy: The Coffee Shop Tally

Imagine a busy coffee shop with 1,000 drink orders per hour. You want to know the top-3 most popular drinks right now. You could write every single order in a notebook (exact counting — uses lots of paper). Or you could use a tally sheet with 20 boxes: each drink gets hashed to a box, and you increment that box. Multiple drinks share boxes (hash collision), so box counts are slightly inflated — but the minimum across 4 independent tally sheets gives you a very accurate estimate with tiny paper. That's Count-Min Sketch. For "what's trending?", 98% accuracy in 32KB beats 100% accuracy in 50GB.

❓R — Requirements3–5 min

Functional Requirements

  • Real-time trending topics: Top-10 hashtags/topics trending RIGHT NOW (last 1 hour, sliding window)
  • Geo-trending: Trending in NYC, in India, globally — separate ranked lists per region
  • Time windows: Trending in last 1 hour, last 24 hours, this week
  • Hashtag search: "Is #SystemDesign trending?" → current rank + trend line (graph of count over last 24h)
  • Trend velocity: A topic trending UP fast is ranked higher than one slowly declining

Non-Functional Requirements

  • Scale: 500M tweets/day = 6,000 tweets/second; 5–10 hashtags per tweet = 30–60K hashtag events/second
  • Freshness: Trending topics must reflect activity from the last 5 minutes (not 30 minutes stale)
  • Approximate is OK: Top-10 can miss the 11th most trending topic — that's acceptable
  • Query latency: < 50ms for "what's trending right now"
  • NOT required: Exact counts (approximation acceptable — this is a key clarifying question)
⚡ Clarifying Questions to Ask
  • "Can the top-10 be approximate, or do we need exactly the top-10?" → Approximate is fine → opens the door to Count-Min Sketch
  • "How fresh does trending need to be?" → 5 minutes → stream processing (not batch)
  • "Do we need geo-specific trending?" → Yes → multiply data structures by 200 regions (still tiny)

🗄️S — Schema / Data Structures5 min

This problem is unusual: the in-memory data structures are the schema. The persistent DB is just for audit/archival. Start with the in-memory structures.

In-Memory Data Structures (the real schema)

1. Count-Min Sketch — Approximate Frequency Counting

A 2D array: int[d][w] where d = hash functions (rows), w = counters per row (columns).

  • increment(hashtag): For each of d rows, compute hash(hashtag) % w → increment that cell
  • estimate(hashtag): For each of d rows, read the cell → return the MINIMUM across all rows (minimum = least overestimated)
  • Why minimum? Each cell may count multiple hashtags (hash collisions → overestimation). The true count is always ≤ any cell's value. Minimum is closest to truth.
  • Space: d=4, w=2048 → 32KB total (vs 50GB for exact HashMap)

2. Min-Heap of Size K (Top-K Candidates)

PriorityQueue<(count, hashtag)> of size K. When a hashtag's estimated count exceeds the heap's minimum → replace minimum with this hashtag. Maintains top-K in O(log K) per update.

3. Circular Bucket Buffer (Sliding Window)

60 one-minute buckets (for 1-hour window). Each bucket is an independent Count-Min Sketch. On each new minute: oldest bucket is zeroed out and becomes the current bucket. Current window count = sum across all 60 buckets.

Persistent Storage (Trend Graphs + Archival)

// Cassandra — write-heavy, time-series queries

🏗️H — High-level Design10 min

Pipeline Architecture

Pipeline Steps — Explained

  1. INGEST: Tweet events published to Kafka topic tweet-events, partitioned by user_id. Each event: {tweet_id, user_id, hashtags[], timestamp, geo_region}.
  2. EXTRACT: Hashtag Extractor Service consumes from Kafka, emits one event per hashtag. Output to topic hashtag-events, partitioned by hashtag (ensures same hashtag always hits same Flink task — locality for accurate counting).
  3. COUNT (Flink): Each Flink task maintains Count-Min Sketch + Min-Heap in memory. Tumbling 1-minute windows: emit (hashtag, window_start, count) at end of each minute. Also maintains global sketch per time window (1h, 24h, week).
  4. AGGREGATE (top-K merge): Multiple Flink tasks → each produces local top-K. Aggregator merges local top-K lists → global top-K. Stored in Redis: ZADD trending:global:1h <score> <hashtag>.
  5. SERVE: Trending API reads from Redis Sorted Set: ZREVRANGE trending:global:1h 0 9 → top-10 in O(K). Response cached 1 minute at API layer.
🔑 Why partition hashtag-events by hashtag?

If the same hashtag hits different Flink tasks, each task has a partial count. You'd need to merge them, which is expensive. By partitioning by hashtag, all events for #SystemDesign go to the same Flink task → one complete count, no merge needed. The Count-Min Sketch stays accurate.

🔬D — Deep Dive10–15 min

1. Count-Min Sketch — How It Actually Works

The core algorithm. Interviewers expect you to explain this clearly, not just name it.

2. Sliding Window with Circular Bucket Buffer

Why not just one big sketch? Because we need "trending in last 60 minutes" — events from 2 hours ago should not count. A circular buffer of 60 one-minute sketches solves this exactly.

3. Trend Velocity — The "Trending" vs "Popular" Distinction

This is the insight that separates strong candidates from average ones. A hashtag that has 30,000 mentions per minute steadily is popular. A hashtag that jumps from 200 to 50,000 mentions in 5 minutes is trending. The formula:

// velocity = (count_last_15min - count_15min_before) / count_15min_before
// Stored in Redis: ZADD trending:velocity:global <velocity> <hashtag>
// Final rank score = 0.6 × count_rank + 0.4 × velocity_rank

double velocity = (countCurrentWindow - countPreviousWindow)
                  / (double) countPreviousWindow;
// #BreakingNews: (50000 - 200) / 200 = 249.0 → velocity rank #1
// #MondayMotivation: (30000 - 29800) / 29800 = 0.007 → velocity rank low

⚠️E — Evaluate5 min

Failure Modes & Mitigations

  • Hash collision in Count-Min Sketch: Two different hashtags hash to same counter → count overestimated. Mitigation: more hash functions (DEPTH=4 reduces error to ~2% with 99% probability at WIDTH=2048). Acceptable for trending use case.
  • Late-arriving Flink events: Tweets arrive out of order (network delay, mobile reconnect). Mitigation: Flink's watermark mechanism — events up to 30 seconds late are included in the current window. Events beyond 30s late are dropped from window (acceptable: trending doesn't need sub-second precision).
  • Hot Kafka partition: During breaking news, one hashtag (#WorldCup during World Cup final) gets 100K events/sec to one partition. Mitigation: partition by hash(hashtag) + jitter with a whitelist of known-hot hashtags that get special over-partitioning.
  • Geo accuracy: IP geolocation is 80–90% accurate at country level. Geo-trending accepts this — a 10% misclassification is imperceptible to users. Explicit geo tagging (user sets their location) is more accurate but optional.
  • Redis Sorted Set memory: If 1M unique hashtags are in the set, ZREVRANGE is still O(K) not O(N). But ZADD for 1M hashtags uses ~80MB Redis — fine. If extreme, use a Bloom filter to gate which hashtags enter the sorted set.

✅D — Deliver2 min

📣 Your Closing Statement (memorize this structure):

Trending = Count-Min Sketch (approximate counting, 32KB vs 50GB exact) + sliding window of 60 one-minute circular buckets + Min-Heap for top-K. Pipeline: Kafka ingest (partitioned by hashtag for locality) → Flink stream processing (Count-Min Sketch per 1-min tumbling window) → Redis Sorted Sets for O(log N) insert, O(K) range query → API serves top-10 from Redis in <1ms. Add velocity scoring: (current window count − previous window count) / previous = trend direction. Combined rank = 0.6 × count + 0.4 × velocity. Geo: 200 separate Redis sorted sets, still only 200 × 32KB = 6.4MB.

☕Java Implementation

/**
 * CountMinSketch — probabilistic frequency estimation data structure.
 *
 * Space: O(d × w) = 32KB at d=4, w=2048.
 * Error bound: estimate ≤ true_count + ε × total_events
 *   where ε = e/w ≈ 0.0014 and P(error) ≤ e^{-d} ≈ 0.018
 *
 * Why minimum? Hash collisions cause overestimation. Taking the minimum
 * across all hash functions gives the least-overestimated count.
 */
public class CountMinSketch {
    private static final int DEPTH = 4;    // number of independent hash functions
    private static final int WIDTH = 2048; // counters per row (power of 2 for fast modulo)

    private final long[][] table = new long[DEPTH][WIDTH];
    // Different seeds ensure hash functions are independent
    private final long[] hashSeeds = { 0xABCDABCDL, 0x12341234L, 0x56785678L, 0xDEF0DEF0L };

    /**
     * Increments the count for the given item by 1.
     * O(d) time — constant since d is fixed.
     */
    public void increment(String item) {
        for (int row = 0; row < DEPTH; row++) {
            int column = hashToColumn(item, hashSeeds[row]);
            table[row][column]++;
        }
    }

    /**
     * Estimates the count for the given item.
     * Returns the MINIMUM across all rows — this is the least overestimated value.
     * The true count is always ≤ any cell's value (overestimation only, never under).
     * O(d) time.
     */
    public long estimate(String item) {
        long minimum = Long.MAX_VALUE;
        for (int row = 0; row < DEPTH; row++) {
            int column = hashToColumn(item, hashSeeds[row]);
            minimum = Math.min(minimum, table[row][column]);
        }
        return minimum;
    }

    /**
     * Merges another sketch into this one (element-wise addition).
     * Used when summing multiple time-bucket sketches for the sliding window.
     */
    public void mergeFrom(CountMinSketch other) {
        for (int row = 0; row < DEPTH; row++) {
            for (int col = 0; col < WIDTH; col++) {
                table[row][col] += other.table[row][col];
            }
        }
    }

    /** Resets all counters to zero (used when rotating a bucket). */
    public void reset() {
        for (int row = 0; row < DEPTH; row++) {
            java.util.Arrays.fill(table[row], 0L);
        }
    }

    private int hashToColumn(String item, long seed) {
        long h = item.hashCode() ^ seed;
        h ^= (h >>> 33);
        h *= 0xff51afd7ed558ccdL;
        h ^= (h >>> 33);
        return (int) Math.abs(h % WIDTH);
    }
}

/**
 * SlidingWindowTrendCounter — maintains a sliding 60-minute window using
 * a circular buffer of one-minute CountMinSketch buckets.
 *
 * Design choice: 60 independent sketches vs one large sketch with decay.
 * Independent sketches allow exact bucket expiry (step function).
 * Total memory: 60 × 32KB = 1.9MB per region — trivially small.
 */
public class SlidingWindowTrendCounter {
    private static final int WINDOW_MINUTES = 60;

    private final CountMinSketch[] buckets = new CountMinSketch[WINDOW_MINUTES];
    private volatile int currentBucketIndex = 0;
    private final ScheduledExecutorService rotationScheduler =
        Executors.newSingleThreadScheduledExecutor();

    public SlidingWindowTrendCounter() {
        for (int i = 0; i < WINDOW_MINUTES; i++) {
            buckets[i] = new CountMinSketch();
        }
        // Advance to next bucket every minute — old bucket is expired implicitly
        rotationScheduler.scheduleAtFixedRate(
            this::rotateToNextBucket, 1, 1, TimeUnit.MINUTES
        );
    }

    public synchronized void recordHashtag(String hashtag) {
        buckets[currentBucketIndex].increment(hashtag);
    }

    /**
     * Estimates count of hashtag across the entire 60-minute sliding window.
     * Sums all 60 buckets' estimates for this hashtag.
     */
    public long estimateWindowCount(String hashtag) {
        long total = 0;
        for (CountMinSketch bucket : buckets) {
            total += bucket.estimate(hashtag);
        }
        return total;
    }

    /**
     * Rotates to the next bucket: advances index and resets that bucket.
     * The reset bucket was the oldest one — now it becomes the current (newest) bucket.
     * This is the circular buffer rotation: O(WIDTH) to reset, not O(all hashtags).
     */
    private synchronized void rotateToNextBucket() {
        currentBucketIndex = (currentBucketIndex + 1) % WINDOW_MINUTES;
        buckets[currentBucketIndex].reset(); // zero out the oldest bucket
    }
}

/**
 * TopKTracker — maintains top-K hashtags using a min-heap of size K.
 * Space: O(K) — only K entries regardless of total distinct hashtags.
 *
 * Pattern: if a hashtag's estimated count > heap's minimum → evict minimum, insert new.
 * This correctly finds the top-K by count with minimal memory.
 */
public class TopKTracker {
    private static final int TOP_K = 1000;

    // Min-heap: smallest count at top → easy to check if a new item qualifies
    private final PriorityQueue<long[]> minHeap =
        new PriorityQueue<>(Comparator.comparingLong(entry -> entry[0]));
    private final Map<String, Long> hashtagToCount = new HashMap<>();

    /**
     * Updates the tracker with a new count for a hashtag.
     * Called by Flink aggregator after each 1-minute window.
     */
    public synchronized void update(String hashtag, long newCount) {
        hashtagToCount.put(hashtag, newCount);

        if (minHeap.size() < TOP_K) {
            minHeap.offer(new long[]{newCount, hashtag.hashCode()});
        } else if (newCount > minHeap.peek()[0]) {
            minHeap.poll(); // remove smallest
            minHeap.offer(new long[]{newCount, hashtag.hashCode()});
        }
    }

    /**
     * Returns top-K hashtags sorted by count descending.
     * Called once per minute to push results to Redis.
     */
    public List<Map.Entry<String, Long>> getTopK() {
        return hashtagToCount.entrySet().stream()
            .sorted(Map.Entry.<String, Long>comparingByValue().reversed())
            .limit(TOP_K)
            .collect(java.util.stream.Collectors.toList());
    }
}

/**
 * VelocityScorer — computes trend velocity for ranking.
 *
 * velocity = (currentWindowCount - previousWindowCount) / previousWindowCount
 * Ranges from -1.0 (completely stopped) to +∞ (explosive growth).
 * High velocity = emerging trend. Combined rank = 0.6×count + 0.4×velocity.
 */
public class VelocityScorer {
    private final Map<String, Long> previousWindowCounts = new ConcurrentHashMap<>();

    public double computeVelocity(String hashtag, long currentCount) {
        long previousCount = previousWindowCounts.getOrDefault(hashtag, 0L);
        if (previousCount == 0L) {
            previousWindowCounts.put(hashtag, currentCount);
            return 0.0; // no baseline yet
        }
        double velocity = (double)(currentCount - previousCount) / previousCount;
        previousWindowCounts.put(hashtag, currentCount); // update baseline
        return velocity;
    }

    public double combinedRankScore(long countRank, double velocityRank) {
        return 0.6 * countRank + 0.4 * velocityRank;
    }
}
