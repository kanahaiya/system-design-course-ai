Tier 2 — Should Know 45 min Real-time

Design Slack / Real-time Chat

The core challenge: WebSocket connections don't map 1:1 to chat servers. When user A on server 1 sends a message to user B on server 2, you need a cross-server delivery mechanism. Redis Pub/Sub is the standard answer.

🏢 Meta, Google, Slack
⏱️ 45 min interview
📨 Real-time delivery

❓R — Requirements3–5 min

Functional Requirements

  • Send and receive messages in real-time within channels and DMs
  • Support workspaces, channels (public/private), and direct messages
  • Message history — fetch last N messages, paginate older history
  • Presence indicators — who is online
  • File and image sharing (up to 1GB per file)
  • Message reactions, threads (replies)
  • Unread counts and notifications for offline users

Non-Functional Requirements

  • Latency: <100ms message delivery p99 within same region
  • Availability: 99.99% — messaging is business-critical
  • Scale: 10M concurrent WebSocket connections, 1B messages/day
  • Ordering: Messages within a channel must be ordered (no re-ordering)
  • Durability: No message loss — at-least-once delivery

🔢E — Estimation3–5 min

  • 1B messages/day = ~11,600 msg/sec average; peak ~50K msg/sec
  • Avg message size: 200 bytes → 200B bytes/day = 200GB/day storage
  • 10M concurrent connections at ~10KB RAM per WebSocket → 100GB RAM for connections
  • Each chat server can hold ~50K connections → need 200 chat servers for connections alone
  • 5 years retention → 365TB of message storage → use Cassandra or HBase

🗄️S — Schema3–5 min

// Messages table (Cassandra — wide column, write-heavy)
// Partition key: channel_id → all messages in a channel on same node
// Clustering key: message_id (time-ordered ULID/Snowflake) → range queries
CREATE TABLE messages (
    channel_id   UUID,
    message_id   BIGINT,  -- Snowflake ID (timestamp-based, sortable)
    user_id      UUID,
    content      TEXT,
    thread_id    BIGINT,  -- null if top-level
    created_at   TIMESTAMP,
    PRIMARY KEY (channel_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);

// Users table (PostgreSQL)
users: user_id, username, email, status (online/away/dnd), last_seen

// Channels (PostgreSQL)
channels: channel_id, workspace_id, name, is_private, created_at

// channel_members (PostgreSQL)
channel_members: channel_id, user_id, last_read_message_id

🏗️H — High-level Design10 min

The critical insight: WebSocket connections are stateful and sticky. User A connects to Chat Server 1; User B connects to Chat Server 2. When A sends a message to B, server 1 doesn't have B's connection.

  • Client ↔ Chat Server: WebSocket (persistent, bidirectional). Fallback: Long-polling for corporate firewalls.
  • Chat Server: Holds active WebSocket connections. Routes messages via Redis Pub/Sub.
  • Redis Pub/Sub: Each chat server subscribes to channels for its connected users. Delivers cross-server messages.
  • Message Store (Cassandra): Persists all messages. Chat server writes to Cassandra before publishing to Redis.
  • Presence Service: Users publish heartbeat every 5s to Redis. TTL-based — if no heartbeat in 10s, marked offline.
  • Notification Service: For offline users, sends push notifications (APNs/FCM).
  • Service Discovery (ZooKeeper): Clients look up which chat server to connect to. Consistent hashing on user_id → chat server.

🔬D — Deep Dive: Cross-Server Message Routing10 min

Problem: User A (on Chat Server 1) sends a DM to User B (connected to Chat Server 2). How does server 1 deliver to B?

Solution — Redis Pub/Sub:

  1. On connect, Chat Server 2 subscribes to Redis channel user:{B_id}
  2. Server 1 receives message from A, persists to Cassandra, then publishes to Redis channel user:{B_id}
  3. Server 2 receives from Redis, pushes down B's WebSocket
  4. For channel messages: Redis channel = channel:{channel_id}. All servers with members of that channel subscribe.

Fan-out for channels: A channel with 10,000 members means 10,000 Redis publishes or a single publish to a Redis channel that all servers subscribing to that channel pick up and fan out locally. Use the latter — O(servers) not O(members).

Message ordering: Use Snowflake IDs (timestamp-based monotonic). Cassandra clustering on message_id DESC gives natural ordering per channel.

✅E — Evaluate3 min

  • Bottleneck: Redis Pub/Sub is in-memory and not persistent — a Redis crash loses in-flight messages. Mitigation: Redis Cluster with persistence, or replace with Kafka for durability.
  • Celebrity problem: Large channels (10K+ members) cause fan-out storms. Limit to Redis channel approach where each server handles its own members.
  • WebSocket server failure: Client detects via heartbeat timeout, reconnects via service discovery to a new server. Missed messages fetched via REST history API.

🚀D — Deliver2 min

We designed a real-time chat system handling 10M concurrent connections. Key decisions: WebSocket for low-latency delivery, Redis Pub/Sub for cross-server routing (O(servers) fan-out), Cassandra for message storage partitioned by channel_id, Snowflake IDs for globally ordered messages, and a separate presence service with heartbeat TTLs.

⚖️Trade-offs

DecisionChosenAlternativeWhy Chosen
Cross-server routingRedis Pub/SubKafka topicsLower latency (<1ms vs >5ms); Kafka overkill for transient delivery signals
Message storageCassandraPostgreSQLWrite-heavy (1B/day); partition by channel_id scales horizontally; no complex joins needed
Connection protocolWebSocketLong-pollingBidirectional; lower overhead; long-polling wastes connections on idle

☕Java Implementation

/**
 * ChatRouter — cross-server message routing using Redis Pub/Sub.
 * Each chat server subscribes to channels for its connected users.
 * Publishing a message notifies all servers that have the recipient connected.
 */
public class ChatRouter {

    private static final String USER_CHANNEL_PREFIX = "user:";
    private static final String CHANNEL_PREFIX = "channel:";

    private final JedisPool jedisPool;
    // Maps userId → active WebSocket session (local connections only)
    private final Map<String, WebSocketSession> localConnections = new ConcurrentHashMap<>();
    private final JedisSubscriber subscriber = new JedisSubscriber();

    public ChatRouter(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }

    /**
     * Called when a user connects to this server via WebSocket.
     * Subscribes to their personal Redis channel to receive messages from other servers.
     */
    public void registerConnection(String userId, WebSocketSession session) {
        localConnections.put(userId, session);
        // Subscribe in a separate thread — Jedis subscribe() blocks
        Thread.ofVirtual().start(() -> {
            try (Jedis jedis = jedisPool.getResource()) {
                jedis.subscribe(subscriber, USER_CHANNEL_PREFIX + userId);
            }
        });
    }

    /**
     * Called when a user disconnects. Unsubscribes from Redis.
     */
    public void deregisterConnection(String userId) {
        localConnections.remove(userId);
        subscriber.unsubscribe(USER_CHANNEL_PREFIX + userId);
    }

    /**
     * Routes a direct message to the recipient.
     * Publishes to Redis — the server holding the recipient's connection will deliver it.
     */
    public void routeDirectMessage(ChatMessage message, String recipientId) {
        String serializedMessage = serializeMessage(message);
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.publish(USER_CHANNEL_PREFIX + recipientId, serializedMessage);
        }
    }

    /**
     * Routes a channel message. All servers subscribed to this channel's Redis topic
     * will receive it and deliver to their locally connected channel members.
     */
    public void routeChannelMessage(ChatMessage message, String channelId) {
        String serializedMessage = serializeMessage(message);
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.publish(CHANNEL_PREFIX + channelId, serializedMessage);
        }
    }

    /**
     * Delivers a message to a locally connected user's WebSocket.
     * Called by the Redis subscriber callback when this server receives a published message.
     */
    private void deliverToLocalConnection(String userId, String serializedMessage) {
        WebSocketSession session = localConnections.get(userId);
        if (session != null && session.isOpen()) {
            try {
                session.sendMessage(new TextMessage(serializedMessage));
            } catch (IOException ioException) {
                // Session closed between check and send — remove stale entry
                localConnections.remove(userId);
            }
        }
    }

    private String serializeMessage(ChatMessage message) {
        // In production: use Jackson ObjectMapper
        return "{\"id\":" + message.getId() + ",\"content\":\"" + message.getContent() + "\"}";
    }

    private class JedisSubscriber extends JedisPubSub {
        @Override
        public void onMessage(String channel, String message) {
            // Extract userId from "user:{userId}" channel name
            String userId = channel.substring(USER_CHANNEL_PREFIX.length());
            deliverToLocalConnection(userId, message);
        }
    }
}
