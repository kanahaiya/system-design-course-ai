Tier 2 — Should Know 45 min Real-time

Design Slack / Real-time Chat

The core challenge: WebSocket connections don't map 1:1 to chat servers. When user A on server 1 sends a message to user B on server 2, you need a cross-server delivery mechanism. Redis Pub/Sub is the standard answer. Slack runs 20M DAU, 5B messages/day, 500K concurrent WebSocket connections.

🏢 Meta, Google, Slack
⏱️ 45 min interview
📨 Real-time delivery

❓R — Requirements3–5 min

Functional Requirements

  • Send and receive messages in real-time within channels and DMs
  • Support workspaces, channels (public/private), and direct messages (DM, group DM)
  • Message history — fetch last N messages, paginate older history
  • Presence indicators — who is online, away, or do-not-disturb
  • File and image sharing (up to 1GB per file)
  • Message reactions, threads (replies to messages)
  • Slash commands — /giphy, /remind, custom app integrations
  • Unread counts and push notifications for offline users

Non-Functional Requirements

  • Latency: <100ms message delivery p99 within same region
  • Availability: 99.99% — messaging is business-critical
  • Scale: 20M DAU, 500K concurrent WebSocket connections, 5B messages/day
  • Ordering: Messages within a channel must be ordered (no re-ordering)
  • Durability: No message loss — at-least-once delivery
L6 scope clarification: Ask "should we support enterprise features like SAML SSO, compliance retention, e-discovery?" This signals whether you need immutable audit logging (Kafka → S3 → Parquet) on top of the standard message flow.

🔢E — Estimation3–5 min

  • 5B messages/day = ~58,000 msg/sec average; peak ~200K msg/sec
  • Avg message size: 200 bytes → 1TB/day storage → Cassandra handles this at 5-year retention = ~1.8PB
  • 500K concurrent WebSocket connections at ~10KB RAM per WebSocket = 5GB RAM just for connections
  • Each chat server holds ~50K connections → need ~10 chat servers minimum (100 for headroom)
  • Channel fan-out: large channel with 10K members posting 1 msg/sec = 10K deliveries/sec from that one channel alone
  • Redis Pub/Sub throughput: ~1M messages/sec per Redis node — sufficient for the cross-server routing layer

// Partition key: channel_id → all messages in a channel on same node

// WebSocket connection registry (Redis — ephemeral, expires on disconnect)
// Key: "ws:{userId}" → Value: "{serverId}:{connectionId}"
// TTL: 5 minutes (refreshed on each message, acts as keepalive)

// Presence state (Redis — TTL-based heartbeat)
// Key: "presence:{userId}" → Value: "online"
// TTL: 90 seconds (client heartbeat every 30s, 3× buffer for late heartbeats)

Snowflake ID Structure

// 64-bit Snowflake ID: monotonically increasing, globally unique, time-sortable
// | 41 bits timestamp (ms since epoch) | 10 bits worker ID | 12 bits sequence |
// timestamp: 41 bits → 2^41 ms = ~69 years from epoch
// worker ID: 10 bits → 1024 workers
// sequence:  12 bits → 4096 IDs per ms per worker

public class SnowflakeIdGenerator {
    private static final long EPOCH = 1_700_000_000_000L; // Nov 2023 custom epoch
    private static final int WORKER_BITS = 10;
    private static final int SEQUENCE_BITS = 12;

    private final long workerId;
    private long lastTimestampMs = -1;
    private long sequence = 0;

    public synchronized long nextId() {
        long currentMs = System.currentTimeMillis() - EPOCH;
        if (currentMs == lastTimestampMs) {
            sequence = (sequence + 1) & 0xFFF; // 4096 per ms
            if (sequence == 0) currentMs = waitForNextMs(lastTimestampMs);
        } else {
            sequence = 0;
        }
        lastTimestampMs = currentMs;
        return (currentMs << (WORKER_BITS + SEQUENCE_BITS))
             | (workerId << SEQUENCE_BITS)
             | sequence;
    }
    // Guarantees: monotonic per worker, globally unique across workers,
    // time-sortable → Cassandra clustering order gives chronological message order
}

🏗️H — High-level Design10 min

Figure: Message delivery sequence — sender → WS Server 1 → Cassandra persist → Redis Pub/Sub → all subscribed WS servers → recipients

The critical insight: WebSocket connections are stateful and sticky. User A connects to Chat Server 1; User B connects to Chat Server 2. When A sends a message to B, server 1 doesn't have B's connection.

  • Client ↔ Chat Server: WebSocket (persistent, bidirectional). Fallback: Long-polling for corporate firewalls that block WS upgrades.
  • Sticky Sessions: Load balancer routes each user to the same WS server (consistent hashing on userId). This is critical — if a reconnect goes to a different server, the old server's subscription must be cleaned up.
  • Connection Registry (Redis): On connect, WS server writes ws:{userId} → serverId. Allows other services to route messages to the correct server.
  • Redis Pub/Sub: Each channel maps to a Redis Pub/Sub channel. All WS servers with members of that channel subscribe. Message publish = O(subscribed servers), not O(members).
  • Message Store (Cassandra): Write before publishing to Redis. If Redis publish fails, message is in Cassandra — client can fetch via REST history API.
  • Presence Service: Heartbeat every 30s from client. Redis key presence:{userId} with 90s TTL. No heartbeat = key expires = user marked offline.
  • Notification Service: If user not in connection registry (offline): send APNs/FCM push notification. Consumes Kafka events (not Redis Pub/Sub — Kafka is durable for notification audit).
  • Service Discovery (ZooKeeper / Consul): Clients look up healthy WS servers. Consistent hashing routes to the same server on reconnect within a time window.

🔬D — Deep Dive: Fan-out, Presence, and File Sharing10 min

Cross-Server Delivery via Redis Pub/Sub

User A (on WS Server 1) sends a DM to User B (connected to WS Server 2). How does Server 1 deliver to B?

  1. On connect, WS Server 2 looks up which channels User B is in. Subscribes to Redis channels: channel:{channelId} for each of B's channels.
  2. Server 1 receives message from A, assigns a Snowflake message_id, persists to Cassandra (durable first), then publishes to Redis: PUBLISH channel:{channelId} {messageJson}.
  3. Redis delivers to all servers subscribed to that channel, including Server 2.
  4. Server 2 receives from Redis. Iterates its local connections for that channel. Pushes down B's WebSocket.

Channel Fan-out Strategies by Channel Type

Slack has three channel types with different fan-out patterns:

// DM (2 users): publish to Redis channel "dm:{userId1}:{userId2}"
// Each WS server subscribed for each of its connected users' DMs
// Fan-out: 2 deliveries max (trivial)

// Group DM (up to 9 users): publish to Redis channel "gdm:{channelId}"
// Fan-out: up to 9 deliveries. Still simple.

// Channel (unlimited members): one Redis Pub/Sub channel per channel_id
// Critical insight: O(WS servers subscribed), NOT O(members)
// 10,000 member channel: if 100 WS servers, publish reaches all 100 servers at once
// Each server fans out to its locally connected members of that channel
// Total: 100 Redis messages (to WS servers) + up to 10,000 WebSocket pushes (per-server parallel)

// For very large channels (100K+ members like announcements):
// Use tiered fan-out: Kafka → Fan-out workers → Redis Pub/Sub (same as live-comments pattern)

Message Ordering — Why Snowflake IDs Are Critical

// Snowflake ID properties:
// 1. Monotonically increasing per worker (41-bit timestamp component)
// 2. Globally unique across workers (10-bit worker component)
// 3. Time-sortable: comparing two Snowflake IDs = comparing timestamps first

// In Cassandra: PRIMARY KEY (channel_id, message_id)
//               CLUSTERING ORDER BY (message_id DESC)
// "Last 50 messages" = SELECT with LIMIT 50, no sort needed — Cassandra already sorted

// Why not UUID v4? UUID is random → no ordering → Cassandra must sort on read
// Why not auto-increment? Not globally unique across DB shards, requires coordination

// Client-side: client_msg_id is client's own UUID for tracking ACKs
// Server assigns message_id (Snowflake) on receipt — this is the canonical ordering ID

Presence System

// Client heartbeat (every 30 seconds):
// WebSocket frame: { "type": "heartbeat" }

// Server on heartbeat receipt:
jedis.set("presence:" + userId, "online", SetParams.setParams().ex(90));
// TTL = 90s = 3× heartbeat interval (tolerates 2 missed heartbeats before going offline)

// Presence subscription for channel:
// WS Server subscribes to Redis: SUBSCRIBE "presence-updates:{workspaceId}"
// When presence key expires (Redis keyspace notification, or poll):
//   Publish: PUBLISH presence-updates:{workspaceId} {"userId": "...", "status": "offline"}
// All servers in workspace receive and push presence_update to their connections

// Status transitions:
// CONNECT → set presence key → publish "online" to workspace
// HEARTBEAT → refresh TTL
// TTL EXPIRES → keyspace notification → publish "offline"
// CLIENT SETS DND → presence key value = "dnd" instead of "online"

// Scale: 500K concurrent users × 30s heartbeat = ~16,600 Redis writes/sec for presence
//        At <1ms per write, Redis handles this on a single node easily

// Timeout handling: if no response in 3s, send ephemeral "command timed out" to sender
// Ephemeral messages: visible only to sender, not stored in Cassandra

✅E — Evaluate3 min

  • Redis Pub/Sub durability: Redis Pub/Sub is not persistent — a message published while no subscriber is connected is lost. Mitigation: write to Cassandra before publishing to Redis. If Redis fails, client can fetch missed messages via REST history API using the last-known message_id as cursor.
  • Large channels (100K+ members): With 100 WS servers each holding some members, a channel publish reaches all 100 servers. Each server iterates its local connections — safe. The bottleneck is Redis → 100 servers: at 1ms per delivery, all servers notified within 1ms. This doesn't scale to 1M subscriber channels — need hierarchical fan-out (like live-comments) at that scale.
  • WS server failure: Load balancer detects unhealthy server. Sticky session routing fails → clients reconnect to a new server via service discovery. Missed messages: client stores last_received_message_id and fetches gap on reconnect via REST.
  • Thundering herd on WS server restart: When a WS server restarts, all its 50K connections reconnect simultaneously. Stagger reconnection using exponential backoff with jitter on the client side.
  • Message ordering guarantee: Snowflake IDs guarantee ordering within a worker. Cross-worker ordering is clock-dependent — if two workers have clock skew, messages may appear out-of-order by milliseconds. Cassandra stores by message_id but Redis Pub/Sub delivers in publish order. Client deduplicates using message_id and re-sorts if needed.

🚀D — Deliver2 min

We designed a real-time chat system handling Slack's scale: 20M DAU, 500K concurrent connections, 5B messages/day. Key decisions: WebSocket with sticky sessions for low-latency delivery; Redis Pub/Sub for O(servers) cross-server channel fan-out; Cassandra partitioned by channel_id with Snowflake ID clustering for ordered message history; heartbeat-TTL presence (90s window tolerating 2 missed heartbeats); pre-signed S3 URLs for file uploads bypassing API server bandwidth; and slash commands via external webhooks with 3s timeout.

⚖️Trade-offs

DecisionChosenAlternativeWhy Chosen
Cross-server routing Redis Pub/Sub Kafka topics per channel Redis: sub-millisecond delivery, simple API, adequate for transient signals. Kafka: persistent, replayable — 5ms+ latency overhead. For 100ms message delivery SLA, Redis wins. Kafka used only for durable notification events.
Message storage Cassandra (wide-column) PostgreSQL + sharding Cassandra: write-heavy (5B/day), horizontal scaling, partition by channel_id gives O(1) message history fetch. PostgreSQL needs careful sharding; every new channel is a new partition concern. Cassandra's eventual consistency is acceptable for chat.
Connection protocol WebSocket (full-duplex) Long-polling or SSE WebSocket: bidirectional (messages + acks + typing indicators in both directions), lower overhead per message. SSE: server→client only, browser reconnects automatically — suitable for read-only feeds. Long-polling: wastes connections, high latency.
Message ID Snowflake (timestamp-based BIGINT) UUID v4 (random) Snowflake: sortable → Cassandra clustering gives natural chronological order with no additional sorting. UUID: random distribution breaks time ordering. Sortable IDs enable efficient cursor-based pagination (WHERE message_id < cursor LIMIT 50).
File upload path Pre-signed S3 URLs (client → S3 direct) Upload through API server Direct S3 upload: zero bandwidth cost on API servers for potentially large files. Files up to 1GB would saturate API server connections if proxied. Pre-signed URLs expire in 10 minutes and are scoped to one specific S3 key.

☕Java Implementation

/**
 * @file WebSocketMessageRouter.java
 * @description Cross-server message routing using Redis Pub/Sub.
 *              Each WS server subscribes to channels for its connected users.
 *              Publishing a message notifies all servers that have channel members.
 *
 * Public API:
 *   registerConnection(userId, channelIds, session) — subscribe to user's channels
 *   deregisterConnection(userId) — unsubscribe and clean up
 *   routeMessage(message, channelId) — publish to Redis for cross-server delivery
 */
public class WebSocketMessageRouter {

    private static final String CHANNEL_PREFIX = "channel:";
    private static final String CONNECTION_REGISTRY_PREFIX = "ws:";
    private static final int CONNECTION_TTL_SECONDS = 300; // 5 min, refreshed on activity

    private final JedisPool jedisPool;
    private final String thisServerId;
    // userId → active WebSocket session (local connections only)
    private final Map<String, WebSocketSession> localConnections = new ConcurrentHashMap<>();
    // channelId → set of userIds connected on this server
    private final Map<String, Set<String>> channelLocalMembers = new ConcurrentHashMap<>();

    public WebSocketMessageRouter(JedisPool jedisPool, String thisServerId) {
        this.jedisPool = jedisPool;
        this.thisServerId = thisServerId;
    }

    /**
     * Called when a user connects via WebSocket.
     * Registers connection locally and subscribes to their channels' Redis topics.
     *
     * @param userId     connecting user
     * @param channelIds all channels this user is a member of
     * @param session    WebSocket session handle
     */
    public void registerConnection(String userId, List<String> channelIds,
                                    WebSocketSession session) {
        localConnections.put(userId, session);

        // Register in Redis: "this user is connected to this server"
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.setex(CONNECTION_REGISTRY_PREFIX + userId,
                        CONNECTION_TTL_SECONDS, thisServerId);
        }

        // Add user to local channel membership index
        for (String channelId : channelIds) {
            channelLocalMembers.computeIfAbsent(channelId, id -> ConcurrentHashMap.newKeySet())
                               .add(userId);
        }

        // Subscribe to Redis channels for each of this user's channels
        // (Only subscribe once per channel_id on this server — many users may share channels)
        subscribeToChannelIfNeeded(channelIds);
    }

    /**
     * Called on disconnect. Removes from local index and Redis registry.
     */
    public void deregisterConnection(String userId, List<String> channelIds) {
        localConnections.remove(userId);

        try (Jedis jedis = jedisPool.getResource()) {
            jedis.del(CONNECTION_REGISTRY_PREFIX + userId);
        }

        for (String channelId : channelIds) {
            Set<String> members = channelLocalMembers.get(channelId);
            if (members != null) {
                members.remove(userId);
                if (members.isEmpty()) {
                    channelLocalMembers.remove(channelId);
                    // Could unsubscribe from Redis channel here if no local members remain
                }
            }
        }
    }

    /**
     * Routes a message to all members of a channel.
     * Publishes to Redis Pub/Sub — all subscribed WS servers deliver to their local members.
     * Write to Cassandra must happen BEFORE calling this method.
     *
     * @param messageJson serialized message JSON
     * @param channelId   target channel
     */
    public void routeMessage(String messageJson, String channelId) {
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.publish(CHANNEL_PREFIX + channelId, messageJson);
        }
        // Redis deliver to all subscribed servers (including this one) asynchronously
        // This server's subscriber callback handles local delivery
    }

    /**
     * Delivers a Redis-received message to all locally connected channel members.
     * Called by the Redis subscriber callback thread.
     */
    private void deliverToLocalChannelMembers(String channelId, String messageJson) {
        Set<String> localMemberIds = channelLocalMembers.getOrDefault(
            channelId, java.util.Collections.emptySet());

        for (String memberId : localMemberIds) {
            WebSocketSession memberSession = localConnections.get(memberId);
            if (memberSession != null && memberSession.isOpen()) {
                sendToSession(memberSession, messageJson);
            } else if (memberSession != null) {
                localConnections.remove(memberId); // stale entry — session closed
            }
        }
    }

    private void sendToSession(WebSocketSession session, String messageJson) {
        try {
            session.sendMessage(new TextMessage(messageJson));
        } catch (IOException ioException) {
            // WebSocket send failed — session likely closed between check and send
            // Log and let the deregister logic handle cleanup on close event
            System.err.println("[WebSocketMessageRouter.sendToSession] Send failed: "
                + ioException.getMessage());
        }
    }

    private void subscribeToChannelIfNeeded(List<String> channelIds) {
        // In production: maintain a single JedisPubSub subscriber per server
        // and call subscribe() with new channels as users join
        // This is simplified for clarity
        Thread.ofVirtual().start(() -> {
            try (Jedis jedis = jedisPool.getResource()) {
                String[] redisChannels = channelIds.stream()
                    .map(id -> CHANNEL_PREFIX + id)
                    .toArray(String[]::new);

                jedis.subscribe(new JedisPubSub() {
                    @Override
                    public void onMessage(String redisChannel, String message) {
                        String channelId = redisChannel.substring(CHANNEL_PREFIX.length());
                        deliverToLocalChannelMembers(channelId, message);
                    }
                }, redisChannels);
            }
        });
    }
}

// ── PresenceService ───────────────────────────────────────────────

/**
 * @file PresenceService.java
 * @description Tracks user online/offline status using Redis TTL-based heartbeats.
 *
 * Public API:
 *   recordHeartbeat(userId) — refreshes TTL, user is online
 *   setStatus(userId, status) — explicit DND/away
 *   getPresence(userId) — current status
 */
public class PresenceService {

    private static final String PRESENCE_KEY_PREFIX = "presence:";
    private static final int PRESENCE_TTL_SECONDS = 90; // 3× 30s heartbeat

    private final JedisPool jedisPool;

    public PresenceService(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }

    /**
     * Client sends heartbeat every 30 seconds over WebSocket.
     * Refreshes the Redis key TTL — user remains "online".
     * When no heartbeat arrives, TTL expires → user goes offline.
     */
    public void recordHeartbeat(String userId) {
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.setex(PRESENCE_KEY_PREFIX + userId, PRESENCE_TTL_SECONDS, "online");
        }
    }

    /**
     * User explicitly sets their status (DND, away, etc).
     * Overrides the "online" default set by heartbeat.
     */
    public void setStatus(String userId, String status) {
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.setex(PRESENCE_KEY_PREFIX + userId, PRESENCE_TTL_SECONDS, status);
        }
    }

    /**
     * Returns the current presence status for a user.
     * Returns "offline" if key doesn't exist (TTL expired or never connected).
     */
    public String getPresence(String userId) {
        try (Jedis jedis = jedisPool.getResource()) {
            String status = jedis.get(PRESENCE_KEY_PREFIX + userId);
            return status != null ? status : "offline";
        }
    }
}
