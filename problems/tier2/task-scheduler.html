Tier 2 — Should Know45 minDistributed systems

Design Distributed Task Scheduler

The core challenge: in a multi-node cluster, how do you ensure a scheduled job runs exactly once? Running on all nodes = duplicate work. Running on none = missed job. Leader election ensures only one node schedules at a time.

🏢 Airbnb, Uber, LinkedIn
⏱️ 45 min interview
⚙️ Leader election

❓R — Requirements3–5 min

Functional Requirements

  • Schedule jobs: one-time (run at T) and recurring (cron expression)
  • Job execution: trigger a webhook URL or push to a message queue
  • Job state tracking: pending, running, succeeded, failed
  • Retry with exponential backoff on failure
  • Cancel or pause scheduled jobs

Non-Functional Requirements

  • At-most-once: No job should execute twice due to scheduler failover
  • At-least-once (for critical jobs): Configurable per job
  • Scale: 100M jobs/day, 10M concurrent scheduled jobs
  • Precision: Jobs fire within 5 seconds of scheduled time

🔢E — Estimation3–5 min

  • 100M jobs/day = ~1,200 executions/sec; each job metadata ~500 bytes → 50GB/day
  • Poll interval: scheduler polls DB every 5s for due jobs → 1,200 jobs/poll → manageable with indexed queries
  • 10M scheduled jobs in DB → index on (status, scheduled_time) essential

🗄️S — Schema3–5 min

jobs:
    job_id          UUID PRIMARY KEY,
    name            VARCHAR(255),
    cron_expression VARCHAR(100),   -- null for one-time jobs
    webhook_url     VARCHAR(500),
    payload         JSONB,
    next_run_at     TIMESTAMP,      -- indexed
    status          ENUM(scheduled, running, succeeded, failed, cancelled),
    retry_count     INT DEFAULT 0,
    max_retries     INT DEFAULT 3,
    last_run_at     TIMESTAMP,
    created_at      TIMESTAMP,
    INDEX (status, next_run_at)     -- critical: scheduler polls this index

🏗️H — High-level Design10 min

  • Scheduler Cluster: Multiple nodes for availability. Leader election via ZooKeeper/etcd. Only the leader polls the DB for due jobs.
  • Leader Election: ZooKeeper ephemeral node: first node to create /scheduler/leader wins. On leader crash, ephemeral node deleted automatically → follower wins election.
  • Job Execution: Leader picks jobs due within next poll interval. Marks status=running (with timestamp). Dispatches to Executor pool via Kafka.
  • Executor Workers: Pull jobs from Kafka. Execute (HTTP webhook call). Update job status. For recurring jobs: compute next_run_at from cron expression and reset to scheduled.
  • Heartbeat: Running jobs must post heartbeat. If no heartbeat for >30s, scheduler marks job failed and triggers retry.

🔌A — APIs5 min

  Body: { name, cronExpression, webhookUrl, payload, maxRetries }

GET  /v1/jobs/{jobId}/executions  // execution history

🔬D — Deep Dive: Leader Election + At-Most-Once10 min

Leader election via ZooKeeper ephemeral nodes:

  1. Each scheduler node tries to create /scheduler/leader (ephemeral, sequential).
  2. ZooKeeper guarantees only one node can create this node at a time.
  3. Winner = leader. Loser watches the node for deletion (to re-elect on leader crash).
  4. Ephemeral node is automatically deleted when the creating session disconnects (leader crash, network partition).

At-most-once execution:

  1. Leader atomically claims a job: UPDATE jobs SET status='running', claimed_by='{leader_id}' WHERE job_id=? AND status='scheduled'
  2. If 0 rows updated: another leader claimed it first (split-brain scenario) → skip.
  3. Only the node that updates the row executes the job.

Zombie jobs: Leader starts job, then crashes before completing. Job stays as status='running' forever. Solution: jobs with status='running' and last_heartbeat older than 30s are re-queued by the new leader (may execute twice in this edge case — trade-off for recovery).

✅E — Evaluate3 min

  • ZooKeeper SPOF: ZooKeeper itself is a 3-node cluster with Raft consensus. etcd is a modern alternative. Both are highly available.
  • DB polling bottleneck: At 1,200 jobs/sec, DB polling every 5s = 6,000 due jobs per poll. Use DB index on (status, next_run_at) — efficient range scan. Partition jobs table by date for hot partition avoidance.

🚀D — Deliver2 min

We designed a distributed task scheduler handling 100M jobs/day. Key decisions: ZooKeeper leader election for single-node scheduling, atomic DB claim for at-most-once execution, Kafka for job dispatch, heartbeat for zombie job detection, and cron expression re-scheduling for recurring jobs.

⚖️Trade-offs

DecisionChosenAlternativeWhy Chosen
Leader electionZooKeeper ephemeral nodesDB-based lockZooKeeper auto-releases lock on crash; DB lock requires timeout-based cleanup which has a gap window
Job dispatchKafka queueDirect HTTP to executorKafka absorbs traffic spikes; executor at-capacity doesn't block scheduling; retry on consumer failure is automatic
At-most-once guaranteeAtomic DB claim (CAS update)Distributed lock per jobCAS in the DB is simpler and eliminates the need for a separate lock service per job

☕Java Implementation

/**
 * JobScheduler — polls for due jobs and claims them atomically.
 * Only runs on the leader node (enforced by ZooKeeper leader election).
 */
public class JobScheduler {
    private static final int POLL_INTERVAL_SECONDS = 5;
    private static final int BATCH_SIZE = 1000;

    private final DataSource dataSource;
    private final KafkaProducer<String, String> kafkaProducer;
    private final String nodeId;

    public JobScheduler(DataSource dataSource, KafkaProducer<String, String> kafkaProducer, String nodeId) {
        this.dataSource = dataSource;
        this.kafkaProducer = kafkaProducer;
        this.nodeId = nodeId;
    }

    /**
     * Main scheduling loop — runs only on the leader.
     * Polls for due jobs, atomically claims them, dispatches to Kafka.
     */
    public void runSchedulingLoop() {
        while (!Thread.currentThread().isInterrupted()) {
            try {
                List<Job> dueJobs = claimDueJobs();
                for (Job job : dueJobs) {
                    dispatchToKafka(job);
                }
                Thread.sleep(POLL_INTERVAL_SECONDS * 1000L);
            } catch (InterruptedException interruptedException) {
                Thread.currentThread().interrupt();
            }
        }
    }

    /**
     * Atomically claims jobs that are due and not yet running.
     * Uses UPDATE … WHERE status='scheduled' to prevent duplicate claims.
     */
    private List<Job> claimDueJobs() {
        String claimSql = "UPDATE jobs SET status='running', claimed_by=?, last_run_at=NOW() " +
                          "WHERE job_id IN (" +
                          "  SELECT job_id FROM jobs WHERE status='scheduled' AND next_run_at <= NOW() LIMIT ?" +
                          ") AND status='scheduled' RETURNING *";

        List<Job> claimedJobs = new ArrayList<>();
        try (Connection connection = dataSource.getConnection();
             PreparedStatement statement = connection.prepareStatement(claimSql)) {
            statement.setString(1, nodeId);
            statement.setInt(2, BATCH_SIZE);
            try (ResultSet resultSet = statement.executeQuery()) {
                while (resultSet.next()) {
                    claimedJobs.add(mapRowToJob(resultSet));
                }
            }
        } catch (SQLException sqlException) {
            System.err.println("[JobScheduler.claimDueJobs] DB error: " + sqlException.getMessage());
        }
        return claimedJobs;
    }

    private void dispatchToKafka(Job job) {
        String jobJson = "{\"jobId\":\"" + job.getJobId() + "\",\"webhookUrl\":\"" + job.getWebhookUrl() + "\"}";
        kafkaProducer.send(new ProducerRecord<>("job-executions", job.getJobId().toString(), jobJson));
    }

    private Job mapRowToJob(ResultSet resultSet) throws SQLException {
        return new Job(
            UUID.fromString(resultSet.getString("job_id")),
            resultSet.getString("webhook_url"),
            resultSet.getString("cron_expression")
        );
    }
}
