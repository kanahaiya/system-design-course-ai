Tier 2 — Should Know 45 min Inventory/Concurrency

Design Hotel Booking System

The hard problem: two users simultaneously book the last available room. Without proper concurrency control, both succeed — double booking. Optimistic locking with a version field is the standard production approach. The two-phase pattern (HOLD → CONFIRM) is the key L6 insight: separate the "claim" from the "commitment".

🏢 Booking.com, Airbnb, Hotels.com
⏱️ 45 min interview
🏨 Inventory concurrency

❓R — Requirements3–5 min

Functional Requirements

  • Search hotels by location, dates, guests — show availability and pricing
  • Book a room: reserve specific room type for date range
  • View and cancel bookings with cancellation policy enforcement
  • Hotel management: add rooms, manage pricing, update availability
  • Dynamic pricing: prices change based on demand and occupancy rate

Non-Functional Requirements

  • No double-booking: A room can only be booked once per date range — the primary correctness requirement
  • Scale: 500M users, 1M bookings/day, 10M search queries/day
  • Latency: Search results <1s; booking confirmation <3s
  • Read/write ratio: 100:1 — search dominates; booking is the rare write
  • Availability of hold: Room held for payment for max 10 minutes, then auto-released
L6 clarification to ask: "Should we support overbooking (airlines do this intentionally at ~10%)?" The answer shapes whether we need strict 1-to-1 inventory or allow a configurable overbook buffer. Airlines book 110 seats for a 100-seat plane.

🔢E — Estimation3–5 min

  • 1M bookings/day = ~12 TPS average; spikes during Black Friday / holiday → 500 TPS
  • 10M searches/day = ~115 search QPS; CDN/cache absorbs most repeated queries
  • Room inventory: 500K hotels × avg 100 rooms × 365 days = 18B availability records/year → Elasticsearch for search, Cassandra for availability grid
  • Active holds at any moment: 500 TPS × 10 min hold window = 300,000 concurrent holds → Redis easily holds this
  • Pricing data: 500K hotels × 100 rooms × 365 days × 8 bytes = ~146GB — fits in Cassandra with replication

Inventory as a Bitset

For efficient date-range availability queries, represent a room's booked status as a bitset — one bit per calendar day. Checking 30-night availability is a single bitwise AND operation across 30 bits rather than 30 individual row reads:

// Room available for [checkIn, checkOut) if bits[checkIn..checkOut-1] are all 0
// Using Java's BitSet:
BitSet bookedDays = loadFromCassandra(roomId);  // one bit per day
BitSet requestedRange = new BitSet();
requestedRange.set(checkInDayOffset, checkOutDayOffset); // set bits for requested nights

// Available if the intersection is empty
boolean isAvailable = !bookedDays.intersects(requestedRange);

// Book: set bits for all requested nights atomically
bookedDays.or(requestedRange);

This is how Airbnb and Booking.com store availability at scale — the entire year of availability for a room fits in 365 bits (~46 bytes). A month's availability is a single 64-bit long comparison.

🏗️H — High-level Design10 min

Figure: Hotel booking system — search path (eventual consistency) vs booking path (strong consistency via two-phase hold)

  • Search Service: Elasticsearch indexed with hotel location (geohash), amenities, room types. Availability pre-computed and cached in Redis. Read-heavy, eventual consistency acceptable.
  • Booking Service: Strong consistency required. PostgreSQL with optimistic locking. Two-phase: HOLD → CONFIRM or RELEASE.
  • Redis Hold Layer: SETNX with 10-minute TTL creates an atomic reservation hold. Room is "claimed" before payment completes.
  • Pricing Service: Dynamic pricing based on occupancy rate (more bookings → higher price), competitor rates, season. Prices cached in Redis (TTL 5 min). On cache miss, computed from base_price × demand_multiplier.
  • Payment Service: Authorization hold on card during booking window. Capture on booking confirmation. Release hold on cancel or expiry.
  • Notification Service: Email/SMS confirmation via event-driven (Kafka consumer).
  • Expiry Job: Scheduled every minute. Scans for bookings with status=on_hold and hold_expires_at < NOW(). Releases inventory and sends user notification.

🔬D — Deep Dive: Two-Phase Booking + Concurrency10 min

The Two-Phase Booking Pattern

Booking a hotel room involves a window of time between "user decides to book" and "payment completes." You must hold the room during this window without permanently committing it. Two-phase booking solves this:

Figure: Two-phase booking state machine — green path = successful booking, red dashed = rollback to available

Phase 1: HOLD — Redis SETNX

// Atomic claim using Redis SETNX (set if not exists)
// Key: "hold:{roomId}:{date}" for each night in range
// TTL: 600 seconds (10 minutes)
// Value: holdId + userId (to validate ownership on confirm)

for (LocalDate night : getAllNightsInRange(checkIn, checkOut)) {
    String holdKey = "hold:" + roomId + ":" + night;
    // SETNX is atomic: only one caller can set this key
    String result = jedis.set(holdKey, holdId + ":" + userId,
        SetParams.setParams().nx().ex(600));
    if (!"OK".equals(result)) {
        // Another user holds this night — release all nights we already claimed
        releasePartialHold(roomId, checkIn, night, holdId);
        throw new RoomUnavailableException("Room held by another user on " + night);
    }
}
// All nights claimed — create DB record
insertHoldRecord(roomId, userId, checkIn, checkOut, holdId);

Phase 2a: CONFIRM — DB Transaction

// On payment success:
// 1. Validate hold ownership in Redis
// 2. Write confirmed booking to PostgreSQL (optimistic lock)
// 3. Delete Redis hold keys (DB is now source of truth)

BEGIN TRANSACTION;
  -- Decrement available count using optimistic lock
  UPDATE room_inventory
  SET booked_count = booked_count + 1, version = version + 1
  WHERE room_id = ? AND date = ? AND version = ? AND booked_count < total_count;
  -- If 0 rows: version mismatch (concurrent booking) → rollback + retry

  UPDATE bookings SET status = 'confirmed', payment_id = ? WHERE booking_id = ?;
COMMIT;

// Delete Redis hold keys (cleanup)
for (LocalDate night : nights) {
    jedis.del("hold:" + roomId + ":" + night);
}

Phase 2b: RELEASE — Timeout or Payment Failure

// Scheduled job: runs every 60 seconds
@Scheduled(fixedDelay = 60_000)
public void releaseExpiredHolds() {
    List<Booking> expiredHolds = bookingRepository.findExpiredHolds();
    for (Booking expiredHold : expiredHolds) {
        // Mark booking as expired in DB
        bookingRepository.updateStatus(expiredHold.getBookingId(), BookingStatus.EXPIRED);
        // Redis keys already expired via TTL — no cleanup needed
        // Notify user
        notificationService.sendHoldExpiredEmail(expiredHold.getUserId());
    }
}

Three Concurrency Approaches Compared

Option A — Pessimistic locking (SELECT FOR UPDATE):

BEGIN;
SELECT * FROM room_inventory WHERE room_id=? AND date BETWEEN ? AND ? FOR UPDATE;
-- holds row lock until transaction commits
UPDATE room_inventory SET booked_count=booked_count+1 WHERE ...;
INSERT INTO bookings ...;
COMMIT;

Problem: row-level lock blocks all concurrent bookings for that room. Under contention, threads queue up — poor throughput. Lock holder crash stalls all waiters.

Option B — Optimistic locking (version field + CAS):

// Read current state including version
SELECT booked_count, total_count, version FROM room_inventory WHERE ...;
// Only update if version hasn't changed (no concurrent modification)
UPDATE room_inventory SET booked_count=booked_count+1, version=version+1
WHERE room_id=? AND date=? AND version=? AND booked_count < total_count;
// If 0 rows updated: version changed → retry

Winner for low contention (most rooms). No lock held; retry on conflict. For hot rooms during a sale (high contention), retry loops amplify DB load.

Option C — Redis SETNX for reservation hold (production choice):

// Redis SETNX is the fastest "first-mover wins" mechanism
// Atomic at the Redis level — no DB involved for the hold phase
String result = jedis.set("hold:" + roomId + ":" + date, holdId,
    SetParams.setParams().nx().ex(600));
boolean holdGranted = "OK".equals(result);

Best of both worlds: Redis SETNX handles the hot-path atomically (no DB load during hold phase), then a single DB write on payment confirmation. Used in production at booking platforms.

Dynamic Pricing

Price increases with demand — the occupancy rate drives a multiplier:

/**
 * Calculates the dynamic price for a room based on current occupancy.
 * Uses tiered multipliers: higher occupancy = higher price.
 * Cached in Redis with 5-minute TTL to avoid constant DB queries.
 */
public BigDecimal calculateDynamicPrice(UUID roomId, LocalDate date) {
    String cacheKey = "price:" + roomId + ":" + date;
    String cachedPrice = jedis.get(cacheKey);
    if (cachedPrice != null) {
        return new BigDecimal(cachedPrice);
    }

    InventoryRow inventory = inventoryRepository.findByRoomIdAndDate(roomId, date);
    double occupancyRate = (double) inventory.getBookedCount() / inventory.getTotalCount();

    double multiplier;
    if (occupancyRate >= 0.90) {
        multiplier = 2.5;       // 90%+ booked → 2.5× base price
    } else if (occupancyRate >= 0.70) {
        multiplier = 1.8;       // 70-90% booked → 1.8× base price
    } else if (occupancyRate >= 0.50) {
        multiplier = 1.3;       // 50-70% booked → 1.3× base price
    } else if (occupancyRate < 0.20 && isWithin3Days(date)) {
        multiplier = 0.7;       // last-minute discount: 30% off
    } else {
        multiplier = 1.0;       // base price
    }

    BigDecimal dynamicPrice = inventory.getBasePrice().multiply(BigDecimal.valueOf(multiplier));
    jedis.setex(cacheKey, 300, dynamicPrice.toPlainString()); // 5-min TTL
    return dynamicPrice;
}

private boolean isWithin3Days(LocalDate date) {
    return date.isBefore(LocalDate.now().plusDays(3));
}

Overbooking Strategy

Airlines routinely overbook at 5–10%. Hotels can too. The key is defining overbook_buffer per room type:

// Allow bookings up to total_count * (1 + overbook_rate)
// overbook_rate = 0.10 means allow 10% more bookings than physical rooms

UPDATE room_inventory
SET booked_count = booked_count + 1, version = version + 1
WHERE room_id = ? AND date = ? AND version = ?
  AND booked_count < (total_count * (1 + overbook_rate));

// When a room is overbooked: compensation policy
// - Upgrade to higher room type (preferred)
// - Move to partner hotel same category
// - Refund + penalty payment to customer

Cancellation Policy Engine

/**
 * Calculates refund amount based on days until check-in.
 * Most hotels: free cancellation >48h before check-in, penalty within 48h.
 */
public BigDecimal calculateCancellationRefund(Booking booking) {
    long daysUntilCheckIn = ChronoUnit.DAYS.between(LocalDate.now(), booking.getCheckIn());

    if (daysUntilCheckIn > 7) {
        return booking.getTotalPrice();                          // full refund
    } else if (daysUntilCheckIn > 2) {
        return booking.getTotalPrice().multiply(new BigDecimal("0.50")); // 50% refund
    } else {
        return BigDecimal.ZERO;                                  // no refund
    }
}

✅E — Evaluate3 min

  • Hot room scenario (Black Friday): 1,000 concurrent requests for 1 room. Redis SETNX serializes: one caller gets "OK", 999 get null → instant "unavailable" response with no DB load. Superior to optimistic locking retry loops under extreme contention.
  • Date range booking: Must hold all nights atomically. If Redis SETNX fails on night 5 of 7, roll back nights 1–4 (delete those Redis keys). Atomic at the night granularity.
  • Hold expiry race: Expiry job + Redis TTL create a small window. DB hold_expires_at is the authoritative source. If Redis key expired but DB hold is still valid (within grace period), honor the DB.
  • Redis failure: If Redis is down, fall back to PostgreSQL pessimistic locking (SELECT FOR UPDATE). Slower but correct. Redis is an optimization, not a correctness requirement.
  • Search availability staleness: Elasticsearch availability may lag by 30–60 seconds (acceptable for search). Always confirm true availability via PostgreSQL on the booking path.

🚀D — Deliver2 min

We designed a hotel booking system with zero double-booking tolerance. Key decisions: two-phase booking (HOLD via Redis SETNX → CONFIRM via PostgreSQL transaction) separates "claiming" from "committing"; optimistic locking with version field prevents concurrent booking of the same physical room; Elasticsearch for geo+amenity search with 30s eventual consistency; dynamic pricing with demand multiplier cached in Redis; and a scheduled expiry job releases stale holds every 60 seconds.

⚖️Trade-offs

DecisionChosenAlternativeWhy Chosen
Hold mechanism Redis SETNX (TTL-based hold) DB pessimistic lock (SELECT FOR UPDATE) Redis hold is non-blocking: 999 concurrent requests get instant rejection rather than queuing. DB lock serializes all requests. Redis degrades gracefully to DB lock on failure.
Confirm locking Optimistic locking (version CAS) Pessimistic locking Confirm phase has low contention (one booking per hold). Optimistic avoids holding locks, scales better under normal load. Redis hold already filtered out 99.9% of concurrent attempts.
Availability storage Bitset per room (one bit/day) Row per room+date in PostgreSQL Bitset enables O(N) range queries (N = number of nights) with a single bitwise AND. Row-per-date requires N individual reads or a range scan. Bitset: ~365 bytes vs ~365 rows per room/year.
Search index Elasticsearch PostgreSQL full-text + PostGIS Geo-search, faceted filtering, full-text on amenities — Elasticsearch excels. PostgreSQL FTS is weaker for complex geo-spatial + filter combinations. ES scales read-horizontally.
Availability replica Cassandra for availability grid PostgreSQL for everything Cassandra partitions by hotel_id: "available rooms for hotel X over dates" is a single partition read. PostgreSQL range scans across 18B records would need careful sharding.

☕Java Implementation

/**
 * @file BookingService.java
 * @description Orchestrates the two-phase hotel booking: HOLD via Redis SETNX,
 *              CONFIRM via PostgreSQL optimistic lock, RELEASE on expiry/failure.
 *
 * Public API:
 *   tryHold(roomId, userId, checkIn, checkOut) — claims room via Redis, returns holdId
 *   confirmBooking(holdId, paymentId) — converts hold to confirmed booking in DB
 *   releaseExpiredHolds() — scheduled job, releases stale holds
 */
public class BookingService {

    private static final String HOLD_KEY_PREFIX = "hold:";
    private static final int HOLD_TTL_SECONDS = 600;    // 10-minute hold window
    private static final int MAX_RETRY_ATTEMPTS = 3;

    private final JedisPool jedisPool;
    private final DataSource dataSource;
    private final NotificationService notificationService;

    public BookingService(JedisPool jedisPool, DataSource dataSource,
                          NotificationService notificationService) {
        this.jedisPool = jedisPool;
        this.dataSource = dataSource;
        this.notificationService = notificationService;
    }

    // ── Phase 1: HOLD via Redis SETNX ────────────────────────────────

    /**
     * Attempts to place a hold on a room for all nights in the date range.
     * Uses Redis SETNX atomically — exactly one concurrent caller succeeds per night.
     *
     * @param roomId   target room
     * @param userId   user placing the hold
     * @param checkIn  first night
     * @param checkOut exclusive end date (night before checkout)
     * @return holdId if successful
     * @throws RoomUnavailableException if any night in the range is already held
     */
    public String tryHold(UUID roomId, UUID userId, LocalDate checkIn, LocalDate checkOut) {
        String holdId = UUID.randomUUID().toString();
        List<LocalDate> requestedNights = getAllNights(checkIn, checkOut);
        List<LocalDate> claimedNights = new ArrayList<>();

        try (Jedis jedis = jedisPool.getResource()) {
            for (LocalDate night : requestedNights) {
                String holdKey = buildHoldKey(roomId, night);
                String holdValue = holdId + ":" + userId;

                // SET NX EX — atomic: set only if key doesn't exist, with TTL
                String redisResult = jedis.set(holdKey, holdValue,
                    SetParams.setParams().nx().ex(HOLD_TTL_SECONDS));

                if (!"OK".equals(redisResult)) {
                    // This night is already claimed — release nights we already set
                    releaseHoldKeys(jedis, roomId, claimedNights);
                    throw new RoomUnavailableException("Room unavailable on " + night);
                }
                claimedNights.add(night);
            }
        }

        // All nights claimed — persist hold record to DB
        persistHoldRecord(roomId, userId, holdId, checkIn, checkOut);
        return holdId;
    }

    // ── Phase 2a: CONFIRM via DB transaction ─────────────────────────

    /**
     * Converts a Redis hold to a confirmed booking in PostgreSQL.
     * Uses optimistic locking to guard against concurrent confirmations.
     * Deletes Redis hold keys after successful DB commit.
     *
     * @param holdId    returned from tryHold()
     * @param paymentId Stripe/PayPal charge reference
     * @return confirmed Booking
     * @throws BookingConflictException if concurrent modification detected after retries
     */
    public Booking confirmBooking(String holdId, String paymentId) {
        HoldRecord holdRecord = loadHoldRecord(holdId);
        validateHoldNotExpired(holdRecord);

        for (int attempt = 0; attempt < MAX_RETRY_ATTEMPTS; attempt++) {
            try {
                Booking confirmed = executeConfirmTransaction(holdRecord, paymentId);
                cleanupHoldKeys(holdRecord);
                return confirmed;
            } catch (OptimisticLockException lockException) {
                if (attempt == MAX_RETRY_ATTEMPTS - 1) {
                    throw new BookingConflictException("Booking conflict after " + MAX_RETRY_ATTEMPTS + " retries");
                }
                sleepBriefly(50L * (attempt + 1));
            }
        }
        throw new BookingConflictException("Booking failed");
    }

    private Booking executeConfirmTransaction(HoldRecord holdRecord, String paymentId) {
        try (Connection connection = dataSource.getConnection()) {
            connection.setAutoCommit(false);
            try {
                List<InventoryRow> inventoryRows = readInventoryRows(
                    connection, holdRecord.getRoomId(), holdRecord.getCheckIn(), holdRecord.getCheckOut());

                validateAvailability(inventoryRows);
                int updatedRows = applyOptimisticLockUpdate(connection, inventoryRows);

                if (updatedRows != inventoryRows.size()) {
                    connection.rollback();
                    throw new OptimisticLockException("Version mismatch on inventory update");
                }

                Booking booking = insertConfirmedBooking(connection, holdRecord, paymentId);
                connection.commit();
                return booking;

            } catch (Exception exception) {
                connection.rollback();
                throw exception;
            }
        } catch (SQLException sqlException) {
            throw new RuntimeException("[BookingService.confirmBooking] DB error", sqlException);
        }
    }

    private int applyOptimisticLockUpdate(Connection connection, List<InventoryRow> rows)
            throws SQLException {
        String sql = "UPDATE room_inventory " +
                     "SET booked_count = booked_count + 1, version = version + 1 " +
                     "WHERE room_id = ? AND date = ? AND version = ? AND booked_count < total_count";
        int totalUpdated = 0;
        try (PreparedStatement statement = connection.prepareStatement(sql)) {
            for (InventoryRow row : rows) {
                statement.setObject(1, row.getRoomId());
                statement.setDate(2, Date.valueOf(row.getDate()));
                statement.setLong(3, row.getVersion());
                totalUpdated += statement.executeUpdate();
            }
        }
        return totalUpdated;
    }

    // ── Phase 2b: RELEASE on expiry ──────────────────────────────────

    /**
     * Scheduled every 60 seconds. Finds bookings with status=ON_HOLD
     * whose hold_expires_at has passed. Marks them EXPIRED.
     * Redis TTL handles key cleanup automatically.
     */
    @Scheduled(fixedDelay = 60_000)
    public void releaseExpiredHolds() {
        List<Booking> expiredHolds = loadExpiredHolds();
        for (Booking expiredHold : expiredHolds) {
            markBookingExpired(expiredHold.getBookingId());
            notificationService.sendHoldExpiredNotification(expiredHold.getUserId());
        }
    }

    // ── Helpers ───────────────────────────────────────────────────────

    private String buildHoldKey(UUID roomId, LocalDate night) {
        return HOLD_KEY_PREFIX + roomId + ":" + night;
    }

    private List<LocalDate> getAllNights(LocalDate checkIn, LocalDate checkOut) {
        List<LocalDate> nights = new ArrayList<>();
        LocalDate current = checkIn;
        while (current.isBefore(checkOut)) {
            nights.add(current);
            current = current.plusDays(1);
        }
        return nights;
    }

    private void releaseHoldKeys(Jedis jedis, UUID roomId, List<LocalDate> nights) {
        for (LocalDate night : nights) {
            jedis.del(buildHoldKey(roomId, night));
        }
    }

    private void cleanupHoldKeys(HoldRecord holdRecord) {
        List<LocalDate> nights = getAllNights(holdRecord.getCheckIn(), holdRecord.getCheckOut());
        try (Jedis jedis = jedisPool.getResource()) {
            releaseHoldKeys(jedis, holdRecord.getRoomId(), nights);
        }
    }

    private void validateHoldNotExpired(HoldRecord holdRecord) {
        if (holdRecord.getHoldExpiresAt().isBefore(Instant.now())) {
            throw new HoldExpiredException("Hold " + holdRecord.getHoldId() + " has expired");
        }
    }

    private void sleepBriefly(long milliseconds) {
        try {
            Thread.sleep(milliseconds);
        } catch (InterruptedException interruptedException) {
            Thread.currentThread().interrupt();
        }
    }
    // readInventoryRows, persistHoldRecord, loadHoldRecord, loadExpiredHolds,
    // markBookingExpired, insertConfirmedBooking — standard JDBC, omitted for brevity
}
