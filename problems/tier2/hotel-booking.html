Tier 2 — Should Know 45 min Inventory/Concurrency

Design Hotel Booking System

The hard problem: two users simultaneously book the last available room. Without proper concurrency control, both succeed — double booking. Optimistic locking with a version field is the standard production approach.

🏢 Booking.com, Airbnb, Hotels.com
⏱️ 45 min interview
🏨 Inventory concurrency

❓R — Requirements3–5 min

Functional Requirements

  • Search hotels by location, dates, guests — show availability and pricing
  • Book a room: reserve specific room type for date range
  • View and cancel bookings
  • Hotel management: add rooms, manage pricing, update availability

Non-Functional Requirements

  • No double-booking: A room can only be booked once per date range — the primary correctness requirement
  • Scale: 500M users, 1M bookings/day, 10M search queries/day
  • Latency: Search results <1s; booking confirmation <3s
  • Read/write ratio: 100:1 — search dominates; booking is the rare write

🔢E — Estimation3–5 min

  • 1M bookings/day = ~12 TPS average; spikes during sales → 500 TPS
  • 10M searches/day = ~115 search QPS; CDN/cache absorbs most repeated queries
  • Room inventory: 500K hotels × avg 100 rooms × 365 days = 18B availability records/year → ElasticSearch for search, PostgreSQL for booking

🗄️S — Schema3–5 min

// PostgreSQL — booking (ACID required for no double-booking)
hotels: hotel_id, name, location, star_rating, amenities
rooms: room_id, hotel_id, room_type, capacity, price_per_night

// Key: version field enables optimistic locking
room_inventory:
    room_id         UUID,
    date            DATE,
    total_count     INT,  -- total rooms of this type available
    booked_count    INT,  -- currently booked
    version         BIGINT DEFAULT 0,  -- incremented on every update
    PRIMARY KEY (room_id, date)

bookings:
    booking_id   UUID PRIMARY KEY,
    user_id      UUID,
    room_id      UUID,
    check_in     DATE,
    check_out    DATE,
    status       ENUM(pending, confirmed, cancelled),
    total_price  DECIMAL(10,2),
    created_at   TIMESTAMP

🏗️H — High-level Design10 min

  • Search Service: ElasticSearch indexed with hotel location, amenities, room types. Availability pre-computed and cached. Read-heavy, eventual consistency acceptable.
  • Booking Service: Strong consistency required. PostgreSQL with optimistic locking. Checks availability, creates booking, decrements inventory in one transaction.
  • Pricing Service: Dynamic pricing based on demand, season, competitor rates. Caches prices in Redis (TTL 5 min).
  • Payment Service: Authorization hold on card during booking window. Capture on check-in. Release hold on cancellation.
  • Notification Service: Email/SMS confirmation via event-driven (Kafka consumer).

🔬D — Deep Dive: Preventing Double-Booking10 min

Three approaches, one winner:

Option A — Pessimistic locking (SELECT FOR UPDATE):

BEGIN;
SELECT * FROM room_inventory WHERE room_id=? AND date BETWEEN ? AND ? FOR UPDATE;
-- holds row lock until transaction commits
UPDATE room_inventory SET booked_count=booked_count+1 WHERE ...;
INSERT INTO bookings ...;
COMMIT;

Problem: row-level lock blocks all concurrent bookings for that room. Under contention, threads queue up — poor throughput.

Option B — Optimistic locking (version field + CAS):

// Read current state including version
SELECT booked_count, total_count, version FROM room_inventory WHERE ...;
// Only update if version hasn't changed (no concurrent modification)
UPDATE room_inventory SET booked_count=booked_count+1, version=version+1
WHERE room_id=? AND date=? AND version=? AND booked_count < total_count;
// If 0 rows updated: version changed → retry

Winner for low contention (most rooms). No lock held; retry on conflict. For hot rooms during a sale (high contention), retry loops become expensive.

Option C — Redis atomic decrement: Store available_count in Redis. DECR → if result < 0, INCR back and reject. Fast but requires Redis→DB sync.

✅E — Evaluate3 min

  • Hot room scenario (Black Friday): 1,000 concurrent requests for 1 room. Optimistic locking → 999 retries, 1 succeeds. Under extreme contention, consider Redis-based request queue to serialize access.
  • Date range booking: Must check availability for every night in the range atomically. Optimistic lock all rows in the range; if any row update fails, rollback the whole booking.

🚀D — Deliver2 min

We designed a hotel booking system with zero double-booking tolerance. Key decisions: optimistic locking with version field for low-contention booking atomicity, ElasticSearch for availability search, Redis for pricing cache, and a payment authorization-hold pattern for risk management.

⚖️Trade-offs

DecisionChosenAlternativeWhy Chosen
Double-booking preventionOptimistic locking (version CAS)Pessimistic locking (SELECT FOR UPDATE)Most bookings have low contention. Optimistic avoids holding locks, scales better. Pessimistic only better when contention is consistently high.
Search storageElasticSearchPostgreSQL full-textGeo-search, faceted filtering, full-text search on amenities — ElasticSearch excels. PostgreSQL FTS is weaker for geo-spatial queries.
Payment timingAuthorize on booking, capture on check-inCharge immediatelyAuthorization holds funds without charging. If booking is cancelled before check-in, the hold releases automatically — no refund needed.
Availability dataSeparate room_inventory tableQuery bookings table to compute availabilityPre-materialized availability avoids expensive COUNT queries across bookings on every search.

☕Java Implementation

/**
 * BookingService — prevents double-booking via optimistic locking.
 * The version field acts as a compare-and-swap guard:
 * only the first concurrent transaction to update wins; others retry.
 */
public class BookingService {

    private static final int MAX_RETRY_ATTEMPTS = 3;
    private final DataSource dataSource;

    public BookingService(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    /**
     * Creates a booking for a room over a date range.
     * Uses optimistic locking to prevent double-booking under concurrent requests.
     *
     * @throws BookingConflictException if room unavailable or all retries exhausted
     */
    public Booking createBooking(UUID roomId, UUID userId, LocalDate checkIn, LocalDate checkOut) {
        for (int attempt = 0; attempt < MAX_RETRY_ATTEMPTS; attempt++) {
            try {
                return attemptBooking(roomId, userId, checkIn, checkOut);
            } catch (OptimisticLockException lockException) {
                if (attempt == MAX_RETRY_ATTEMPTS - 1) {
                    throw new BookingConflictException("Room no longer available after " + MAX_RETRY_ATTEMPTS + " attempts");
                }
                // Brief pause before retry to reduce thundering herd
                sleepBriefly(50 * (attempt + 1));
            }
        }
        throw new BookingConflictException("Booking failed after retries");
    }

    private Booking attemptBooking(UUID roomId, UUID userId, LocalDate checkIn, LocalDate checkOut) {
        try (Connection connection = dataSource.getConnection()) {
            connection.setAutoCommit(false);
            try {
                // Step 1: Read current inventory with version for all nights in date range
                List<InventoryRow> inventoryRows = readInventoryWithVersion(connection, roomId, checkIn, checkOut);
                validateAvailability(inventoryRows);

                // Step 2: Optimistic update — only succeeds if version unchanged
                int updatedRowCount = updateInventoryWithVersionCheck(connection, inventoryRows);
                if (updatedRowCount != inventoryRows.size()) {
                    connection.rollback();
                    throw new OptimisticLockException("Concurrent modification detected");
                }

                // Step 3: Create booking record
                Booking booking = insertBooking(connection, roomId, userId, checkIn, checkOut);
                connection.commit();
                return booking;

            } catch (Exception exception) {
                connection.rollback();
                throw exception;
            }
        } catch (SQLException sqlException) {
            throw new RuntimeException("[BookingService.attemptBooking] DB error", sqlException);
        }
    }

    private int updateInventoryWithVersionCheck(Connection connection, List<InventoryRow> inventoryRows)
            throws SQLException {
        int totalUpdated = 0;
        String updateSql = "UPDATE room_inventory SET booked_count = booked_count + 1, version = version + 1 " +
                           "WHERE room_id = ? AND date = ? AND version = ? AND booked_count < total_count";

        try (PreparedStatement statement = connection.prepareStatement(updateSql)) {
            for (InventoryRow row : inventoryRows) {
                statement.setObject(1, row.getRoomId());
                statement.setDate(2, Date.valueOf(row.getDate()));
                statement.setLong(3, row.getVersion()); // CAS: only update if version matches
                totalUpdated += statement.executeUpdate();
            }
        }
        return totalUpdated; // If < inventoryRows.size(), a version mismatch occurred
    }

    private void validateAvailability(List<InventoryRow> inventoryRows) {
        for (InventoryRow row : inventoryRows) {
            if (row.getBookedCount() >= row.getTotalCount()) {
                throw new RoomUnavailableException("Room fully booked on " + row.getDate());
            }
        }
    }

    private void sleepBriefly(long milliseconds) {
        try {
            Thread.sleep(milliseconds);
        } catch (InterruptedException interruptedException) {
            Thread.currentThread().interrupt();
        }
    }

    // InventoryRow, Booking, BookingConflictException, OptimisticLockException,
    // RoomUnavailableException are value objects / domain exceptions (not shown for brevity)
}
