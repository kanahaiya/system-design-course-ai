Tier 2 — Should Know 45 min Collaborative editing

Design Google Docs (Collaborative Editing)

Google Docs' hardest problem: two users edit the same character position simultaneously. Without conflict resolution, one user's change silently overwrites the other. Operational Transformation (OT) solves this by transforming every incoming operation to account for concurrent changes — guaranteeing all clients converge to identical state regardless of network ordering.

🏢 Google, Notion, Figma, Linear
⏱️ 45 min interview
📝 Real-time collaboration

❓R — Requirements 3–5 min

Interviewer signal: Start by locking in the hardest constraint: "Does every user need to see exactly the same document state, or is eventual consistency acceptable?" For collaborative editing, convergence is non-negotiable — this drives the entire architecture toward OT or CRDT.

Functional Requirements (Scope these first)

  • Real-time collaborative text editing — multiple users editing simultaneously, changes propagated within <500ms
  • Cursor presence — see where other active users are editing, with a colored cursor and username label
  • Version history — view named revisions, diff between any two revisions, restore to any past state
  • Permission model — owner, editor, commenter, viewer; link-sharing with access levels
  • Offline editing — changes buffered locally, merged automatically on reconnect (no manual conflict resolution for the user)
  • Comments and suggestions — threaded comments anchored to text ranges, suggestion mode that shows tracked changes

Non-Functional Requirements (These define the hard constraints)

  • Convergence (strongest guarantee): All clients must converge to identical document state after all operations are delivered — this is the core invariant; no user's edit is silently lost
  • Latency: Local edits appear instantly (optimistic UI, no round-trip); remote edits propagated in <100ms P99 on the same continent
  • Scale: 1 billion documents, 100 million concurrent editors, peak ~10 million documents with active concurrent editing
  • Durability: Zero operation loss — every keystroke must be durably committed; RPO = 0
  • Availability: 99.99% for document reads; brief degradation of live sync is acceptable during partial outages (users continue editing with queued ops)

What to explicitly out-of-scope in the interview

  • Rich text formatting details (bold, italic — same OT principles, just more operation types)
  • Spreadsheet formulas (Google Sheets is a separate, more complex problem)
  • Full-text search across all documents
  • Mobile-specific offline sync (same design, different client)

Key Design Implication

The broadcast fan-out (8.3M msgs/sec outbound) is the hardest scaling problem — not the inbound operation rate. A single collaboration server can only hold ~100K WebSocket connections. With 10M concurrent editors, we need ~100 collaboration server instances per region, with a router layer that maps doc_id → server_instance (sticky routing by document).

🗄️S — Schema 5–7 min

Key insight: Google Docs uses a log-structured storage model (Event Sourcing). The operation log is the source of truth. The current document state is a materialized view derived by replaying all operations from the last snapshot. This enables time travel, version history, and crash recovery for free.

Operation log — Cassandra (append-only, high write throughput, partition by document)

-- Cassandra table (CQL syntax)
-- Partition key = doc_id: all ops for one doc on same node = fast range scans
-- Clustering key = revision: monotonically increasing, server-assigned
CREATE TABLE operations (
    doc_id      UUID,
    revision    BIGINT,                    -- server-side global counter per document
    user_id     UUID,
    client_id   TEXT,                      -- UUID per browser session (for de-duplication)
    op_type     TEXT,                      -- 'insert' | 'delete' | 'retain' (for rich text)
    position    INT,                       -- character offset in the document
    content     TEXT,                      -- for insert: the inserted string; for delete: null
    length      INT,                       -- for delete: number of characters to remove
    base_rev    BIGINT,                    -- client's revision when this op was created (for OT)
    applied_at  TIMESTAMP,
    PRIMARY KEY (doc_id, revision)         -- range scan: SELECT WHERE doc_id=? AND revision > ?
) WITH CLUSTERING ORDER BY (revision ASC)
  AND compaction = {'class': 'LeveledCompactionStrategy'};  -- fast range reads

-- Index for client de-duplication (prevent replay on reconnect)
CREATE INDEX ON operations (doc_id, client_id, base_rev);

🏗️H — High-level Design 10 min

Architecture Overview

Component Responsibilities

1. Client (Browser/Mobile)

  • Optimistic local application: Every keystroke is applied to the local document immediately — zero latency for the typing user. The op is simultaneously queued for server transmission.
  • Client state machine: The client tracks two states — synchronized (no unacknowledged ops) and pending (ops sent but not yet ACK'd). While pending, any new local ops are buffered and not sent until the pending op is ACK'd. This prevents ordering chaos.
  • Transform on receipt: When the server broadcasts another user's op, the client transforms it against any pending/buffered ops before applying it to the local document.

2. WebSocket Router (Sticky routing by doc_id)

  • Maintains a routing table: doc_id → collab_server_instance_id
  • All connections for the same document MUST go to the same collaboration server — this is required for OT correctness, because the collab server maintains the per-document operation queue in memory
  • When a collab server fails, the router reassigns the doc to another instance and that instance loads the latest snapshot + op log to reconstruct state

3. Collaboration Server (The OT engine)

  • Holds in-memory state for all active documents: a map of doc_id → {revision, in-flight ops, connected session IDs}
  • Receives an op from Client A with base_revision=N
  • Fetches all server-side ops from revision N+1 to current from its in-memory queue (or Cassandra if not cached)
  • Transforms the incoming op against each of those ops sequentially (the diamond problem — explained in Deep Dive)
  • Assigns the next revision number atomically (in-memory counter, flushed to Cassandra)
  • Persists the transformed op to Cassandra, then broadcasts to all other sessions on the same document

4. Snapshot Worker

  • Monitors the operations log per document. When a document accumulates 1,000 new operations since its last snapshot, the worker materializes the current state and writes it to S3
  • Updates documents.snapshot_rev in PostgreSQL to point to the new snapshot revision
  • Without this, loading a 3-year-old document would require replaying millions of operations — unacceptable latency

5. Document Load Path

  1. REST call to fetch the document: returns snapshot_rev and the S3 snapshot URL
  2. Client downloads and decompresses the S3 snapshot (the base state)
  3. Client fetches operations from Cassandra: WHERE doc_id=? AND revision > snapshot_rev
  4. Client applies all ops in revision order to the snapshot — now at current state
  5. Client upgrades to WebSocket for live sync

     → { content: "full document text at this revision" }
     // Server replays from nearest snapshot to requested revision

     → { new_revision: 301 }
     // Inserts a special RESTORE op into the log — does not delete history

L6 note — RESTORE as an operation: Restoring to a past revision is NOT implemented by truncating the operation log (which would violate durability and audit requirements). Instead, the system inserts a RESTORE operation at the current head that says "set document content to revision 150's state." This preserves full history and allows you to undo the restore.

🔬D — Deep Dive: OT, CRDT, Presence, and Offline Sync 10–12 min

1. Operational Transformation — The Core Algorithm

Google's choice: Google Docs uses OT, not CRDT. The server serializes all operations — every op passes through a single coordination point per document. This is acceptable because Google controls the infrastructure and can guarantee low latency to that server. CRDT is preferred for peer-to-peer systems (Figma, Linear) where you cannot assume a reliable central coordinator.

OT defines two fundamental operation types for a text document:

  • Insert(position, text) — insert text at character offset position
  • Delete(position, length) — delete length characters starting at position

The invariant OT must preserve is called CP1 (Convergence Property 1):

For any two concurrent operations op1 and op2:
apply(apply(doc, op1), transform(op2, op1)) ≡ apply(apply(doc, op2), transform(op1, op2))

In plain English: if both users start from the same document, apply their own op, and then apply the other's transformed op — they must reach the exact same document state.

The OT Diamond Problem — Visualized

OT Transform Rules — Full Table

The transform(op_a, op_b) function returns a new op_a' that can be correctly applied after op_b has already been applied:

op_a (to transform)op_b (already applied)Transformed op_a'Reason
Insert(posA, text) Insert(posB, textB) If posB ≤ posA: Insert(posA + len(textB), text)
Else: Insert(posA, text)		 B's insert before A shifts A's target position right
Insert(posA, text) Delete(posB, lenB) If posB < posA: Insert(posA - min(lenB, posA-posB), text)
If posB ≥ posA: unchanged		 B deleted characters before A's target — shift A left by deleted amount
Delete(posA, lenA) Insert(posB, textB) If posB ≤ posA: Delete(posA + len(textB), lenA)
Else: unchanged		 B's insert shifted the characters A wants to delete
Delete(posA, lenA) Delete(posB, lenB) Complex: adjust posA and shrink lenA to account for overlap (see implementation) Overlapping deletes must not double-delete; both users deleting the same text = no-op for the second

Server-Side OT: The Complete Flow

// Pseudocode for the server's operation processing loop (per document)
void receiveOperation(IncomingOp incomingOp) {
    // incomingOp.baseRevision = the revision the client was at when they typed this
    // serverRevision = current committed revision for this document

    List<Operation> concurrentOps =
        operationLog.getRange(incomingOp.docId,
                              fromRevision = incomingOp.baseRevision + 1,
                              toRevision = serverRevision);

    // Transform the incoming op against every op that was committed
    // on the server since the client's base revision
    Operation transformedOp = incomingOp.op;
    for (Operation serverOp : concurrentOps) {
        transformedOp = transform(transformedOp, serverOp);
    }

    // Atomically assign the next revision and persist
    long newRevision = ++serverRevision;
    operationLog.append(incomingOp.docId, newRevision, transformedOp);

    // Send ACK to the original sender
    sender.sendAck(incomingOp.clientId, newRevision);

    // Broadcast the transformed op to all other editors of this document
    broadcastToOtherEditors(incomingOp.docId, incomingOp.clientId,
                            newRevision, transformedOp);
}

2. CRDT — The Alternative: Replicated Growable Array (RGA)

CRDT (Conflict-free Replicated Data Type) embeds merge semantics into the data structure itself. The RGA variant handles text sequences by assigning each character a globally unique identifier (a logical clock + site ID tuple), creating a total order that all replicas can agree on without coordination.

How RGA works for concurrent inserts:

  • Each character is a node: {id: (timestamp, siteId), value: char, prev: id}
  • Insert means "insert this character after the character with id prev"
  • If two users both insert after the same character (prev is the same), the tie-break is deterministic: the character with the higher (timestamp, siteId) goes first
  • Because the tie-break is deterministic and depends only on the operations themselves (not on delivery order), any two replicas that receive the same set of operations will converge to the same sequence — without needing a server
OT vs CRDT — The real trade-off:

OT requires server serialization — all ops flow through a single server that transforms and orders them. This means the server is a single point of failure per document (mitigated by failover), and all clients must be online to commit. However, the document representation is just a string — no metadata overhead per character.

CRDT (RGA) is peer-to-peer — any two replicas can sync directly. Figma uses this for vector design objects. However, every character carries metadata (the unique ID + prev pointer), which can make the document 3–5× larger in memory. RGA also accumulates "tombstones" — deleted characters remain in the structure (just marked invisible) to preserve the ordering invariant. Long-lived documents accumulate significant tombstone overhead.

Google chose OT because: (1) they control the infrastructure and can guarantee low-latency server access, (2) no tombstone overhead, (3) OT's correctness for plain text is well-understood and proven. Figma chose CRDT because their design objects need peer-to-peer sync across potentially disconnected clients, and the metadata overhead for vector graphics objects (which are large already) is relatively small.

3. WebSocket Architecture — Sticky Sessions

Why sticky sessions are required for OT correctness:

  • The collaboration server maintains the per-document operation queue and current revision counter in memory. This in-memory state is what enables fast transforms without hitting the database on every operation.
  • If two operations for the same document went to two different servers, each server would have an incomplete view of the concurrent ops — producing incorrect transform results.
  • The sticky routing rule: hash(doc_id) mod num_servers routes all connections for the same document to the same server.
  • On failover: the new server loads the document's operation log from Cassandra and rebuilds in-memory state (at most 1,000 ops since last snapshot).

Connection lifecycle:

// Client WebSocket connection state machine
enum ClientState {
    CONNECTING,
    LOADING_SNAPSHOT,   // downloading S3 snapshot
    REPLAYING_OPS,      // fetching ops from snapshot_rev to current_rev
    SYNCHRONIZED,       // no pending ops, fully caught up
    PENDING,            // one op in-flight (sent, not ACK'd)
    BUFFERING,          // pending op not yet ACK'd, new ops buffered locally
    RECONNECTING        // WebSocket dropped, attempting reconnect
}

// Only ONE op is ever in-flight at a time (pending state).
// While an op is pending, new keystrokes go into a buffer.
// On ACK, the buffered ops are transformed against the ACK'd revision
// and the first buffered op is sent.

4. Presence System — Colored Cursors

The presence system is decoupled from the OT operation log because cursor positions are ephemeral — they don't need durability, just low latency.

  • Client sends cursor updates via the same WebSocket connection, but as a separate message type ("type": "cursor"), not as an operation in the log.
  • Collab server receives cursor updates and writes them to Redis: HSET presence:{doc_id}:{user_id} cursor_pos 247 ... EX 30
  • Server broadcasts the cursor update to all other editors on the document immediately (via their WebSocket connections)
  • Cursor positions need OT too: If User A has their cursor at position 50, and User B inserts 5 characters at position 30, A's cursor must shift to position 55. The client applies the same transform logic to cursor positions when receiving operations from other users.
  • Color assignment: Each user's cursor color is deterministically derived from a hash of their user_id — same color on every session, no coordination needed.

5. Offline Editing and Reconnect Merge

This is where OT shines over simpler last-write-wins approaches:

  1. User goes offline at revision = 500. They continue typing — 20 local operations are buffered in the client.
  2. Meanwhile, the server processes operations from other users: revisions 501 through 560.
  3. User reconnects. Client sends buffered ops, each tagged with base_revision = 500.
  4. Server transforms each buffered op against ops 501–560 in sequence, assigns new revision numbers (561–580), persists, and broadcasts.
  5. Client receives ACKs and the server's ops 501–560. Client transforms the server's ops against its own pending ops (the same diamond-transform, from the client's perspective) and applies them to the local document.
  6. Result: the user's offline edits are merged correctly — no data lost, no manual conflict resolution required.
Why not just "last write wins"? LWW would silently discard one user's work whenever two users edit nearby positions. For a word processor, that's catastrophic. OT guarantees that every user's intent is preserved — both users' text appears in the document, at the correct positions relative to each other.

6. Document Versioning — Snapshot + Delta

Loading a document that was edited 2 years ago without efficient versioning would require replaying millions of operations. The snapshot + delta model solves this:

StrategyLoad time for old docStorage costComplexity
Full log replay from op 0O(N) operations — potentially minutesJust the logSimple
Snapshot + delta (chosen)O(1,000) ops max (since last snapshot)Log + snapshots (~2× storage)Snapshot worker needed
Store only current stateO(1) — just fetch the stateMinimalNo history, no version restore

The snapshot worker is a background service that:

  1. Polls Cassandra for documents where current_rev - snapshot_rev > 1000
  2. Replays operations from snapshot_rev to current_rev to materialize the current text
  3. Compresses with gzip (~10:1 ratio for text) and uploads to S3 with path snapshots/{doc_id}/{current_rev}.json.gz
  4. Updates documents.snapshot_rev = current_rev atomically

✅E — Evaluate 3 min

Does the design satisfy each requirement?

RequirementHow it's satisfiedRisk / edge case
Convergence (strongest) Server-side OT with a single server per document provides proven CP1 convergence. All clients apply the same sequence of transformed operations. Requires sticky routing — if two ops for the same doc land on different servers, correctness breaks. Mitigated by consistent hash routing.
Latency <500ms for remote edits Local edit: instant (optimistic). Remote: WebSocket push → no polling. Typical RTT is 20–80ms. Transform + persist + broadcast adds ~10ms. Mitigation: shard high-collaboration docs across multiple collab servers using sub-document partitioning (by paragraph range).
Zero operation loss (RPO = 0) Cassandra is synchronously written to quorum (QUORUM write) before ACK is sent to client. No op is ACK'd until it's durably committed on 2 of 3 replicas. Client doesn't retry until it receives an ACK — this ensures no duplicate ops from network timeouts.
Version history and restore Append-only log provides complete history. Named versions in PostgreSQL. Restore inserts a RESTORE op rather than truncating history. Restoring a very old version of a large document requires replaying from a distant snapshot — mitigated by writing an intermediate snapshot immediately before the restore.
Offline editing Client buffers ops locally during disconnect; on reconnect, sends all ops tagged with the offline base_revision. Server transforms each against concurrent server ops. If offline >1 hour on a highly active document (many concurrent editors), the transform chain is very long. Mitigation: cap at 500 offline ops and surface a merge UI if exceeded.

Failure scenarios

  • Collab server crash: The router detects the failure (TCP RST to all connected clients). Clients reconnect; router hashes their doc_id to a different live server. That server loads the last 1,000 ops from Cassandra, rebuilds in-memory state, and begins accepting connections. Clients resend any unACK'd ops with their base_revision — server transforms and applies normally.
  • Cassandra write failure: The collab server retries with exponential backoff. The op is NOT broadcast until it is durably committed. Clients do not see their ACK and retry (idempotent via client_id + base_rev deduplication).
  • Network partition between regions: Clients route to the nearest region's collab server. If the global router is partitioned, documents may temporarily have two active collab servers (split-brain). This breaks OT correctness. Mitigation: use a distributed lock (Zookeeper/etcd) to ensure only one collab server is active per document globally. On partition, the secondary server rejects operations with a 503 — clients queue locally and retry when partition heals.

🚀D — Deliver 2 min

We designed Google Docs to support 1B documents and 10M concurrent editors. The key architectural decisions:

  1. Server-side OT for conflict resolution — each document has a single authoritative collab server that transforms and serializes all operations, providing proven convergence with a simple text-only document representation.
  2. Append-only operation log in Cassandra — partitioned by doc_id, clustered by revision. This is the durable source of truth, enables offline merge, and supports version history without any additional infrastructure.
  3. Snapshot + delta loading — periodic S3 snapshots every 1,000 ops ensure document load time stays bounded regardless of document age.
  4. Sticky WebSocket routing by doc_id — required for OT correctness; the collab server's in-memory state must see all operations for a document.
  5. Redis-backed presence system — ephemeral cursor state with 30s TTL, decoupled from the durable operation log.

The most critical scalability constraint is the fan-out of operation broadcasts. At 10M concurrent editors with an average of 5 co-editors per document, the system must push 8.3M messages/sec — this drives the horizontal scaling of collab servers and the choice of long-lived WebSocket connections over polling.

Operation value objects

/**
 * @file Operation.java
 * @description Immutable value object representing a single text editing operation.
 *              Operations are the atomic unit of the OT log — Insert or Delete at a position.
 *
 * @requires none
 *
 * Public API:
 *   Operation.insert(position, content) — creates an Insert operation
 *   Operation.delete(position, length)  — creates a Delete operation
 *   getType(), getPosition(), getContent(), getLength() — field accessors
 */
public final class Operation {

    public enum Type { INSERT, DELETE }

    private final Type type;
    private final int position;
    private final String content;  // non-null for INSERT; null for DELETE
    private final int length;      // 0 for INSERT; chars to remove for DELETE

    private Operation(Type type, int position, String content, int length) {
        this.type = type;
        this.position = position;
        this.content = content;
        this.length = length;
    }

    public static Operation insert(int position, String content) {
        if (content == null || content.isEmpty()) {
            throw new IllegalArgumentException("Insert content must be non-empty");
        }
        return new Operation(Type.INSERT, position, content, 0);
    }

    public static Operation delete(int position, int length) {
        if (length <= 0) {
            throw new IllegalArgumentException("Delete length must be positive");
        }
        return new Operation(Type.DELETE, position, null, length);
    }

    public Type getType()       { return type; }
    public int getPosition()    { return position; }
    public String getContent()  { return content; }
    public int getLength()      { return length; }

    @Override
    public String toString() {
        return type == Type.INSERT
            ? String.format("Insert('%s', pos=%d)", content, position)
            : String.format("Delete(pos=%d, len=%d)", position, length);
    }
}

The transform() function — the core of OT

/**
 * @file OperationalTransformer.java
 * @description Implements the OT transform function for text editing operations.
 *              transform(opA, opB) returns opA' such that:
 *              apply(apply(doc, opB), opA') == apply(apply(doc, opA), transform(opB, opA))
 *              This is the CP1 (Convergence Property 1) guarantee.
 *
 * @requires Operation.java
 *
 * Public API:
 *   transform(operationA, operationB) — transforms opA against concurrent opB, returns opA'
 */
public class OperationalTransformer {

    /**
     * Transforms operationA so it can be correctly applied after operationB has already
     * been applied. Returns a new Operation — the original is never mutated.
     *
     * @param operationA  the operation to transform (client's pending op)
     * @param operationB  the concurrent operation already applied by the server
     * @return transformed operationA that accounts for operationB's effect
     */
    public Operation transform(Operation operationA, Operation operationB) {
        if (operationA.getType() == Operation.Type.INSERT) {
            return operationB.getType() == Operation.Type.INSERT
                ? transformInsertAgainstInsert(operationA, operationB)
                : transformInsertAgainstDelete(operationA, operationB);
        } else {
            return operationB.getType() == Operation.Type.INSERT
                ? transformDeleteAgainstInsert(operationA, operationB)
                : transformDeleteAgainstDelete(operationA, operationB);
        }
    }

    /**
     * Insert vs Insert:
     * If B inserted at or before A's position, A's position shifts right by B's length.
     * Tie-break: if both insert at the exact same position, B goes first (server priority),
     *            so A shifts right.
     */
    private Operation transformInsertAgainstInsert(Operation insertA, Operation insertB) {
        int transformedPosition = insertA.getPosition();
        if (insertB.getPosition() <= insertA.getPosition()) {
            transformedPosition += insertB.getContent().length();
        }
        return Operation.insert(transformedPosition, insertA.getContent());
    }

    /**
     * Insert vs Delete:
     * If B deleted characters entirely before A's position, shift A left by deleted length.
     * If B's delete range overlaps A's position, A moves to where B's deletion started.
     */
    private Operation transformInsertAgainstDelete(Operation insertA, Operation deleteB) {
        int posA = insertA.getPosition();
        int posB = deleteB.getPosition();
        int lenB = deleteB.getLength();

        if (posB >= posA) {
            // B's deletion is entirely after A's position — A is unaffected
            return insertA;
        }

        // B deleted some characters before A's position
        int charsDeletedBeforeA = Math.min(lenB, posA - posB);
        return Operation.insert(posA - charsDeletedBeforeA, insertA.getContent());
    }

    /**
     * Delete vs Insert:
     * If B inserted at or before A's deletion point, shift A's position right.
     */
    private Operation transformDeleteAgainstInsert(Operation deleteA, Operation insertB) {
        int transformedPosition = deleteA.getPosition();
        if (insertB.getPosition() <= deleteA.getPosition()) {
            transformedPosition += insertB.getContent().length();
        }
        return Operation.delete(transformedPosition, deleteA.getLength());
    }

    /**
     * Delete vs Delete:
     * Most complex case — handles four sub-cases:
     * 1. B is entirely after A: no effect on A
     * 2. B is entirely before A: shift A's position left
     * 3. B is entirely within A's range: shrink A's length
     * 4. Overlapping: compute surviving range
     *
     * The key invariant: if A and B both want to delete the same characters,
     * A's transformed version should delete 0 of those characters (they're already gone).
     */
    private Operation transformDeleteAgainstDelete(Operation deleteA, Operation deleteB) {
        int posA = deleteA.getPosition();
        int lenA = deleteA.getLength();
        int posB = deleteB.getPosition();
        int lenB = deleteB.getLength();

        // Case 1: B starts after A's range ends — B has no effect on A
        if (posB >= posA + lenA) {
            return deleteA;
        }

        // Case 2: B ends before A starts — B entirely precedes A, shift A left
        if (posB + lenB <= posA) {
            return Operation.delete(posA - lenB, lenA);
        }

        // Cases 3 & 4: B's range overlaps with A's range
        // Compute how many of A's characters B has already deleted
        int overlapStart = Math.max(posA, posB);
        int overlapEnd   = Math.min(posA + lenA, posB + lenB);
        int alreadyDeleted = overlapEnd - overlapStart;

        int newPosition = Math.min(posA, posB);
        int newLength   = Math.max(0, lenA - alreadyDeleted);

        // If the entire range was already deleted by B, return a no-op delete of length 0
        // (caller should check for length == 0 and skip applying)
        if (newLength == 0) {
            return Operation.delete(newPosition, 0);
        }
        return Operation.delete(newPosition, newLength);
    }
}

Server-side operation processing loop

/**
 * @file CollaborationServer.java
 * @description Per-document operation processing loop running on the collaboration server.
 *              Each document has exactly one active CollaborationServer instance (sticky routing).
 *              Responsible for transforming incoming ops, assigning revisions, persisting,
 *              and broadcasting.
 *
 * @requires OperationalTransformer.java, Operation.java
 *
 * Public API:
 *   processOperation(incomingOp, senderSessionId) — main entry point for client ops
 *   getDocumentState() — returns current document text (for snapshot worker)
 */
public class CollaborationServer {

    private final String documentId;
    private final OperationalTransformer transformer;
    private final OperationLog operationLog;         // Cassandra-backed
    private final SessionRegistry sessionRegistry;   // tracks WebSocket sessions per doc
    private final PresenceStore presenceStore;        // Redis-backed

    // In-memory cache: ops since last snapshot, ordered by revision
    // Bounded at 2,000 entries — older ops evicted (still in Cassandra)
    private final Deque<CommittedOperation> recentOps = new ArrayDeque<>();
    private volatile long currentRevision;

    /**
     * Main entry point. Called once per incoming operation from any connected client.
     * Must be called on a single thread per document (or with document-level locking)
     * to maintain OT correctness — no concurrent transforms for the same document.
     *
     * @param incomingOp        the raw operation from the client
     * @param senderSessionId   the WebSocket session ID of the sending client
     */
    public synchronized void processOperation(IncomingOp incomingOp, String senderSessionId) {
        // 1. Find all server-side ops committed since the client's base revision
        List<CommittedOperation> concurrentOps =
            getOpsSince(incomingOp.getBaseRevision());

        // 2. Transform the incoming op against each concurrent server op
        Operation transformedOp = incomingOp.getOp();
        for (CommittedOperation serverOp : concurrentOps) {
            transformedOp = transformer.transform(transformedOp, serverOp.getOperation());
        }

        // 3. Skip no-op deletes (can result from overlapping concurrent deletes)
        if (isNoOp(transformedOp)) {
            sendAck(senderSessionId, currentRevision);
            return;
        }

        // 4. Assign next revision atomically (in-memory, then persisted)
        long newRevision = ++currentRevision;

        // 5. Persist to Cassandra (QUORUM write — blocks until 2/3 replicas confirm)
        CommittedOperation committed = new CommittedOperation(
            documentId, newRevision, incomingOp.getUserId(),
            incomingOp.getClientId(), transformedOp, Instant.now()
        );
        operationLog.appendWithQuorum(committed);

        // 6. Cache in memory for future transforms
        recentOps.addLast(committed);
        if (recentOps.size() > 2_000) {
            recentOps.removeFirst();
        }

        // 7. ACK the sender (must happen after durability confirmed)
        sendAck(senderSessionId, newRevision);

        // 8. Broadcast to all other editors on this document
        broadcastToOtherEditors(senderSessionId, newRevision, transformedOp,
                                incomingOp.getUserId());
    }

    private List<CommittedOperation> getOpsSince(long baseRevision) {
        // Check in-memory cache first — avoids Cassandra read in the common case
        long oldestCached = recentOps.isEmpty()
            ? currentRevision : recentOps.peekFirst().getRevision();

        if (baseRevision >= oldestCached - 1) {
            return recentOps.stream()
                .filter(op -> op.getRevision() > baseRevision)
                .collect(Collectors.toList());
        }

        // Cache miss (large offline gap) — fetch from Cassandra
        return operationLog.getRangeInclusive(documentId, baseRevision + 1, currentRevision);
    }

    private boolean isNoOp(Operation operation) {
        return operation.getType() == Operation.Type.DELETE
            && operation.getLength() == 0;
    }

    private void sendAck(String sessionId, long revision) {
        sessionRegistry.sendToSession(sessionId,
            new AckMessage(revision));
    }

    private void broadcastToOtherEditors(String excludeSessionId, long revision,
                                          Operation operation, String userId) {
        sessionRegistry.getSessionsForDocument(documentId).stream()
            .filter(sessionId -> !sessionId.equals(excludeSessionId))
            .forEach(sessionId -> sessionRegistry.sendToSession(sessionId,
                new OperationBroadcast(revision, operation, userId)));
    }
}

Client-side OT state machine

/**
 * @file ClientOtEngine.java
 * @description Client-side OT state machine. Ensures only one op is in-flight at a time,
 *              and transforms received server ops against the pending/buffered client ops.
 *
 * Key insight: the client needs to transform server-broadcast ops against its own
 * pending op before applying them — otherwise the local document diverges from
 * what the server committed.
 *
 * Public API:
 *   applyLocalOp(op)          — user typed something; apply locally and queue for server
 *   onServerOp(op, revision)  — server broadcast; transform and apply to local doc
 *   onAck(revision)           — server ACK'd our pending op; send next buffered op
 */
public class ClientOtEngine {

    private final OperationalTransformer transformer;
    private final DocumentState localDocument;
    private final WebSocketConnection serverConnection;

    // The one op we've sent to the server and are waiting for ACK on
    private Operation pendingOp = null;

    // Ops typed locally while pendingOp is in-flight; sent after ACK received
    private final Deque<Operation> bufferedOps = new ArrayDeque<>();

    private long currentRevision = 0;

    /**
     * User typed something. Apply immediately to local document (optimistic UI).
     * If no op is in-flight, send to server. If one is in-flight, buffer it.
     */
    public void applyLocalOp(Operation localOp) {
        localDocument.apply(localOp);

        if (pendingOp == null) {
            pendingOp = localOp;
            serverConnection.sendOp(localOp, currentRevision);
        } else {
            bufferedOps.addLast(localOp);
        }
    }

    /**
     * Server broadcast: another user's op arrived (already transformed by the server).
     * We must transform it against our pending + buffered ops before applying locally.
     * This is the "client-side diamond" — our pending op and the server's op both
     * branched from the same base revision.
     */
    public void onServerOp(Operation serverOp, long revision) {
        Operation transformedServerOp = serverOp;

        // Transform against pending op (if any) — our pending op branched from
        // the same base revision as this server op
        if (pendingOp != null) {
            transformedServerOp = transformer.transform(transformedServerOp, pendingOp);
            // Also update our pending op: transform it against what the server just applied
            pendingOp = transformer.transform(pendingOp, serverOp);
        }

        // Transform against each buffered op
        for (int index = 0; index < bufferedOps.size(); index++) {
            Operation bufferedOp = getBufferedAt(index);
            Operation transformedBuffered = transformer.transform(bufferedOp, transformedServerOp);
            transformedServerOp = transformer.transform(transformedServerOp, bufferedOp);
            replaceBufferedAt(index, transformedBuffered);
        }

        localDocument.apply(transformedServerOp);
        currentRevision = revision;
    }

    /**
     * Server ACK'd our pending op — it's now committed.
     * If there are buffered ops, send the first one.
     */
    public void onAck(long revision) {
        currentRevision = revision;
        pendingOp = bufferedOps.isEmpty() ? null : bufferedOps.pollFirst();
        if (pendingOp != null) {
            serverConnection.sendOp(pendingOp, currentRevision);
        }
    }

    // Helper methods (getBufferedAt, replaceBufferedAt) omitted for brevity
}
