Tier 2 — Should Know 45 min Geo/Algorithms

Design Google Maps

Google Maps combines three fundamentally hard problems: storing a planet-scale hierarchical tile system, computing shortest paths on a billion-node road graph in milliseconds, and continuously incorporating real-time traffic without recomputing the entire graph. The L6 signal is understanding why Contraction Hierarchies beats A*, how S2 geometry enables O(1) geospatial indexing, and how 5B daily route requests stay under 200ms P99.

🏢 Google, Uber, Lyft, Apple Maps, Waze
⏱️ 45 min interview
🗺️ 1B+ users, 5B routes/day

❓R — Requirements 3–5 min

Functional Requirements

  • Map rendering: Display interactive map tiles at any zoom level worldwide (zoom 0–22)
  • Routing: Turn-by-turn directions between two points — driving, walking, cycling, transit
  • Real-time traffic: Display current congestion overlay; incorporate into ETA during active navigation
  • ETA calculation: Accurate arrival time estimate using historical patterns + live speed data
  • Forward geocoding: Address string → (lat, lng) coordinates
  • Reverse geocoding: (lat, lng) → human-readable address
  • Place search (POI): "coffee near me", "Eiffel Tower" → ranked list of places with distance
  • Live navigation: GPS-track user, recalculate route if they deviate, update ETA every 30s

Non-Functional Requirements

  • Scale: 1B+ users; 5B route requests/day; 25B tile requests/day at peak
  • Routing latency: P99 < 200ms for long-haul routes (cross-country); P50 < 50ms
  • Tile latency: < 20ms from CDN edge; < 100ms from origin on cache miss
  • Traffic freshness: Road speeds updated within 60s of real-world change
  • Map storage: ~100PB globally across all zoom levels (including satellite imagery)
  • Availability: 99.99% — navigation failure during a drive is a safety incident
  • Map data pipeline: Ingest OSM changesets + proprietary data, re-render tiles within 1 hour
Scope decision for 45 min: Focus on (1) tile system, (2) routing with Contraction Hierarchies, and (3) traffic ingestion pipeline. Mention geocoding and POI search as "same Elasticsearch pattern as Yelp" and move on — spending 10 minutes on geocoding is a trap.

What's Out of Scope

  • Street View imagery pipeline and rendering
  • Indoor maps and venue routing
  • Transit schedule integration (GTFS feeds) — mention it exists, don't design it
  • Map data collection (Street View cars, satellites) — out of scope

Tile Storage Math

The tile pyramid follows 4z tiles at zoom level z. Each tile is 512×512 pixels (vector tiles are much smaller — typically 5–20 KB compressed):

  • Zoom 0–14 (overview → city block): ≈ 357M tiles × ~50 KB avg = ~18 TB (raster)
  • Zoom 15–20 (street → building): ≈ 68B tiles, but only ~10% are land = ~340 TB raster
  • Zoom 21–22 (indoor detail): sparse, only major metros — negligible
  • Vector tiles (MapLibre GL-compatible, PBF format): ~10× smaller → ~35 TB for zoom 0–20
  • Satellite imagery at max zoom: adds ~90PB (raw imagery before compression)
L6 insight: The naive calculation (sum of 4z for z=0..22 × tile size) gives ~22TB for raster tiles, but this assumes the entire globe is land. In practice, ~70% of Earth is ocean — those tiles are never pre-rendered or are trivially small. Real storage for road-level raster tiles is closer to 5TB per zoom "stripe." The 100PB figure comes primarily from satellite imagery, not road tiles.

Routing Server Sizing

A Contraction Hierarchies (CH) query on the world road graph takes ~0.5ms on a modern CPU core. At 200K QPS peak, we need 200,000 × 0.5ms = 100 CPU-cores dedicated to routing. With 64-core servers, that's ~2 servers — surprisingly small. The bottleneck is loading the 50GB graph into RAM per server. With geographic sharding (each server holds one continent), each shard is ~5–10GB and fits comfortably in memory.

L6 insight — why not store the road graph in a graph DB like Neo4j? Graph databases are optimized for multi-hop traversal and OLAP-style queries. For shortest-path routing you need: (1) the full graph in RAM to avoid disk I/O on hot paths, (2) O(1) access to adjacency lists by node ID, (3) custom algorithms (CH) not supported by any off-the-shelf graph DB. A hand-crafted binary adjacency list in memory outperforms Neo4j by 100–1000× for routing queries. This is why Google, HERE, and OSRM all use custom in-memory graph representations.

Service Breakdown

  1. Tile Service: Serves map tiles. Client requests a tile by (zoom, x, y) using standard XYZ. Service translates to quadkey, redirects to CDN. Cache-Control: max-age=2592000 (30 days) for vector tiles — they rarely change. When map data updates, the Tile Renderer writes new tiles with a version suffix and invalidates CDN via cache tag.
  2. Route Service: Loads the Contraction Hierarchies graph into RAM at startup (~50GB for world graph; 5–10GB per continent shard). For each route request: snap origin/destination to nearest CH node via spatial index, run bidirectional CH-Dijkstra, look up live speeds from Redis for each segment, compute ETA, serialize as encoded polyline + turn-by-turn instructions.
  3. Traffic Ingestion Service: Receives 500K GPS pings/sec from navigating users. Each ping (lat, lng, speed, heading) is published to Kafka. Map Matching consumers snap GPS traces to road segments using a Hidden Markov Model (to handle GPS noise). Traffic Aggregation computes rolling average speed per segment, writes to Redis with 120s TTL.
  4. Geocoding Service: Forward geocoding: tokenize input address → Elasticsearch query with fuzzy matching + geo_distance boost. Reverse geocoding: given (lat, lng), find the S2 cell, look up polygon hierarchy (country → state → city → neighborhood → street), find the nearest addressed building using a k-d tree. Returns structured address components.
  5. Navigation Service: Stateful service managing active navigation sessions. Tracks user GPS via WebSocket. When user deviates from route by >50m or a faster route emerges from traffic data, triggers Route Service to compute a new route. Pushes updated turn instructions to the client.
  6. Map Data Pipeline: OSM changesets arrive every minute. A diff processor detects changed road segments. Triggers incremental graph rebuild (rebuild only affected CH nodes, not the full graph). Also triggers tile re-render for affected zoom levels. For satellite imagery, ingests new imagery, runs cloud-masking and color-balancing, tiles at zoom levels 14–20.

🔬D — Deep Dive 10 min

1. Map Tile System: The Tile Pyramid

The world map is divided into a hierarchical quadtree. At zoom 0, a single 512×512 pixel tile covers the entire globe. Each zoom level doubles resolution in both dimensions, quadrupling the tile count:

Zoom 0 — 1 tile covers the world

Quadkey encoding: Each tile's position in the quadrant hierarchy is encoded as a string where each character (0–3) represents one zoom level's quadrant: 0=NW, 1=NE, 2=SW, 3=SE. A zoom-3 tile covering central North America encodes as "012" — 3 characters for 3 zoom levels.

Why quadkeys beat (zoom, x, y) for object storage: In GCS/S3, spatially adjacent tiles share a key prefix. A region query becomes a prefix scan. S3 partitions by key prefix — geographically close tiles land on the same storage partition, improving cache locality. Serving a viewport requires 12–16 adjacent tiles; with quadkey encoding, these tiles are likely in the same CDN cache shard.

L6 insight — vector tiles change the economics: Raster tiles (PNG) are pre-rendered server-side and immutable once created. Vector tiles (PBF/MVT format) contain raw geometry — road lines, building polygons, labels — and are styled client-side using WebGL (MapLibre GL JS). This shifts rendering from server to client, reducing tile count from 23 zoom levels to about 15 (zoom 14 vector tiles contain enough detail to render zoom 15–22 at higher DPI). The storage cost drops 10×, the pipeline simplifies, and the map can be styled dynamically (dark mode, colorblind mode) without re-rendering any tiles. This is why Google switched to vector tiles in 2013.

2. Routing: Why Contraction Hierarchies Beat A*

The world road graph has ~50M nodes and ~120M edges. A naive Dijkstra to route from New York to Los Angeles would explore millions of nodes. Even A* with a straight-line heuristic explores ~1M nodes for long routes. Production systems need sub-100ms routing — this requires preprocessing.

Algorithm Comparison

AlgorithmQuery TimePreprocessingTraffic UpdatesProduction Use
Dijkstra ~30 min (world graph) None Trivial — just update weights Never at scale
A* ~5 min (world), ~2s (city) None Trivial — just update weights City-scale only
ALT (A* + Landmarks) ~100ms (world) Hours, ~few GB Moderate — landmark distances fixed Sometimes
Contraction Hierarchies (CH) ~0.5ms (world) ~1–2h, ~2× graph size Hard — requires customizable CH OSRM, HERE, Waze
Customizable CH (CCH) ~2ms (world) Hours (metric-independent phase) Easy — customization in milliseconds Google, Microsoft

How Contraction Hierarchies Work

Phase 1 — Preprocessing (offline, run once or on graph change):

  1. Node Ordering: Assign an "importance" level to every node. Less important nodes are contracted first. Importance = edge difference (shortcuts added − edges removed) + weighted node depth + search space size estimate.
  2. Node Contraction: Remove the least important node v from the graph. For every pair of neighbors (u, w) where the shortest path u→w goes through v, add a shortcut edge u→w with weight = dist(u,v) + dist(v,w). This preserves all shortest paths even with v removed.
  3. Repeat: After contracting v, update importance of its neighbors and repeat. The contracted graph grows (shortcuts added) but is now hierarchical — high-importance nodes (motorways, highway interchanges) survive longest.

Phase 2 — Query (online, per route request):

  1. Bidirectional search: Run Dijkstra forward from source s and backward from target t simultaneously, but only relax edges going up the hierarchy (toward higher importance nodes).
  2. Meeting point: The two search spaces meet at the highest-importance node on the optimal path (e.g., a major highway interchange). The optimal path cost = min(forward_dist[v] + backward_dist[v]) over all meeting nodes v.
  3. Path unpacking: Shortcuts are expanded recursively to recover the actual road sequence. A shortcut edge (u, w) via node v expands to the original path u→v→w.
L6 insight — CH query explores only ~1,000 nodes vs 50M: The bidirectional search only goes "up" the hierarchy. For a cross-country route, the forward search quickly reaches the interstate highway level (high importance), and so does the backward search. They meet at a highway node and terminate. The total nodes examined is typically 1,000–10,000 even for transcontinental routes — a 5,000× speedup over Dijkstra. This is why a CH-powered routing server can handle 200K QPS with just a few CPU cores.

Traffic integration with Customizable CH (CCH): Standard CH bakes edge weights into shortcuts during preprocessing. When live traffic changes edge weights, the shortcuts are invalidated — you can't re-preprocess the full graph every minute. CCH separates the graph structure from edge weights:

  • Offline phase: Preprocess graph topology only (which shortcuts to add, node order) — runs once or on structural changes (new roads). Takes hours.
  • Customization phase: Apply current edge weights to the preprocessed structure. Recomputes shortcut weights using live traffic data. Takes ~100ms for world-scale graphs — fast enough to run every 60s.
  • Query phase: Same bidirectional CH-Dijkstra, but now shortcut weights reflect current traffic.

3. Geospatial Indexing: S2 Geometry vs Geohash

Google Maps uses the S2 Geometry Library — an open-source library (now open to all) that Google developed for internal use. Understanding why S2 is superior to Geohash is an L6 signal.

PropertyGeohashS2 Geometry
Cell shape Rectangular (lat/lng grid) Quadrilateral projected on sphere
Area uniformity Bad — cells near poles are tiny Good — cells near poles same area as equatorial cells
Cell ID Base-32 string (12 chars = ~cm precision) 64-bit integer — fast arithmetic, no string ops
Neighbor finding Moderate — need 8 adjacent cell calculations O(1) — arithmetic on cell IDs
Region covering Poor — rectangular regions don't cover arbitrary shapes Excellent — covers arbitrary polygon with min cells
Hierarchy 30 levels (level 1 = 5,009 km²) 30 levels (level 0 = face, level 30 = ~1cm²)

How Google Maps uses S2:

  • Every Point of Interest is indexed by its S2 cell ID at multiple levels (e.g., level 13 ≈ 1.5km², level 15 ≈ 0.1km²)
  • A viewport query (what's on screen?) is converted to a set of S2 cell IDs that cover the viewport region. This is a "cell union" — typically 4–8 cells at the right level
  • Query Bigtable for all POIs with cell ID in that set — O(1) per cell lookup, O(k) where k is cell count
  • The map-matching algorithm (snapping GPS traces to roads) uses S2 to find candidate road segments within a 50m S2 cell
L6 insight — S2 enables polygon containment without geometry: Traditional GIS uses polygon containment queries (is point P inside polygon Q?) which require expensive computational geometry. With S2, a city boundary is pre-computed as a "cell union" — a set of S2 cell IDs that approximates the polygon. To check if a point is in San Francisco, compute its cell ID and check if it's in the cell union — pure integer comparison, no geometry. This is how reverse geocoding scales to millions of QPS.

4. Live Traffic: From GPS Ping to ETA Adjustment

Google Maps has an inherent advantage: it IS the traffic sensor. 100M+ users navigating simultaneously send GPS pings every 15 seconds. This creates a real-time, planet-scale speed measurement system:

  1. GPS Ping Collection: Navigating user sends {lat, lng, speed_kph, heading, accuracy_meters} every 15s. Batched and sent over existing WebSocket/HTTP/2 connection. At 100M navigating users: 100M / 15s = 6.7M pings/sec ingested into Kafka (partitioned by S2 cell prefix).
  2. Map Matching: Raw GPS traces are noisy (multipath errors, tunnel exits). A Hidden Markov Model (HMM) matches each trace to the most likely road segment sequence. Candidate segments are found via S2 cell lookup. The HMM considers: GPS error radius, road connectivity, heading alignment, speed plausibility.
  3. Speed Aggregation: Map Matching outputs (segment_id, speed_kph) pairs. Traffic Aggregation Service computes a rolling 5-minute exponential moving average per segment. Minimum probe density required: fewer than 3 probes → inherit historical speed; 3+ probes → use probe average. Anomaly detection flags sudden speed drops (potential accident).
  4. Redis Update: Current speed written to Redis with 120s TTL. Route Service reads these during query: travel_time = distance_meters / current_speed_kph. ETA = sum of travel_times for all segments on route.
  5. Historical Baselines: For segments with no live probes, fall back to historical speed patterns (day-of-week + time-of-day buckets, trained from 5 years of GPS history). This is how Google Maps predicts "usually fast on Sunday at 2pm."
ETA accuracy: Google Maps reports ±10% ETA accuracy for typical routes. The dominant error source is not algorithmic but probabilistic — a traffic jam that forms 5 minutes from now cannot be predicted, only observed. Machine learning models trained on historical patterns can predict likely congestion, but real-time GPS data is still the ground truth.

5. Map Rendering: Vector Tiles and Client-Side WebGL

Modern Google Maps and its open-source equivalents (MapLibre GL) use a pipeline:

  • Server: Pre-generates vector tiles in Mapbox Vector Tile (MVT/PBF) format. Each tile contains layers: roads, buildings, water, land use, labels. Raw geometry in tile-local coordinates (0–4096). No styling — just data.
  • Client (WebGL / MapLibre GL JS): Downloads tile PBF, deserializes geometry, applies style rules (color, width, visibility based on zoom). Renders roads as WebGL polylines, buildings as extruded 3D polygons, using GPU for real-time performance.
  • Style spec: A JSON document defines what to draw and how. Changing dark mode = swap one JSON file. No re-render needed on server. The same tiles serve light mode, dark mode, satellite hybrid, colorblind mode.

Tile generation pipeline:

// Simplified tile generation pipeline:

✅E — Evaluate 3 min

Does This Meet the Requirements?

Routing latency P99 < 200ms

CH query: ~0.5ms. Redis lookups for segment speeds: ~5ms (pipelined). Serializing response: ~2ms. Network round-trip (client → PoP → routing server): ~20–50ms. Total: ~30–60ms P50; ~150ms P99. ✓

Failure modes: cold start (loading 10GB graph shard into RAM takes ~45s — mitigated by warm spare, rolling restarts). Hot spot if a single city shard gets >10K QPS — solved by horizontal sharding of the routing tier.

Tile latency < 20ms from CDN

CDN cache hit rate for tiles should be >99% — tiles at popular zoom levels in dense cities are requested constantly. Long TTL (30 days) means CDN never evicts them. P50 tile latency from CDN edge: ~5–8ms. ✓

Traffic freshness within 60s

GPS ping → Kafka (sub-second) → Map Matching (~5s processing window) → Aggregation → Redis write. End-to-end latency: ~15–30s for a meaningful speed estimate to appear. Redis TTL of 120s ensures stale data is purged. ✓ Well within 60s target.

Failures and Edge Cases

  • Routing server crash: Geographic sharding means only one continent's routing is affected. Traffic is redirected to a hot standby. Graph reload takes ~45s — acceptable given 99.99% availability target allows 52 min/year downtime.
  • Kafka consumer lag: If traffic ingestion falls behind (e.g., during a concert when millions of users are in one area), segment speeds fall back to historical baselines after 120s TTL. ETA accuracy degrades gracefully — doesn't fail catastrophically.
  • GPS spoofing / bad data: Anomaly detection in Traffic Aggregation rejects pings with implausible speed changes (>10 m/s² acceleration), speed > physical road limit × 1.5, or heading inconsistent with road geometry. Probes from verified navigation sessions weighted higher than probes from passive location sharing.
  • Map data errors: OSM vandalism can introduce false roads. Road data goes through validation pipeline: cross-check against satellite imagery, flag sharp geometry angles (likely editing errors), require 3+ independent sources for new road additions. Emergency data rollback restores previous graph version in minutes.
  • International routing (routing across geographic shards): Most routes are within one continent shard. Cross-continent routes (NYC → London — not meaningful by car, but relevant for global graph consistency) are handled by "stitching" nodes at border crossings between shards using precomputed inter-shard distances.
Cold start problem — the hardest operational challenge: A routing server loads a 10GB graph shard at startup. During this 45-second window, it cannot serve requests. In a rolling restart (normal deployment), the old server continues serving until the new one is ready. But if an entire shard crashes simultaneously (e.g., AZ failure), users in that region see routing failures until the backup AZ warms up. Mitigation: pre-warm routing servers in secondary AZ continuously, not just on failure.

🚀D — Deliver 2 min

We designed Google Maps at planet scale (1B+ users, 5B routes/day) around three architectural pillars:

  1. Tile System: Quadkey-encoded vector tiles (PBF format) stored in GCS, served via CDN with 30-day cache TTL, rendered client-side via MapLibre GL WebGL. The vector tile approach shifts rendering work to the client, reduces storage 10× vs raster, and enables dynamic styling without server re-renders.
  2. Routing with Contraction Hierarchies: Road graph loaded into RAM per geographic shard (~10GB/shard). CH preprocessing reduces query time from minutes (Dijkstra) to ~0.5ms. Customizable CH re-applies live traffic weights in ~100ms — enabling per-minute traffic refresh without full preprocessing. 200K QPS served by ~2–4 servers per continent.
  3. Traffic Pipeline: 100M navigating users produce 6.7M GPS pings/sec → Kafka → HMM map-matching → rolling average per road segment → Redis (120s TTL). Historical patterns serve as fallback when live probe density is low. ETA accuracy ±10% for typical routes.

Supporting services: S2 Geometry Library for all geospatial indexing (POI search, reverse geocoding, map-matching), Elasticsearch for forward geocoding and POI full-text search, Bigtable for tile metadata and historical traffic patterns.

What would be different at earlier scale:

  • Under 10M users: single routing server with A* (no CH needed), Postgres with PostGIS for geocoding
  • Under 100M users: A* with continent sharding, Redis for traffic, CDN with raster tiles
  • 1B+ users: Full CH/CCH, vector tiles, S2 geometry throughout, dedicated traffic ingestion pipeline as described above

☕Java Implementation — Contraction Hierarchies

Below is a simplified but algorithmically correct implementation of CH preprocessing and query. Production implementations (OSRM, RoutingKit) are 10× more optimized, but this captures the essential structure an L6 would be expected to understand.

Part 1: Graph Representation and Node Ordering

/**
 * ContractionHierarchies.java
 *
 * Simplified Contraction Hierarchies (CH) preprocessing and query.
 * Demonstrates: node ordering by importance, shortcut creation,
 * and bidirectional Dijkstra on the augmented CH graph.
 *
 * Production CH (e.g., OSRM, RoutingKit) uses the same algorithmic
 * structure but adds: witness search optimization, lazy updates for
 * importance, parallel contraction, and efficient binary heap.
 */
import java.util.*;

public class ContractionHierarchies {

    // ── Graph representation ───────────────────────────────────────────────
    // Stored as adjacency list: nodeEdges[nodeId] = list of (toNode, weight, isShortcut)
    private final int nodeCount;
    private final List[] forwardEdges;   // forwardEdges[u] = {v, weight, viaNode}
    private final List[] backwardEdges;  // backwardEdges[v] = {u, weight, viaNode}
    private final int[] chLevel;               // contraction order (lower = contracted earlier)
    private final boolean[] contracted;

    private static final int VIA_NODE_NONE = -1;

    @SuppressWarnings("unchecked")
    public ContractionHierarchies(int nodeCount) {
        this.nodeCount = nodeCount;
        this.forwardEdges = new List[nodeCount];
        this.backwardEdges = new List[nodeCount];
        this.chLevel = new int[nodeCount];
        this.contracted = new boolean[nodeCount];
        for (int nodeIndex = 0; nodeIndex < nodeCount; nodeIndex++) {
            forwardEdges[nodeIndex] = new ArrayList<>();
            backwardEdges[nodeIndex] = new ArrayList<>();
        }
    }

    /** Adds a directed edge. Call twice for undirected roads. */
    public void addEdge(int fromNode, int toNode, int weightMs) {
        forwardEdges[fromNode].add(new int[]{toNode, weightMs, VIA_NODE_NONE});
        backwardEdges[toNode].add(new int[]{fromNode, weightMs, VIA_NODE_NONE});
    }

    // ── Node importance scoring ────────────────────────────────────────────
    /**
     * Computes node importance for ordering.
     *
     * The key metric is "edge difference": number of shortcuts added minus
     * number of edges removed when contracting this node. Nodes that cause
     * many shortcuts (high connectivity, graph-critical) get contracted last
     * (high importance = high CH level).
     *
     * @param nodeId  the node to evaluate
     * @return importance score (lower = contract sooner)
     */
    private int computeImportance(int nodeId) {
        int predecessorCount = 0;
        int successorCount = 0;
        int shortcutsNeeded = 0;

        // Count in-edges (predecessors) and out-edges (successors, excluding contracted)
        for (int[] backEdge : backwardEdges[nodeId]) {
            if (!contracted[backEdge[0]]) {
                predecessorCount++;
            }
        }
        for (int[] fwdEdge : forwardEdges[nodeId]) {
            if (!contracted[fwdEdge[0]]) {
                successorCount++;
            }
        }

        // Estimate shortcuts: for each (predecessor u, successor w) pair,
        // check if u→nodeId→w is the only shortest path u→w (simplified — no witness search).
        // Real CH runs Dijkstra from each predecessor to verify if a witness path exists.
        // Here we use the upper bound: all u→w pairs may need shortcuts.
        shortcutsNeeded = predecessorCount * successorCount;

        int edgesRemoved = predecessorCount + successorCount;
        int edgeDifference = shortcutsNeeded - edgesRemoved;

        // Depth bonus discourages contracting nodes that were neighbors of many contracted nodes
        // (deep in the hierarchy already) — keeps the hierarchy balanced.
        int depth = 0; // simplified: in production, track max contracted-neighbor depth

        return edgeDifference * 10 + depth;
    }

    // ── Preprocessing: contract all nodes ─────────────────────────────────
    /**
     * Builds the Contraction Hierarchy.
     *
     * Contracts nodes in order of increasing importance. After contracting
     * a node, shortcuts are added to preserve all shortest paths in the
     * remaining graph. The result is an augmented graph that supports
     * O(log n)-ish bidirectional Dijkstra queries.
     */
    public void preprocess() {
        // Priority queue ordered by importance (min-heap = contract least important first)
        PriorityQueue nodeQueue = new PriorityQueue<>(
            Comparator.comparingInt(entry -> entry[1])
        );

        // Initialize importance for all nodes
        for (int nodeIndex = 0; nodeIndex < nodeCount; nodeIndex++) {
            nodeQueue.offer(new int[]{nodeIndex, computeImportance(nodeIndex)});
        }

        int contractionLevel = 0;
        while (!nodeQueue.isEmpty()) {
            int[] entry = nodeQueue.poll();
            int nodeToContract = entry[0];

            // Lazy update: recompute importance — may have changed as neighbors were contracted
            int currentImportance = computeImportance(nodeToContract);
            if (currentImportance > entry[1]) {
                // Importance increased — reinsert with updated importance
                nodeQueue.offer(new int[]{nodeToContract, currentImportance});
                continue;
            }

            // Contract this node
            contractNode(nodeToContract, contractionLevel);
            contracted[nodeToContract] = true;
            chLevel[nodeToContract] = contractionLevel++;
        }
    }

    /**
     * Contracts a single node: adds shortcuts for all (predecessor, successor) pairs
     * where the shortest path goes through this node.
     *
     * In production, a "witness search" Dijkstra runs from each predecessor to find
     * if an alternative path (not through this node) is equally short — if so,
     * no shortcut is needed for that pair. We omit witness search here for clarity.
     */
    private void contractNode(int nodeToContract, int level) {
        List predecessors = backwardEdges[nodeToContract];
        List successors = forwardEdges[nodeToContract];

        for (int[] inEdge : predecessors) {
            int predecessorNode = inEdge[0];
            int weightToContracted = inEdge[1];

            if (contracted[predecessorNode]) continue;

            for (int[] outEdge : successors) {
                int successorNode = outEdge[0];
                int weightFromContracted = outEdge[1];

                if (contracted[successorNode]) continue;
                if (predecessorNode == successorNode) continue;

                int shortcutWeight = weightToContracted + weightFromContracted;

                // Add shortcut edge: predecessor → successor (bypassing nodeToContract)
                // This preserves the shortest path through the contracted node.
                int[] shortcutForward = {successorNode, shortcutWeight, nodeToContract};
                int[] shortcutBackward = {predecessorNode, shortcutWeight, nodeToContract};

                // Only add if no cheaper path already exists (simplified check)
                boolean shortcutNeeded = true;
                for (int[] existingEdge : forwardEdges[predecessorNode]) {
                    if (existingEdge[0] == successorNode && existingEdge[1] <= shortcutWeight) {
                        shortcutNeeded = false;
                        break;
                    }
                }

                if (shortcutNeeded) {
                    forwardEdges[predecessorNode].add(shortcutForward);
                    backwardEdges[successorNode].add(shortcutBackward);
                }
            }
        }
    }

Part 2: Bidirectional CH-Dijkstra Query

    // ── Bidirectional CH-Dijkstra query ───────────────────────────────────
    /**
     * Finds the shortest path from sourceNode to targetNode using
     * bidirectional Dijkstra on the CH graph.
     *
     * Key insight: only relax edges going UPWARD in the hierarchy
     * (toward higher CH level nodes). This ensures both searches
     * meet at the "highest importance" node on the optimal path.
     *
     * @param sourceNode  origin node ID (snapped to nearest road node)
     * @param targetNode  destination node ID
     * @return shortest path distance in milliseconds, or Integer.MAX_VALUE if unreachable
     */
    public QueryResult query(int sourceNode, int targetNode) {
        int[] forwardDist = new int[nodeCount];
        int[] backwardDist = new int[nodeCount];
        int[] forwardParent = new int[nodeCount];
        int[] backwardParent = new int[nodeCount];
        Arrays.fill(forwardDist, Integer.MAX_VALUE);
        Arrays.fill(backwardDist, Integer.MAX_VALUE);
        Arrays.fill(forwardParent, -1);
        Arrays.fill(backwardParent, -1);

        forwardDist[sourceNode] = 0;
        backwardDist[targetNode] = 0;

        // PQ entries: {distance, nodeId}
        PriorityQueue forwardQueue = new PriorityQueue<>(Comparator.comparingInt(e -> e[0]));
        PriorityQueue backwardQueue = new PriorityQueue<>(Comparator.comparingInt(e -> e[0]));
        forwardQueue.offer(new int[]{0, sourceNode});
        backwardQueue.offer(new int[]{0, targetNode});

        int bestPathCost = Integer.MAX_VALUE;
        int meetingNode = -1;

        Set forwardSettled = new HashSet<>();
        Set backwardSettled = new HashSet<>();

        while (!forwardQueue.isEmpty() || !backwardQueue.isEmpty()) {
            // Alternate between forward and backward search
            if (!forwardQueue.isEmpty()) {
                int[] current = forwardQueue.poll();
                int currentDist = current[0];
                int currentNode = current[1];

                if (forwardSettled.contains(currentNode)) continue;
                forwardSettled.add(currentNode);

                // Pruning: if current distance exceeds best found path, stop
                if (currentDist > bestPathCost) break;

                // Check if backward search has reached this node → candidate meeting point
                if (backwardDist[currentNode] != Integer.MAX_VALUE) {
                    int candidateCost = currentDist + backwardDist[currentNode];
                    if (candidateCost < bestPathCost) {
                        bestPathCost = candidateCost;
                        meetingNode = currentNode;
                    }
                }

                // Only relax edges going UPWARD in the CH hierarchy
                for (int[] edge : forwardEdges[currentNode]) {
                    int neighborNode = edge[0];
                    int edgeWeight = edge[1];

                    // CH constraint: only explore if neighbor has higher CH level
                    if (chLevel[neighborNode] <= chLevel[currentNode]) continue;

                    int newDist = currentDist + edgeWeight;
                    if (newDist < forwardDist[neighborNode]) {
                        forwardDist[neighborNode] = newDist;
                        forwardParent[neighborNode] = currentNode;
                        forwardQueue.offer(new int[]{newDist, neighborNode});
                    }
                }
            }

            // Symmetric backward search (same logic, using backwardEdges, going upward)
            if (!backwardQueue.isEmpty()) {
                int[] current = backwardQueue.poll();
                int currentDist = current[0];
                int currentNode = current[1];

                if (backwardSettled.contains(currentNode)) continue;
                backwardSettled.add(currentNode);

                if (currentDist > bestPathCost) break;

                if (forwardDist[currentNode] != Integer.MAX_VALUE) {
                    int candidateCost = forwardDist[currentNode] + currentDist;
                    if (candidateCost < bestPathCost) {
                        bestPathCost = candidateCost;
                        meetingNode = currentNode;
                    }
                }

                for (int[] edge : backwardEdges[currentNode]) {
                    int neighborNode = edge[0];
                    int edgeWeight = edge[1];

                    if (chLevel[neighborNode] <= chLevel[currentNode]) continue;

                    int newDist = currentDist + edgeWeight;
                    if (newDist < backwardDist[neighborNode]) {
                        backwardDist[neighborNode] = newDist;
                        backwardParent[neighborNode] = currentNode;
                        backwardQueue.offer(new int[]{newDist, neighborNode});
                    }
                }
            }
        }

        return new QueryResult(bestPathCost, meetingNode, forwardParent, backwardParent);
    }

    /** Result of a CH query — includes the meeting node for path unpacking. */
    public static class QueryResult {
        public final int totalDistanceMs;
        public final int meetingNode;
        private final int[] forwardParent;
        private final int[] backwardParent;

        QueryResult(int totalDistanceMs, int meetingNode,
                    int[] forwardParent, int[] backwardParent) {
            this.totalDistanceMs = totalDistanceMs;
            this.meetingNode = meetingNode;
            this.forwardParent = forwardParent;
            this.backwardParent = backwardParent;
        }

        /**
         * Reconstructs the node sequence from source to target.
         * Shortcuts are NOT unpacked here — production code recursively
         * expands shortcut edges via their stored viaNode reference.
         */
        public List reconstructPath(int sourceNode, int targetNode) {
            if (meetingNode < 0) return Collections.emptyList();

            LinkedList path = new LinkedList<>();

            // Walk backward from meeting node to source
            int currentNode = meetingNode;
            while (currentNode != sourceNode && forwardParent[currentNode] >= 0) {
                path.addFirst(currentNode);
                currentNode = forwardParent[currentNode];
            }
            path.addFirst(sourceNode);

            // Walk forward from meeting node to target
            currentNode = backwardParent[meetingNode];
            while (currentNode >= 0 && currentNode != targetNode) {
                path.addLast(currentNode);
                currentNode = backwardParent[currentNode];
            }
            if (currentNode == targetNode) path.addLast(targetNode);

            return path;
        }
    }
}

Part 3: Tile Server with Web Mercator Projection

/**
 * TileServer.java
 * Converts between geographic coordinates, tile coordinates,
 * and quadkey encoding for the map tile serving pipeline.
 */
public class TileServer {

    private static final String CDN_BASE_URL = "https://tiles.maps.example.com";
    private static final int MAX_ZOOM_LEVEL = 22;
    private static final double EARTH_CIRCUMFERENCE_METERS = 40_075_016.686;

    /**
     * Converts (zoom, x, y) tile coordinates to a quadkey string.
     *
     * Each character in the quadkey represents one zoom level's quadrant:
     * 0=NW, 1=NE, 2=SW, 3=SE. Length of quadkey == zoom level.
     * Spatially adjacent tiles share a common quadkey prefix — this is the
     * property that gives S3/GCS storage spatial locality for free.
     *
     * @param zoomLevel zoom level (0 = whole world, 22 = street level)
     * @param tileX     tile column (0 to 2^zoom - 1, increasing east)
     * @param tileY     tile row (0 to 2^zoom - 1, increasing south)
     * @return quadkey string of length == zoomLevel
     */
    public String encodeToQuadkey(int zoomLevel, int tileX, int tileY) {
        if (zoomLevel < 0 || zoomLevel > MAX_ZOOM_LEVEL) {
            throw new IllegalArgumentException(
                "Zoom level must be 0–" + MAX_ZOOM_LEVEL + ", got: " + zoomLevel
            );
        }
        StringBuilder quadkey = new StringBuilder(zoomLevel);
        for (int level = zoomLevel; level > 0; level--) {
            int digit = 0;
            int mask = 1 << (level - 1);
            if ((tileX & mask) != 0) digit++;      // bit set in X → east half → +1
            if ((tileY & mask) != 0) digit += 2;   // bit set in Y → south half → +2
            quadkey.append(digit);
        }
        return quadkey.toString();
    }

    /**
     * Decodes a quadkey back to (zoom, x, y) tile coordinates.
     * Inverse of encodeToQuadkey.
     */
    public int[] decodeQuadkey(String quadkey) {
        int zoomLevel = quadkey.length();
        int tileX = 0;
        int tileY = 0;
        for (int level = zoomLevel; level > 0; level--) {
            int mask = 1 << (level - 1);
            char quadrant = quadkey.charAt(zoomLevel - level);
            switch (quadrant) {
                case '0': break;                    // NW — no bit set
                case '1': tileX |= mask; break;    // NE — X bit set
                case '2': tileY |= mask; break;    // SW — Y bit set
                case '3': tileX |= mask; tileY |= mask; break; // SE — both set
                default: throw new IllegalArgumentException(
                    "Invalid quadkey character: " + quadrant + " in " + quadkey
                );
            }
        }
        return new int[]{zoomLevel, tileX, tileY};
    }

    /**
     * Converts latitude/longitude to Web Mercator tile coordinates.
     *
     * Uses the Web Mercator projection (EPSG:3857) — the same projection
     * used by Google Maps, OpenStreetMap, and all slippy-map tile systems.
     * Note: Web Mercator distorts area near the poles significantly —
     * this is an accepted trade-off for mathematical simplicity and
     * 90-degree north/south alignment.
     *
     * @param latitudeDegrees  latitude (-85.05 to +85.05 — Web Mercator valid range)
     * @param longitudeDegrees longitude (-180 to +180)
     * @param zoomLevel        target zoom level
     * @return int[]{tileX, tileY}
     */
    public int[] latLngToTile(double latitudeDegrees, double longitudeDegrees, int zoomLevel) {
        // Clamp to Web Mercator valid range (poles are at infinity in Mercator)
        double clampedLat = Math.max(-85.05112878, Math.min(85.05112878, latitudeDegrees));

        int totalTilesPerAxis = 1 << zoomLevel; // 2^zoom tiles in each dimension
        double latitudeRadians = Math.toRadians(clampedLat);

        int tileX = (int) Math.floor(
            (longitudeDegrees + 180.0) / 360.0 * totalTilesPerAxis
        );
        int tileY = (int) Math.floor(
            (1.0 - Math.log(Math.tan(latitudeRadians) + 1.0 / Math.cos(latitudeRadians))
             / Math.PI) / 2.0 * totalTilesPerAxis
        );

        // Clamp to valid range (floating-point can push us 1 tile out of bounds)
        tileX = Math.max(0, Math.min(totalTilesPerAxis - 1, tileX));
        tileY = Math.max(0, Math.min(totalTilesPerAxis - 1, tileY));

        return new int[]{tileX, tileY};
    }

    /**
     * Returns the set of tile coordinates needed to cover a rectangular viewport.
     * Used by the client to determine which tiles to fetch for the current map view.
     *
     * @param northLat  northern boundary latitude
     * @param southLat  southern boundary latitude
     * @param westLng   western boundary longitude
     * @param eastLng   eastern boundary longitude
     * @param zoomLevel current zoom level
     * @return list of {tileX, tileY} pairs covering the viewport
     */
    public List getTilesForViewport(double northLat, double southLat,
                                            double westLng, double eastLng,
                                            int zoomLevel) {
        int[] topLeftTile = latLngToTile(northLat, westLng, zoomLevel);
        int[] bottomRightTile = latLngToTile(southLat, eastLng, zoomLevel);

        List viewportTiles = new ArrayList<>();
        for (int tileX = topLeftTile[0]; tileX <= bottomRightTile[0]; tileX++) {
            for (int tileY = topLeftTile[1]; tileY <= bottomRightTile[1]; tileY++) {
                viewportTiles.add(new int[]{tileX, tileY});
            }
        }
        return viewportTiles;
    }

    /**
     * Builds the CDN URL for a vector tile request.
     * Uses XYZ format in the URL (client-compatible) while the backend
     * resolves this to the quadkey-keyed GCS object internally.
     */
    public String buildTileUrl(int zoomLevel, int tileX, int tileY) {
        // XYZ format in URL for client library compatibility
        return CDN_BASE_URL + "/v1/tiles/" + zoomLevel + "/" + tileX + "/" + tileY + ".pbf";
    }

    /**
     * Returns the ground resolution in meters per pixel at a given zoom and latitude.
     * At zoom 0, one pixel = 78.27 km at the equator.
     * At zoom 20, one pixel = ~0.075 m at the equator.
     * Near the poles, the same zoom level shows less ground area per pixel.
     */
    public double groundResolutionMetersPerPixel(double latitudeDegrees, int zoomLevel) {
        double latitudeRadians = Math.toRadians(latitudeDegrees);
        int tilePixelSize = 512; // standard tile size in pixels
        long totalPixels = (long) tilePixelSize << zoomLevel; // 512 × 2^zoom pixels wrap Earth
        return Math.cos(latitudeRadians) * EARTH_CIRCUMFERENCE_METERS / totalPixels;
    }
}
L6 insight on the implementation: The bidirectional CH query settles only ~1,000 nodes for a transcontinental route because the "only go upward" constraint prunes the search space dramatically. A motorway network (high CH level) is reached within a few hops from any city-center node. The forward and backward searches both converge on the highway network and meet there. In production, this is combined with "stall-on-demand" — if a settled node can be reached more cheaply via a non-upward edge, its distance is marked as a "stall" and not used to relax neighbors. This further reduces the search space and handles the minor correctness issue in simplified bidirectional CH.
