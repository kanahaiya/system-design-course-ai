Tier 2 — Should Know 45 min Geo/Algorithms

Design Google Maps

Google Maps involves three distinct hard problems: storing a tile-based map efficiently, running shortest-path routing on a graph with billions of nodes, and incorporating real-time traffic without recomputing the whole graph.

🏢 Google, Uber, Lyft
⏱️ 45 min interview
🗺️ 1B+ users

❓R — Requirements3–5 min

Functional Requirements

  • Display map tiles at any zoom level worldwide
  • Turn-by-turn routing between two points (driving, walking, transit)
  • Real-time traffic overlays and ETA recalculation
  • Search for places by name or address (geocoding)
  • Reverse geocoding: coordinates → human-readable address

Non-Functional Requirements

  • Scale: 1B users, 10M route calculations/day, 1B tile requests/day
  • Latency: Route calculation <2s; tile load <100ms from CDN
  • Map data: ~100TB total across all zoom levels

🔢E — Estimation3–5 min

  • Zoom levels 0–22: total tiles = sum(4^z) for z=0..22 ≈ 22TB of tile data
  • With satellite imagery at max zoom: ~100TB total map storage
  • 10M routes/day = ~115 QPS for routing; peaks around commute hours → 500 QPS
  • 1B tile requests/day = ~11,600 tile QPS; CDN handles 99% → origin sees ~120 QPS
  • Road graph: 50M nodes, 120M edges for the entire world (compressed: ~100GB in memory)

🗄️S — Schema3–5 min

// Map tiles (object storage — S3/GCS)
// Key format: tiles/{zoom}/{x}/{y}.png  (slippy map / XYZ standard)
// Or quadkey: tiles/{quadkey}.png  (Microsoft Bing style — each char is 0/1/2/3)

// Road graph (in-memory on routing servers, sourced from OpenStreetMap + proprietary)
// Node: intersection (lat/lng)
// Edge: road segment with distance_meters, speed_limit_kph, road_type
// Graph stored as adjacency list, serialized to binary (Protocol Buffers)

// Real-time traffic (Redis time-series)
// Key: traffic:{segment_id}  Value: current_speed_kph with 60s TTL
// Updated by GPS-reporting clients and traffic sensors

// Places index (Elasticsearch)
// Fields: place_id, name, address, lat, lng, category, rating
// Geo-indexed for radius queries

🏗️H — High-level Design10 min

  • Tile Service: Tiles pre-rendered and stored in S3. CDN caches tiles with long TTL (months — tiles rarely change). Client requests tile by (zoom, x, y).
  • Routing Service: Loads road graph into memory. Uses A* with a geographical heuristic (straight-line distance) — faster than Dijkstra on large graphs. Traffic data modifies edge weights at query time.
  • Traffic Ingestion: GPS-reporting users send location every 15s. Aggregation service maps (lat/lng, speed) to road segment IDs, updates Redis TTL-keyed traffic speeds.
  • Geocoding Service: Address → coordinates uses indexed address database (ElasticSearch). Coordinates → address uses reverse geocoding tree (hierarchical polygon containment).
  • ETA Engine: Sum of (distance / current_speed) for each segment on route. Recalculates every 30s while navigating.

🔬D — Deep Dive: Tile Storage with Quadkeys10 min

The world map is divided into a hierarchical quadtree. At zoom 0: 1 tile covers the whole world. At zoom 1: 4 tiles. At zoom z: 4^z tiles. Each tile is 256×256 pixels.

Quadkey encoding: At each zoom level, each tile's position in the quadrant (NW=0, NE=1, SW=2, SE=3) appends one digit. Zoom 3, tile at position (0,0) = "000". This encodes location + zoom in one string — great for object storage key prefix-based routing.

Why quadkeys beat (zoom, x, y) for object storage: Spatially adjacent tiles share a key prefix. You can list all tiles in a region with a prefix scan. S3 partitions by key prefix — spatially related tiles end up on the same S3 partition, improving cache locality.

✅E — Evaluate3 min

  • Routing at scale: Road graph for whole world is ~100GB. Not practical to load into one server's memory. Solution: partition graph by geographic region. Most routes are local — route within region, stitch at boundaries (contraction hierarchies).
  • Traffic update latency: Redis TTL approach means traffic data is at most 60s stale. Acceptable for ETA accuracy.
  • Tile freshness: Roads change rarely. Tiles can have months-long CDN TTL. When map data changes, use versioned tile keys (tile/v2/...) and deploy new CDN content.

🚀D — Deliver2 min

We designed Google Maps handling 1B users, 100TB of map tile storage, and real-time routing. Key decisions: quadkey-encoded tiles on S3 with CDN (long TTL), A* routing with traffic-adjusted edge weights loaded in-memory, Redis for real-time traffic speeds with 60s TTL, and ElasticSearch for geocoding and place search.

☕Java Implementation

/**
 * TileServer — encodes map coordinates to quadkey format and generates
 * CDN-friendly tile URLs for the slippy map tile system.
 */
public class TileServer {

    private static final String CDN_BASE_URL = "https://tiles.maps.example.com";
    private static final int MAX_ZOOM_LEVEL = 22;

    /**
     * Converts (zoom, x, y) tile coordinates to a quadkey string.
     * Each character in the quadkey represents one zoom level's quadrant (0-3).
     *
     * @param zoomLevel zoom level (0 = whole world, 22 = street level)
     * @param tileX     tile column (0 to 2^zoom - 1)
     * @param tileY     tile row (0 to 2^zoom - 1)
     * @return quadkey string of length == zoomLevel
     */
    public String encodeToQuadkey(int zoomLevel, int tileX, int tileY) {
        if (zoomLevel < 0 || zoomLevel > MAX_ZOOM_LEVEL) {
            throw new IllegalArgumentException("Zoom level must be 0–" + MAX_ZOOM_LEVEL);
        }
        StringBuilder quadkey = new StringBuilder();
        for (int level = zoomLevel; level > 0; level--) {
            int digit = 0;
            int mask = 1 << (level - 1);
            if ((tileX & mask) != 0) {
                digit++; // bit set in X → east half → +1
            }
            if ((tileY & mask) != 0) {
                digit += 2; // bit set in Y → south half → +2
            }
            quadkey.append(digit);
        }
        return quadkey.toString();
    }

    /**
     * Generates the full CDN URL for a map tile.
     * Tiles are immutable — URL includes zoom+quadkey for natural CDN caching.
     */
    public String buildTileUrl(int zoomLevel, int tileX, int tileY) {
        String quadkey = encodeToQuadkey(zoomLevel, tileX, tileY);
        return CDN_BASE_URL + "/tiles/" + zoomLevel + "/" + quadkey + ".png";
    }

    /**
     * Converts latitude/longitude to tile coordinates at a given zoom level.
     * Uses the standard Web Mercator (EPSG:3857) projection.
     */
    public int[] latLngToTile(double latitudeDegrees, double longitudeDegrees, int zoomLevel) {
        int totalTiles = 1 << zoomLevel;
        double latitudeRadians = Math.toRadians(latitudeDegrees);
        int tileX = (int) Math.floor((longitudeDegrees + 180.0) / 360.0 * totalTiles);
        int tileY = (int) Math.floor(
            (1.0 - Math.log(Math.tan(latitudeRadians) + 1.0 / Math.cos(latitudeRadians)) / Math.PI)
            / 2.0 * totalTiles
        );
        return new int[]{tileX, tileY};
    }
}
