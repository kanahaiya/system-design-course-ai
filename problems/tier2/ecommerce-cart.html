Tier 2 — Important 45 min Transactions / Consistency

Design E-commerce Cart & Checkout

Three hard problems in one: prevent overselling with two competing checkouts, make checkout idempotent against double-clicks, and roll back gracefully when payment fails. The Saga pattern and optimistic locking are non-negotiable here.

🏢 Amazon, Alibaba, Shopify
⏱️ 45 min interview
📈 Spike traffic (flash sales)

❓ R — Requirements 3–5 min

Functional Requirements

  • Add, remove, and update item quantities in cart
  • View cart with current prices and total
  • Checkout: validate inventory → calculate total → apply coupon → process payment → confirm order
  • Order history and status tracking (PENDING → PAID → SHIPPED → DELIVERED)

Non-Functional Requirements

  • Scale: 10M DAU, 1M checkouts/day; peak 100× on flash sales (~1,200 checkout QPS)
  • Cart latency: <50ms retrieval (Redis)
  • Inventory correctness: No overselling — must be strictly enforced, not eventually consistent
  • Idempotency: Double-clicking checkout must not create duplicate orders or double-charge
  • Payment atomicity: Payment failure = no order created; order should not exist in a half-paid state
Flash sale scenario: 100,000 users try to buy the same item simultaneously when only 1,000 units are available. Ask the interviewer about this case — it defines whether you need pessimistic or optimistic inventory locking.

🔢 E — Estimation 3–5 min

  • Cart writes: 10M DAU × 5 cart updates/day ÷ 86,400s = ~580 QPS normal, ~10× peak = 5,800 QPS
  • Checkout QPS: 1M checkouts/day ÷ 86,400 = ~12 QPS normal; flash sale peak ~1,200 QPS
  • Cart data size: 10M active carts × avg 5 items × 200B per item = ~10GB (fits in Redis with plenty of headroom)
  • Order history: 1M orders/day × 1KB per order = 1GB/day → ~365GB/year (PostgreSQL handles this easily)
  • Inventory contention: During a flash sale, potentially 100K writes/second to a single product_id row → this is the critical hot-spot to design around

🗄️ S — Schema 5 min 

-- carts: use JSONB for flexible item list; user_id is the natural PK
-- In Redis: HASH cart:{user_id} with field per product_id
CREATE TABLE carts (
    user_id     UUID        PRIMARY KEY,
    items       JSONB       NOT NULL DEFAULT '[]',
    -- Each item: { product_id, quantity, unit_price_snapshot, added_at }
    -- Price snapshot: lock in price at cart-add time (show "price when added")
    updated_at  TIMESTAMP   DEFAULT NOW()
);

-- products: inventory_count = available; reserved_count = pending checkout
CREATE TABLE products (
    product_id       UUID         PRIMARY KEY,
    name             VARCHAR(255),
    price            DECIMAL(10,2),
    inventory_count  INT          NOT NULL DEFAULT 0,
    reserved_count   INT          NOT NULL DEFAULT 0,
    -- available = inventory_count - reserved_count
    version          BIGINT       DEFAULT 0   -- optimistic lock version
);

-- orders: JSONB items snapshot + status machine
CREATE TABLE orders (
    order_id         UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id          UUID         NOT NULL,
    status           VARCHAR(20)  DEFAULT 'PENDING',
    items            JSONB        NOT NULL,  -- snapshot of cart at checkout time
    subtotal         DECIMAL(10,2),
    discount_amount  DECIMAL(10,2) DEFAULT 0,
    total            DECIMAL(10,2),
    payment_id       VARCHAR(255),           -- Stripe/PayPal charge ID
    idempotency_key  VARCHAR(255) UNIQUE,    -- prevents duplicate checkout submissions
    created_at       TIMESTAMP    DEFAULT NOW()
);

-- coupons: track usage with max_uses ceiling
CREATE TABLE coupons (
    coupon_code     VARCHAR(50)  PRIMARY KEY,
    discount_type   VARCHAR(10),   -- PERCENT or FIXED
    discount_value  DECIMAL(10,2),
    min_order       DECIMAL(10,2) DEFAULT 0,
    max_uses        INT,
    used_count      INT          DEFAULT 0,
    expires_at      TIMESTAMP
);

🏗️ H — High-level Design 10 min

Services

  • Cart Service — Redis (primary) + PostgreSQL (durability); HASH per user; TTL 30 days
  • Product / Inventory Service — manages inventory_count and reserved_count; handles reservation and confirmation
  • Order Service — orchestrates checkout saga; creates order record; idempotency gate
  • Payment Service — integrates with Stripe/PayPal; returns payment_id on success
  • Coupon Service — validates and applies discount codes; atomic increment of used_count
  • Notification Service — sends confirmation email after successful checkout (async via Kafka)

Checkout Saga (Happy Path)

// 1. Client sends POST /v1/checkout with idempotency_key (UUID generated client-side)
//
// 2. Order Service: idempotency gate
//    → Redis SET NX idempotency:{key} → if exists, return cached order_id
//
// 3. Inventory Service: reserve items (two-phase)
//    → UPDATE products SET reserved_count += qty WHERE inventory_count - reserved_count >= qty
//    → If any item fails: return 409 Conflict "item out of stock"
//
// 4. Coupon Service: validate + apply coupon (if provided)
//    → Check expiry, min_order, remaining uses
//    → Return discount_amount
//
// 5. Order Service: create order record (status = PENDING)
//    → Calculate total = subtotal - discount_amount
//
// 6. Payment Service: charge payment method
//    → Stripe charge API → returns payment_id
//    → On failure: trigger compensating transactions (see Deliver)
//
// 7. Order Service: mark order PAID, store payment_id
//
// 8. Inventory Service: confirm reservation → deduct from inventory_count
//    UPDATE products SET inventory_count -= qty, reserved_count -= qty
//
// 9. Notification Service: async → send confirmation email (Kafka event)

🔬 D — Deep Dive: Preventing Overselling 10 min

The Race Condition

Two users simultaneously check inventory (1 unit available). Both see "in stock". Both create orders. You've sold the same unit twice — overselling. You need atomic check-and-decrement.

Option A: Pessimistic Locking (SELECT FOR UPDATE)

BEGIN;
SELECT inventory_count FROM products WHERE product_id = ? FOR UPDATE;
-- ^ Acquires row-level lock. Other checkouts for same product block here.
IF inventory_count >= qty:
    UPDATE products SET inventory_count = inventory_count - qty;
    COMMIT;
ELSE:
    ROLLBACK; -- out of stock

Works, but: serializes all checkouts for the same product. At 1,200 QPS flash sale, creates a queue. Lock holder crash can stall others.

Option B: Optimistic Locking (Recommended)

// Atomic conditional UPDATE — no lock held
UPDATE products
SET reserved_count = reserved_count + ?
WHERE product_id = ?
  AND (inventory_count - reserved_count) >= ?;
-- If 0 rows affected: sold out (another checkout got the last unit)
// rowsAffected == 0 → return "Out of stock" to user
// rowsAffected == 1 → reservation succeeded, proceed to payment

Why this works: The database evaluates the AND condition atomically. Only one of two concurrent UPDATEs will satisfy inventory - reserved >= qty. No lock, no blocking.

Option C: Redis Atomic Decrement (Flash Sale)

// Pre-load inventory into Redis: SET inventory:{product_id} 1000
// On each checkout attempt:
Long remaining = jedis.decrBy("inventory:" + productId, requestedQty);
if (remaining < 0) {
    jedis.incrBy("inventory:" + productId, requestedQty);  // rollback
    return "OUT_OF_STOCK";
}
// Asynchronously sync Redis count back to DB

For flash sales: DECR is O(1) and single-threaded in Redis. No DB contention at all during the hot spike. DB inventory updated async after the sale window closes.

⚖️ E — Evaluate 3 min

  • Overselling: Optimistic locking on reserved_count ensures exactly one thread wins the last unit. Redis DECR handles flash-sale spike traffic without DB contention.
  • Idempotency: Redis SET NX on idempotency_key ensures double-click returns the same order_id, no second charge. Key TTL 24h covers all realistic retry windows.
  • Payment failure rollback: Saga compensating transaction releases the reservation. No orphaned reserved inventory.
  • Cart durability: Write-through to both Redis (fast) and PostgreSQL (persistent). Redis miss → load from PostgreSQL → re-warm Redis.

🚀 D — Deliver 2 min

  • Cart: Redis HASH as primary storage (O(1) per field access), write-through to PostgreSQL for durability. TTL 30 days on Redis keys.
  • Inventory: Two-phase reservation (reserve on checkout start → confirm on payment success → release on payment failure). Optimistic locking via conditional UPDATE prevents overselling without holding locks.
  • Idempotency: Client generates UUID per checkout intent. Server does Redis SET NX — first request processes, retries return cached result. Eliminates double-charge risk.
  • Saga: Choreography-based saga. Payment failure publishes an event; Inventory Service subscribes and releases the reservation. No 2PC distributed transaction required.

⚡ Trade-offs

Decision Option A Option B Choose When
Cart storage Redis + PostgreSQL write-through DynamoDB (managed, auto-scaling) Redis+PG: lowest latency, familiar ops. DynamoDB: managed TTL, global tables for multi-region carts, no Redis ops overhead.
Inventory locking Optimistic (conditional UPDATE) Redis DECR (atomic counter) Optimistic: general use, normal traffic, no extra infrastructure. Redis DECR: flash sales with extreme contention on a single product — offloads DB entirely.
Checkout orchestration Synchronous saga (one service calls all others) Async saga via events (Kafka) Synchronous: simpler, immediate response, easier debugging. Async: better resilience if any service is slow, but harder to trace and return order_id immediately.
Checkout service architecture Monolith checkout service (all in one) Microservices (one per domain: cart, inventory, order, payment) Monolith: start here; simpler transactions, fewer network hops. Microservices: scale each domain independently when bottlenecks emerge.

☕ Java Implementation 

import redis.clients.jedis.Jedis;
import java.math.BigDecimal;
import java.util.List;
import java.util.UUID;

/**
 * CheckoutService: orchestrates the full checkout saga.
 *
 * Flow: idempotency gate → reserve inventory → validate coupon
 *       → create order → charge payment → confirm inventory → notify
 *
 * Compensating transactions triggered on any failure after reservation.
 */
public class CheckoutService {

    private static final String IDEMPOTENCY_KEY_PREFIX = "idempotency:checkout:";
    private static final int IDEMPOTENCY_TTL_SECONDS = 86_400;   // 24 hours

    private final Jedis redisClient;
    private final InventoryRepository inventoryRepository;
    private final OrderRepository orderRepository;
    private final CouponService couponService;
    private final PaymentGateway paymentGateway;
    private final NotificationPublisher notificationPublisher;

    public CheckoutService(
            Jedis redisClient,
            InventoryRepository inventoryRepository,
            OrderRepository orderRepository,
            CouponService couponService,
            PaymentGateway paymentGateway,
            NotificationPublisher notificationPublisher) {
        this.redisClient = redisClient;
        this.inventoryRepository = inventoryRepository;
        this.orderRepository = orderRepository;
        this.couponService = couponService;
        this.paymentGateway = paymentGateway;
        this.notificationPublisher = notificationPublisher;
    }

    // ── Public API ─────────────────────────────────────────────────

    /**
     * Processes a checkout request end-to-end.
     * Returns the order ID (same value on duplicate submission).
     *
     * @param idempotencyKey UUID generated by client on checkout button click
     * @param cartItems      items from the user's cart
     * @param couponCode     optional coupon code (null if not used)
     * @param paymentMethodId Stripe payment method ID
     * @return CheckoutResult with order_id and final total
     */
    public CheckoutResult processCheckout(
            String idempotencyKey,
            List<CartItem> cartItems,
            String couponCode,
            String paymentMethodId) {

        // Step 1: Idempotency gate — prevents duplicate checkout processing
        String cachedOrderId = getIdempotencyCache(idempotencyKey);
        if (cachedOrderId != null) {
            return CheckoutResult.fromCachedOrderId(cachedOrderId);
        }

        // Step 2: Reserve inventory (two-phase reservation)
        boolean reservationSucceeded = inventoryRepository.reserveItems(cartItems);
        if (!reservationSucceeded) {
            throw new OutOfStockException("One or more items are no longer available");
        }

        try {
            // Step 3: Validate and apply coupon
            BigDecimal subtotal = calculateSubtotal(cartItems);
            BigDecimal discountAmount = (couponCode != null)
                ? couponService.validateAndApply(couponCode, subtotal)
                : BigDecimal.ZERO;
            BigDecimal orderTotal = subtotal.subtract(discountAmount);

            // Step 4: Create order record in PENDING state
            String newOrderId = UUID.randomUUID().toString();
            orderRepository.createOrder(newOrderId, cartItems, orderTotal, discountAmount);

            // Step 5: Charge payment (external call — most likely failure point)
            String paymentId = paymentGateway.charge(paymentMethodId, orderTotal);

            // Step 6: Confirm order and reduce actual inventory
            orderRepository.markOrderPaid(newOrderId, paymentId);
            inventoryRepository.confirmReservation(cartItems);

            // Step 7: Cache result for idempotency; publish notification
            storeIdempotencyCache(idempotencyKey, newOrderId);
            notificationPublisher.publishOrderConfirmation(newOrderId);

            return new CheckoutResult(newOrderId, orderTotal, "PAID");

        } catch (PaymentFailedException paymentError) {
            // Compensating transaction: release the reservation we made in Step 2
            inventoryRepository.releaseReservation(cartItems);
            throw paymentError;

        } catch (Exception unexpectedError) {
            // Safety net: always release reservation on any unexpected failure
            inventoryRepository.releaseReservation(cartItems);
            throw new CheckoutException("Checkout failed unexpectedly", unexpectedError);
        }
    }

    // ── Private helpers ────────────────────────────────────────────

    private String getIdempotencyCache(String idempotencyKey) {
        return redisClient.get(IDEMPOTENCY_KEY_PREFIX + idempotencyKey);
    }

    private void storeIdempotencyCache(String idempotencyKey, String orderId) {
        redisClient.setex(IDEMPOTENCY_KEY_PREFIX + idempotencyKey, IDEMPOTENCY_TTL_SECONDS, orderId);
    }

    private BigDecimal calculateSubtotal(List<CartItem> cartItems) {
        return cartItems.stream()
            .map(item -> item.getUnitPriceSnapshot().multiply(
                BigDecimal.valueOf(item.getQuantity())
            ))
            .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}

// ── Inventory Repository: optimistic locking ─────────────────────

// SQL for reserving a single item (called per cart item):
// UPDATE products
// SET reserved_count = reserved_count + :qty
// WHERE product_id = :product_id
//   AND (inventory_count - reserved_count) >= :qty;
//
// Returns rowsAffected. If 0 → out of stock.
// No lock acquired. Database evaluates condition atomically.

// SQL for confirming reservation after payment success:
// UPDATE products
// SET inventory_count = inventory_count - :qty,
//     reserved_count  = reserved_count  - :qty
// WHERE product_id = :product_id;

// SQL for releasing reservation after payment failure:
// UPDATE products
// SET reserved_count = reserved_count - :qty
// WHERE product_id = :product_id;
