Tier 2 — Senior 45 min CDN · Collab Filtering · DRM

Design Spotify

Music streaming = STORE (audio in object storage) + STREAM (adaptive bitrate via CDN) + DISCOVER (two recommendation engines) + OFFLINE (DRM-encrypted downloads). Each is a fully independent subsystem with different scaling characteristics.

🏢 Spotify, Apple Music, Amazon Music, YouTube Music
⏱️ 45 min interview
🎯 CDN streaming · Collab filtering · DRM
🧠 The Core Mental Model

STORE → STREAM → DISCOVER → OFFLINE. Audio files live in S3 (3 quality tiers per song). Audio is delivered directly from CDN edge nodes — it never touches your API servers. Discovery is two separate systems: batch collaborative filtering for Discover Weekly, real-time audio-feature ANN for Radio. Offline is DRM-encrypted downloads with license keys that expire. Use these four pillars as your interview skeleton.

❓R — Requirements3–5 min

Functional Requirements

  • Stream songs: Playback starts within 2 seconds, no buffering on a decent connection. Gapless between tracks.
  • Search: Songs, artists, albums — results in <200ms with fuzzy matching
  • Playlists: Create, edit, reorder, share playlists. Collaborative playlists (multiple editors).
  • Recommendations: Discover Weekly (refreshed Sunday, personalized 30-song playlist) and Radio (real-time "more like this song")
  • Offline mode (Premium): Download up to 10,000 songs to device for playback without internet
  • Podcast support: Same streaming infrastructure, separate content ingestion pipeline

Non-Functional Requirements

  • Scale: 600M users, 250M Premium (paying) — largest music platform on earth
  • Audio storage: 100M songs × 3 quality tiers = ~1PB of audio files
  • Play latency: p99 <2s time-to-first-audio, p99 seek <500ms
  • Availability: 99.99% — "music never stops" is a core brand promise
  • Concurrent streams: 600M DAU × avg 30 min/day listening = ~300K simultaneous streams at peak
⛔ Explicitly Out of Scope

Social features (following friends), live events/concerts, video, lyrics sync display (mention as a deep dive option), royalty calculation pipeline. State these at the start.

🏗️H — High-level Design10 min

STORE — Audio File Management

  • 3 quality tiers per song: 96kbps AAC (mobile low-data), 160kbps (standard), 320kbps (Premium lossless). S3 key: /audio/{song_id}/{quality}.aac
  • No audio through API servers — the most important architectural decision. API server returns a presigned CDN URL with 4-hour TTL. Client fetches audio directly from the nearest CDN POP.
  • Upload pipeline: Artist uploads raw WAV → SQS queue → FFmpeg workers transcode to 3 tiers → audio feature extraction → copyright fingerprint check → S3 upload → song marked "available".

STREAM — Adaptive Bitrate Audio Delivery

  • CDN pre-positioning: Popular songs are pre-pushed to all CDN POPs globally. Viral songs are served from cache edge-to-client; S3 never sees the spike.
  • Adaptive bitrate: Client measures available bandwidth every 10 seconds. On poor connection (mobile on subway): auto-downgrades to 96kbps. On WiFi: uses 320kbps. Switch is seamless mid-song.
  • Prefetch buffer: Client downloads the next 30 seconds of audio ahead of the current playback position. Seek within buffered range is instant.
  • Gapless playback: When 15 seconds remain in current song, client fires background request for next song's CDN URL and begins buffering. Crossfade over 5 seconds eliminates audible gap.

DISCOVER — Two Recommendation Systems

System 1: Collaborative Filtering (Discover Weekly — batch)

  • User-song play matrix: 600M users × 100M songs (extremely sparse — each user has heard ~0.001% of catalog)
  • Matrix factorization (ALS algorithm): decomposes into user vectors (600M × 100) and song vectors (100M × 100)
  • Cosine similarity between user vectors → find users with similar taste → surface songs they loved but you haven't heard
  • Run as weekly Spark job Sunday night, store top-50 per user in Redis, refreshed Monday morning

System 2: Audio Feature ANN (Radio — real-time)

  • Spotify analyzes every song: BPM, musical key, energy (0–1), danceability (0–1), acousticness, valence (musical happiness)
  • Each song is a point in 100-dimensional audio-feature space
  • Radio = "find k nearest neighbors in this space to the seed song" → FAISS/HNSW index for approximate nearest neighbor in milliseconds
  • No user history needed → solves cold start for new users and new songs simultaneously

OFFLINE — DRM-Encrypted Downloads

  • Client requests presigned S3 URL for encrypted audio file + DRM license key from license server
  • Audio file encrypted with AES-128. Key tied to user's subscription status via license server.
  • License keys have 24-48h TTL — client must periodically renew while connected to internet
  • When subscription expires: license server refuses key renewal → encrypted files become unplayable ciphertext

🔬D — Deep Dive15 min

1. Why Audio Never Touches Your API Servers

This is the single most important architectural insight in the problem. Let's calculate why:

300,000 concurrent streams × 160kbps = 48 Gbps of audio data
A standard API server can handle ~10 Gbps throughput maximum.
You would need 5+ dedicated servers just for bandwidth — not for compute.

CDN solution:
→ API server returns presigned CDN URL (just 200 bytes of JSON)
→ Client fetches audio from nearest CDN POP (possibly 5ms away)
→ API server load: 300K × ~100 bytes/s of control traffic ≈ 30 MB/s
→ CDN handles: 48 Gbps across 200+ POPs = 240 Mbps per POP average

This is why Netflix, Spotify, YouTube, Apple Music ALL use CDN for media.
If you route audio through your API servers in an interview, flag it immediately.

2. Gapless Playback — The Engineering Detail Interviewers Love

The 100ms silence between tracks that amateur streaming apps produce is a UX catastrophe for music. Gapless playback requires coordinating two concurrent streams:

Timeline:
  t=0s:  Song A starts playing
  t=3:05s (15s before end): Client fires GET /v1/songs/{B}/stream
                            Client starts buffering Song B in background
  t=3:15s:  Song A has 5s left. Begin crossfade:
            AudioA.volume fading 1.0 → 0.0 over 5s
            AudioB.volume fading 0.0 → 1.0 over 5s
  t=3:20s:  Song A ends. Song B already fully buffered and playing.
            Zero gap, zero buffering spinner.

Browser implementation: two <audio> elements, swap currentTime listeners.
Native mobile: use AudioQueueRef (iOS) or AudioTrack (Android) with seamless handoff.

3. The Cold Start Problem in Recommendations

Collaborative filtering is useless for a new user — no play history means no position in the user-song matrix. This is the cold start problem.

  • Onboarding signal: Ask new user to pick 3+ favorite artists/genres → immediately use content-based ANN on those artists' top songs
  • Implicit signals from day 1: Play duration is a powerful signal even without history. <30 seconds = strong skip (negative). Full play + repeat = strong like (positive). These feed into the model after just a few sessions.
  • Geo + demographic defaults: New user in Brazil → start with trending Brazilian artists. Not ideal but far better than random.
  • Audio features solve cold start for NEW SONGS: A song uploaded today has no play history but has audio features immediately. ANN can recommend it to users who like acoustically similar songs before a single play event exists.
💡 Discover Weekly: The Mechanics

Matrix factorization decomposes the enormous user-song play matrix into two smaller matrices: User Factors (600M × 100) and Song Factors (100M × 100). The 100-dimensional vectors are latent representations — the algorithm discovers features like "affinity for acoustic indie" automatically without labeling. Two users with similar factor vectors have similar tastes. Top-N songs for a user = k-nearest songs in factor space that the user hasn't heard. Computed for all 600M users in parallel via Spark ALS — precomputed and stored in Redis, so query time is O(1).

4. Audio Upload Processing Pipeline

When an artist (or podcaster) uploads new content, synchronous processing would mean users wait minutes for the upload to "finish" and timeout on large files. The correct pattern is async pipeline:

1. API accepts raw upload → stores to S3 raw bucket → returns 202 Accepted + job_id
2. SQS message triggers processing workers (independent, retriable):
   a. FFmpeg workers: transcode to 96/160/320 kbps AAC (parallelized per tier)
   b. Feature extractor: BPM, key, energy, danceability → store in songs table
   c. Waveform generator: amplitude array → stored as JSONB for visualization
   d. Copyright detector: Shazam-style audio fingerprint against known catalog
3. All outputs uploaded to S3 production bucket
4. Song record updated: status = AVAILABLE
5. Elasticsearch index updated: song is now searchable
6. Webhook/push notification to artist: "Your song is live!"

Total time: typically 2-8 minutes depending on file size and queue depth.
Status endpoint: GET /v1/upload/{job_id}/status → { status: "PROCESSING", progress: 60 }

5. Royalty Tracking at Scale

Every play_event feeds into a royalty calculation pipeline — music labels receive per-stream payments. 6 billion events/day cannot be processed synchronously.

  • play_events → Kafka topic → Flink stream processing → aggregate by (song_id, day) → royalty_calculations table
  • End-of-month batch job: sum all daily aggregates → generate payout amounts per rights holder → trigger payment processing
  • Short plays (<30 seconds) do NOT generate royalties (industry standard) — the duration_played_ms field in the play_event schema is critical for this filter

⚖️E — Evaluate Bottlenecks5 min

🚨 Bottleneck 1: Viral Song Thundering Herd

A new Taylor Swift album drops. 50M users start playing the same song simultaneously. Mitigation: (1) CDN pre-positioning — the new release is pre-pushed to all CDN POPs before the release timestamp. (2) Multi-CDN: route through Akamai AND Cloudflare — no single CDN POP becomes a bottleneck. (3) S3 already handles millions of concurrent reads natively. The CDN absorbs 99.9% of the spike before S3 sees it.

🚨 Bottleneck 2: Discover Weekly — 600M Playlists in One Night

Sunday night: generate 600M personalized playlists using matrix factorization. This takes ~6 hours on a 10,000-node Spark cluster. Key insight: matrix factorization computes ALL user vectors and song vectors in one pass — it doesn't run separately per user. The computation scales with matrix size, not user count. Pre-store results in Redis with a 7-day TTL. If the job overruns, last week's recommendations serve as fallback.

🚨 Bottleneck 3: Copyright and DRM Compliance

Music labels require DRM for all audio content — this is non-negotiable. Every audio file must be encrypted (AES-128 or Widevine). The license server is a critical availability dependency — if it goes down, no one can play music (even online streams need license verification on first play). Mitigation: multi-region license server with 99.999% SLA. License keys cached on client for 24h so brief outages don't interrupt playback.

🎯D — Deliver: Closing Statement2 min

"Spotify is four independent subsystems. STORE: 100M songs stored in S3 as 3 quality tiers per song (96/160/320kbps). STREAM: the most critical insight — audio never touches your API servers. The client gets a presigned CDN URL and fetches audio directly from the nearest CDN edge node. Adaptive bitrate auto-switches quality based on bandwidth. Gapless playback prefetches the next song 15 seconds early. DISCOVER: two engines for different use cases — weekly Spark matrix factorization for Discover Weekly (batch, stored in Redis), real-time FAISS audio-feature ANN for Radio (solves cold start too). OFFLINE: DRM-encrypted files with 24-hour license keys. Subscription expiry = license server denies renewal = files become unplayable ciphertext on the device."

⚡Key Trade-offs

Decision Option A Option B Winner & Why
Audio delivery Proxy through API servers Presigned CDN URL — audio direct to client ✅ CDN — API servers cannot handle 48Gbps; CDN scales horizontally across global POPs
Recommendations Only collaborative filtering Collab filtering + audio-feature ANN ✅ Both — collab for personalization, ANN for cold start and real-time radio
Offline protection Trust client to check subscription status DRM: encrypted files + expiring license keys from server ✅ DRM — only cryptographically enforced solution. Client-side checks are trivially bypassed.
Play event DB MySQL Cassandra (append-only, time-series) ✅ Cassandra — 6B events/day is pure write throughput. MySQL would require extreme sharding.
Search Custom inverted index Elasticsearch ✅ Elasticsearch — 100M songs is manageable, operational simplicity wins at this scale vs building from scratch
Quality selection User selects manually Adaptive (auto, with user override) ✅ Adaptive default — prevents most buffering. Power users can force 320kbps. Best of both.

☕Java Implementation

The core streaming service: presigned URL generation, quality gating, and async play event logging:

/**
 * MusicStreamingService — core service for song streaming and event tracking.
 *
 * Key design decisions:
 *   - Audio delivery via presigned CDN URLs only (no audio bytes through this service)
 *   - Play events logged asynchronously to Kafka (non-blocking — never delay a stream for logging)
 *   - Premium quality gating: free users get 160kbps max
 *   - URL TTL: 4 hours (long enough for a full album listen, short enough to limit abuse)
 */
import java.util.UUID;
import java.time.Instant;
import java.time.Duration;
import java.util.concurrent.CompletableFuture;

public class MusicStreamingService {

    // ── Constants ──────────────────────────────────────────────────────────────

    private static final Duration CDN_URL_TTL = Duration.ofHours(4);
    private static final int MIN_PLAY_DURATION_MS_FOR_ROYALTY = 30_000;  // 30 seconds
    private static final String CDN_BASE_URL = "https://cdn.spotify.com/audio";

    // ── Inner Types ────────────────────────────────────────────────────────────

    public enum AudioQuality {
        LOW_96KBPS("96kbps", false),         // mobile data-saver, available to all
        STANDARD_160KBPS("160kbps", false),  // default, available to all
        HIGH_320KBPS("320kbps", true);       // Premium only

        public final String label;
        public final boolean requiresPremium;

        AudioQuality(String label, boolean requiresPremium) {
            this.label = label;
            this.requiresPremium = requiresPremium;
        }
    }

    public record StreamResponse(
        String streamUrl,          // presigned CDN URL — expires in 4 hours
        AudioQuality quality,      // actual quality granted (may downgrade if not Premium)
        int durationMs,
        double[] waveformData      // amplitude array for visualization UI
    ) {}

    public record PlayEvent(
        UUID userId,
        UUID songId,
        long durationPlayedMs,
        String source,             // search | playlist | radio | recommendation
        String deviceType,
        Instant playedAt
    ) {}

    // ── Dependencies (injected) ────────────────────────────────────────────────

    private final SongRepository songRepository;
    private final UserRepository userRepository;
    private final CdnSigningService cdnSigningService;    // generates presigned URLs
    private final KafkaProducer<String, PlayEvent> kafkaProducer;

    public MusicStreamingService(
        SongRepository songRepository,
        UserRepository userRepository,
        CdnSigningService cdnSigningService,
        KafkaProducer<String, PlayEvent> kafkaProducer
    ) {
        this.songRepository = songRepository;
        this.userRepository = userRepository;
        this.cdnSigningService = cdnSigningService;
        this.kafkaProducer = kafkaProducer;
    }

    // ── Core Logic ─────────────────────────────────────────────────────────────

    /**
     * Returns a presigned CDN URL for the requested song.
     * Audio NEVER flows through this service — only the URL is returned.
     *
     * Quality is downgraded to STANDARD_160KBPS if user is not Premium
     * and HIGH_320KBPS was requested. This is enforced server-side —
     * never trust the client to gate Premium features.
     *
     * @param songId    the song to stream
     * @param userId    the requesting user (used to check subscription)
     * @param requested the quality tier the client wants
     * @return StreamResponse with a 4-hour CDN URL
     * @throws SongNotFoundException if song_id does not exist or is not yet available
     * @throws UserNotFoundException if user_id is invalid
     */
    public StreamResponse getSongStreamUrl(UUID songId, UUID userId, AudioQuality requested) {
        Song song = fetchSongOrThrow(songId);
        User user = fetchUserOrThrow(userId);

        AudioQuality grantedQuality = resolveGrantedQuality(requested, user.isPremium());
        String presignedUrl = buildPresignedCdnUrl(songId, grantedQuality);

        return new StreamResponse(
            presignedUrl,
            grantedQuality,
            song.durationMs(),
            song.waveformData()
        );
    }

    /**
     * Logs a play event to Kafka asynchronously.
     * This must NEVER block the streaming response — royalty accounting happens
     * in a separate async pipeline. Fire-and-forget: if Kafka is temporarily down,
     * we lose some play events but we never delay music playback.
     *
     * Events with duration < 30s are still logged but flagged as "skips" —
     * they do NOT generate royalty payments but ARE used as negative signals
     * for recommendation training.
     *
     * @param event  the play event to record
     */
    public void logPlayEventAsync(PlayEvent event) {
        // Non-blocking: returns immediately, Kafka send happens on producer thread pool
        CompletableFuture.runAsync(() -> {
            try {
                kafkaProducer.send("play-events", event.userId().toString(), event);
            } catch (KafkaException kafkaException) {
                // Log internally but DO NOT surface to user or caller.
                // A missed play event is acceptable. A delayed stream is not.
                System.err.println("[MusicStreamingService.logPlayEventAsync] Kafka send failed: " + kafkaException.getMessage());
            }
        });
    }

    // ── Helper Logic ──────────────────────────────────────────────────────────

    /**
     * Enforces Premium quality gating server-side.
     * 320kbps is downgraded to 160kbps for free-tier users.
     * This prevents client-side manipulation of the quality parameter.
     */
    private AudioQuality resolveGrantedQuality(AudioQuality requested, boolean isPremium) {
        if (requested.requiresPremium && !isPremium) {
            return AudioQuality.STANDARD_160KBPS;  // silent downgrade — standard UX
        }
        return requested;
    }

    /**
     * Builds a presigned CDN URL with 4-hour expiry signature.
     * The URL points directly to the CDN edge — client fetches audio without
     * any further involvement from this service.
     *
     * Pattern: {CDN_BASE}/{song_id}/{quality}.aac?sig={hmac_signature}&expires={ts}
     */
    private String buildPresignedCdnUrl(UUID songId, AudioQuality quality) {
        String audioPath = String.format("%s/%s/%s.aac", CDN_BASE_URL, songId, quality.label);
        long expiresAt = Instant.now().plus(CDN_URL_TTL).getEpochSecond();
        String signature = cdnSigningService.sign(audioPath, expiresAt);
        return String.format("%s?expires=%d&sig=%s", audioPath, expiresAt, signature);
    }

    private Song fetchSongOrThrow(UUID songId) {
        return songRepository.findById(songId)
            .orElseThrow(() -> new SongNotFoundException("Song not found or not yet available: " + songId));
    }

    private User fetchUserOrThrow(UUID userId) {
        return userRepository.findById(userId)
            .orElseThrow(() -> new UserNotFoundException("User not found: " + userId));
    }
}

// ─────────────────────────────────────────────────────────────────────────────

/**
 * RecommendationService — two engines for different contexts.
 *
 * Weekly:    Redis lookup — O(1), pre-computed Sunday night by Spark job
 * Radio:     Real-time ANN search in audio-feature vector space — p99 <50ms
 */
public class RecommendationService {

    private static final int RADIO_RESULT_COUNT = 25;

    private final RedisClient redisClient;
    private final SongFeatureRepository songFeatureRepository;
    private final AnnIndex annIndex;  // FAISS or HNSW index of audio feature vectors

    public RecommendationService(RedisClient redisClient,
                                  SongFeatureRepository songFeatureRepository,
                                  AnnIndex annIndex) {
        this.redisClient = redisClient;
        this.songFeatureRepository = songFeatureRepository;
        this.annIndex = annIndex;
    }

    /**
     * Returns pre-computed Discover Weekly playlist for a user.
     * Pre-computed by weekly Spark matrix factorization job, stored in Redis.
     * Key: "discover_weekly:{user_id}" → JSON list of 30 song UUIDs.
     *
     * Falls back to trending songs if no pre-computed result exists
     * (new users, or Spark job not yet run this week).
     *
     * @param userId  the user requesting their weekly playlist
     * @return ordered list of recommended song IDs
     */
    public java.util.List<UUID> getDiscoverWeekly(UUID userId) {
        String cacheKey = "discover_weekly:" + userId;
        java.util.List<UUID> cachedRecommendations = redisClient.getList(cacheKey, UUID.class);

        if (cachedRecommendations != null && !cachedRecommendations.isEmpty()) {
            return cachedRecommendations;
        }

        // Cold start or cache miss: fall back to curated trending songs for user's geo
        return getTrendingFallback(userId);
    }

    /**
     * Radio: finds songs acoustically similar to the seed song.
     * Uses Approximate Nearest Neighbor (ANN) search on 100-dimensional
     * audio feature vectors: [bpm, key, energy, danceability, valence, acousticness, ...]
     *
     * This solves the cold start problem for both:
     *   - New users (no play history needed — just a seed song)
     *   - New songs (can be recommended immediately after feature extraction)
     *
     * @param seedSongId  the song to find similar tracks for
     * @return list of acoustically similar song IDs, sorted by similarity descending
     */
    public java.util.List<UUID> getRadio(UUID seedSongId) {
        double[] seedFeatureVector = fetchAudioFeatureVector(seedSongId);

        // ANN lookup: finds k nearest neighbors in O(log N) — approximate but fast
        // HNSW index: ~5ms at 100M songs, vs exact search ~500ms
        java.util.List<UUID> similarSongIds = annIndex.findNearestNeighbors(
            seedFeatureVector,
            RADIO_RESULT_COUNT + 1  // +1 because the seed itself will be in results
        );

        // Remove the seed song itself from radio results
        similarSongIds.remove(seedSongId);
        return similarSongIds.subList(0, Math.min(RADIO_RESULT_COUNT, similarSongIds.size()));
    }

    private double[] fetchAudioFeatureVector(UUID songId) {
        SongFeatures features = songFeatureRepository.findById(songId)
            .orElseThrow(() -> new SongNotFoundException("Audio features not found for: " + songId));
        // Feature vector: [bpm_norm, key_norm, energy, danceability, valence, acousticness, ...]
        return new double[]{
            features.bpmNormalized(), features.keyNormalized(),
            features.energy(), features.danceability(),
            features.valence(), features.acousticness()
            // ... additional learned latent features from the ALS model
        };
    }

    private java.util.List<UUID> getTrendingFallback(UUID userId) {
        // Placeholder: in production, fetch from a trending-songs service
        // partitioned by user geography and onboarding genre preferences
        return java.util.Collections.emptyList();
    }
}
