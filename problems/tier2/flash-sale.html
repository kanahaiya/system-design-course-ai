Design E-commerce Flash Sale System

A flash sale has two hard problems: 1) Don't oversell (sell more units than exist). 2) Don't crash under a 10× traffic spike that lasts 5 minutes. Redis DECR is atomic — the solution to problem 1. Kafka queues solve problem 2.

🏢 Amazon, Alibaba, Shopify
⏱️ 45 min interview
⚡ 10× traffic spike

❓R — Requirements3–5 min

Functional Requirements

  • Users can view flash sale products and purchase at discounted price
  • Limited inventory (e.g., 1,000 iPhones at $199)
  • First-come-first-served within sale window
  • Order confirmation with payment processing

Non-Functional Requirements

  • No overselling: Never sell more units than available inventory
  • Traffic spike: Handle 100K requests/sec for a product with 1K inventory
  • Fair: Random selection is acceptable; but no request should succeed after stock is 0
  • Availability: Flash sale page must remain responsive even under extreme load

🔢E — Estimation3–5 min

  • Normal traffic: 10K req/sec. Flash sale: 10× = 100K req/sec for 5 minutes
  • 1,000 units available → only 1,000 orders succeed out of 100K attempts in first second
  • Rate of rejection: 99%+ → reject fast (before hitting DB) to save resources
  • Redis atomic DECR: 500K ops/sec on a single Redis instance → can handle 100K purchase attempts/sec

🗄️S — Schema3–5 min

// Redis (hot inventory counter — single source of truth during sale)
// Key: inventory:{productId}  Value: remaining_count (integer)
// Initialized before sale start: SET inventory:{productId} 1000

// Products (PostgreSQL)
products: product_id, name, original_price, sale_price, sale_start, sale_end

// Orders (PostgreSQL — written by order processor workers)
orders: order_id, user_id, product_id, quantity, status (pending/confirmed/failed),
        created_at, payment_intent_id

🏗️H — High-level Design10 min

  • Static Product Page: CDN-cached. No DB hits for browsing. Only the "Buy Now" action hits servers.
  • Rate Limiter: IP-based rate limiting at gateway. 1 request/user/second. Rejects obvious bots. Implemented via sliding window in Redis.
  • Inventory Check (Redis): Atomic DECR on inventory:{productId}. If result ≥ 0: reserved. If result < 0: INCR back + reject. This is the gatekeeper — fast (<1ms) and atomic.
  • Order Queue (Kafka): Successful reservations published to Kafka. Returns 202 Accepted immediately. Client polls order status.
  • Order Processor Workers: Consume Kafka. Create DB order record. Process payment. Update order status. Release inventory to DB on success.
  • Presale Warmup: Before sale starts, pre-warm CDN, load inventory to Redis, spin up extra order processor pods (Kubernetes HPA on queue depth).

🔌A — APIs5 min

GET  /v1/products/{productId}/flash-sale   // product page (CDN-cached)
POST /v1/orders/flash                      // purchase attempt (rate limited)
  Body: { productId, paymentMethodId }
  Returns: { orderId, status: "pending" } or 429/sold-out
GET  /v1/orders/{orderId}                  // poll order status

🔬D — Deep Dive: Redis Atomic Inventory10 min

Why Redis DECR is the right tool:

  • Redis is single-threaded. All commands execute sequentially. DECR is atomic by design — no race conditions.
  • At 100K purchase attempts/sec, a DB check-then-update pattern would require locking, causing serialization and timeout cascades under load.
  • Redis DECR + check result is O(1) and completes in <1ms — can handle 500K ops/sec on a single instance.

The atomic pattern:

long remaining = jedis.decr("inventory:" + productId);
if (remaining >= 0) {
    // Reserved! User gets a spot. Publish to Kafka.
} else {
    jedis.incr("inventory:" + productId); // undo the decrement
    return soldOut(); // reject request
}

Edge case: Redis crash between DECR and Kafka publish. The inventory is decremented but no order is created — a unit is "lost." Mitigation: write to Redis + DB atomically using Lua script or accept <1% inventory discrepancy, reconcile in batch.

✅E — Evaluate3 min

  • Thundering herd: 100K users hit at sale start simultaneously. Rate limiting at API gateway + CDN-served product page absorbs most. Only POST /orders hits the stack. Redis handles the inventory check.
  • Payment failure after inventory reserved: Order processor reserves inventory but payment fails. Must release inventory back to Redis (+1) to avoid permanently losing a unit.

🚀D — Deliver2 min

We designed a flash sale system handling 100K req/sec with zero overselling. Key decisions: Redis atomic DECR as gatekeeper (prevents overselling), CDN for product page (removes browse traffic from servers), Kafka queue to decouple purchase acceptance from order processing, and rate limiting to reduce bot traffic.

⚖️Trade-offs

DecisionChosenAlternativeWhy Chosen

☕Java Implementation

/**
 * FlashSaleService — atomic inventory reservation using Redis DECR.
 * Only successful reservations are forwarded to the order queue.
 */
public class FlashSaleService {
    private static final String INVENTORY_KEY_PREFIX = "inventory:";
    private final JedisPool jedisPool;
    private final KafkaProducer<String, String> kafkaProducer;

    public FlashSaleService(JedisPool jedisPool, KafkaProducer<String, String> kafkaProducer) {
        this.jedisPool = jedisPool;
        this.kafkaProducer = kafkaProducer;
    }

    /**
     * Attempts to reserve one unit for a flash sale product.
     * Returns a reservation token if successful, throws SoldOutException if not.
     */
    public String attemptPurchase(String productId, String userId, String paymentMethodId) {
        String inventoryKey = INVENTORY_KEY_PREFIX + productId;

        try (Jedis jedis = jedisPool.getResource()) {
            // Atomic decrement — Redis single-threaded guarantees no race condition
            long remainingInventory = jedis.decr(inventoryKey);

            if (remainingInventory < 0) {
                // Undo the decrement — we overshot, put it back
                jedis.incr(inventoryKey);
                throw new SoldOutException("Product " + productId + " is sold out");
            }

            // Reservation successful — publish to order queue asynchronously
            String orderId = UUID.randomUUID().toString();
            String orderJson = buildOrderJson(orderId, productId, userId, paymentMethodId);
            kafkaProducer.send(new ProducerRecord<>("flash-sale-orders", orderId, orderJson),
                (metadata, kafkaException) -> {
                    if (kafkaException != null) {
                        // Kafka publish failed — must release the reserved inventory
                        releaseInventory(inventoryKey);
                        System.err.println("[FlashSaleService] Kafka publish failed for order " + orderId
                                           + ": " + kafkaException.getMessage());
                    }
                });
            return orderId;
        }
    }

    private void releaseInventory(String inventoryKey) {
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.incr(inventoryKey);
        }
    }

    private String buildOrderJson(String orderId, String productId, String userId, String paymentMethodId) {
        return "{\"orderId\":\"" + orderId + "\",\"productId\":\"" + productId
               + "\",\"userId\":\"" + userId + "\",\"paymentMethodId\":\"" + paymentMethodId + "\"}";
    }
}
