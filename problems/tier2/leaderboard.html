Tier 2 — Should Know 45 min Redis data structures

Design Gaming Leaderboard

Redis Sorted Set is the canonical leaderboard data structure: O(log N) insert, O(log N) rank lookup, O(log N + M) range query. The interview tests whether you understand why — it's a skiplist with augmented node sizes, not a B-tree. The real challenge: 100M players, 10B score updates per day, friends leaderboards, and sub-100ms rank reads at any scale.

🏢 Riot Games, Activision, Epic, EA
⏱️ 45 min interview
🏆 100M concurrent players

❓ R — Requirements 3–5 min

Functional Requirements

  • Score update: Record a player's new score after each game match (overwrite or accumulate)
  • Global top-N: Return the top 100 (or top K) players globally with rank + score + username
  • Player rank lookup: Return a specific player's current rank, score, and percentile ("you're in the top 3%")
  • Friends leaderboard: Among a player's friends only — ranked list with their scores
  • Time-windowed leaderboards: All-time, monthly, weekly — each is an independent leaderboard
  • Score history: View a player's score progression over time (audit trail, not real-time)

Non-Functional Requirements

  • Scale: 100M registered players; 10M daily active players; 10B score updates per day (~115K/sec average, 500K/sec burst at end-of-match)
  • Read latency: Top-100 query <50ms; single player rank lookup <20ms; friends leaderboard <100ms
  • Write latency: Score update acknowledged <50ms (async propagation to leaderboard acceptable, <500ms)
  • Consistency: Eventual consistency acceptable — a rank can be slightly stale by up to 1 second
  • Availability: 99.99% for reads; writes can tolerate brief degradation at end-of-match burst
  • Durability: Score history must be durable (RDBMS). The Redis leaderboard is a derived cache — rebuildable from the database.
Critical clarification to ask the interviewer: Are scores cumulative (total XP earned over all games) or "best score" (highest single match score)? This changes the ZADD semantics — cumulative needs ZINCRBY; best-score needs conditional ZADD with NX/GT flags. For most gaming leaderboards: cumulative all-time, reset-per-period for weekly/monthly.

Out of Scope

  • Anti-cheat enforcement (flag only; not gameplay-level validation)
  • Matchmaking (not related to leaderboard)
  • Player authentication and session management

🔢 E — Estimation 3–5 min

Redis Sorted Set Memory Footprint

  • Per-entry cost: score (8 bytes, IEEE-754 double) + member pointer (8 bytes) + skiplist node metadata (~24 bytes) + hash table entry (~16 bytes) ≈ 56 bytes per player
  • 100M players global ZSET: 100M × 56 bytes = ~5.6GB — fits in a single Redis node (64GB RAM typical), but leaves little headroom
  • 10 shards of 10M players each: 10M × 56 bytes = 560MB per shard — very comfortable, leaves room for other keys and OS overhead
  • Weekly + monthly leaderboards (active players only ~10M): 10M × 56 bytes = 560MB each — negligible

Throughput

  • Score updates: 10B/day = 115,700/sec average; burst to 500K/sec at end-of-match windows
  • Single Redis node ZADD capacity: ~500K ops/sec (single-threaded, CPU-bound)
  • Kafka ingestion rate needed: 500K msgs/sec at burst — 50 partitions × 10K msgs/sec each
  • Read QPS: Top-100 cached, so ~1K cache misses/sec; player rank lookups ~50K/sec (ZREVRANK is O(log N))
  • Network bandwidth for score updates: 500K/sec × 64 bytes per message ≈ 32MB/sec — trivial

Latency Budget for Rank Lookup

  • API server → Redis ZREVRANK: ~0.5ms (local datacenter)
  • Redis ZREVRANK for 100M ZSET: O(log 100M) = ~27 comparisons → <0.1ms CPU
  • Player metadata enrichment (Redis hash lookup): ~0.3ms
  • Total: ~1ms p50, <5ms p99 — well within 20ms budget
L6 signal: The interviewer wants to see you do the 5.6GB calculation unprompted. It's the pivotal number — small enough for one node (so why shard?), but large enough to cause ops pain (single point of failure, 5GB RDB snapshot takes time, no horizontal write scaling). Sharding is about resilience and write throughput, not just memory.

🗄️ S — Schema 5 min

Redis Data Model (Hot Tier — Leaderboard Engine)

// ── Global all-time leaderboard (one ZSET per game) ──────────────────
// Key:    leaderboard:{gameId}:global
// Score:  cumulative player score (double)
// Member: player_id (string)
// Size:   100M entries ≈ 5.6GB
//
// Key operations:
//   ZADD leaderboard:fortnite:global GT {score} {playerId}   // GT: only update if new > current; O(log N)
//   ZREVRANK leaderboard:fortnite:global {playerId}          // 0-indexed rank (0 = #1); O(log N)
//   ZSCORE leaderboard:fortnite:global {playerId}            // current score; O(1)
//   ZREVRANGE leaderboard:fortnite:global 0 99 WITHSCORES    // top 100; O(log N + 100)
//   ZCARD leaderboard:fortnite:global                        // total players; O(1)
//   ZREVRANGEBYSCORE leaderboard:fortnite:global +inf {min}  // players above score threshold

// ── Time-windowed leaderboards (active players only) ─────────────────
// Key:    leaderboard:{gameId}:weekly:{YYYY-Www}   e.g., leaderboard:fortnite:weekly:2024-W52
// Key:    leaderboard:{gameId}:monthly:{YYYY-MM}   e.g., leaderboard:fortnite:monthly:2024-12
// TTL:    SET leaderboard:...:weekly:... EX 2592000 (30 days after period ends)
// Score:  score earned WITHIN that time window (not cumulative all-time)
// Note:   ZINCRBY for incremental — adds delta to existing score

// ── Player metadata cache (lookup after ZRANGE enrichment) ────────────
// Key:    player:{playerId}:meta
// Type:   Redis Hash
// Fields: username, avatar_url, country
// TTL:    3600 (1 hour — profile changes are rare)

// ── Friend graph (for friends leaderboard) ───────────────────────────
// Key:    friends:{playerId}
// Type:   Redis Set (or Bloom filter for large friend lists)
// Members: friend player IDs
// TTL:    600 (10 minutes — friend list changes infrequently)
// Size:   avg 200 friends × 8 bytes = 1.6KB per player

// ── Top-100 global cache (99% of homepage requests) ──────────────────
// Key:    leaderboard:{gameId}:top100:cache
// Type:   Redis String (serialized JSON of top-100 list)
// TTL:    5 seconds (near-real-time freshness)
// Refresh: background worker updates every 5 seconds via ZREVRANGE

PostgreSQL Schema (Cold/Durable Tier — Source of Truth)

-- Player scores (durable record — Redis is derived from this)
CREATE TABLE player_scores (
    player_id       BIGINT          NOT NULL,
    game_id         VARCHAR(64)     NOT NULL,
    all_time_score  BIGINT          NOT NULL DEFAULT 0,
    weekly_score    BIGINT          NOT NULL DEFAULT 0,
    monthly_score   BIGINT          NOT NULL DEFAULT 0,
    week_key        VARCHAR(8)      NOT NULL,   -- e.g., '2024-W52'
    month_key       VARCHAR(7)      NOT NULL,   -- e.g., '2024-12'
    updated_at      TIMESTAMPTZ     NOT NULL DEFAULT now(),
    PRIMARY KEY (player_id, game_id)
);
CREATE INDEX idx_player_scores_game_alltime ON player_scores(game_id, all_time_score DESC);

-- Score event log (immutable audit trail for cheat detection + Redis rebuild)
CREATE TABLE score_events (
    event_id        UUID            PRIMARY KEY DEFAULT gen_random_uuid(),
    player_id       BIGINT          NOT NULL,
    game_id         VARCHAR(64)     NOT NULL,
    match_id        UUID            NOT NULL,
    score_delta     INT             NOT NULL,         -- points earned this match
    score_after     BIGINT          NOT NULL,         -- cumulative score after event
    validated_at    TIMESTAMPTZ,                      -- NULL if pending anti-cheat
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT now()
);
CREATE INDEX idx_score_events_player ON score_events(player_id, created_at DESC);
CREATE INDEX idx_score_events_match  ON score_events(match_id);

-- Players (profile — enriches leaderboard display)
CREATE TABLE players (
    player_id       BIGINT          PRIMARY KEY,
    username        VARCHAR(64)     NOT NULL UNIQUE,
    avatar_url      VARCHAR(512),
    country_code    CHAR(2),
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT now()
);
Why PostgreSQL for the source of truth? Redis is an in-memory cache. If a Redis node fails without RDB/AOF persistence, scores are lost. The PostgreSQL score_events table lets us rebuild the Redis ZSET by replaying events. Writes go to both — Redis for low-latency reads, PostgreSQL for durability. This is the standard "write-through cache" pattern.

🏗️ H — High-level Design 10 min

Architecture Diagram

Write Path: Score Update

  1. Game server publishes match result to Kafka topic score-events (key = player_id for sticky partition routing)
  2. Score Processor consumers (one consumer group per game) read events, validate them against anti-cheat rules, then:
    • Execute ZADD leaderboard:{gameId}:global GT {newScore} {playerId} in Redis — "GT" flag means only update if the new score is greater than current (for best-score semantics) or ZINCRBY for cumulative
    • Write INSERT INTO score_events ... to PostgreSQL (async, batched every 100ms)
  3. Top-100 background job runs every 5 seconds: ZREVRANGE leaderboard:{gameId}:global 0 99 WITHSCORES, enriches with usernames, writes JSON to leaderboard:{gameId}:top100:cache

Read Path: Top-100 Query (99% of traffic)

  1. Client requests GET /v1/leaderboard/fortnite/top?limit=100
  2. CDN checks for cached response (TTL: 5s) → cache hit returns in <10ms
  3. On cache miss: API server reads leaderboard:fortnite:top100:cache from Redis → still <5ms
  4. On Redis key miss: re-execute ZREVRANGE + username enrichment → <20ms

Read Path: Single Player Rank Lookup

  1. Client requests GET /v1/leaderboard/fortnite/rank?playerId=abc123
  2. Execute ZREVRANK leaderboard:fortnite:global abc123 → returns 0-based rank → O(log N) ≈ 27 ops for 100M entries
  3. Execute ZSCORE leaderboard:fortnite:global abc123 → score in O(1)
  4. Percentile: rank / ZCARD * 100 — ZCARD is O(1), rank from step 2
  5. Enrich: HGETALL player:abc123:meta for display name
  6. Total: 3 Redis commands, ~1ms round-trip

Friends Leaderboard

This is the graph intersection problem: given player P's friend list F, find each friend's score and rank them. Two approaches:

  • Per-friend ZSCORE (recommended for ≤500 friends): Fetch friend list from Redis Set (friends:{playerId}), pipeline 200 ZSCORE calls (single round-trip via Redis pipeline), sort result in application layer. O(F log F) where F = friend count. Always fresh.
  • ZINTERSTORE (for ad-hoc): Create a temp ZSET friends-lb:{playerId}:{timestamp} by intersecting the global ZSET with the friends set via ZINTERSTORE. This operation is O(N × log M) where N=friends, M=global ZSET size. For 200 friends in a 100M ZSET: O(200 × 27) = O(5400) — fine. Then ZREVRANGE the temp key. But creating temp keys per-request at scale is wasteful; pipelined ZSCORE is cleaner.
L6 trap question: "Why not maintain a dedicated sorted set per user for friends?" Because with 100M players averaging 200 friends each, every score update would require updating up to 200 friend-leaderboard ZSETs. 115K score updates/sec × 200 = 23M Redis writes/sec — crushes the cluster. Per-request ZSCORE pipeline is the right call.

🔬 D — Deep Dive 10–15 min

1. Redis Sorted Set Internals: Why Skiplist + Hash Table?

L6 insight — Skiplist vs B-tree: Redis ZSET uses a skiplist, not a B-tree. The reason: a skiplist can be augmented with per-node subtree sizes. Each skiplist node stores the number of nodes "below" it in its tower. ZRANK then becomes O(log N) by accumulating these counts as it traverses down — no full scan needed. A B-tree cannot give you a rank this efficiently without additional bookkeeping. This "order statistics tree" property is the entire reason ZRANK is O(log N) rather than O(N).

Redis Sorted Set maintains two parallel data structures:

  • Hash table (member → score): O(1) lookup for ZSCORE. Allows "what is player X's score?" to be answered without touching the skiplist at all.
  • Skiplist (ordered by score, then member): O(log N) for ZADD, ZRANK, ZRANGE, ZREVRANGE. The skiplist supports efficient range queries that a hash table cannot.

Skiplist Memory Layout (simplified):

// Skiplist node structure (from Redis source: t_zset.c)
// Each node has a variable-height "tower" of forward pointers
// Each forward pointer stores: (1) the next node at that level, (2) span — number of nodes skipped

Level 3:  [HEAD] ─────────────────────────────────────► [score:10000] → NIL
Level 2:  [HEAD] ───────────────► [score:5000] ────────► [score:10000] → NIL
Level 1:  [HEAD] ──► [score:100] → [score:5000] → [score:8000] → [score:10000] → NIL
Level 0:  [HEAD] → [s:10] → [s:100] → [s:500] → [s:5000] → [s:8000] → [s:10000] → NIL
                    span=1    span=1    span=1    span=1    span=1     span=1

// ZRANK("player_with_score_5000"):
// Start at HEAD, level 3: span to score:10000 is 5 nodes → too far, drop to level 2
// Level 2: span to score:5000 is 3 nodes → accumulated rank = 3
// Return rank = 3 (0-indexed)
// Total: O(log N) hops, each hop skips 2× more nodes on average

Memory per node:

  • Score: 8 bytes (IEEE-754 double)
  • Member string pointer + length: 8 + 8 bytes
  • Skiplist forward pointers: average 1.33 levels × (8 + 8 bytes per pointer+span) ≈ 21 bytes
  • Hash table entry: ~16 bytes
  • Allocator overhead: ~8 bytes
  • Total ≈ 69 bytes per entry (vs the theoretical 56 bytes — allocator fragmentation adds ~20%)

2. Why ZRANGE is O(log N + M), Not O(M)

The log N term is the cost to find the starting position in the skiplist (like a binary search). The M term is the cost to traverse the next M elements from that position. For ZREVRANGE 0 99 (top 100): the start is always the head of the reversed list, so the O(log N) seek is effectively O(1) here — it just returns the last node and walks back 100 steps. Real cost: O(100) = O(M). This is why top-N queries are fast regardless of total set size.

3. Sharding: When One Redis Instance Isn't Enough

A single 100M-entry ZSET has three problems despite fitting in RAM:

  1. Single point of failure: One Redis node goes down → leaderboard is unavailable
  2. RDB snapshot latency: 5.6GB snapshot takes 15–30 seconds during which writes can stall (copy-on-write overhead)
  3. Write throughput ceiling: Redis is single-threaded per core. 500K ZADD/sec is the hard limit. Burst at end-of-match can exceed this.

Strategy A: Score-Range Sharding (Recommended)

// Shard assignment by score range:
// Shard 0: scores 0–999         (casual players, ~60% of 100M = 60M players)
// Shard 1: scores 1000–9999     (regular players, ~30% = 30M players)
// Shard 2: scores 10000–99999   (competitive players, ~9% = 9M players)
// Shard 3: scores 100000+        (elite players, ~1% = 1M players)

// Keys:
// lb:fortnite:global:shard:0   → 60M entries
// lb:fortnite:global:shard:1   → 30M entries
// lb:fortnite:global:shard:2   →  9M entries
// lb:fortnite:global:shard:3   →  1M entries

// WRITE: score event comes in → determine shard, ZADD to that shard
// If score crosses threshold (e.g., 999→1000): ZREM from old shard, ZADD to new shard (atomic via Lua)

// TOP-N READ: query shard 3 first (top 1M players)
// For top-100: shard 3 always has enough → single Redis call. Done.
// For top-1M: shard 3 + shard 2 → merge 1M + 9M, take top 1M

// RANK LOOKUP for player with score 5000 (shard 1):
// globalRank = ZCARD(shard3) + ZCARD(shard2) + ZREVRANK(shard1, playerId) + 1
// = 1M + 9M + rank_within_shard + 1 → 3 Redis calls
Why score-range beats hash sharding here: With hash sharding, every top-100 query fans out to all 10 shards. With score-range sharding, the top-100 query almost always hits only shard 3 (elite players). Given that 99% of leaderboard traffic is "show me the top 100," score-range sharding eliminates scatter-gather for the hottest query path.

Strategy B: Hash Sharding (Better for Write Balance)

// Shard by hash(player_id) % 10
// Each shard has ~10M players regardless of score distribution
// Pros: perfectly balanced write load
// Cons: top-N requires querying all 10 shards, merging 10 sorted lists (10-way merge)

// Top-100 query with hash sharding:
// For each shard i: ZREVRANGE lb:shard:{i} 0 99 WITHSCORES  → 10 parallel calls
// In application: 10-way merge sort of 10 lists of 100 entries → take top 100
// Cost: 10 Redis calls (parallel) + O(10 × 100 × log 10) merge ≈ trivial CPU
// Latency: max(10 parallel Redis calls) ≈ same as 1 call since they're parallel

4. Near-Real-Time Updates: Per-Event vs Batched

Per-event ZADD<500ms end-to-end500K ops/sec per nodeReal-time rank; higher write pressure on Redis

Recommended: Per-event updates via Kafka → Score Processor. The Kafka buffer absorbs burst traffic (500K/sec end-of-match spike) and Score Processor consumers pace the writes to Redis at a sustainable rate. If all 50K players finish a match simultaneously, Kafka queues the events and Redis sees a smooth stream at its 500K/sec capacity.

7. Cheat Detection and Score Validation

The leaderboard is only as trustworthy as the score update pipeline. L6 candidates are expected to address this proactively:

  • Server-side score calculation: Game servers compute final scores — client never sends its own score. Clients report match actions (kills, objectives), server validates and computes score. Never trust client input for score values.
  • Rate limiting score updates: A player can only submit one score per completed match. The Score Processor checks: "has this player submitted a score for this matchId?" (idempotency key in Redis with TTL). Duplicate submissions are rejected.
  • Spike detection: Anti-Cheat consumer group reads the same Kafka topic. For each event: if scoreDelta > MAX_SCORE_PER_MATCH or scoreAfter > player's historical_max × SPIKE_FACTOR, flag for review and hold the update. Score is not applied to the leaderboard until the event is either cleared or rejected.
  • Retroactive invalidation: If a cheat is confirmed post-facto, Score Processor replays the player's event log minus the cheated events, recomputes their true score, and ZADD GT with the corrected score.
The score-update race condition: Two game servers submit score events for the same player simultaneously (different matches). Redis ZADD is atomic per command, but the "remove from old shard + add to new shard" operation for score-range sharding is two commands. Use a Lua script for atomic cross-shard moves: 
// Lua script for atomic shard-boundary score update
// Runs on the Redis node holding the leaderboard key
-- KEYS[1] = old shard key, KEYS[2] = new shard key
-- ARGV[1] = player_id, ARGV[2] = new_score
local removed = redis.call('ZREM', KEYS[1], ARGV[1])
if removed == 1 then
    redis.call('ZADD', KEYS[2], ARGV[2], ARGV[1])
end
return removed

// In Java (Jedis):
String luaScript = "...";
jedis.eval(luaScript, Arrays.asList(oldShardKey, newShardKey),
           Arrays.asList(playerId, String.valueOf(newScore)));

8. Cache Strategy for Top-100

The top-100 global leaderboard is the highest-traffic, lowest-selectivity query. It's the same for all users requesting it. This is the perfect CDN cache candidate:

  • Cache key: /v1/leaderboard/{gameId}/top?period=global — no user-specific component
  • TTL: 5 seconds — top rank changes are exciting but players tolerate ~5s staleness
  • Cache warming: A background cron job (runs every 5s) pre-computes the top-100, enriches with usernames, serializes to JSON, and pushes to both Redis cache and CDN. No request ever needs to do a cold ZREVRANGE.
  • Invalidation: If a player in the top 100 achieves a new rank, the background job will catch it within 5 seconds. No event-driven invalidation needed — polling is sufficient given the 5s TTL matches the polling interval.

Cache hit rate math: 50M daily reads / 86,400 seconds = 578 reads/sec. With 5s TTL, cache is refreshed 17,280 times/day. Each cache entry serves 578 × 5 ≈ 2,890 requests. Cache hit rate: (2890 - 1) / 2890 ≈ 99.97% cache hit rate for top-100 queries.

Edge Cases and Failure Modes

  • Tie-breaking: Redis ZSET with equal scores orders members lexicographically by member name. For gaming fairness, encode time-of-achievement in the score: effectiveScore = score * 1_000_000L + (Long.MAX_VALUE - achievedAtUnixMs). Players who achieved the score earlier rank higher. The precision factor (1M) means scores up to 9,223 trillion are safe — no overflow for realistic game scores.
  • Redis node failure: Redis Sentinel or Cluster handles failover in ~30 seconds. During failover, rank queries fail-open (return HTTP 503 with cached last-known top-100). Score updates queue in Kafka — consumed after Redis recovers. No data loss because PostgreSQL is the source of truth.
  • Score crossing a shard boundary: Handled atomically via Lua script (see Deep Dive §7). Without atomicity, a player could briefly appear in both shards or neither — causing incorrect global rank calculation.
  • Player never played (no entry in ZSET): ZREVRANK returns nil → API returns 404 for rank lookup → frontend shows "Unranked." ZSCORE returns nil → don't include in friends leaderboard.
  • Extremely large friend lists (celebrities, influencers with 10K+ friends): 10K ZSCORE calls pipelined is still a single Redis round-trip returning 10K values. O(10K) application sort is ~0.1ms. Still acceptable. Cap at 500 friends shown in friends leaderboard for UI reasons.

🚀 D — Deliver 2 min

We designed a gaming leaderboard handling 100M players with sub-20ms rank lookups and 500K score updates/sec burst capacity. The key architectural decisions:

  • Redis Sorted Set (ZSET) as the leaderboard engine — its skiplist structure gives O(log N) rank operations, which is fundamental to the design. ZRANK is not O(N) — this is the insight that separates senior candidates.
  • Score-range sharding across 10 Redis nodes — distributes write load and eliminates the single point of failure, while keeping top-N queries to a single shard (the elite shard).
  • Kafka as the write buffer — decouples game servers from the leaderboard pipeline, absorbs end-of-match bursts (500K/sec), and enables exactly-once score processing via idempotent matchId keys.
  • PostgreSQL as the durable source of truth — Redis is a derived cache. Score events are immutable append-only records enabling Redis rebuild after failure, cheat investigation, and score history.
  • 5-second CDN cache for top-100 — eliminates 99.97% of leaderboard read load from Redis with an RPC that only staleness is 5 seconds, which is the right product-engineering tradeoff for a live leaderboard.
  • Pipelined ZSCORE for friends leaderboard — avoids the combinatorial explosion of maintaining per-user friend ZSETs (would require 23M Redis writes/sec).

⚖️ Trade-offs

Decision Chosen Approach Alternative Why Chosen / When to Switch
Rank data structure Redis Sorted Set (skiplist) PostgreSQL RANK() OVER (ORDER BY score DESC) window function Redis ZREVRANK is O(log N) ≈ 0.1ms. PostgreSQL window function re-ranks entire table at query time — O(N log N) without pre-computed rank column. For 100M rows: tens of seconds. Even with an index on score, COUNT(*) to find rank is O(N) without rank materialization. Redis wins by 3–4 orders of magnitude for rank lookup latency.
Score update path Async via Kafka → Score Processor → Redis Synchronous: game server directly calls ZADD on Redis Async path: absorbs 500K/sec burst via Kafka queue; game server gets fast 202 ACK. Sync path: simpler but game server must wait for Redis; burst can overwhelm Redis directly. For a real-time game, the 500ms eventual consistency is acceptable — rank precision during the match isn't critical.
Sharding strategy Score-range sharding (shard by score bucket) Hash sharding (shard by hash(player_id) % N) Score-range: top-N query hits only the highest shard (O(1) shards for top-100). Downside: uneven write distribution (casual players are in shard 0, which gets 60% of writes). Hash sharding: perfectly balanced writes; top-N requires all-shard fanout. Given 5:1 read:write ratio and top-100 being 90% of reads, score-range wins. Switch to hash if write throughput imbalance becomes a bottleneck.

ZINTERSTORE: cleaner code but O(N × log M) where N=friends, M=global ZSET size; creates temporary keys at request time — memory pressure at scale. Pipelined ZSCORE wins for <500 friends. ZINTERSTORE makes more sense if friend lists are stable and you can cache the intersected ZSET (TTL: 60s).
Top-100 freshness 5-second CDN/Redis cache with background refresh Per-request ZREVRANGE (real-time) Cache: 99.97% hit rate, <10ms latency, protects Redis from thundering herd. Real-time: always accurate, but 578 uncacheable ZREVRANGE calls/sec hits Redis directly. For most games, 5-second stale top-100 is fine. Exception: esports live tournament finals where real-time rank matters — use WebSocket push with server-side subscription instead.
Per-event vs batch score updates Per-event updates (Kafka consumer, one ZADD per event) Batch every 1–10 seconds (accumulate deltas, one ZADD per batch) Per-event: rank reflects last match result within 500ms. Batch: 10× more write-efficient via pipelined multi-ZADD; rank can lag by batch interval. For weekly/monthly leaderboards: batch is fine (rank doesn't need to update in seconds). For real-time in-game leaderboards: per-event is required. Our architecture supports both by changing the consumer commit interval.
Redis durability AOF persistence + PostgreSQL source of truth Redis RDB snapshots only (or no persistence) AOF: every write is appended to disk; data loss window is at most 1 second (appendfsync everysec). RDB: full snapshot every N minutes; can lose minutes of updates. No persistence: Redis is pure cache, rebuild from PostgreSQL on failure (takes ~5 minutes for 100M entries). The right choice depends on rebuild tolerance. If Redis rebuild from Postgres takes <5 min and 5-min stale leaderboard is acceptable: skip AOF, save ~30% write throughput.

LeaderboardService — Core ZSET Operations

/**
 * LeaderboardService — wraps Redis Sorted Set operations for a single leaderboard.
 *
 * All operations assume the Redis key format:
 *   leaderboard:{gameId}:{period}  e.g., leaderboard:fortnite:global
 *
 * ZADD GT semantics: score only increases (best-score leaderboard).
 * Use ZINCRBY variant for cumulative (total XP) leaderboards.
 */
public class LeaderboardService {

    private static final String KEY_PREFIX = "leaderboard:";
    private static final String PLAYER_META_PREFIX = "player:";
    private static final String TOP100_CACHE_SUFFIX = ":top100:cache";
    private static final int TOP100_CACHE_TTL_SECONDS = 5;
    private static final int PLAYER_META_TTL_SECONDS = 3600;

    private final JedisPool jedisPool;

    public LeaderboardService(JedisPool jedisPool) {
        this.jedisPool = jedisPool;
    }

    /**
     * Updates a player's score. Uses ZADD with GT flag — score only moves upward.
     * For cumulative leaderboards, use updateScoreIncremental() instead.
     *
     * @param gameId   game identifier
     * @param period   leaderboard period key (e.g., "global", "weekly:2024-W52")
     * @param playerId player identifier
     * @param newScore the player's new absolute score
     * @return true if the score was updated (new score was higher than previous)
     */
    public boolean updateScore(String gameId, String period, String playerId, double newScore) {
        String leaderboardKey = buildLeaderboardKey(gameId, period);
        try (Jedis jedis = jedisPool.getResource()) {
            // GT flag: only update if newScore > current stored score
            // NX flag would mean "only add if not present" — don't use that here
            Map<String, Double> scoreMap = Map.of(playerId, newScore);
            long updatedCount = jedis.zadd(leaderboardKey, scoreMap,
                ZAddParams.zAddParams().gt());
            return updatedCount > 0;
        }
    }

    /**
     * Increments a player's score by delta (for cumulative / XP-based leaderboards).
     *
     * @param gameId     game identifier
     * @param period     leaderboard period key
     * @param playerId   player identifier
     * @param scoreDelta points to add (must be positive)
     * @return the new cumulative score after increment
     */
    public double incrementScore(String gameId, String period, String playerId, double scoreDelta) {
        String leaderboardKey = buildLeaderboardKey(gameId, period);
        try (Jedis jedis = jedisPool.getResource()) {
            return jedis.zincrby(leaderboardKey, scoreDelta, playerId);
        }
    }

    /**
     * Returns the top-N players with their scores, enriched with display names.
     * Reads from cache first; falls back to live ZREVRANGE on cache miss.
     *
     * @param gameId game identifier
     * @param period leaderboard period key
     * @param topN   number of players to return (1–1000)
     * @return ordered list of PlayerRankEntry, rank 1 = best
     */
    public List<PlayerRankEntry> getTopPlayers(String gameId, String period, int topN) {
        String leaderboardKey = buildLeaderboardKey(gameId, period);

        try (Jedis jedis = jedisPool.getResource()) {
            // ZREVRANGE returns members ordered highest score first
            // 0-indexed: index 0 = rank 1, index (topN-1) = rank topN
            List<Tuple> topEntries = jedis.zrevrangeWithScores(leaderboardKey, 0, topN - 1);

            List<PlayerRankEntry> result = new ArrayList<>(topEntries.size());
            int rank = 1;
            for (Tuple entry : topEntries) {
                String username = getPlayerUsername(jedis, entry.getElement());
                result.add(new PlayerRankEntry(rank++, entry.getElement(), username, entry.getScore()));
            }
            return result;
        }
    }

    /**
     * Returns a single player's rank, score, and percentile.
     * ZREVRANK is O(log N) — safe for 100M entries.
     *
     * @param gameId   game identifier
     * @param period   leaderboard period key
     * @param playerId player identifier
     * @return PlayerRankInfo or empty if player has no score in this leaderboard
     */
    public Optional<PlayerRankInfo> getPlayerRank(String gameId, String period, String playerId) {
        String leaderboardKey = buildLeaderboardKey(gameId, period);

        try (Jedis jedis = jedisPool.getResource()) {
            // ZREVRANK: 0-indexed rank where 0 = highest score (rank #1)
            Long zeroIndexedRank = jedis.zrevrank(leaderboardKey, playerId);
            if (zeroIndexedRank == null) {
                return Optional.empty(); // player not in this leaderboard
            }

            Double score = jedis.zscore(leaderboardKey, playerId);
            long totalPlayers = jedis.zcard(leaderboardKey);
            long oneIndexedRank = zeroIndexedRank + 1;

            // percentile: 99 = top 1%, 50 = top 50%, etc.
            double percentile = (1.0 - (double) zeroIndexedRank / totalPlayers) * 100.0;

            return Optional.of(new PlayerRankInfo(
                playerId,
                getPlayerUsername(jedis, playerId),
                oneIndexedRank,
                score != null ? score : 0.0,
                percentile,
                totalPlayers
            ));
        }
    }

    /**
     * Returns the friends leaderboard by pipelining ZSCORE calls for each friend.
     * Single Redis round-trip regardless of friend count (up to ~500 friends).
     *
     * @param gameId    game identifier
     * @param period    leaderboard period key
     * @param playerId  the player whose friends list to use
     * @param friendIds list of friend player IDs
     * @return friends ranked by score, viewer included in the list
     */
    public List<PlayerRankEntry> getFriendsLeaderboard(
            String gameId, String period, String playerId, List<String> friendIds) {

        String leaderboardKey = buildLeaderboardKey(gameId, period);
        // Include the requesting player in the friends leaderboard
        List<String> allParticipants = new ArrayList<>(friendIds);
        if (!allParticipants.contains(playerId)) {
            allParticipants.add(playerId);
        }

        try (Jedis jedis = jedisPool.getResource()) {
            // Pipeline all ZSCORE calls into a single round-trip
            Pipeline pipeline = jedis.pipelined();
            List<Response<Double>> scoreResponses = new ArrayList<>(allParticipants.size());
            for (String participantId : allParticipants) {
                scoreResponses.add(pipeline.zscore(leaderboardKey, participantId));
            }
            pipeline.sync(); // single round-trip to Redis

            // Build (participantId, score) pairs, filtering unranked players
            List<double[]> scoredParticipants = new ArrayList<>();
            for (int index = 0; index < allParticipants.size(); index++) {
                Double participantScore = scoreResponses.get(index).get();
                if (participantScore != null) {
                    // store as [encodedScore, originalIndex] for sort-then-lookup
                    scoredParticipants.add(new double[]{participantScore, index});
                }
            }

            // Sort descending by score in application layer
            scoredParticipants.sort((entryA, entryB) -> Double.compare(entryB[0], entryA[0]));

            List<PlayerRankEntry> result = new ArrayList<>(scoredParticipants.size());
            int friendRank = 1;
            for (double[] participantEntry : scoredParticipants) {
                int originalIndex = (int) participantEntry[1];
                String participantId = allParticipants.get(originalIndex);
                String username = getPlayerUsername(jedis, participantId);
                result.add(new PlayerRankEntry(friendRank++, participantId, username, participantEntry[0]));
            }
            return result;
        }
    }

    private String buildLeaderboardKey(String gameId, String period) {
        return KEY_PREFIX + gameId + ":" + period;
    }

    private String getPlayerUsername(Jedis jedis, String playerId) {
        String metaKey = PLAYER_META_PREFIX + playerId + ":meta";
        String username = jedis.hget(metaKey, "username");
        return username != null ? username : playerId; // fallback to ID if not cached
    }

    public record PlayerRankEntry(int rank, String playerId, String username, double score) {}

    public record PlayerRankInfo(
        String playerId, String username, long rank,
        double score, double percentile, long totalPlayers
    ) {}
}

ShardedLeaderboardService — Score-Range Sharding for 100M Players

/**
 * ShardedLeaderboardService — distributes a global leaderboard across multiple Redis
 * sorted sets using score-range sharding for efficient top-N queries and global rank.
 *
 * Shard topology (static thresholds — tune based on score distribution analysis):
 *   Shard 0: score < 1,000        (casual players, ~60% of population)
 *   Shard 1: score < 10,000       (regular players, ~30%)
 *   Shard 2: score < 100,000      (competitive players, ~9%)
 *   Shard 3: score >= 100,000     (elite players, ~1%)
 *
 * Why static thresholds? Dynamic thresholds require knowing the score distribution
 * in advance (percentile-based sharding). Static thresholds are predictable and
 * operationally simpler. Re-balance by adjusting thresholds and reloading.
 */
public class ShardedLeaderboardService {

    private static final String SHARD_KEY_TEMPLATE = "leaderboard:%s:global:shard:%d";
    private static final double[] SHARD_THRESHOLDS = {1_000.0, 10_000.0, 100_000.0, Double.MAX_VALUE};

    // Lua script for atomic shard boundary crossing (ZREM + ZADD as one operation)
    private static final String SHARD_CROSS_LUA_SCRIPT = """
        local removed = redis.call('ZREM', KEYS[1], ARGV[1])
        if removed == 1 then
            redis.call('ZADD', KEYS[2], tonumber(ARGV[2]), ARGV[1])
        end
        return removed
        """;

    private final JedisPool jedisPool;
    private final String gameId;

    public ShardedLeaderboardService(JedisPool jedisPool, String gameId) {
        this.jedisPool = jedisPool;
        this.gameId = gameId;
    }

    /**
     * Updates a player's score, handling shard boundary crossings atomically.
     * If the player moves from one score tier to another, the Lua script ensures
     * they are removed from the old shard and added to the new shard atomically.
     *
     * @param playerId player identifier
     * @param newScore the player's updated score
     */
    public void updateScore(String playerId, double newScore) {
        int newShardIndex = resolveShardIndex(newScore);
        String newShardKey = buildShardKey(newShardIndex);

        try (Jedis jedis = jedisPool.getResource()) {
            // Find current shard for this player (needed to handle cross-shard moves)
            Integer currentShardIndex = findPlayerCurrentShard(jedis, playerId);

            if (currentShardIndex == null) {
                // New player — simply add to the correct shard
                jedis.zadd(newShardKey, newScore, playerId);
                return;
            }

            if (currentShardIndex == newShardIndex) {
                // Same shard — simple ZADD with GT (only update if higher)
                jedis.zadd(newShardKey, Map.of(playerId, newScore), ZAddParams.zAddParams().gt());
                return;
            }

            // Cross-shard boundary — must be atomic to avoid double-counting or gaps in rank
            String oldShardKey = buildShardKey(currentShardIndex);
            jedis.eval(SHARD_CROSS_LUA_SCRIPT,
                Arrays.asList(oldShardKey, newShardKey),
                Arrays.asList(playerId, String.valueOf(newScore)));
        }
    }

    /**
     * Returns the top-N players globally by reading from the highest shard down.
     * For top-100: almost always returns from shard 3 only (elite players).
     *
     * @param topN number of top players to return
     * @return ordered list of PlayerEntry, rank 1 = best
     */
    public List<PlayerEntry> getTopPlayers(int topN) {
        List<PlayerEntry> collectedResults = new ArrayList<>(topN);

        try (Jedis jedis = jedisPool.getResource()) {
            // Iterate from highest-scoring shard (index 3) down to lowest (index 0)
            for (int shardIndex = SHARD_THRESHOLDS.length - 1; shardIndex >= 0; shardIndex--) {
                if (collectedResults.size() >= topN) break;

                int remainingNeeded = topN - collectedResults.size();
                String shardKey = buildShardKey(shardIndex);

                // ZREVRANGE: highest scores first within this shard
                List<Tuple> shardEntries = jedis.zrevrangeWithScores(shardKey, 0, remainingNeeded - 1);
                for (Tuple shardEntry : shardEntries) {
                    int globalRank = collectedResults.size() + 1;
                    collectedResults.add(new PlayerEntry(shardEntry.getElement(), shardEntry.getScore(), globalRank));
                }
            }
        }
        return collectedResults;
    }

    /**
     * Computes a player's global rank across all shards.
     * Global rank = (total players in higher shards) + (rank within own shard) + 1.
     *
     * Three Redis calls:
     *   1. Find player's shard via ZSCORE (up to 4 attempts)
     *   2. ZCARD for each higher-scoring shard (1–3 calls)
     *   3. ZREVRANK within the player's own shard (1 call)
     *
     * @param playerId player identifier
     * @return 1-indexed global rank, or -1 if player not found
     */
    public long getGlobalRank(String playerId) {
        try (Jedis jedis = jedisPool.getResource()) {
            Integer playerShardIndex = findPlayerCurrentShard(jedis, playerId);
            if (playerShardIndex == null) {
                return -1; // player has no score entry
            }

            // Count all players in shards with higher score thresholds
            long playersInHigherShards = 0;
            for (int higherShardIndex = playerShardIndex + 1;
                 higherShardIndex < SHARD_THRESHOLDS.length;
                 higherShardIndex++) {
                playersInHigherShards += jedis.zcard(buildShardKey(higherShardIndex));
            }

            // Rank within own shard (0-indexed; 0 = highest in shard)
            Long rankWithinShard = jedis.zrevrank(buildShardKey(playerShardIndex), playerId);
            if (rankWithinShard == null) {
                return -1; // shouldn't happen if findPlayerCurrentShard succeeded
            }

            // Global rank: all players in higher shards rank ahead of this player
            return playersInHigherShards + rankWithinShard + 1; // convert to 1-indexed
        }
    }

    /**
     * Returns total number of players across all shards.
     * Used for percentile calculation: percentile = (1 - rank/total) * 100
     */
    public long getTotalPlayerCount() {
        try (Jedis jedis = jedisPool.getResource()) {
            long totalCount = 0;
            for (int shardIndex = 0; shardIndex < SHARD_THRESHOLDS.length; shardIndex++) {
                totalCount += jedis.zcard(buildShardKey(shardIndex));
            }
            return totalCount;
        }
    }

    private Integer findPlayerCurrentShard(Jedis jedis, String playerId) {
        // Check each shard from highest to lowest (elite players found faster)
        for (int shardIndex = SHARD_THRESHOLDS.length - 1; shardIndex >= 0; shardIndex--) {
            Double scoreInShard = jedis.zscore(buildShardKey(shardIndex), playerId);
            if (scoreInShard != null) {
                return shardIndex;
            }
        }
        return null; // player not in any shard
    }

    private int resolveShardIndex(double score) {
        for (int shardIndex = 0; shardIndex < SHARD_THRESHOLDS.length; shardIndex++) {
            if (score < SHARD_THRESHOLDS[shardIndex]) {
                return shardIndex;
            }
        }
        return SHARD_THRESHOLDS.length - 1; // score exceeds all thresholds → top shard
    }

    private String buildShardKey(int shardIndex) {
        return String.format(SHARD_KEY_TEMPLATE, gameId, shardIndex);
    }

    public record PlayerEntry(String playerId, double score, int globalRank) {}
}

ScoreProcessor — Kafka Consumer with Idempotent Write Logic

/**
 * ScoreProcessor — Kafka consumer that processes score events from game servers
 * and applies them to the sharded Redis leaderboard + PostgreSQL durable store.
 *
 * Idempotency: each event has a matchId. Duplicate events (game server retries)
 * are detected via a Redis bloom filter keyed on matchId before processing.
 */
public class ScoreProcessor {

    private static final String PROCESSED_MATCHES_BLOOM_KEY = "bloom:processed-matches";
    private static final double MAX_SCORE_PER_MATCH = 10_000.0;  // anti-cheat threshold
    private static final String KAFKA_TOPIC = "score-events";

    private final ShardedLeaderboardService shardedLeaderboard;
    private final ScoreEventRepository scoreEventRepository; // PostgreSQL
    private final JedisPool jedisPool;
    private final KafkaConsumer<String, ScoreEvent> kafkaConsumer;

    public ScoreProcessor(
            ShardedLeaderboardService shardedLeaderboard,
            ScoreEventRepository scoreEventRepository,
            JedisPool jedisPool,
            KafkaConsumer<String, ScoreEvent> kafkaConsumer) {
        this.shardedLeaderboard = shardedLeaderboard;
        this.scoreEventRepository = scoreEventRepository;
        this.jedisPool = jedisPool;
        this.kafkaConsumer = kafkaConsumer;
    }

    /**
     * Main processing loop — consumes score events from Kafka and applies them.
     * Runs in a dedicated thread per Kafka partition consumer.
     */
    public void run() {
        kafkaConsumer.subscribe(List.of(KAFKA_TOPIC));
        while (!Thread.currentThread().isInterrupted()) {
            ConsumerRecords<String, ScoreEvent> kafkaRecords = kafkaConsumer.poll(Duration.ofMillis(100));
            for (ConsumerRecord<String, ScoreEvent> kafkaRecord : kafkaRecords) {
                processScoreEvent(kafkaRecord.value());
            }
            // Manual offset commit after batch is fully processed (at-least-once delivery)
            kafkaConsumer.commitSync();
        }
    }

    /**
     * Processes a single score event with idempotency and anti-cheat validation.
     * Steps:
     *   1. Idempotency check (bloom filter + PostgreSQL fallback)
     *   2. Anti-cheat validation (score delta within acceptable range)
     *   3. Write to Redis sharded leaderboard
     *   4. Write to PostgreSQL (async batch — separate thread pool)
     */
    private void processScoreEvent(ScoreEvent scoreEvent) {
        // Step 1: Idempotency — skip if this matchId was already processed
        if (isMatchAlreadyProcessed(scoreEvent.matchId())) {
            return; // silently skip duplicate — already applied
        }

        // Step 2: Anti-cheat validation
        if (!isScoreEventValid(scoreEvent)) {
            flagForAntiCheatReview(scoreEvent);
            return; // hold the score — don't apply until reviewed
        }

        // Step 3: Update Redis leaderboard (all active periods)
        shardedLeaderboard.updateScore(scoreEvent.playerId(), scoreEvent.scoreAfter());

        // Update weekly and monthly period ZSETs (incremental)
        String weekKey = "weekly:" + getCurrentWeekKey();
        String monthKey = "monthly:" + getCurrentMonthKey();
        // Use a non-sharded LeaderboardService for time-windowed (smaller ZSETs)
        // leaderboardService.incrementScore(scoreEvent.gameId(), weekKey, scoreEvent.playerId(), scoreEvent.scoreDelta());
        // leaderboardService.incrementScore(scoreEvent.gameId(), monthKey, scoreEvent.playerId(), scoreEvent.scoreDelta());

        // Step 4: Mark as processed (bloom filter for fast path, PostgreSQL for truth)
        markMatchAsProcessed(scoreEvent.matchId());
        scoreEventRepository.saveAsync(scoreEvent); // fire-and-forget to PostgreSQL
    }

    private boolean isMatchAlreadyProcessed(String matchId) {
        try (Jedis jedis = jedisPool.getResource()) {
            // BF.EXISTS: O(1) probabilistic check — false positives possible, no false negatives
            // If bloom says "exists": double-check PostgreSQL (rare case)
            // If bloom says "not exists": definitely not processed (skip PostgreSQL)
            Object bloomResult = jedis.sendCommand(
                SafeEncoder.encode("BF.EXISTS"),
                SafeEncoder.encode(PROCESSED_MATCHES_BLOOM_KEY),
                SafeEncoder.encode(matchId)
            );
            if ((long) bloomResult == 1L) {
                // Bloom filter says "seen" — verify with PostgreSQL to avoid false positive
                return scoreEventRepository.existsByMatchId(matchId);
            }
            return false;
        }
    }

    private void markMatchAsProcessed(String matchId) {
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.sendCommand(
                SafeEncoder.encode("BF.ADD"),
                SafeEncoder.encode(PROCESSED_MATCHES_BLOOM_KEY),
                SafeEncoder.encode(matchId)
            );
        }
    }

    private boolean isScoreEventValid(ScoreEvent scoreEvent) {
        // Score delta must be positive and within the maximum achievable per match
        return scoreEvent.scoreDelta() > 0
            && scoreEvent.scoreDelta() <= MAX_SCORE_PER_MATCH
            && scoreEvent.scoreAfter() >= scoreEvent.scoreDelta(); // no underflow
    }

    private void flagForAntiCheatReview(ScoreEvent scoreEvent) {
        // Publish to separate Kafka topic for anti-cheat service to process
        // Anti-cheat service will either clear the event (re-publish to score-events)
        // or reject it (write rejection record to PostgreSQL)

    private String getCurrentWeekKey() {
        return LocalDate.now().format(DateTimeFormatter.ofPattern("YYYY-'W'ww"));
    }

    private String getCurrentMonthKey() {
        return LocalDate.now().format(DateTimeFormatter.ofPattern("yyyy-MM"));
    }

    public record ScoreEvent(
        String eventId,
        String playerId,
        String gameId,
        String matchId,
        double scoreDelta,

        long timestampMs
    ) {}
