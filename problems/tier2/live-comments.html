Tier 2 — Important 45 min Real-time / Fan-out

Design a Live Comments System

The core challenge: one comment posted to a stream with 100,000 viewers must reach all of them within 500ms. That's 100,000 push deliveries per comment — the fan-out problem defines this entire design.

🏢 YouTube, Twitch, Meta, TikTok
⏱️ 45 min interview
📈 Write-amplification at scale

❓ R — Requirements 3–5 min

Functional Requirements

  • Post a comment on a live stream (text, max 500 characters)
  • View real-time comment feed — new comments appear within 500ms for all viewers
  • React to comments (👍 ❤️) — lightweight, eventual consistency acceptable
  • Moderator can delete a comment; deleted comment disappears for all active viewers

Non-Functional Requirements

  • Scale: 100K concurrent viewers per popular stream; 1M concurrent viewers globally across all streams
  • Throughput: 10K comments/minute per stream during peak = 167 write QPS per stream
  • Latency: Comment must appear to all viewers within 500ms of posting
  • Durability: Comments persisted for later VOD (Video On Demand) playback
Fan-out calculation: 167 writes/s × 100K viewers = 16.7M message deliveries per second per stream. State this number explicitly to the interviewer — it frames the entire architectural challenge.

🔢 E — Estimation 3–5 min

  • Active streams: 1M concurrent viewers ÷ 100K viewers/stream = ~10 popular live streams at peak
  • Comment writes: 10 streams × 167 QPS = ~1,670 total comment writes/second globally
  • Fan-out deliveries: 1,670 writes/s × 100K avg viewers = 167M deliveries/second — the dominant load
  • Storage: 1,670 comments/s × 500B avg = ~835KB/s = ~72GB/day persisted to Cassandra
  • WebSocket connections: 1M concurrent viewers requires ~10–100 WebSocket servers (each can hold 10K–100K connections)

🗄️ S — Schema 5 min 

-- Cassandra schema (time-series, write-heavy)
-- Partition key: (stream_id, time_bucket) — caps partition size for high-traffic streams
-- Clustering key: comment_id DESC — newest comments first within partition

CREATE TABLE comments (
    stream_id    UUID,
    time_bucket  TEXT,          -- e.g., '2024-01-15-14' (hour bucket)
    comment_id   BIGINT,        -- Snowflake ID: sortable, globally unique
    user_id      UUID,
    username     TEXT,
    content      TEXT,
    is_deleted   BOOLEAN DEFAULT FALSE,
    created_at   TIMESTAMP,
    PRIMARY KEY ((stream_id, time_bucket), comment_id)
) WITH CLUSTERING ORDER BY (comment_id DESC)
  AND default_time_to_live = 2592000;  -- 30 day TTL

-- streams table (PostgreSQL — small table, relational)
CREATE TABLE streams (
    stream_id   UUID PRIMARY KEY,
    creator_id  UUID NOT NULL,
    title       VARCHAR(255),
    status      VARCHAR(10) DEFAULT 'LIVE',  -- LIVE, ENDED
    created_at  TIMESTAMP DEFAULT NOW()
);

-- comment_reactions (Cassandra counter table)
CREATE TABLE comment_reactions (
    comment_id    BIGINT,
    reaction_type TEXT,          -- 'LIKE', 'HEART', etc.
    count         COUNTER,
    PRIMARY KEY (comment_id, reaction_type)
);
Why time_bucket? Without bucketing, a popular stream with 10K comments/min would put millions of rows in a single Cassandra partition — causing hot partition performance degradation. Bucketing by hour caps partition size.

🏗️ H — High-level Design 10 min

Figure: Live comments fan-out — 1 Kafka write triggers N parallel fan-out workers → M Redis publishes → M WebSocket servers each push to their local viewer connections

Component Overview

  • WebSocket Servers — maintain persistent connections with viewers; each server holds a subset of connections (shard by stream_id or random)
  • Comment Service — receives new comments via HTTP; publishes to Kafka; persists to Cassandra
  • Kafka — one topic per stream (or stream_id as partition key); buffers write spikes; enables replay
  • Fan-out Workers — Kafka consumers; each worker reads from a Kafka partition and publishes to Redis Pub/Sub
  • Redis Pub/Sub — lightweight message broker; WebSocket servers subscribe to channels for streams their clients are watching

Comment Post Flow

// 1. Viewer posts comment → HTTP POST to Comment Service
// 2. Comment Service:
//    a. Rate limit check (Redis token bucket: 1 comment / 3s per user_id)
//    b. Persist to Cassandra (async, don't block response)
//    c. Publish to Kafka topic: stream-comments-{stream_id}
//    d. Return 202 Accepted to poster
//
// 3. Fan-out Worker (Kafka consumer):
//    a. Read comment from Kafka
//    b. Publish to Redis Pub/Sub channel: live-comments-{stream_id}
//
// 4. WebSocket Server:
//    a. Subscribed to Redis channel for active stream_ids on this server
//    b. On Redis message: push JSON payload to all WebSocket connections watching that stream
//
// 5. Viewer receives comment via WebSocket push (target: <500ms total)

Viewer Connect Flow (Initial State + Live)

// On viewer connect:
// 1. REST: GET /v1/streams/{id}/comments?limit=50 → fetch last 50 from Cassandra
// 2. WebSocket: SUBSCRIBE stream/{id} → live comments pushed going forward
// 3. Use timestamp of last fetched comment as cursor to avoid gap between step 1 and 2

🔌 A — APIs 5 min 

// Post a comment (HTTP)
POST /v1/streams/{stream_id}/comments
// Body: { content: "LET'S GOOO" }
// Response: 202 Accepted { comment_id: "..." }

// Get recent comments (for initial load on connect)
GET /v1/streams/{stream_id}/comments?limit=50&before_comment_id=...
// Response: { comments: [...], has_more: true }

// WebSocket: bidirectional (viewers + moderators)
// Connect: ws://chat.example.com/streams/{stream_id}
// Outbound (server → viewer): { type: "NEW_COMMENT", comment: {...} }
// Outbound: { type: "DELETE_COMMENT", comment_id: "..." }
// Inbound: (not used for comments — client sends via REST)

// Moderator delete
DELETE /v1/streams/{stream_id}/comments/{comment_id}
// 200 OK → triggers DELETE_COMMENT event to all WebSocket connections

// React to comment
POST /v1/comments/{comment_id}/reactions
// Body: { reaction_type: "LIKE" }
// Response: 200 OK (fire-and-forget, eventually consistent counter)

🔬 D — Deep Dive: Scaling Fan-out to 1M Viewers 10 min

The Fan-out Problem at 1M Viewers

One comment → 1M push deliveries. No single server can do this serially — it would take seconds just to iterate the connections. The solution: parallel fan-out via partitioning.

Kafka → Redis Pub/Sub Fan-out Architecture

// Comment published to Kafka: 10 partitions for popular stream
//
// 10 Fan-out Workers (one per Kafka partition) each:
//   → Publish to Redis Pub/Sub: channel "live-{stream_id}"
//
// 100 WebSocket Servers, each holding 10K connections
//   → All 100 servers subscribed to Redis channel "live-{stream_id}"
//   → Each server pushes to its 10K connections in parallel
//
// Total: 1 Kafka write → 10 parallel workers → 100 Redis messages
//        → 100 WebSocket servers × 10K pushes each = 1M deliveries
//        All in parallel → sub-100ms fan-out time

Rate Limiting: Token Bucket per User

// Redis token bucket per user_id (1 token refills every 3 seconds):
// MULTI
//   GET rate:comment:{user_id}
//   SET rate:comment:{user_id} {tokens-1} EX 3
// EXEC
// If tokens == 0: return 429 Too Many Requests

WebSocket vs SSE Decision

For read-only viewers, Server-Sent Events (SSE) over HTTP/2 is simpler: browsers handle reconnection natively, no WebSocket upgrade needed, and SSE is unidirectional (server → client) which matches viewer use case. Reserve WebSocket for streamers/moderators who need bidirectional communication.

⚖️ E — Evaluate 3 min

  • Latency: Kafka p99 ~10ms + Redis Pub/Sub ~1ms + WebSocket push ~5ms = well under 500ms for most viewers. Geographic distribution (regional WebSocket servers) handles global latency.
  • Durability: Cassandra replication factor 3 ensures comment persistence. Kafka retention (7 days) allows replay for debugging or late-joining VOD consumers.
  • Scale: Each component scales independently — more Kafka partitions → more fan-out workers → more WebSocket servers. Linear scaling.
  • Moderation: Delete events published to the same Kafka topic → fan-out workers push DELETE_COMMENT to all WebSocket servers → comment removed from all active feeds in <500ms.

🚀 D — Deliver 2 min

  • Write path: Comment Service → Kafka (per-stream topic) → Fan-out Workers → Redis Pub/Sub → WebSocket Servers → Viewers. Async, durable, scalable.
  • Storage: Cassandra with (stream_id, time_bucket) partition key. Prevents hot partitions on popular streams. 30-day TTL for automatic cleanup.
  • Fan-out scaling: Add Kafka partitions + fan-out workers + WebSocket servers independently. 1M viewers = 100 WebSocket servers × 10K connections each.
  • Initial state on connect: Two-phase: REST fetch last 50 comments → WebSocket subscribe anchored at last fetched comment_id to prevent gaps.

⚡ Trade-offs

Decision Option A Option B Choose When
Push protocol WebSocket (bidirectional) SSE (server-sent events) WebSocket: moderators, streamers need to send. SSE: read-only viewers — simpler, browser auto-reconnect, works over HTTP/2 multiplexing.
Message broker Kafka (durable, ordered, replayable) Redis Pub/Sub (simple, low-latency) Kafka: replay capability needed (VOD, debugging, auditing). Redis: lowest latency, acceptable to lose messages on broker restart.
Kafka topic layout One topic per stream Single topic, stream_id as partition key One topic per stream: isolation (popular stream doesn't affect others). Single topic: simpler management, but topic creation overhead per stream start.
Comment storage Cassandra (write-optimized) MySQL/PostgreSQL (relational) Cassandra: multi-region writes, time-series queries, high write QPS. MySQL: simpler schema, complex queries, moderate scale (<1000 writes/s).

☕ Java Implementation 

import org.apache.kafka.clients.producer.KafkaProducer;
import org.apache.kafka.clients.producer.ProducerRecord;
import org.apache.kafka.clients.consumer.KafkaConsumer;
import redis.clients.jedis.Jedis;
import redis.clients.jedis.JedisPubSub;
import javax.websocket.Session;
import java.util.Map;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;

/**
 * LiveCommentService: three components working together.
 *
 * 1. CommentPublisher — accepts new comments, rate-limits, publishes to Kafka
 * 2. CommentFanoutWorker — Kafka consumer, publishes to Redis Pub/Sub
 * 3. WebSocketCommentServer — manages WebSocket connections, pushes to viewers
 */

// ── Component 1: Comment Publisher ────────────────────────────────

public class CommentPublisher {

    private static final String KAFKA_TOPIC_PREFIX = "stream-comments-";
    private static final int RATE_LIMIT_SECONDS = 3;        // 1 comment per 3s per user
    private static final String RATE_LIMIT_KEY_PREFIX = "rate:comment:";

    private final KafkaProducer<String, String> kafkaProducer;
    private final Jedis redisClient;
    private final CommentRepository commentRepository;

    public CommentPublisher(
            KafkaProducer<String, String> kafkaProducer,
            Jedis redisClient,
            CommentRepository commentRepository) {
        this.kafkaProducer = kafkaProducer;
        this.redisClient = redisClient;
        this.commentRepository = commentRepository;
    }

    /**
     * Publishes a new comment to the stream.
     * Returns the generated comment_id, or throws RateLimitException if user is rate-limited.
     */
    public String publishComment(String streamId, String userId, String content) {
        if (isRateLimited(userId)) {
            throw new RateLimitException("Post limit: 1 comment per " + RATE_LIMIT_SECONDS + "s");
        }

        long commentId = SnowflakeIdGenerator.nextId();  // globally unique, time-sortable
        String timeBucket = computeTimeBucket();

        Comment comment = new Comment(commentId, streamId, timeBucket, userId, content);

        // Persist to Cassandra (async — don't block the response)
        commentRepository.saveAsync(comment);

        // Publish to Kafka for fan-out
        String kafkaTopic = KAFKA_TOPIC_PREFIX + streamId;
        String commentJson = comment.toJson();
        kafkaProducer.send(new ProducerRecord<>(kafkaTopic, streamId, commentJson));

        return String.valueOf(commentId);
    }

    private boolean isRateLimited(String userId) {
        String rateLimitKey = RATE_LIMIT_KEY_PREFIX + userId;
        // SET NX (set if not exists) with TTL — atomic rate limit token
        String result = redisClient.set(rateLimitKey, "1", "NX", "EX", RATE_LIMIT_SECONDS);
        // If SET returned null, key already exists → rate limited
        return result == null;
    }

    private String computeTimeBucket() {
        // Hour bucket: "2024-01-15-14" — caps Cassandra partition at ~10K rows/hour
        return java.time.LocalDateTime.now()
            .format(java.time.format.DateTimeFormatter.ofPattern("yyyy-MM-dd-HH"));
    }
}

// ── Component 2: Fan-out Worker (Kafka Consumer) ──────────────────

public class CommentFanoutWorker implements Runnable {

    private static final String KAFKA_TOPIC_PREFIX = "stream-comments-";
    private static final String REDIS_CHANNEL_PREFIX = "live-comments-";

    private final KafkaConsumer<String, String> kafkaConsumer;
    private final Jedis redisPublisher;
    private final String assignedStreamId;

    public CommentFanoutWorker(
            KafkaConsumer<String, String> kafkaConsumer,
            Jedis redisPublisher,
            String assignedStreamId) {
        this.kafkaConsumer = kafkaConsumer;
        this.redisPublisher = redisPublisher;
        this.assignedStreamId = assignedStreamId;
    }

    @Override
    public void run() {
        String kafkaTopic = KAFKA_TOPIC_PREFIX + assignedStreamId;
        kafkaConsumer.subscribe(java.util.Collections.singletonList(kafkaTopic));

        while (true) {
            var records = kafkaConsumer.poll(java.time.Duration.ofMillis(100));
            for (var record : records) {
                String redisChannel = REDIS_CHANNEL_PREFIX + assignedStreamId;
                // Publish comment JSON to Redis — all subscribed WebSocket servers receive it
                redisPublisher.publish(redisChannel, record.value());
            }
            kafkaConsumer.commitSync();
        }
    }
}

// ── Component 3: WebSocket Server ─────────────────────────────────

public class WebSocketCommentServer {

    private static final String REDIS_CHANNEL_PREFIX = "live-comments-";

    // Map of streamId → set of WebSocket sessions watching that stream
    private final Map<String, Set<Session>> streamViewers = new ConcurrentHashMap<>();
    private final Jedis redisSubscriber;

    public WebSocketCommentServer(Jedis redisSubscriber) {
        this.redisSubscriber = redisSubscriber;
    }

    /** Called when a viewer connects and starts watching a stream. */
    public void onViewerJoin(String streamId, Session viewerSession) {
        streamViewers.computeIfAbsent(streamId, ignored -> ConcurrentHashMap.newKeySet())
                     .add(viewerSession);

        // Subscribe to Redis channel for this stream if not already subscribed
        subscribeToStreamIfNeeded(streamId);
    }

    /** Called when a viewer disconnects. */
    public void onViewerLeave(String streamId, Session viewerSession) {
        Set<Session> viewers = streamViewers.get(streamId);
        if (viewers != null) {
            viewers.remove(viewerSession);
        }
    }

    private void subscribeToStreamIfNeeded(String streamId) {
        String redisChannel = REDIS_CHANNEL_PREFIX + streamId;
        // Subscribe in a background thread — JedisPubSub.subscribe() is blocking
        Thread.ofVirtual().start(() ->
            redisSubscriber.subscribe(new JedisPubSub() {
                @Override
                public void onMessage(String channel, String commentJson) {
                    pushToAllViewers(streamId, commentJson);
                }
            }, redisChannel)
        );
    }

    /** Pushes a comment to all WebSocket sessions watching the given stream. */
    private void pushToAllViewers(String streamId, String commentJson) {
        Set<Session> viewers = streamViewers.getOrDefault(streamId, java.util.Collections.emptySet());
        for (Session viewerSession : viewers) {
            if (viewerSession.isOpen()) {
                viewerSession.getAsyncRemote().sendText(commentJson);
            }
        }
    }
}
