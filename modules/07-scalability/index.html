Module 07

Scalability Patterns

How to distribute data and traffic across nodes predictably: consistent hashing, intelligent load balancing, feed fanout architecture, and the horizontal vs vertical scaling decision.

⏱️ 35 min read

Consistent Hashing with Virtual Nodes

Naive modular hashing (key % N) requires remapping nearly every key when nodes are added or removed. Consistent hashing maps both keys and nodes to positions on a hash ring (a circular space of 232 values). A key is assigned to the first node clockwise from its hash position.

When a node is added, only the keys between the new node and its predecessor need to be remapped—approximately K/N keys where K is total keys and N is the new node count. Removal is symmetric.

Virtual Nodes (vnodes)

Physical nodes may be unevenly distributed on the ring, causing hotspots. Virtual nodes solve this: each physical node is placed at multiple positions on the ring using different hash inputs (e.g., hash("node1#0"), hash("node1#1"), …, hash("node1#150")). Benefits:

  • Even distribution: With 150 vnodes per physical node, the load is statistically balanced across all nodes.
  • Heterogeneous capacity: Assign more vnodes to more powerful servers.
  • Graceful adds/removes: When a node is added, it takes a fraction of load from many existing nodes rather than all load from one neighbor.

Layer 4 vs Layer 7 LB: Layer 4 load balancers operate at the TCP level (fast, no content inspection). Layer 7 load balancers inspect HTTP headers and can route by path (/api vs /static), enable SSL termination, and inject headers — at the cost of slightly higher latency.

Push vs Pull vs Hybrid Fanout

In social networks and activity feeds, fanout is the process of distributing a new post to followers' feeds.

Push (Fanout on Write)

When a user posts, immediately write to every follower's feed inbox. Read is O(1) — just read the inbox. Write is O(followers). For celebrities with 10M followers, a single tweet triggers 10M writes, causing write amplification.

Pull (Fanout on Read)

Do nothing on write. When a user opens their feed, query all followed accounts' recent posts and merge. Read is O(followed_count × query_cost). Write is O(1). Scales poorly for users following thousands of accounts — each feed load is expensive.

Hybrid Fanout

Most production systems (Twitter, Instagram) use a hybrid: push fanout for normal users (followers < threshold, e.g., 1M), pull for celebrity accounts. On feed load, merge the pre-built inbox (from pushed posts) with freshly pulled posts from celebrity accounts the user follows. This caps both write amplification and read-time cost.

Horizontal vs Vertical Scaling Decision Framework

Vertical scaling (scale up): Add more CPU, RAM, or faster disk to existing machines. Simple — no code changes. Limited by maximum machine size and creates a single point of failure. Cost scales super-linearly (doubling resources often costs 4× the price).

Horizontal scaling (scale out): Add more machines and distribute load. Requires services to be stateless (or externalize state to Redis/DB). Enables near-linear cost scaling and eliminates SPOF via redundancy.

Decision heuristic:

  1. If the bottleneck is a single database write path → vertical scale first (faster disk, more RAM for buffer pool), then shard.
  2. If the bottleneck is stateless compute (web servers, API handlers) → horizontal scale immediately.
  3. If you need >99.9% availability → horizontal scaling is mandatory (vertical = SPOF).
  4. If the service holds session state in memory → add sticky sessions or externalize state before horizontal scaling.

Database Read Replicas

Most applications have a read-heavy ratio (typically 80–95% reads). Read replicas receive a continuous replication stream from the primary and serve read queries, offloading the primary for writes.

Replication lag is the key tradeoff: replicas are eventually consistent with the primary. For read-your-own-writes consistency, route the user's reads immediately after a write to the primary for a short window, or use synchronous replication (at the cost of write latency).

Common patterns:

  • Route all writes + consistency-sensitive reads to primary.
  • Route analytics queries, reporting, and search to replicas.
  • Use a read replica in a different availability zone as a hot standby.
  • Monitor Seconds_Behind_Master (MySQL) or replication_delay (Postgres) — alert if lag exceeds acceptable threshold.

Java Implementation: Consistent Hash Ring

/**
 * Consistent hash ring with virtual nodes.
 * Thread-safe for concurrent reads; uses write lock for topology changes.
 */
public class ConsistentHashRing {

    private static final int DEFAULT_VIRTUAL_NODES_PER_PHYSICAL = 150;

    private final int virtualNodesPerPhysical;
    // Sorted map: ring position → physical node name
    private final TreeMap<Long, String> ring = new TreeMap<>();
    private final ReadWriteLock ringLock = new ReentrantReadWriteLock();

    public ConsistentHashRing() {
        this(DEFAULT_VIRTUAL_NODES_PER_PHYSICAL);
    }

    public ConsistentHashRing(int virtualNodesPerPhysical) {
        this.virtualNodesPerPhysical = virtualNodesPerPhysical;
    }

    /**
     * Adds a physical node to the ring by creating virtualNodesPerPhysical
     * virtual node entries at positions hash("nodeName#0") … hash("nodeName#N-1").
     */
    public void addNode(String nodeName) {
        ringLock.writeLock().lock();
        try {
            for (int virtualIndex = 0; virtualIndex < virtualNodesPerPhysical; virtualIndex++) {
                long ringPosition = computeHash(nodeName + "#" + virtualIndex);
                ring.put(ringPosition, nodeName);
            }
        } finally {
            ringLock.writeLock().unlock();
        }
    }

    /**
     * Removes a physical node and all its virtual node positions from the ring.
     */
    public void removeNode(String nodeName) {
        ringLock.writeLock().lock();
        try {
            for (int virtualIndex = 0; virtualIndex < virtualNodesPerPhysical; virtualIndex++) {
                long ringPosition = computeHash(nodeName + "#" + virtualIndex);
                ring.remove(ringPosition);
            }
        } finally {
            ringLock.writeLock().unlock();
        }
    }

    /**
     * Returns the physical node responsible for the given key.
     * Finds the first ring position >= hash(key), wrapping around to
     * the lowest position if none exists (ring is circular).
     *
     * @param key - the data key to look up
     * @return the responsible node name, or null if the ring is empty
     */
    public String getNodeForKey(String key) {
        if (key == null || key.isEmpty()) {
            throw new IllegalArgumentException("Key must not be null or empty");
        }
        ringLock.readLock().lock();
        try {
            if (ring.isEmpty()) {
                return null;
            }
            long keyPosition = computeHash(key);
            // Find the first entry clockwise from keyPosition
            Map.Entry<Long, String> clockwiseEntry = ring.ceilingEntry(keyPosition);
            if (clockwiseEntry == null) {
                // Wrap around: key is beyond the last node, so use the first node
                clockwiseEntry = ring.firstEntry();
            }
            return clockwiseEntry.getValue();
        } finally {
            ringLock.readLock().unlock();
        }
    }

    /**
     * Returns an ordered list of N distinct physical nodes starting from
     * the position responsible for the given key. Used for replication.
     */
    public List<String> getReplicaNodesForKey(String key, int replicaCount) {
        ringLock.readLock().lock();
        try {
            Set<String> uniquePhysicalNodes = new LinkedHashSet<>();
            long keyPosition = computeHash(key);
            // Walk the ring clockwise, collecting distinct physical nodes
            NavigableMap<Long, String> tailMap = ring.tailMap(keyPosition, true);
            for (String nodeName : tailMap.values()) {
                uniquePhysicalNodes.add(nodeName);
                if (uniquePhysicalNodes.size() == replicaCount) {
                    return new ArrayList<>(uniquePhysicalNodes);
                }
            }
            // Wrap around from start of ring
            for (String nodeName : ring.values()) {
                uniquePhysicalNodes.add(nodeName);
                if (uniquePhysicalNodes.size() == replicaCount) {
                    break;
                }
            }
            return new ArrayList<>(uniquePhysicalNodes);
        } finally {
            ringLock.readLock().unlock();
        }
    }

    /**
     * MurmurHash-inspired 64-bit hash. Using a consistent non-cryptographic
     * hash ensures uniform distribution without the overhead of MD5/SHA.
     */
    private long computeHash(String input) {
        try {
            MessageDigest digest = MessageDigest.getInstance("MD5");
            byte[] hashBytes = digest.digest(input.getBytes(StandardCharsets.UTF_8));
            // Take first 8 bytes as a long for a 64-bit position
            long position = 0L;
            for (int byteIndex = 0; byteIndex < 8; byteIndex++) {
                position |= ((long) (hashBytes[byteIndex] & 0xFF)) << (byteIndex * 8);
            }
            return position;
        } catch (NoSuchAlgorithmException algorithmException) {
            // MD5 is always available in the JVM; this branch is unreachable
            throw new IllegalStateException("MD5 unavailable", algorithmException);
        }
    }
}

Why TreeMap? TreeMap maintains sorted order, enabling O(log N) ceilingEntry and firstEntry lookups. A plain HashMap cannot support the clockwise-walk operation efficiently.
