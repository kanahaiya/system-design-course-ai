Module 09

Security & Auth Patterns

Design secure systems with OAuth 2.0, validate JWTs correctly, enforce mTLS between microservices, and apply zero-trust principles — all with production-grade implementation details.

⏱️ 35 min read

OAuth 2.0 Authorization Code Flow

OAuth 2.0 delegates authorization: it lets a user grant an application access to their resources on another service without sharing credentials. The Authorization Code Flow is the most secure variant for server-side applications:

  1. User initiates login: The client redirects the user to the Authorization Server with response_type=code, client_id, redirect_uri, scope, and a state parameter (CSRF protection).
  2. User authenticates: The Authorization Server authenticates the user (login form, MFA) and asks for consent.
  3. Authorization code returned: Authorization Server redirects to redirect_uri?code=AUTH_CODE&state=STATE. The code is short-lived (60 seconds) and single-use.
  4. Code exchange: The client's backend sends a POST to the token endpoint with code, client_id, client_secret, redirect_uri. This happens server-to-server — the client secret never goes to the browser.
  5. Tokens issued: Authorization Server responds with an access_token, refresh_token, and id_token (if OpenID Connect).
  6. API access: Client sends Authorization: Bearer access_token to the Resource Server.

PKCE (Proof Key for Code Exchange): For public clients (mobile apps, SPAs) that cannot hold a client_secret, PKCE adds a code_challenge/code_verifier pair. The client generates a random verifier, hashes it to a challenge, sends the challenge in step 1, and proves ownership of the verifier in step 5.

JWT Structure and Validation

A JWT is three Base64URL-encoded JSON objects joined by dots: header.payload.signature.

  • Header: {"alg":"RS256","typ":"JWT"} — algorithm and token type.
  • Payload: Claims — sub (subject), iss (issuer), aud (audience), exp (expiry Unix timestamp), iat (issued at), plus custom claims.
  • Signature: For RS256: RSA_Sign(SHA256(base64(header) + "." + base64(payload)), private_key). The receiver verifies with the public key.

Critical validation steps (all must pass):

  1. Verify the signature using the issuer's public key (fetched from /.well-known/jwks.json).
  2. Check exp is in the future (using server time, not client).
  3. Check iss matches the expected issuer.
  4. Check aud contains your service's identifier (prevents token reuse from another service).
  5. Reject alg: none — never accept unsigned tokens.

mTLS for Service-to-Service Authentication

Standard TLS authenticates only the server (client trusts the server's certificate). Mutual TLS (mTLS) requires both parties to present and verify certificates — the server also validates the client's certificate. This is the foundation of zero-trust service mesh authentication.

How it works:

  1. Each service has a certificate issued by an internal Certificate Authority (CA), typically with the SPIFFE SVID standard for identity (spiffe://cluster/ns/default/sa/order-service).
  2. On connection, both sides exchange and verify certificates against the trusted internal CA.
  3. If validation fails (untrusted CA, expired cert, wrong SPIFFE ID), the TLS handshake fails and no data is transmitted.

In practice: Service meshes like Istio and Linkerd automate certificate rotation and mTLS enforcement via sidecar proxies — application code doesn't need to implement it directly. The mesh intercepts all traffic at the pod level.

Encryption: At Rest vs In Transit

Encryption in transit protects data as it moves over the network: TLS 1.2+ for external traffic, mTLS for internal service calls. Prevents eavesdropping and man-in-the-middle attacks. Once data reaches the server and is decrypted, transit encryption provides no protection.

Encryption at rest protects data stored on disk: AES-256 for object storage, database tablespace encryption, or application-level field encryption. Protects against physical disk theft, cloud provider data exposure, and unauthorized storage access.

Key management is the hard part of encryption at rest. Use a dedicated KMS (AWS KMS, HashiCorp Vault, GCP Cloud KMS) — never store encryption keys in the same location as encrypted data. Implement envelope encryption: a data encryption key (DEK) encrypts the data, and a key encryption key (KEK) encrypts the DEK. Rotate DEKs without re-encrypting all data.

GDPR data flow requirements: Personal data must not leave the EU without adequate safeguards. For multi-region architectures: use data residency controls (store EU user data only in eu-west regions), implement data minimisation (don't log PII), enforce right-to-erasure by tracking all locations where a user's data is stored, and document cross-border data transfers in your Data Processing Agreement.

Zero-Trust Architecture

Traditional perimeter security assumes anything inside the corporate network is trusted. Zero-trust assumes breach: never trust, always verify. Every request — whether from outside or inside the network — must be authenticated and authorized.

Core principles:

  • Verify explicitly: Authenticate every request using strong identity (certificates, short-lived tokens). No implicit trust from network location.
  • Least privilege: Each service has access only to the resources it needs. Scoped tokens, fine-grained RBAC/ABAC policies.
  • Assume breach: Log everything, detect lateral movement, segment workloads so a compromised service cannot access everything.

Implementation: Service mesh (Istio) enforces mTLS between all services. An identity-aware proxy (Google IAP, HashiCorp Boundary) sits in front of internal tools. Short-lived credentials (AWS STS, Vault dynamic secrets) ensure compromised credentials expire quickly.

Java Implementation: JWT Validation Filter

/**
 * JWT validation filter for Spring-style servlet filter chain.
 * Validates RS256 JWTs: signature, expiry, issuer, and audience.
 * Fetches the public key from the JWKS endpoint and caches it.
 */
public class JwtValidationFilter implements Filter {

    private static final String AUTHORIZATION_HEADER = "Authorization";
    private static final String BEARER_PREFIX = "Bearer ";
    private static final String EXPECTED_ISSUER = "https://auth.example.com";
    private static final String EXPECTED_AUDIENCE = "api.example.com";

    private final JwksKeyProvider jwksKeyProvider;

    public JwtValidationFilter(JwksKeyProvider jwksKeyProvider) {
        this.jwksKeyProvider = jwksKeyProvider;
    }

    @Override
    public void doFilter(ServletRequest request,
                          ServletResponse response,
                          FilterChain chain) throws IOException, ServletException {
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        HttpServletResponse httpResponse = (HttpServletResponse) response;

        String authorizationHeader = httpRequest.getHeader(AUTHORIZATION_HEADER);
        if (authorizationHeader == null || !authorizationHeader.startsWith(BEARER_PREFIX)) {
            httpResponse.sendError(HttpServletResponse.SC_UNAUTHORIZED,
                "Missing or malformed Authorization header");
            return;
        }

        String rawJwtToken = authorizationHeader.substring(BEARER_PREFIX.length()).trim();
        JwtValidationResult validationResult = validateJwt(rawJwtToken);

        if (!validationResult.isValid()) {
            // Log the internal reason; return a generic message to the client
            System.err.println("[JwtFilter] Rejected: " + validationResult.getRejectionReason());
            httpResponse.sendError(HttpServletResponse.SC_UNAUTHORIZED, "Invalid token");
            return;
        }

        // Attach verified claims to request for downstream handlers
        httpRequest.setAttribute("jwt.claims", validationResult.getClaims());
        chain.doFilter(request, response);
    }

    /**
     * Validates the JWT in five mandatory steps.
     * Returns a result with the parsed claims on success, or a rejection reason on failure.
     */
    private JwtValidationResult validateJwt(String rawJwtToken) {
        try {
            // Step 1: Parse header to get key ID (kid) for JWKS lookup
            String[] jwtParts = rawJwtToken.split("\\.");
            if (jwtParts.length != 3) {
                return JwtValidationResult.rejected("Malformed JWT structure");
            }

            JwtHeader header = parseHeader(jwtParts[0]);

            // Step 2: Reject unsigned tokens — never accept alg:none
            if ("none".equalsIgnoreCase(header.getAlgorithm())) {
                return JwtValidationResult.rejected("alg:none is not permitted");
            }

            // Step 3: Verify signature using public key from JWKS
            RSAPublicKey publicKey = jwksKeyProvider.getPublicKey(header.getKeyId());
            if (!verifySignature(jwtParts[0], jwtParts[1], jwtParts[2], publicKey)) {
                return JwtValidationResult.rejected("Signature verification failed");
            }

            // Step 4: Parse and validate claims
            JwtClaims claims = parseClaims(jwtParts[1]);

            // Step 5a: Check expiry
            long nowSeconds = Instant.now().getEpochSecond();
            if (claims.getExpiry() <= nowSeconds) {
                return JwtValidationResult.rejected("Token expired at " + claims.getExpiry());
            }

            // Step 5b: Verify issuer
            if (!EXPECTED_ISSUER.equals(claims.getIssuer())) {
                return JwtValidationResult.rejected("Unexpected issuer: " + claims.getIssuer());
            }

            // Step 5c: Verify audience — prevents token relay attacks
            if (!claims.getAudience().contains(EXPECTED_AUDIENCE)) {
                return JwtValidationResult.rejected("Token not intended for this service");
            }

            return JwtValidationResult.valid(claims);

        } catch (Exception parseException) {
            System.err.println("[JwtFilter] Parse error: " + parseException.getMessage());
            return JwtValidationResult.rejected("Token parse failure");
        }
    }

    private boolean verifySignature(String encodedHeader,
                                     String encodedPayload,
                                     String encodedSignature,
                                     RSAPublicKey publicKey) throws Exception {
        Signature rsaSignature = Signature.getInstance("SHA256withRSA");
        rsaSignature.initVerify(publicKey);
        rsaSignature.update((encodedHeader + "." + encodedPayload)
            .getBytes(StandardCharsets.UTF_8));
        byte[] decodedSignatureBytes = Base64.getUrlDecoder().decode(encodedSignature);
        return rsaSignature.verify(decodedSignatureBytes);
    }

    // Parsing helpers (header/claims decode from Base64 and JSON) omitted for brevity
    private JwtHeader parseHeader(String encodedHeader) { /* JSON decode */ return null; }
    private JwtClaims parseClaims(String encodedPayload) { /* JSON decode */ return null; }
}

Why validate audience? Without audience validation, a JWT issued for Service A can be replayed against Service B. An attacker who steals a token from one service can impersonate the user on any other service in your ecosystem that trusts the same issuer.
