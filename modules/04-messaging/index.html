Messaging & Event Streaming

Asynchronous messaging decouples services and absorbs traffic spikes. Kafka handles 10 million events per second at LinkedIn. Understand its internals deeply enough to explain partitioning, consumer groups, and exactly-once semantics on a whiteboard.

🏗️ Kafka Architecture Deep Dive

Brokers and Topics

A Kafka cluster consists of multiple brokers (servers). Each broker holds a subset of partitions. A topic is a logical stream of records divided into one or more partitions. Partitions are the unit of parallelism — more partitions enable more parallel consumers. Each partition is an ordered, immutable log of records.

Partitions and Ordering

Kafka guarantees ordering within a partition — not across partitions. To ensure order for a specific entity (e.g., all events for order-123 are ordered), use the entity ID as the partition key: producer.send(topic, orderId, event). The same key always maps to the same partition (via hash), guaranteeing per-key ordering.

Consumer Groups

Each consumer in a group is assigned exclusive ownership of one or more partitions. Within a group, each partition is consumed by exactly one consumer (no duplication). Multiple consumer groups can read the same topic independently — each maintains its own offsets. This enables fan-out: Order events processed by both the Inventory service group and the Analytics service group independently.

Offsets and Retention

Kafka is a distributed log, not a traditional queue. Records are retained for a configurable period (default: 7 days), regardless of whether they've been consumed. Consumers can replay from any offset. This enables event sourcing and audit trails natively.

📬 Delivery Guarantees

At-Most-Once

Producer fires and forgets (acks=0). Consumer commits offset before processing. Messages may be lost. Acceptable for metrics/analytics where occasional loss is tolerable. Never use for financial transactions.

At-Least-Once (Default)

Producer retries on failure (acks=all, retries=MAX_INT). Consumer commits offset after successful processing. On crash between processing and commit, the record is redelivered → possible duplicates. Application must be idempotent: processing the same message twice produces the same result. Idempotency strategies: database upserts keyed by message ID, idempotency keys in APIs, deduplication tables with TTL.

Exactly-Once (Kafka 0.11+)

Kafka's idempotent producer assigns a sequence number to each message per partition. The broker deduplicates retransmissions. Combined with Kafka transactions (atomic read-process-write), this achieves exactly-once semantics within the Kafka ecosystem.

Configuration: enable.idempotence=true (idempotent producer) + transactional.id (named transactions) + consumer isolation.level=read_committed (only read committed transaction data).

Important caveat: Exactly-once within Kafka-to-Kafka pipelines. Kafka → external system (database, API) still requires application-level idempotency.

📡 Pub-Sub vs Point-to-Point Queues

Point-to-Point (Traditional Queue: SQS, RabbitMQ)

A message is consumed by exactly one consumer. Once consumed, it is deleted from the queue. Best for task distribution: send an email, process an image, charge a card. Competing consumers naturally distribute load without coordination. SQS Standard: at-least-once, unordered. SQS FIFO: exactly-once, ordered, lower throughput (3,000 msg/s with batching).

Publish-Subscribe (Kafka, SNS, Google Pub/Sub)

A message is broadcast to all subscribers independently. Each subscriber (consumer group in Kafka) processes every message. Best for event-driven architecture: "Order placed" event consumed by Inventory, Email, Analytics, and Recommendation services simultaneously. No coupling between publisher and subscribers.

When to Use Which

  • Use a queue (SQS) when you want exactly one service to process each task. Email sending, payment processing, image resizing.
  • Use pub-sub (Kafka) when multiple independent services need the same event. Event sourcing, audit logs, real-time analytics.
  • Use Kafka over SQS when you need: message retention >14 days, replay capability, >100K messages/sec, strict per-key ordering, or stream processing (Kafka Streams, Flink).

☠️ Dead-Letter Queues (DLQ)

A DLQ stores messages that failed processing after N retry attempts. Without a DLQ, a poison-pill message (e.g., malformed JSON) blocks the consumer forever. With a DLQ, the message is sidelined after max retries, the queue continues processing, and engineers can inspect and replay DLQ messages after fixing the bug.

DLQ Pattern

  1. Consumer processes message → throws exception
  2. Queue retries with exponential backoff (1s, 2s, 4s, 8s...)
  3. After maxReceiveCount (e.g., 5), message is moved to DLQ
  4. Alerting fires on DLQ depth > threshold
  5. Engineer fixes root cause, replays DLQ to original queue

SQS DLQ setup: Create a separate SQS queue and configure the source queue's RedrivePolicy with deadLetterTargetArn and maxReceiveCount.

Kafka equivalent: No native DLQ, but the pattern is implemented by catching exceptions in the consumer, writing the failed message to a topic-name.DLT (dead-letter topic) with error metadata headers, and committing the original offset to unblock the partition.

🌊 Backpressure

Backpressure is a mechanism for a slow consumer to signal a fast producer to slow down, preventing memory exhaustion and cascade failures. Without backpressure, a slow downstream service causes the upstream queue to grow unboundedly until OOM.

Kafka Backpressure

Kafka provides natural backpressure: the consumer controls its read rate via max.poll.records and polling frequency. If consumers fall behind, the lag (topic partition offset lag) grows — this is the key metric to monitor (consumer-lag in CloudWatch / Prometheus kafka_consumer_group_lag). Alert when lag exceeds a threshold (e.g., 10,000 messages × avg processing time > SLA).

Reactive Streams Backpressure

Reactive Streams (Project Reactor, RxJava) formalize backpressure with the Subscription.request(n) contract: a subscriber signals exactly how many items it can handle. The producer respects this bound. Overflow strategies: BUFFER (queue items), DROP (discard excess), LATEST (keep only newest), ERROR (fail fast).

Application-Level Backpressure

Semaphore-based: limit concurrent in-flight requests. When the semaphore is exhausted, new requests either queue (bounded), drop (shed load), or return a 503 (immediate feedback to caller). Circuit breakers (Resilience4j, Hystrix) provide a higher-level backpressure mechanism: when failure rate exceeds threshold, open the circuit and fail fast rather than queueing.

☕ Java Implementation: Kafka Producer/Consumer with Idempotency 

import org.apache.kafka.clients.producer.*;
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.common.serialization.*;
import java.time.Duration;
import java.util.*;
import java.util.concurrent.*;
import java.util.logging.Logger;

/**
 * Demonstrates idempotent Kafka producer and at-least-once consumer
 * with application-level deduplication for true exactly-once processing
 * when writing to an external system (like a database).
 *
 * Producer: idempotent (enable.idempotence=true) + acks=all + retries
 * Consumer: manual offset commit after successful processing + deduplication
 */
public class IdempotentKafkaPatterns {

    private static final Logger LOG = Logger.getLogger(IdempotentKafkaPatterns.class.getName());
    private static final String ORDERS_TOPIC = "orders";
    private static final String BOOTSTRAP_SERVERS = "localhost:9092";
    private static final int DEDUP_CACHE_SIZE_MAX = 10_000;

    // --- PRODUCER ---

    /**
     * Creates an idempotent Kafka producer.
     * enable.idempotence=true automatically sets:
     *   acks=all, retries=MAX_INT, max.in.flight.requests.per.connection=5
     * This guarantees each message is written exactly once to a partition,
     * even if the producer retries due to transient network failures.
     */
    public static Producer<String, String> createIdempotentProducer() {
        Properties producerProperties = new Properties();
        producerProperties.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, BOOTSTRAP_SERVERS);
        producerProperties.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
        producerProperties.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());

        // Idempotence: broker assigns a sequence number per (producer, partition).
        // Duplicate retransmissions are detected and discarded at the broker level.
        producerProperties.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

        // Compression reduces network and disk I/O (~4-8x for JSON payloads)
        producerProperties.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4");

        // Batching: wait up to 5ms to accumulate records into a batch
        producerProperties.put(ProducerConfig.LINGER_MS_CONFIG, 5);
        producerProperties.put(ProducerConfig.BATCH_SIZE_CONFIG, 64 * 1024); // 64 KB batches

        return new KafkaProducer<>(producerProperties);
    }

    /**
     * Sends an order event with the orderId as the partition key.
     * Using orderId as key guarantees all events for the same order
     * land on the same partition → strict ordering per order.
     *
     * @param producer    the Kafka producer
     * @param orderId     the order identifier (used as partition key)
     * @param orderPayload JSON-serialized order event
     */
    public static void sendOrderEvent(Producer<String, String> producer,
                                      String orderId,
                                      String orderPayload) {
        ProducerRecord<String, String> kafkaRecord =
            new ProducerRecord<>(ORDERS_TOPIC, orderId, orderPayload);

        producer.send(kafkaRecord, (metadata, sendException) -> {
            if (sendException != null) {
                LOG.severe("[Producer] Failed to send order " + orderId
                    + ": " + sendException.getMessage());
                // In production: push to a local retry queue or DLQ
            } else {
                LOG.info("[Producer] Order " + orderId
                    + " sent to " + metadata.topic()
                    + " partition=" + metadata.partition()
                    + " offset=" + metadata.offset());
            }
        });
    }

    // --- CONSUMER ---

    /**
     * Creates a Kafka consumer configured for at-least-once delivery.
     * enable.auto.commit=false is critical: we commit offsets manually
     * only after successful processing, ensuring we never skip a message.
     */
    public static Consumer<String, String> createAtLeastOnceConsumer(String consumerGroupId) {
        Properties consumerProperties = new Properties();
        consumerProperties.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, BOOTSTRAP_SERVERS);
        consumerProperties.put(ConsumerConfig.GROUP_ID_CONFIG, consumerGroupId);
        consumerProperties.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        consumerProperties.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());

        // Manual commit: never auto-commit — we control when offset advances
        consumerProperties.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);

        // How many records to fetch per poll() call
        consumerProperties.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 100);

        // Backpressure: if processing takes > 5 min, consumer is considered dead
        // and partitions are reassigned. Set slightly above max processing batch time.
        consumerProperties.put(ConsumerConfig.MAX_POLL_INTERVAL_MS_CONFIG, 300_000);

        return new KafkaConsumer<>(consumerProperties);
    }

    /**
     * Order processor with application-level deduplication.
     * Even though the producer is idempotent (no broker-side duplicates),
     * consumer-side at-least-once delivery means the SAME message can be
     * redelivered if the consumer crashes between processing and committing.
     * Solution: maintain a processed-IDs set (backed by a DB in production).
     */
    public static class IdempotentOrderProcessor {

        // In production: use Redis SETNX or DB unique constraint on messageId
        private final Set<String> processedMessageIds =
            Collections.newSetFromMap(new LinkedHashMap<String, Boolean>() {
                @Override
                protected boolean removeEldestEntry(Map.Entry<String, Boolean> eldest) {
                    return size() > DEDUP_CACHE_SIZE_MAX;
                }
            });

        /**
         * Processes an order event exactly once.
         * Duplicate messages (same messageId) are detected and skipped.
         *
         * @param messageId    unique ID embedded in the message (e.g., UUID in payload)
         * @param orderPayload the raw message payload
         * @return true if processed, false if duplicate
         */
        public boolean processOrder(String messageId, String orderPayload) {
            if (processedMessageIds.contains(messageId)) {
                LOG.warning("[Consumer] Duplicate detected, skipping: " + messageId);
                return false;
            }
            // Simulate processing: update inventory, send email, etc.
            LOG.info("[Consumer] Processing order: " + messageId);
            // In production: wrap this AND the dedup set update in a DB transaction
            processedMessageIds.add(messageId);
            return true;
        }
    }

    /**
     * Main consume loop: poll → process → commit.
     * Offset committed only after successful processing of the entire batch.
     */
    public static void runConsumerLoop(Consumer<String, String> consumer,
                                       IdempotentOrderProcessor processor) {
        consumer.subscribe(List.of(ORDERS_TOPIC));
        try {
            while (!Thread.currentThread().isInterrupted()) {
                ConsumerRecords<String, String> consumerRecords =
                    consumer.poll(Duration.ofMillis(500));

                for (ConsumerRecord<String, String> kafkaRecord : consumerRecords) {
                    // Message ID from headers or payload — not the Kafka offset
                    String messageId = "order-" + kafkaRecord.partition() + "-" + kafkaRecord.offset();
                    try {
                        processor.processOrder(messageId, kafkaRecord.value());
                    } catch (RuntimeException processingException) {
                        LOG.severe("[Consumer] Processing failed for " + messageId
                            + ": " + processingException.getMessage());
                        // In production: send to DLQ topic after max retries
                        // Do NOT commit offset — Kafka will redeliver
                        return;
                    }
                }
                // Commit after all records in batch are processed successfully
                consumer.commitSync();
            }
        } finally {
            consumer.close();
        }
    }
}
