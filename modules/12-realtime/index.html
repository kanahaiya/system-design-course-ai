Module 12

Real-time Communication

HTTP is request-response — the server cannot push without being asked. This module covers the four real-time techniques interviewers expect you to compare: Short Polling, Long Polling, Server-Sent Events, and WebSocket — with Java implementations and the Redis Pub/Sub scaling pattern.

⏱️ 35 min read

Why Real-time Communication Is a System Design Staple

Standard HTTP is pull-based: the client asks, the server answers, the connection closes. This works for loading a webpage or fetching a user profile. It breaks down the moment the server needs to push data to the client without being explicitly asked.

Use Cases That Require Server Push
Use CaseWhat makes it real-timeBest technique
Live chat (WhatsApp, Slack)Messages arrive without the recipient clicking refreshWebSocket
Live sports scoresScores update every 30s, 1M simultaneous viewersSSE
Collaborative editing (Google Docs)Both sides send and receive keystrokes in real timeWebSocket
Notification bellServer pushes badge count on events like new messagesSSE or Long Polling
Stock price tickerPrice changes pushed every second to subscribed clientsSSE or WebSocket
Multiplayer game stateEach player's moves must appear on all others' screens instantlyWebSocket

Option 1: Short Polling

The client sends an HTTP request on a fixed timer (every N seconds). The server responds immediately with whatever is available — even if that is an empty "no updates" response.

Short Polling Trade-offs
ProsCons
Trivially simple — any HTTP client worksLatency up to N seconds before client sees an update
Stateless — any server handles any requestConstant request load even when no updates exist
Works through all proxies and firewallsWasted bandwidth on empty responses

When to use: Updates that happen less often than every 30 seconds (e.g., "check for new email every minute"). The simplicity justifies the inefficiency at low update frequency.

// ── Short Polling — Spring REST endpoint ─────────────────────────
@RestController
@RequestMapping("/api/v1")
public class ShortPollingController {

    private final UpdateStore updateStore; // injected — holds pending updates

    public ShortPollingController(UpdateStore updateStore) {
        this.updateStore = updateStore;
    }

    /**
     * Client calls this every N seconds.
     * Returns immediately with whatever updates are available (possibly empty).
     */
    @GetMapping("/updates")
    public ResponseEntity<List<UpdateEvent>> getUpdates(
            @RequestParam String userId,
            @RequestParam long sinceTimestamp) {
        List<UpdateEvent> updates = updateStore.getUpdatesSince(userId, sinceTimestamp);
        return ResponseEntity.ok(updates); // empty list = no updates, client retries
    }
}

Option 2: Long Polling (Comet)

The client sends an HTTP request, but the server holds the connection open — blocking until either an update is available or a timeout (typically 30 seconds) expires. On response (or timeout), the client immediately re-issues the request.

The critical insight: Long polling simulates server push using HTTP. The server holds the thread (or async context) open instead of responding immediately. This works through firewalls because it looks like a slow HTTP response, not a persistent connection.
Long Polling Trade-offs
ProsCons
Near-real-time: client gets update within one RTT of it being availableServer holds threads/async contexts — resource intensive at scale
Works through most firewalls and proxiesReconnect latency after each response (one RTT gap)
Compatible with HTTP/1.1 — no protocol upgrade requiredComplex reconnection and timeout handling logic on the client
Good fallback when WebSocket is blocked by corporate proxiesEach request still carries full HTTP headers (overhead)
 
// ── Long Polling — Spring async endpoint ─────────────────────────
@RestController
@RequestMapping("/api/v1")
public class LongPollingController {

    private static final long TIMEOUT_MS = 30_000; // 30-second server timeout

    private final UpdateStore updateStore;

    public LongPollingController(UpdateStore updateStore) {
        this.updateStore = updateStore;
    }

    /**
     * Server holds the request open until an update is available or TIMEOUT_MS passes.
     * Uses DeferredResult so the Tomcat thread is NOT blocked — this scales to
     * thousands of concurrent connections without exhausting the thread pool.
     *
     * Why DeferredResult over CompletableFuture? DeferredResult integrates directly
     * with Spring MVC's async processing and handles timeout natively.
     */
    @GetMapping("/updates/long-poll")
    public DeferredResult<ResponseEntity<UpdateEvent>> longPoll(
            @RequestParam String userId,
            @RequestParam long sinceTimestamp) {

        DeferredResult<ResponseEntity<UpdateEvent>> deferredResult =
            new DeferredResult<>(TIMEOUT_MS);

        // On timeout: return 204 No Content — client immediately re-polls
        deferredResult.onTimeout(() ->
            deferredResult.setResult(ResponseEntity.noContent().build()));

        // Register the deferred result — update store notifies it when data arrives
        updateStore.subscribe(userId, sinceTimestamp, updateEvent -> {
            deferredResult.setResult(ResponseEntity.ok(updateEvent));
        });

        return deferredResult;
    }
}

Option 3: Server-Sent Events (SSE)

A single long-lived HTTP connection where the server continuously streams events as text/event-stream. The browser has a built-in EventSource API. Unlike WebSocket, SSE is unidirectional — server to client only.

SSE Trade-offs
ProsCons
Simpler than WebSocket — standard HTTP, no protocol upgradeUnidirectional: server → client only; client must use separate POST for sends
Built-in auto-reconnect with Last-Event-ID replayText only (UTF-8) — no binary frames
HTTP/2 multiplexes many SSE streams over one TCP connectionHTTP/1.1 browsers: max 6 concurrent SSE connections per domain
Works through most proxies (standard HTTP GET)Some corporate proxies buffer response bodies, breaking streaming
 
// ── SSE — Spring endpoint using SseEmitter ────────────────────────
@RestController
@RequestMapping("/api/v1")
public class SseController {

    private static final long SSE_TIMEOUT_MS = 5 * 60 * 1000L; // 5 minutes

    private final ScoreUpdatePublisher scoreUpdatePublisher;

    public SseController(ScoreUpdatePublisher scoreUpdatePublisher) {
        this.scoreUpdatePublisher = scoreUpdatePublisher;
    }

    /**
     * Opens an SSE stream. The SseEmitter is registered with the publisher,
     * which calls emitter.send() whenever a score update is available.
     *
     * SseEmitter vs WebFlux Flux: SseEmitter is simpler for servlet-based apps.
     * If using Spring WebFlux, return Flux<ServerSentEvent> instead.
     */
    @GetMapping(value = "/scores/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public SseEmitter streamScores(@RequestParam String matchId) {
        SseEmitter emitter = new SseEmitter(SSE_TIMEOUT_MS);

        emitter.onCompletion(() -> scoreUpdatePublisher.removeEmitter(matchId, emitter));
        emitter.onTimeout(()    -> scoreUpdatePublisher.removeEmitter(matchId, emitter));
        emitter.onError(error  -> scoreUpdatePublisher.removeEmitter(matchId, emitter));

        scoreUpdatePublisher.addEmitter(matchId, emitter);
        return emitter;
    }
}

// ── ScoreUpdatePublisher.java ─────────────────────────────────────
@Component
public class ScoreUpdatePublisher {

    /** matchId → list of active emitters for that match */
    private final Map<String, List<SseEmitter>> emitters = new ConcurrentHashMap<>();
    private final AtomicLong eventIdCounter = new AtomicLong(0);

    public void addEmitter(String matchId, SseEmitter emitter) {
        emitters.computeIfAbsent(matchId, key -> new CopyOnWriteArrayList<>()).add(emitter);
    }

    public void removeEmitter(String matchId, SseEmitter emitter) {
        List<SseEmitter> matchEmitters = emitters.get(matchId);
        if (matchEmitters != null) {
            matchEmitters.remove(emitter);
        }
    }

    /**
     * Called when a score update arrives (e.g., from a Kafka consumer).
     * Broadcasts to all clients watching this match.
     * Removes dead emitters (client disconnected) silently.
     */
    public void publishScoreUpdate(String matchId, ScoreUpdate update) {
        List<SseEmitter> matchEmitters = emitters.getOrDefault(matchId, List.of());
        long eventId = eventIdCounter.incrementAndGet();

        matchEmitters.forEach(emitter -> {
            try {
                emitter.send(SseEmitter.event()
                    .id(String.valueOf(eventId))
                    .name("score-update")
                    .data(update)
                    .reconnectTime(3000)); // tell client to retry in 3s if disconnected
            } catch (IOException sendError) {
                removeEmitter(matchId, emitter); // dead connection — remove silently
            }
        });
    }
}

Option 4: WebSocket

A persistent, full-duplex TCP connection established via an HTTP upgrade handshake (101 Switching Protocols). After the handshake, both client and server can send frames at any time — binary or text — with minimal per-message overhead (just framing bits, no HTTP headers).

WebSocket Trade-offs
ProsCons
Lowest latency — no request overhead between messagesStateful: server must track each connection (hard to scale horizontally)
Full-duplex — client and server both initiate messagesDoes not work through all corporate proxies (not standard HTTP)
Binary and text frames — efficient for game state, mediaNo built-in reconnection — client must implement reconnect logic
No per-message HTTP header overhead after handshakeRequires sticky sessions or Redis Pub/Sub for horizontal scaling
 
// ── WebSocket Server — Spring @ServerEndpoint (JSR-356) ───────────
@ServerEndpoint(value = "/ws/chat/{userId}")
@Component
public class ChatWebSocketEndpoint {

    // Thread-safe map: userId → session. Must be static so all endpoint
    // instances (one per connection) share the same registry.
    private static final Map<String, Session> activeSessions = new ConcurrentHashMap<>();

    @OnOpen
    public void onOpen(Session session, @PathParam("userId") String userId) {
        activeSessions.put(userId, session);
        System.out.println("[WebSocket] User connected: " + userId
            + " | Total connections: " + activeSessions.size());
    }

    @OnMessage
    public void onMessage(String messageJson, @PathParam("userId") String senderId) {
        ChatMessage message = parseMessage(messageJson);
        deliverToRecipient(senderId, message);
    }

    @OnClose
    public void onClose(@PathParam("userId") String userId, CloseReason reason) {
        activeSessions.remove(userId);
        System.out.println("[WebSocket] User disconnected: " + userId
            + " | Reason: " + reason.getReasonPhrase());
    }

    @OnError
    public void onError(@PathParam("userId") String userId, Throwable error) {
        System.err.println("[WebSocket] Error for user " + userId + ": " + error.getMessage());
        activeSessions.remove(userId);
    }

    private void deliverToRecipient(String senderId, ChatMessage message) {
        Session recipientSession = activeSessions.get(message.getRecipientId());
        if (recipientSession != null && recipientSession.isOpen()) {
            try {
                recipientSession.getBasicRemote().sendText(message.toJson());
            } catch (IOException deliveryError) {
                System.err.println("[WebSocket] Failed to deliver to "
                    + message.getRecipientId() + ": " + deliveryError.getMessage());
            }
        } else {
            // Recipient not connected — store for later delivery (offline inbox)
            messageStore.saveOfflineMessage(message.getRecipientId(), message);
        }
    }

    private ChatMessage parseMessage(String json) {
        // JSON deserialization omitted for brevity — use Jackson ObjectMapper
        return new ChatMessage(json);
    }
}

Full Comparison: All Four Techniques

Real-time Communication Techniques — Complete Comparison
Dimension Short Polling Long Polling SSE WebSocket
Protocol HTTP/1.1+ HTTP/1.1+ HTTP/1.1+ (best with HTTP/2) WS / WSS (upgrade from HTTP)
Direction Client → Server (pull) Client → Server (pull, held open) Server → Client only Full-duplex (both directions)
Latency Up to N seconds ~1 RTT after update available ~1 RTT (sub-second) Lowest — no request overhead
Connection overhead New connection each poll New connection per poll cycle One persistent connection One persistent connection
Binary support Yes (Content-Type: binary) Yes No — text/UTF-8 only Yes — text and binary frames
Proxy / firewall friendly Yes — standard HTTP Yes — looks like slow HTTP Mostly yes — some proxies buffer No — corporate proxies often block WS
Auto-reconnect N/A (client retries on timer) Client re-issues request manually Yes — EventSource built-in No — must implement in client code
Scaling difficulty Easy — stateless, any server Medium — held connections, async Medium — stateful connections Hard — sticky sessions or pub/sub
Best for Infrequent updates (>30s interval) Fallback when WS/SSE blocked Live dashboards, notifications, feeds Chat, games, collaborative editing

Scaling Real-time Systems — The Hard Part

Short polling and long polling are stateless — any server handles any request. SSE and WebSocket are stateful: a user's connection is pinned to one server instance. This creates a fundamental fan-out problem when you scale horizontally.

The problem: User A is connected to Server 1. User B is connected to Server 3. User A sends a message to User B. Server 1 does not have User B's WebSocket connection. How does Server 3 know to push the message to User B?

// ── Redis Pub/Sub WebSocket fan-out (Spring + Lettuce) ───────────

// ── WebSocketMessageRouter.java — publishes to Redis ─────────────
@Component
public class WebSocketMessageRouter {

    private static final String CHANNEL_PREFIX = "ws:messages:";

    private final RedisTemplate<String, String> redisTemplate;

    public WebSocketMessageRouter(RedisTemplate<String, String> redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    /**
     * Called when a WebSocket message arrives on this server.
     * Publishes to Redis so ALL server instances receive it.
     * The current server also receives its own publish (via subscription).
     */
    public void route(ChatMessage message) {
        String channel = CHANNEL_PREFIX + message.getRecipientId();
        redisTemplate.convertAndSend(channel, message.toJson());
    }
}

// ── RedisMessageListener.java — receives from Redis, pushes to WS ──
@Component
public class RedisWebSocketListener implements MessageListener {

    private final WebSocketSessionRegistry sessionRegistry;

    public RedisWebSocketListener(WebSocketSessionRegistry sessionRegistry) {
        this.sessionRegistry = sessionRegistry;
    }

    /**
     * Every server instance subscribes to ALL user channels.
     * When a message arrives, only the server that has the recipient's
     * WebSocket session actually pushes it — others discard silently.
     */
    @Override
    public void onMessage(Message redisMessage, byte[] pattern) {
        String messageJson = new String(redisMessage.getBody());
        ChatMessage message = ChatMessage.fromJson(messageJson);

        Session recipientSession = sessionRegistry.getSession(message.getRecipientId());
        if (recipientSession != null && recipientSession.isOpen()) {
            try {
                recipientSession.getBasicRemote().sendText(messageJson);
            } catch (IOException deliveryError) {
                System.err.println("[Redis→WS] Failed to deliver: " + deliveryError.getMessage());
            }
        }
        // else: not connected to this server — another server will deliver
    }
}
Sticky sessions as an alternative: Configure the load balancer to route all requests from a given client to the same server (IP hash or cookie-based affinity). Simpler, but no failover — if the server goes down, all its connections are lost and clients must reconnect to a different server. Redis Pub/Sub handles server failures gracefully since any server can serve any client.
