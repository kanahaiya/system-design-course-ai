🌐 HTTP / HTTPS Basics

HTTP (HyperText Transfer Protocol) is a request-response protocol. Think of it like a formal postal system: every conversation starts with a client (your browser) sending a letter (request) to a server, and the server mailing back a reply (response). Critically, the postal system has no memory — each letter is treated as if it is the first one ever sent. This is what stateless means: HTTP does not remember previous requests. The server treats request #1,000 the same as request #1.

Every HTTP request has three parts: a method (what action to take), a URL (where to take it), and optional headers + body (extra metadata and data). Every response has a status code (what happened) plus optional headers and body.

HTTP Methods — What Each One Means

Methods tell the server what you want to do, not just which resource to act on. Two important properties: idempotent means calling it multiple times gives the same result as calling it once (like pressing a light switch that's already on). Safe means it does not change any server-side data.

💡
Why Idempotency Matters in System Design
Networks fail. Retries happen. If your payment API uses POST for a charge and the network drops after the server processes the request but before the client gets the response, a naive retry creates a double charge. Safe, idempotent APIs (using PUT with an idempotency key, or GET) make retries harmless. Always design critical mutations with idempotency in mind.

HTTP Headers — Metadata That Controls Everything

Headers are key-value pairs that travel with every request and response. They are invisible to most users but control caching, authentication, content negotiation, and security.

  • Content-Type: Tells the receiver what format the body is in. application/json, text/html, multipart/form-data. Without this, the receiver would have to guess.
  • Authorization: Carries authentication credentials. Typically Bearer <JWT-token> or Basic <base64>. This is how every API authenticates requests.
  • Cache-Control: Tells browsers and CDNs how long to cache the response. max-age=3600 = cache for 1 hour. no-cache = always revalidate. no-store = never cache (for sensitive data).
  • ETag: A unique fingerprint (hash) of the resource content. The server sends this with a response. On the next request, the client sends If-None-Match: <etag>. If the resource hasn't changed, the server returns 304 Not Modified with no body — saving bandwidth.

HTTPS = HTTP + TLS

Plain HTTP sends everything as readable text — like sending a postcard. Anyone who can intercept the network traffic (your ISP, a coffee shop WiFi operator) can read your passwords. HTTPS wraps HTTP inside TLS (Transport Layer Security) — like putting your postcard in a sealed, tamper-evident envelope that only the recipient can open.

The TLS handshake (simplified) works like this:

  1. Client Hello: Browser says "I want to talk securely. Here are the encryption algorithms I support."
  2. Server Hello + Certificate: Server picks an algorithm and sends its SSL certificate (issued by a Certificate Authority like DigiCert, Let's Encrypt).
  3. Certificate Validation: Browser verifies the certificate was signed by a trusted CA and matches the domain. If not, you see the scary "Not Secure" warning.
  4. Key Exchange: Browser and server use asymmetric cryptography (RSA or ECDHE) to agree on a shared secret without sending it over the wire.
  5. Symmetric Encryption: All subsequent data is encrypted with that shared secret using AES — fast symmetric encryption. Asymmetric was only used to securely bootstrap the symmetric key.

⚠️
Interview Tip: HTTP/2 Matters for Microservices
gRPC (Google's internal RPC framework used at scale) runs on HTTP/2 and gets bidirectional streaming and multiplexing for free. When an interviewer asks "why gRPC over REST?", one answer is: HTTP/2 multiplexing means a single connection handles thousands of concurrent RPCs without head-of-line blocking.

📖 DNS Resolution — Step by Step

DNS (Domain Name System) is the internet's phonebook. You know a person's name (google.com), but computers need their phone number (IP address: 142.250.80.46) to actually call them. DNS translates human-readable names into machine-readable IP addresses.

Without DNS, you would need to memorise 142.250.80.46 to visit Google. With DNS, you type google.com and your computer figures out the IP automatically — typically in 20–120ms for a cold lookup.

The 8-Step DNS Resolution Walk-through

When you type api.github.com in your browser for the first time (cold start — no cache), here is exactly what happens:

Breaking down each step:

  1. Browser Cache: Chrome/Firefox maintain their own DNS cache. If you visited github.com in the last few hours, the IP is cached here. Cache hit = done instantly.
  2. OS Cache (/etc/hosts): The OS checks its local DNS cache and the /etc/hosts file. This is how developers point localhost to 127.0.0.1.
  3. Recursive Resolver: On a cache miss, your device asks your ISP's recursive resolver (or Google's 8.8.8.8 / Cloudflare's 1.1.1.1). This resolver does the heavy lifting on your behalf.
  4. Root Nameserver: The recursive resolver asks one of the 13 root nameservers (operated by ICANN, Verisign, etc.). The root server doesn't know the IP — but it knows who handles .com domains. It replies with the TLD nameserver address.
  5. TLD Nameserver: The resolver asks the .com TLD server. It knows who is authoritative for github.com and returns that nameserver's address.
  6. Authoritative Nameserver: The resolver asks GitHub's own nameserver. This is the source of truth — it has the actual A record mapping api.github.com → 140.82.121.6.
  7. Response to Resolver: Authoritative NS returns the IP with a TTL (Time To Live). The resolver caches this for TTL seconds.
  8. Response to Browser: Resolver returns the IP to your browser, which now opens a TCP connection to that IP on port 443 (HTTPS).

TTL, Caching, and Why DNS Changes Take Time

Every DNS record has a TTL (Time To Live) — a number in seconds that tells every resolver how long to cache the answer. If api.stripe.com has a TTL of 300 seconds (5 minutes), then for 5 minutes after resolution, every resolver in the world that has cached it will serve the old IP without re-querying.

This is why changing DNS takes time: even after you update your A record, the old record is cached everywhere until TTL expires. For critical migrations, engineers lower the TTL to 60 seconds a few days before the change, perform the change, then raise it back to 3600 after traffic has shifted.

GeoDNS — Route Users to the Nearest Datacenter

GeoDNS (also called latency-based routing) returns different IP addresses based on where the DNS query originated. If a user in India queries api.netflix.com, the authoritative nameserver returns the IP of the Mumbai datacenter instead of the US datacenter. This reduces latency from ~200ms to ~15ms. AWS Route 53's latency-based routing and Cloudflare's Anycast both use this principle.

🎯
Interview Takeaway: DNS + Load Balancer Together
In real systems, the DNS A record points to a load balancer IP, not individual server IPs. The load balancer then distributes traffic. This gives you geo-routing at the DNS level AND granular health-check routing at the load balancer level — two layers of intelligent traffic management.

🔌 TCP vs UDP

At the transport layer, every internet communication uses one of two protocols: TCP or UDP. The choice affects reliability, latency, and complexity of your system.

TCP — The Reliable, Careful Protocol

Think of TCP like a certified postal service. Before sending anything, sender and receiver perform a handshake to establish the connection. Every packet sent is acknowledged; if an ack doesn't arrive, the packet is retransmitted. Packets are delivered in order — if packet 5 arrives before packet 4, TCP buffers packet 5 until packet 4 arrives. This is what connection-oriented, reliable, ordered delivery means.

TCP 3-Way Handshake (establishing a connection):

  1. SYN: Client sends a SYN (synchronize) packet. "I want to connect. My starting sequence number is X."
  2. SYN-ACK: Server replies with SYN-ACK. "Acknowledged your X. My starting sequence number is Y."
  3. ACK: Client sends ACK. "Acknowledged your Y. Connection established."

This handshake takes 1 full round-trip before any data is sent. For a client in New York connecting to a server in London (100ms RTT), you lose 100ms just establishing the connection — before a single byte of HTTP data flows. This is why connection pooling and HTTP keep-alive matter at scale.

TCP also implements flow control (receiver tells sender how much buffer space it has, preventing overflow) and congestion control (sender slows down if the network is congested, preventing packet storms).

UDP — The Fast, Unreliable Protocol

UDP is like dropping a postcard in a mailbox. You don't know if it arrived. You don't know if it arrived in the right order. There is no handshake. This makes UDP much faster (no setup cost, no retransmission overhead) but you get no guarantees.

For many applications, this tradeoff is exactly right: if you are streaming video and frame 1000 is lost, you don't want to pause playback to retransmit it — you'd rather skip it and show frame 1001. A slightly degraded video is better than a frozen one.

Java Code: Simple TCP Server/Client

The clearest way to understand TCP's connection model is to see it in code. The ServerSocket.accept() call blocks until a client connects — this is the TCP handshake completing. Only after that can you read/write data. 

// TCP Server — listens for one client, echoes what it receives
import java.io.*;
import java.net.*;

public class TcpEchoServer {

    private static final int PORT = 8080;
    private static final int MAX_BUFFER_BYTES = 1024;

    public static void main(String[] args) throws IOException {
        // ServerSocket binds to port 8080 — OS queues incoming connections
        try (ServerSocket serverSocket = new ServerSocket(PORT)) {
            System.out.println("[Server] Listening on port " + PORT);

            // accept() BLOCKS until a client completes the TCP 3-way handshake
            // Each call returns one connected Socket — spawn a thread per client in prod
            try (Socket clientSocket = serverSocket.accept()) {
                System.out.println("[Server] Client connected: "
                    + clientSocket.getInetAddress());

                BufferedReader inputReader = new BufferedReader(
                    new InputStreamReader(clientSocket.getInputStream()));
                PrintWriter outputWriter = new PrintWriter(
                    clientSocket.getOutputStream(), true /* autoFlush */);

                String receivedLine;
                // Read lines until client closes connection (null return = EOF)
                while ((receivedLine = inputReader.readLine()) != null) {
                    System.out.println("[Server] Received: " + receivedLine);
                    outputWriter.println("ECHO: " + receivedLine); // write back
                }
            }
        } // ServerSocket auto-closes — OS releases port binding
    }
}

// TCP Client — connects to server, sends a message, reads the echo
public class TcpEchoClient {

    private static final String SERVER_HOST = "localhost";
    private static final int SERVER_PORT = 8080;

    public static void main(String[] args) throws IOException {
        // new Socket() triggers the TCP 3-way handshake immediately
        // Throws ConnectException if server is not running
        try (Socket socket = new Socket(SERVER_HOST, SERVER_PORT)) {
            System.out.println("[Client] Connected to " + SERVER_HOST + ":" + SERVER_PORT);

            PrintWriter outputWriter = new PrintWriter(
                socket.getOutputStream(), true);
            BufferedReader inputReader = new BufferedReader(
                new InputStreamReader(socket.getInputStream()));

            outputWriter.println("Hello, TCP Server!"); // send data
            String serverReply = inputReader.readLine(); // wait for echo
            System.out.println("[Client] Server replied: " + serverReply);
        } // Socket auto-closes — sends TCP FIN to begin 4-way teardown
    }
}
💡
Real-World: HTTP/3 Uses UDP via QUIC
Google invented QUIC (now standardized as HTTP/3) to get the best of both worlds: reliability and ordering (like TCP) with lower latency (like UDP). QUIC implements its own reliability layer on top of UDP at the application level, plus it combines the TLS handshake with the connection setup into a single round-trip. It also avoids TCP's head-of-line blocking: if packet 5 is lost, only stream 5 is blocked, not all streams.

🏗️ Client-Server & 3-Tier Architecture

Client-server is the foundational model of the internet: one party (the client) makes requests, and another party (the server) fulfils them. The server is stateless by default — it does not remember previous client interactions unless it explicitly stores state (in a session or database).

As systems grow, the single "server" becomes multiple layers, each with a distinct responsibility. This separation is what "N-tier architecture" means.

Why 3-Tier? Separation of Concerns

  • Presentation layer (browser, mobile app): Renders UI. Knows nothing about how data is stored. You can rebuild the entire frontend without touching the backend.
  • Application layer (API servers): Contains business logic — authentication, validation, orchestration. Horizontally scalable: add more API servers when traffic grows. Stateless by design so any server can handle any request.
  • Data layer (database, cache): Persistent storage. This is the hardest to scale and the most critical to protect. The separation prevents the application layer from being a bottleneck to data access patterns.

When to Use Microservices

Microservices split each business domain into its own independently deployable service with its own database. The benefits: independent scaling (scale the payment service without scaling user service), independent deployments (ship features faster), fault isolation (a crash in recommendations doesn't crash checkout). The costs: distributed system complexity, network latency between services, harder debugging, eventual consistency challenges.

Start with a monolith. Extract services when you feel the pain. Amazon, Netflix, and Uber all started as monoliths and extracted microservices when specific components needed independent scaling.

⚖️ Load Balancers — L4 vs L7

A load balancer is a traffic cop sitting in front of your servers. When 100,000 requests arrive per second and you have 10 servers, the load balancer decides which server handles which request. Without a load balancer, all 100,000 requests would hit server #1, which would collapse under the load while servers #2–#10 sit idle.

Load balancers operate at different layers of the network stack. The two most important for system design are Layer 4 (Transport) and Layer 7 (Application).

L4 Load Balancer — Transport Layer

An L4 load balancer operates at the TCP/UDP layer. It sees only IP addresses and port numbers — it cannot read HTTP headers, URLs, or cookies. It is essentially a very fast TCP proxy that forwards packets to backend servers.

Because it does not parse application-level data, it is extremely fast with very low latency overhead. It is ideal for high-throughput, non-HTTP protocols: database connections, SMTP, game servers. Examples: AWS Network Load Balancer (NLB), HAProxy in TCP mode.

L7 Load Balancer — Application Layer

An L7 load balancer terminates the TCP/TLS connection, reads the full HTTP request (URL path, headers, cookies, body), makes a routing decision, then opens a new connection to the backend. This gives it powerful capabilities:

  • URL-based routing: Send /api/* to the API cluster and /static/* to the CDN or object store cluster.
  • Header-based routing: Route requests with X-Version: v2 header to the v2 service — useful for canary deployments and A/B testing.
  • SSL termination: Decrypt HTTPS at the load balancer so backend servers handle plain HTTP internally — simpler certificate management and faster backend processing.
  • Sticky sessions: Use the session cookie to route a specific user to the same backend server — needed for legacy stateful apps.
  • Content-based routing: Route to different clusters based on Accept-Language header for geo-localized content.

Examples: AWS Application Load Balancer (ALB), Nginx, Traefik, HAProxy in HTTP mode.

Load Balancing Algorithms

  • Round-robin: Server 1, Server 2, Server 3, Server 1, … Equal distribution, ignores server load.
  • Weighted round-robin: Server 1 gets 50% of traffic, Servers 2 and 3 get 25% each. Useful when servers have different capacities.
  • Least connections: Send each new request to the server with the fewest active connections. Better than round-robin when requests have variable processing times.
  • IP hash: Hash the client's IP address and mod by the number of servers. The same client always hits the same server. Provides sticky sessions without cookies.
  • Random: Pick a server randomly. Surprisingly effective with enough servers (law of large numbers).

Health Checks — How Load Balancers Know a Server is Down

Every load balancer periodically sends a health check request to each backend server (e.g., GET /health every 10 seconds). If a server fails to respond with 200 within the timeout (say, 5 seconds) for 3 consecutive checks, the load balancer marks it as unhealthy and stops routing traffic to it. When it recovers and passes health checks, it is added back automatically. This is the mechanism behind zero-downtime deployments.

🎯
Interview Answer: Which Load Balancer?
When asked "what load balancer would you use?" in a system design, the safe default is L7 for web/API traffic. Justify it: "I'd use an L7 load balancer (like AWS ALB) because it lets me route /api/* to the application cluster and /static/* to S3/CloudFront, handle SSL termination in one place, and implement health checks at the HTTP level. If I needed to load-balance raw TCP connections to a database cluster or needed sub-millisecond overhead, I'd use L4."

🔢 Ports & Protocols Quick Reference

A port is a number (0–65535) that identifies which application on a server should receive a packet. Think of an IP address as the building address and the port as the apartment number. When your browser connects to https://github.com, it connects to IP 140.82.121.4 on port 443 — the HTTPS apartment.

Ports 0–1023 are "well-known ports" reserved for standard protocols. Ports 1024–49151 are registered (like Redis on 6379). Ports 49152–65535 are ephemeral — the OS assigns them dynamically to client connections.

The OSI Model — Simplified to What Matters

The OSI model has 7 layers but for system design interviews, you need to understand 4 practical layers and how they compose:

⚠️
Security: Never Expose Database Ports to the Internet
In production, database ports (3306, 5432, 6379, 27017) must only be accessible within a private VPC subnet. Only your application servers (in the app layer subnet) should be able to connect to the database. Load balancers expose only port 443 to the internet. This is enforced with security groups / firewall rules. Any architecture that exposes a database port to 0.0.0.0/0 is a critical vulnerability.
