Module 03

Caching Strategies

Caching is the single highest-leverage technique for scaling read-heavy systems. Master the four write patterns, know when each eviction policy applies, and understand how to prevent the thundering herd from taking down your database.

⏱️ 35 min read
🎯 Intermediate
🏆 Very High Frequency

🗃️ Cache Write Patterns

Cache-Aside (Lazy Loading)

Application manages the cache explicitly. On read: check cache → if miss, read from DB → populate cache → return. On write: write to DB, then invalidate (not update) the cache key. Pros: resilient — cache failure doesn't break reads. Only requested data is cached. Cons: cache miss penalty (extra DB read). Stale data window between write and invalidation. Used by: most applications. Memcached + MySQL at Facebook historically.

Write-Through

Every write goes to cache AND database synchronously before acknowledging to the client. Cache is always consistent with DB. Pros: no stale reads after writes. No thundering herd on fresh keys. Cons: every write pays double latency. Caches fill with data that may never be read. Used by: write-through Redis in front of PostgreSQL for user profile data.

Write-Back (Write-Behind)

Write to cache only; asynchronously flush dirty cache entries to DB in batches. Pros: lowest write latency. Batches reduce DB write pressure (great for counters). Cons: data loss risk if cache node fails before flushing. Complex dirty-tracking. Used by: gaming leaderboards, view counters, like counts — where occasional loss is acceptable.

Write-Around

Writes bypass the cache and go directly to DB. Cache is populated only on read miss. Prevents cache pollution for write-once read-rarely data (file uploads, logs). Highest cache miss rate on first read.

🗑️ Eviction Policies

LRU — Least Recently Used

Evicts the item that has not been accessed for the longest time. Works on temporal locality assumption: if you haven't used it recently, you probably won't need it. Implementation: doubly linked list + hash map. O(1) get and put. Weakness: a sequential scan (one-time bulk read) pollutes the cache by evicting hot items. Solution: Redis uses approximated LRU (samples N random keys, evicts the stalest) for O(1) with lower memory overhead.

LFU — Least Frequently Used

Evicts the item with the fewest total accesses. Better than LRU for workloads with stable hot items (e.g., a viral video that gets millions of repeated views). Harder to implement efficiently. Weakness: newly added popular items get evicted before accumulating enough frequency counts. Solution: decay mechanisms reduce frequency counts over time (aging). Redis 4.0+ supports LFU.

TTL-based Expiration

Every key has a time-to-live. After TTL, the key is treated as a miss regardless of eviction policy. TTL is the primary consistency tool for cache-aside: set TTL to your maximum acceptable staleness window. Combine with active invalidation on writes for the best consistency/performance balance.

🔴 Redis Data Structures for System Design

Redis is not just a key-value store. Choosing the right data structure eliminates application logic and reduces round trips.

  • String — Simple cache, counters (INCR is atomic). Rate limiters, session tokens, distributed locks (SET NX EX).
  • Hash — Store objects with fields (user profile: HSET user:42 name "Alice" age 30). Partial updates without serializing the whole object. Memory-efficient for small hashes.
  • Sorted Set (ZSET) — Leaderboards, priority queues, rate limiting with sliding window. Each member has a score; range queries by score are O(log N). ZADD leaderboard 9800 "user:42" → ZRANGE leaderboard 0 9 REV WITHSCORES for top-10.
  • List — Message queues (LPUSH + BRPOP), activity feeds, recent items. LRANGE for pagination. LTRIM for bounded lists.
  • Set — Unique visitors, tags, "has user seen this?" (SADD + SISMEMBER). Set operations (SUNION, SINTER) for social graph intersection (mutual friends).
  • HyperLogLog — Probabilistic unique count with 0.81% error, fixed 12 KB memory. PFADD + PFCOUNT. Use for DAU/MAU counting at scale.
  • Pub/Sub — Real-time notifications, live dashboards. At-most-once delivery — not durable. Use Kafka for durability.

🌐 CDN Caching

CDNs (Cloudflare, CloudFront, Fastly) cache content at edge nodes geographically close to users. The latency win is dramatic: serving from an edge node 20ms from the user vs. an origin server 150ms away is a 7.5× improvement.

Cache-Control Headers (the contract between app and CDN)

  • Cache-Control: public, max-age=31536000, immutable — Static assets with content-hashed URLs. Cache forever; never revalidate.
  • Cache-Control: public, max-age=300, stale-while-revalidate=60 — API responses. Serve for 5 minutes; if stale, serve old content while refreshing in background.
  • Cache-Control: private, no-store — User-specific data (bank statement). Never cache at CDN layer.
  • Surrogate-Key / Cache-Tag — Tag CDN objects by logical group. Purge all objects tagged product:42 on price update. Used by Cloudflare Cache Tags, Fastly surrogate keys.

CDN Strategy by Content Type

  • Static assets (JS, CSS, images) — Immutable with hashed filenames. TTL = 1 year. Zero origin hits after warm-up.
  • API responses — Short TTL (1–60s) with stale-while-revalidate. Balance freshness vs. origin traffic.
  • User-specific HTML — Never cache at CDN unless using Edge Side Includes (ESI) to inject dynamic fragments.

🦬 Cache Stampede (Thundering Herd)

A cache stampede occurs when a popular cache entry expires and thousands of concurrent requests all miss the cache simultaneously, all attempt to rebuild the cache from the database, and the database is overwhelmed. This is a real production failure mode.

Prevention Strategies

  • Mutex / distributed lock: When a miss occurs, one request acquires a lock and rebuilds the cache. Other requests wait (blocking) or serve stale content (non-blocking). Use Redis SET NX EX as a distributed mutex. Non-blocking is preferred: serve stale while one request refreshes.
  • Probabilistic early expiration (PER): Before the TTL expires, each cache read has a small probability of triggering a refresh. The probability increases as expiration approaches. Eliminates the synchronized miss at TTL=0. Formula: refresh if (currentTime - createdAt) > TTL - β × ln(random())
  • TTL jitter: Add random jitter (±10%) to TTLs when populating the cache. Prevents synchronized mass expiration of related keys at the same second. Simple, effective, should always be used.
  • Background refresh: A separate worker thread refreshes cache entries before they expire. Requires knowing which keys to refresh (use a separate TTL tracking set in Redis).

☕ Java Implementation: Thread-Safe LRU Cache

Production-quality LRU cache using LinkedHashMap's access-order mode. Thread safety via ReentrantReadWriteLock — read-heavy workloads benefit from concurrent reads while writes are exclusive. Includes stampede prevention via a per-key mutex. 

import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.locks.ReentrantReadWriteLock;
import java.util.function.Supplier;

/**
 * Thread-safe LRU cache with stampede prevention.
 * Uses LinkedHashMap access-order mode as the O(1) LRU core.
 * Stampede prevention: per-key ConcurrentHashMap mutex ensures only
 * one thread computes a missing value; others wait or return stale.
 *
 * @param  cache key type
 * @param  cache value type
 */
public class LruCache<K, V> {

    private final int maximumCapacity;
    private final ReentrantReadWriteLock readWriteLock = new ReentrantReadWriteLock();
    private final ReentrantReadWriteLock.ReadLock readLock = readWriteLock.readLock();
    private final ReentrantReadWriteLock.WriteLock writeLock = readWriteLock.writeLock();

    // Per-key semaphore map: prevents stampede by serializing cache misses per key
    private final ConcurrentHashMap<K, Semaphore> keyLocks = new ConcurrentHashMap<>();

    // LinkedHashMap with access-order=true: get() moves entry to the end (most recently used)
    private final LinkedHashMap<K, V> cacheStore;

    public LruCache(int maximumCapacity) {
        this.maximumCapacity = maximumCapacity;
        // accessOrder=true means iteration order is from LRU to MRU
        this.cacheStore = new LinkedHashMap<K, V>(maximumCapacity, 0.75f, true) {
            @Override
            protected boolean removeEldestEntry(Map.Entry<K, V> eldestEntry) {
                // Called on every put(); returns true to evict the LRU entry
                return size() > maximumCapacity;
            }
        };
    }

    /**
     * Returns cached value for key, or null if not present.
     * Accessing a key promotes it to most-recently-used position.
     *
     * @param key the cache key
     * @return the cached value, or null on miss
     */
    public V get(K key) {
        readLock.lock();
        try {
            // LinkedHashMap.get() with accessOrder=true reorders internally — needs write lock
            // We use write lock for get() because access-order mutation is not thread-safe
        } finally {
            readLock.unlock();
        }
        // Use write lock because get() in access-order mode mutates the map structure
        writeLock.lock();
        try {
            return cacheStore.get(key);
        } finally {
            writeLock.unlock();
        }
    }

    /**
     * Inserts or updates a key-value pair in the cache.
     * If at capacity, the least recently used entry is evicted.
     *
     * @param key   the cache key
     * @param value the value to cache
     */
    public void put(K key, V value) {
        writeLock.lock();
        try {
            cacheStore.put(key, value);
        } finally {
            writeLock.unlock();
        }
    }

    /**
     * Cache-aside get with stampede prevention.
     * If key is missing: acquires a per-key mutex, calls the loader once,
     * populates the cache, releases the mutex. Concurrent threads for the
     * same key wait on the mutex and then get the populated value.
     *
     * @param key    the cache key
     * @param loader supplies the value on cache miss (e.g., a DB call)
     * @return the cached or freshly loaded value
     */
    public V getOrLoad(K key, Supplier<V> loader) {
        V cachedValue = get(key);
        if (cachedValue != null) {
            return cachedValue;
        }

        // Cache miss: acquire per-key semaphore to serialize DB calls for the same key
        Semaphore keyMutex = keyLocks.computeIfAbsent(key, ignored -> new Semaphore(1));
        try {
            keyMutex.acquire();
            // Double-check after acquiring — another thread may have populated it
            V valueAfterLock = get(key);
            if (valueAfterLock != null) {
                return valueAfterLock;
            }
            // Only one thread reaches here per key: call the loader
            V freshValue = loader.get();
            if (freshValue != null) {
                put(key, freshValue);
            }
            return freshValue;
        } catch (InterruptedException interruptedException) {
            Thread.currentThread().interrupt();
            // Fallback: load without caching rather than fail entirely
            return loader.get();
        } finally {
            keyMutex.release();
            keyLocks.remove(key); // Clean up to prevent memory leak
        }
    }

    public int size() {
        readLock.lock();
        try {
            return cacheStore.size();
        } finally {
            readLock.unlock();
        }
    }

    // --- Demo ---
    public static void main(String[] args) throws Exception {
        LruCache<String, String> userProfileCache = new LruCache<>(3);

        // Simulate DB loader
        Supplier<String> dbLoader = () -> {
            System.out.println("  [DB HIT] Loading from database...");
            return "UserProfileData-" + System.currentTimeMillis();
        };

        System.out.println("First access (cache miss):");
        String profile1 = userProfileCache.getOrLoad("user:1", dbLoader);
        System.out.println("  Got: " + profile1);

        System.out.println("Second access (cache hit):");
        String profile2 = userProfileCache.getOrLoad("user:1", dbLoader);
        System.out.println("  Got: " + profile2);

        System.out.println("Fill cache to capacity (3 items):");
        userProfileCache.getOrLoad("user:2", dbLoader);
        userProfileCache.getOrLoad("user:3", dbLoader);
        System.out.println("Cache size: " + userProfileCache.size());

        System.out.println("Access user:4 → evicts LRU entry (user:1):");
        userProfileCache.getOrLoad("user:4", dbLoader);
        System.out.println("user:1 in cache: " + (userProfileCache.get("user:1") != null));
        System.out.println("user:4 in cache: " + (userProfileCache.get("user:4") != null));
    }
}
