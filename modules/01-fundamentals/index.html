Distributed Systems Fundamentals

The bedrock theorems and mental models every MAANG interviewer expects you to know cold. CAP, ACID vs BASE, consistency guarantees, and the latency numbers that anchor every estimation you'll ever do on a whiteboard.

⏱️ 35 min read
🎯 Foundation
🏆 Essential

🔺 CAP Theorem

Brewer's CAP theorem (2000, proved by Gilbert & Lynch 2002) states that a distributed data store can guarantee at most two of three properties simultaneously:

  • Consistency (C) — Every read returns the most recent write or an error. All nodes see the same data at the same time.
  • Availability (A) — Every request receives a (non-error) response, though it may not contain the most recent write.
  • Partition tolerance (P) — The system continues operating even when network partitions cause arbitrary message loss between nodes.

The real insight: In any real network, partitions will happen. So P is non-negotiable. The practical choice is always CP vs AP:

  • CP systems (HBase, Zookeeper, etcd): On partition, reject writes to maintain consistency. Prefer correctness over uptime.
  • AP systems (Cassandra, DynamoDB, CouchDB): On partition, continue serving stale data. Prefer uptime over correctness.

PACELC extension: PACELC (2012) improves on CAP by noting that even without partitions, there is a latency vs consistency trade-off (L vs C). DynamoDB defaults to AP+L (low latency eventual consistency) but offers strongly consistent reads at higher latency cost.

⚗️ ACID vs BASE

ACID is the transaction model of traditional relational databases. BASE is the relaxed model embraced by large-scale NoSQL systems.

ACID Properties

  • Atomicity — A transaction is all-or-nothing. If any operation fails, the entire transaction rolls back. Implemented via write-ahead logs (WAL) and two-phase commit (2PC).
  • Consistency — A transaction brings the database from one valid state to another, preserving all defined rules (constraints, cascades, triggers).
  • Isolation — Concurrent transactions execute as if they were serial. Isolation levels (READ UNCOMMITTED → SERIALIZABLE) trade performance for correctness.
  • Durability — Once committed, a transaction survives crashes. Achieved via WAL flushed to disk before commit acknowledgment.

BASE Properties

  • Basically Available — The system guarantees availability (per CAP's definition), accepting that some data may be stale.
  • Soft state — State may change over time even without input, as the system converges to consistency.
  • Eventually consistent — Given no new updates, all replicas will eventually converge to the same value. Conflict resolution (last-write-wins, CRDTs, vector clocks) is the hard part.

Interview signal: Don't say "NoSQL is BASE." Say: "Cassandra uses tunable consistency — I can request QUORUM reads for stronger guarantees at higher latency cost, or ONE for lowest latency with eventual consistency. The choice depends on whether we're handling financial transactions or social media timelines."

📊 Consistency Models (Strongest to Weakest)

  • Linearizability (strong consistency) — Operations appear instantaneous and atomic. Every read reflects the latest completed write across all nodes. Requires synchronous replication and Paxos/Raft consensus. High latency.
  • Sequential consistency — All nodes see operations in the same order, but not necessarily real-time order. Cheaper than linearizability.
  • Causal consistency — If operation A causally precedes B (A happened-before B), all nodes see A before B. Unrelated operations can be reordered. Used by MongoDB with causal sessions.
  • Read-your-writes — A client always reads its own writes, even if other clients may see stale data. Session-level guarantee.
  • Eventual consistency — Given no new updates, all replicas eventually converge. Conflict resolution is application-defined. Lowest latency, highest availability.

🧮 Back-of-Envelope Estimation

Interviewers use estimation to test whether you think in orders of magnitude. Be within 10× — precision is not the goal, sanity is.

Power of 2 Reference

  • 2¹⁰ = 1,024 ≈ 1 thousand (KB)
  • 2²⁰ ≈ 1 million (MB)
  • 2³⁰ ≈ 1 billion (GB)
  • 2⁴⁰ ≈ 1 trillion (TB)

Common Estimation Anchors

  • Twitter DAU: ~240M active users, ~500M tweets/day ≈ 6,000 tweets/sec
  • YouTube: 500 hours of video uploaded per minute → ~50 GB/min raw storage
  • Throughput rules: A single server handles ~10,000 RPS for simple reads; ~1,000 RPS for heavy writes with durable commits
  • Storage: 1 character = 1 byte; 1 tweet (280 chars + metadata) ≈ 300 bytes; 500M tweets/day × 300B ≈ 150 GB/day

Estimation Template

  1. DAU / MAU → daily request volume
  2. Reads vs writes ratio (social: 100:1, financial: 10:1)
  3. Peak = 2–3× average
  4. Object size × daily volume = daily storage ingestion
  5. Retention period × daily ingestion = total storage
  6. Bandwidth = throughput × object size

☕ Java Implementation: CAP Theorem Illustrated

This implementation shows a simplified distributed key-value store that explicitly models the CP vs AP choice during a network partition. The PartitionPolicy enum makes the trade-off explicit rather than hiding it. 

import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicBoolean;
import java.util.Optional;
import java.util.logging.Logger;

/**
 * Illustrates CAP theorem choices in a simplified distributed KV store.
 * In CP mode: rejects writes during partition to guarantee consistency.
 * In AP mode: accepts writes during partition, resolves conflicts with
 *             last-write-wins (LWW) after partition heals.
 */
public class CapKeyValueStore {

    private static final Logger LOG = Logger.getLogger(CapKeyValueStore.class.getName());

    public enum PartitionPolicy { CP, AP }

    private record VersionedValue(String value, long timestampMs) {}

    private final ConcurrentHashMap<String, VersionedValue> localStore = new ConcurrentHashMap<>();
    private final AtomicBoolean partitioned = new AtomicBoolean(false);
    private final PartitionPolicy policy;

    public CapKeyValueStore(PartitionPolicy policy) {
        this.policy = policy;
    }

    /**
     * Simulates a network partition event.
     * After this, the node cannot reach its replicas.
     */
    public void simulatePartition(boolean isPartitioned) {
        partitioned.set(isPartitioned);
        LOG.info("Partition state changed: " + isPartitioned + " (policy=" + policy + ")");
    }

    /**
     * Write a key-value pair.
     *
     * CP: throws PartitionException during partition — consistency preserved.
     * AP: accepts the write and marks it dirty for later reconciliation.
     *
     * @param key   the storage key
     * @param value the value to store
     * @throws PartitionException if CP policy and node is partitioned
     */
    public void put(String key, String value) throws PartitionException {
        if (partitioned.get()) {
            if (policy == PartitionPolicy.CP) {
                // CP: refuse the write. The client gets an error, but data stays consistent.
                throw new PartitionException(
                    "CP mode: write rejected during partition. Consistency guaranteed, availability sacrificed."
                );
            }
            // AP: accept the write. Availability preserved, consistency sacrificed temporarily.
            LOG.warning("AP mode: accepting write during partition. May create conflict on " + key);
        }

        long timestamp = System.currentTimeMillis();
        localStore.put(key, new VersionedValue(value, timestamp));
        LOG.info("Written: " + key + "=" + value + " @" + timestamp);
    }

    /**
     * Read a value by key.
     * CP: may return empty if partition prevents quorum read confirmation.
     * AP: always returns local value (may be stale).
     *
     * @param key the key to look up
     * @return the value, or empty if CP-mode uncertainty during partition
     */
    public Optional<String> get(String key) {
        if (partitioned.get() && policy == PartitionPolicy.CP) {
            // A real CP system would return an error here rather than stale data.
            // We return empty to model "no stale read" guarantee.
            LOG.warning("CP mode: read rejected during partition — cannot confirm quorum.");
            return Optional.empty();
        }
        return Optional.ofNullable(localStore.get(key))
                       .map(VersionedValue::value);
    }

    /**
     * Reconciles a conflicting remote value after partition heals.
     * Uses last-write-wins (LWW) based on timestamp — simplest conflict resolution.
     * Production systems use vector clocks or CRDTs for richer semantics.
     *
     * @param key         the conflicted key
     * @param remoteValue the value from the other partition
     * @param remoteTs    the timestamp of the remote write
     */
    public void reconcile(String key, String remoteValue, long remoteTs) {
        localStore.merge(key, new VersionedValue(remoteValue, remoteTs), (local, remote) -> {
            // LWW: higher timestamp wins
            String winner = local.timestampMs() >= remote.timestampMs()
                            ? "local" : "remote";
            LOG.info("Conflict on '" + key + "': " + winner + " wins (LWW)");
            return local.timestampMs() >= remote.timestampMs() ? local : remote;
        });
    }

    public static class PartitionException extends Exception {
        public PartitionException(String message) { super(message); }
    }

    // --- Demo ---
    public static void main(String[] args) throws Exception {
        System.out.println("=== CP Mode Demo ===");
        CapKeyValueStore cpStore = new CapKeyValueStore(PartitionPolicy.CP);
        cpStore.put("user:42", "Alice");
        cpStore.simulatePartition(true);
        try {
            cpStore.put("user:42", "AliceUpdated"); // This will throw
        } catch (PartitionException partitionException) {
            System.out.println("Expected: " + partitionException.getMessage());
        }

        System.out.println("\n=== AP Mode Demo ===");
        CapKeyValueStore apStore = new CapKeyValueStore(PartitionPolicy.AP);
        apStore.put("user:42", "Bob");
        apStore.simulatePartition(true);
        apStore.put("user:42", "BobUpdated"); // Accepted, diverged state
        apStore.simulatePartition(false);
        // Simulating remote node had "BobFromReplica" written at a later timestamp
        apStore.reconcile("user:42", "BobFromReplica", System.currentTimeMillis() + 1000);
        System.out.println("After reconciliation: " + apStore.get("user:42").orElse("empty"));
    }
}

PropertyStrong Consistency (CP)Eventual Consistency (AP)When to choose
Read latencyHigh (quorum round-trip)Low (local read)AP for timelines, CP for balances
Write availabilityLow (rejected on partition)High (always accepted)AP for shopping carts, CP for inventory counts
Conflict resolutionNot needed (single truth)Required (LWW, CRDT, manual)CP when conflict resolution is business logic
