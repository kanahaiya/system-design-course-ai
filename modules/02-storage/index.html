Storage & Databases

Choose the right database, shard it correctly, replicate it safely. The three decisions that determine whether your system survives 10× traffic growth or collapses under it.

🗄️ SQL vs NoSQL: Decision Framework

The question is never "which is better?" — it's "which fits this access pattern?" Most large systems use both: PostgreSQL for transactional data, Cassandra for time-series writes, Redis for caching, S3 for blobs.

Choose SQL (Relational) when:

  • Data has complex relationships requiring multi-table joins (e.g., e-commerce: orders, line items, products, users)
  • ACID transactions are required (payment processing, inventory management)
  • Schema is stable and well-understood upfront
  • Read patterns are diverse and ad-hoc (reporting, analytics on operational data)
  • Data volume is below ~10 TB and write throughput below ~10,000 writes/sec

Choose NoSQL when:

  • Document (MongoDB, Firestore): Hierarchical data accessed as a unit; schema flexibility needed; rapid product iteration
  • Wide-column (Cassandra, HBase): Write-heavy time-series data; known query patterns at design time; massive scale (petabytes)
  • Key-value (DynamoDB, Redis): Single-key lookups at extreme scale; session storage, user profiles, shopping carts
  • Graph (Neo4j, Amazon Neptune): Relationship-centric queries (social networks, recommendation engines, fraud detection)

Interview signal: Never choose NoSQL just for "scale." PostgreSQL with proper indexing, connection pooling (PgBouncer), and read replicas handles millions of users. Choose NoSQL when your access pattern demands it.

🔀 Horizontal Sharding Strategies

Sharding (horizontal partitioning) splits data across multiple database nodes. Each shard is an independent database holding a subset of rows. The shard key is the most important design decision — it determines data distribution and which queries require cross-shard scatter-gather.

1. Range Sharding

Partition by contiguous ranges of the shard key (e.g., userId 1–1M on shard 1, 1M–2M on shard 2). Simple to implement. Enables range scans within a shard. Problem: hotspots if recent data is always in the same range (e.g., sharding tweets by timestamp puts all new writes on one shard).

2. Hash Sharding

Apply a hash function to the shard key: shardIndex = hash(key) % numShards. Distributes load evenly. Eliminates hotspots. Problem: re-sharding requires rehashing and moving ~half the data. Solution: consistent hashing reduces data movement to 1/N on shard addition.

3. Directory (Lookup) Sharding

A separate lookup table maps each key (or key range) to a shard. Maximum flexibility — you can move individual users between shards without rehashing. Problem: the lookup table is a single point of failure and bottleneck. Must be replicated and cached aggressively.

Choosing a Shard Key

  • High cardinality — enough distinct values to distribute evenly
  • Low correlation with time — avoid auto-increment IDs that create write hotspots
  • Aligns with query patterns — queries that need data from one shard are fast; cross-shard queries are slow
  • Immutable — changing a shard key requires moving the row to a different shard

🔄 Replication Patterns

Leader-Follower (Single-Leader)

All writes go to the leader. The leader replicates to followers asynchronously (low latency, possible data loss on crash) or synchronously (no data loss, but write latency blocked by slowest follower). MySQL, PostgreSQL, MongoDB, Redis use this pattern. On leader failure, a follower is promoted — this is where inconsistency windows occur.

Multi-Leader

Multiple nodes accept writes simultaneously, then replicate to each other. Used for multi-datacenter deployments (each DC has a leader). Problem: write conflicts are inevitable and hard to resolve. Conflict resolution strategies: last-write-wins (risky), application-level resolution, CRDTs. Example: CouchDB, Google Docs (operational transforms).

Leaderless (Dynamo-style)

Any node accepts writes. Reads and writes use quorum: if W + R > N (total replicas), at least one node in a read quorum overlaps with the latest write quorum. Common: W=2, R=2, N=3. Cassandra, DynamoDB, Riak use this. Enables highest availability — no single point of failure for writes.

🌲 B-tree vs LSM-tree Indexes

The index structure determines whether your database is optimized for reads or writes. This is a deep topic that differentiates strong candidates.

B-tree (PostgreSQL, MySQL InnoDB, most relational DBs)

  • Balanced tree structure; pages are fixed-size (typically 4–16 KB)
  • Updates are in-place: a write finds the right page and modifies it on disk
  • Read performance: excellent — O(log N) lookups, great for range scans
  • Write performance: good but involves random I/O (write amplification factor ~5–10×)
  • Write amplification: one logical write may cause multiple disk page rewrites (COW, WAL, dirty page flush)

LSM-tree (Cassandra, LevelDB, RocksDB, HBase)

  • Log-Structured Merge-tree: writes always go to an in-memory memtable, then flushed to immutable SSTables on disk
  • SSTables are periodically compacted (merged) in the background
  • Write performance: excellent — all writes are sequential (no random I/O)
  • Read performance: worse — must check memtable + multiple SSTables (bloom filters mitigate this)
  • Space amplification: duplicate keys exist across SSTables until compaction
  • Write amplification is lower than B-trees for write-heavy workloads

Rule of thumb: B-tree for read-heavy mixed workloads. LSM-tree for write-heavy append-mostly workloads (logging, metrics, IoT).

☕ Java Implementation: Consistent Hash Ring + Replication Log 

import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.*;
import java.util.concurrent.ConcurrentSkipListMap;
import java.util.logging.Logger;

/**
 * Consistent hash ring for database sharding.
 * Virtual nodes (vnodes) ensure even distribution even with heterogeneous hardware.
 * Adding/removing a node only moves ~1/N of the keys to adjacent nodes.
 */
public class ConsistentHashRing {

    private static final Logger LOG = Logger.getLogger(ConsistentHashRing.class.getName());
    private static final int DEFAULT_VNODES_PER_NODE = 150; // Twitter uses ~1000

    // Sorted map: hash position → physical node name
    private final ConcurrentSkipListMap<Long, String> ring = new ConcurrentSkipListMap<>();
    private final int vnodesPerNode;

    public ConsistentHashRing(int vnodesPerNode) {
        this.vnodesPerNode = vnodesPerNode;
    }

    public ConsistentHashRing() {
        this(DEFAULT_VNODES_PER_NODE);
    }

    /**
     * Adds a node to the ring with its virtual node positions.
     * Virtual nodes prevent the "hot shard" problem when nodes have
     * unequal data volumes after addition.
     *
     * @param nodeName physical node identifier (e.g., "db-shard-1")
     */
    public void addNode(String nodeName) {
        for (int virtualNodeIndex = 0; virtualNodeIndex < vnodesPerNode; virtualNodeIndex++) {
            long hashPosition = hash(nodeName + "#vnode-" + virtualNodeIndex);
            ring.put(hashPosition, nodeName);
        }
        LOG.info("Added node " + nodeName + " with " + vnodesPerNode + " virtual nodes.");
    }

    /**
     * Removes a node and all its virtual positions.
     * Keys that mapped to this node now map to the next node on the ring.
     *
     * @param nodeName physical node identifier to remove
     */
    public void removeNode(String nodeName) {
        for (int virtualNodeIndex = 0; virtualNodeIndex < vnodesPerNode; virtualNodeIndex++) {
            long hashPosition = hash(nodeName + "#vnode-" + virtualNodeIndex);
            ring.remove(hashPosition);
        }
        LOG.info("Removed node: " + nodeName);
    }

    /**
     * Returns the list of nodes responsible for a given key.
     * The primary node plus (replicationFactor - 1) clockwise neighbors.
     * This is how Cassandra selects its replica set.
     *
     * @param key               the shard key (e.g., userId, orderId)
     * @param replicationFactor number of replicas (typically 3)
     * @return ordered list of node names: [primary, replica1, replica2, ...]
     */
    public List<String> getReplicaNodes(String key, int replicationFactor) {
        if (ring.isEmpty()) {
            return Collections.emptyList();
        }
        long keyHash = hash(key);
        List<String> replicaNodes = new ArrayList<>();
        Set<String> seenPhysicalNodes = new LinkedHashSet<>();

        // Start at the key's position and walk clockwise
        NavigableMap<Long, String> tailMap = ring.tailMap(keyHash);
        Iterator<Map.Entry<Long, String>> ringIterator =
            (tailMap.isEmpty() ? ring : tailMap).entrySet().iterator();

        // Wrap around if needed
        while (seenPhysicalNodes.size() < replicationFactor) {
            if (!ringIterator.hasNext()) {
                ringIterator = ring.entrySet().iterator();
            }
            if (!ringIterator.hasNext()) break;
            String physicalNode = ringIterator.next().getValue();
            seenPhysicalNodes.add(physicalNode);
        }
        replicaNodes.addAll(seenPhysicalNodes);
        return replicaNodes;
    }

    /**
     * MD5 hash → long for ring position.
     * Using MD5 only for distribution (not security).
     */
    private long hash(String input) {
        try {
            MessageDigest digest = MessageDigest.getInstance("MD5");
            byte[] hashBytes = digest.digest(input.getBytes());
            // Take first 8 bytes as a long
            long hashValue = 0;
            for (int byteIndex = 0; byteIndex < 8; byteIndex++) {
                hashValue = (hashValue << 8) | (hashBytes[byteIndex] & 0xFF);
            }
            return hashValue;
        } catch (NoSuchAlgorithmException algorithmException) {
            throw new IllegalStateException("MD5 not available", algorithmException);
        }
    }

    // --- Replication log for leader-follower demo ---

    /**
     * Simplified write-ahead log entry for replication.
     * In production: MySQL binlog, PostgreSQL WAL, MongoDB oplog.
     */
    public record ReplicationLogEntry(long sequenceNumber, String key, String value, long timestampMs) {}

    /**
     * Simulates a replication log (WAL/binlog).
     * Followers apply entries in sequence-number order.
     */
    public static class ReplicationLog {
        private final List<ReplicationLogEntry> logEntries = new ArrayList<>();
        private long sequenceCounter = 0;

        public ReplicationLogEntry append(String key, String value) {
            ReplicationLogEntry entry = new ReplicationLogEntry(
                ++sequenceCounter, key, value, System.currentTimeMillis()
            );
            logEntries.add(entry);
            return entry;
        }

        /** Returns all entries after the given sequence number (for follower catch-up). */
        public List<ReplicationLogEntry> getEntriesAfter(long lastAppliedSequence) {
            return logEntries.stream()
                .filter(entry -> entry.sequenceNumber() > lastAppliedSequence)
                .toList();
        }
    }

    public static void main(String[] args) {
        ConsistentHashRing hashRing = new ConsistentHashRing(150);
        hashRing.addNode("shard-1");
        hashRing.addNode("shard-2");
        hashRing.addNode("shard-3");

        String[] testKeys = {"user:1001", "user:5042", "order:88291", "session:abc123"};
        for (String testKey : testKeys) {
            List<String> replicas = hashRing.getReplicaNodes(testKey, 2);
            System.out.println(testKey + " → primary=" + replicas.get(0) + ", replica=" + replicas.get(1));
        }

        System.out.println("\nAdding shard-4 (only ~25% of keys should move)...");
        hashRing.addNode("shard-4");
        for (String testKey : testKeys) {
            List<String> replicas = hashRing.getReplicaNodes(testKey, 2);
            System.out.println(testKey + " → " + replicas.get(0));
        }
    }
}

⚖️ Trade-off Table

DimensionSQL (PostgreSQL)Wide-Column (Cassandra)Key-Value (DynamoDB)
Write throughput~10K writes/sec (single leader)>1M writes/sec (leaderless)Virtually unlimited (auto-scaling)
Read flexibilityArbitrary joins, aggregationsDenormalized tables per query patternSingle-key or sparse secondary index
ConsistencyACID, strong by defaultTunable (ONE to QUORUM)Eventual by default; strong optional
Operational complexityMedium (replication, failover)High (tuning, compaction, tombstones)Low (fully managed)
Best forFinancial data, inventory, user recordsTime-series, IoT, activity feedsSessions, caching layer, leaderboards
