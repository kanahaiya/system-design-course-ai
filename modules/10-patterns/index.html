Module 10

Resilience & Architecture Patterns

Build systems that stay available under failure: CQRS and event sourcing for scalable reads and auditability, Circuit Breaker and Bulkhead for fault isolation, Sidecar for cross-cutting concerns, and Strangler Fig for safe legacy migration.

⏱️ 35 min read

CQRS: Command Query Responsibility Segregation

CQRS separates the write model (Commands) from the read model (Queries). Commands change state and are handled by the domain model. Queries return data and are served by a separate read model optimised for the specific query pattern — often a denormalised, pre-aggregated view.

Why separate them? The optimal data model for writes (normalised, transactional, domain-rich) is different from the optimal model for reads (denormalised, fast, shaped to the UI). CQRS allows each side to be independently scaled and optimised: the write side can be a relational DB with complex domain logic; the read side can be Elasticsearch or a Redis hash per user.

Event Store: In CQRS with event sourcing, the write model publishes domain events. A separate event projector listens to these events and updates the read model. The event store is the source of truth; read models are derived views that can be rebuilt by replaying events.

CQRS: When to Use vs When to Avoid
Use CQRS whenAvoid CQRS when
Read and write load is very asymmetric (e.g., 100:1 read/write ratio)Domain is simple CRUD — the overhead outweighs benefits
Multiple read models are needed for the same data (mobile, web, analytics)Eventual consistency between read and write model is unacceptable
Write and read scalability requirements differ significantlyTeam lacks experience with event-driven architectures
Audit trail and event replay are business requirementsLow traffic systems where a single DB handles both fine

Event Sourcing: Rebuilding State from Events

Instead of storing the current state of an entity, Event Sourcing stores every event that led to that state. The current state is derived by replaying all events in order from the beginning. An Account entity's balance is not stored — it is calculated from AccountCreated, MoneyDeposited, and MoneyWithdrawn events.

Benefits:

  • Complete audit trail: Every state change is recorded with who did it and when.
  • Temporal queries: "What was the account balance on March 15th?" is answerable by replaying events up to that date.
  • Event replay for projections: Add a new read model at any time by replaying historical events into it.
  • Debugging: Reproduce any bug by replaying the exact event sequence that caused it.

Challenges: Event schema evolution (old events must still be deserializable after schema changes). Replaying a large number of events to reconstruct state — solved with snapshots: periodically persist the current state so replay starts from the latest snapshot, not from the beginning.

Circuit Breaker Pattern

The Circuit Breaker prevents cascading failures: when a downstream service is slow or failing, continuing to send requests wastes resources and delays the caller's failure detection. The Circuit Breaker wraps calls to the remote service and tracks the failure rate.

Three states form a state machine:

  • CLOSED (normal operation): Requests pass through. The circuit monitors the error rate. When it exceeds the threshold (e.g., 50% failures in a 30-second window), the circuit trips to OPEN.
  • OPEN (fail fast): All requests fail immediately with a fallback response — no calls reach the downstream service. The circuit stays open for a configured reset timeout (e.g., 60 seconds). This gives the downstream service time to recover.
  • HALF-OPEN (probe): After the reset timeout, one probe request is allowed through. If it succeeds, the circuit transitions to CLOSED. If it fails, the circuit returns to OPEN and the reset timeout restarts.

Bulkhead Pattern: Thread Pool Isolation

Named after watertight compartments in ships, the Bulkhead pattern isolates failures by assigning separate thread pools (or semaphores) to each dependency. If calls to Service A exhaust their thread pool, Service B's pool is unaffected — the application stays partially available.

Without bulkheads: a slow dependency fills the shared thread pool; all inbound requests queue; the entire application becomes unresponsive. With bulkheads: Service A degrades; the rest of the application continues serving requests.

Implementation options:

  • Thread pool isolation: Each dependency gets a dedicated thread pool. Full fault isolation at the cost of more threads. Hystrix's original approach.
  • Semaphore isolation: Limit concurrent calls with a semaphore. Lower overhead but doesn't protect against thread hangs (the caller's thread is used for the call).

Sidecar Pattern and Strangler Fig Migration

Sidecar

Deploy cross-cutting concerns (observability, mTLS, service discovery, config) as a separate container alongside every application container, rather than embedding them in each service. Benefits: language-agnostic (Node.js service gets the same mTLS sidecar as a Go service), independently upgradable, and no library version skew across services. Istio's Envoy proxy is the canonical sidecar.

Strangler Fig Pattern

Incrementally migrate a legacy monolith to microservices without a risky big-bang rewrite. Named after the strangler fig tree, which grows around and eventually replaces its host:

  1. Place a façade (API gateway or reverse proxy) in front of the monolith.
  2. Extract one bounded context at a time as a new microservice.
  3. Route traffic for the extracted domain to the new service through the façade.
  4. Repeat until the monolith is fully replaced and can be decommissioned.

At each step, both old and new code run in production, allowing gradual traffic shifts (1% → 10% → 100% canary) with easy rollback.

Java Implementation: Circuit Breaker State Machine

/**
 * Thread-safe Circuit Breaker with CLOSED → OPEN → HALF_OPEN → CLOSED
 * state machine. Uses a sliding window for error rate calculation.
 */
public class CircuitBreaker {

    public enum State { CLOSED, OPEN, HALF_OPEN }

    private static final int FAILURE_THRESHOLD_COUNT = 5;
    private static final int SUCCESS_THRESHOLD_IN_HALF_OPEN = 2;
    private static final long OPEN_TIMEOUT_MS = 60_000; // 60 seconds before probing

    private volatile State currentState = State.CLOSED;
    private final AtomicInteger failureCount = new AtomicInteger(0);
    private final AtomicInteger successCountInHalfOpen = new AtomicInteger(0);
    private volatile long openedAtMs = 0L;
    private final Object stateLock = new Object();

    /**
     * Executes the given action through the circuit breaker.
     * Throws CircuitOpenException if the circuit is OPEN.
     * Records success or failure and transitions state accordingly.
     *
     * @param action - the remote call to protect
     * @return the result of the action
     */
    public <T> T execute(Callable<T> action) throws Exception {
        checkStateBeforeCall();

        try {
            T result = action.call();
            recordSuccess();
            return result;
        } catch (Exception callException) {
            recordFailure();
            throw callException;
        }
    }

    /**
     * Checks the current circuit state before allowing a call.
     * CLOSED: allowed. OPEN: blocked (fail fast). HALF_OPEN: one probe allowed.
     */
    private void checkStateBeforeCall() {
        synchronized (stateLock) {
            if (currentState == State.OPEN) {
                long timeSinceOpen = System.currentTimeMillis() - openedAtMs;
                if (timeSinceOpen >= OPEN_TIMEOUT_MS) {
                    // Reset timeout expired — allow one probe request
                    transitionTo(State.HALF_OPEN);
                    successCountInHalfOpen.set(0);
                } else {
                    throw new CircuitOpenException(
                        "Circuit is OPEN. Retry after "
                        + (OPEN_TIMEOUT_MS - timeSinceOpen) + "ms");
                }
            }
            // CLOSED and HALF_OPEN: allow the call to proceed
        }
    }

    /**
     * Records a successful call.
     * In HALF_OPEN: enough successes → transition back to CLOSED.
     * In CLOSED: reset the failure counter.
     */
    private void recordSuccess() {
        synchronized (stateLock) {
            if (currentState == State.HALF_OPEN) {
                int successes = successCountInHalfOpen.incrementAndGet();
                if (successes >= SUCCESS_THRESHOLD_IN_HALF_OPEN) {
                    transitionTo(State.CLOSED);
                    failureCount.set(0);
                    successCountInHalfOpen.set(0);
                }
            } else if (currentState == State.CLOSED) {
                // Successful call in CLOSED state: reduce failure count (sliding window)
                failureCount.updateAndGet(count -> Math.max(0, count - 1));
            }
        }
    }

    /**
     * Records a failed call.
     * In CLOSED: increment failure count; trip to OPEN if threshold exceeded.
     * In HALF_OPEN: probe failed — return to OPEN and restart the timeout.
     */
    private void recordFailure() {
        synchronized (stateLock) {
            if (currentState == State.HALF_OPEN) {
                // Probe failed — not recovered yet
                transitionTo(State.OPEN);
                openedAtMs = System.currentTimeMillis();
            } else if (currentState == State.CLOSED) {
                int failures = failureCount.incrementAndGet();
                if (failures >= FAILURE_THRESHOLD_COUNT) {
                    transitionTo(State.OPEN);
                    openedAtMs = System.currentTimeMillis();
                }
            }
        }
    }

    private void transitionTo(State newState) {
        System.out.println("[CircuitBreaker] Transitioning: "
            + currentState + " → " + newState);
        currentState = newState;
    }

    public State getState() {
        return currentState;
    }

    public static class CircuitOpenException extends RuntimeException {
        public CircuitOpenException(String message) {
            super(message);
        }
    }
}

Why synchronized on state transitions? State transitions must be atomic — checking the state and changing it must not interleave with another thread's read/write. Using volatile alone on currentState prevents stale reads but doesn't prevent race conditions during compound check-then-act operations like "if OPEN and timeout expired, transition to HALF_OPEN".
