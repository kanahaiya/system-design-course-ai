Module 06

Distributed Consensus & Transactions

Deep dive into Raft consensus, distributed locking with Redlock, the fundamental limits of 2PC, and the Saga pattern that powers modern microservices payment flows.

⏱️ 35 min read

Raft Consensus Algorithm

Raft was designed to be more understandable than Paxos while achieving equivalent fault tolerance. It decomposes consensus into three sub-problems: leader election, log replication, and safety.

Leader Election

Every node starts as a Follower. If no heartbeat is received within the election timeout (150–300 ms, randomised), a follower transitions to Candidate and starts a new term. It votes for itself and sends RequestVote RPCs to all peers. A candidate becomes Leader once it receives votes from a majority of the cluster (⌊N/2⌋ + 1).

Randomised timeouts prevent split votes: each node picks a different timeout, so one node usually times out first and wins the election before others start competing.

Log Replication

Once elected, the leader accepts client writes, appends them to its own log, then sends AppendEntries RPCs in parallel to all followers. An entry is committed once a majority acknowledges it. The leader then applies the entry to its state machine and responds to the client. Followers apply entries once they observe the leader's commitIndex advance.

Safety Guarantees

Raft's Election Restriction ensures only candidates with an up-to-date log can win: a candidate's last log term must be ≥ the voter's last log term, and if equal, its log must be at least as long. This prevents any node from winning if it is missing committed entries.

Distributed Locks: Redlock

A single-node Redis lock is fast but fails if that node crashes. Redlock runs across N independent Redis instances (typically 5). The algorithm:

  1. Record the current time in milliseconds.
  2. Attempt to acquire the lock on all N nodes sequentially using SET resource_name random_token NX PX ttl.
  3. The lock is acquired only if at least ⌊N/2⌋+1 nodes succeeded and the total elapsed time is less than the TTL.
  4. The effective lock validity = TTL − elapsed time − clock drift safety margin.
  5. To release, send a Lua script to all nodes: delete the key only if the value matches the random token (prevents releasing another client's lock).

Why a random token? If a client holds the lock and its thread pauses (GC, network lag) past the TTL, another client may acquire it. When the first client wakes and tries to release, the random token check prevents it from deleting the new holder's lock.

Critique (Martin Kleppmann): Redlock does not protect against clock jumps or process pauses longer than the TTL. For strong mutual exclusion, use a fencing token: a monotonically increasing integer from the lock service that storage systems can reject if out of order.

Two-Phase Commit (2PC) and Its Limits

2PC coordinates an atomic commit across multiple participants using a coordinator:

  • Phase 1 – Prepare: Coordinator sends PREPARE to all participants. Each participant locks resources, writes undo/redo logs, then replies YES or NO.
  • Phase 2 – Commit/Abort: If all replied YES, coordinator sends COMMIT; otherwise sends ABORT. Participants apply or revert.
2PC Limitations vs. Saga Trade-offs
Dimension2PCSaga
ConsistencyStrong (ACID)Eventual (BASE)
BlockingBlocks on coordinator failureNon-blocking; compensates
Cross-serviceRequires XA-capable resourcesWorks with any REST/event service
ScalabilityPoor — lock contentionHigh — each step is local tx
Failure recoveryManual intervention if coordinator dies in Phase 2Automatic via compensation
Use caseInternal DB shards (rare)Microservices workflows

The critical flaw: if the coordinator crashes after sending COMMIT to some participants but before others receive it, the system is in an uncertain state. Participants that prepared cannot unilaterally abort or commit—they must wait for the coordinator to recover, potentially blocking for minutes or hours.

Saga Pattern for Distributed Transactions

A Saga is a sequence of local transactions where each step publishes an event or message to trigger the next. If any step fails, it executes compensating transactions in reverse order to undo completed steps.

Two implementation styles:

  • Choreography: Each service listens for events and decides what to do. Simple but hard to track overall saga state.
  • Orchestration: A central Saga Orchestrator drives the workflow, calling each service in sequence and invoking compensations on failure. Easier to reason about and monitor.

CAP Theorem Revisited

CAP states that a distributed system can guarantee at most two of: Consistency, Availability, and Partition Tolerance. In practice, network partitions are inevitable, so the real choice is: when a partition occurs, do you sacrifice C or A?

  • CP systems (HBase, ZooKeeper, etcd): Return an error or timeout rather than serve stale data. Correct for leader election and distributed locks.
  • AP systems (Cassandra, DynamoDB, CouchDB): Continue serving reads/writes but may return stale or conflicting data. Resolve conflicts via last-write-wins or CRDTs.

The more nuanced PACELC model extends CAP: even when there is no partition (P), systems trade off latency (L) vs. consistency (C). For example, DynamoDB defaults to AP but offers strongly consistent reads at higher latency cost—a PACELC tradeoff.

Relating to Saga: Sagas accept eventual consistency — the system is temporarily inconsistent after each step. This is an explicit AP choice that trades atomicity for availability and partition tolerance.

Java Implementation: Saga Orchestrator

The following implementation demonstrates an orchestrator-style Saga for a payment flow with full compensation support. Each step declares its forward action and its compensating action. The orchestrator tracks completed steps and unwinds them on failure.

/**
 * Saga orchestrator for payment flow:
 * 1. Debit account
 * 2. Reserve inventory
 * 3. Create shipment
 * Each step registers a compensating action executed in reverse on failure.
 */
public class PaymentSagaOrchestrator {

    private final PaymentService paymentService;
    private final InventoryService inventoryService;
    private final ShippingService shippingService;

    // Tracks completed steps in order so we can compensate in reverse
    private final Deque<Runnable> compensationStack = new ArrayDeque<>();

    public PaymentSagaOrchestrator(PaymentService paymentService,
                                    InventoryService inventoryService,
                                    ShippingService shippingService) {
        this.paymentService = paymentService;
        this.inventoryService = inventoryService;
        this.shippingService = shippingService;
    }

    /**
     * Executes the full saga. Returns true if all steps succeed.
     * On any failure, compensates already-completed steps in reverse order.
     */
    public SagaResult execute(OrderRequest orderRequest) {
        try {
            // Step 1: Debit the customer account
            String paymentId = executeStep(
                () -> paymentService.debitAccount(orderRequest.getCustomerId(),
                                                   orderRequest.getAmount()),
                () -> paymentService.refundAccount(orderRequest.getCustomerId(),
                                                    orderRequest.getAmount()),
                "DEBIT_ACCOUNT"
            );

            // Step 2: Reserve inventory items
            String reservationId = executeStep(
                () -> inventoryService.reserveItems(orderRequest.getItemIds(),
                                                     orderRequest.getQuantities()),
                () -> inventoryService.releaseReservation(reservationId),
                "RESERVE_INVENTORY"
            );

            // Step 3: Create shipment
            String shipmentId = executeStep(
                () -> shippingService.createShipment(orderRequest.getAddress(),
                                                      reservationId),
                () -> shippingService.cancelShipment(shipmentId),
                "CREATE_SHIPMENT"
            );

            compensationStack.clear(); // All steps succeeded; clear compensation state
            return SagaResult.success(paymentId, reservationId, shipmentId);

        } catch (SagaStepException stepException) {
            // Compensate in reverse order (LIFO via Deque)
            compensate();
            return SagaResult.failure(stepException.getFailedStep(),
                                      stepException.getCause());
        }
    }

    /**
     * Executes a single saga step, registers its compensation, and returns the result.
     * Throws SagaStepException on any failure to trigger compensation.
     */
    private <T> T executeStep(StepAction<T> action,
                                Runnable compensation,
                                String stepName) {
        try {
            T result = action.execute();
            // Register compensation only after successful forward action
            compensationStack.push(compensation);
            return result;
        } catch (Exception cause) {
            throw new SagaStepException(stepName, cause);
        }
    }

    /**
     * Executes all registered compensating actions in reverse order (LIFO).
     * Each compensation is attempted independently; failures are logged but
     * do not prevent subsequent compensations from running.
     */
    private void compensate() {
        while (!compensationStack.isEmpty()) {
            Runnable compensatingAction = compensationStack.pop();
            try {
                compensatingAction.run();
            } catch (Exception compensationError) {
                // Log for manual remediation; do NOT rethrow — keep unwinding
                System.err.println("[SagaOrchestrator] Compensation failed: "
                    + compensationError.getMessage());
            }
        }
    }

    @FunctionalInterface
    interface StepAction<T> {
        T execute() throws Exception;
    }
}

// ── Result type ───────────────────────────────────────────────────
public record SagaResult(boolean success,
                          String failedStep,
                          Throwable cause,
                          String paymentId,
                          String reservationId,
                          String shipmentId) {

    public static SagaResult success(String paymentId,
                                      String reservationId,
                                      String shipmentId) {
        return new SagaResult(true, null, null,
                              paymentId, reservationId, shipmentId);
    }

    public static SagaResult failure(String failedStep, Throwable cause) {
        return new SagaResult(false, failedStep, cause, null, null, null);
    }
}

Why Deque as a stack? ArrayDeque is preferred over Stack (which is synchronized) and gives O(1) push/pop. The LIFO order of compensation mirrors how database transactions undo operations in reverse.
