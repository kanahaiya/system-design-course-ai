Module 00 — Start Here

The RESHADED Framework

A universal 8-step structure for answering any system design question at MAANG companies — in exactly 45 minutes. Master this before touching any individual problem.

⏱️ 30 min read
🎯 Foundation
🏆 Essential — Do this first

🗺️ What is RESHADED?

RESHADED is a mnemonic for the 8 phases every strong system design answer covers. It's not a rigid script — it's a skeleton. The interviewer doesn't care about the letters; they care that you structure your thinking, make trade-offs explicit, and go deep on the hard part. RESHADED ensures you never miss a phase.

Without a framework, most candidates either rush to a high-level diagram without clarifying requirements (fatal) or get lost discussing one component for 30 minutes and never finish the design (also fatal). RESHADED gives you a clock and a map.

RESHADED — 8 Phases in 45 Minutes

⏱️ The 45-Minute Timeline

MAANG system design interviews are 45 minutes. Below is the recommended time allocation. These are guidelines — shift time based on the problem's complexity. But if you're still on Requirements at minute 10, you've already lost.

Phase Time What you're doing Red flag if you…
R — Requirements 3–5 min Ask functional + non-functional requirements. Clarify scope. Pin a scale number. Skip this. You'll design the wrong system.
E — Estimation 3–5 min Back-of-envelope: DAU, QPS, storage, bandwidth. This drives every design choice. Skip this. You can't justify your choices.
S — Schema 3–5 min Sketch the core data model. Pick SQL vs NoSQL. Show key fields and relationships. Over-engineer 10 tables. Show 3–5 core entities.
H — High-level Design 10 min Draw the system: clients → LB → API servers → services → data stores. Use boxes and arrows. Jump here without finishing R and E first.
A — APIs 5 min Define the 3–5 most important endpoints. Include request/response shape. Define 15 endpoints. Scope to the critical path.
D — Deep Dive 10 min Pick the hardest sub-problem and go deep. This is where L5/L6 separates from L4. Stay shallow. This is the most important phase.
E — Evaluate 3 min Identify bottlenecks, single points of failure, and trade-offs you accepted. Only say nice things about your design.
D — Deliver 2 min Summarize, answer follow-up questions, show you can adapt the design. Run out of time before reaching this phase.

❓ R — Requirements 3–5 min

Never start designing before you finish requirements. The single most common failure mode is a candidate who draws a beautiful design for the wrong product.

Functional Requirements

Ask what users can DO. Scope to a core slice — never try to build all of Twitter in 45 minutes. A strong answer picks 2–3 key flows and designs them correctly.

  • What is the primary action users perform? (post, view, search, book, pay)
  • What are the read vs write patterns? (read-heavy? write-heavy?)
  • Is this real-time (feeds, chat) or batch (analytics, reports)?
  • Any important user types? (admin, normal user, celebrity/power user)

Non-Functional Requirements

These drive every architecture decision. Always ask about scale, latency, durability, and availability.

  • Scale: How many daily active users (DAU)?
  • Latency: What's the acceptable p99 latency? (100ms? 1s?)
  • Availability: 99.9%? 99.99%? (8.7 hrs/year vs 52.6 min/year downtime)
  • Consistency: Can users see slightly stale data? (eventual vs strong)
  • Durability: Is data loss acceptable? (payments = never, likes = maybe)
💡
Pro Tip — The Scope Pin
End Requirements with a summary: "To confirm: I'll design X for Y users with Z as the primary constraint. I'll focus on these 3 flows: [A, B, C]. I'm setting aside [D, E] for now — OK to proceed?" This shows structure and gets explicit buy-in before you touch a whiteboard.

🔢 E — Estimation 3–5 min

Back-of-envelope estimation justifies your design choices. Every number you pick later (number of servers, database choice, need for a cache) should trace back to these estimates.

The Standard Estimation Playbook

  • Start with DAU → derive QPS (DAU × avg requests per day / 86,400 seconds)
  • Read:Write ratio → determines caching strategy and replica count
  • Storage per record × total records → how much storage you need
  • Bandwidth → storage × QPS → need for CDN?

Twitter Feed Estimation Example

  • 300M DAU, each user reads feed 5×/day → 1,500M read requests/day → ~17,000 read QPS
  • Each user tweets 0.05×/day → 15M writes/day → ~175 write QPS
  • Read:Write = ~100:1 → cache is essential
  • Tweet: 280 bytes + metadata ~= 500B → 15M × 500B = 7.5 GB/day of new data
  • 5 years storage: 7.5 GB × 365 × 5 ≈ 13.7 TB
⚠️
Key Numbers to Memorize
L1 cache: 1ns | RAM: 100ns | SSD random read: 100µs | HDD seek: 10ms | Network round-trip (same DC): 500µs | 1 MB over 1 Gbps: 10ms | Packet CA→NL: 150ms. These are your latency budget building blocks.

🗃️ S — Schema (Data Model) 3–5 min

Sketch the core data model before drawing any system diagram. The data model often reveals the hardest design challenges — and prevents you from designing a system that can't store what it needs.

SQL vs NoSQL Decision Framework

  • Use SQL when: relationships matter, ACID required (payments, bookings), schema is stable
  • Use NoSQL (Document) when: schema varies, fast reads of full documents (user profiles, catalogs)
  • Use NoSQL (Key-Value) when: simple lookup by ID, ultra-high throughput (sessions, caches)
  • Use NoSQL (Column-family) when: time-series, analytics, wide rows (Cassandra)
  • Use NoSQL (Graph) when: relationship traversal is the core operation (social graphs, recommendations)

Twitter Data Model Example

Schema (SQL) 
-- Core entities for Twitter feed design
-- User table: read-heavy, strong consistency for auth
CREATE TABLE users (
    user_id     BIGINT PRIMARY KEY,
    username    VARCHAR(50) UNIQUE NOT NULL,
    email       VARCHAR(255) UNIQUE NOT NULL,
    follower_count INT DEFAULT 0,
    created_at  TIMESTAMP NOT NULL
);

-- Tweets: write-once, read-many, shard by user_id
CREATE TABLE tweets (
    tweet_id    BIGINT PRIMARY KEY,  -- Snowflake ID (time-sorted)
    user_id     BIGINT NOT NULL,
    content     VARCHAR(280) NOT NULL,
    created_at  TIMESTAMP NOT NULL,
    like_count  INT DEFAULT 0,
    INDEX idx_user_created (user_id, created_at DESC)
);

-- Follows: the social graph — consider graph DB at scale
CREATE TABLE follows (
    follower_id  BIGINT NOT NULL,
    followee_id  BIGINT NOT NULL,
    created_at   TIMESTAMP NOT NULL,
    PRIMARY KEY (follower_id, followee_id)
);

-- Feed cache (Redis, not SQL) — pre-computed per user
-- Key: feed:{user_id}  Value: sorted set of tweet_ids

🏗️ H — High-level Design 10 min

Draw the system. Use boxes (services/stores) and labeled arrows (protocols/data). This is the phase most candidates spend all their time on — don't. You want a clear skeleton in 10 minutes, not a masterpiece that leaves no time for the deep dive.

Standard Components to Consider

  • Clients: Web, Mobile, third-party (source of requests)
  • DNS + CDN: Route and cache static assets / geo-distributed content
  • Load Balancer: Round-robin / least-connections across API servers
  • API Gateway: Auth, rate limiting, routing before services
  • Application Services: Stateless, horizontally scalable
  • Message Queue: Async decoupling for write-heavy flows (Kafka)
  • Cache: Redis / Memcached for read-heavy hot data
  • Primary Database: Source of truth (SQL or NoSQL)
  • Object Storage: Blobs — images, videos, files (S3-compatible)
  • Search Index: Elasticsearch for full-text search
Standard High-Level Architecture Pattern

🔌 A — APIs 5 min

Define the 3–5 most important API endpoints. Include the method, path, key request parameters, and the response shape. This proves your system is actionable and reveals whether your schema can support the operations.

GET /v1/tweets/{tweet_id}

🔬 D — Deep Dive 10 min

This is the most important phase. Pick the single hardest sub-problem in the design and go deep. This is what separates an L5 from an L4 candidate at MAANG.

The hard sub-problem is almost never "how to store data" — it's a consistency challenge, a concurrency issue, an extreme scale problem, or a conflicting requirement.

How to Identify the Hard Sub-Problem

  • Twitter feed: Celebrity fanout problem (Justin Bieber has 100M followers — how do you handle posting?)
  • WhatsApp: Message delivery guarantees when recipient is offline
  • Rate limiter: Distributed rate limiting across 50 nodes without a single point of failure
  • Uber: Matching algorithm that's fair, low-latency, and handles geospatial queries at scale
  • URL shortener: Ensuring uniqueness of 7-char codes at 100M QPS without a lock

Deep Dive Pattern: Twitter Celebrity Fanout

Java — Hybrid Fanout Strategy 
/**
 * Hybrid fanout: push for normal users, pull for celebrities.
 * Celebrity threshold = 1,000,000 followers.
 * Normal users get tweet pre-written to their feed cache.
 * Celebrity tweets are fetched at read time and merged.
 */
public class FanoutService {

    private static final int CELEBRITY_THRESHOLD = 1_000_000;
    private final UserRepository userRepository;
    private final FeedCache feedCache;          // Redis sorted set
    private final FollowGraph followGraph;       // Graph DB or adjacency list in Cassandra

    /**
     * Called asynchronously when a tweet is posted.
     * Decides push vs pull based on follower count.
     *
     * @param tweet the newly created tweet
     */
    public void handleNewTweet(Tweet tweet) {
        long authorFollowerCount = userRepository.getFollowerCount(tweet.getAuthorId());

        if (authorFollowerCount < CELEBRITY_THRESHOLD) {
            fanoutPush(tweet);
        } else {
            // Celebrity tweet: just write to the celebrity's own feed entry.
            // Followers will pull celebrity tweets at read time.
            storeCelebrityTweet(tweet);
        }
    }

    /**
     * Push-based fanout: writes tweet_id into each follower's Redis sorted set.
     * Score = tweet timestamp → enables reverse-chronological retrieval.
     * Done asynchronously via Kafka consumers to handle back-pressure.
     *
     * @param tweet the tweet to fan out
     */
    private void fanoutPush(Tweet tweet) {
        List followerIds = followGraph.getFollowers(tweet.getAuthorId());

        // Batch into Kafka for async processing — don't write to Redis synchronously
        // A pool of consumer workers handles the actual Redis ZADD calls
        for (List batch : partition(followerIds, 1000)) {
            FanoutJob job = new FanoutJob(tweet.getTweetId(), tweet.getCreatedAt(), batch);
            kafkaProducer.send("fanout-jobs", job);
        }
    }

    /**
     * At read time, merges pre-computed feed (normal users' tweets) with
     * celebrity tweets fetched on demand. Merges two sorted streams.
     *
     * @param userId the user requesting their feed
     * @param cursor pagination cursor (tweet_id)
     * @param limit  page size
     */
    public List getFeed(long userId, long cursor, int limit) {
        // Step 1: Get pre-computed feed for normal followees
        List feedTweetIds = feedCache.getRange(userId, cursor, limit * 2);

        // Step 2: Get followed celebrities' recent tweets
        List celebIds = followGraph.getCelebrityFollowees(userId, CELEBRITY_THRESHOLD);
        List celebTweetIds = celebIds.stream()
            .flatMap(celebId -> tweetStore.getRecentTweets(celebId, limit).stream())
            .collect(toList());

        // Step 3: Merge and sort by created_at, take top `limit`
        return mergeSortedByTime(feedTweetIds, celebTweetIds, limit);
    }

    private <T> List<List<T>> partition(List<T> list, int size) {
        List<List<T>> partitions = new ArrayList<>();
        for (int i = 0; i < list.size(); i += size) {
            partitions.add(list.subList(i, Math.min(i + size, list.size())));
        }
        return partitions;
    }
}

⚖️ E — Evaluate 3 min

Self-evaluate your design before the interviewer does. This shows senior engineering maturity. Never present a system as perfect — every design has trade-offs.

The Three Questions to Ask Yourself

  • Single Points of Failure: What breaks if one component goes down? Do you have replicas?
  • Bottlenecks: What component handles the most load? Can it scale? How?
  • Trade-offs Accepted: Where did you choose availability over consistency? Performance over cost?
⚠️
What Not to Say
Don't say "my system can handle any load." Every system has a limit. Say instead: "The current design supports ~X QPS. To go beyond that, I would [shard / add more replicas / use a CDN]. The main trade-off I accepted is [consistency vs availability / cost vs performance]."

🎁 D — Deliver 2 min

Give a 60-second summary of what you built. Then open the floor for questions. Demonstrate that you can adapt the design if requirements change.

"To summarize: I designed a Twitter feed system for 300M DAU. I used a hybrid push/pull fanout with a Redis sorted-set cache for feeds. The main trade-off is eventual consistency on feed delivery — a celebrity's tweet may take a few seconds to appear for all followers. If you wanted strong consistency, I'd trade performance for a pull-only model. Questions?"

🚫 10 Common Mistakes That Kill MAANG Interviews

#MistakeWhat to do instead
1Jumping to the HLD without asking requirementsSpend 3–5 minutes on R first. Always.
2Designing a perfect system (no trade-offs)Name 2 trade-offs you accepted in E phase.
3Talking, not drawingDraw components on a whiteboard/document in real-time as you speak.
4Spending 30 min on HLD, 0 on deep diveFollow the time allocation. Deep dive is the differentiator.
5Saying "I'd use Kafka" without explaining whyJustify every technology choice with a specific requirement it satisfies.
6Using SQL for everything or NoSQL for everythingShow you know when to use each. Use both if appropriate.
7Ignoring the data model entirelyShow 3–5 core entities and their relationships before the HLD.
8Not knowing latency numbersMemorize the latency cheat-sheet in Module 01.
9Staying at the surface during deep diveGo to code/pseudocode level for the hardest sub-problem.
10Defending your design when the interviewer pushes backWelcome challenges. Say "Good point — if that's the constraint, I'd change X to Y."
