Module 08

Observability & Monitoring

Build observable systems using the RED and USE frameworks, instrument distributed traces with OpenTelemetry, define meaningful SLOs, and design alerting that pages on symptoms — not causes.

⏱️ 35 min read

RED Method and USE Method

Two complementary frameworks cover the key dimensions of system health:

RED Method (for request-driven services)

Proposed by Tom Wilkie, RED focuses on the experience of each request:

  • Rate: Requests per second the service is receiving.
  • Errors: Rate of failed requests (5xx, timeouts, explicit error codes).
  • Duration: Distribution of request latency (p50, p95, p99 — not averages).

These three metrics answer: "Is my service doing work, is it doing it correctly, and is it doing it fast enough?" They are user-facing signals and directly map to SLIs.

USE Method (for resources)

Proposed by Brendan Gregg, USE analyses each physical or virtual resource:

  • Utilization: Average time the resource is busy (CPU %, disk I/O %)
  • Saturation: Work the resource cannot service — queue depth, run queue length
  • Errors: Error events (ECC errors, network drops, disk errors)

USE answers "which resource is the bottleneck?" It's applied to every resource: CPU, memory, disks, network interfaces, bus bandwidth. High saturation (not just high utilization) is the early warning sign of degradation.

Distributed Tracing with OpenTelemetry

A distributed trace follows a single request as it propagates across multiple services. It answers "where did the latency come from?" in a microservices call chain.

Core Concepts

  • Trace: The entire end-to-end journey of one request, identified by a unique traceId. Contains all spans from all services that processed the request.
  • Span: A single unit of work within a trace (e.g., one HTTP call, one DB query). Has a start time, duration, service name, operation name, status, and key-value attributes. Spans have parent-child relationships forming a tree.
  • Context Propagation: The traceId and spanId are injected into outgoing HTTP headers (W3C traceparent format) so downstream services can create child spans under the same trace.
  • Baggage: Key-value data attached to a context and propagated across service boundaries (e.g., userId, tenantId). Unlike span attributes, baggage travels with every downstream call — use sparingly as it adds header overhead.

OpenTelemetry Architecture

OpenTelemetry (OTel) is the CNCF standard for vendor-neutral instrumentation. The pipeline: instrumented application → OTel SDK → OTel Collector (batches, transforms, routes) → backend (Jaeger, Zipkin, Grafana Tempo, Datadog). The Collector decouples your code from the specific backend, enabling backend switching without code changes.

Alerting Strategies: Symptom-Based vs Cause-Based

Cause-based alerting fires when a specific component crosses a threshold: "CPU > 80%", "disk > 90%". Problems: too noisy (many causes never become user-visible symptoms), alerts for issues that auto-resolve, and misses novel failure modes.

Symptom-based alerting fires when users are actually experiencing problems: "p99 latency > 2s", "error rate > 1%", "availability < 99.9%". The SRE Google approach: alert on SLO burn rate, which directly measures how fast you're consuming your error budget.

Multi-window burn rate alerts (from the SRE Workbook): use a fast window (1 hour) to detect severe burns and a slow window (6 hours) to catch gradual degradation. Alert only when both windows exceed the threshold, reducing false positives.

Keep a separate cause-based dashboard for diagnosis after a symptom alert fires — but don't page on causes alone.

SLI, SLO, and SLA Definitions

  • SLI (Service Level Indicator): A quantitative measure of service behavior. Example: "the ratio of requests completing in under 200ms." SLIs are measured continuously.
  • SLO (Service Level Objective): The target for an SLI over a time window. Example: "99.5% of requests complete in under 200ms measured over 30 days." SLOs are internal targets used to drive engineering decisions.
  • SLA (Service Level Agreement): A contractual commitment to customers with financial penalties for breach. SLAs are typically set below the SLO to leave headroom.

Error Budgets

An error budget = 100% − SLO target. For a 99.9% availability SLO over 30 days, the error budget is 0.1% = 43.2 minutes of downtime. This budget is the engineering team's licence to take risk (deployments, experiments, infra changes).

When the error budget is consumed: halt non-critical releases, prioritize reliability work. When the budget is healthy: invest in features and experiments. Error budgets create a shared language between SRE and product — reliability vs. velocity is quantified, not subjective.

Burn rate: If you consume 5% of a monthly budget in 1 hour, the burn rate is 5% / (1/720) = 36× — an incident requiring immediate attention. Burn rate alerting (from Google SRE Workbook) is the most actionable alerting strategy.

Java Implementation: OTel Tracing + Error Rate Calculator

// ── OpenTelemetry Span Instrumentation ────────────────────────────

/**
 * Demonstrates manual span creation with OpenTelemetry SDK.
 * Attributes, events, and error recording follow OTel semantic conventions.
 */
public class OrderService {

    private static final Tracer TRACER =
        GlobalOpenTelemetry.getTracer("com.example.order-service", "1.0.0");

    /**
     * Fetches order with full distributed trace instrumentation.
     * Creates a child span under whatever trace context is active (set by
     * the HTTP framework's auto-instrumentation on the incoming request).
     */
    public Order getOrderById(String orderId, String userId) {
        Span span = TRACER.spanBuilder("OrderService.getOrderById")
            .setSpanKind(SpanKind.INTERNAL)
            .startSpan();

        // Make this span the active context so downstream calls create children
        try (Scope scope = span.makeCurrent()) {
            span.setAttribute("order.id", orderId);
            span.setAttribute("user.id", userId);
            span.addEvent("cache-lookup-start");

            Order cachedOrder = orderCache.get(orderId);
            if (cachedOrder != null) {
                span.setAttribute("cache.hit", true);
                return cachedOrder;
            }

            span.setAttribute("cache.hit", false);
            span.addEvent("db-lookup-start");

            Order order = orderRepository.findById(orderId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));

            span.setStatus(StatusCode.OK);
            return order;

        } catch (OrderNotFoundException notFoundException) {
            span.recordException(notFoundException);
            span.setStatus(StatusCode.ERROR, "Order not found: " + orderId);
            throw notFoundException;
        } finally {
            span.end(); // Always end the span; never leave it open
        }
    }
}

// ── Sliding Window Error Rate Calculator ─────────────────────────

/**
 * Computes error rate over a sliding time window using a circular buffer
 * of bucketed counters. Avoids storing individual request records.
 *
 * Example: 10 buckets × 6-second duration = 60-second sliding window.
 */
public class SlidingWindowErrorRateCalculator {

    private static final int DEFAULT_BUCKET_COUNT = 10;
    private static final long DEFAULT_BUCKET_DURATION_MS = 6_000; // 6 seconds per bucket

    private final int bucketCount;
    private final long bucketDurationMs;
    private final long[] totalRequestCounts;
    private final long[] errorRequestCounts;
    private final long[] bucketTimestamps;
    private int currentBucketIndex = 0;

    public SlidingWindowErrorRateCalculator() {
        this(DEFAULT_BUCKET_COUNT, DEFAULT_BUCKET_DURATION_MS);
    }

    public SlidingWindowErrorRateCalculator(int bucketCount, long bucketDurationMs) {
        this.bucketCount = bucketCount;
        this.bucketDurationMs = bucketDurationMs;
        this.totalRequestCounts = new long[bucketCount];
        this.errorRequestCounts = new long[bucketCount];
        this.bucketTimestamps = new long[bucketCount];
    }

    /**
     * Records the outcome of a single request into the current time bucket.
     * Advances to a new bucket if the current one has expired.
     */
    public synchronized void recordRequest(boolean isError) {
        long currentTimeMs = System.currentTimeMillis();
        advanceBucketIfExpired(currentTimeMs);
        totalRequestCounts[currentBucketIndex]++;
        if (isError) {
            errorRequestCounts[currentBucketIndex]++;
        }
    }

    /**
     * Returns the error rate (0.0–1.0) across all valid buckets in the window.
     * Returns 0.0 if no requests have been recorded yet.
     */
    public synchronized double getErrorRate() {
        long windowTotalRequests = 0L;
        long windowErrorRequests = 0L;
        long cutoffTimeMs = System.currentTimeMillis() - (bucketCount * bucketDurationMs);

        for (int bucketIndex = 0; bucketIndex < bucketCount; bucketIndex++) {
            if (bucketTimestamps[bucketIndex] > cutoffTimeMs) {
                windowTotalRequests += totalRequestCounts[bucketIndex];
                windowErrorRequests += errorRequestCounts[bucketIndex];
            }
        }
        return windowTotalRequests == 0 ? 0.0
            : (double) windowErrorRequests / windowTotalRequests;
    }

    private void advanceBucketIfExpired(long currentTimeMs) {
        long bucketAge = currentTimeMs - bucketTimestamps[currentBucketIndex];
        if (bucketAge >= bucketDurationMs) {
            currentBucketIndex = (currentBucketIndex + 1) % bucketCount;
            // Clear the new bucket before writing to it
            totalRequestCounts[currentBucketIndex] = 0;
            errorRequestCounts[currentBucketIndex] = 0;
            bucketTimestamps[currentBucketIndex] = currentTimeMs;
        }
    }
}

Why a circular buffer? Storing individual request records would require unbounded memory proportional to request rate. Bucketing into fixed-size time slots gives O(1) memory regardless of traffic volume, and O(N) error rate calculation where N is the small bucket count.
